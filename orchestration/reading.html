Pi 오케스트레이션

pi 코딩 에이전트로 역할을 나누고, 모델 크기를 역할에 맞춰 배분하고, 검증을 다른 모델에 맡기는 사내용 구조. 실행은 pi-subagents 가 맡고, 이 폴더는 사내 조건에 맞춘 배선만 담는다.

왜 필요한가 (Why)

에이전트 하나에 큰 일을 통째로 맡기면 두 군데서 무너진다. 컨텍스트가 먼저 넘치고, 그 다음 검증이 사라진다. 자기가 쓴 코드를 자기가 통과시키기 때문이다.

쪼개면 두 문제가 같이 풀린다. 다만 쪼갠 뒤에 새 문제가 생긴다 — 누가 무엇을 하는지, 결과를 어떻게 걷는지, 동시에 같은 파일을 고치면 어떻게 되는지.

이 셋을 처리하는 기계 장치는 이미 사내에 설치된 pi-subagents 가 갖고 있다. pi 본체는 서브에이전트를 일부러 넣지 않았고, 이 기능은 확장 패키지가 맡는다. 자식 세션 격리, 역할 정의, 도구 allowlist, 병렬 팬아웃, 결과 수집, 자식→부모 에스컬레이션이 전부 들어 있다. 새로 만들 이유가 없다.

그래서 이 폴더가 실제로 더하는 것은 사내 조건 세 가지뿐이다.

  1. 외부 LLM API를 못 쓴다 → 사내 HCP 게이트웨이를 pi에 등록해야 한다.
  2. 크기가 다른 모델 세 개가 있다 → 어느 역할에 어느 크기를 물릴지 정해야 한다.
  3. 외부로 나가면 안 된다 → 웹 검색 역할과 외부 CLI(Claude Code, Codex, Cursor)를 부르는 역할을 꺼야 한다.

이 구조가 업계에서 확인된 패턴 중 어디에 해당하는지는 에이전틱 코딩 문서에 정리했다. 요약하면 쓰기는 한 줄기로, 읽기와 검토는 나눠서다.

핵심 개념 (What)

설계 결정

1. 모델 티어링이 전부다. 판단에는 큰 모델, 양산에는 중간 모델, 읽고 추리는 일에는 작은 모델. 비용 절감은 모델 가격·재시도·태스크 성공률에 따라 달라지며 이 구성에서 실측하지 않았다. pi-subagents 는 subagents.agentOverrides.<역할>.model 로 역할마다 모델을 못박게 해준다.

2. 검증은 다른 세션·다른 모델이 한다. 리뷰어를 워커와 다른 모델로, fresh context 로 띄운다. 한 에이전트의 환각이 다음 단계에서 사실로 굳는 연쇄를 여기서 끊는다.

모델 ID가 다르다고 오류가 독립적이지는 않다. Big·Medium 은 둘 다 GLM 계열이라 같은 착각을 공유할 수 있다. 별칭(HCP-*-Latest)만 보면 계열이 안 보이므로 실제 모델을 확인해야 한다. 독립성의 실질은 모델 이름이 아니라 ① 새 컨텍스트 ② 워커 보고가 아닌 코드를 직접 읽는 것 ③ 검증 명령을 직접 다시 돌리는 것 에서 나온다. 리뷰어 프롬프트가 이 셋을 요구해야 의미가 있다.

빌트인 reviewer 에는 bash 가 없고, 프롬프트도 셸 사용을 금지한다. 0.81 기준 빌트인 프롬프트는 "셸 명령을 쓰지 말고, 돌려야 할 테스트 명령은 보고만 하라"고 지시한다. 이대로면 워커 보고를 글로만 대조하게 되고, 게이트의 절반이 사라진다. 그래서 이 설정은 reviewer 의 tools 에 bash 를 되돌려주고, systemPrompt 도 덮어써 검증 명령을 직접 재실행하게 한다. 도구만 주고 프롬프트를 그대로 두면 모델은 금지 지시를 따른다. 이 폴더가 내용을 고쳐 쓰는 유일한 역할 정의다.

3. 동시 쓰기는 파일 경계로 막는다. oracle 이 파일이 겹치지 않게 쪼갠다. 겹침을 피할 수 없으면 워커마다 별도 워크트리를 준다.

4. 사내 경로를 벗어나는 역할은 끈다. 빌트인 researcher 와 evidence-auditor 는 web_search / fetch_content 로 바깥에 나간다. 0.75 이후 들어온 claude-code·codex-exec·cursor-agent(각각 -writer 포함)는 pi가 아니라 외부 CLI를 실행해서, 사내 게이트웨이 설정이 적용되지 않는다. delegate 는 edit 을 가진 다섯 번째 쓰기 역할인데 역할별 모델 제한이 없다. 사내에서는 이 아홉 개를 disabled: true 로 끈다. 끄는 것은 라우팅 정책이지 네트워크 차단이 아니다.

역할과 모델 배정

빌트인 역할을 그대로 쓰고, 모델과 thinking 을 사내 티어로 배정한다.

agentOverrides 는 기본 배정일 뿐 경계가 아니다. 런당 override(/run reviewer[model=...])가 더 우선한다. 티어를 실제로 강제하려면 modelScope(enforce/strict)가 필요하고, 설정 스니펫에 함께 넣어 뒀다.

빌트인 역할 모델 thinking 도구 하는 일
oracle my-local-provider/HCP-Big-Latest high 읽기 + bash 판단·분해·드리프트 감시
worker my-local-provider/HCP-Medium-Latest high 전체 (edit 포함) 구현, 검증 명령 실행
reviewer my-local-provider/HCP-Big-Latest high 읽기 + bash(덮어씀) + write diff 검토, 검증 재현, 판정
scout itc-vlm/qwen3.8-27b low 읽기 + bash + write 전수 검색, 선별, 목록화
researcher / evidence-auditor — — — 꺼둔다 (웹 검색)
claude-code·codex-exec·cursor-agent 계열 6개 — — — 꺼둔다 (외부 CLI)
delegate — — — 꺼둔다 (모델 제한 없는 쓰기 역할)

별칭은 다섯이지만 실제 모델은 넷이다. 별칭 뒤의 모델이 계열을 결정하므로 같이 적어 둔다.

모델 실제 모델 context / maxTokens 이 구성에서의 자리
my-local-provider/HCP-Big-Latest GLM-5.3 1,048,574 / 1,048,574 판단(oracle) · 검증(reviewer)
my-local-provider/HCP-Medium-Latest GLM-5.3-flash 1,048,574 / 1,048,574 구현(worker) · watchdog
my-local-provider/HCP-Small-Latest Qwen3.6-35B-A3B 262,144 / 262,144 배정 없음. scout 의 빠른 대안
my-local-provider/HCP-Vision-Latest Qwen3.6-35B-A3B (이미지 입력) 262,144 / 262,144 배정 없음. Small 과 같은 모델 + 이미지
itc-vlm/qwen3.8-27b Qwen3.8 27B 262,144 / 32,768 정찰(scout) · reviewer 교차 검증

scout 에 HCP-Small-Latest 가 아니라 qwen3.8-27b 를 쓰는 이유. A3B 는 총 35B 중 토큰당 활성 파라미터가 3B 라는 뜻이다. 활성 파라미터가 적어 계산량 감소를 기대할 수 있지만 실제 처리량은 엔진·하드웨어·배치에 따라 측정해야 한다. scout 의 실패 모드는 속도가 아니라 호출부 누락이다. scout 이 호출 지점을 하나 빠뜨리면 그 뒤 모든 워커가 잘못된 범위를 공유하고, 무인 야간 실행이면 그대로 밤 하나를 날린다. scout 은 전체의 한 단계일 뿐이고 물량은 worker 가 지므로, 정찰이 한 번 느린 비용보다 한 번 놓친 비용이 크다.

물량이 많아 처리량이 급하면 런당 교체한다. modelScope 에 둘 다 열어 뒀다.

/run scout[model=my-local-provider/HCP-Small-Latest] "..."

qwen3.8-27b 를 reviewer 교차 검증에도 쓰는 이유. Big·Medium 은 둘 다 GLM 계열이라 같은 착각을 공유할 수 있다. qwen 은 계열이 다르므로 영향이 큰 변경에 2차 의견으로 값이 있다.

/run reviewer[model=itc-vlm/qwen3.8-27b] "이 diff 를 다시 검증해라. 앞선 리뷰 결과는 보지 마라."

다만 27B 는 Big 보다 판단이 약하므로 주 게이트가 아니라 2차 의견으로만 쓴다. 출력 상한이 32,768 로 다른 모델보다 낮은 것도 감안한다 — scout 의 긴 목록에는 충분하지만 장문 산출에는 좁다.

HCP-Small-Latest 와 HCP-Vision-Latest 는 같은 모델이다. Vision 쪽이 이미지 입력을 받는다는 당시 구성 설명이다. 실제 가중치·템플릿·샘플링이 같은지는 미확인이라 텍스트 품질이 같다고 보장하지 않는다. 그래서 스크린샷을 읽혀야 하면 모델을 바꾸는 것이 아니라 같은 모델의 이미지 입구를 쓰는 것이고, 판단 품질의 동일성은 별도 평가가 필요하다.

코딩 오케스트레이션에서 상시로 쓸 일은 없어 역할에 배정하지 않았다. UI 버그 스크린샷이나 캡처한 문서를 읽혀야 할 때만 런당 지정한다. scout 의 allow 에 함께 넣어 뒀다.

/run scout[model=my-local-provider/HCP-Vision-Latest] "이 스크린샷의 에러 메시지를 읽고 해당 코드를 찾아라"

다만 활성 파라미터가 3B 라는 점은 이미지에서도 같다. 캡처 문서 추출처럼 정확도가 중요한 작업에 이 모델을 그대로 쓰는 것이 맞는지는 별도로 판단할 일이다.

worker 만 edit 을 가진다. 나머지 역할은 allowlist 에서 edit 을 뺐다.

다만 이것은 읽기 전용이 아니다. 정확히 하자면:

  • write 는 기존 파일도 덮어쓸 수 있다. edit 을 뺀다고 파일이 보호되지 않는다.
  • bash 를 가진 역할(oracle·reviewer·scout)은 셸로 수정·삭제·네트워크 호출이 모두 가능하다.
  • 특히 reviewer 가 워커의 검증 명령을 재실행하면 워커가 방금 바꾼 테스트·스크립트가 실행된다. pytest 나 npm test 를 허용한다는 것은 그 안의 임의 코드를 허용한다는 뜻이다.
  • researcher·evidence-auditor 를 끄는 것도 외부 전송 차단이 아니다. bash 가 있으면 나갈 수 있다.

allowlist 는 기본값을 정하는 장치이지 경계가 아니다. 진짜 경계가 필요하면 컨테이너/VM 격리가 필요하다 — oneshot.md 의 "워크트리는 격리가 아니다" 참고.

어떻게 사용하는가 (How)

1. 사내 모델 등록 (이미 돼 있으면 확인만)

~/.pi/agent/models.json 에 my-local-provider 와 itc-vlm 두 provider 가 이미 등록돼 있다면 이 단계는 건너뛰고 smoke.sh -l 0 으로 확인만 한다.

새 모델을 추가할 때 걸리는 곳은 셋이다.

  • 최상위는 {"providers": {...}} 다. provider 를 바로 올리면 must have required properties providers 로 파일 전체가 무시되고 모델이 하나도 안 보인다.
  • apiKey 와 headers 는 $ENV_VAR 치환이 되고 !command 도 된다. baseUrl 은 치환이 안 된다 — 실제 URL 문자열을 넣어야 한다.
  • contextWindow / maxTokens / thinkingLevelMap 은 게이트웨이가 실제로 받아주는 값과 맞춰야 한다. 목록에 보이는 것과 긴 출력·thinking 요청이 성공하는 것은 별개다. smoke.sh -l 2 로 확인한다.

2. 역할별 티어 배선

설정이 두 파일로 나뉜다. 키를 엉뚱한 파일에 넣으면 오류 없이 조용히 무시되니 주의한다.

파일 넣을 것
~/.pi/agent/settings.json settings.snippet.json 내용 — pi 코어의 defaultModel(부모 세션 모델), httpIdleTimeoutMs, 그리고 subagents.defaultModel(자식 기본값), agentOverrides, modelScope, watchdog
~/.pi/agent/extensions/subagent/config.json subagent-config.snippet.json 내용 — timeoutMs, toolTimeoutMs, asyncByDefault

agentOverrides 의 description 은 영어로 쓴다. 취향 문제가 아니라, 이 문자열이 subagent({ action: "list" }) 출력에 실려 부모가 어떤 역할을 쓸지 판단할 때 읽는 텍스트이기 때문이다. 빌트인 역할 설명이 전부 영어라 한글을 섞으면 같은 목록에서 언어가 갈리고, Windows 콘솔에서 깨질 여지도 생긴다. 같은 이유로 운영자용 메모를 여기 쓰지 않는다 — "물량이 급하면 다른 모델로 바꿔라" 같은 문장은 사람이 읽을 내용인데, 모델 컨텍스트에 들어가면 모델이 스스로 모델을 교체해야 한다고 읽을 수 있다. 역할 구분에 필요한 것만 남긴다.

bash·python 을 돌릴 수 있으면 손으로 합치지 말고 merge-settings.py 를 쓴다. (사내 PC 처럼 스크립트 실행이 번거로우면 office-setup.md 의 PROMPT-2 로 한다.) 기존 키를 보존하면서 깊은 병합을 하고, 바뀔 값을 먼저 전부 보여준 뒤 --apply 를 줄 때만 기록한다. 대상 파일은 .bak 으로 백업된다.

# 1) 미리보기 - 무엇이 추가되고 무엇이 덮어써지는지만 본다
python merge-settings.py settings.snippet.json ~/.pi/agent/settings.json
python merge-settings.py subagent-config.snippet.json ~/.pi/agent/extensions/subagent/config.json

# 2) 확인했으면 적용
python merge-settings.py settings.snippet.json ~/.pi/agent/settings.json --apply
python merge-settings.py subagent-config.snippet.json ~/.pi/agent/extensions/subagent/config.json --apply

PowerShell 에서도 그대로 쓴다 (~ 대신 $HOME).

python .\orchestration\merge-settings.py .\orchestration\settings.snippet.json $HOME\.pi\agent\settings.json
python .\orchestration\merge-settings.py .\orchestration\subagent-config.snippet.json $HOME\.pi\agent\extensions\subagent\config.json

덮어씀 항목은 기존 값이 사라진다는 뜻이니 반드시 확인한다. 특히 defaultModel 을 이미 다른 모델로 쓰고 있었다면 그 값이 바뀐다. 없는 디렉터리·파일은 알아서 만든다. 같은 스니펫을 두 번 병합하면 변경이 없을 수 있다. 동시 편집·기록 중 장애·백업 덮어쓰기의 안전성을 보장하지 않으며, 깨진 대상 JSON은 덮어쓰기 전에 멈춘다. 생략한 키는 삭제하지 않는다.

저장소 단위로만 적용하려면 settings 쪽 대상 경로를 그 저장소의 .pi/settings.json 으로 바꾼다 (프로젝트 설정이 사용자 설정을 이긴다).

사내 세팅은 office-setup.md 의 프롬프트를 pi 에게 시켜서 한다. 각 프롬프트에 PROMPT-1 ~ PROMPT-7 번호가 붙어 있어 "office-setup.md 의 PROMPT-4 를 실행해라" 처럼 지시하면 된다.

PROMPT-2 settings.json 병합
PROMPT-3 extensions/subagent/config.json 생성
PROMPT-4 설정 검증 15항목

붙여넣을 JSON 이 문서에 그대로 박혀 있어 모델이 값을 지어낼 여지가 없고, 단계마다 성공 판정과 보고 항목이 정해져 있다. PROMPT-4 가 핵심이다 — 지금까지 실제로 발목을 잡은 함정 12가지를 항목별로 검사한다. 전부 오류 없이 조용히 무시되는 종류라 눈으로는 안 보인다.

2-1. 스크립트로 검증할 수 있으면 (smoke.sh)

배선이 맞았는지는 눈으로 보지 말고 돌려서 확인한다. 계층이 올라갈수록 비싸므로 아래에서부터 쓴다.

./orchestration/smoke.sh -l 0     # 설정만. LLM 호출 0회, 비용 0
./orchestration/smoke.sh          # L0 + 모델 3종 연결 (기본)
./orchestration/smoke.sh -l 2     # + 도구 호출 검증
./orchestration/smoke.sh -l 3     # + 서브에이전트 왕복. 첫 세팅 때 1회
./orchestration/smoke.sh -l 0 -v  # 실패 원인 상세
계층 보는 것 비용
L0 models.json 구조·baseUrl·apiKey, 역할 4종 배정, thinking 레벨 유효성, modelScope ↔ 역할 배정 교차 검증, watchdog, 런타임 상한이 맞는 파일에 있는지, 모델 3종 등록 0
L1 역할/대안 목록의 게이트웨이 연결·인증·compat (모델당 1회) 목록 크기에 따라 달라짐
L2 숫자 출력 확인; 실제 도구 호출은 transcript 추가 확인 목록 크기에 따라 달라짐
L3 부모가 자식을 띄우고 결과가 돌아오는지 수 회

L0 이 실패하면 위 계층은 돌리지 않는다. 설정 오류로 낭비할 호출이 없다.

L0 이 잡아내는 것 중 눈으로는 안 보이는 것들:

  • models.json 최상위 providers 래퍼 누락 → 파일 전체가 조용히 무시된다
  • thinking 레벨이 그 모델에서 미지원 → 오류 없이 다른 레벨로 바뀐다. 판정 규칙은 셋이다.
  • reasoning 이 없거나 false → off 하나만 지원. 다른 값을 주면 thinking 이 통째로 꺼진 채 돈다
  • reasoning: true 인데 thinkingLevelMap 이 없으면 → off~high 지원, xhigh·max 만 미지원 (정상)
  • thinkingLevelMap 이 있으면 → 값이 null 인 레벨이 미지원
  • modelScope.agents.<역할>.allow 가 그 역할의 배정 모델과 어긋남 → 그 역할이 항상 실패한다
  • agentOverrides 가 가리키는 모델이 models.json 에 없음 (오타·provider 혼동)
  • tools 를 "read, grep, bash" 같은 쉼표 문자열로 씀 → 빌트인 frontmatter 는 이 표기를 받지만 settings.json 은 배열만 받는다. 같은 필드명이라도 담는 파일이 다르면 형식이 다르다
  • 에이전트별 allow 에 넣은 대안 모델이 전역 allow 에 없음 → 에이전트 규칙은 전역을 완화하지 못하므로 쓰는 순간 거부된다
  • timeoutMs 를 settings.json 에 넣음 → 오류 없이 무시된다
  • apiKey 평문 하드코딩

Windows PowerShell 에서 돌릴 때

smoke.sh 는 bash 스크립트라 PowerShell 에서 바로 실행되지 않는다. 셋 중 하나를 쓴다.

# 1) Git for Windows 가 있으면 (가장 흔함)
& "C:\Program Files\Git\bin\bash.exe" ./smoke.sh -l 0

# 2) WSL 이 있으면
wsl ./smoke.sh -l 0

# 3) Git Bash 를 열어서 평소처럼
./smoke.sh -l 0

한글이 깨져 보이면 콘솔 코드페이지 문제다. 스크립트 출력은 UTF-8 인데 Windows 콘솔은 기본이 949(한국어)라 그대로 읽으면 깨진다. 스크립트가 Git Bash/MSYS 에서 실행되면 알아서 chcp 65001 을 걸지만, PowerShell 에서 직접 돌리거나 그래도 깨지면 아래를 먼저 실행한다.

chcp 65001
[Console]::OutputEncoding = [System.Text.Encoding]::UTF8
$OutputEncoding = [System.Text.Encoding]::UTF8

매번 치기 싫으면 PowerShell 프로필에 넣는다.

notepad $PROFILE      # 없으면: New-Item -Path $PROFILE -ItemType File -Force
# 위 세 줄을 붙여넣고 저장, 새 창에서 적용

Git Bash 를 쓰는데도 깨지면 터미널 글꼴이 한글을 못 그리는 경우다. D2Coding, Malgun Gothic, Cascadia Mono 중 하나로 바꾼다 (Git Bash: 창 우클릭 → Options → Text → Font).

python3 가 아니라 python 만 있는 환경이 흔해서, 스크립트가 python3 → python → py 순으로 찾아 Python 3 인 것만 쓰도록 해 뒀다. 셋 다 없으면 거기서 멈춘다.

Windows의 timeout.exe는 GNU timeout과 다른 대기 명령이다. 아래 PowerShell 예제는 여러 줄 prompt 인자 전달·자식 종료를 검증하지 않았으므로 적용 전에 검토 보충의 한계를 확인한다.

$prompt = Get-Content .\oneshot-prompt.txt -Raw
$p = Start-Process pi -ArgumentList '-p', $prompt -PassThru -NoNewWindow
Wait-Process -Id $p.Id -Timeout 28800 -ErrorAction SilentlyContinue   # 8시간
if (-not $p.HasExited) { Stop-Process -Id $p.Id -Force }

그리고 Windows 에서 무인 실행을 할 거면 smoke.sh -l 3 을 반드시 한 번 돌린다. pi-subagents 의 백그라운드 자식 실행은 공식 검증 대상이 Linux x64 이고 Windows 는 실험 단계로 표기돼 있다. npm 으로 설치한 pi 는 Node 러너를 쓰므로 일반 경로지만, 검증 매트릭스에 없다는 사실은 그대로다. 포그라운드(asyncByDefault: false)로 쓰는 편이 안전하다.

3. 런북

pi-subagents 는 부모 pi 세션이 오케스트레이터다. 자연어로 지시하면 부모가 subagent 도구를 호출한다.

기본 루프 — 패키지가 권장하는 순서이자 이 설계와 같은 모양이다.

clarify → scout → worker → fresh reviewer → worker

scout 으로 <경로> 아래에서 <대상> 관련 파일을 찾아줘. 그 밖은 뒤지지 마.
worker 로 <작업>을 구현해줘. 끝나면 reviewer 를 띄워서 검증 명령을 직접 다시 돌리게 하고, 지적이 있으면 worker 에게 되돌려줘.

정확성·테스트·불필요한 복잡도를 각각 보는 리뷰어를 동시에 띄우고 결과를 합친다.

결정적 파이프라인이 필요할 때 — 부모 모델의 판단에 맡기지 않고 순서를 고정하려면 workflowScript 를 쓴다. runs.all([{ key, agent, task }, ...]) 가 팬아웃이고, 결과는 순서대로 배열로 돌아온다.

3-1. 사내 규칙은 작업 저장소의 AGENTS.md 에 둔다

"배정된 파일 밖 수정 금지", "git add -A 쓰지 말 것", "검증 명령을 지어내지 말 것" 같은 규칙의 제자리가 거기다. 원샷 프롬프트에만 적으면 대화형으로 쓸 때는 자식에게 전달되지 않는다. 넣을 내용은 agents-md.snippet.md 에 있다.

자식은 스킬을 상속하지 않으므로(inheritSkills: false) 스킬에 의존하는 규칙은 쓰지 않는다.

속도 제한 (RPM / TPM)

사내 게이트웨이는 분당 500,000토큰, 50요청으로 묶여 있다. 에이전트는 매 요청에 지금까지의 대화를 (압축 후 남은 만큼) 다시 보내므로, 요청 하나가 10,000토큰을 넘는 순간부터는 요청 수가 아니라 토큰 수가 먼저 찬다. 코딩 에이전트는 거의 항상 그렇다. 계산 방법, 자식 수 정하는 공식, 측정 스크립트, 재시도 설정, 운영팀 확인 목록은 속도 제한 아래에서 오케스트레이션하기에 따로 정리했다. 집에서 구독 요금제(5시간 창)로 쓸 때의 차이도 같은 문서에 있다.

요점만 옮기면 이렇다.

  • pi에는 분당 토큰·요청 제한기가 없다. 아래 값은 "몇 개를 띄울지"를 정할 뿐이다. 다른 pi 세션과 다른 harness는 서로의 사용량을 모른다.
  • 동시성보다 자식의 컨텍스트 크기와 요청 주기가 먼저다. 요청당 60K 토큰이면 분당 8번이 한계다. 자식 하나가 30초마다 요청하면 둘까지, 10초마다면 하나도 벅차다.
  • 게이트웨이가 캐시 적중 토큰을 세는지 먼저 확인한다. 에이전트 요청은 대부분이 캐시 적중이라, 이 답에 따라 같은 작업의 집계량이 몇 배씩 달라진다.
  • 재시도는 두 층이 곱해진다. 현재 값이면 생성 하나에 최악 35번 요청이 나간다.
설정 파일 기본값 이 구성 왜
globalConcurrencyLimit config.json 20 2 한 실행 안에서 동시에 도는 자식 수
parallel.concurrency config.json 4 2 병렬 그룹의 동시 실행 수
maxActiveAsyncRunsPerSession config.json 무제한 1 동시에 도는 최상위 비동기 실행 수
maxSubagentSpawnsPerRun config.json 64 12 한 실행에서 띄울 수 있는 자식 총량. 폭주 방지
retry.maxRetries settings.json 3 6 429 는 정상적으로 발생한다. 재시도로 넘긴다
retry.baseDelayMs settings.json 2000 8000 2초 후 재시도는 분당 한도에서 다시 429 를 부른다
retry.provider.maxRetries settings.json 0 4 HTTP 계층 재시도. Retry-After 헤더를 따른다

스니펫은 업무 중(대화형) 기준이다. 무인 실행 값과 프로필별 예산은 속도 제한 문서에 있다.

watchdog 이 숨은 소비자다. 턴 경계마다 별도 모델 호출이 들어가고, 이 호출은 세션 로그에 사용량이 남지 않는다. 그래서 cadence 는 끄고 경계 검토만 남겼고, 자식 watchdog 은 아예 껐다. 자식의 품질 통제는 watchdog 이 아니라 reviewer 게이트가 맡는다.

알아둘 동작

  • 모델 해석 우선순위: 런당 override → provider별 역할 override → agentOverrides.<역할>.model → 에이전트 frontmatter → subagents.defaultModel → 부모 세션 모델.
  • agentOverrides 로 덮어쓸 수 있는 필드에 tools, thinking, model, description, disabled, systemPrompt 가 포함된다. 역할 파일을 통째로 복사할 필요가 없다.
  • 빌트인을 통째로 고쳐야 하면 subagent({ action: "eject", agent: "reviewer" }) 로 사용자 디렉터리에 복사본을 꺼낸다.
  • 사용자 역할은 ~/.pi/agent/agents/**/*.md, 프로젝트 역할은 .pi/agents/**/*.md 에 둔다.
  • 0.79 이후 같은 Pi 프로세스에서 세션을 넘겨받아도 이전 세션의 백그라운드 실행을 보고, 기다리고, 멈출 수 있다. 끝난 워커를 한 번 더 돌리는 재개도 된다.
  • /subagents-doctor 가 설치·설정·비동기 용량을 한 번에 점검한다. smoke.sh 와 겹치지만 패키지가 직접 보는 값이라 같이 본다.
  • 새 세션에서 subagent 도구 대신 subagents_enable 만 보일 수 있다(toolActivation: "auto"). 모델이 대화 중 도구 추가를 지원하면 필요할 때 켜는 방식이다. 배선 오류가 아니며, 먼저 subagents_enable 을 부르면 된다.
  • 작업 시간 상한 직전에 "정리하고 멈춰라" 신호를 주는 checkpointBeforeDeadlineMs 가 있다. 단 비동기 단일 실행에만 걸리고, 도구 호출 경계에서만 전달되는 최선 노력 기능이다. 기본 포그라운드 경로는 보호하지 않는다.
  • 자식 도구 권한(permissions: allow/ask/deny)은 선택 기능이다. ask 는 자식 watchdog 모델이 판정하는데, 이 설정은 자식 watchdog 을 꺼 두었으므로 ask 는 전부 거부된다. bash 는 이 기능으로 막을 수 없다.
  • pi --list-models <이름> 은 못 찾으면 No models matching "이름" 이라고 답한다. 안내문에 검색어가 그대로 들어 있어서 단순 grep으로 존재 확인을 하면 항상 통과한다. 표의 provider·model 열로 대조해야 한다.

퇴근 원샷 (무인)

달라지는 것은 셋뿐이다.

  1. 결정을 미리 위임한다 — .orch/decisions.md 에 A(미리 승인) / B(기본값 규칙) / C(자가 판단 금지) 3단 정책을 써둔다. 자식이 막히면 부모가 이 파일을 근거로 답한다. 스스로 정한 것은 전부 .orch/결정로그.md 에 되돌리는 법까지 남긴다.

판정은 하드가드 → D → C → A → B 순서로만 한다. D(사람이 미리 구체적으로 답한 것)가 C보다 앞인 이유는, C는 "사람에게 물어라"는 뜻이고 D는 이미 물어서 받은 답이기 때문이다. A를 먼저 보면 "기존 패턴 따르기(A)"인 동시에 "인증 로직 변경(C)"인 변경이 승인되어 버린다.

세 모드가 실제로 다른 지점은 C 목록의 적용 범위다. 보수는 전체를 멈추고, 균형은 그 단위만 멈추고, 자율은 C를 하드 가드까지만 좁혀 나머지는 B 규칙으로 스스로 정하고 계속 간다. "전부 자가 판단"은 "전부 허용"이 아니라 "멈추지 않음"이다.

정책은 프롬프트 본문에 그대로 붙여넣는다. 파일만 트리 밖에 두고 chmod 444 를 걸어도 같은 사용자 권한의 bash 가 되돌릴 수 있어 실수 방지 수준에 그친다. 컨텍스트에 들어온 원문이 기준이 되어야 파일 교체가 의미를 잃는다. 2. 워크트리를 분리하고 단위별로 커밋한다 — 단위 하나를 통째로 revert 할 수 있어야 반쯤 고친 호출부가 남지 않는다. 단 git add -A 가 아니라 그 단위의 경로만 올린다. 전체를 올리면 병렬 워커의 미완성 변경이 섞여 revert 가 남의 작업까지 지운다. 워커를 2명 이상 동시에 돌릴 때는 워커마다 워크트리를 따로 준다. push 만 금지한다. 단, 워크트리는 되돌리기 수단이지 격리가 아니다 — 홈·SSH 키·네트워크에는 그대로 닿는다. 3. 상한을 건다 — timeoutMs 는 개별 subagent 실행 제한이지 밤 작업 전체의 상한이 아니다. 부모가 단위를 계속 만들면 전체 시간은 계속 늘어난다. 전체 벽시계 상한은 timeout 8h pi 처럼 OS 레벨로 걸어야 한다.

프롬프트 템플릿은 oneshot.md, 정책 템플릿은 decisions.example.md.

작업 스케줄러로 매시간 돌린다면 한 번에 전부 끝내는 프롬프트를 쓰면 안 된다. 회차가 겹치면 같은 워크트리를 두 에이전트가 고친다. night-setup.md 의 NIGHT-1~NIGHT-5 를 쓴다 — 회차당 한 단위, 스케줄러 등록, 이전 회차가 살아 있으면 건너뛰기, .orch\STOP 으로 종료.

그리고 무인이든 아니든 subagents.watchdog 은 켜둔다. 턴 경계에서 다른 모델이 방금 한 일을 되짚어 범위 이탈·루프 위험·위험한 변경을 찾는다.

단 이것은 사후 검토이지 실행 전 차단이 아니다. 전송이나 삭제가 일어난 뒤에 지적한다. 하드 가드를 대신하지 못한다. 그리고 watchdog.main.model 을 생략하면 세션 모델을 상속하므로, 부모와 다른 모델이 되도록 명시해야 한다 — 스니펫에 넣어 뒀다. 중간 점검이 필요하면 cadence.everyNTools 를 함께 켠다.

왜 원샷에 pi-subagents 인가

분해를 미리 알 수 없기 때문이다. 원샷 프롬프트는 "이거 해둬"에 가깝고, 워커를 몇 명 띄울지는 저장소를 읽어 본 뒤에 정해진다. 부모 세션이 그 판단을 하고 자식을 띄우는 것이 Supervisor 패턴의 핵심이며, 고정 파이프라인으로는 안 된다.

에이전틱 코딩(Agentic Coding): 2026년에 정리된 것들

에이전트가 코드를 읽고, 고치고, 실행하고, 결과를 보고 다음 행동을 정하는 방식의 개발. 2025~2026년에 무엇이 합의됐고, 멀티 에이전트는 언제 이기며, 어디서 무너지는지 정리한다. 이 폴더의 설정이 왜 그렇게 생겼는지도 여기서 설명한다.

왜 알아야 하나 (Why)

이 폴더의 설정값 하나하나는 결국 에이전틱 코딩에서 반복해서 확인된 실패를 막으려는 장치다. 리뷰어에게 bash를 돌려주는 것도, 워커마다 파일을 나눠 주는 것도, 야간 실행을 회차당 한 단위로 자르는 것도 다 이유가 있다. 그 이유를 모르고 설정만 복사하면, 모델이나 패키지가 바뀌었을 때 무엇을 지키고 무엇을 버려도 되는지 판단할 수 없다.

또 하나. 이 분야는 반년 사이에도 권장 사항이 바뀐다. 2025년 6월에 "멀티 에이전트를 만들지 마라"라고 했던 Cognition이 2026년 4월에는 "이런 조합은 된다"로 입장을 좁혔다. 무엇이 근거 있는 주장이고 무엇이 업체 블로그의 경험담인지 구분해 두면, 다음 유행이 와도 휘둘리지 않는다.

핵심 개념 (What)

에이전틱 코딩은 "루프"다

자동완성은 다음 몇 줄을 예측한다. 채팅형 코딩은 답이나 코드를 주고, 적용은 사람이 한다. 에이전틱 코딩은 모델이 도구를 직접 호출해 파일을 읽고, 수정하고, 명령을 돌리고, 그 결과를 보고 다음 행동을 고른다. 차이는 에이전트 수가 아니라 실행과 피드백이 닫힌 루프에 있다. Microsoft가 2026년 6월 GitHub Copilot 운영 트레이스를 분석했을 때도 모델 호출과 도구 실행이 거의 1:1로 맞물려 돌았다.

그래서 이 방식에서 가장 비싼 자원은 모델의 지능이 아니라 두 가지다.

  • 컨텍스트: 읽은 파일, 명령 출력, 대화가 전부 한 창에 쌓인다. 창이 찰수록 앞의 지시를 잊고 실수가 늘어난다.
  • 검증: 에이전트는 "끝난 것처럼 보이면" 멈춘다. 돌려 볼 수 있는 검사가 없으면 사람이 검증 루프가 된다.

Addy Osmani는 2026년 3월 발표에서 이 변화를 한 줄로 정리했다. 병목은 이제 생성이 아니라 검증이다.

2025~2026년에 사실상 합의된 실천

업체 문서와 연구가 공통으로 가리키는 것만 추렸다. "표준"이라기보다 여러 곳에서 같은 결론에 도달한 실천이고, 모든 과제에서 효과가 증명된 것은 아니다.

긴 작업은 상태를 파일에 둔다 진행 목록과 결정을 파일과 git에 남기고, 세션은 매번 새로 시작한다 Anthropic, Effective harnesses (2025-11)

LLM이 자동 생성한 파일은 효과가 거의 없었다. 반대 결과를 낸 연구도 있어 결론은 아직 열려 있다. 저자들이 권하는 것은 길이를 줄이는 것 자체가 아니라, 그 저장소에만 있는 비표준 정보만 적고 효과를 측정해 보는 것이다. 실무 규칙으로 옮기면 이렇다. 에이전트가 스스로 알아낼 수 없는 것만, 사람이 직접 쓴다.

멀티 에이전트는 언제 이기나

"에이전트를 여러 개 띄우면 더 잘한다"는 직관은 반만 맞다. 근거를 날짜순으로 보면 그림이 선명해진다.

  1. Anthropic, 2025년 6월. 리드 에이전트 하나가 하위 에이전트들에게 조사를 나눠 맡기는 구조가 단일 에이전트보다 내부 리서치 평가에서 90.2% 나았다. 대신 토큰은 일반 채팅의 약 15배를 썼다(단일 에이전트는 약 4배). 이것은 리서치 과제이고, 저자들도 서로 얽힌 코딩 작업은 병렬화가 덜 된다고 적었다.
  2. Cognition, 2025년 6월. "Don't Build Multi-Agents." 병렬로 쓰는 에이전트들은 서로 다른 암묵적 결정을 내리고, 그 충돌을 마지막 에이전트가 떠안는다. 원칙은 둘이다. 맥락을 통째로 공유할 것, 그리고 행동에는 암묵적 결정이 담겨 있다는 것.
  3. Google Research, 2026년 1월. 180개 구성을 통제 실험했다. 병렬로 쪼갤 수 있는 금융 분석 과제에서는 중앙 조율형 멀티 에이전트가 80.9% 나았다. 순서가 중요한 계획 과제(PlanCraft)에서는 모든 멀티 에이전트 변형이 39~70% 나빠졌다. 서로 소통하지 않는 독립형 구조는 오류를 17.2배 증폭했고, 오케스트레이터가 있는 중앙형은 4.4배로 막았다.
  4. Cursor, 2026년 1월. 에이전트들을 공유 파일과 잠금으로 평평하게 조율하자 잠금 대기로 시간을 다 썼다. 20개를 띄워도 처리량은 2~3개 수준이었다. 잠금을 풀자 이번에는 다들 쉬운 일만 골랐다. 계획자·작업자·판정자로 층을 나누고, 판정자가 회차마다 계속할지 정한 뒤 다음 회차를 새로 시작하게 하자 굴러갔다.
  5. Cognition, 2026년 4월. 1년 만의 후속 글에서 입장을 좁혔다. 병렬로 쓰는 에이전트 무리는 여전히 안 된다. 되는 것은 쓰기는 한 줄기로 유지하고, 추가 에이전트는 행동이 아니라 판단을 보태는 구조다. 읽기 전용 탐색 에이전트, 새 컨텍스트에서 diff만 보는 리뷰어(PR당 평균 약 2건의 버그를 잡았고 그중 약 58%가 심각), 큰 작업을 나눠 맡기는 관리자 구조가 여기에 든다.

이 연구들의 과제와 모델은 제각각이라 한 줄로 일반화할 수는 없다. 그래도 공통으로 가리키는 방향은 있다. 넓게 읽는 일은 나누면 이기는 경우가 많고, 한 덩어리로 쓰는 일은 나누면 지는 경우가 많다. 리뷰처럼 새 눈이 필요한 일은 나누는 편이 낫다. 그리고 나눌수록 토큰 비용은 대개 크게 는다.

사내 오픈 웨이트 모델에서 더 챙길 것

외부 API를 못 쓰고 사내 게이트웨이의 GLM·Qwen 계열만 쓰는 환경에서는 아래를 먼저 확인한다. 모두 일반 원칙을 이 환경에 적용한 권고이고, 사내 모델로 측정한 결과는 아니다.

  • 도구 호출이 실제로 되는지부터 본다. OpenAI 호환 API라고 해서 도구 호출이 같은 방식으로 도는 것은 아니다. Qwen3.6 모델 카드는 추론 파서와 도구 호출 파서를 따로 설정하라고 안내한다. 도구를 못 부르는 증상이 모델 지능 문제가 아니라 서빙 설정 문제일 수 있다. smoke.sh -l 2가 이 확인용이다.
  • 도구는 적게, 출력은 짧게. 도구 호출이 약한 모델일수록 도구 수를 줄이고, 설명을 분명히 하고, 출력 길이에 상한을 두고, 오류 메시지가 다음 행동을 알려 주게 만든다.
  • 모델 사양의 최대 컨텍스트가 실제 작업에 알맞은 입력 크기를 뜻하지는 않는다. GLM-5.3은 100만 토큰을 받지만, 창이 찰수록 성능이 떨어지는 것은 같다. 자식에게는 새 컨텍스트를 주고, 부모가 자식의 전사를 흡수하지 않게 한다. TPM 한도에도 이 편이 유리하다.
  • 쓰는 에이전트는 하나부터 시작한다. 읽기 전용 탐색과 리뷰만 나누고, 병렬 작성은 통합 실패율과 총비용을 단일 에이전트와 비교해 본 뒤에 늘린다.
  • 같은 계열끼리의 검증을 믿지 않는다. Big과 Medium은 둘 다 GLM이다. 영향이 큰 변경은 계열이 다른 Qwen으로 2차 검증한다.

핵심 개념 (What)

요청 하나가 대화 전체다

게이트웨이가 세는 단위는 사람의 질문 수도, 에이전트 수도, 도구 호출 수도 아니다. 모델 호출 수다. 모델이 다음 응답을 만들 때마다 호출이 한 번 일어난다. 한 응답에 도구 호출 여러 개가 묶일 수 있고, 그 결과를 받으면 다음 호출이 이어진다. 호출마다 시스템 프롬프트, 도구 정의, 지금까지의 대화(압축·제거 후 남은 부분), 방금 받은 도구 결과가 다시 들어간다.

그래서 세션이 길어지면 누적 토큰은 호출 수의 제곱에 비례해 는다. 첫 호출의 입력이 C0, 호출마다 대화가 g씩 늘고, 출력이 평균 o라면 N번 호출의 합은 다음과 같다.

입력 합 = N × C0 + g × N × (N − 1) / 2
출력 합 = N × o

예를 들어 시작 컨텍스트 20K, 호출마다 2K씩 늘고, 출력 1K로 20번 호출하면 입력 780K + 출력 20K = 800K 토큰이다. 마지막 컨텍스트는 58K에 불과한데 누적은 그 열네 배다. 이 20번을 3분 안에 하면 분당 약 27만 토큰으로, 세션 하나가 한도의 절반 넘게 쓴다.

어느 한도가 먼저 차나

요청 하나가 평균 q 토큰을 쓰면, 분당 보낼 수 있는 요청 수는 min(50, 500,000 ÷ q)이다. 경계는 요청당 10,000토큰이다. 그보다 크면 TPM이 먼저 찬다. 코딩 에이전트의 요청은 거의 항상 이보다 크다.

요청당 토큰 TPM 기준 분당 요청 RPM 기준 먼저 차는 쪽 고르게 보낼 때 간격
20,000 25 50 TPM 2.4초
60,000 8.3 50 TPM 7.2초
150,000 3.3 50 TPM 18초
400,000 1.25 50 TPM 48초

이 값은 요청을 완벽하게 고르게 보냈을 때의 평균이다. 게이트웨이가 "직전 60초"를 세는 방식이면 400K 요청 두 개가 48초 간격으로 들어와도 한 구간에 겹쳐 한도를 넘는다. 실제로는 간격을 이보다 넉넉히 둬야 한다.

HCP-Big과 HCP-Medium의 컨텍스트 창이 100만 토큰이라는 사실은 여기서 함정이 된다. 창이 넓다고 컨텍스트를 채우면, 요청 하나로 분당 한도 전체를 쓴다. 넓은 창은 가끔 필요한 여유이지 평소에 쓸 공간이 아니다.

자식은 몇 개까지 돌릴 수 있나

자식 하나가 요청 하나를 처리하는 주기(모델 응답 + 도구 실행 시간)가 L초라면, 그 자식은 분당 60 ÷ L번 요청하고 60 × q ÷ L 토큰을 쓴다. 부모와 watchdog 몫을 먼저 떼어 두고 남은 예산을 나누면 된다.

자식 수 ≤ min( 남은 RPM × L ÷ 60 ,  남은 TPM × L ÷ (60 × q) )

계산 예다. 다른 harness와 측정 오차를 감안해 한도의 80%인 400K TPM / 40 RPM만 쓰기로 하고, 그중 100K / 10을 부모와 watchdog에 남긴다. 자식에게는 300K / 30이 돌아간다.

150K 30초 300K 1

결론은 단순하다. 동시성 설정보다 자식의 컨텍스트 크기와 요청 주기가 먼저다. 이 문서는 자식의 요청당 60K를 잠정 목표로 쓴다. 절대 기준은 아니다. 요청당 150K라도 30초마다 한 번이면 하나는 돌고, 요청이 크고 주기까지 짧으면 동시성을 1로 낮춰도 혼자서 한도를 넘는다. 판단은 언제나 q와 L과 남은 예산으로 한다.

캐시 적중 토큰을 세는가

에이전트는 같은 앞부분을 계속 다시 보내므로 프롬프트 캐시 적중이 많다. pi 로그에서도 입력의 대부분이 cacheRead다. 문제는 이것을 한도에 세는지가 게이트웨이마다 다르다는 점이다.

  • OpenAI는 캐시된 입력도 TPM에 센다. 싸고 빠를 뿐 한도에서 빠지지 않는다.
  • LiteLLM 프록시의 기본 TPM은 입력 + 출력이다. 별도로 켜는 베타 ITPM/OTPM 제한기는 응답 후 정산에서 캐시 적중을 뺀다.
  • 사내 게이트웨이가 무엇을 쓰는지, 어떤 모드인지는 모른다.

확인하기 전까지는 캐시 적중도 센다고 가정한다. 안전한 쪽으로 틀리는 편이 낫다.

pi에는 재시도 층이 두 개 있다. 바깥쪽 retry.maxRetries는 에이전트 단위로 다시 시도하고, 안쪽 retry.provider.maxRetries는 HTTP 요청 단위로 다시 시도한다. 둘 다 모든 오류를 재시도하면 곱해진다.

  • 현재 스니펫(바깥 6회, 안쪽 4회): 생성 하나에 최악 (1+6) × (1+4) = 35번 HTTP 요청이 나간다. 바깥쪽 대기만 8+16+32+64+120+120 = 360초다.
  • 야간 값(바깥 8회, 안쪽 4회): 최악 45번이다.

두 층은 성격도 다르다. 안쪽은 서버가 보낸 Retry-After 헤더를 따르고, 헤더가 없으면 지터를 섞은 짧은 대기(최대 8초)를 쓴다. 단 서버가 요구한 대기가 maxRetryDelayMs(스니펫 60초)를 넘으면 기다리지 않고 바로 실패한다. 바깥쪽은 지터 없이 2배씩 늘린다. 여러 자식이 동시에 429를 받으면 똑같은 시각에 다시 몰려 들어갈 수 있다.

반복되는 429는 "재시도로 회복되고 있다"는 신호가 아니라 "부하를 줄여야 한다"는 신호다.

어떻게 하는가 (How)

1. 게이트웨이 운영팀에 먼저 확인한다

이 답에 따라 아래 숫자가 전부 바뀐다. ⟨확인⟩ 항목이다.

  1. 한도의 단위는 무엇인가? API 키, 계정, 팀, 모델 별칭, 백엔드 배포 중 무엇인가? my-local-provider와 itc-vlm이 같은 한도를 나눠 쓰는가?
  2. 무엇을 세는가? 입력만, 출력만, 합계, 아니면 입력·출력 따로인가? 캐시 적중 토큰과 thinking 토큰을 세는가?
  3. 출력은 언제 세는가? 실제 생성량인가, 요청의 max_tokens를 미리 예약하는가? 예약이면 언제 돌려받는가?
  4. 구간 방식은? 달력 1분 고정, 직전 60초 슬라이딩, 토큰 버킷 중 무엇인가? 순간 버스트 상한이 따로 있는가?
  5. 429와 실패한 요청도 한도에 드는가? 끊긴 스트림, 게이트웨이 내부 재시도는?
  6. 429 응답에 Retry-After 헤더가 오는가? 남은 한도를 알려 주는 헤더가 있는가? 한도 소진(영구)과 일시 혼잡을 구분하는 오류 코드가 있는가?
  7. 동시 처리 중인 요청 수(in-flight) 상한이 따로 있는가? 대화형 작업 몫을 따로 떼어 줄 수 있는가?
  8. 게이트웨이의 요청·사용량 로그를 받아 볼 수 있는가? pi 로그와 대조하는 데 필요하다.

확인 전에는 이렇게 가정한다. 키 하나에 모든 모델과 모든 harness가 묶여 있고, 캐시 적중도 세고, 직전 60초 슬라이딩 방식이다.

2. 지금 부하를 잰다

설정을 바꾸기 전에 실제로 얼마나 쓰는지 본다. rate-usage.py는 pi 세션 로그에서 모델 응답마다 남는 usage를 모아 분당 요청과 토큰을 계산한다. 표준 라이브러리만 쓰고, 대화 내용은 읽어도 출력하지 않는다.

# 사내 PC (PowerShell). 최근 2시간, 사내 provider 만
python .\orchestration\rate-usage.py --hours 2 --provider my-local-provider

# 한도를 바꿔 보고 싶으면
python .\orchestration\rate-usage.py --hours 8 --rpm 50 --tpm 500000

출력에서 볼 것은 셋이다.

  • 응답당 평균 토큰: 위 "자식은 몇 개까지" 계산의 q다.
  • 임의의 60초 구간 최대 TPM: 캐시 포함과 제외가 따로 나온다. 운영팀 답에 맞는 쪽을 본다.
  • 80% 넘긴 분: 이 값이 0이 아니면 다른 harness와 겹칠 때 429가 난다.

이 수치는 기록된 모델 응답 수와 보고된 사용량에서 낸 추정치다. 게이트웨이가 센 값과는 다르다. 빠지는 것이 있다: watchdog 검토 호출은 세션에 사용량을 남기지 않고, 안쪽 HTTP 재시도는 응답 하나 안에서 일어나 따로 남지 않으며, 같은 키를 쓰는 Claude Code나 다른 경로에 저장된 세션도 안 잡힌다. 거꾸로 들어가는 것도 있다: 요청을 보내지 못한 로컬 오류도 응답 한 건으로 남을 수 있다. 같은 폴더 아래의 다른 pi 세션은 전부 합산된다. 한도를 지켰는지 판정하는 근거로는 게이트웨이 로그만 쓴다.

3. 예산을 나눠서 정한다

전체 한도를 다 쓰지 않는다. 측정 오차, 다른 harness, 순간 버스트를 위해 20%를 남기고, 그 안에서 부모 몫을 먼저 뗀다. 아래는 출발점이지 검증된 최적값이 아니다.

업무 중, 혼자 사용 400K TPM / 40 RPM 100K / 10 300K / 30 60K 이하

야간 목표를 낮게 잡은 이유는 아무도 429를 보지 못하기 때문이다. 밤에는 급할 일이 없으니 느리게 돌고 작업을 날리지 않는 쪽을 고른다.

나눠 쓰는 경우의 "반씩"은 모두가 지킬 때만 성립한다. pi는 다른 harness의 사용량을 모른다. 가능하면 harness마다 다른 키를 받는 것이 가장 깔끔하다. 그게 안 되면 같은 시간대에 둘을 동시에 무겁게 돌리지 않는다.

4. 설정값으로 옮긴다

설정 파일 업무 중 (현재 스니펫) 무인 실행 컨텍스트가 크고 캐시도 센다면
globalConcurrencyLimit config.json 2 1 1
parallel.concurrency config.json 2 1 1
maxActiveAsyncRunsPerSession config.json 1 1 1
maxSubagentSpawnsPerRun config.json 12 8 8
watchdog.children.enabled settings.json false false false
watchdog.cadence settings.json 없음 없음 없음

업무 중 기본값을 2로 두는 이유는 평소 작업이 scout → worker → reviewer처럼 순차라서다. 실제로 2를 쓰는 것은 /parallel-review 같은 팬아웃뿐이다. 다만 운영팀이 캐시 적중도 센다고 답하고, rate-usage.py로 잰 q와 L을 위 공식에 넣었을 때 자식 둘이 예산을 넘으면 업무 중에도 1로 내린다.

maxSubagentSpawnsPerSession은 기본이 무제한이다. 한 세션에서 자식을 끝없이 띄우는 실수를 막고 싶으면 config.json에 24 정도를 넣는다. 다 쓰면 사람이 grant-spawn-budget으로 늘려 줘야 한다.

5. 컨텍스트를 작게 유지한다

동시성보다 효과가 큰 쪽이 여기다. 요청당 토큰을 절반으로 줄이면 같은 한도에서 자식을 두 배 돌릴 수 있다.

  • 자식은 새 컨텍스트로 띄운다. worker는 기본이 fresh이고, reviewer는 프롬프트에서 fresh를 요구한다. oracle은 기본이 fork라서 부모 대화를 통째로 물려받는다. 큰 판단이 아니면 oracle을 자주 부르지 않는다.
  • 부모 컨텍스트에는 자식의 실행 기록 전체 대신 요약과 필요한 결과만 넣는다. 기본 반환 방식은 자식의 최종 출력을 그대로 부모에게 넣는다(inline). 결과가 길 것 같으면 출력 경로를 주고 outputMode: "file-only"로 띄운다. 그러면 부모에게는 "어디에 저장했다"는 한 줄만 돌아온다. 부모에게 그 파일 전체를 읽으라고 시키면 이 이점이 사라지니, 필요한 절만 읽게 한다.
  • scout의 결과는 파일로 받는다. 호출 지점 목록 같은 긴 결과는 위 방식으로 파일에 저장하고, 워커에게는 그 경로를 준다. 자식에게 "파일에 써라"라고만 말해서는 반환 방식이 바뀌지 않는다. outputMode를 함께 지정한다.
  • 도구 출력을 줄인다. grep -r 대신 경로를 한정한 rg, 전체 테스트 대신 해당 테스트, 로그는 tail. 도구 결과 한 번이 다음 요청부터 계속 따라다닌다. AGENTS.md 규칙의 탐색 규칙이 이것이다.
  • 작업이 바뀌면 세션을 새로 연다. 앞 작업의 대화가 다음 작업의 모든 요청에 실린다. pi가 알아서 하는 압축(compaction)은 모델 창 크기를 기준으로 하므로, 100만 창 모델에서는 너무 늦게 일어난다. 작업 경계에서 직접 새 세션을 연다.
  • AGENTS.md는 짧게 쓴다. 모든 자식의 모든 요청에 들어간다. 한 줄이 늘면 그 줄 × 전체 요청 수만큼 토큰이 는다.

6. 정찰과 워크플로에 상한을 건다

읽기만 하는 역할에는 도구 호출 상한을 걸어도 안전하다. 예를 들어 scout에 toolBudget: { soft: 20, hard: 30, block: "*" }를 주면 20번째 호출에서 마무리하라는 안내를 받고, 30번 뒤에는 도구를 못 쓰고 최종 답만 낸다.

scout 으로 <경로> 아래에서 <대상>의 호출 지점을 찾아라.
output 은 .orch/scout.md, outputMode 는 "file-only" 로 해라.
options.toolBudget 은 { soft: 20, hard: 30, block: "*" } 로 해라.

워크플로 전체에는 usageBudget으로 토큰 상한을 둘 수 있다. 단 이것은 분당 한도가 아니라 누적 총량이고, 넘으면 다음 자식을 띄우지 않을 뿐 도는 자식은 멈추지 않는다. 합산에서 캐시 토큰이 빠지므로 게이트웨이가 세는 양보다 작게 나온다.

워커나 고칠 권한이 있는 리뷰어에는 빡빡한 상한을 걸지 않는다. 검증 직전에 도구가 막히면 반쯤 고친 상태로 끝난다. 패키지 문서도 같은 이유로 쓰기 역할에는 걸지 말라고 권한다.

7. 429가 보이면 이렇게 한다

보이는 것 뜻 할 일
가끔 재시도 표시가 뜨고 곧 진행된다 한도 근처에서 일시 초과 그대로 둔다
재시도가 자주 보인다 지속적으로 한도 근처 동시성을 1로 낮춘다. rate-usage.py로 요청당 토큰을 확인한다
재시도 후에도 실패로 끝난다 재시도 대기보다 한도 회복이 느리다 옆에서 도는 다른 harness를 멈춘다. 자식 컨텍스트를 줄인다
대기 없이 바로 실패한다 서버 요구 대기가 maxRetryDelayMs를 넘었거나 한도 소진(영구) 운영팀에 오류 코드와 헤더를 확인한다
야간 실행이 회차마다 같은 단위에서 실패한다 그 단위의 요청이 너무 크다 단위를 더 잘게 쪼갠다

무인 실행에서는 재시도 횟수를 늘려서 숨기지 않는다. 회차당 한 단위로 자른 야간 템플릿은 실패한 단위를 기록하고 멈추므로, 다음 회차가 한도가 회복된 뒤 다시 시도한다.

8. 재시도 층을 하나로 정한다

두 층을 둘 다 크게 두면 위에서 본 것처럼 35~45번까지 곱해진다. 운영팀의 6번 답(Retry-After 헤더를 주는가)을 받은 뒤 하나를 주 재시도로 고른다.

  • 헤더를 준다면: 안쪽(provider)이 헤더를 따르므로 이쪽을 주로 쓴다. retry.provider.maxRetries를 유지하고, maxRetryDelayMs를 서버가 요구하는 최대 대기보다 크게 둔다. 바깥쪽 retry.maxRetries는 2~3으로 줄인다.
  • 헤더를 주지 않는다면: 안쪽의 짧은 대기(최대 8초)는 분 단위 한도에서 효과가 없다. pi 문서의 권장대로 retry.provider.maxRetries를 0으로 두고, 바깥쪽을 maxRetries: 3, baseDelayMs: 15000으로 둔다. 대기는 15·30·60초가 된다.

현재 스니펫은 2026-09-22 사내 검증을 통과한 값이라 그대로 두었다. 위 판단은 운영팀 답을 받은 뒤 적용한다.

집에서는 Claude(Pro·Max)와 ChatGPT(Plus·Pro) 구독으로 Claude Code, Codex CLI, 그리고 그 구독에 연결한 pi를 쓴다. 한도의 모양이 회사와 완전히 다르다. 아래는 2026-10-24에 공식 도움말에서 확인한 내용이다. 구독 한도는 자주 바뀌므로 숫자보다 구조를 기억한다.

자식은 같은 지갑에서 쓴다

새 컨텍스트, 새 프로세스, 새 워크트리는 새 구독이 아니다. 같은 인증 계정이면 provider 이름이나 프로세스가 달라도 같은 한도를 쓴다.

  • Claude Code의 서브에이전트와 agent team 팀원은 각자 요청을 보내고, 전부 본 대화와 같은 한도에서 차감된다.
  • pi의 openai-codex provider는 ChatGPT 로그인(OAuth)으로 ChatGPT 백엔드를 쓴다. API 키 요금제가 아니라 그 계정의 구독 한도를 쓴다.
  • pi의 pi-claude-bridge 패키지는 Claude Agent SDK, 즉 로컬 Claude Code를 거쳐 Claude를 부른다. 로컬 Claude Code가 구독으로 로그인돼 있으면 그 구독 한도를 쓴다. 환경 변수에 ANTHROPIC_API_KEY가 있으면 API 요금제로 바뀔 수 있다.
  • pi-subagents의 자식은 실행마다 모델과 provider를 고른다. 같은 계정으로 띄운 자식 열 개는 한 지갑에서 열 번 쓴다. 다른 지갑이 되려면 다른 구독 계정이나 다른 과금 경로여야 한다. provider 이름만 다른 것으로는 부족하다. 예를 들어 pi의 openai와 openai-codex가 같은 ChatGPT 계정으로 로그인돼 있을 수 있다.

Anthropic의 2026-10-07 도움말 갱신은 Agent SDK, claude -p, 서드파티 앱에서도 구독 한도를 계속 쓸 수 있다고 밝혔다. 단 개발자가 자기 앱에 Claude.ai 로그인을 넣거나 사용자의 구독 자격 증명을 모아서 대신 호출하는 것은 금지다. 본인이 공식 Claude Code에 직접 로그인해서 쓰는 경로는 허용된다. 브리지 패키지가 이 조건을 지키는지는 패키지마다 확인해야 한다.

집에서의 운영 방식

1. 시간 예산으로 나눈다. 분당 토큰 대신 "이 창에서 몇 %를 쓸지"를 정한다. 예를 들어 5시간 창이 60% 남았고 앞으로 3시간 일한다면, 20%를 남기고 40%를 3시간에 나눠 시간당 약 13%를 쓴다. 큰 팬아웃 전과 큰 단위가 끝난 뒤에 확인한다. 수시로 들여다볼 필요는 없다.

2. 주간 한도를 따로 본다. 5시간 창이 회복돼도 주간 한도는 회복되지 않는다. 주간이 40% 남았고 4일 더 쓸 계획이면 10%를 남기고 하루 7.5%다. 주말 직전에 큰 작업을 몰아서 돌리다가 주중에 막히는 일이 흔하다.

3. 병렬은 "빨리 끝나는 값"이 있을 때만. 회사에서는 분당 한도가 병렬을 막지만, 집에서는 병렬이 창을 빨리 소진하는 것이 문제다. 자식을 늘리면 끝나는 시간은 줄 수 있어도 창이 닫히는 시점도 앞당겨진다. 시간이 얼마나 줄고 총소비가 얼마나 느는지는 직접 재 본다. 서로 독립인 작업이고 빨리 끝나야 할 이유가 있을 때만 병렬로 돌린다.

4. 역할마다 모델 크기를 나눈다. 회사의 티어링과 같은 원리다. Claude라면 단순 탐색은 Haiku, 일상 구현은 Sonnet, 어려운 설계와 위험한 변경의 검토만 Opus에 맡긴다. 기본 상속으로 모든 자식이 가장 비싼 부모 모델을 쓰지 않게 한다. Codex도 기계적인 작업은 작은 모델, 어려운 변경과 검토는 큰 모델을 쓴다. Fast·Ultrafast 모드는 한도를 2.5~8배 빨리 쓰므로 예산이 빠듯할 때는 Standard를 쓴다.

5. 두 회사의 구독을 두 개의 지갑으로 쓴다. Claude로 쓰고 Codex로 검토하면 한쪽 한도만 빨리 닳는 것을 막는다. 계열이 다른 모델로 검토하는 효과도 있다. 다만 계열이 다르다고 오류가 독립이라는 보장은 없다. 검증 명령을 직접 다시 돌리는 원칙은 그대로다.

6. 유료 연장은 미리 정해 둔다. Claude의 사용 크레딧, ChatGPT의 크레딧은 한도 뒤에도 계속 쓰게 해 주지만 별도 요금이다. 무인으로 돌리기 전에 크레딧 자동 구매와 지출 상한을 확인한다. 의도하지 않았다면, 한도에 닿으면 체크포인트를 남기고 멈추는 쪽이 맞다.

7. 무인 실행은 창 시작에 맞춘다. 밤새 돌릴 작업은 5시간 창이 거의 새로 시작될 때 걸고, 한 회차가 창 하나를 넘지 않게 단위를 자른다. 회사 야간 템플릿의 "회차당 한 단위" 원칙이 집에서도 그대로 쓸모 있다. 한도에 닿은 회차는 실패로 기록하고 멈추고, 다음 창에서 이어 간다.

남은 양을 화면에 띄운다

Claude Code의 statusline 스크립트는 stdin으로 rate_limits.five_hour와 rate_limits.seven_day를 받는다. 각각 used_percentage(0~100)와 resets_at(Unix 초)이 있다. 구독 사용자에게만, 그리고 세션의 첫 응답 뒤에만 나타난다. 값이 없다고 무제한이라는 뜻이 아니다.

#!/usr/bin/env bash
# ~/.claude/statusline.sh : 5시간·주간 사용률을 한 줄로 보여 준다
in=$(cat)
five=$(jq -r '.rate_limits.five_hour.used_percentage // empty' <<<"$in")
week=$(jq -r '.rate_limits.seven_day.used_percentage // empty' <<<"$in")
reset=$(jq -r '.rate_limits.five_hour.resets_at // empty' <<<"$in")
printf '5h %s%%  7d %s%%' "${five:-?}" "${week:-?}"
[ -n "$reset" ] && printf '  (5h 재설정 %s)' "$(date -r "$reset" +%H:%M 2>/dev/null || date -d "@$reset" +%H:%M)"
echo

~/.claude/settings.json의 statusLine에 {"type": "command", "command": "~/.claude/statusline.sh"}로 등록한다. Codex CLI는 /status와 /statusline으로 같은 정보를 본다.

## 에이전트 작업 규칙

### 범위
- 배정받은 파일 밖은 수정하지 않는다. 밖을 고쳐야 하면 고치지 말고 보고에 적는다.
- 요청하지 않은 리팩터링·추상화·설정 파일·의존성을 만들지 않는다.
- 여러 에이전트가 동시에 일할 수 있다. 내 단위 밖의 변경을 되돌리거나 덮어쓰지 않는다.

### 탐색 (scout 포함 모든 역할)
- 탐색은 **지정받은 경로 아래로 한정**한다. `find /`, 저장소 루트에서의 `find .`·`grep -r` 을 하지 않는다.
  루트 전체 탐색은 `node_modules`·`.git`·빌드 산출물까지 훑어 도구 타임아웃(`toolTimeoutMs`)을 그대로 태운다.
- 경로를 지정받지 못했으면 먼저 `ls` 로 최상위 구조만 보고, 대상이 있을 법한 디렉터리를 고른 뒤 그 안에서만 찾는다.
- `find`·`grep` 에는 항상 `.git`, `node_modules`, `venv`, `dist`, `build` 를 제외 조건으로 건다.
  가능하면 `rg` 나 `git ls-files | grep` 을 쓴다 — `rg`는 기본 ignore 규칙을 적용하고 `git ls-files`는 추적 파일을 나열한다.
  이미 추적된 파일은 나중에 .gitignore에 들어가도 목록에 남는다.

### Git
- `git push`, `git reset --hard`, `git clean`, `git checkout .`, 브랜치 전환을 하지 않는다.
- 커밋할 때 `git add -A` 를 쓰지 않는다. 내 단위의 경로만 명시해서 올린다.
- 변경 확인은 `git add -N -- <배정 경로> && git diff -- <배정 경로>` 로 한다. 그냥 `git diff` 는 새 파일을 보여주지 않는다.

### 검증
- 검증 명령: <이 저장소의 실제 명령. 예: pytest, npm run typecheck, npm test>
- 돌리지 않았으면 돌렸다고 쓰지 않는다. 없는 명령을 지어내지 않는다.
- 실패하면 출력을 그대로 붙이고, 이번 변경 때문인지 원래 깨져 있었는지 구분한다.

### 보고
- 결론이 아니라 근거를 남긴다: `파일:줄`, 실행한 명령과 실제 출력.
- 확인하지 않은 것을 확인했다고 쓰지 않는다. 모르면 모른다고 쓴다.

### 리뷰
- 리뷰할 때는 상대의 보고를 믿지 않는다. 코드를 직접 읽고 검증 명령을 직접 다시 돌린다.
- 코드를 고치지 않는다. 지적만 한다. 스타일 취향은 지적하지 않는다.

### 보안
- `.env`, 인증서, 개인 키를 읽거나 출력하지 않는다.
- 사내 HCP 게이트웨이 외 외부 네트워크로 코드·로그를 보내지 않는다.

왜 AGENTS.md 인가

역할 파일 직접 정의 빌트인을 통째로 복제해야 함 같음 4벌

주의

  • 자식은 스킬을 상속하지 않는다(inheritSkills: false). 스킬에 의존하는 규칙을 쓰지 않는다.
  • AGENTS.md 는 프로젝트 신뢰를 거절해도 로드될 수 있다. 신뢰하지 않는 저장소에서는 내용을 먼저 확인한다.
  • 여기 적은 규칙은 프롬프트 수준이다. 강제가 아니다 — 실제 경계는 컨테이너/VM 이다.

결정 정책 (사전 승인)

저장소 바깥(예: ~/.orch-policy/<저장소>.md)에 두고 읽기 전용으로 준다. 무인 실행 중 워커가 결정 앞에서 멈추는 대신, 부모 세션이 이 파일을 근거로 답한다.

이 파일을 작업 트리 안에 두지 않는다

에이전트가 쓸 수 있는 곳에 정책을 두면 자기 승인 근거를 자기가 고칠 수 있다. 실수로든 목표 달성 압박으로든 한 줄만 바꾸면 C가 A가 된다. 정책 원본은 작업 트리 밖에 두고, 결정 로그 (.orch/결정로그.md)만 작업 트리 안에 쓴다.

다만 트리 밖 + chmod 444 는 실수 방지 수준이다. 에이전트는 실행한 사용자 권한을 그대로 가지므로 bash 로 권한을 되돌리거나 파일을 교체할 수 있다. 이것을 실제 통제로 삼으려면 둘 중 하나가 필요하다.

  1. 정책 본문을 프롬프트에 그대로 붙여넣는다. 부모 컨텍스트에 들어온 원문이 기준이 되므로 파일을 바꿔도 의미가 없다. 가장 싸고, 무인 실행에서는 이 방법을 권한다.
  2. 별도 사용자/컨테이너로 실행해 정책 파일을 에이전트 UID가 쓸 수 없게 만든다.

판정 순서 — 반드시 이 순서로

위에서 걸리면 아래는 보지 않는다. A를 먼저 보면 "기존 인증 코드를 그대로 복사"처럼 A(기존 패턴 따르기)이면서 동시에 C(인증·권한)인 변경이 승인되어 버린다.

0. 하드 가드에 해당하나?      → 해당하면 즉시 중단. 모드와 무관. 예외 없음.
1. D 표에 "구체적인" 답이 있나? → 있으면 그 답을 쓰고 끝. (사람이 이미 결정한 것이다)
2. C 목록에 해당하나?         → 해당하면 아래 "모드" 표대로. A/B 를 보지 않는다.
3. A 목록에 있나?             → 있으면 승인.
4. 그 외                      → B 기본값 규칙으로 정한다.

D가 C보다 앞인 이유는, D는 사람이 이 저장소를 보고 미리 내린 결정이기 때문이다. C는 "사람에게 물어라"는 뜻이고, D는 이미 물어서 받은 답이다. 순서를 뒤집으면 미리 답해둔 것이 무시된다.

단 "구체적인" 답만 유효하다. D의 답이 그 결정을 지목해야 한다. "타임아웃 기본값은 30초" 는 유효하다. "알아서 해" 는 무효다 — 범위가 없는 사전 승인은 승인이 아니다. 무효인 D 항목은 없는 것으로 치고 2단계(C)로 내려간다. 하드 가드는 D로 해제되지 않는다.

모드 — 하나만 남기고 지운다

프롬프트에 결정 모드: <이름> 으로 적는다. 하드 가드(0단계)는 어느 모드에서도 동일하다.

모드 C를 만나면 C 목록 적용 범위
보수 전체 실행을 멈춘다 C 전체
균형 (기본) 그 작업 단위만 중단, 나머지 단위는 계속 C 전체
자율 멈추지 않는다. B 규칙으로 스스로 정하고 진행 하드 가드만. 나머지 C 항목은 B로 내려온다

세 모드가 실제로 다른 지점은 C 목록의 적용 범위다. 균형과 자율이 "나머지는 계속"으로 같아 보이면 모드를 나눌 이유가 없다. 자율은 C를 좁혀서 더 많이 스스로 정하는 모드다.

자율 모드

"전부 자가 판단"은 "전부 허용"이 아니라 "멈추지 않음" 이다.

  • C 목록 중 하드 가드가 아닌 항목(공개 인터페이스 변경, 기존 동작 변경 등)은 B 규칙으로 스스로 정한다.
  • 확신 60% 미만 규칙은 끈다. 대신 로그에 확신도를 숫자로 적는다.
  • 하드 가드에 걸리면 그 작업 단위를 되돌리고 [SKIP-HARD] 로 기록한 뒤 다음 단위로 간다. 우회로를 만들어 돌아가지 않는다. 건너뛰는 것과 우회하는 것은 다르다.
  • 결정 로그는 선택이 아니라 필수다. 멈춤 지점이 없는 만큼 사후 추적이 유일한 안전망이다.

  • 시크릿·인증서·키 읽기·출력·전송
  • 외부 네트워크 전송 (사내 HCP 게이트웨이 외)

  • 공개 인터페이스 변경 (API 시그니처, 응답 스키마, CLI 플래그, 설정 키 이름)

A. 미리 승인한 것 — 묻지 말고 진행

위 0·C 단계를 통과한 것에만 적용된다.

  • 이름 짓기(변수·함수·파일명). 기존 저장소 관례를 따를 것.
  • 기존 패턴을 그대로 따르는 선택. 같은 일을 하는 코드가 이미 있으면 그 모양을 복사한다.
  • 테스트 추가. 기존 프레임워크·디렉터리 구조를 따를 것.
  • 주석·docstring 추가, 오탈자 수정.
  • 에러 메시지 문구.
  • 이미 있는 유틸리티/헬퍼 재사용 (새로 만들지 않고).
  • <이 저장소에서 추가로 미리 승인할 것>

B. 기본값 규칙 — 위 어디에도 안 걸리면 이 규칙으로 정한다

  1. 되돌리기 쉬운 쪽을 고른다. 두 안이 비슷하면 diff가 작은 쪽.
  2. 기존 코드에 더 가까운 쪽을 고른다. 일관성이 우아함을 이긴다.
  3. 범위를 넓히지 않는 쪽을 고른다. 겸사겸사 고치지 않는다.
  4. 확신이 60% 미만이면 C로 간주한다. (자율 모드에서는 이 규칙을 끄고 확신도를 로그에 적는다)

진행 방식:
1. scout 으로 대상 범위의 현재 구조와 호출 지점을 먼저 파악해라.
   scout 이 놓친 호출부가 있을 수 있으니, 구현 전에 worker 가 자기 단위의 호출 지점을 다시 확인해라.
2. 그 결과로 작업을 파일이 겹치지 않는 단위로 쪼개라. 겹치면 쪼개지 말고 순서를 줘라.
   파일이 안 겹쳐도 API·설정·공유 테스트로 엮이면 의존이다. 의존 순서를 명시해라.
3. worker 를 단위마다 띄워 구현해라. 단위가 하나면 한 명만 띄워라.
4. **단위가 끝날 때마다 그 단위만 커밋해라.** push 는 하지 마라.
   커밋은 되돌리기 위한 것이다 — 단위 하나를 통째로 revert 할 수 있어야 한다.

   **`git add -A` 를 쓰지 마라.** 다른 워커가 동시에 고치는 중이면 그 미완성 변경까지 커밋에 들어가고,
   나중에 이 단위를 revert 할 때 남의 작업까지 지워진다. 그 단위에 배정된 경로만 명시해서 올려라:
   `git add -- <그 단위의 경로들> && git commit -m "unit/<이름>: <요약>"`

   **워커를 2명 이상 동시에 돌릴 때는 워커마다 워크트리를 따로 줘라.** 한 워킹 트리에서 여러 워커가
   동시에 커밋하면 인덱스가 경합하고 커밋이 섞인다. 병렬이 필요 없으면 순차로 돌리는 편이 안전하다.
5. 각 단위가 끝나면 reviewer 를 fresh context 로 띄워 검증해라.
   reviewer 에게 주는 검증 대상은 **그 단위의 커밋**이다: `git show <sha>` 와 `git diff <직전sha>..<sha>`.
   보고를 믿지 말고 코드를 직접 읽고, 검증 명령도 직접 다시 돌리게 해라.
6. reviewer 가 지적하면 그 worker 에게 되돌려라. 수정 루프는 **단위당 최대 2회**.
   2회 뒤에도 안 끝나면 그 단위의 커밋을 revert 하고 포기 상태로 기록해라.
7. 전 단위가 끝나면 **마지막에 통합 검증을 한 번 더 해라.** 단위별 검증만으로는
   최종 트리가 쓸 수 있는 상태인지 알 수 없다.

검증:
- <이 저장소의 실제 명령. 예: pytest tests/payment, npm run typecheck>
- 없으면 지어내지 말고 "검증 명령 없음"이라고 기록해라.
- 커밋 전 변경 확인은 `git add -N -- <배정 경로> && git diff -- <배정 경로>` 로 해라.
  그냥 `git diff` 는 **새로 만든 파일을 보여주지 않는다.**

중단·포기 처리:
- **`보수` 모드면 C를 만나는 즉시 전체 실행을 멈춘다.** 남은 단위를 시작하지 마라.
  아래 "독립 단위는 계속" 규칙은 `균형`·`자율` 에만 적용된다.
- 어떤 이유로든(하드가드, C, 루프 2회 초과, 오류) 단위를 포기하면
  **그 단위의 변경을 되돌려라.** 반쯤 고친 호출부를 남기지 마라.
  커밋했으면 revert, 아직이면 그 단위가 만든 파일만 정리해라.
- 포기한 단위에 **의존하는 후속 단위는 시작하지 마라.** 기록만 남기고 건너뛴다.
- (`균형`·`자율`) 독립적인 나머지 단위는 계속 진행해라. 한 단위가 막혔다고 전체를 세우지 마라.

결정 처리:
- 자식이 결정 앞에서 막히면 contact_supervisor 로 너(부모)에게 올린다.
  너는 정책의 **판정 순서(하드가드 → D → C → A → B)** 를 그대로 적용해 답해라.
  순서를 바꾸지 마라. A 를 먼저 보면 금지 항목이 승인되고, C 를 D 보다 먼저 보면
  내가 미리 답해둔 것이 무시된다. 하드 가드는 D 로도 해제되지 않는다.
- 자식이 스스로 정하게 두지 마라. 판정은 네가 한다.
- 스스로 정한 것은 전부 `.orch/결정로그.md` 에 규칙 번호·대안·근거·되돌리는 법·file:line 과 함께 남겨라.

보고:
- 단위별 결과는 .orch/reports/<단위>.md 에 써라.
- **`.orch/아침보고.md` 는 단위가 하나 끝날 때마다 그때그때 갱신해라.**
  마지막에 몰아쓰지 마라 — 시간 상한에 걸려 강제 종료되면 보고가 통째로 없어진다.
- 아침보고에 담을 것:
  1. 끝난 것 / 못 끝낸 것 / 포기한 것, 각각 한 줄 + 해당 커밋 sha
  2. 변경된 파일 전체 목록 (`git diff --stat <시작sha>..HEAD` 와 신규 파일 포함)
  3. 실행한 검증 명령과 실제 출력 (붙여넣기, 요약 금지)
  4. 내가 아침에 결정해야 할 것들
  5. 커밋하기 전에 사람이 꼭 봐야 할 diff 구간 (file:line)

이 템플릿이 하는 일

문단 막는 실패
정책 본문을 프롬프트에 인라인 에이전트가 자기 승인 근거를 고치는 것 (파일만으로는 못 막는다)
판정 순서 하드가드 → D → C → A → B "기존 패턴 따르기(A)"로 인증 코드 변경(C)이 승인되는 것
단위 경로만 커밋 + 포기 시 revert 반쯤 고친 호출부가 남아 다음 단위가 그 위에 쌓는 것
의존 단위 중단 규칙 파일이 안 겹친다고 독립이라 착각하는 것
git add -N -- <배정 경로> && git diff -- <배정 경로> 새로 만든 파일이 리뷰에서 통째로 빠지는 것
마지막 통합 검증 단위별로는 다 통과했는데 합치면 안 도는 것
수정 루프 2회 상한 + 단위 수 상한 reviewer↔worker 무한 왕복, 단위 무한 증식
아침보고 증분 갱신 강제 종료 시 보고가 통째로 사라지는 것
"지어내지 말고 없다고 기록" 존재하지 않는 검증 명령을 돌렸다고 쓰는 것

상한 수단 실효성
개별 subagent 실행 시간 timeoutMs (config.json) 강제됨
개별 도구 호출 시간 toolTimeoutMs (config.json) 강제됨
모델 응답 대기 httpIdleTimeoutMs (settings.json) 강제됨

총 호출·단위 수 없음 프롬프트의 "단위 최대 N개"로만. 강제 아님

subagents.timeoutMs 라고 쓰면 안 된다 — 이 키는 settings.json 이 아니라 ~/.pi/agent/extensions/subagent/config.json 에 있다. 잘못 넣으면 오류 없이 무시된다.

워크트리는 격리가 아니다

git worktree 는 되돌리기를 쉽게 해줄 뿐, 경계를 만들지 않는다. 에이전트는 실행한 사용자 권한을 그대로 가지므로 홈 디렉터리, SSH 키, 운영 자격증명, 네트워크에 그대로 닿는다. "워크트리를 버리면 다 원복된다"는 작업 트리 안에서만 참이다.

진짜 경계가 필요하면 컨테이너/VM에 작업 사본만 넣고 홈·SSH agent·Docker 소켓을 노출하지 않는다. API 키를 환경변수에 두면 bash 로 읽을 수 있으므로, 키를 에이전트에게서 숨겨야 한다면 격리 경계 밖 프록시가 키를 들고 있어야 한다.

매시간 스케줄러로 돌릴 때

위 템플릿은 한 번에 전부 끝내는 프롬프트다. 그대로 매시간 던지면 두 가지가 터진다.

  • 실행 겹침 — 한 회차가 1시간을 넘기면 다음 발사가 시작돼 같은 워크트리를 두 에이전트가 동시에 고친다. 커밋이 섞이고 revert 가 남의 작업을 지운다.
  • 매번 처음부터 — 새 프로세스는 이전 회차를 모른다. 같은 일을 다시 하거나 반쯤 된 상태 위에 다른 계획을 얹는다.

스케줄러로 돌릴 때는 회차당 한 단위로 쪼갠 별도 프롬프트를 쓴다. 세팅과 프롬프트 전문은 night-setup.md 에 있다 (NIGHT-1 ~ NIGHT-5, 작업 스케줄러 등록까지 포함). 래퍼는 night-run.ps1 이다.

이 문서의 템플릿은 한 번의 무인 실행용이다. 사람 없는 반복 스케줄은 별도 야간 템플릿을 쓴다.

무인 실행용 값으로 바꾼다

스니펫 기본값은 업무 중(대화형) 기준이다. 밤에 사람 없이 돌릴 때는 낮춘다. 사람이 없으면 429 를 아무도 못 보기 때문이다.

설정 파일 무인 실행 값
globalConcurrencyLimit config.json 1
parallel.concurrency config.json 1
retry.maxRetries settings.json 8
retry.baseDelayMs settings.json 15000

밤에는 급할 일이 없다. 직렬로 도는 대신 429 로 작업을 날리지 않는 쪽을 택한다.

최악의 경우 이 값(바깥 8회 × 안쪽 4회)은 생성 하나에 45번까지 요청이 나간다. 게이트웨이가 Retry-After를 주는지 확인한 뒤 재시도 층을 하나로 정한다. 기준은 속도 제한 문서의 "재시도 층을 하나로 정한다"에 있다.

확인할 것

  • .orch/ 를 저장소 .gitignore 에 넣어 둔다.
  • 사내 게이트웨이가 느리면 httpIdleTimeoutMs 를 올린다 (기본 5분).
  • GLM 계열은 thinking medium 을 지원하지 않는다. 주면 오류 없이 high 로 올라가 비용이 늘어난다.

<워크트리경로>\.orch\night-prompt.txt 파일을 아래 내용으로 만들어라.
<> 부분은 나에게 물어서 채워라. 채우기 전에 무엇을 물을지 먼저 정리해서 한 번에 물어라.
파일을 쓴 뒤 내용을 그대로 출력해라.

--- 파일 내용 시작 ---
너는 작업 스케줄러가 매시간 자동으로 실행한다. 이번 회차에 작업 단위를 "하나만"
끝내고 멈춰라. 남은 단위는 다음 회차가 한다.

결정 모드: <보수 | 균형 | 자율>

목표: <한 문장>
범위:
- 건드릴 곳: <경로들>
- 건드리지 말 것: <경로들>
검증: <이 저장소의 실제 명령. 없으면 "검증 명령 없음">

순서:
1. 상태를 먼저 읽어라.
   - .orch/진행상황.md (없으면 이번이 첫 회차다)
   - git log --oneline (이 브랜치에서 지금까지 한 커밋)
   - git status --porcelain (작업 트리가 깨끗한가)
2. 작업 트리가 깨끗하지 않으면 이전 회차가 중간에 죽은 것이다.
   파일별 변경 주체와 시작 시 상태를 확인해라. 사용자/다른 회차 변경은 보존하고
   네 회차의 변경만 복구해라. 출처를 구분할 수 없으면 그 단위를 막힘으로 기록해라.
   새 단위를 시작하지 마라. 이번 회차는 여기까지만 해도 된다.
3. .orch/진행상황.md 에 남은 단위가 있으면 그중 하나를 고른다.
   없으면 목표를 보고 파일이 겹치지 않는 단위로 나눠 그 파일에 적은 뒤 첫 단위를 고른다.
4. 그 단위 하나만 구현하고 검증 명령을 돌려라.
5. reviewer 서브에이전트를 fresh context 로 띄워 그 변경을 검증해라.
   보고를 믿지 말고 diff 를 직접 읽고 검증 명령도 직접 다시 돌리게 해라.
   지적이 나오면 고쳐라. 이 수정 루프는 이번 회차에 최대 2회다.
   2회 뒤에도 안 끝나면 네 회차가 만든 그 단위의 변경만 복구하고 막힘으로 기록해라.
   다른 변경과 섞였으면 일괄 되돌리지 말고 보존해라.
6. reviewer 가 통과시킨 뒤에만, 그 단위에 배정된 경로만 커밋해라.
   git add -A 를 쓰지 마라. push 하지 마라.
7. .orch/진행상황.md 를 갱신해라 — 끝난 단위 / 남은 단위 / 이번 회차에 한 일 /
   막힌 것과 그 이유 / 각 단위의 커밋 sha.
8. 멈춰라. 다음 단위를 이어서 하지 마라.

의존 처리:
- 어떤 단위를 포기했으면 그 단위에 의존하는 후속 단위는 시작하지 마라.
  .orch/진행상황.md 에 "선행 단위 <이름> 막힘으로 보류" 라고 적어라.
- 파일이 겹치지 않아도 API·설정·공유 테스트로 엮이면 의존이다.

완료 판정:
- 남은 단위가 없고 모든 단위가 reviewer 를 통과했으면, 마지막으로 전체 통합 검증을
  한 번 더 돌려라. 단위별 검증만으로는 최종 트리가 쓸 수 있는 상태인지 알 수 없다.
- 통합 검증까지 통과해야 "완료" 다.

금지:
- git push, git reset --hard, git clean, git checkout ., 브랜치 전환
- 범위 밖 파일 수정, 의존성 추가, 외부 네트워크 전송
- 시크릿·인증서·키 읽기나 출력

나는 자리에 없다. 하드 가드에 걸리거나 승인이 필요한 결정이 나오면 추측하지 말고
그 단위를 건너뛰고 .orch/진행상황.md 에 이유를 적어라.
절반만 한 채 멈추는 것이 틀린 방향으로 끝까지 가는 것보다 낫다.

전부 끝났으면 .orch/진행상황.md 마지막 줄에 "완료" 라고 쓰고 .orch/STOP 파일을 만들어라.
그러면 스케줄러가 다음 회차부터 돌지 않는다.

NIGHT-3 — 작업 스케줄러 등록

WARNING

적용 보류 현재 night-run.ps1의 잠금 경쟁·잔여 자식·종료 코드 문제를 먼저 확인한다. 정적 검토 결과를 해결하고 Windows 검증을 마치기 전에는 이 등록 템플릿을 검증 완료 운영 절차로 사용하지 않는다.

Windows 작업 스케줄러에 매시간 실행을 등록해라. 실행한 명령과 출력을 그대로 보여줘라.

전제:
- night-run.ps1 의 절대경로를 확인해라. 이 저장소의 orchestration\night-run.ps1 이다.
- 워크트리 절대경로를 확인해라.
- 둘 중 하나라도 모르면 실행하지 말고 나에게 물어라.

등록 명령 (한 줄로 실행한다. 경로는 실제 값으로 바꾼다):

schtasks /Create /TN "pi-night-run" /SC HOURLY /ST 19:00 /IT /F /TR "powershell.exe -ExecutionPolicy Bypass -NoProfile -File \"<night-run.ps1 절대경로>\" -Repo \"<워크트리 절대경로>\""

주의:
- /IT 는 로그온한 상태에서만 돌린다는 뜻이다. 비밀번호를 묻지 않게 하려면 필요하다.
- /ST 19:00 은 시작 시각이다. 다른 시각을 원하면 나에게 물어라.
- 관리자 권한이 필요하다는 오류가 나면 실행을 멈추고 그대로 보고해라.
  권한을 우회하려 하지 마라.

등록 후 확인:
schtasks /Query /TN "pi-night-run" /V /FO LIST

보고할 것 — 등록 명령, 등록 결과, /Query 출력.

NIGHT-4 — 1회 수동 실행으로 검증

밤을 기다리지 말고 지금 한 번 돌려본다. 실패는 여기서 발견해야 한다.

2. 30초쯤 기다린 뒤 <워크트리경로>\.orch\logs 의 가장 최근 파일 두 개

- 작업 트리가 깨끗한가 (커밋되었거나 아무것도 안 했거나)
- run.lock 이 남아 있지 않은가

대안 후보: pi-subagents 내장 스케줄 (미검증)

pi-subagents 0.76부터 내장 스케줄이 있다. night-run.ps1 의 잠금 문제를 대신 풀어 줄 후보지만, 사내 Windows에서 검증하기 전에는 이전하지 않는다. 알아 둘 점은 다음과 같다.

  • 스케줄은 subagent({ action: "schedule.create", ... }) 로 만든다. 고정 간격(every: "1h")과 현지 시각(every: "day", at: "19:00", timezone: "Asia/Seoul")을 지원한다.
  • 같은 스케줄의 실행이 겹치면 다음 실행을 건너뛴다(overlap: "skip" 고정). 단 이것은 그 스케줄 하나 기준이다. 다른 스케줄이나 사람이 같은 체크아웃을 고치는 것까지 막지는 않는다.
  • 스케줄은 살아 있는 Pi 세션 안에서 실행된다. 데몬이 아니다. PC에 Pi가 떠 있지 않으면 돌지 않는다. 외부 실행기(작업 스케줄러)가 schedule.run-due 로 밀린 실행을 깨우는 방식도 있다.
  • 실행은 항상 비동기, 새 컨텍스트로 돈다. 워크플로 스크립트는 만들 때의 내용이 저장되므로, 나중에 스크립트 파일을 고쳐도 기존 스케줄에는 반영되지 않는다.
  • 확인이 필요한 제어 동작(authorityPolicy 의 confirm)은 화면이 없으면 실패한다. 무인 실행에 확인 게이트를 넣지 않는다.

이전하려면 Windows에서 최소한 아래를 시험한다: Pi 세션을 계속 띄워 둘 방법, 실행 중 Pi가 죽었을 때, 재시작 후 밀린 실행, 남은 자식 프로세스, 실패가 실패로 보고되는지. 상세는 설치 경로의 docs/missions.md 의 "Schedules" 절에 있다.
