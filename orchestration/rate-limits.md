# 속도 제한 아래에서 오케스트레이션하기 (500K TPM · 50 RPM)

> 사내 오픈 웨이트 모델은 **분당 500,000토큰, 50요청**으로 묶여 있다. 에이전트는 매 요청마다 대화 전체를 다시 보내므로, 거의 항상 요청 수보다 토큰 수가 먼저 찬다. 이 문서는 그 한도 안에서 자식 에이전트를 몇 개까지, 어떻게 굴릴지 계산하고 설정하는 방법을 정리한다. 마지막 절은 집에서 Claude·ChatGPT 구독(5시간 창)으로 쓸 때의 차이다.

## 왜 필요한가 (Why)

한도를 넘으면 게이트웨이는 429를 돌려준다. 재시도로 넘기지 못하면 그 자식 하나가 맡은 작업 단위가 통째로 날아간다. pi-subagents는 속도 제한 오류에서 다른 모델로 넘어가지 않는다. 사람이 보고 있으면 동시성을 낮추면 되지만, 무인 실행에서는 아무도 모른 채 밤이 지나간다.

그리고 한도는 생각보다 빨리 찬다. 개인 PC의 pi 세션 로그 643건(사내 모델이 아닌 다른 provider)을 [`rate-usage.py`](./rate-usage.py)로 집계해 보면 이렇다.

| 지표 | 값 |
|---|---|
| 응답당 평균 토큰 (캐시 적중 포함) | 72,366 |
| 토큰이 가장 많았던 60초 구간: 기록된 응답 수 | 49 |
| 같은 구간의 토큰 (캐시 적중 포함) | 6,817,619 |
| 같은 구간의 토큰 (캐시 적중 제외) | 77,779 |
| 캐시 제외 토큰이 가장 많았던 60초 구간 (다른 구간) | 241,138 |

이 패턴을 사내 게이트웨이에 그대로 올리면 결과는 **게이트웨이가 캐시 적중 토큰을 TPM에 세는지**에 크게 좌우된다. 센다면 가장 바쁜 구간이 한도의 13배를 넘고, 안 센다면 가장 바쁜 구간도 한도의 절반 아래다. 그래서 설정보다 먼저 [운영팀에 확인](#1-게이트웨이-운영팀에-먼저-확인한다)해야 한다.

## 핵심 개념 (What)

### 요청 하나가 대화 전체다

게이트웨이가 세는 단위는 사람의 질문 수도, 에이전트 수도, 도구 호출 수도 아니다. **모델 호출 수**다. 모델이 다음 응답을 만들 때마다 호출이 한 번 일어난다. 한 응답에 도구 호출 여러 개가 묶일 수 있고, 그 결과를 받으면 다음 호출이 이어진다. 호출마다 시스템 프롬프트, 도구 정의, 지금까지의 대화(압축·제거 후 남은 부분), 방금 받은 도구 결과가 다시 들어간다.

그래서 세션이 길어지면 누적 토큰은 호출 수의 제곱에 비례해 는다. 첫 호출의 입력이 `C0`, 호출마다 대화가 `g`씩 늘고, 출력이 평균 `o`라면 N번 호출의 합은 다음과 같다.

```text
입력 합 = N × C0 + g × N × (N − 1) / 2
출력 합 = N × o
```

예를 들어 시작 컨텍스트 20K, 호출마다 2K씩 늘고, 출력 1K로 20번 호출하면 입력 780K + 출력 20K = **800K 토큰**이다. 마지막 컨텍스트는 58K에 불과한데 누적은 그 열네 배다. 이 20번을 3분 안에 하면 분당 약 27만 토큰으로, 세션 하나가 한도의 절반 넘게 쓴다.

### 어느 한도가 먼저 차나

요청 하나가 평균 `q` 토큰을 쓰면, 분당 보낼 수 있는 요청 수는 `min(50, 500,000 ÷ q)`이다. 경계는 **요청당 10,000토큰**이다. 그보다 크면 TPM이 먼저 찬다. 코딩 에이전트의 요청은 거의 항상 이보다 크다.

| 요청당 토큰 | TPM 기준 분당 요청 | RPM 기준 | 먼저 차는 쪽 | 고르게 보낼 때 간격 |
|---:|---:|---:|---|---:|
| 20,000 | 25 | 50 | TPM | 2.4초 |
| 60,000 | 8.3 | 50 | TPM | 7.2초 |
| 150,000 | 3.3 | 50 | TPM | 18초 |
| 400,000 | 1.25 | 50 | TPM | 48초 |

이 값은 요청을 완벽하게 고르게 보냈을 때의 평균이다. 게이트웨이가 "직전 60초"를 세는 방식이면 400K 요청 두 개가 48초 간격으로 들어와도 한 구간에 겹쳐 한도를 넘는다. 실제로는 간격을 이보다 넉넉히 둬야 한다.

**HCP-Big과 HCP-Medium의 컨텍스트 창이 100만 토큰이라는 사실은 여기서 함정이 된다.** 창이 넓다고 컨텍스트를 채우면, 요청 하나로 분당 한도 전체를 쓴다. 넓은 창은 가끔 필요한 여유이지 평소에 쓸 공간이 아니다.

### 자식은 몇 개까지 돌릴 수 있나

자식 하나가 요청 하나를 처리하는 주기(모델 응답 + 도구 실행 시간)가 `L`초라면, 그 자식은 분당 `60 ÷ L`번 요청하고 `60 × q ÷ L` 토큰을 쓴다. 부모와 watchdog 몫을 먼저 떼어 두고 남은 예산을 나누면 된다.

```text
자식 수 ≤ min( 남은 RPM × L ÷ 60 ,  남은 TPM × L ÷ (60 × q) )
```

계산 예다. 다른 harness와 측정 오차를 감안해 한도의 80%인 400K TPM / 40 RPM만 쓰기로 하고, 그중 100K / 10을 부모와 watchdog에 남긴다. 자식에게는 300K / 30이 돌아간다.

| 자식의 요청당 토큰 | 요청 주기 | 자식 하나의 TPM | 동시에 돌릴 수 있는 자식 |
|---:|---:|---:|---:|
| 60K | 30초 | 120K | **2** |
| 60K | 10초 | 360K | **1도 벅참** (속도를 늦춰야 함) |
| 150K | 30초 | 300K | **1** |
| 400K | 30초 | 800K | **0** (컨텍스트를 줄여야 함) |

결론은 단순하다. **동시성 설정보다 자식의 컨텍스트 크기와 요청 주기가 먼저다.** 이 문서는 자식의 요청당 60K를 잠정 목표로 쓴다. 절대 기준은 아니다. 요청당 150K라도 30초마다 한 번이면 하나는 돌고, 요청이 크고 주기까지 짧으면 동시성을 1로 낮춰도 혼자서 한도를 넘는다. 판단은 언제나 `q`와 `L`과 남은 예산으로 한다.

### 캐시 적중 토큰을 세는가

에이전트는 같은 앞부분을 계속 다시 보내므로 프롬프트 캐시 적중이 많다. pi 로그에서도 입력의 대부분이 `cacheRead`다. 문제는 이것을 한도에 세는지가 게이트웨이마다 다르다는 점이다.

- OpenAI는 캐시된 입력도 TPM에 센다. 싸고 빠를 뿐 한도에서 빠지지 않는다.
- LiteLLM 프록시의 기본 TPM은 입력 + 출력이다. 별도로 켜는 베타 ITPM/OTPM 제한기는 응답 후 정산에서 캐시 적중을 뺀다.
- 사내 게이트웨이가 무엇을 쓰는지, 어떤 모드인지는 모른다.

확인하기 전까지는 **캐시 적중도 센다고 가정한다.** 안전한 쪽으로 틀리는 편이 낫다.

### pi와 pi-subagents가 막아 주는 것, 못 막는 것

가장 중요한 사실은 **pi에 분당 토큰·요청 제한기가 없다**는 것이다. 아래 설정은 전부 "몇 개를 띄울지"나 "얼마나 기다릴지"를 정할 뿐, 분당 사용량을 직접 조절하지 않는다. 여러 pi 세션과 다른 harness는 서로의 존재를 모른다.

| 설정 | 파일 | 막는 것 | 못 막는 것 |
|---|---|---|---|
| `globalConcurrencyLimit` | `config.json` | 한 실행 안에서 동시에 도는 자식 수. 기본 20 | 다른 실행·세션·프로세스, 부모·watchdog 호출, 분당 토큰 |
| `parallel.concurrency` | `config.json` | 병렬 그룹의 동시 실행 수. 기본 4 | 자식 하나의 호출 빈도 |
| `maxActiveAsyncRunsPerSession` | `config.json` | 한 부모 세션의 동시 비동기 실행 수. **기본은 무제한** | 포그라운드 실행, 실행 안의 자식 수 |
| `maxSubagentSpawnsPerRun` | `config.json` | 한 실행에서 띄우는 자식 총수. 기본 64 | 자식 하나의 턴 수, 토큰 |
| `maxSubagentSpawnsPerSession` | `config.json` | 한 부모 세션 전체의 자식 총수. 기본 무제한 | 다른 세션 |
| `toolBudget` | 호출 옵션 또는 `config.json` | 자식의 도구 호출 수. `soft`에서 마무리하라고 알리고, `hard` 뒤에는 도구를 막는다 | 토큰, 분당 요청 |
| `usageBudget` | 호출 옵션 (워크플로) | 보고된 누적 토큰이 `hard`를 넘으면 **다음** 자식을 띄우지 않는다 | 이미 도는 자식, 분당 한도. 캐시 토큰은 합산에서 빠진다 |
| `retry.*` | `settings.json` | 일시 오류에서 다시 시도 | 첫 요청의 진입 속도. 바깥쪽 재시도에는 지터(jitter)가 없다 |
| `watchdog` | `settings.json` | 턴 경계 검토 | 그 자체가 추가 모델 호출이다. 세션 로그에 사용량이 남지 않는다 |

### 재시도는 두 겹이다

pi에는 재시도 층이 두 개 있다. 바깥쪽 `retry.maxRetries`는 에이전트 단위로 다시 시도하고, 안쪽 `retry.provider.maxRetries`는 HTTP 요청 단위로 다시 시도한다. 둘 다 모든 오류를 재시도하면 곱해진다.

- 현재 스니펫(바깥 6회, 안쪽 4회): 생성 하나에 최악 `(1+6) × (1+4) = 35`번 HTTP 요청이 나간다. 바깥쪽 대기만 8+16+32+64+120+120 = 360초다.
- 야간 값(바깥 8회, 안쪽 4회): 최악 45번이다.

두 층은 성격도 다르다. 안쪽은 서버가 보낸 `Retry-After` 헤더를 따르고, 헤더가 없으면 지터를 섞은 짧은 대기(최대 8초)를 쓴다. 단 서버가 요구한 대기가 `maxRetryDelayMs`(스니펫 60초)를 넘으면 기다리지 않고 바로 실패한다. 바깥쪽은 지터 없이 2배씩 늘린다. 여러 자식이 동시에 429를 받으면 똑같은 시각에 다시 몰려 들어갈 수 있다.

반복되는 429는 "재시도로 회복되고 있다"는 신호가 아니라 "부하를 줄여야 한다"는 신호다.

## 어떻게 하는가 (How)

### 1. 게이트웨이 운영팀에 먼저 확인한다

이 답에 따라 아래 숫자가 전부 바뀐다. ⟨확인⟩ 항목이다.

1. **한도의 단위**는 무엇인가? API 키, 계정, 팀, 모델 별칭, 백엔드 배포 중 무엇인가? `my-local-provider`와 `itc-vlm`이 같은 한도를 나눠 쓰는가?
2. **무엇을 세는가?** 입력만, 출력만, 합계, 아니면 입력·출력 따로인가? **캐시 적중 토큰**과 thinking 토큰을 세는가?
3. **출력은 언제 세는가?** 실제 생성량인가, 요청의 `max_tokens`를 미리 예약하는가? 예약이면 언제 돌려받는가?
4. **구간 방식**은? 달력 1분 고정, 직전 60초 슬라이딩, 토큰 버킷 중 무엇인가? 순간 버스트 상한이 따로 있는가?
5. **429와 실패한 요청도 한도에 드는가?** 끊긴 스트림, 게이트웨이 내부 재시도는?
6. 429 응답에 **`Retry-After`** 헤더가 오는가? 남은 한도를 알려 주는 헤더가 있는가? 한도 소진(영구)과 일시 혼잡을 구분하는 오류 코드가 있는가?
7. 동시 처리 중인 요청 수(in-flight) 상한이 따로 있는가? 대화형 작업 몫을 따로 떼어 줄 수 있는가?
8. 게이트웨이의 요청·사용량 로그를 받아 볼 수 있는가? pi 로그와 대조하는 데 필요하다.

확인 전에는 이렇게 가정한다. 키 하나에 모든 모델과 모든 harness가 묶여 있고, 캐시 적중도 세고, 직전 60초 슬라이딩 방식이다.

### 2. 지금 부하를 잰다

설정을 바꾸기 전에 실제로 얼마나 쓰는지 본다. [`rate-usage.py`](./rate-usage.py)는 pi 세션 로그에서 모델 응답마다 남는 `usage`를 모아 분당 요청과 토큰을 계산한다. 표준 라이브러리만 쓰고, 대화 내용은 읽어도 출력하지 않는다.

```powershell
# 사내 PC (PowerShell). 최근 2시간, 사내 provider 만
python .\orchestration\rate-usage.py --hours 2 --provider my-local-provider

# 한도를 바꿔 보고 싶으면
python .\orchestration\rate-usage.py --hours 8 --rpm 50 --tpm 500000
```

출력에서 볼 것은 셋이다.

- **응답당 평균 토큰**: 위 "자식은 몇 개까지" 계산의 `q`다.
- **임의의 60초 구간 최대 TPM**: 캐시 포함과 제외가 따로 나온다. 운영팀 답에 맞는 쪽을 본다.
- **80% 넘긴 분**: 이 값이 0이 아니면 다른 harness와 겹칠 때 429가 난다.

이 수치는 기록된 모델 응답 수와 보고된 사용량에서 낸 **추정치**이고, 게이트웨이가 센 값과 다르다. 다음은 집계에서 빠진다.

- watchdog 검토 호출. 세션에 사용량을 남기지 않는다.
- 안쪽 HTTP 재시도. 응답 하나 안에서 일어나서 따로 남지 않는다.
- 같은 키를 쓰는 Claude Code, 다른 경로에 저장된 세션.

반대로 다음은 집계에 들어간다.

- 요청을 보내지 못한 로컬 오류. 응답 한 건으로 남을 수 있다.
- 같은 폴더 아래의 다른 pi 세션. 전부 합산된다.

한도를 지켰는지 판정할 때는 게이트웨이 로그만 근거로 쓴다.

### 3. 예산을 나눠서 정한다

전체 한도를 다 쓰지 않는다. 측정 오차, 다른 harness, 순간 버스트를 위해 20%를 남기고, 그 안에서 부모 몫을 먼저 뗀다. 아래는 출발점이지 검증된 최적값이 아니다.

| 프로필 | 목표 사용량 | 부모·watchdog 몫 | 자식 몫 | 자식의 요청당 토큰 목표 |
|---|---|---|---|---|
| 업무 중, 혼자 사용 | 400K TPM / 40 RPM | 100K / 10 | 300K / 30 | 60K 이하 |
| 무인 실행 (야간) | 300K TPM / 25 RPM | 100K / 10 | 200K / 15 | 60K 이하 |
| 다른 harness와 나눠 씀 (둘이 반씩) | 각자 200K TPM / 20 RPM | 60K / 5 | 140K / 15 | 60K 이하 |

야간 목표를 낮게 잡은 이유는 아무도 429를 보지 못하기 때문이다. 밤에는 급할 일이 없으니 느리게 돌고 작업을 날리지 않는 쪽을 고른다.

나눠 쓰는 경우의 "반씩"은 **모두가 지킬 때만** 성립한다. pi는 다른 harness의 사용량을 모른다. 가능하면 harness마다 다른 키를 받는 것이 가장 깔끔하다. 그게 안 되면 같은 시간대에 둘을 동시에 무겁게 돌리지 않는다.

### 4. 설정값으로 옮긴다

| 설정 | 파일 | 업무 중 (현재 스니펫) | 무인 실행 | 컨텍스트가 크고 캐시도 센다면 |
|---|---|---|---|---|
| `globalConcurrencyLimit` | `config.json` | 2 | 1 | 1 |
| `parallel.concurrency` | `config.json` | 2 | 1 | 1 |
| `maxActiveAsyncRunsPerSession` | `config.json` | 1 | 1 | 1 |
| `maxSubagentSpawnsPerRun` | `config.json` | 12 | 8 | 8 |
| `watchdog.children.enabled` | `settings.json` | false | false | false |
| `watchdog.cadence` | `settings.json` | 없음 | 없음 | 없음 |

업무 중 기본값을 2로 두는 이유는 평소 작업이 `scout → worker → reviewer`처럼 순차라서다. 실제로 2를 쓰는 것은 `/parallel-review` 같은 팬아웃뿐이다. 다만 운영팀이 캐시 적중도 센다고 답하고, `rate-usage.py`로 잰 `q`와 `L`을 위 공식에 넣었을 때 자식 둘이 예산을 넘으면 업무 중에도 1로 내린다.

`maxSubagentSpawnsPerSession`은 기본이 무제한이다. 한 세션에서 자식을 끝없이 띄우는 실수를 막고 싶으면 `config.json`에 `24` 정도를 넣는다. 다 쓰면 사람이 `grant-spawn-budget`으로 늘려 줘야 한다.

### 5. 컨텍스트를 작게 유지한다

동시성을 조정하는 것보다 효과가 크다. 요청당 토큰을 절반으로 줄이면 같은 한도에서 자식을 두 배 돌릴 수 있다.

- **자식은 새 컨텍스트로 띄운다.** `worker`는 기본이 fresh이고, `reviewer`는 프롬프트에서 fresh를 요구한다. `oracle`은 기본이 fork라서 부모 대화를 통째로 물려받는다. 큰 판단이 아니면 `oracle`을 자주 부르지 않는다.
- **부모 컨텍스트에는 자식의 실행 기록 전체 대신 요약과 필요한 결과만 넣는다.** 기본 반환 방식은 자식의 최종 출력을 그대로 부모에게 넣는다(inline). 결과가 길 것 같으면 출력 경로를 주고 `outputMode: "file-only"`로 띄운다. 그러면 부모에게는 "어디에 저장했다"는 한 줄만 돌아온다. 부모에게 그 파일 전체를 읽으라고 시키면 이 이점이 사라지니, 필요한 절만 읽게 한다.
- **`scout`의 결과는 파일로 받는다.** 호출 지점 목록 같은 긴 결과는 위 방식으로 파일에 저장하고, 워커에게는 그 경로를 준다. 자식에게 "파일에 써라"라고만 말해서는 반환 방식이 바뀌지 않는다. `outputMode`를 함께 지정한다.
- **도구 출력을 줄인다.** `grep -r` 대신 경로를 한정한 `rg`를, 전체 테스트 대신 해당 테스트를, 로그 전체 대신 `tail`을 쓴다. 도구 결과는 한 번 들어오면 다음 요청마다 다시 실린다. [AGENTS.md 규칙](./agents-md.snippet.md)의 탐색 규칙이 이것이다.
- **작업이 바뀌면 세션을 새로 연다.** 앞 작업의 대화가 다음 작업의 모든 요청에 실린다. pi가 알아서 하는 압축(compaction)은 모델 창 크기를 기준으로 하므로, 100만 창 모델에서는 너무 늦게 일어난다. 작업 경계에서 직접 새 세션을 연다.
- **`AGENTS.md`는 짧게 쓴다.** 모든 자식의 모든 요청에 들어간다. 한 줄이 늘면 그 줄 × 전체 요청 수만큼 토큰이 는다.

### 6. 정찰과 워크플로에 상한을 건다

읽기만 하는 역할에는 도구 호출 상한을 걸어도 안전하다. 예를 들어 scout에 `toolBudget: { soft: 20, hard: 30, block: "*" }`를 주면 20번째 호출에서 마무리하라는 안내를 받고, 30번 뒤에는 도구를 못 쓰고 최종 답만 낸다.

```text
scout 으로 <경로> 아래에서 <대상>의 호출 지점을 찾아라.
output 은 .orch/scout.md, outputMode 는 "file-only" 로 해라.
options.toolBudget 은 { soft: 20, hard: 30, block: "*" } 로 해라.
```

워크플로 전체에는 `usageBudget`으로 토큰 상한을 둘 수 있다. 단 이것은 **분당 한도가 아니라 누적 총량**이고, 넘으면 다음 자식을 띄우지 않을 뿐 도는 자식은 멈추지 않는다. 합산에서 캐시 토큰이 빠지므로 게이트웨이가 세는 양보다 작게 나온다.

워커나 고칠 권한이 있는 리뷰어에는 빡빡한 상한을 걸지 않는다. 검증 직전에 도구가 막히면 반쯤 고친 상태로 끝난다. 패키지 문서도 같은 이유로 쓰기 역할에는 걸지 말라고 권한다.

### 7. 429가 보이면 이렇게 한다

| 보이는 것 | 뜻 | 할 일 |
|---|---|---|
| 가끔 재시도 표시가 뜨고 곧 진행된다 | 한도 근처에서 일시 초과 | 그대로 둔다 |
| 재시도가 자주 보인다 | 지속적으로 한도 근처 | 동시성을 1로 낮춘다. `rate-usage.py`로 요청당 토큰을 확인한다 |
| 재시도 후에도 실패로 끝난다 | 재시도 대기보다 한도 회복이 느리다 | 옆에서 도는 다른 harness를 멈춘다. 자식 컨텍스트를 줄인다 |
| 대기 없이 바로 실패한다 | 서버 요구 대기가 `maxRetryDelayMs`를 넘었거나 한도 소진(영구) | 운영팀에 오류 코드와 헤더를 확인한다 |
| 야간 실행이 회차마다 같은 단위에서 실패한다 | 그 단위의 요청이 너무 크다 | 단위를 더 잘게 쪼갠다 |

무인 실행에서는 재시도 횟수를 늘려서 숨기지 않는다. 회차당 한 단위로 자른 [야간 템플릿](./night-setup.md)은 실패한 단위를 기록하고 멈추므로, 다음 회차가 한도가 회복된 뒤 다시 시도한다.

### 8. 재시도 층을 하나로 정한다

두 층을 둘 다 크게 두면 위에서 본 것처럼 35~45번까지 곱해진다. 운영팀의 6번 답(`Retry-After` 헤더를 주는가)을 받은 뒤 하나를 주 재시도로 고른다.

- **헤더를 준다면:** 안쪽(provider)이 헤더를 따르므로 이쪽을 주로 쓴다. `retry.provider.maxRetries`를 유지하고, `maxRetryDelayMs`를 서버가 요구하는 최대 대기보다 크게 둔다. 바깥쪽 `retry.maxRetries`는 2~3으로 줄인다.
- **헤더를 주지 않는다면:** 안쪽의 짧은 대기(최대 8초)는 분 단위 한도에서 효과가 없다. pi 문서의 권장대로 `retry.provider.maxRetries`를 0으로 두고, 바깥쪽을 `maxRetries: 3`, `baseDelayMs: 15000`으로 둔다. 대기는 15·30·60초가 된다.

현재 스니펫은 2026-09-22 사내 검증을 통과한 값이라 그대로 두었다. 위 판단은 운영팀 답을 받은 뒤 적용한다.

## 집에서 구독 요금제로 쓸 때는 다르다

집에서는 Claude(Pro·Max)와 ChatGPT(Plus·Pro) 구독으로 Claude Code, Codex CLI, 그리고 그 구독에 연결한 pi를 쓴다. 한도의 모양이 회사와 완전히 다르다. 아래는 2026-10-24에 공식 도움말에서 확인한 내용이다. 구독 한도는 자주 바뀌므로 숫자보다 구조를 기억한다.

### 한도의 모양

| | 회사 게이트웨이 | Claude 구독 | ChatGPT 구독 (Codex) |
|---|---|---|---|
| 짧은 창 | **1분**: 500K 토큰, 50요청 | **5시간** 롤링 세션 한도 | Plus: **5시간** 한도. Pro: 현재 5시간 한도 없음 |
| 긴 창 | 없음 | **주간** 한도. Max는 Fable 모델 주간 한도가 따로 있다 | **주간** 한도가 적용될 수 있다 |
| 단위 | 토큰과 요청 수 | 공개된 고정 수치 없음. 모델·대화 길이·기능에 따라 차감 | 공개된 고정 수치 없음. 모델별 "5시간당 로컬 메시지" 추정 범위만 공개 |
| 함께 쓰는 곳 | 같은 키의 모든 harness | claude.ai(웹·데스크톱·모바일)와 Claude Code가 한 한도를 나눠 쓴다 | 로컬 Codex와 클라우드 작업이 한 한도를 나눠 쓴다. 클라우드 작업이 더 많이 쓴다 |
| 남은 양 보기 | `rate-usage.py`, 게이트웨이 로그 | Claude Code `/usage`, `/status`, statusline의 `rate_limits` | Codex CLI `/status`, `/usage`, 사용량 대시보드 |
| 다 쓰면 | 429. 구간 방식에 따라 수십 초~1분 안에 다시 받을 수 있는 경우가 많다(운영팀 확인) | 멈춘다. 진행 중인 단계를 마무리하게 해 주는 기능은 단계적으로 배포 중이라 계정마다 다르다. 재설정을 기다리거나 사용 크레딧(유료)을 켠다 | 진행 중인 턴은 공정 사용 범위에서 마무리될 수 있다. 재설정, 크레딧, 업그레이드 |

가장 큰 차이는 **막혔을 때 기다리는 시간의 단위**다. 회사의 분당 한도는 대개 짧게 기다리면 다시 받을 수 있다. 그래서 재시도와 속도 조절이 답이다. 다만 한도 소진이 영구 오류로 오는지, 언제 풀리는지는 운영팀 확인이 필요하다. 구독에서 한도에 닿으면 몇 시간을 기다려야 하고, 주간 한도라면 며칠이다. 재시도해도 소용이 없다. 대신 분 단위 속도는 회사만큼 신경 쓰지 않아도 된다. 단 구독에도 짧은 혼잡 제한이나 동시성 제한이 있을 수 있다.

### 자식은 같은 한도를 나눠 쓴다

새 컨텍스트, 새 프로세스, 새 워크트리는 새 구독이 아니다. **같은 인증 계정이면 provider 이름이나 프로세스가 달라도 같은 한도를 쓴다.**

- Claude Code의 서브에이전트와 agent team 팀원은 각자 요청을 보내고, 전부 **본 대화와 같은 한도**에서 차감된다.
- pi의 `openai-codex` provider는 ChatGPT 로그인(OAuth)으로 ChatGPT 백엔드를 쓴다. API 키 요금제가 아니라 **그 계정의 구독 한도**를 쓴다.
- pi의 `pi-claude-bridge` 패키지는 Claude Agent SDK, 즉 로컬 Claude Code를 거쳐 Claude를 부른다. 로컬 Claude Code가 구독으로 로그인돼 있으면 그 구독 한도를 쓴다. 환경 변수에 `ANTHROPIC_API_KEY`가 있으면 API 요금제로 바뀔 수 있다.
- pi-subagents의 자식은 실행마다 모델과 provider를 고른다. 같은 계정으로 띄운 자식 열 개는 한 한도에서 열 번 차감된다. 한도가 따로 잡히려면 **다른 구독 계정이나 다른 과금 경로**여야 한다. provider 이름만 다른 것으로는 부족하다. 예를 들어 pi의 `openai`와 `openai-codex`가 같은 ChatGPT 계정으로 로그인돼 있을 수 있다.

Anthropic의 2026-10-07 도움말 갱신은 Agent SDK, `claude -p`, 서드파티 앱에서도 구독 한도를 계속 쓸 수 있다고 밝혔다. 단 개발자가 자기 앱에 Claude.ai 로그인을 넣거나 사용자의 구독 자격 증명을 모아서 대신 호출하는 것은 금지다. 본인이 공식 Claude Code에 직접 로그인해서 쓰는 경로는 허용된다. 브리지 패키지가 이 조건을 지키는지는 패키지마다 확인해야 한다.

### 집에서의 운영 방식

**1. 시간 예산으로 나눈다.** 분당 토큰 대신 "이 창에서 몇 %를 쓸지"를 정한다. 예를 들어 5시간 창이 60% 남았고 앞으로 3시간 일한다면, 20%를 남기고 40%를 3시간에 나눠 시간당 약 13%를 쓴다. 큰 팬아웃 전과 큰 단위가 끝난 뒤에 확인한다. 수시로 들여다볼 필요는 없다.

**2. 주간 한도를 따로 본다.** 5시간 창이 회복돼도 주간 한도는 회복되지 않는다. 주간이 40% 남았고 4일 더 쓸 계획이면 10%를 남기고 하루 7.5%를 쓴다. 큰 작업을 하루에 몰아서 돌리면 남은 날에 막힐 수 있다.

**3. 병렬은 "빨리 끝나는 값"이 있을 때만.** 회사에서는 분당 한도가 병렬을 막지만, 집에서는 병렬이 창을 빨리 소진하는 것이 문제다. 자식을 늘리면 끝나는 시간은 줄 수 있어도 창이 닫히는 시점도 앞당겨진다. 시간이 얼마나 줄고 총소비가 얼마나 느는지는 직접 재 본다. 서로 독립인 작업이고 빨리 끝나야 할 이유가 있을 때만 병렬로 돌린다.

**4. 역할마다 모델 크기를 나눈다.** 회사의 티어링과 같은 원리다. Claude라면 단순 탐색은 Haiku, 일상 구현은 Sonnet, 어려운 설계와 위험한 변경의 검토만 Opus에 맡긴다. 기본 상속으로 모든 자식이 가장 비싼 부모 모델을 쓰지 않게 한다. Codex도 기계적인 작업은 작은 모델, 어려운 변경과 검토는 큰 모델을 쓴다. Fast·Ultrafast 모드는 한도를 2.5~8배 빨리 쓰므로 예산이 빠듯할 때는 Standard를 쓴다.

**5. 두 회사의 구독을 서로 다른 한도로 쓴다.** Claude로 쓰고 Codex로 검토하면 한쪽 한도만 빨리 닳는 것을 막는다. 계열이 다른 모델로 검토하는 효과도 있다. 다만 계열이 다르다고 오류가 독립이라는 보장은 없다. 검증 명령을 직접 다시 돌리는 원칙은 그대로다.

**6. 유료 연장은 미리 정해 둔다.** Claude의 사용 크레딧, ChatGPT의 크레딧은 한도 뒤에도 계속 쓰게 해 주지만 별도 요금이다. 무인으로 돌리기 전에 크레딧 자동 구매와 지출 상한을 확인한다. 의도하지 않았다면, 한도에 닿으면 체크포인트를 남기고 멈추는 쪽이 맞다.

**7. 무인 실행은 창 시작에 맞춘다.** 밤새 돌릴 작업은 5시간 창이 거의 새로 시작될 때 걸고, 한 회차가 창 하나를 넘지 않게 단위를 자른다. 회사 야간 템플릿의 "회차당 한 단위" 원칙이 집에서도 그대로 쓸모 있다. 한도에 닿은 회차는 실패로 기록하고 멈추고, 다음 창에서 이어 간다.

### 남은 양을 화면에 띄운다

Claude Code의 statusline 스크립트는 stdin으로 `rate_limits.five_hour`와 `rate_limits.seven_day`를 받는다. 각각 `used_percentage`(0~100)와 `resets_at`(Unix 초)이 있다. 구독 사용자에게만, 그리고 세션의 첫 응답 뒤에만 나타난다. 값이 없다고 무제한이라는 뜻이 아니다.

```bash
#!/usr/bin/env bash
# ~/.claude/statusline.sh : 5시간·주간 사용률을 한 줄로 보여 준다
in=$(cat)
five=$(jq -r '.rate_limits.five_hour.used_percentage // empty' <<<"$in")
week=$(jq -r '.rate_limits.seven_day.used_percentage // empty' <<<"$in")
reset=$(jq -r '.rate_limits.five_hour.resets_at // empty' <<<"$in")
printf '5h %s%%  7d %s%%' "${five:-?}" "${week:-?}"
[ -n "$reset" ] && printf '  (5h 재설정 %s)' "$(date -r "$reset" +%H:%M 2>/dev/null || date -d "@$reset" +%H:%M)"
echo
```

`~/.claude/settings.json`의 `statusLine`에 `{"type": "command", "command": "~/.claude/statusline.sh"}`로 등록한다. Codex CLI는 `/status`와 `/statusline`으로 같은 정보를 본다.
