# 결정 정책 (사전 승인)

> 저장소 **바깥**(예: `~/.orch-policy/<저장소>.md`)에 두고 읽기 전용으로 준다. 무인 실행 중 워커가
> 결정 앞에서 멈추는 대신, 부모 세션이 **이 파일을 근거로** 답한다.

## 이 파일을 작업 트리 안에 두지 않는다

에이전트가 쓸 수 있는 곳에 정책을 두면 **자기 승인 근거를 자기가 고칠 수 있다.** 실수로든 목표 달성
압박으로든 한 줄만 바꾸면 C가 A가 된다. 정책 원본은 작업 트리 밖에 두고, 결정 로그
(`.orch/결정로그.md`)만 작업 트리 안에 쓴다.

**다만 트리 밖 + `chmod 444` 는 실수 방지 수준이다.** 에이전트는 실행한 사용자 권한을 그대로 가지므로
`bash` 로 권한을 되돌리거나 파일을 교체할 수 있다. 이것을 실제 통제로 삼으려면 둘 중 하나가 필요하다.

1. **정책 본문을 프롬프트에 그대로 붙여넣는다.** 부모 컨텍스트에 들어온 원문이 기준이 되므로 파일을
   바꿔도 의미가 없다. 가장 싸고, 무인 실행에서는 이 방법을 권한다.
2. 별도 사용자/컨테이너로 실행해 정책 파일을 에이전트 UID가 쓸 수 없게 만든다.

## 판정 순서 — 반드시 이 순서로

**위에서 걸리면 아래는 보지 않는다.** A를 먼저 보면 "기존 인증 코드를 그대로 복사"처럼
A(기존 패턴 따르기)이면서 동시에 C(인증·권한)인 변경이 승인되어 버린다.

```
0. 하드 가드에 해당하나?      → 해당하면 즉시 중단. 모드와 무관. 예외 없음.
1. D 표에 "구체적인" 답이 있나? → 있으면 그 답을 쓰고 끝. (사람이 이미 결정한 것이다)
2. C 목록에 해당하나?         → 해당하면 아래 "모드" 표대로. A/B 를 보지 않는다.
3. A 목록에 있나?             → 있으면 승인.
4. 그 외                      → B 기본값 규칙으로 정한다.
```

D가 C보다 앞인 이유는, D는 **사람이 이 저장소를 보고 미리 내린 결정**이기 때문이다. C는 "사람에게
물어라"는 뜻이고, D는 이미 물어서 받은 답이다. 순서를 뒤집으면 미리 답해둔 것이 무시된다.

**단 "구체적인" 답만 유효하다.** D의 답이 그 결정을 지목해야 한다.
"타임아웃 기본값은 30초" 는 유효하다. "알아서 해" 는 무효다 — 범위가 없는 사전 승인은 승인이 아니다.
무효인 D 항목은 없는 것으로 치고 2단계(C)로 내려간다. 하드 가드는 D로 해제되지 않는다.

## 모드 — 하나만 남기고 지운다

프롬프트에 `결정 모드: <이름>` 으로 적는다. 하드 가드(0단계)는 어느 모드에서도 동일하다.

| 모드 | C를 만나면 | C 목록 적용 범위 |
|------|-----------|-----------------|
| `보수` | 전체 실행을 멈춘다 | C 전체 |
| `균형` (기본) | 그 작업 단위만 중단, 나머지 단위는 계속 | C 전체 |
| `자율` | 멈추지 않는다. B 규칙으로 스스로 정하고 진행 | **하드 가드만.** 나머지 C 항목은 B로 내려온다 |

세 모드가 실제로 다른 지점은 **C 목록의 적용 범위**다. `균형`과 `자율`이 "나머지는 계속"으로 같아
보이면 모드를 나눌 이유가 없다. `자율`은 C를 좁혀서 더 많이 스스로 정하는 모드다.

### `자율` 모드

"전부 자가 판단"은 **"전부 허용"이 아니라 "멈추지 않음"** 이다.

- C 목록 중 **하드 가드가 아닌 항목**(공개 인터페이스 변경, 기존 동작 변경 등)은 B 규칙으로 스스로 정한다.
- 확신 60% 미만 규칙은 끈다. 대신 **로그에 확신도를 숫자로 적는다.**
- 하드 가드에 걸리면 그 작업 단위를 되돌리고 `[SKIP-HARD]` 로 기록한 뒤 다음 단위로 간다.
  우회로를 만들어 돌아가지 않는다. 건너뛰는 것과 우회하는 것은 다르다.
- 결정 로그는 선택이 아니라 **필수**다. 멈춤 지점이 없는 만큼 사후 추적이 유일한 안전망이다.

## 0. 하드 가드 — 모드와 무관, 예외 없음

되돌릴 수 없는 것들이다. 판단 대상이 아니라 경계다.

- `git push`, 태그 push, 원격 브랜치 조작
- `git reset --hard`, `git clean`, `git checkout .`, 브랜치 전환, 작업 트리 밖 파일 수정
- DB 마이그레이션 **실행**, 데이터 삭제·이동, 운영 API 호출
- 시크릿·인증서·키 읽기·출력·전송
- 외부 네트워크 전송 (사내 HCP 게이트웨이 외)

## C. 자가 판단 금지 (`보수`·`균형`에서 중단, `자율`에서는 B로 내려옴)

- 공개 인터페이스 변경 (API 시그니처, 응답 스키마, CLI 플래그, 설정 키 이름)
- DB 스키마 **정의** 변경 (실행은 하드 가드)
- 의존성 추가·제거·버전 변경
- 인증·권한·암호화 **로직** 변경
- 성능과 정확성이 맞바꿔지는 선택
- 기존 동작 변경 (버그 수정처럼 보여도, 누군가 그 동작에 기대고 있을 수 있다)
- <이 저장소에서 추가로 금지할 것>

## D. 예상 질문에 미리 답해둔 것

> 퇴근 전 2분에 채우는 칸. 비어 있어도 된다. **구체적인 답만 C를 해제한다.**

| 예상 질문 | 미리 준 답 |
|---|---|
| <예: 타임아웃 기본값을 몇 초로?> | <예: 30초. 기존 http 클라이언트와 맞춰라.> |
| <예: 기존 함수 시그니처를 바꿔야 하면?> | <예: 바꾸지 말고 래퍼를 추가해라.> |

## A. 미리 승인한 것 — 묻지 말고 진행

> 위 0·C 단계를 통과한 것에만 적용된다.

- 이름 짓기(변수·함수·파일명). 기존 저장소 관례를 따를 것.
- 기존 패턴을 그대로 따르는 선택. 같은 일을 하는 코드가 이미 있으면 그 모양을 복사한다.
- 테스트 추가. 기존 프레임워크·디렉터리 구조를 따를 것.
- 주석·docstring 추가, 오탈자 수정.
- 에러 메시지 문구.
- 이미 있는 유틸리티/헬퍼 재사용 (새로 만들지 않고).
- <이 저장소에서 추가로 미리 승인할 것>

## B. 기본값 규칙 — 위 어디에도 안 걸리면 이 규칙으로 정한다

1. **되돌리기 쉬운 쪽**을 고른다. 두 안이 비슷하면 diff가 작은 쪽.
2. **기존 코드에 더 가까운 쪽**을 고른다. 일관성이 우아함을 이긴다.
3. **범위를 넓히지 않는 쪽**을 고른다. 겸사겸사 고치지 않는다.
4. 확신이 60% 미만이면 C로 간주한다. (`자율` 모드에서는 이 규칙을 끄고 확신도를 로그에 적는다)

## 결정 로그 의무

스스로 정한 **모든 결정**을 `.orch/결정로그.md` 에 한 줄씩 남긴다.

```markdown
- [A-2] `parseTimeout` 이름 채택 — 근거: 같은 파일 `parseRetry` 관례. 되돌리기: 이름만 변경. (src/http/config.ts:41)
- [B-1] 재시도 3회 선택 (확신 70%) — 대안: 5회. 근거: 기존 기본값과 동일. (src/http/retry.ts:18)
- [SKIP-HARD] 마이그레이션 실행 필요 → 하드 가드. 단위 되돌림(커밋 abc1234 revert).
  영향: 신규 컬럼 없이는 이 기능 동작 안 함. (migrations/0042_add_retry.sql:1)
```

담을 것: **어느 규칙으로** 정했는지 / 무엇을 골랐는지 / 탈락시킨 대안 / 근거 / **되돌리는 법** / `file:line`.

근거를 한 줄로 못 쓰겠으면 그건 C다.
