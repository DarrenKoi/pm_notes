# Codex와 상의한 기록

herdr로 pane (`codex-advisor`)을 열어 codex (GPT-6.2-Sol high)를 띄우고 상의함. 요청문은 `codex-rN-prompt.md`, 답 전문은 `codex-rN.md`.

## 1회차: 배경만 주고 독립적으로 후보 뽑기

- 준 것: 배경 (9명 파트, 해 온 일, 15~20명 요청, 파견 구조, AI Solution 팀 지향, 네 가지 뼈대, 폐쇄망). 내 후보와 다른 문서는 보여 주지 않음
- 받은 것: 후보 27개 (하는 일, 파트로 어려운 이유, 효과, 지표), "파트로도 되잖아" 위험 표시 6개 (업무 진단, Agent 지침, 교육, 문화 확산, PoC 방법론, 구매 수요 취합), 파트와 팀의 권한 차이 표 (일반 형태이고 사내 확인이 필요하다고 명시)
- 요지: 부문장에게 먼저 낼 것은 과제 접수와 우선순위 조정, 확대 과제의 인력과 예산 배정, 출시한 솔루션의 운영 책임. 교육, 문화, 방법론은 그 자체로는 승격 근거가 약함

| 받아들인 것 | 이유 |
|------------|------|
| 운영 책임 (장애 접수, 복구, 백업)을 리스트 맨 앞으로 | 근거 문서에 직접 기록이 있는 막힘 (1인 개발과 운영 병행, 백업 미충원)과 맞음 |
| 파견자 평가의 공동 관리, 복귀 전 인수 검증을 별도 장치로 | 사용자 전제 (파견 구조)에서 부문장이 물을 질문과 맞음 |
| 지표 후보 (접수부터 결정까지 일수, 인수 후 90일 사용 유지율, 백업 검증률) | 기준선 없이도 승격 뒤 바로 잴 수 있음 |
| 교육과 문화 확산은 "기획"을 빼고 "정례 운영, 적용 추적"만 남김 | 기획은 지금 파트로 하고 있음 |

| 받아들이지 않은 것 | 이유 |
|-------------------|------|
| 분기별 임원 회의에 조정 안건 상정 (R1 25번)을 독립 항목으로 | 보고 라인은 사내 직제 확인 전이라 리스트 항목으로 약속하기 어려움. 과제 창구 항목에 흡수 |
| 도구와 교육 구매 수요 통합 (R1 27번) | Codex 스스로 위험 표시. 효과가 부문 단위가 아님 |

## 2회차: 합친 목록에서 빠진 것과 "파트로도 되는 일" 지적

- 준 것: 내 후보 35개, Codex 후보 27개, `evidence.md`, 근거에서 나온 불편한 사실 네 가지 (파트라서 막혔다는 문장은 없음, ARC 기획안이 정규 조직 신설을 배제함, 겸직은 리스크 사유로 쓰지 않음, 직제와 예산 정보 없음)
- 받은 것: 추가 후보 2개 (같은 인력과 성과를 두 조직이 함께 잡을 때의 조정 절차, 백업 담당자의 단독 대응 검증), 후보별로 뺄 범위와 남길 범위, 최종 9개 제안과 대안 비교 (인원만 충원한 파트, TF), ARC 모순에 대한 답변 문안, 시기 배치
- 요지: 9개 중 대부분이 "인원을 충원하고 같은 책임을 위임한 파트"로도 가능해 승격 근거가 약함. 판단 기준은 "기한 없는 반복 수요에 대해 누가 인력과 운영비를 배정하고 과제 충돌을 조정하며 장애와 인수 결과를 책임지는가"

| 받아들인 것 | 이유 |
|------------|------|
| 판단 기준을 "상시 책임 단위"로 잡음 | 리스트 전체를 꿰는 한 문장이 됨. 기획서 요약과 1절에 씀 |
| ARC 모순의 답: ARC의 판단 (검증 전 과제에 조직을 새로 만들지 않음)은 유지하고, 이번 요청은 이미 운영 중인 일의 상시 책임을 정하는 것 | 같은 부문장이 두 문서를 다 보므로 앞뒤가 맞아야 함 |
| 백업 담당자의 단독 대응 검증을 운영 책임 항목의 지표로 | 백업 "지정"만으로는 실제로 되는지 알 수 없음 |
| 같은 인력을 AX Team과 ARC TF가 함께 잡는 중복 배정 확인 | ARC TF 개발 3명이 AX Part 소속이라 실제로 생길 문제. 5절 경계와 8절 리스크에 넣음 |
| 시기 배치: 승격 직후 (운영 책임, 창구, 파견, 자원), 1년 안 (확대, 평가, FDE 시범, 교육), 그 뒤 (자립) | 사용자 전제의 두 단계와 맞음 |
| 5절에 대안 비교표를 두고 인원만 충원안과 TF가 되는 부분을 숨기지 않음 | 부문장이 먼저 떠올릴 대안이므로 먼저 답하는 편이 신뢰를 얻음 |

| 받아들이지 않은 것 | 이유 |
|-------------------|------|
| "증원한 파트에 같은 책임과 위임을 줄 수 있다면 그 방식이 먼저"라는 문장을 기획서 본문에 그대로 넣기 | 요청서가 스스로 대안을 권하는 꼴이 됨. 대신 5절 비교표에 "인원만 충원"안의 되는 것과 안 되는 것을 사실대로 적고, 사내 직제 확인 항목을 open-questions 1번으로 올림 |
| FDE 시범을 "1년 안"에 배치 | 사용자 전제는 FDE가 검토 단계. 중앙 운영 백업이 선 뒤여야 하므로 "그 뒤"로 두되 검토 착수는 1년 안으로 적음 |
| 외부 LLM API 도입을 전제에서 제외 | 받아들임에 가까움. 리스트 항목으로는 넣지 않되, 사용자 메모에 2027 사내 도입 예정이 있어 리스크나 일정에는 언급하지 않음 |

## 3회차: 초안의 가장 약한 곳 세 군데


- 준 것: 초안 (`01-team-proposal.md` 1차본), `evidence`, `grilling.md`. 부문장 입장에서 가장 약한 곳 세 군데, 아직 "파트로도 되잖아"가 나올 항목, 근거와 어긋난 수치, 문체 점검을 요청
- 받은 것 (전문은 `codex-r3.md`): 결론은 "현재 초안 기준으로는 승인 보류"
  1. 팀 직제가 꼭 필요하다는 결론이 근거보다 앞섬 ("상시 책임 단위가 지금은 없음", "사람 수와 상관없이 팀 직제가 있어야 되는 일", "예산과 정원을 요구하는 단위가 팀임")
  2. 정원 요청에 팀장 보임안과 실제 가용 인력이 빠짐 (15명과 20명의 차이, ARC TF와 겹치는 인력)
  3. 파견을 보내는 팀이 질 업무 공백과 복귀 조건이 빠짐 ("사람을 잃지 않고"라는 표현, 본인 선택으로 잔류)
  - 그 밖에: 한 사람의 회고를 파트 전체로 넓혀 쓴 문장, 수치의 시점 표시, ARC 계획을 확정처럼 쓴 표현, 8번의 일정 충돌 (첫해에 복귀 파견자가 없음), 표 안의 마침표와 "Lesson Learned" 표기

| 받아들인 것 | 반영한 곳 |
|------------|----------|
| 사례의 범위를 "확인한 사례"로 한정, "막혔다"와 "파트라서 막혔다"를 구분 | 1절 문제 표 아래 문단, 3절 1, 3, 6번 |
| 수치에 시점 표시 (2026-10 보고 기준), 10% 단축은 전망으로, 60명은 검토 중으로 | 요약, 1절, 2절, 4절 |
| ARC TF는 승인 보고 전 초안의 계획, "종료 때 인수"가 아니라 "검증을 통과한 범위의 인수" | 1절, 3절 1번, 6절 ARC 일정 표 |
| 승격 뒤 6개월, 12개월 점검과 ARC의 2027-06, 2027-12를 따로 표기 | 6절 |
| 파견 전 합의 항목에 기존 업무의 대체 담당, 납기 책임을 추가. 복귀와 잔류는 양 팀 협의. "사람을 잃지 않고" 삭제 | 3절 2번, 4절 대상별 효과, 5절 파견 운영 원칙 |
| 8번의 접점: 첫해는 각 팀이 지정한 담당자, 그 뒤 복귀 파견자 | 3절 8번 |
| 인원을 기능별로 나눈 표, ARC TF 3명을 따로 셈, 개인별 투입 시간 합산 | 5절 인원 규모별 업무 범위 |
| 표 안의 문장 정리, "Lesson Learned"를 "추진 과정에서 확인한 점"으로, 요약의 문단을 개조식 목록으로 | 요약, 2절 |
| 3절 각 항목의 "충원한 파트라면"에 파트로 되는 범위를 더 넓게 인정 (백업 지정, 접수와 집계, 한 과제의 TF) | 3절 1, 2, 3, 6, 7번 |

| 받아들이지 않은 것 | 이유 |
|-------------------|------|
| FDE의 Palantir, OpenAI 언급 삭제 ("제공된 근거로 검증하지 못함") | 웹 검색으로 출처를 확인했음 (The Pragmatic Engineer). 지시서가 외부 사례는 출처와 함께 쓰라고 했으므로 출처를 적고 유지 |
| 요약 첫머리를 "증원한 파트와 상위 팀에 같은 책임을 줄 수 있다면 그 방식을 먼저 적용"으로 쓰기 | 요청서가 대안을 먼저 권하는 모양이 됨. 대신 요약에 "요청의 형태" 갈림 두 줄로 넣어 직제 확인 결과에 따라 정하게 함 |
| 1~5번을 "팀 전용으로 분류하기 어렵다"며 구분을 없애기 | 구분은 유지하되 직제 확인 뒤 위임 가능한 항목은 "가"에서 뺀다고 3절 머리에 적음. open-questions 1번으로 올림 |
