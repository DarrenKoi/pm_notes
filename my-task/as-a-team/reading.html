0101-team-proposal.md

AX Team 승격 기획안

AX Part를 AX Team으로 승격하면 추진할 수 있는 업무 11가지와 승격 요청 사항

1. 배경

  • 기반기술센터는 업무와 성격이 다른 조직이 모인 부문으로, "As a One Team"을 기조로 운영 중
  • AX 확산에는 지식 자산화 병행 필수: 조직마다 흩어진 지식을 자산으로 모아야 AX를 센터 전체로 확산 가능
  • 양산총괄 등 다른 부문은 지식 자산화를 장기간 추진해 왔고 현재 그 성과를 활용 중
  • 솔루션의 장기 발전에는 백업 인력 필요: 현재 솔루션마다 개발과 운영을 한 사람이 담당, 운영 대응과 기능 고도화의 병행에 한계
  • 백업 인력이 있어야 담당자 부재에도 운영 유지, 담당자는 고도화와 신규 개발에 시간 확보
  • 연구소, 양산총괄 등 다른 부문은 AX 조직을 15~20명 규모의 팀으로 운영 중
  • 기반기술센터도 1~2년 안에 AX Team 필요. 더 늦기 전에 지금 구성하자는 취지
  • 정기 인사는 연 1회 (가을~겨울): 이번 시기를 넘기면 정규 인원 충원 (전배)은 다음 정기 인사까지 대기
  • 정기 인사 뒤에는 파견만 가능하고 상반기가 지나면 파견 기피 증가. 2026-12 안에 승격 결정 필요

2. 팀이 되면 추진할 수 있는 업무

가. 인사, 예산 권한이 있어야 추진할 수 있는 업무

# 업무 추진 내용 기대 효과
1 TF 결과 인수와 솔루션 상시 운영 솔루션마다 책임자와 백업 지정, ARC (Auto Recipe Creation) TF가 검증한 결과 인수 TF 종료 뒤에도 검증된 자산 유지, 운영 요청으로 인한 신규 개발 지연 축소
2 현업 개발 인력의 순환 파견 수용 파견자가 자기 과제와 함께 합류, 과제는 AX Team이 책임지고 추진, 성과는 원소속 팀과 공동 실적 현업 과제의 추진 속도 확보, 복귀 인력이 원소속 팀의 AX 거점 역할
3 센터 AX 과제 창구와 우선순위 조정 접수 창구 통합, 수락 기준 공개, 분기마다 과제와 성과 집계 보고 부문장님께 센터 AX 과제 일괄 보고, 중복 과제 축소
4 연간 인력, 예산, 연산 자원 요구와 배정 운영 솔루션과 신규 과제의 자원 수요를 연간 계획으로 요구, 승인 자원을 과제에 배정 자원 부족으로 대기하는 과제 축소
5 보안, 배포 검토와 공통 평가의 대표 창구 Agent의 승인, 중단, 복구 기준을 승인 조직과 한 번 합의해 여러 과제에 적용 과제마다 반복되는 심사 축소, 현장 배치 기간 단축

나. 팀 규모가 되어야 추진할 수 있는 업무

# 업무 추진 내용 기대 효과
6 여러 역할을 같이 배치하는 대규모 과제 범위가 큰 과제에 3명 이상 배치, 1인 1 Agent 개발에서 팀 단위 개발로 전환 현업 엔지니어의 반복 업무 시간 절감
7 AX 교육 정례 운영과 사내 강사, 멘토 양성 반복 과정은 사내 강사가 운영, 업체 과정은 사내에 없는 주제로 한정 업체 의존 축소, 센터 환경에 맞춘 교육
8 교육 수료자의 현업 적용 지원 수료자의 첫 과제를 90일 동안 지원, 팀별 AX 담당자 연결망 운영 2027년 고급 과정 (60명 검토 중)이 현업 적용으로 연결
9 현업 배치 개발 개발 인력이 부족한 팀의 과제에 AX Team 엔지니어 1명을 1개월 이내로 배치해 개발 후 인도, 그 팀 구성원이 배우면서 운영까지 맡도록 가이드 개발 인력이 부족한 팀의 AI/DT 과제 추진, 현업 팀의 운영 역량 확보
10 도메인 지식을 넣은 자체 모델 개발 (fine-tuning) 회사 기밀 문서는 외부 LLM API 사용 불가, 사내 LLM API로 제공할 자체 모델 개발 도메인 업무에서 Agent 정확도 향상
11 엔지니어 업무의 지식 자산화와 DB 관리 엔지니어의 업무 지식을 수집, 정리해 DB로 구축, 담당 인력이 상시 관리 AX 확산의 기반 확보, Agent와 자체 모델이 활용할 도메인 지식 축적

FDE (Forward Deployed Engineer) 조사와 AX Team 적용안

FDE는 "한 고객, 여러 기능"을 맡는 현장 배치 엔지니어와 "한 기능, 여러 고객"을 맡는 플랫폼 엔지니어를 짝으로 운영하는 방식이며, 사내에서는 "현업 배치 개발"이라는 이름으로 AX Team 엔지니어 1명이 개발 인력이 부족한 팀의 과제를 1개월 이내에 개발해 인도하고 운영은 그 팀이 맡는 방식으로 적용

1. Why: 조사 배경

  • 기획안 업무 9번 (현업 배치 개발)은 한 줄 설명만 있고, 운영 방식과 근거 미정
  • 9번의 문제 인식: 요청을 받아 만드는 방식은 현업의 실제 업무 흐름을 늦게 알게 되고, 만든 뒤 현업 인수에 시간 소요
  • 안 하면 생기는 일: PoC와 현업 적용 사이의 간격 유지, 개발 인력이 없는 현업 팀의 AI/DT 과제 대기
  • 이 문서의 범위: FDE를 처음 만든 회사와 도입한 회사가 직접 밝힌 내용 정리 (2절), 우리 조직 조건에 맞춘 운영안 (3절)

2.4 운영 방식

항목 확인한 내용 출처
팀 크기 고객별 팀은 4~5명의 소규모, 자율적으로 빠르게 운영 [P6]
짝 구성 FDE (구축)와 Deployment Strategist (문제 정의, 사용자 교육, 보고)가 한 팀. 제품 디자이너도 참여 [P4]
선후배 구성 경력 있는 리드가 후배와 한 조 (pod)를 이루는 방식 (Ramp FDE 책임자 인터뷰) [S1]
과제 진행 3단계 범위 탐색 (현장 며칠, 사용자 옆에서 업무 흐름 파악, 가치가 큰 영역 선정) → 검증 (평가 기준 합의, 평가 문항 구축, 결과 보고) → 전달 (주 며칠 현장, 가장 작은 단위의 끝에서 끝까지 동작하는 결과물부터) (OpenAI FDE 책임자 인터뷰) [S1]
검증을 먼저 하는 이유 범위 논의에서 고객이 설명한 내용과 실제 데이터, 시스템 상태가 다른 경우가 잦아, 막히는 지점을 먼저 확인하고 범위 조정 [S1]
배치 기간 표준 기간을 밝힌 1차 자료는 확인하지 못함. 개인 사례로 6개월, 1년 근무 언급 [P1], [P6]
제품 환원 경로 1 FDE가 현장에서 수작업으로 하던 일을 제품팀이 도구로 만들고, 그 도구 묶음이 플랫폼 제품으로 발전 [P6]
제품 환원 경로 2 FDE가 핵심 제품에 직접 코드 기여. 큰 기능 요청은 제품팀 로드맵과 맞춰 검증, 제품팀이 변경 리뷰 [P1]
제품 환원 경로 3 현장에서 설정한 제품과 작업 흐름을 다른 FDE에게 공유, 다음 팀은 더 다듬어진 기준 제품에서 시작 [P2]
제품 환원 경로 4 연구팀과 격주 공유, 제품 책임자 대상 격주 보고, 현장 기록 채널, 분기 합숙 (OpenAI FDE 책임자 인터뷰) [S1]
현장 판단 FDE가 필요한 기능을 핵심 플랫폼에 넣을지, 빨리 전달할 수 있는 맞춤 개발로 할지 수시로 결정 [P1]
성과 측정 고객 목표 지표에 준 영향 (Palantir), 운영 도입과 업무 개선 (OpenAI), "고객이 성공할 때 성공, 출시한 기능 수가 기준이 아님" (Ramp) [P1], [O1], [S1]

2.5 한계와 실패 유형

유형 당사자가 말한 내용 출처
맞춤 개발 누적 FDE만 있으면 수천 개의 대형 맞춤 솔루션을 무기한 유지해야 하는 상태에 도달. 플랫폼 조직이 일반화를 맡아야 성립 [S2]
맞춤 개발 누적 핵심 플랫폼에 고객별 로직이 촉수처럼 붙는 "octopus" 상태 경계. 고객마다 일회성 개발 금지를 운영 원칙으로 둠 (Ramp FDE 책임자 인터뷰) [S1]
일반화의 어려움 "지나친 일반화와 부족한 일반화를 계속 반복함". 공통 기술 하나가 나오기까지 맞춤 구현 10~20건이 필요했던 제품도 있음 [P5]
기술 부채 FDE의 코드는 빨리 끝내는 데 맞춰져 기술 부채와 임시 처리 발생. 확장과 안정성은 제품 엔지니어의 몫 [P6]
제품팀과의 갈등 FDE와 핵심 제품팀의 관계는 모순이 겹친 갈등 관계. FDE는 맞춤 개발을 권장받고, Dev는 FDE를 무시하라는 말도 들음 [P5]
범위 팽창 전달할수록 고객의 요구가 커지고 과제 범위가 달마다 다시 정의됨 [P5]
소수 인력 의존 특정 인물 몇 명이 없었다면 성립하지 않았을 것이라는 key-man risk 인정 [P5]
형식만 모방 FDE를 도입했지만 사업 전략이 따라가지 않으면 시스템 통합 비용만 떠안고 장기 효과는 없음 [P5]
수요 초과 도입 3개월 만에 고객 수요가 몰려 대상 고객을 선별하기로 결정 (OpenAI FDE 책임자 인터뷰) [S1]
비용 맞춤 작업은 초기에 매출 총이익률을 낮추고 지출을 키움 (투자사 분석) [S3]
이동 부담 출장비가 장기간 통제되지 않았다는 회고, 공고상 출장 25~50% [P6], [P3]
현장의 장애물 고객 조직 안에서 일할 때의 장애물은 대부분 기술이 아니라 조직 내부의 이해관계 [P6]
  • 인력 소진 (burnout)을 당사자가 직접 말한 1차 자료는 확인하지 못함. 위 표의 이동 부담이 간접 근거

  • Palantir의 Deployment Strategist 일부는 사내 팀과 사내 문제에도 배치 [P4]

2.7 조사에서 얻은 결론

  • FDE는 혼자 서는 제도가 아님: 현장 배치 (Delta)와 일반화 담당 (Dev)이 짝이어야 맞춤 개발 누적을 피함 [P1], [P6], [S2]
  • 현장 팀은 구축 담당과 문제 정의 담당의 조합 [P4]
  • 과제는 범위 탐색, 검증, 전달 순서로 진행하고, 검증 단계에서 막히는 지점을 먼저 확인 [S1]
  • 성과는 만든 기능 수가 아니라 고객의 목표 지표로 측정 [P1], [O1]
  • 사내 적용 사례의 공통 원칙: 과제 주인은 현업, 결과물은 공통 도구로, 종료 조건은 미리 합의 [G1]

3. How: AX Team 적용안

사내에서는 FDE라는 말 대신 "현업 배치 개발"로 부릅니다. 3.1은 2026-11-26에 정한 운영 방향이고, 3.2부터는 그 방향에 맞춘 작성자의 제안입니다. 근거가 없는 값은 ⟨확인⟩으로 남겼습니다.

피드백 현업 팀의 피드백 수집, 다음 배치의 개선에 사용

3.2 외부 FDE와의 차이

항목 외부 FDE (조사 결과) 현업 배치 개발
고객 외부 회사 같은 센터의 현업 팀
목적 고객 성과와 제품 확장, 매출 개발 인력이 없는 팀의 과제 추진, 현업 팀의 운영 역량 확보
규모와 기간 구축 담당과 문제 정의 담당의 조합, 개인 사례는 6개월에서 1년 1명, 1개월 이내
근무 위치 고객 현장 근무, 출장 25~50% 자리 이동 없음, 메신저와 대면 미팅
운영 운영 전환까지 책임 인도 뒤 현업 팀이 운영, 멘토링으로 준비
일반화 담당 제품 개발 조직 (Dev) AX Team의 플랫폼과 운영 기능 (업무 1번, 5번)
모델 자사 최신 모델 사내에 올린 오픈 모델만 사용. 사외 LLM API 사용 불가
데이터 고객 데이터 직접 연결 문서 대부분이 DRM 보호, 화면 캡처와 Vision 모델을 거치는 추출 경로 필요
Agent 운영 회사마다 다름 엔지니어가 자리에 있는 상태에서 운영하는 자동 대응
  • 조사 결과에서 가져온 것: 과제 주인은 현업, 결과물은 공통 도구로, 종료 조건은 미리 합의 [G1], 성과는 현업의 목표 지표로 측정 [P1], [O1]
  • 조사 결과와 다르게 둔 것: 규모를 1명과 1개월로 줄이고 현장 상주를 두지 않음. 과제 범위를 작게 잡는 것이 전제

3.3 순환 파견과의 관계

항목 순환 파견 (업무 2번) 현업 배치 개발 (업무 9번)
방향 현업 인력이 AX Team으로 AX Team 인력이 현업 과제로
움직이는 사람 현업 팀의 개발 인력 AX Team 엔지니어 1명 (자리 이동 없음)
기간 2~5년 1개월 이내
대상 팀 개발 인력이 있는 팀 개발 인력이 부족하거나 없는 팀
과제 책임 AX Team (성과는 원소속 팀과 공동 실적) 개발과 인도는 AX Team, 운영은 현업 팀
남는 것 AX Team 안의 도메인 지식, 복귀자의 거점 역할 현업 팀의 운영 역량, AX Team의 공통 자산
  • 역할 구분: 파견은 개발 인력이 있는 팀의 사람과 과제를 안으로 모으는 제도, 현업 배치 개발은 파견을 보낼 수 없는 팀을 지원하는 수단

3.4 진행 방식 (제안)

과제 선정 기준

기준 확인 방법 근거
업무 3번 창구로 접수되고 수락 기준 통과 접수 기록 수요 초과 때 선별이 필요했던 사례 [S1]
1개월 안에 개발과 인도를 마칠 수 있는 범위 착수 전 범위 합의 3.1의 기간
현업 팀이 배우고 운영할 구성원 지정 팀장 합의 변경의 책임은 주인에게 있다는 원칙 [G1]
효과의 기준선 측정 가능 (대상 업무의 현재 소요 시간, 건수) 착수 전 측정 고객 목표 지표로 성과 측정 [P1]
필요한 데이터와 화면에 접근 가능, DRM 문서는 추출 경로 확보 착수 전 확인 설명과 실제 데이터가 다른 사례 [S1]
사내 오픈 모델로 달성할 수 있는 범위 착수 전 시험 검증을 전달보다 먼저 두는 방식 [S1]

단계

단계 하는 일
착수 전 범위, 인도 기준, 운영할 구성원 합의. 데이터 접근과 사내 모델로 가능한지 확인
개발 (1개월 이내) AX Team 엔지니어가 개발, 현업 구성원은 메신저와 대면 미팅으로 판단 기준을 제공하며 구조와 운영 방법 학습
인도 운영 문서와 중단, 복구 절차 인도. 현업 구성원의 단독 운영 확인
인도 뒤 정해진 기간의 문의 대응 ⟨확인: 인도 뒤 문의 대응 기간⟩, 현업 팀의 피드백 수집
  • 1개월 안에 끝나지 않는 과제: 범위를 줄이거나 업무 3번 창구에 새 과제로 접수 (업무 6번 대규모 과제 후보)
  • Agent 운영 원칙: 인도하는 Agent는 엔지니어가 자리에 있는 상태에서 돌아가는 자동 대응. 승인, 중단, 복구 기준은 업무 5번에서 합의한 기준 적용

현업 팀이 내야 하는 것

  • 운영을 맡을 구성원과 그 시간 ⟨확인: 주당 투입 시간⟩
  • 데이터, 화면, 문서에 대한 접근 권한과 보안 절차 협조
  • 판단 기준: 현업 엔지니어가 정답과 평가 문항 제공
  • 기준선 수치: 대상 업무의 현재 소요 시간과 건수
  • 종료 때의 피드백

공통 자산으로 되돌리는 방법

대상 방법 연결 업무
코드 일회성 스크립트 대신 공통 도구를 개선해 사용 [G1]. 저장 위치는 ⟨확인: 현업 팀이 운영하는 코드의 저장 위치⟩ 1번
공통화 판단 같은 요구가 두 번째 팀에서 나오면 공통 기능으로 올릴지 검토 [P5], [P6] 1번, 6번
평가 문항 과제에서 만든 평가 문항과 정답을 공통 평가에 등록 5번
도메인 지식 개발 중 파악한 업무 흐름, 판단 기준, 용어를 지식 DB에 등록 11번
피드백 현업 팀의 피드백을 AX Team 안에서 공유, 다음 배치의 진행 방식에 반영 3번

성과 지표

지표 뜻 현재 값
착수부터 인도까지 기간 1개월 이내 달성 여부 ⟨확인: 요청을 받아 만든 기존 과제의 같은 기간, 비교 기준선⟩
현업 엔지니어 절감 시간 대상 업무의 전후 비교 착수 전 측정
인도 뒤 현업 자체 운영 인도 뒤 AX Team 도움 없이 처리한 문의와 수정의 비율 인도 뒤 측정
지원한 팀 수 현업 배치 개발로 지원한 팀 0 (착수 전)
재사용 만든 것을 다른 팀 과제가 다시 쓴 건수 0 (착수 전)
  • 만든 기능 수는 지표로 쓰지 않음 (Palantir, OpenAI, Ramp 모두 고객 쪽 결과로 측정 [P1], [O1], [S1])

3.5 예상되는 문제와 대응 (제안)

문제 대응
1명 배치라 담당자 부재 때 과제 중단 기간이 1개월 이내라 영향 제한, AX Team 안에 대신 맡을 사람 지정
개발 인력이 없는 팀이라 인도 뒤 수정이 어려움 멘토링 범위를 운영과 간단한 수정으로 한정, 그 이상의 수정은 업무 3번 창구로 접수
운영을 배운 구성원의 이동, 부재 운영 문서 인도, 팀장이 대신 맡을 사람 지정
범위가 1개월을 넘게 커짐 착수 전 범위 합의, 추가 요구는 새 과제로 접수 [P5]
팀마다 맞춤 개발이 쌓임 공통 도구 우선 사용, 공통화 검토 [S1], [S2]
사내 오픈 모델의 성능이 과제 요구에 못 미침 착수 전 시험, 부족분은 업무 10번 (자체 모델)의 요구 사항으로 기록
DRM 문서의 추출 품질 부족 착수 전 추출 경로 시험, 대상 문서 범위 축소
요청 급증 업무 3번 창구의 수락 기준 적용, 동시 배치 건수의 상한 설정 ⟨확인: 상한⟩
배치 인원이 맡던 운영 솔루션의 공백 운영 백업 지정이 끝난 인원만 배치

3.6 기획안의 다른 업무와의 연결

업무 연결
1번 솔루션 상시 운영 배치 인원의 운영 백업이 전제. 인도한 결과물은 현업 팀이 운영하므로 AX Team의 운영 대상은 늘지 않음
2번 순환 파견 파견을 보낼 수 없는 팀에 대한 지원 수단
3번 과제 창구 과제 접수와 선정, 추가 요구의 접수 경로
5번 보안, 배포, 공통 평가 승인, 중단, 복구 기준을 받아 쓰고, 과제별 평가 문항을 제공
6번 대규모 과제 1개월 범위를 넘는 과제의 다음 경로
7번, 8번 교육 교육 수료자가 운영을 맡을 구성원 후보. 멘토링 경험을 사내 강사, 멘토 양성에 활용
10번 자체 모델 사내 오픈 모델이 부족했던 업무와 평가 문항 제공
11번 지식 자산화 개발 중 파악한 업무 흐름과 판단 기준 등록
