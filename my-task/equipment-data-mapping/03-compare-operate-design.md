# 장비 데이터 매핑 Agent — 비교·관리·운영 설계

> 지도가 만들어진 뒤의 일을 정한다. 여러 장비의 값을 나란히 놓아 차이를 찾고, 관리할 파라미터를 가려내고, 같은 장비를 주기적으로 다시 보고, 모든 모델과 장비로 넓힌다. 2단계 이후(P2~P4)를 구현하는 사람이 읽는 문서다. 설계 초안이며 실제 장비 데이터로 검증된 것이 아니다.

## 왜 필요한가? (Why)

지도는 "무엇이 어디에 있나"까지다. 이 과제가 끝내 남기려는 것은 **관리해야 하는 파라미터의 목록**이고, 그러려면 지도 위에 값을 올려 장비끼리 비교하고, 그 결과를 엔지니어가 확인하고 조치할 수 있는 모양으로 내야 한다. 그리고 한 번으로 끝나면 낡는다. 같은 장비를 다시 보고 달라진 곳을 갱신해야 하며, 한 모델에서 된 것을 다른 모델로 옮길 수 있어야 한다.

이 문서는 [지도 만들기 설계](./02-map-design.md)의 지도 스키마, 필드 분류, 추출 계약을 그대로 쓴다. 용어의 정의는 그 문서에 있다.

## 핵심 개념 (What)

| 만드는 것 | 뜻 | 파이프라인 단계 |
|---|---|---|
| 값 스냅샷 | 구조 지도의 필드마다 그 장비가 그 시점에 가진 값 | ⑦ |
| 차이 후보표 | 장비 무리에서 벗어난 값의 목록. 엔지니어가 판정한다 | ⑧ |
| 관리 대상 파라미터 목록 | 엔지니어가 "관리해야 한다"고 확정한 값과 그 기준 | ⑧ 이후 |
| 변경 보고 | 지난 회차와 달라진 것 | 정기 점검 |
| 개념 대응표 | 벤더가 다른 필드를 공통 개념에 연결한 것 | ⑨ |

## 어떻게 사용하는가? (How)

### 비교 규칙 — "벗어났다"를 무엇으로 정하는가

| 정할 것 | 규칙 |
|---|---|
| 비교군 | S/W 버전과 옵션 구성이 같은 장비끼리만 묶는다. 조건이 다른 장비는 따로 묶거나 뺀다 |
| 장비 대수가 적을 때 | 최소 대수 ⟨확인⟩에 못 미치면 "벗어남"을 판정하지 않는다. 값을 나란히 놓은 표만 내고 사람이 본다 |
| 숫자 값 | 무리의 가운데에서 떨어진 정도로 본다. 평균과 표준편차는 벗어난 한 대에 끌려가므로 가운뎃값 기준을 쓴다 |
| 글자·선택 값 | 다수와 다른 장비를 올린다 |
| 모든 장비가 같은 값 | 후보에 올리지 않되 "전 장비 동일"로 기록한다. 다음 점검 때 달라지면 그때 올린다 |
| 값이 없는 장비 | 숫자로 채우지 않는다. "없음" 자체를 차이로 따로 올린다 |
| 시간에 따라 움직이는 값 | 상태 분류의 값(온도, 누적 카운터, 부품 사용 시간)은 읽은 시각이 다르면 그것만으로 달라진다. 장비들을 가까운 시간대에 함께 읽고, 그러지 못한 값은 장비끼리 비교하지 않고 그 장비의 지난 값과만 비교한다. 값마다 읽은 시각을 적는다 |
| 장비마다 다른 것이 정상인 값 | 장비 고유 번호나 개체별 교정값은 무리와 비교하지 않고 그 장비의 지난 값과만 비교한다 |
| 의미 있는 차이의 크기 | 통계적으로 벗어났다는 것과 실무에서 문제가 된다는 것은 다르다. 문턱은 엔지니어가 정한다 |
| 후보의 수 | 필드가 수천 개면 우연히 벗어나 보이는 값도 많다. 회차마다 올리는 후보 수에 상한 ⟨확인⟩을 두고 순위가 높은 것부터 낸다 |

무리의 분포를 그대로 관리 허용 범위로 쓰지 않는다. 분포는 "지금 어떻게 흩어져 있나"이고 허용 범위는 "어디까지 괜찮은가"다. 뒤의 것은 엔지니어가 정한다.

### 차이 후보표 — 엔지니어가 확인하고 조치할 수 있는 모양

⑧의 산출물이 "값이 다르다"의 나열이면 쓰이지 않는다. 후보 하나마다 엔지니어가 다음 행동을 정할 수 있을 만큼의 정보를 붙인다.

| 열 | 내용 |
|---|---|
| 필드 | 뜻, 분류(설정·교정·상태), 검증 상태 |
| 어디에 있나 | 파일 종류와 파일 안의 위치. 장비에서 바로 열어 볼 수 있게 |
| 장비별 값 | 전체 장비의 값을 한 줄로. 무리의 중심과 퍼짐 |
| 벗어난 장비 | 어느 장비가 얼마나 벗어났는가 |
| 차이의 유형 | 한 대만 벗어남 / 두 무리로 갈림 / 전부 제각각 |
| 결과와의 관계 | 벗어난 장비가 기존 장비 간 차이 관리 지표에서도 차이가 나는 장비인가. Agent가 계산하지 않고 이미 있는 지표를 받아 붙인다 ⟨확인: 조건을 맞춰 잰 장비 간 차이 지표가 있는지, 어디서 얻는지⟩ |
| 다음 행동 제안 | 의도한 설정인지 확인 / 벤더에 확인 요청 / 재조정 검토 / 참고만 |
| 엔지니어 판정 | 조치함 / 의도한 차이 / 무관 — 이 판정을 다시 받아 적어 다음 비교 때 같은 후보를 반복해 올리지 않는다 |

정렬 순서도 정한다. **교정 분류이면서 한 대만 벗어났고 그 장비가 결과에서도 차이가 나는 후보**를 맨 위에 올린다. "전부 제각각"인 필드는 그 자체가 정보이지만(표준이 없다는 뜻) 따로 모아 보여 준다.

**결과와의 관계는 조건이 맞을 때만 쓴다.** 장비가 내놓는 측정 산출 파일의 값은 웨이퍼·레시피·측정 조건이 제각각이어서, 그대로 장비별로 비교하면 일의 차이를 장비의 차이로 잘못 읽는다. 그래서 Agent는 측정 산출에서 장비 간 차이를 직접 계산하지 않는다. 같은 기준 시료나 맞춘 조건으로 잰 기존 지표가 있으면 그것을 받아 쓰고, 없으면 이 칸을 비워 둔 채 **설정·교정 값의 차이를 찾는 데까지만** 한다.

### 관리 대상 파라미터 — 이 Agent의 최종 산출물

전부 비교하는 목적은 **우리가 관리해야 하는 파라미터를 가려내는 것**이다. 차이 후보표는 중간 산출물이고, 엔지니어의 판정을 거쳐 관리 대상 목록이 된다.

필드 하나는 다음 길을 간다.

```
발견(지도에 올라감) → 비교(장비 간 값을 나란히) → 차이 후보 → 엔지니어 판정 ─┬→ 관리 대상
                                                                    ├→ 참고 (다르지만 관리할 필요 없음)
                                                                    └→ 무관 (의도한 차이)
```

관리 대상 목록은 모델마다 하나다. 항목 하나의 모양(값은 가상):

```yaml
# watchlist/<vendor>/<model>.yaml 의 항목 하나
- field: fc_meas_cal.correction_a      # 구조 지도의 필드 id
  reason: "장비 간 측정값 차이에 직접 영향. 한 대가 벗어나 있던 이력"
  baseline:                            # 기준. 장비 무리의 분포에서 뽑고 엔지니어가 확정한다
    kind: fleet_range                  # fixed(같아야 함) | fleet_range(무리의 범위 안) | per_tool(장비별 기준값에서 안 변해야 함)
    center: 0.0
    tolerance: 0.5
  check_every: 7d                      # 점검 주기
  on_violation: "담당 엔지니어에게 알림"
  decided_by: "<엔지니어>"
  decided_on: 2027-01-15
```

`kind` 세 가지를 나눈 것은 "관리한다"의 뜻이 값마다 다르기 때문이다. 모든 장비가 같아야 하는 값이 있고, 장비마다 달라도 되지만 무리에서 벗어나면 안 되는 값이 있고, 장비마다 고유하지만 한번 정해지면 변하면 안 되는 값이 있다.

기준과 주기는 Agent가 제안하고 엔지니어가 확정한다. Agent가 스스로 관리 대상을 정하지 않는다.

**관리 대상은 두 길로 들어온다.** 차이가 난 필드만 올리면 "지금은 모든 장비가 같지만 중요한 값"이 빠진다. 그래서 엔지니어가 이미 중요하다고 아는 파라미터를 먼저 목록에 넣고, 거기에 비교에서 새로 드러난 후보를 더한다.

**"무관" 판정은 영구가 아니다.** 판정에는 그때의 조건(S/W 버전, 값)을 함께 적는다. 값이 판정 때와 달라지거나 S/W가 바뀌면 다시 올린다. 판정에는 재검토 시점을 둔다 ⟨확인: 기간⟩.

### 실행 모드 네 가지

Agent는 한 번 돌고 끝나지 않는다. 같은 파이프라인을 상황에 따라 다른 범위로 돌린다.

| 모드 | 언제 | 하는 일 | LLM | 현업 검증 |
|---|---|---|---|---|
| **최초 매핑** | 새 모델을 처음 볼 때 | ①~⑥ 전체. 구조 지도를 만든다 | 많이 씀 | 필요 |
| **장비 추가** | 지도가 있는 모델의 다른 장비를 붙일 때 | ①로 목록을 뽑아 지도와 맞는지 보고 ⑦⑧ | 안 씀 | 차이 후보만 |
| **정기 점검** | 같은 장비를 주기적으로 | 아래 참조 | 달라진 곳만 | 달라진 곳만 |
| **버전 변경** | S/W가 바뀌었을 때 | 달라진 파일 종류만 ②~⑥ 다시 | 달라진 곳만 | 달라진 곳만 |

**정기 점검이 보는 것.** 지난 회차의 결과와 비교해 달라진 것만 다룬다.

| 달라진 것 | 알아내는 방법 | 뜻 | 하는 일 |
|---|---|---|---|
| 새 파일 종류가 생겼다 / 없어졌다 | 목록을 지난 목록과 비교 | S/W나 옵션이 바뀌었다 | 새 종류만 표본 수집·프로파일링해 지도에 더한다 |
| 파일 종류의 구조가 바뀌었다 | ⑦에서 `locator`가 실패하거나, 표본의 구조 지문(열·키·자료형·단위 표기를 요약한 값)이 지도에 적힌 것과 다르다 | 포맷이 바뀌었다. 추출이 성공해도 단위나 열이 바뀌었을 수 있다 | 그 종류만 다시 프로파일링한다. 그 종류에 속한 관리 대상은 기준을 다시 본다 |
| 값을 읽지 못했다 | 추출 상태가 없음·개수 불일치·파싱 실패 | 수집 문제이거나 구조 변화다. 값이 바뀐 것과 다르다 | 값 변화로 알리지 않고 수집 이상으로 따로 알린다 |
| 관리 대상의 값이 기준을 벗어났다 | 값을 기준과 비교 | 조치가 필요할 수 있다 | 엔지니어에게 알린다 |
| 관리 대상이 아닌 값이 바뀌었다 | 값을 지난 값과 비교 | 누가 바꿨거나 장비가 스스로 갱신했다 | 변경 기록에 남긴다. 반복되면 차이 후보로 올린다 |
| 새 장비가 무리의 분포를 바꿨다 | 무리의 분포를 다시 계산 | 기준을 다시 볼 때다 | 기준 재검토를 제안한다 |

`locator` 실패만 보면 조용한 변화를 놓친다. 키 이름은 그대로인데 단위나 배율이 바뀌면 추출은 성공하고 틀린 비교가 계속된다. 새 필드가 생겨도 기존 `locator`는 실패하지 않는다. 그래서 전체 값을 보는 회차와 S/W 버전이 바뀐 때에는 파일 종류마다 표본을 다시 떠서 구조 지문을 맞춰 본다. 값 스냅샷에는 어느 개정의 지도와 파서로 읽었는지를 적어서, 지도가 고쳐진 뒤에도 옛 값이 무엇을 읽은 것인지 알 수 있게 한다.

주기는 두 단으로 둔다. **관리 대상은 자주**(목록이 짧아 가볍다), **전체 값은 드물게** 본다 ⟨확인: 주기⟩. 지도는 점검 때마다 조금씩 고쳐지며, 고친 이력은 남긴다.

점검은 사람이 지켜보지 않아도 돌아야 한다. 그러려면 다음을 지킨다.

- 장비에는 읽기만 한다. 조회 속도를 제한하고 정해진 시간대에만 돈다.
- 중간에 끊기면 끊긴 단계부터 다시 돈다. 한 장비의 실패가 다른 장비의 점검을 막지 않는다.
- 회차마다 무엇을 읽었고 무엇이 달라졌는지 기록을 남긴다.
- 알림은 달라진 것이 있을 때만 보낸다. 매번 "이상 없음"을 보내면 아무도 읽지 않게 된다.

### 모든 모델과 장비로 넓히는 구조

한 모델로 시작하지만 처음부터 모든 모델과 장비를 받을 수 있는 모양으로 만든다. 원칙은 **모델마다 다른 것과 모든 모델에 같은 것을 분리**하는 것이다.

| 층 | 모든 모델 공통 | 모델(또는 벤더)마다 다름 |
|---|---|---|
| 접근 | 목록 조회·표본 복사의 호출 방식 | 접속 방법, 허용 경로 |
| 묶기 | 이름을 자리표시로 바꾸는 절차 | 그 모델만의 이름 규칙, 제외 규칙 |
| 프로파일링 | 알려진 포맷의 처리, 프로파일의 모양 | 고유 확장자의 파서 규칙 |
| 지도 | 스키마, 필드 분류 6종, 역할 3종 | 지도의 내용 |
| 비교·점검 | 비교 방법, 후보표의 모양, 실행 모드 | 관리 대상 목록과 기준 |

모델마다 다른 것은 되도록 코드가 아니라 **설정 파일**로 둔다. 다만 새로운 접속 방식이나 설정 문법으로 못 쓰는 포맷은 코드를 더해야 한다. 그런 곳은 접속과 파서 두 군데로 한정하고 나머지 절차는 손대지 않게 한다. 같은 모델이라도 장비의 옵션 구성이 다르면 지도가 그대로 맞지 않을 수 있다. 지도를 적용하기 전에 목록이 지도와 맞는지 검사하고, 안 맞는 부분은 추가 매핑으로 보낸다.

```
registry/equipment.yaml            # 장비 대장: 장비 id, 벤더, 모델, S/W 버전, 접근 경로
adapters/<vendor>/<model>/         # 그 모델만의 설정: 접속, 제외 규칙, 이름 규칙, 파서 규칙
maps/<vendor>/<model>/<sw>/        # 구조 지도 (모델 × S/W 버전)
watchlist/<vendor>/<model>.yaml    # 관리 대상 목록
concepts/                          # 벤더 공통 개념 (3단계)
snapshots/<tool>/<date>/           # 값 스냅샷 — 사내에만 둔다
runs/<tool>/<date>/                # 회차별 실행 기록
```

**무엇이 늘 때 무엇이 드는가.**

| 늘어나는 것 | 드는 것 | 이유 |
|---|---|---|
| 같은 모델의 장비 한 대 | 대장에 한 줄. 코드만 돈다 | 구조 지도를 그대로 쓴다 |
| 같은 벤더의 새 모델 | 줄어든 최초 매핑 | 같은 벤더는 포맷과 이름 규칙을 공유하는 경우가 많다. 파서 규칙과 필드의 뜻을 물려받는다 ⟨확인: 실제로 얼마나 겹치는지⟩ |
| 새 벤더 | 온전한 최초 매핑 | 물려받을 것이 공통 개념뿐이다 |
| S/W 버전 | 달라진 부분만 | 버전 간 지도는 대부분 같다 |

비용은 두 덩어리로 나뉜다. **지도를 만드는 비용**(LLM과 뜻 검증)은 모델·버전·옵션 구성의 수에 비례하고 장비 대수와는 무관하다. 장비가 백 대여도 모델이 다섯이면 지도는 다섯 번 만든다. **수집과 후보 검토의 비용**은 장비 대수와 점검 횟수에 비례한다. 수집은 코드가 하지만 올라온 후보를 보는 것은 사람이다. 전체로 넓힐 수 있다는 근거는 앞의 것이고, 넓힌 뒤 사람의 부담을 정하는 것은 뒤의 것이다. 다만 "두 번째 모델이 첫 번째보다 얼마나 싼가"는 해 봐야 아는 숫자이고, 넓히기 전에 재야 한다.

### 개념 정합 — 벤더 간 대응 (⑨)

벤더 A의 필드와 벤더 B의 필드를 직접 잇지 않고, 둘을 각각 **공통 개념**에 연결한다. 벤더가 셋, 넷으로 늘어도 대응표가 벤더 수의 제곱으로 불어나지 않는다.

| 관계 | 뜻 |
|---|---|
| 동일 | 뜻·단위·정의가 같다 |
| 유사 | 뜻은 같지만 단위나 기준점이 다르다. 변환 방법을 함께 적는다 |
| 상위/하위 | 한쪽이 다른 쪽을 포함한다 |
| 대응 없음 | 이 벤더에만 있다. 이것도 기록한다 |

**개념 목록은 사람이 먼저 정한다.** LLM이 개념 이름을 자유롭게 지으면 같은 뜻이 여러 이름으로 갈라져서, 대응표가 불어나지 않게 하려던 구조가 무너진다. 그래서 개념 목록은 사람이 정의한 닫힌 목록으로 시작한다. LLM이 하는 일은 필드를 기존 개념에 잇는 것과, 맞는 개념이 없을 때 새 개념을 제안하는 것까지다. 새 개념은 사람이 승인해야 목록에 들어간다.

이름이 비슷하다는 것만으로는 연결하지 않는다. 단위, 값의 범위, 저장 위치(어느 서브시스템인가), 매뉴얼의 정의 가운데 둘 이상이 맞아야 후보로 올린다. 후보는 후보일 뿐이다. 이름과 단위가 같아도 기준점, 부호의 방향, 좌표계, 적용되는 단계가 다를 수 있다. 대응을 승인할 때는 정의, 변환식, 적용 조건, 그리고 실제 값으로 맞춰 본 예를 함께 적는다.
