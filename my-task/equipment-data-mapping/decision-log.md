# 장비 데이터 매핑 Agent — 결정 기록

> 기획 과정에서 정한 것과 그 이유를 날짜순으로 남긴다. 문서 본문은 결정의 결과만 담으므로, 왜 그렇게 정했는지와 무엇을 뒤집었는지는 여기서 찾는다.

## 2026-10-09 — 기획 착수 (home)

### 출발점

- 목적: MI 장비 안에 저장된 데이터의 계층·포맷·의미·연결을 지도로 만드는 AI Agent를 설계하고 배포한다.
- 범위의 확장 순서: 장비 모델 1종 → 같은 모델의 여러 장비 값 비교 → 같은 목적의 다른 벤더 장비와 의미 대응.
- 작업 분담: 기획과 설계는 home, 실제 실행은 office의 사내 LLM(GLM-5.3).
- 독자: 임원과 매니저를 설득해야 한다.

### 정한 것

| # | 결정 | 이유 |
|---|---|---|
| 1 | 가치를 3단(지도 → 비교 → 정합)으로 나누고 단계마다 통과 기준과 중단 조건을 둔다 | 한 번에 약속하면 하나가 막혔을 때 전체가 실패로 보인다. 앞 단계만 끝나도 결과가 남아야 한다 |
| 2 | 자유롭게 탐색하는 Agent가 아니라 고정 파이프라인으로 만든다. LLM이 다음 행동을 고르는 곳은 처음 보는 포맷의 탐색 한 군데다 | 장비 간 비교는 모든 장비에 같은 절차를 돌려야 성립한다. 사내 LLM에는 일을 작게 줘야 한다 |
| 3 | 구조 지도(모델 × S/W 버전)와 값 스냅샷(장비 × 시점)을 분리한다 | 지도는 한 번 만들어 여러 장비에 쓰고, 값 추출은 LLM 없이 코드로만 돌린다 |
| 4 | 장비의 파일을 전부 내려받지 않는다. 목록 조회 → 이름으로 묶기 → 표본만 수집 → 프로파일 추출 | 파일이 장비 한 대에 수만 단위라 전부 받으면 수집에 시간이 다 간다 |
| 5 | 프로파일에 포맷·열·자료형·값과 범위·키워드를 담고, LLM에는 원본이 아니라 프로파일을 준다 | 수집량과 LLM 입력을 함께 줄인다 |
| 6 | 큰 파일은 앞·뒤 일부만 읽는다 | 구조를 아는 데 전체가 필요 없다 |
| 7 | 이름에 `lock`·`tmp`·`temp`가 들어간 파일은 읽지 않는다 | 임시·잠금 파일이다. 장비가 쓰는 중일 수 있다 |
| 8 | xlsx와 pdf는 대상에서 뺀다 | 대상에서 제외하기로 함 |
| 9 | 파일 종류에 역할 셋을 붙인다: 설정·운영 / 측정 산출 / 상태 점검 | 장비의 파일이 실제로 이 셋으로 나뉜다. 역할에 따라 수집 방법과 쓰임이 다르다. 수만 개의 대부분은 측정 산출이다 |
| 10 | 주기적으로 갱신되는 파일은 목록을 두 번 뽑지 않고, 한 번 뽑은 목록 안의 날짜 차이로 가려낸다 | 다른 파일들은 몇 달 전인데 혼자 최근이면 갱신되거나 새로 생긴 파일이다 |
| 11 | 과제의 중심 논리를 "탐색 리드타임 단축"에서 "장비 장악력과 장비 간 차이"로 옮긴다 | 담당 엔지니어도 장비 안의 데이터를 다 알지 못한다. 공정이 미세해질수록 장비 간 차이는 더 줄어야 하고, 그 판단에는 복합적인 요소가 걸린다 |
| 12 | 중심 지표를 장악률(뜻이 확인된 파일 종류·필드의 비율)로 둔다 | 지도가 나오는 즉시 잴 수 있고, 과제 전의 값도 엔지니어에게 물어 바로 얻는다 |
| 13 | 이 과제가 직접 약속하는 것은 "볼 수 있는 범위를 넓히는 것"이다. 장비 간 차이 감소는 엔지니어의 확인과 조치를 거친 결과로 적는다 | 지도 자체가 차이를 줄이지는 않는다. 대신 Agent의 산출물은 엔지니어가 확인하고 조치할 수 있는 모양이어야 한다 |
| 14 | 실제 사례(측정값 보정 수치)를 대표 근거이자 2단계의 시험 문제로 쓴다 | 우연히 전체 장비의 값을 비교하다가 한 대가 벗어난 것을 발견했고, 그 장비가 늘 차이가 나던 장비였다. 비교해 보기 전에는 알 수 없었다 |
| 15 | 과제를 한 문장으로: "우연을 절차로 바꾼다" | 사람이 값 하나를 골라 비교한 일을 Agent가 모든 값에 대해 한다 |
| 16 | 최종 산출물은 관리 대상 파라미터 목록이다 | 전부 확인하는 목적이 관리해야 할 값을 가려내는 것이다 |
| 17 | 한 모델로 시작하되 모든 모델과 장비를 받을 수 있게 설계한다. 모델마다 다른 것은 설정 파일로 뗀다 | 최종 목표가 전체 확장이다. 새 모델을 붙이는 일이 코드 수정이 되면 넓히지 못한다 |
| 18 | 같은 장비를 주기적으로 다시 보고 달라진 곳만 갱신한다. 실행 모드는 최초 매핑 / 장비 추가 / 정기 점검 / 버전 변경 | 지도와 값은 낡는다. 관리 대상이 기준을 벗어나면 알려야 한다 |

### 뒤집은 것

| 처음 설계 | 바꾼 설계 | 계기 |
|---|---|---|
| 장비 데이터를 통째로 복사한 스냅샷에서 일한다 | 목록만 훑고 표본만 가져온다 | 파일 수와 수행 시간 |
| 며칠 간격으로 목록을 두 번 뽑아 갱신 주기를 본다 | 한 번 뽑은 목록의 날짜 차이로 본다 | 날짜 차이만으로 충분하다 |
| 현업이 뜻을 검증한 필드만 비교에 쓴다 | 값을 뽑을 수 있으면 미검증이어도 전부 비교하고, 차이가 난 필드부터 검증한다 | 보정 수치 사례에서 비교가 먼저였고 이해가 나중이었다. 모델이 늘 때 검증이 병목이 되는 것도 막는다 |
| 브레인스토밍 목록의 "용량 지도" | 뺀다 | 용량의 대부분은 측정 데이터라 얻을 것이 없다 |

### 아직 약한 곳 (이 시점의 기록)

지금의 목록은 [왜 해야 하는가](./01-why-proposal.md)의 "논리의 약한 고리" 한 곳에서 관리한다. 아래는 이 날짜에 적어 둔 것이다.

1. 과제 전의 장악률과 탐색 소요 수치가 없다.
2. 값 비교의 근거가 사례 하나다. 전부 비교해도 의미 있는 후보가 더 안 나올 수 있다.
3. 벤더 간 대응표를 받아 쓸 수요처가 지목되지 않았다.
4. "두 번째 모델이 첫 번째보다 싸다"는 가정이다. 넓히기 전에 재야 한다.
5. 정기 점검의 알림이 많으면 무시된다.
6. 장비 접근 승인이 전제다.

### 급한 일

- **보정 수치 재조정이 끝나기 전에 조정 전 값과 장비 간 차이를 기록한다.** 끝나면 되돌려 잴 수 없다. 기록은 사내용 문서에 둔다.

2. 약한 곳 여섯 개를 하나씩 압박해 본다.
3. home에서 가짜 장비 폴더와 지도 스키마 검사 코드를 만든다.

## 2026-10-09 — 외부 검토 두 건 반영

Codex와 OpenCode(GLM-5.3, 실제 실행을 맡을 모델과 같다)에게 문서를 읽기 전용으로 검토받았다. 두 검토가 겹친 지적과 각자만 짚은 지적을 가려 반영했다.

### 구성을 바꾼 것

| 바꾼 것 | 이유 |
|---|---|
| 설계 문서를 둘로 나눴다: 지도 만들기(02) / 비교·관리·운영(03). 실행 계획은 04가 됐다 | 한 문서가 너무 길었고 1단계 구현자가 2단계 이후 설계까지 읽어야 했다. 절의 순서도 파이프라인을 따르지 않았다 |
| 지표의 정의는 04 한 곳에만 둔다 | 중심 지표(장악률)가 01에만 있고 설계 문서의 지표표에는 없었다 |
| 약한 고리의 목록은 01 한 곳에만 둔다 | 세 문서에 개수와 내용이 다르게 적혀 있었다 |
| README의 "확인된 전제"는 요약이고 정의는 02에 있다고 밝혔다 | 같은 규칙이 세 곳에 있어 어긋나기 시작했다 |

### 설계를 고친 것

| # | 고친 것 | 누가 짚었나 |
|---|---|---|
| 1 | 근거에 `ref`와 `quote`를 두고 코드가 "그 자리에 그 글자가 있는가"만 검사한다. 신뢰도는 검증 순서를 정하는 데만 쓴다 | 둘 다 |
| 2 | 필드에 추출 계약을 둔다: 어느 파일, 반복 키, 기대 개수. 추출 결과는 정상 / 없음 / 개수 불일치 / 파싱 실패로 구분한다 | Codex |
| 3 | 비교 규칙을 정했다: 비교군의 조건, 최소 장비 대수, 자료형별 방법, 값이 없을 때, 후보 수의 상한. 무리의 분포를 허용 범위로 그대로 쓰지 않는다 | Codex |
| 4 | Agent는 측정 산출에서 장비 간 차이를 직접 계산하지 않는다. 조건을 맞춘 기존 지표가 있으면 받아 쓰고, 없으면 설정·교정 값의 차이 찾기까지만 한다 | Codex |
| 5 | 정기 점검은 `locator` 실패뿐 아니라 구조 지문이 달라졌는지도 본다. 값 스냅샷에 지도와 파서의 개정 번호를 적는다 | Codex |
| 6 | 수집 전후로 크기와 수정 시각을 확인하고 재시도한다. "방금 수정된 파일은 건너뛴다"는 규칙을 없앴다. 못 읽은 것을 값 변화와 구분한다 | Codex |
| 7 | 설정·운영 파일은 일부 읽기를 하지 않고 끝까지 읽는다. 반복되는 큰 파일은 앞·가운데·끝 세 구간을 읽는다 | 둘 다 |
| 8 | 임시·잠금 파일의 제외를 글자 포함에서 **토막 일치**로 바꿨다. `temperature`, `clock`이 걸리지 않게 | Codex |
| 9 | 날짜로 한 역할 판정은 후보다. 표본의 시각 기록과 현업 확인으로 확정하고 "역할 불명"을 허용한다 | Codex |
| 10 | 실행은 프로그램이 쥔다. LLM은 닫힌 선택지 안에서 답만 돌려준다. 이름 자리표시, 파서 규칙의 칸, 분류, 개념 이름이 모두 닫힌 목록이다 | 둘 다 |
| 11 | 이름을 자리표시로 바꾸는 일은 코드가 한다. LLM이 하지 않는다 | OpenCode |
| 12 | 재현성은 LLM의 답을 지도에 얼려서 얻는다. 같은 물음을 다시 묻지 않는다 | OpenCode |
| 13 | 물음마다 LLM에 주는 입력의 모양을 정했다. 뜻을 물을 때는 파일 종류의 필드 전부를 함께 준다 | OpenCode |
| 14 | 상태 값은 읽은 시각이 다르면 그것만으로 달라지므로, 가까운 시간대에 함께 읽지 못한 값은 장비끼리 비교하지 않는다 | OpenCode |
| 15 | 관리 대상은 두 길로 들어온다: 이미 중요하다고 아는 파라미터 + 비교에서 드러난 후보. "무관" 판정에는 조건과 재검토 시점을 둔다 | Codex |
| 16 | 비용을 둘로 나눴다: 지도를 만드는 비용은 모델 수에, 수집과 후보 검토의 비용은 장비 대수에 비례한다 | Codex |

### 논리와 계획을 고친 것

| # | 고친 것 | 누가 짚었나 |
|---|---|---|
| 1 | 대표 사례를 "원인"이 아니라 "유력한 원인 후보, 재조정으로 확인 중"으로 낮췄다 | Codex |
| 2 | 대표 사례는 개발용 재현 시험으로만 쓰고, 통과 판정에는 개발 때 보지 않은 사례를 쓴다. 정렬 규칙을 이 사례를 보고 만들었기 때문이다 | Codex |
| 3 | 판정용 사례가 없을 때의 대체 통과 기준을 적었다. S/W 버전 변경은 실제 장비가 아니라 가짜 장비 폴더로 시험한다 | OpenCode |
| 4 | 정답 지도를 조정용과 판정용으로 나눴다. 누락률과 추출 정확도를 지표에 넣었다. 포괄률은 역할별로 낸다 | Codex |
| 5 | 뜻의 채점은 사람이 하고 `unknown`은 틀림으로 세지 않는다 | OpenCode |
| 6 | P0에 평가 계약(지표별 분모, 절차, 판정자, 목표의 고정 시점)과 GLM-5.3 능력 시험을 통과 조건으로 넣었다 | 둘 다 |
| 7 | 사용 시험은 다른 과제의 소요와 비교하지 않고, 같은 찾기 문제를 지도 있이/없이 풀어 비교한다 | OpenCode |
| 8 | 승인을 구하는 단위를 P0~P1로 정하고, 일반 코드만 쓰는 대안과 비교하는 행을 넣었다 | Codex |
| 9 | 수요처 확인을 P3 작업 앞에 뒀다. "다른 벤더의 두 번째 지도가 더 빨라야 한다"는 조건은 없애고 같은 벤더의 두 번째 모델에 걸었다 | Codex |

### 반영하지 않은 것

| 지적 | 이유 |
|---|---|
| 약한 고리의 단일 소스를 결정 기록으로 | 결정 기록은 날짜별 이력이고 약한 고리는 계속 고쳐 쓰는 목록이다. 설득 문서(01)에 두는 편이 맞다고 봤다 |
| 표본을 버전·옵션·레시피별로 층화 | 첫 장비에서는 어떤 층이 있는지 모른다. 표본끼리 다르면 더 가져오는 규칙과 장비를 더할 때의 지도 적용 검사로 대신한다. 실제 장비에서 변형이 많이 나오면 다시 본다 |
