# 장비 데이터 매핑 Agent — 지도 만들기 설계

> 장비 모델 하나의 데이터 지도를 어떤 모양으로 저장하고, 어떤 순서로 만들고, 그 과정에서 LLM에게 무엇을 맡기고 무엇을 맡기지 않는지 정한다. 1단계(P1)를 구현하는 사람이 읽는 문서다. 설계 초안이며 실제 장비 데이터로 검증된 것이 아니다.

## 왜 필요한가? (Why)

"장비 폴더를 LLM에게 주고 지도를 그리게 한다"로는 일이 되지 않는다. 이유는 세 가지다.

- **비교하려면 절차가 같아야 한다.** 장비 A와 B의 값을 나란히 놓으려면 두 장비에 똑같은 절차를 돌려야 한다. LLM이 그때그때 다르게 탐색하면 차이가 장비의 차이인지 탐색의 차이인지 알 수 없다.
- **사내 LLM은 한 번에 큰 일을 못 맡긴다.** 일을 작게 쪼개고, 출력 형식을 코드로 검사해야 결과를 믿을 수 있다.
- **검증할 수 있어야 한다.** "이 필드는 이런 뜻이다"라는 주장마다 근거가 붙어 있어야 현업이 판정한다.

그래서 설계 원칙은 다음과 같다.

| 원칙 | 뜻 |
|---|---|
| 코드가 할 수 있는 일은 코드가 한다 | 폴더 순회, 파일 통계, 정형 포맷 파싱, 값 비교는 일반 코드다. LLM을 쓰지 않는다 |
| LLM은 해석에만 쓴다 | 처음 보는 포맷의 구조 추정, 필드 이름의 의미 추정, 개념 대응 후보 제시 |
| 사람이 확정한다 | LLM의 출력은 전부 "미검증" 상태로 들어가고 현업이 승인해야 "검증"이 된다 |
| 구조와 값을 분리한다 | 모델 공통의 구조 지도와 장비 개체별 값 스냅샷을 다른 파일에 둔다 |
| 전부 가져오지 않는다 | 장비에서는 목록 조회와 표본 복사만 한다. 파일 종류마다 몇 개만 가져와 프로파일을 뽑는다 |
| 장비를 바꾸지 않는다 | 모든 접근은 읽기 전용이다. 분석은 가져온 표본에서 한다 |

## 핵심 개념 (What)

### 지도의 두 층

| 층 | 단위 | 담는 것 | 바뀌는 때 |
|---|---|---|---|
| **구조 지도** | 장비 모델 × S/W 버전 | 저장소 계층, 파일 종류, 포맷, 필드의 뜻·단위·분류, 파일 간 연결 | S/W 버전이 바뀔 때 |
| **값 스냅샷** | 장비 개체 × 시점 | 구조 지도의 각 필드에 대해 그 장비가 그 시점에 가진 실제 값 | 스냅샷을 뜰 때마다 |

구조 지도는 한 번 만들고 여러 대에 재사용한다. 값 스냅샷은 장비마다 뜬다. 2단계의 비교는 "같은 구조 지도 위에 올린 값 스냅샷 여러 장의 차이"다. 값 스냅샷은 사내 수치이므로 이 저장소에 올리지 않는다.

### 지도를 이루는 것

| 요소 | 뜻 | 예 (가상) |
|---|---|---|
| 저장소(Store) | 데이터가 모여 있는 곳 | 디렉터리, 내장 DB |
| 파일 종류(File Class) | 이름 규칙과 포맷이 같은 파일 묶음. 파일 하나하나가 아니라 묶음을 지도에 올린다 | "날짜별 이벤트 로그", "레시피 정의" |
| 필드(Field) | 파일 종류 안의 값 하나 | 키, 열, 태그 |
| 연결(Link) | 파일 종류나 필드 사이의 관계 | A 파일의 레시피 ID가 B 파일을 가리킨다 |
| 개념(Concept) | 벤더와 무관한 공통 의미. 3단계에서 쓴다 | "스테이지 X축 위치 보정" |

파일 수만 개를 하나씩 올리지 않고 **파일 종류**로 묶는 것이 지도를 사람이 읽을 수 있는 크기로 유지하는 방법이다.

### 파일 종류의 역할 세 가지

장비 안의 파일은 쓰임에 따라 셋으로 나뉜다. 역할에 따라 수집 방법과 쓰임새가 달라지므로 파일 종류마다 역할을 붙인다.

| 역할 | 뜻 | 목록만 보고 알아보는 단서 | 주로 담긴 필드 분류 | 어디에 쓰는가 |
|---|---|---|---|---|
| **설정·운영** | 장비 H/W 설정과 운영에 쓰는 파일 | 개수가 적다. 이름이 고정이다. 수정 시각이 오래됐거나 드물게 바뀐다 | 식별·설정·교정 | 2단계 장비 간 비교의 주 대상 |
| **측정 산출** | 웨이퍼를 측정한 뒤 장비가 내놓는 파일 | 개수가 가장 많다. 이름에 날짜·랏·웨이퍼 번호가 들어간다. 한 번 쓰이고 바뀌지 않는다 | 결과 | 구조만 지도에 올린다. 값은 웨이퍼에 따라 달라서 그대로는 장비 비교에 못 쓴다 |
| **상태 점검** | 장비가 자기 컨디션을 보려고 몇 시간~며칠 주기로 갱신하는 파일 | 같은 이름이 주기적으로 덮어쓰이거나, 일정한 간격의 날짜 이름으로 쌓인다 | 상태·교정 | 2단계 비교와 4단계의 시간 변화 추적 |

역할은 파일을 열지 않고 ① 목록의 정보(개수, 이름 규칙, 날짜)만으로 1차 판정한다. 목록은 한 번만 뽑는다. 갱신 여부는 **파일들 사이의 날짜 차이**로 가려낸다.

| 날짜에서 보이는 것 | 읽는 법 |
|---|---|
| 같은 폴더의 다른 파일들은 몇 달 전 날짜인데 혼자 최근이다 | 주기적으로 갱신되거나 새로 생긴 파일이다 |
| 생성 시각은 오래됐는데 수정 시각이 최근이다 | 같은 이름으로 덮어쓰이는 파일이다 → 상태 점검 후보 |
| 생성 시각과 수정 시각이 모두 최근이다 | 새로 만들어진 파일이다 → 이름 규칙을 보고 측정 산출인지 날짜로 쌓이는 상태 점검인지 가른다 |
| 날짜 이름으로 쌓인 파일들의 간격이 일정하다 | 그 간격이 갱신 주기다 |
| 모든 파일이 비슷한 옛 날짜에 몰려 있다 | 설치·셋업 때 만들어진 뒤 바뀌지 않은 설정·운영 파일이다 |

날짜로 한 판정은 후보다. 한 번 고쳤거나 복원한 파일도 "혼자 최근"으로 보인다. 역할은 ③에서 표본 안의 시각 기록을 보고, 그리고 현업 확인과 다음 회차의 관측으로 확정한다. 판정이 서지 않으면 "역할 불명"으로 두고 지어 붙이지 않는다.

덮어쓰이는 파일은 목록만으로 "최근에 갱신됐다"까지만 알 수 있고 주기는 알 수 없다. 주기는 ③에서 표본 안의 시각 기록을 보고 채운다. 생성 시각을 얻을 수 없는 환경이면 수정 시각의 차이만으로 판정한다 ⟨확인: 장비에서 생성 시각을 얻을 수 있는지⟩.

파일 수만 개의 대부분은 측정 산출일 가능성이 높다. 개수는 많지만 구조는 반복되므로 지도에서는 몇 줄로 줄어든다. 반대로 설정·운영 파일은 개수는 적지만 하나하나가 다르고, 2단계에 가장 직접 쓰인다.

### 필드 분류 — 2단계 비교의 바탕

같은 "값이 다르다"라도 뜻이 다르다. 필드마다 분류를 붙인다.

| 분류 | 뜻 | 장비 간에 값이 다르면 |
|---|---|---|
| 식별(Identity) | 장비 번호, S/W 버전, 옵션 구성 | 비교 전에 조건을 맞추는 데 쓴다 |
| 설정(Setting) | 사람이 정한 값 — 레시피, 운영 옵션 | 운영 방식이 다른 것이다. 의도한 차이인지 확인한다 |
| 교정(Calibration) | 장비 개체의 특성을 보정하려고 넣은 값 | H/W 개체 차이의 흔적이다. 2단계의 주 관심 대상 |
| 상태(State) | 센서 값, 카운터, 부품 사용 시간 | 현재 컨디션이 다른 것이다 |
| 결과(Result) | 측정·검사 산출물 | 성능이 다른 것이다 |
| 이력(Log) | 알람, 동작 기록 | 빈도와 패턴을 본다 |

2단계의 핵심 질문은 "**교정·상태 값의 차이가 결과의 차이와 함께 움직이는가**"다. Agent는 이 조합이 눈에 띄는 필드를 후보로 올리고, 원인 판단은 엔지니어가 한다.

### 항목 하나의 모양

지도의 모든 항목은 근거와 검증 상태를 함께 가진다. 구조 지도의 필드 하나는 다음처럼 생긴다(값은 가상).

```yaml
# structure-map/<model>/<sw-version>/fields.yaml 의 항목 하나
- id: fc_stage_cal.x_offset
  file_class: fc_stage_cal            # 속한 파일 종류
  extract:                            # 추출 계약 — 어느 파일의 어디서 몇 개를 읽는가
    file_select: only                 # 파일 종류 안에서 어느 파일인가: only(하나뿐) | latest | each(전부)
    locator: "section=[Stage] key=XOffset"
    repeat_key: null                  # 같은 키가 축·채널·레시피마다 반복되면 그것을 구분하는 키
    expect_count: 1                   # 기대 개수. 다르면 값이 아니라 추출 이상으로 기록한다
    parser_rev: 3                     # 이 계약을 만든 파서 규칙의 개정 번호
  dtype: float
  unit: um
  category: calibration               # identity|setting|calibration|state|result|log
  meaning: "스테이지 X축 원점 보정값"
  evidence:                           # 이 뜻이라고 본 근거
    - type: name                      # name|unit|value_range|location|manual|co_variation
      ref: "sample:s0012 line 48"     # 코드가 매긴 표본 id와 줄 번호
      quote: "XOffset=0.42"           # 그 줄의 글자 그대로. 코드는 이 글자가 그 줄에 있는지만 본다
      note: "키 이름이 XOffset이고 [Stage] 섹션에 있음"
    - type: manual
      ref: "manual:m03 chunk 112"     # 매뉴얼도 코드가 자른 조각의 id로만 가리킨다
      quote: "XOffset"
      note: "스테이지 보정 절에 같은 이름"
  confidence: medium                  # low|medium|high — LLM의 자기 평가가 아니라 근거 개수·종류로 코드가 매긴다
  status: unverified                  # unverified|verified|rejected
  verified_by: null
  concept: null                       # 3단계에서 채운다
```

`confidence`를 LLM에게 묻지 않고 코드가 계산한다. LLM의 자기 확신은 믿을 근거가 못 된다. 다만 근거의 개수만 세면 LLM이 그럴듯한 근거를 지어내도 통과한다. 그래서 다음을 지킨다.

- 근거는 `ref`(코드가 매긴 표본 id·줄 번호나 매뉴얼 조각 id)와 `quote`(그 자리의 글자 그대로)를 가져야 한다. 코드는 `quote`가 `ref` 자리에 있는지만 확인하고, 없으면 그 근거를 버린다. `note`는 사람이 읽는 설명이고 검사하지 않는다. 이 검사가 되려면 프로파일이 표본의 줄 번호와 원문을 공백까지 그대로 간직해야 한다.
- 같은 종류의 근거는 한 번만 센다. 이름과 위치처럼 사실상 같은 단서를 두 번 세지 않는다.
- 신뢰도는 **검증 순서를 정하는 데만** 쓴다. 뜻이 맞다는 보증으로 쓰지 않는다.

필드 하나에는 서로 다른 세 가지 상태가 있고 섞지 않는다.

| 상태 | 뜻 | 누가 확인하나 |
|---|---|---|
| 추출 확인 | 추출 계약대로 값이 기대 개수만큼 읽힌다 | 코드 |
| 뜻 추정 | 이 값이 무엇인지 LLM이 근거와 함께 제안했다 | LLM, 근거의 실재는 코드 |
| 현업 승인 | 뜻과 분류가 맞다고 엔지니어가 확인했다 | 사람 |

값 비교에는 "추출 확인"만 있으면 된다. 관리 대상 지정과 개념 정합에는 "현업 승인"이 필요하다.

**필드 id와 반복 항목.** 같은 키가 축마다, 채널마다, 레시피마다 반복되는 경우가 많다. 이때 필드 id는 하나로 두고 `repeat_key`로 구분되는 여러 값을 가진다. 비교는 같은 `repeat_key`끼리 한다. S/W 버전이 바뀌어도 위치와 뜻이 같으면 필드 id를 유지하고, 뜻이나 단위가 바뀌면 새 id를 발급하고 옛 id와의 관계를 적는다.

**추출 결과는 값만 적지 않는다.** 값마다 읽은 원본 파일·위치·읽은 시각을 남기고, 상태를 넷으로 구분한다: 정상 / 없음 / 개수 불일치 / 파싱 실패. 뒤의 셋을 "값이 다르다"와 섞으면 수집 문제를 장비 차이로 잘못 읽는다.

### 저장 방식

YAML/JSONL 파일로 둔다. 사람이 읽는 화면은 이 파일에서 마크다운을 뽑아 만든다. 그래프 DB나 검색 엔진은 지도가 파일로 감당이 안 될 만큼 커진 뒤에 붙인다.

## 어떻게 사용하는가? (How)

### 파이프라인

```
[장비] → ①목록화 → ②묶기·표본 수집 → ③프로파일링 → ④의미 추정 → ⑤연결 찾기 → ⑥현업 검증 → 구조 지도
        (내용 안 읽음)  (종류당 몇 개만)                                                    │
                              값 스냅샷(장비별) ← ⑦선별 수집·값 추출 ←───────────────────────┘
                                    │
                                    ├→ ⑧장비 간 비교 (2단계)
                                    └→ ⑨개념 정합 (3단계)
```

| 단계 | 하는 일 | 누가 | 산출물 |
|---|---|---|---|
| ① 목록화 | 장비의 폴더를 순회(walk)해 경로·크기·생성 시각·수정 시각·확장자만 기록한다. 파일 내용은 읽지 않고 내려받지도 않는다 | 코드 | 파일 목록 |
| ② 묶기·표본 수집 | 폴더와 이름 규칙이 같은 파일을 파일 종류로 묶고 역할(설정·운영/측정 산출/상태 점검)을 붙인 뒤, 역할에 맞는 방법으로 표본만 가져온다. 규칙으로 안 묶이는 것만 LLM에게 묻는다 | 코드 + LLM | 파일 종류 목록, 표본 |
| ③ 프로파일링 | 표본에서 포맷·열·자료형·값의 범위·키워드를 뽑는다. 알려진 포맷(INI·XML·CSV·JSON·이미지)은 코드가 처리하고, 모르는 텍스트 포맷과 고유 확장자는 LLM이 구조를 추정해 파서 규칙을 제안한다. 바이너리는 "해석 불가"로 표시하고 넘어간다 | 코드 + LLM | 파일 종류별 프로파일 |
| ④ 의미 추정 | 원본 파일이 아니라 ③의 프로파일을 주고 필드의 뜻과 분류를 추정한다. 벤더 매뉴얼이 있으면 해당 부분을 함께 준다 | LLM | 필드 항목(미검증) |
| ⑤ 연결 찾기 | 여러 파일 종류에 같은 값이 나타나는 필드(레시피 ID, 웨이퍼 ID, 시각)와 파일 안의 경로 참조를 찾는다. 값이 겹치는 비율을 함께 적는다. 겹친다는 것만으로 관계를 확정하지 않고 후보로 둔다 | 코드, 애매한 것만 LLM | 연결 후보 목록 |
| ⑥ 현업 검증 | 현업이 승인/기각/수정한다. 전부를 한 번에 하지 않는다. 비교가 돌기 전(P1)에는 설정·운영 역할의 교정·설정 분류부터 하고, 비교가 돌기 시작하면(P2) 차이 후보로 올라온 필드부터 한다 | 사람 | 검증된 구조 지도 |
| ⑦ 선별 수집·값 추출 | 비교하려는 필드가 든 파일 종류만 골라 각 장비에서 가져오고, 구조 지도의 `locator`대로 값을 뽑는다. LLM 없음 | 코드 | 값 스냅샷 |
| ⑧ 장비 간 비교 | 조건(S/W 버전, 옵션)을 맞춘 뒤 필드별로 장비 무리에서 벗어난 값을 찾는다 | 코드, 요약만 LLM | 차이 후보표 |
| ⑨ 개념 정합 | 벤더 A·B의 검증된 필드를 공통 개념에 연결한다. 필드끼리 직접 잇지 않고 개념을 거친다 | LLM 제안 + 사람 승인 | 개념 대응표 |

①~⑥이 이 문서의 범위다. ⑦~⑨의 상세는 [비교·관리·운영 설계](./03-compare-operate-design.md)에 있다.

⑦이 LLM 없이 돈다는 점이 이 구조의 이득이다. 구조 지도를 한 번 만들면 장비 100대의 값 추출은 코드만으로 끝난다.

**⑥ 검증은 ⑦⑧ 비교를 막지 않는다.** 값이 장비마다 다른지는 그 값의 뜻을 몰라도 알 수 있다. 보정값 사례도 비교가 먼저였고 이해가 나중이었다. 그래서 값을 뽑을 수 있는 필드는 뜻이 미검증이어도 전부 비교에 올리고, 차이가 드러난 필드부터 뜻을 검증한다. 현업의 검증 시간은 수만 개 필드 전체가 아니라 차이가 난 곳에 쓴다. 검증이 반드시 필요한 것은 관리 대상으로 올릴 때와 ⑨ 개념 정합이다.

### LLM에게 맡기는 일과 실행 계약

파이프라인의 순서는 고정이다. LLM이 스스로 다음 행동을 고르는 곳은 ③의 "모르는 포맷 탐색" 한 군데로 한정한다. 여기서 Agent는 표본을 더 가져올지, 다른 파일과 비교할지, 포기하고 "해석 불가"로 넘길지를 정한다. 호출 횟수 상한을 둔다.

나머지 단계의 LLM 호출은 "입력 하나 → 정해진 형식의 출력 하나"다. 출력은 스키마로 검사하고, 형식이 틀리면 다시 시킨다.

**실행을 쥐는 것은 프로그램이다.** 단계의 순서와 도구 호출은 프로그램이 하고, LLM은 물음마다 정해진 형식의 답만 돌려준다. ③의 탐색에서도 LLM은 "표본 더 / 다른 파일과 비교 / 파서 규칙 제안 / 포기" 가운데 하나를 고른 답을 내고, 실제 호출은 프로그램이 한다. 이렇게 하면 사내 LLM이 tool calling을 지원하지 않아도 돈다.

| 정할 것 | 내용 |
|---|---|
| 닫힌 어휘 | LLM은 정해진 선택지 안에서만 고른다. 필드 분류 6종, 역할 3종, 파서 규칙의 항목, 파일 종류의 이름 자리표시가 모두 닫힌 목록이다. LLM이 새 낱말을 지어내면 스키마 검사에서 떨어뜨린다. 회차마다 다른 낱말이 나오면 장비의 차이와 절차의 차이를 가를 수 없기 때문이다 |
| 파서 규칙의 문법 | LLM이 제안할 수 있는 것을 좁게 정한다(아래 예). 이 문법으로 못 쓰는 포맷은 "해석 불가"다 |
| 실패를 되돌려 주는 모양 | 규칙이 틀렸을 때 "실패"만 돌려주지 않는다. 몇 번째 줄에서 무엇이 안 맞았는지(기대한 열 수와 실제 열 수, 그 줄의 원문)를 정해진 형식으로 돌려준다. 이것이 없으면 재시도가 헛돈다 |
| 결과의 고정 | LLM의 답은 지도에 한 번 적히면 그대로 쓴다. 장비를 더하거나 정기 점검을 돌 때 같은 물음을 다시 묻지 않는다. 재현성은 LLM을 결정적으로 만들어서가 아니라 **답을 얼려서** 얻는다. 호출할 때는 temperature를 0으로 두고 그 밖의 실행 값도 인계 패키지에 고정한다 ⟨확인: 사내 API가 고정을 지원하는 범위⟩ |
| 모른다는 답 | 모든 물음에 `unknown`을 허용한다. 벤더 내부 약어는 매뉴얼 근거가 없으면 맞힐 수 없다. 답을 강제하면 지어낸다 |
| 예산 | 파일 종류 하나에 LLM 호출 횟수와 시간의 상한. 넘으면 "해석 불가"로 끝낸다 |
| 재시도 | 형식 오류는 정해진 횟수까지만. 넘으면 그 항목을 "실패"로 적고 다음으로 간다. 무한히 되묻지 않는다 |
| 파서 검증 | 규칙을 만들 때 쓴 표본이 아닌 다른 표본으로 돌려 본다. 만든 표본에서만 되는 규칙을 걸러 낸다 |
| 끝난 상태 | 파일 종류마다 넷 중 하나로 끝난다: 해석됨 / 일부 해석 / 해석 불가 / 실패 |

파서 규칙은 LLM이 코드를 쓰는 것이 아니라 다음 같은 칸을 채우는 것이다(값은 가상). 칸의 목록은 닫혀 있다.

```yaml
kind: delimited            # delimited | key_value | sectioned_key_value | fixed_width | line_pattern
encoding: utf-8
delimiter: ","
header_line: 3             # 머리글이 있는 줄. 없으면 null
skip_lines: [1, 2]         # 건너뛸 줄
comment_prefix: "#"
section_pattern: null      # sectioned_key_value일 때만: 섹션을 여는 줄의 모양
columns: null              # fixed_width일 때만: 열마다 시작·끝 글자 위치
```

**물음마다 주는 입력의 모양.** LLM이 잘 답하려면 무엇을 한꺼번에 봐야 하는지가 일마다 다르다.

| 일 | 한 번의 호출에 주는 것 | 틀리기 쉬운 곳 |
|---|---|---|
| ③ 파서 규칙 제안 | 표본의 앞·가운데·끝 발췌(공백 보존, 줄 번호 포함), 줄 길이의 분포, 구분자 후보별 개수, 앞선 시도의 실패 정보 | "거의 맞는" 규칙. 고정 폭 열은 글자 위치 통계 없이는 못 맞힌다. 파일 중간에 구조가 바뀌는 포맷 |
| ④ 뜻·분류 추정 | 파일 종류 하나의 **필드 전부**(이웃한 키가 맥락이다), 필드마다 값 예시 3~5개와 단위 표기, 파일 종류의 역할, 관련 매뉴얼 조각 | 벤더 내부 약어. 매뉴얼 근거가 없으면 `unknown`이 옳은 답이다 |
| ⑨ 개념 대응 | 사람이 정한 개념 목록, 대응시킬 필드의 뜻·단위·값 범위·속한 서브시스템을 두 벤더 나란히 | 이름과 단위가 같은데 기준점·부호·좌표계가 다른 경우 |

### Agent에게 주는 도구

| 도구 | 하는 일 | 제약 |
|---|---|---|
| `list_dir(path)` | 하위 항목과 개수 | 허용 경로 밖 거부 |
| `fetch_sample(file_class, how)` | 파일 종류에서 표본을 더 가져온다 | 종류당 개수·용량 상한. 읽기 전용. 제외 규칙에 걸린 파일은 거부 |
| `stat(path)` | 크기, 수정 시각, 앞부분 바이트 | |
| `read_sample(path, offset, length)` | 파일 일부를 읽는다 | 길이 상한. 전체를 한 번에 읽지 않는다 |
| `hexdump(path, offset, length)` | 바이너리 일부를 16진으로 | 길이 상한 |
| `try_parse(path, rule)` | 제안한 파서 규칙을 실제로 돌려 성공 여부와 추출 결과 일부를 돌려준다 | 규칙은 정해진 문법 안에서만. 임의 코드 실행 없음 |
| `search_manual(query)` | 벤더 매뉴얼에서 관련 부분을 찾는다 | 매뉴얼이 있을 때만 |
| `write_entry(entry)` | 지도 항목을 쓴다 | 스키마 검사 통과 시에만. 항상 `unverified` |

모든 도구는 읽기 전용이거나 지도 파일에만 쓴다. 장비의 파일은 바꾸지 않는다.

### 표본 수집과 프로파일 (①~③ 상세)

장비 안의 파일을 전부 가져오면 수집에만 시간이 다 간다. 목록만 훑고, 비슷한 이름끼리 묶고, 묶음마다 몇 개만 가져온다.

**이름으로 묶는 방법.** 파일 이름에서 변하는 부분을 자리표시로 바꾼 뒤, 폴더 위치와 바뀐 이름이 같으면 한 종류로 본다.

| 실제 이름 (가상) | 바꾼 이름 |
|---|---|
| `log/event_20260901.txt`, `log/event_20260902.txt` | `log/event_<DATE>.txt` |
| `result/LOT1234/W05_meas.csv` | `result/LOT<NUM>/W<NUM>_meas.csv` |
| `recipe/ABC_v3.rcp`, `recipe/XYZ_v12.rcp` | `recipe/*_v<NUM>.rcp` (2차 규칙) |

이름을 바꾸는 일은 **코드가 정해진 규칙으로** 한다. LLM이 하지 않는다. 자리표시는 닫힌 목록이다.

| 자리표시 | 바꾸는 것 |
|---|---|
| `<DATE>` | 날짜로 읽히는 숫자열 (8자리·6자리, 구분 기호 포함) |
| `<TIME>` | 시각으로 읽히는 숫자열 |
| `<NUM>` | 그 밖의 숫자열 |
| `<HEX>` | 길이가 일정한 16진 문자열 |

규칙은 두 번 건다. 1차로 위 자리표시를 바꿔 같아진 이름끼리 묶는다. 사람이 자유롭게 지은 이름(레시피 이름 따위)은 1차로 안 묶이므로, 2차로 같은 폴더에서 확장자와 자리표시 부분이 같고 나머지만 다른 파일을 `*`로 묶는다. 2차로 묶은 것은 이름이 아니라 표본의 프로파일이 일치하는지로 확정한다. 그래도 남는 것만 LLM에게 묻되, LLM은 "기존 종류 가운데 어느 것 / 새 종류 / 모름"만 고른다. 폴더 이름에도 같은 규칙을 쓴다. 이렇게 하면 파일 수만 개가 종류 수백 개 이하로 줄어든다 ⟨확인: 실제 장비에서의 종류 수⟩.

**읽지 않는 파일.** 이름에 `lock`, `tmp`, `temp`가 **토막으로** 들어간 파일과 폴더는 임시 파일이거나 잠금용이다. 글자가 포함됐다는 것만으로 걸면 `temperature`나 `clock`, `block`이 들어간 경로까지 빠진다. 이름을 `_`·`-`·`.`과 대소문자 경계로 자른 토막이 정확히 일치할 때만 제외한다(`run.lock`, `tmp_001`, `Temp/`는 제외, `stage_temperature.csv`는 대상). 목록에는 "제외"로 남기되 내용은 읽지도 가져오지도 않는다. 장비가 쓰고 있는 중일 수 있고, 지도에 올릴 가치도 없다. 제외 규칙은 코드에 박지 않고 목록 파일로 두어 장비마다 더하고 뺄 수 있게 한다. 제외한 것은 숨기지 않는다. 회차마다 제외 규칙별 파일 수와 용량을 보고하고, 현업이 한 번 훑어 잘못 빠진 것이 없는지 본다.

| 제외 대상 | 판정 | 목록에 남는 기록 |
|---|---|---|
| 이름의 토막이 `lock`·`tmp`·`temp` (대소문자 무시, 폴더 포함) | 이름 규칙 | 경로, 제외 사유 |
| 확장자가 `xlsx`·`pdf` | 확장자 | 경로, 제외 사유 |

**표본을 고르는 방법.** 무작위로만 뽑지 않는다. 종류마다 다음을 가져온다 (기본 3~5개, 조정 가능).

| 표본 | 고르는 이유 |
|---|---|
| 가장 최근 파일 | 현재 S/W가 쓰는 포맷이다 |
| 가장 오래된 파일 | S/W 업그레이드로 포맷이 바뀌었는지 드러난다 |
| 가장 큰 파일과 가장 작은 파일 | 열이 더 있거나 비어 있는 변형이 드러난다 |
| 무작위 1개 | 위 기준이 놓친 경우를 본다 |

같은 모양의 줄이 반복되는 큰 파일(로그, 표)은 통째로 가져오지 않고 앞·가운데·끝 세 구간만 읽는다. 앞과 끝만 보면 중간에 구조가 바뀌는 파일을 놓친다. 읽지 않은 구간이 있었다는 것을 프로파일에 적는다. 이미지는 내용을 가져오지 않고 크기·해상도 같은 머리 정보만 본다.

**역할에 따라 수집 방법을 달리한다.**

| 역할 | 수집 방법 | 이유 |
|---|---|---|
| 설정·운영 | 묶이지 않는 파일은 표본이 아니라 전부 가져와 **끝까지 읽는다.** 일부 읽기를 쓰지 않는다 | 개수가 적고 파일마다 내용이 다르다. 키=값 형식은 중간에만 있는 섹션이 있어서 앞·뒤만 읽으면 필드를 놓친다. 지도에 없는 필드는 비교에도 오르지 않으므로 나중에 발견되지도 않는다 |
| 측정 산출 | 종류당 표본 몇 개만. 가장 강하게 줄인다 | 개수가 많고 구조가 반복된다 |
| 상태 점검 | 덮어쓰이는 파일은 현재본 하나. 날짜로 쌓이는 파일은 최신·최고와 중간 몇 개 | 구조는 하나로 충분하고, 시간에 따른 값 변화는 ⑦에서 따로 가져온다 |

**확장자에 따라 읽는 방법이 다르다.**

| 종류 | 처리 | 일부 읽기 |
|---|---|---|
| txt·csv와 텍스트로 열리는 고유 확장자 | 앞·뒤 일부로 구조를 추정한다 | 가능 |
| xlsx·pdf | 대상에서 뺀다. 목록에 "제외"로만 남긴다. 일부 읽기가 안 되어 통째로 가져와야 하고, 장비가 쓰는 데이터보다는 사람이 만든 문서일 가능성이 높다 | — |
| 바이너리인 고유 확장자 | 앞부분 바이트와 그 안의 읽을 수 있는 문자열만 기록하고 "해석 불가"로 둔다 | 가능 |

고유 확장자는 확장자만으로 텍스트인지 바이너리인지 알 수 없다. 앞부분 바이트를 읽어 판정한다. 판정 전에 인코딩 표시(BOM)를 먼저 본다. UTF-16 텍스트는 바이트 사이에 0이 끼어 있어 그냥 보면 바이너리로 잘못 읽힌다. 같은 확장자가 두 가지로 섞여 있을 수도 있다.

**표본이 서로 다르면 더 가져온다.** 같은 종류로 묶은 표본들의 프로파일이 다르면(열 개수가 다르다, 구분자가 다르다) 이름만 같고 내용이 다른 것이다. 종류를 쪼개고 표본을 더 가져온다. 프로파일이 일치하면 거기서 멈춘다. 수집량을 정하는 것은 파일 개수가 아니라 종류의 다양성이다. 다만 표본 몇 개가 같다는 것은 "관찰한 표본에서는 같았다"까지다. 드문 옵션이나 레시피에서만 나타나는 변형은 놓칠 수 있다.

**프로파일에 담는 것.** 코드가 표본에서 뽑는다. LLM은 이 프로파일만 본다.

| 항목 | 내용 |
|---|---|
| 포맷 | 텍스트/바이너리, 인코딩, 줄바꿈, 구조 유형(키=값, 구분자 표, 태그, 자유 형식 로그) |
| 원문 발췌 | 읽은 구간의 글자 그대로. 공백을 줄이지 않고 줄 번호를 붙인다. 근거 검사와 고정 폭 열 판정에 쓴다 |
| 줄의 통계 | 줄 길이의 분포, 구분자 후보별 줄당 개수 |
| 구조 | 구분자, 머리글 유무, 열 이름 또는 키 이름, 섹션 이름 |
| 자료형 | 열·키마다 정수/실수/문자/날짜·시각/불리언 |
| 값 | 최솟값·최댓값, 서로 다른 값의 개수, 빈 값 비율, 예시 값 몇 개 |
| 키워드 | 자주 나오는 토막, 단위 표기(um, nm, V, deg), 다른 파일의 경로나 이름처럼 보이는 문자열 |
| 표본 정보 | 표본 몇 개에서 뽑았는지, 표본 사이에 달랐던 점 |

**수집은 한 시점의 사진이 아니다.** 목록을 뽑은 때와 파일을 가져온 때 사이에 파일이 바뀔 수 있다. 가져오기 전후로 크기와 수정 시각을 확인하고, 달라졌으면 정해진 횟수만큼 다시 가져온다. 늘 갱신되는 상태 파일을 "방금 수정됐다"는 이유로 매번 건너뛰면 영영 못 읽으므로, 건너뛰지 않고 전후가 같을 때까지 재시도한다. 파일마다 읽은 시각을 남긴다. 끝내 못 읽은 파일이 있는 회차는 "불완전"으로 표시하고 그 파일은 비교에서 뺀다. 못 읽은 것과 파일이 없어진 것, 값이 바뀐 것은 서로 다른 일로 기록한다.

**표본 방식의 한계.** 프로파일의 값 범위는 "표본에서 관찰된 범위"다. 실제 범위는 더 넓다. 구조도 "관찰한 표본에서 확인된 구조"다. 그래서 구조(포맷·열·자료형)는 표본으로 확정하되, 값의 범위와 장비 간 차이는 ⑦에서 필요한 파일만 골라 다시 가져와서 본다.

**스크립트는 데이터가 아니라 단서다.** `.sh`·배치 파일은 프로파일 대상이 아니다. 대신 "어느 폴더의 무엇을 어디로 옮기고 무엇을 지우는가"가 적혀 있어서 ⑤ 연결 찾기의 근거로 쓴다. 통째로 읽어 경로와 파일 이름만 뽑는다.

### 미리 아는 위험

| 위험 | 대응 |
|---|---|
| 중요한 데이터가 해석 못 하는 바이너리에 있다 | "해석 불가"를 숨기지 않고 지도에 표시한다. 그 비중이 크면 1단계 통과 기준에서 걸러진다. 벤더 제공 변환 도구가 있는지 확인한다 |
| LLM이 그럴듯한 뜻을 지어낸다 | 근거 없는 항목은 신뢰도 `low`. 값 비교는 뜻과 무관하므로 미검증이어도 하지만, 관리 대상 지정과 개념 정합은 검증된 필드로만 한다 |
| 모델이 늘면서 현업 검증이 밀린다 | 검증을 차이가 난 필드로 좁힌다. 전체 검증을 넓히는 조건으로 삼지 않는다 |
| 정기 점검의 알림이 너무 많아 무시된다 | 달라진 것만, 관리 대상 위주로 알린다. 엔지니어가 "무관"으로 판정한 것은 다시 올리지 않는다 |
| 이미지·로그의 양이 너무 많다 | 파일 종류로 묶고 표본만 가져온다. ⑦에서도 필요한 필드가 든 종류만 가져온다 |
| 이름은 같은데 내용이 다른 파일이 한 종류로 묶인다 | 표본끼리 프로파일을 비교해 다르면 쪼갠다 |
| 표본이 드문 변형을 놓친다 | 지도에 표본 개수를 적어 둔다. ⑦에서 `locator`가 실패한 파일이 나오면 그 종류를 다시 프로파일링한다 |
| 목록 조회가 가동 중인 장비에 부담을 준다 | 조회 속도를 제한하고 장비가 쉬는 시간에 돈다 ⟨확인: 허용 조건⟩ |
| S/W 버전에 따라 구조가 달라진다 | 구조 지도를 버전별로 둔다. 버전 간 차이는 지도끼리의 diff로 본다 |
| 사내 LLM이 긴 입력을 감당 못 한다 | 한 번의 호출에 필드 수십 개 이하만 준다. 단계 간 상태는 파일로 넘긴다 |
| 값 스냅샷이 저장소에 섞여 들어간다 | 구조 지도와 값 스냅샷의 경로를 분리하고, 값·실제 파라미터 이름은 사내에만 둔다 |
