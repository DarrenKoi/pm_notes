# 장비 데이터 매핑 Agent — 단계별 실행 계획

> 다섯 단계로 나누고 단계마다 통과 기준을 둔다. 기준을 넘지 못하면 다음 단계로 가지 않는다. 설계는 home에서, 실행은 office의 사내 LLM(GLM-5.3)이 한다.

## 왜 필요한가? (Why)

세 가지 가치(지도·비교·정합)를 한 번에 약속하면 어느 하나가 막혔을 때 전체가 실패로 보인다. 단계를 끊고 통과 기준을 미리 적어 두면 두 가지가 생긴다.

- 매니저와 임원이 **언제 무엇을 보고 계속/중단을 정하는지** 미리 안다.
- 뒷 단계의 가설(값 비교가 H/W 개선점을 찾는다, 벤더 간 대응이 온톨로지에 쓰인다)이 틀려도 앞 단계의 결과는 남는다.

## 핵심 개념 (What)

### 단계 한눈에

| 단계 | 이름 | 답하려는 질문 | 대상 | 기간 |
|---|---|---|---|---|
| P0 | 준비 | 시작할 수 있는가, 할 만한 크기의 문제인가 | — | ⟨확인⟩ |
| P1 | 지도 | Agent가 쓸 만한 지도를 만드는가 | 장비 모델 1종, 1대 | ⟨확인⟩ |
| P2 | 비교 | 값 비교가 엔지니어에게 쓸모 있는 후보를 내는가 | 같은 모델 여러 대 | ⟨확인⟩ |
| P3 | 정합 | 벤더가 다른 장비의 파라미터를 같은 개념으로 묶을 수 있는가 | 같은 목적, 다른 벤더 1종 | ⟨확인⟩ |
| P4 | 운영·확대 | 사람이 지켜보지 않아도 주기적으로 돌고, 모델을 더할수록 싸지는가 | 모든 모델과 장비 | 상시 |

P2와 P3는 둘 다 P1에만 의존한다. 순서를 바꾸거나 한쪽만 할 수 있다. 수요가 분명한 쪽을 먼저 한다. P4는 둘로 나뉜다. 지도를 갱신하고 모델을 넓히는 일은 P1만 있으면 되고, 관리 대상 값을 점검하는 일은 P2가 끝나야 한다.

### 단계별 할 일과 통과 기준

#### P0 — 준비

| 할 일 | 산출물 |
|---|---|
| 장비의 파일 목록을 뽑아 파일 종류로 묶고, 담당 엔지니어에게 "뜻을 안다"에 표시하게 한다 | 과제 전 장악률 ⟨확인⟩ |
| 지금 장비 간 차이를 볼 때 확인하는 항목을 받아 적는다 | 과제 전 추적 요인 수 ⟨확인⟩ |
| 진행 중인 보정 수치 재조정의 조정 전 값과 장비 간 차이를 기록해 둔다. 조정이 끝나면 되돌려 잴 수 없다 | 재조정 전 기록 (사내용) |
| 최근 연계·분석 과제의 "데이터 찾기" 소요를 조사한다 | 탐색 소요 기준선 ⟨확인⟩ |
| 대상 장비 모델을 정한다. 보유 대수가 여러 대이고 현업 협조가 되는 모델 | 대상 모델 ⟨확인⟩ |
| 장비 폴더의 목록 조회와 표본 복사를 읽기 전용으로 할 수 있는 경로와 승인을 확보한다 | 접근 경로, 파일 목록 1벌 |
| 벤더 계약·보안상 분석 가능 범위를 확인한다 | 대상/제외 목록 |
| GLM-5.3의 능력을 가짜 장비 폴더로 시험한다 — 컨텍스트 길이, 구조화 출력이 형식을 지키는 비율, 처음 보는 포맷의 파서 규칙을 맞히는 비율, 뜻 추정의 정확도 | 모델 시험 결과 |
| **평가 계약**을 쓴다 — 지표마다 분모, 재는 절차, 최소 평가량, 판정하는 사람. 목표 수치는 기준선을 잰 뒤 정하되 P1을 돌리기 전에 고정한다 | 평가 계약서 |
| 승인받을 범위를 정한다 — P0~P1의 기간, 본인 투입, 현업 검증 시간의 상한 | 승인 단위 ⟨확인⟩ |
| 현업 검증자를 정하고 정답 지도(파일 종류 10~20개)를 부탁한다. 엔지니어가 확실히 아는 것과 매뉴얼로 확인되는 것만 넣는다. 쉬운 포맷만 고르지 않고 고유 확장자와 설정·운영 파일을 넣는다. 절반은 고치는 데 쓰고 절반은 통과 판정에만 쓴다 | 정답 지도 (조정용 / 판정용) |
| (home) 가짜 장비 폴더, 스키마, 파이프라인 코드, 프롬프트 초안, 평가 스크립트 | 인계 패키지 |

**통과 기준**: 장비의 파일 목록을 뽑았고 표본을 가져올 수 있다 · 기준선 수치가 있다 · 검증자가 정해졌다 · 인계 패키지가 가짜 장비 폴더에서 끝까지 돈다 · GLM-5.3이 모델 시험에서 정한 선을 넘는다 · 평가 계약의 목표 수치가 고정됐다.

**중단 조건**: 접근 승인이 안 난다. 또는 담당 엔지니어가 이미 대부분을 알고 있고 탐색 소요도 작아서 넓힐 여지가 없다.

#### P1 — 지도 (장비 1대)

| 할 일 | 산출물 |
|---|---|
| 파이프라인 ①~⑤를 실제 장비에 돌린다. 목록 → 묶기 → 표본 수집 → 프로파일 순서 | 구조 지도(미검증), 수집 비율 |
| 역할별로 순서를 둔다: 설정·운영 → 상태 점검 → 측정 산출. 개수가 적고 2단계에 바로 쓰이는 것부터 한다 | 역할별 구조 지도 |
| 목록의 날짜 차이로 주기적으로 갱신되는 파일을 가려낸다 | 상태 점검 파일 목록 |
| 조정용 정답 지도로 채점하며 프롬프트·규칙을 고친다. 판정용은 마지막에 한 번만 쓴다 | 평가 결과 |
| 같은 표본에 대해 사람이 파서와 뜻을 직접 채울 때 걸리는 시간을 일부만 재어 LLM을 쓴 쪽과 비교한다 | LLM이 줄인 시간 |
| 현업이 설정·운영 역할의 교정·설정 분류부터 검증한다 | 구조 지도(검증) |
| 사용 시험: "이 값이 어디에 있는가" 같은 찾기 문제를 여러 개 만들어, 절반은 지도 없이 절반은 지도를 보고 풀게 한다. 다른 과제의 소요와 비교하지 않고 같은 종류의 문제끼리 비교한다 | 사용 시험 기록 |

**통과 기준**: 판정용 정답 지도에서 역할별 포괄률·해석률·누락률·추출 정확도·의미 정확도가 평가 계약의 목표를 넘는다 · 설정·운영 역할의 파일 종류는 빠짐없이 지도에 올랐다 · 사용 시험에서 지도를 본 쪽이 담당자에게 묻지 않고 찾았고, 지도 없이 푼 쪽보다 빨랐다 · 검증된 지도의 장악률이 과제 전보다 높다.

**중단 조건**: 설정·운영과 상태 점검 역할의 해석률이 평가 계약에서 정한 바닥에 못 미친다(핵심 데이터가 해석 못 하는 바이너리에 있다). 또는 같은 표본에서 잰 값으로 볼 때, LLM의 초안을 검증하는 시간이 사람이 직접 채우는 시간보다 평가 계약에서 정한 비율만큼 줄지 않는다.

**P1만으로 남는 것**: 장비 모델 1종의 검증된 데이터 지도. 2027 계획의 장비 연계와 Agent 과제가 바로 쓴다.

#### P2 — 비교 (같은 모델 여러 대)

| 할 일 | 산출물 |
|---|---|
| 같은 모델의 다른 장비에서 목록만 뽑아 파일 종류가 첫 장비와 같은지 본다 | 장비별 목록 ⟨확인: 대수⟩ |
| ⑦ 선별 수집·값 추출을 돌린다. 비교할 필드가 든 파일 종류만 가져온다 | 값 스냅샷, 재적용 비용 |
| 엔지니어에게 이미 아는 장비 간 차이 사례를 받는다. 측정값 보정 수치 사례는 개발 중에 맞춰 보는 재현 시험으로 쓰고, 통과 판정에는 개발 때 보지 않은 다른 사례를 쓴다 | 알려진 차이 목록 (개발용 / 판정용) ⟨확인: 다른 사례가 있는지⟩ |
| 엔지니어가 이미 중요하다고 아는 파라미터를 받아 관리 대상 목록의 첫 줄로 넣는다 | 기존 중요 파라미터 |
| 조건을 맞춰 잰 기존 장비 간 차이 지표가 있는지 확인한다. 없으면 이 단계의 범위를 설정·교정 값의 차이 찾기까지로 줄인다 | 범위 결정 |
| 비교군의 조건, 최소 장비 대수, 후보 수의 상한을 정한다 | 비교 규칙 |
| ⑧ 비교를 돌려 차이 후보표를 만든다. 뜻이 미검증인 필드도 값을 뽑을 수 있으면 올린다 | 차이 후보표 |
| 엔지니어가 후보를 관리 대상 / 참고 / 무관으로 판정하고, 관리 대상의 기준과 점검 주기를 정한다 | 관리 대상 파라미터 목록 1판 |
| 후보표가 알려진 차이를 찾아냈는지, 새 후보 가운데 쓸 만한 것이 있는지 엔지니어와 본다 | 검토 기록 |

**통과 기준 (판정용 사례가 있을 때)**: 판정용 사례가 후보표의 상위 N개 ⟨확인⟩ 안에 든다(보정 수치 사례가 상위에 드는 것은 최소 조건이지 통과의 증거가 아니다. 정렬 규칙을 이 사례를 보고 만들었기 때문이다) · 엔지니어가 "몰랐는데 확인해 볼 만하다"고 한 후보가 한 건 이상 있다 · 상위 N개를 엔지니어가 검토하는 데 드는 시간이 평가 계약의 상한 안이다 · 문제없는 장비를 벗어났다고 올린 비율이 상한 안이다.

**통과 기준 (판정용 사례가 없을 때)**: 재료가 없다고 판정을 미루지 않는다. 상위 N개 후보를 엔지니어가 전부 판정해서, "의도한 차이"나 "무관"이 아닌 것의 비율이 평가 계약의 바닥을 넘고 · 그 가운데 관리 대상으로 올린 것이 한 건 이상이며 · 검토 시간이 상한 안이면 통과다. 어느 쪽 기준을 쓸지는 P2를 시작할 때 정해 적는다.

**중단 조건**: 구조 지도가 장비마다 달라서 재적용이 안 된다. 또는 차이의 대부분이 의도한 설정 차이라 걸러 내면 남는 것이 없다.

**주의**: "값이 다르다"와 "H/W를 고쳐야 한다" 사이에는 엔지니어의 판단이 있다. 이 단계의 산출물은 원인 진단이 아니라 볼 곳을 좁힌 후보표다. 보고할 때 이 선을 넘지 않는다.

#### P3 — 정합 (다른 벤더)

| 할 일 | 산출물 |
|---|---|
| **먼저** 대응표를 받아 쓸 조직·과제를 확인한다. 없으면 이 단계를 시작하지 않는다 | 수요처 ⟨확인⟩ |
| 같은 목적의 다른 벤더 장비 1종에 P1을 다시 한다 | 두 번째 구조 지도, 소요 시간 |
| 공통 개념 목록을 만든다. 처음에는 교정·결과 분류의 핵심 파라미터로 좁힌다 | 개념 목록 |
| ⑨ 개념 정합을 돌리고 현업이 승인한다 | 개념 대응표 |
| 대응표를 받아 쓸 조직·과제에 넘긴다 | 인계 기록 ⟨확인: 수요처⟩ |

**통과 기준**: 공통 절차의 코드를 고치지 않고 두 번째 지도를 만들었다(고친 곳은 접속과 파서뿐이다) · 대응표 승인율이 평가 계약의 목표를 넘는다 · 대응표를 실제로 쓰는 곳이 한 군데 이상 있다. 다른 벤더는 물려받을 것이 적으므로 "첫 번째보다 빨라야 한다"는 조건을 걸지 않는다. 그 조건은 P4의 같은 벤더 두 번째 모델에 건다.

**중단 조건**: 대응표의 수요처가 없다.

#### P4 — 운영

| 할 일 | 산출물 |
|---|---|
| 정기 점검을 예약 실행으로 돌린다. 관리 대상은 자주, 전체 값은 드물게 | 회차별 변경 보고 |
| 관리 대상 값이 기준을 벗어나면 담당 엔지니어에게 알린다 | 알림과 판정 기록 |
| 목록이 달라졌거나 값 추출이 실패한 파일 종류만 다시 프로파일링해 지도를 갱신한다 | 지도 변경 이력 |
| S/W 버전이 바뀌면 이전 버전 지도와의 차이를 낸다 | 버전 간 diff |
| 같은 벤더의 두 번째 모델을 붙이고 든 시간을 잰다. 그다음 다른 벤더 | 모델 추가 비용 |
| 장비 대장에 장비를 더해 간다 | 지도가 덮는 모델 수와 장비 수 |
| 다른 Agent와 과제가 지도를 읽는 창구를 정한다. 처음에는 파일 그대로 | 조회 방법 |

**통과 기준 (전체로 넓히기 전)**: 정기 점검이 사람 손 없이 정해 둔 기간 ⟨확인⟩ 동안 이어서 돌았다 · 수집 성공률이 평가 계약의 목표를 넘는다 · 일부러 끊었을 때 끊긴 단계부터 다시 돈다 · 가짜 장비 폴더에서 S/W 버전이 바뀐 상황(열 추가, 단위 변경, 새 파일 종류)을 만들어 정기 점검이 이를 잡아내는지 시험했다. 실제 장비의 버전 변경은 일정에 넣을 수 없으므로 통과 조건으로 걸지 않고, 일어나면 따로 검증한다 · 알린 것 가운데 조치로 이어진 비율과 놓친 것(엔지니어가 따로 찾은 변화)이 상한 안이다.

**지속 지표**: 지도가 덮는 모델 수와 장비 수 · 관리 대상 파라미터 수 · 점검이 알린 것 가운데 조치로 이어진 비율 · 모델 하나를 더하는 데 드는 시간 · 지도를 재사용한 과제 수.

**넓히기 전에 확인할 것**: 같은 벤더의 두 번째 모델에 든 시간(LLM 호출, 본인 작업, 현업 검증)이 첫 번째보다 평가 계약에서 정한 비율 이상 줄어야 한다. 싸지 않으면 공통으로 뗀 부분이 실제로는 공통이 아니었다는 뜻이므로, 넓히기 전에 설계를 고친다.

## 어떻게 사용하는가? (How)

### 지표 — 정의는 여기 한 곳에만 둔다

| 지표 | 정의 | 쓰는 단계 |
|---|---|---|
| **장악률** | P0에서 뽑은 파일 종류 목록(분모 고정) 가운데 뜻이 확인된 비율. 과제 전은 담당 엔지니어가 "무엇이 들어 있고 어디에 쓰이는지 말할 수 있다"고 표시한 비율이고, 과제 후는 뜻이 지도에 적히고 현업이 승인한 비율이다. 역할별로 따로 낸다. 과제 중에 새로 발견된 항목은 "추가 발견"으로 따로 센다 | 0·1 |
| **추적 요인 수** | 장비 간 비교에 실제로 올린 필드의 수. 과제 전은 지금 장비 간 차이를 볼 때 확인하는 항목의 수다 | 0·2 |
| 포괄률 | 목록의 파일 가운데 어떤 파일 종류에든 속한 비율. **역할별로 따로** 낸다. 측정 산출이 개수의 대부분이라 합쳐서 내면 설정·운영 파일의 누락이 가려진다. 제외한 파일은 분모에서 빼지 않고 "제외"로 따로 센다 | 1 |
| 수집 비율 | 전체 용량 대비 실제로 가져온 표본의 용량. 작을수록 좋다 | 1 |
| 묶음 순도 | 한 종류로 묶은 표본들의 프로파일이 서로 일치한 비율 | 1 |
| 해석률 | 파일 종류 가운데 필드까지 뽑아낸 비율. 나머지는 "해석 불가"로 명시된다 | 1 |
| 누락률 | 정답 지도에 있는 필드 가운데 Agent가 지도에 올리지 못한 비율. 어려운 필드를 빼서 정확도를 높이는 것을 막는다 | 1 |
| 추출 정확도 | 정답 지도의 필드에서 추출 계약대로 읽은 값이 맞은 비율 | 1 |
| 의미 정확도 | 정답 지도와 겹치는 필드에서 뜻·분류가 맞은 비율. 누락률과 함께 본다 | 1 |
| 검증 부담 | 현업이 항목 하나를 판정하는 데 걸린 시간 | 1 |
| 재적용 비용 | 두 번째 장비·두 번째 버전에 지도를 적용하는 데 걸린 시간 | 1→2 |
| 알려진 차이 재현율 | 엔지니어가 이미 아는 장비 간 차이를 비교표가 후보로 올린 비율 | 2 |
| 대응표 승인율 | 제안한 개념 대응 가운데 현업이 승인한 비율 | 3 |
| 관리 대상 수 | 엔지니어가 관리 대상으로 확정한 파라미터의 수. 과제 전에 관리하던 수와 비교한다 | 2 |
| 모델 추가 비용 | 새 모델의 최초 매핑에 든 시간과 검증 시간. 모델을 더할수록 줄어야 한다 | 4 |
| 점검 적중률 | 정기 점검이 알린 것 가운데 엔지니어가 조치한 비율 | 4 |

목표 수치는 0단계에서 기준선을 잰 뒤 정한다. 지금 숫자를 적으면 근거 없는 숫자가 된다.

**채점 규칙.** 뜻이 맞았는지는 글자 비교로 가릴 수 없다. LLM이 채점하면 LLM이 LLM을 채점하는 꼴이 된다. 그래서 다음을 평가 계약에 적는다.

- 뜻의 채점은 사람이 한다. 채점에 드는 시간을 현업 검증 시간에 넣어 잡는다.
- 판정은 넷이다: 맞음 / 일부 맞음(상위 개념까지만 맞음) / 틀림 / `unknown`.
- `unknown`은 틀림으로 세지 않고 따로 센다. 틀린 답을 낸 비율과 답을 안 낸 비율을 함께 본다. `unknown`을 틀림으로 치면 LLM은 지어내서라도 답한다.
- 정답 지도와 Agent의 답이 어긋날 때 정답이 틀렸을 수도 있다. 어긋난 항목은 매뉴얼이나 실제 값으로 다시 확인하고, 정답을 고친 이력을 남긴다.

**장악률의 전과 후는 같은 행위를 재는 것이 아니다.** 전은 사람의 머릿속에 있는 것이고 후는 문서에 적혀 승인된 것이다. 이 차이가 지식 자산화의 뜻이므로 숨기지 않고 그대로 적는다. 전의 값이 부풀려지지 않도록, 엔지니어가 "안다"고 표시한 것 가운데 몇 개를 골라 실제로 설명하게 해 본다.

### home과 office의 분업

| | home | office |
|---|---|---|
| 만드는 것 | 스키마, 파이프라인 코드, 도구, 프롬프트 초안, 가짜 장비 폴더, 평가 스크립트 | 실제 지도, 값 스냅샷, 평가 결과 |
| 검증 방법 | 가짜 장비 폴더에서 끝까지 도는지 | 정답 지도 채점, 현업 검증 |
| 넘어가는 방향 | home → office: 코드와 문서 | office → home: 일반화된 교훈만. 실제 경로·파라미터 이름·수치는 넘기지 않는다 |

가짜 장비 폴더는 실제 장비를 정확히 흉내 낼 필요가 없다. 파이프라인이 만날 **종류**를 담으면 된다: 정형 설정 파일, 날짜별 로그 수백 개, 이름 규칙이 있는 이미지 묶음, 고유 확장자의 텍스트 포맷, 바이너리, 서로를 가리키는 ID, 경로가 적힌 스크립트, 이름 규칙은 같은데 중간에 열이 바뀐 파일.

### 인계 패키지 — GLM-5.3이 실행할 수 있게

home에서 만든 것을 office의 LLM이 그대로 실행하려면 다음을 갖춘다.

| 항목 | 내용 |
|---|---|
| 실행 절차서 | 단계 번호, 각 단계의 입력 파일·명령·출력 파일·성공 판정. 사람이 읽고 따라 할 수 있는 수준 |
| 단계별 프롬프트 | 단계 하나에 프롬프트 하나. 역할, 입력 형식, 출력 스키마, 금지 사항, 예시 한두 개 |
| 출력 스키마 | 코드로 검사한다. 틀리면 오류 내용을 붙여 다시 시킨다 |
| 중간 상태 파일 | 단계 사이의 상태는 전부 파일이다. LLM의 대화 기억에 기대지 않는다. 중간에 끊겨도 그 단계부터 다시 돈다 |
| 가짜 장비 폴더와 기대 출력 | office에서 환경이 맞는지 먼저 돌려 보는 용도 |
| 닫힌 어휘와 문법의 사양 | 이름 자리표시, 파서 규칙의 칸, 분류·역할 목록. 예제를 두세 개씩 붙인다 |
| 단계별 중간 상태 파일의 스키마 | 이름만이 아니라 칸의 정의까지. 단계마다 무엇을 읽고 무엇을 쓰는지 |
| 실패를 되돌려 주는 형식 | 형식 오류와 파서 실패를 LLM에게 어떻게 알려 주는지 |
| 예산의 실제 숫자 | 파일 종류당 LLM 호출 횟수와 시간, 재시도 횟수 ⟨확인: 모델 시험 뒤 정함⟩ |
| 실행 값의 고정 | temperature 등 호출 설정. LLM의 답은 지도에 적힌 뒤 다시 묻지 않는다 |
| 매뉴얼을 자르는 규격 | 조각 크기와 한 번에 주는 조각 수 |

사내 LLM에 맞춘 지시문 원칙:

- 한 번의 호출에 한 가지 일만 시킨다.
- 입력은 짧게 자른다. 파일 전체가 아니라 표본을 준다.
- 판단 기준을 문장이 아니라 표로 준다 (예: 필드 분류 6종의 정의와 예).
- "모르겠으면 `unknown`"을 허용한다. 답을 강제하면 지어낸다. 채점에서도 `unknown`을 틀림으로 치지 않는다.
- 선택지는 닫힌 목록으로 준다. 새 낱말을 지어내면 떨어뜨린다.
- 뜻을 물을 때는 필드 하나가 아니라 파일 종류의 필드 전부를 함께 준다. 이웃한 키가 맥락이다.
- 출력에 근거를 반드시 쓰게 한다. 근거가 비면 스키마 검사에서 떨어뜨린다.
