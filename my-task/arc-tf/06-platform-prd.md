# ARC 플랫폼 1차 PRD: 측정 위치, Align 셋업 반자동화

> 공통 플랫폼 팀이 2027년에 바탕(관찰, 절차, 입력 없는 제안)을 만들고 2028 보조 단계에서 1차 장비군 담당(CD-SEM, VeritySEM, Thickness)이 검증할 제품의 요구사항. 무엇을 만들고, 무엇으로 합격을 판단하고, 무엇은 만들지 않는가.

## 1. 요약 (Executive Summary)

MI 엔지니어가 레시피 셋업의 **측정 위치, Align 셋업 구간**을 맡길 수 있는 반자동 Agent를 만든다. Agent는 엔지니어 본인 PC에서 돌고, 엔지니어가 보는 원격 화면(RCS, 웹 VDI → RCS/Radmin)을 읽고 같은 화면에 입력한다. 측정 실행과 저장은 엔지니어가 승인한다. 지금 이 구간은 숙련자가 "측정 → 실패 → 재조정"을 손으로 되풀이하는 곳이고, 레시피 셋업 전체에 평균 30~60분이 든다(현업 경험치). 일정은 [기획안](./01-tf-proposal.md)의 단계를 따른다. 2027년에는 화면 입력 없이 관찰, 절차화, Shadow 제안(S12)까지 만들고, 화면 입력(S1~S5, S8)은 2028 보조 단계에서 연다. 2028 보조 단계 파일럿에서 1차 장비군마다 대표 레시피 유형 1개의 이 구간 건당 소요 시간을 ⟨확인⟩% 줄이고, 오조작으로 잘못 저장된 레시피는 0건을 지킨다. Align Fail 무인 대응의 화면 입력은 기획안의 승인된 예외로 따로 다룬다.

플랫폼 구조(Offline 지식화, Online 실행, 판단과 규칙 확인과 실행의 분리, 안전 관문)는 [공통 플랫폼 기술 설계](./07-platform-architecture.md)에 있다.

## 2. 문제 (Problem Statement)

상세는 [문제 정의](./00-problem-statement.md)에 있다. 여기서는 요구사항으로 이어지는 부분만 적는다.

### 누가

계측(MI) 장비의 레시피를 셋업하고 튜닝하는 현업 엔지니어. 1차는 CD-SEM, VeritySEM, Thickness 담당자다.

### 무엇이 문제인가

측정 위치와 Align Key를 잡는 동안 측정, 실패, 재조정을 되풀이하고, 그동안 화면 앞을 떠날 수 없다. 그 사이 다른 레시피 요청과 측정 문제의 원인 분석이 밀린다.

### 왜 아픈가

- **엔지니어**: 중요한 일인데 시간 대부분을 같은 클릭과 재조정에 쓴다. 지치고, 실험할 여력이 남지 않는다.
- **회사**: 노하우가 사람에게만 있어 품질이 사람마다 다르고, 장비가 늘면 셋업 인력도 같은 비율로 늘어야 한다.

### 근거

| 종류 | 내용 | 상태 |
|---|---|---|
| 현업 경험치 | 레시피당 평균 30~60분 (셋업 전체) | 확보 |
| 구간 실측 | 측정 위치, Align 구간만의 소요 시간 | ⟨확인: 온보딩 8주차⟩ |
| 셋업 수요 | 장비군별 월 셋업 건수와 증가 추세 | ⟨확인⟩ |
| 엔지니어 목소리 | 리드(CD-SEM) 본인의 경험 | 🔶 가정: VeritySEM, Thickness도 같다. 온보딩 첫 주 인터뷰로 확인 |
| 기술 가능성 | Align Fail PoC에서 API 없는 화면 조작, 오프라인 Align Key 탐색 확인 | 확보 ([PoC 자산](./05-poc-assets.md)) |

## 3. 사용자 (Target Users & Personas)

### 주 사용자: 1차 담당 엔지니어

- **역할**: 자기 장비군의 레시피 셋업 담당. TF에는 주 5시간(근무일마다 1시간) 겸직으로 참여한다.
- **기술 수준**: Python 코드를 읽고 간단히 고칠 수 있다. LLM, VLM의 특성은 온보딩에서 배운다.
- **원하는 것**: 시행착오 구간을 맡기고, 결과만 확인해 승인하는 것.
- **걱정하는 것**: Agent가 생산 레시피를 잘못 건드리는 것. 그래서 저장과 위험 조작의 최종 승인권을 엔지니어가 갖는다.
- **장비군별 차이**: CD-SEM은 엔지니어 PC → RCS로 바로 접속한다. VeritySEM, Thickness는 웹 VDI를 한 번 더 거친다. 화질, 지연, 단축키 처리가 다르다.

### 부 사용자

- **2차 담당 엔지니어**: 1차 기간에는 Agent를 쓰지 않는다. 자기 장비 작업을 녹화하고 절차서를 만든다. 플랫폼이 준비되면 같은 역할로 들어온다.
- **공통 플랫폼 팀**: 장비군별 절차를 받아 엔진에 담고, 실패 기록으로 원인을 찾는다.

### 해야 할 일 (Jobs-to-be-Done)

- 새 레시피의 측정 위치와 Align Key를, 장비 자체 알고리즘이 통하는 위치로 빨리 잡는다.
- 셋업이 어디서 왜 실패했는지 기록으로 확인한다.
- 자기 장비의 절차를 사람이 바뀌어도 남는 형태로 정리한다.

## 4. 전략적 맥락 (Strategic Context)

### 사업 목표

- ITC AIX 로드맵의 레시피 셋업 자동화 과제다. 🔵 열린 질문: 이 과제가 걸린 조직 KPI나 OKR이 있는가, 있다면 무엇인가. 보고 대상 임원(AI TF 담당 임원, 기반기술센터장)과 12월 보고 전에 확인한다.
- 회사에 남는 것: 회수되는 엔지니어 시간(월 ⟨확인⟩시간), 신규 제품, 공정 도입 때 셋업 대기 단축, 장비가 늘어도 셋업 인력을 같은 비율로 늘리지 않는 구조.

### 대안 비교

| 대안 | 왜 안 되는가 |
|---|---|
| 장비 API, 스크립트 자동화 | 장비에 외부 조작 API가 없다 |
| 장비 벤더 기능 | ⟨확인: 벤더가 레시피 자동 셋업을 제공하는지⟩. 제공해도 장비군마다 따로다 |
| 장비군별로 각자 자동화 | 화면 인식, 조작, 안전 장치를 장비마다 새로 만든다 |
| 외부 상용 Computer-use Agent | 외부 LLM API가 사내망에서 막혀 있다 |

### 왜 지금인가

- Align Fail PoC가 끝나 화면 이해, 조작, 안전 규칙이라는 출발점이 있다. 지금 이어 가지 않으면 PoC 자산이 흩어진다.
- 2027년 TF 구성(01 기획안)이 12월에 승인되면 담당 엔지니어 시간이 생긴다. 제품 요구사항이 그 전에 정해져 있어야 1월 온보딩에서 무엇을 재고 무엇을 녹화할지가 정해진다.

## 5. 해결책 개요 (Solution Overview)

### 무엇을 만드나

엔지니어 PC에 설치하는 **반자동 셋업 Agent**와 그것을 장비군마다 쓸 수 있게 하는 **공통 플랫폼**.

**한 건의 흐름**

```
엔지니어: 레시피 생성, 기본 정보 입력 (수동)
   │
   ▼  "여기서부터 맡김"
Agent: 화면 확인 → Align Key 후보 탐색 → 등록 → 측정 위치 후보 탐색 → 등록
   │   단계마다 화면 변화를 검증하고, 실패하면 중단하고 넘긴다
   │
   ├─ 측정 실행이 필요하면 → 승인 화면 → 엔지니어 승인 → 실행 → 결과 판정
   │
   ▼  "여기까지 했음" (근거 화면, 시도 기록과 함께)
엔지니어: 파라미터 설정, 검증 측정 판정, 저장 승인 (수동)
```

### 핵심 기능

| 기능 | 하는 일 | PoC에서 가져오는 것 |
|---|---|---|
| 화면 이해, 조작 | 원격 화면 캡처, 대략 위치 → 정밀 좌표 → OCR 확인 순서로 클릭, 입력 | 2단계 좌표 찾기, VLM/CV 역할 분리 |
| 실행 엔진 | 장비군별 절차를 단계별로 실행하고, 단계마다 성공 조건을 검증 | 상태 머신 기반 실행, 판정 계층 (데모 단계 → 제품화) |
| Align, 측정 위치 셋업 | 기존 Key 재탐색, 신규 위치 후보 제안 | 기준 이미지 기반 Align Key 탐색 (신규 제안은 새로 만든다) |
| 승인 화면 | 위험 조작과 저장 전 엔지니어 승인, 진행 상황 표시 | 알림, 확정 버튼 (대화형으로 확장) |
| 중단, 인계 | 즉시 중단, 마우스, 키보드 반환, 마지막 화면과 단계 전달 | 검증 실패 시 중단 규칙 |
| 기록, 지표 | 시도마다 화면, VLM 응답, 좌표, 판정, 소요 시간 기록 | 실패 회복 기록 |
| 절차 정의 | 담당 엔지니어가 녹화 → 절차서 → 플랫폼 절차로 옮기는 도구 | 녹화 → 조작 타임라인 → 한국어 절차서 |
| 설치형 배포 | 개발 도구 없는 엔지니어 PC에서 실행 | 배포 방식만 결정됨, 패키징은 새로 |

## 6. 성공 지표 (Success Metrics)

측정 규칙(구간의 시작과 끝, 무엇을 개입으로 세는가)은 [기획안의 측정 규칙](./01-tf-proposal.md#효과)과 [온보딩의 기준선 측정 양식](./04-onboarding.md#기준선-측정-양식)을 그대로 쓴다.

### 주 지표

**자동화 대상 구간(측정 위치, Align 셋업)의 건당 소요 시간**
- 현재: ⟨확인: 온보딩 8주차 실측⟩. 참고로 셋업 전체는 30~60분
- 목표: ⟨확인⟩% 단축. 실측 전에는 숫자로 약속하지 않는다
- 시점: 2028 보조 단계 파일럿, 1차 장비군마다 대표 유형 1개. 2027년에는 Shadow 제안의 판단 정확도만 잰다 (S12)

### 보조 지표

| 지표 | 현재 | 목표 |
|---|---|---|
| 건당 예정에 없던 엔지니어 개입 횟수 | ⟨확인⟩ | ⟨확인⟩ |
| 셋업 뒤 첫 측정 성공률 | ⟨확인⟩ | 현재 이상 |
| 엔지니어 1명이 월에 처리하는 레시피 건수 | ⟨확인⟩ | ⟨확인⟩ |
| 절차서로 정리된 레시피 유형 수 | 0 | 장비군마다 1개 이상 |

### 가드레일 지표 (나빠지면 안 되는 것)

| 지표 | 기준 |
|---|---|

| 승인 없이 실행된 위험 조작(측정 실행, 삭제, 모드 변경) | 0건 |
| 생산 측정에 영향 | 0건. 실장비 검증은 인가받은 비생산 검증 시간(하루 1시간)에만 |

## 7. 요구사항 (User Stories & Requirements)

### 가설 (Epic Hypothesis)

측정 위치, Align 셋업 구간을 반자동 Agent에 맡기면, 담당 엔지니어의 이 구간 건당 소요 시간이 ⟨확인⟩% 줄 것이다. 지금은 숙련자가 화면에서 시행착오를 손으로 되풀이하는 것 말고는 방법이 없기 때문이다. 파일럿에서 기준선과 같은 양식으로 재서 확인한다.

### 사용자 스토리

우선순위: **필수**(해당 단계 통과에 필요), **권장**(파일럿 전까지), **나중**(2차 이후).

**단계 구분** (2026-11-08 기획안과 맞춤): 2027 관찰과 지식화에서 만드는 것은 S6, S7, S9, S10, S11, S12. 화면에 입력하는 S1~S5, S8과 S13은 2028 보조 단계에서 연다. 2027년에 S1~S5의 설계와 녹화본 모의 실행은 해도 되지만 실장비 입력은 하지 않는다.

**S1. 구간을 Agent에 맡기기**, 필수
담당 엔지니어로서, 레시피 기본 정보를 입력한 뒤 측정 위치, Align 셋업을 Agent에게 넘기고 싶다. 그래야 시행착오 구간에서 손을 뗄 수 있다.
- [ ] 엔지니어가 시작 화면에서 "시작"을 누르면 Agent가 그 화면을 절차의 시작 화면으로 인식한다. 시작 화면이 아니면 시작하지 않고 이유를 보여준다
- [ ] 실행 중에는 현재 단계와 다음 단계가 승인 화면에 보인다
- [ ] 끝나면 끝 화면, 등록된 위치, 소요 시간을 보여주고 제어권을 엔지니어에게 돌려준다

**S2. Align Key 등록**, 필수
담당 엔지니어로서, Agent가 Align Key를 장비 자체 알고리즘이 통하는 위치로 등록하기를 원한다.
- [ ] 이미 성공 이미지가 있는 레시피 유형은 기준 이미지로 Key 후보를 찾는다
- [ ] 후보마다 CV 매칭 점수를 남기고, 점수가 기준 ⟨확인: 담당 엔지니어가 정함⟩ 미만이면 VLM 답으로 덮어쓰지 않고 중단한다
- [ ] 등록 뒤 장비의 Align이 성공했는지 화면으로 확인한다
- 🔵 열린 질문: 성공 이미지가 없는 **신규** 레시피에서 좋은 Key 위치를 어떻게 고르는가. PoC는 기존 Key 재탐색만 다뤘다. 1차 구축 초기에 장비군 담당과 기준을 정한다

**S3. 측정 위치 등록**, 필수
담당 엔지니어로서, Agent가 레시피 유형의 측정 위치를 절차대로 등록하기를 원한다.
- [ ] 담당 엔지니어가 정한 절차의 단계마다 성공 조건을 검증한다
- [ ] 측정 실행이 필요한 단계는 S4의 승인을 거친다
- [ ] 측정 결과를 담당 엔지니어가 정한 판정 기준(성공/실패, 위치 오프셋)으로 판정하고, 판정 근거 화면을 남긴다

**S4. 위험 조작 승인**, 필수
담당 엔지니어로서, 측정 실행, 저장, 적용, 삭제, 덮어쓰기, 모드 변경 전에 승인하고 싶다. Agent가 생산 레시피를 혼자 확정하면 안 된다.
- [ ] [운영 방식의 조작별 승인 표](./03-operating-rhythm.md#조작별-승인)대로 승인이 필요한 조작은 승인 없이 실행되지 않는다
- [ ] 승인 화면에 무엇을 하려는지, 근거 화면, 되돌릴 수 있는지가 보인다
- [ ] 1차에서는 삭제, 덮어쓰기, 모드 변경을 Agent의 조작 목록에서 뺀다

**S5. 즉시 중단과 인계**, 필수
담당 엔지니어로서, 언제든 Agent를 멈추고 이어서 직접 하고 싶다.
- [ ] 중단 수단(⟨확인: 버튼, 단축키⟩)을 누르면 진행 중인 조작이 끝난 직후 멈추고 마우스, 키보드에서 손을 뗀다
- [ ] 검증 실패, 예상 밖 화면, VDI 잠김, 세션 끊김이면 Agent가 스스로 중단한다
- [ ] 중단하면 마지막 화면, 진행 단계, 이유를 엔지니어에게 넘긴다
- [ ] 되돌릴 수 없는 조작이 실패하면 자동으로 다시 실행하지 않는다

**S6. 시도 기록과 지표**, 필수
TF 리드로서, 시도마다 무엇을 했고 어디서 실패했는지 남기고 싶다. 그래야 기준선과 비교하고 원인을 찾을 수 있다.
- [ ] 시도 1건마다 조작 전후 화면, VLM 응답, 좌표, CV 점수, 판정, 구간 소요 시간, 개입 여부를 기록한다
- [ ] 소요 시간은 기준선 측정 양식과 같은 시작, 끝 화면 기준으로 잰다. 승인 대기 시간은 따로 적는다
- [ ] 기록은 장비 뷰어 창만 담는다. 데스크톱 전체와 키 입력은 기록하지 않는다 ([데이터 취급](./03-operating-rhythm.md#데이터-취급))

**S7. 장비군별 절차 정의**, 필수
담당 엔지니어로서, 내 장비의 절차를 코드를 크게 고치지 않고 플랫폼에 정의하고 싶다.
- [ ] 절차는 단계, 각 단계의 성공 조건, 실패 시 행동, 조작별 승인 분류로 정의한다
- [ ] 정의한 절차를 녹화본에 대고 모의 실행할 수 있다 (온보딩 7주차 실습)
- [ ] 장비군별 절차는 공통 저장소 안의 장비군 폴더로 나누고, 공통 엔진은 고치지 않는다
- 🔶 가정: 세 장비군의 차이를 절차 정의만으로 담을 수 있다. 담기지 않으면 결정 기록에 남기고 범위를 조정한다 (위험 R4)

**S8. VDI 경유 장비군 지원**, 필수 (VeritySEM, Thickness 담당)
VeritySEM, Thickness 담당 엔지니어로서, 웹 VDI를 거치는 화면에서도 같은 Agent를 쓰고 싶다.
- [ ] VDI 브라우저가 전체 화면(F11), 배율 100%가 아니면 시작하지 않는다
- [ ] 조작마다 화면이 바뀔 때까지 기다린 뒤 검증한다
- [ ] 절차는 클릭과 일반 문자 입력 위주로 만들고, 로컬 OS가 가로채는 단축키는 쓰지 않는다
- [ ] CD-SEM에서 통과한 결과를 근거로 쓰지 않고 장비군마다 따로 검증한다
- 🔵 열린 질문: 엔지니어 PC의 입력 주입이 VDI 경로에서 막히지 않는가. 리드 본인 PC 테스트 대기 (위험 R16)

**S9. 작업 녹화 → 절차서**, 권장
담당 엔지니어로서, 내가 셋업하는 모습을 녹화해 한국어 절차서로 바꾸고 싶다. 그래야 노하우가 남고 S7의 재료가 된다.
- [ ] 녹화는 본인 동의를 받고 녹화 중임을 화면에 표시한다
- [ ] 녹화본에서 조작 타임라인을 뽑고 한국어 절차서 초안을 만든다
- [ ] 계정, 비밀번호 입력 구간은 가린다

**S10. 설치형 배포**, 필수
담당 엔지니어로서, 개발 도구 없이 내 PC에 설치해 쓰고 싶다.
- [ ] 엔지니어 PC에 설치 프로그램 하나로 설치된다. 장비 PC와 VDI 안에는 설치하지 않는다
- [ ] 사내 VLM 엔드포인트에만 연결한다
- 🔵 열린 질문: 보안 승인 범위와 절차 (위험 R6). 2027-03 전 확정

**S11. 성공 이미지 수집**, 권장
플랫폼 팀으로서, 셋업이 성공할 때마다 Align 성공 이미지를 모으고 싶다. 기준 이미지 방식은 이미지가 쌓여야 효과가 난다.
- [ ] 엔지니어가 성공을 승인한 셋업의 Align 화면을 레시피 유형별로 저장한다
- [ ] 담당 엔지니어가 초기 이미지를 직접 넣을 수 있다

**S12. 입력 없는 Shadow 제안**, 필수 (2027 4분기)
담당 엔지니어로서, Agent가 내 화면을 보고 "다음에 무엇을 할지" 제안만 하는 것을 먼저 보고 싶다. 그래야 화면 입력을 맡기기 전에 판단을 믿을 수 있는지 확인할 수 있다.
- [ ] Agent는 화면에 입력하지 않고, 현재 단계, 다음 조작 단위, 근거 시연, 근거 화면을 승인 화면에 보여준다
- [ ] 제안마다 담당 엔지니어가 맞음, 틀림, 모름을 표시하고 기록한다
- [ ] 상태, 분기 정확도와 미승인 행동 제안률을 [기술 설계의 평가 방법](./07-platform-architecture.md#6-평가-방법)대로 집계한다. 평가 시연은 지식 자산에서 뺀다

**S13. 판단, 규칙 확인, 실행 분리**, 필수 (2028 보조)
TF 리드로서, LLM이 제안한 조작이 승인된 범위 밖이면 실행되지 않기를 원한다.
- [ ] LLM은 분기, 조작 단위, 근거만 제안하고, 서버의 규칙 확인이 권한, 허용 분기, 인자, 값과 단위를 다시 확인한다
- [ ] 규칙 확인이 거부한 제안은 실행으로 넘어가지 않고 기록된다
- [ ] 승인 절차서와 허용 범위는 신뢰 저장소에서만 읽는다. 화면 OCR이나 검색 문서의 글로 바뀌지 않는다
- [ ] 조작 단위는 사전조건, 인자, 사후조건, 재시도 한도를 가진 계약으로 정의한다 ([조작 단위 계약](./07-platform-architecture.md#4-조작-단위-계약))

### 제약과 예외 상황

- **장비 API 없음**: 모든 조작은 화면으로만 한다.
- **사내 모델만**: 외부 LLM API는 쓰지 않는다. 화면 이해는 사내 VLM, OCR로 한다.
- **화면 크기**: FHD 모니터 기준. 🔵 열린 질문: FHD가 아닌 모니터를 쓰는 엔지니어가 있는가.
- **VDI 워터마크**: 🔵 열린 질문: VDI 화면에 워터마크 오버레이가 있는가. 있으면 OCR, CV 매칭 기준을 다시 맞춘다.
- **모델, 화면 변경**: VLM 모델, 플랫폼, 장비 화면, 절차 중 하나라도 바뀌면 이전 검증 결과를 쓰지 않고 재검증한다.
- **추론 서비스 장애**: Agent가 멈추면 장비군 담당은 수동 셋업으로 돌아간다. 장애가 진행 중인 레시피에 흔적을 남기지 않아야 한다.

## 8. 범위 밖 (Out of Scope)

| 만들지 않는 것 | 이유 |
|---|---|
| 레시피 생성과 기본 정보 입력, 파라미터 설정, 검증 측정 판정, 저장의 자동화 | 1차는 시행착오가 가장 많은 구간에 집중한다. 전 과정 자동화는 2028년 이후 |
| 완전 자동(승인 없는 실행) | 반복 검증과 안전 중단 기록이 쌓인 레시피 유형만 단계 승인을 거쳐 나중에 검토한다 |
| 삭제, 덮어쓰기, 장비 모드 변경을 Agent가 하는 것 | 되돌리기 어렵다. 1차에서는 사람만 한다 |
| 장비 PC, VDI 안 설치 | 장비 PC를 바꾸지 않아야 보안 승인 범위가 작아진다. VDI 안 설치는 입력 주입이 막힐 때만 대안으로 검토 |
| 2차 장비군 지원 | 플랫폼이 1차 장비군에서 안정되기 전에 넓히지 않는다. 2차 장비군 담당은 녹화와 절차서로 준비한다 |
| 장비 유지보수, 하드웨어 제어 | ARC 범위가 아니다 |
| Python 기초 교육 | 담당 엔지니어가 갖고 오는 것으로 기대한다 |

## 자기 점검 (Self-Assessment)

- **가장 단단한 절**: 7절 요구사항과 8절 범위 밖. PoC 자산, 안전 원칙, 결정 기록이 이미 있어서 수용 기준을 근거로 쓸 수 있었다.
- **가장 약한 절**: 6절 성공 지표. 주 지표의 현재 값과 목표가 모두 ⟨확인⟩이다. 온보딩 8주차 실측 전에는 이 PRD로 효과를 약속할 수 없다.
- **먼저 검증할 가정**:
  1. Q3 입력 주입, 막히면 S8, S10의 구조가 바뀐다
  2. Q1 신규 위치 선정 기준, S2의 신규 레시피 지원 여부가 여기에 달렸다
  3. S7의 가정, 세 장비군 차이를 절차 정의만으로 담을 수 있는가
- **공유 전 다음 단계**: 플랫폼 팀과 7절 스토리를 함께 읽고 우선순위를 맞춘다. VeritySEM, Thickness 담당 엔지니어가 정해지면 3절과 S8을 같이 검토한다.
