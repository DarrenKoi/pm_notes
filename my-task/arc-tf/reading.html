00README.md

ARC TF — 레시피 자동 생성 태스크포스

장비 레시피(Recipe) 셋업을 컴퓨터 사용(Computer-use) Agent로 자동화하려고, MI 현업 엔지니어와 공통 플랫폼 팀을 묶어 운영하는 TF의 작업공간. 본인이 리드한다.

한 문단 요약

레시피 셋업은 숙련 엔지니어가 원격 제어 화면에서 손으로 하는 반복 작업이고, 장비가 늘면 사람도 그만큼 늘어야 한다. 1차 PoC(Align Fail 대응 자동화)에서 사내 VLM으로 API 없는 장비 화면을 보고 조작할 수 있다는 것, VLM과 CV를 나눠 쓰면 오프라인 평가에서 정밀 좌표도 잡힌다는 것을 확인했다. 남은 문제는 두 가지다. 하나는 현장 신뢰성과 실행 엔진 제품화이고, 다른 하나는 장비군마다 다른 레시피 절차다. 뒤의 것은 현업 지식 없이는 풀 수 없다. 그래서 공통 플랫폼 팀이 엔진을 만들고, 장비군별 셀(MI 엔지니어)이 절차와 판정 기준을 맡는 TF를 꾸린다. 2026-11에 기획안을 쓰고, 12월에 임원 승인을 받고, 2027-01에 가동한다.

0101-tf-proposal.md

ARC TF 구성 기획안

장비 레시피(Recipe) 셋업을 컴퓨터 사용(Computer-use) Agent로 자동화하려고, MI 현업 엔지니어와 공통 플랫폼 팀을 묶은 TF를 2027년 1월부터 운영하겠다는 제안.

한 줄 요청

2027년 1월부터 ARC TF를 구성하는 것을 승인해 주시고, 장비군별 MI 엔지니어가 겸직으로 참여하는 것(주 ⟨확인: N⟩시간)을 허락해 주십시오.

1. 왜 해야 하는가

문제

  • 레시피 셋업은 숙련 엔지니어가 원격 제어 화면에서 마우스와 키보드로 하는 반복 수작업이다. 측정 위치를 잡을 때는 측정, 실패, 재조정을 되풀이한다.
  • 노하우가 개인에게 있다. 사람이 바뀌면 지식이 사라지고, 사람마다 품질이 다르다.
  • 장비가 늘어나면 셋업 인력도 같은 비율로 늘어야 한다. 이 구조로는 규모를 키울 수 없다.

안 하면 생기는 일

  • ⟨확인: 신규 제품·공정 도입 때 레시피 셋업 대기로 늦어지는 기간⟩
  • ⟨확인: 장비군별 레시피 셋업에 쓰는 엔지니어 시간 (월 기준)⟩
  • 장비군마다 따로 자동화를 시도하면 화면 인식, 조작, 안전 장치를 매번 새로 만들게 된다.

효과

효과 측정 지표 현재 목표
셋업 시간 단축 레시피 1건 셋업 소요 시간 ⟨확인: 셀별 실측⟩ ⟨확인⟩% 단축
사람 개입 감소 1건당 엔지니어 개입 횟수 ⟨확인⟩ ⟨확인⟩
품질 균일화 셋업 뒤 첫 측정 성공률 ⟨확인⟩ ⟨확인⟩
지식 자산화 절차서로 정리된 레시피 유형 수 0 장비군마다 1개 이상
확장성 새 장비군 합류에 드는 기간 — ⟨확인⟩

현재 값은 TF 온보딩 기간(2027-01~02)에 셀 엔지니어가 직접 측정해 채운다. 측정하기 전에는 목표를 숫자로 약속하지 않는다.

측정 규칙 (기준선과 파일럿을 같은 조건으로 비교하려고 온보딩 측정 양식에 고정한다)

  • 대상: 셀마다 정한 대표 레시피 유형 1개. 전체 셋업이 아니라 자동화 대상 구간(측정 위치·Align 셋업) 의 시작과 끝을 정해 잰다.
  • 포함: 그 구간 안의 실패·재작업·수동 인계 시간. 승인 대기 시간은 따로 적는다.
  • 개입 횟수: 반드시 거치는 승인(저장 전 등)은 세지 않고, 예정에 없던 개입만 센다.

셋업 시간이 줄면 회사에 무엇이 남는가

레시피 셋업 수요(건/월) × 건당 엔지니어 투입 시간 감소분
  → 회수되는 엔지니어 시간 (월 ⟨확인⟩시간)
  → 신규 제품·공정 도입 때 셋업 대기 단축, 엔지니어가 분석·개선 업무로 이동
  → 장비가 늘어도 셋업 인력을 같은 비율로 늘리지 않아도 됨
  • 가정: ⟨확인: 장비군별 월 셋업 수요와 증가 추세⟩. 셋업 수요가 장비·제품 수와 함께 늘어야 "인력이 비례해야 한다"는 주장이 성립한다.
  • Align Fail PoC의 효과(장비 가동 시간 회수)는 운영 중 정렬 실패를 대응한 효과다. 신규 레시피 셋업의 효과로 옮겨 쓰지 않는다.

2. 이미 확보한 것 — 1차 PoC (Align Fail 대응 자동화)

ARC는 처음부터 레시피 자동 생성을 목표로 했다. 1차 PoC로는 범위가 좁고 효과를 재기 쉬운 Align Fail(정렬 실패) 무인 대응을 골랐다. 이 PoC에서 레시피 자동 생성에 그대로 쓸 기반을 검증했다.

확보한 것 레시피 자동 생성에서의 쓰임
사내 인프라에서 화면 이해 모델(VLM·OCR)을 자체 운영 외부 API 없이 화면 이해
표준 컴포넌트가 아닌 계측 화면에서도 대략 위치 → 정밀 좌표 → OCR 확인 순서로 클릭 API 없는 장비 화면 조작
VLM은 "어디를 볼지", CV는 "정확히 어디인지"를 맡는 역할 분리 원칙 측정 위치·Align Key 등록의 정확도
최근 성공 사례를 모은 기준 이미지로 Align Key 탐색 정확도 개선 (오프라인 평가 기준) 레시피 Align 셋업
실장비 반자동 운영: 위치 재조정은 자동, 최종 확정은 엔지니어 TF의 안전 원칙
엔지니어 작업 녹화 → 조작 타임라인 → 한국어 절차서 장비별 레시피 절차 정의

상세 목록은 PoC 자산과 남은 과제에 있다. 수치는 사내용 문서에만 둔다.

PoC로 확인한 것: API 없는 장비 화면을 보고 조작할 수 있다는 것, 오프라인 평가에서 Align Key를 찾을 수 있다는 것.

아직 확인하지 못한 것:

  • 현장 통합의 신뢰성: 실알람 첫 완주, Align Key 탐색의 실장비 검증이 남아 있다.
  • 실행 엔진: 절차를 실행하는 엔진은 아직 데모 단계다. 레시피 셋업에 쓰려면 제품 수준으로 만들어야 한다.
  • 신규 등록: 기존 Key를 찾는 능력과 새로 등록할 좋은 위치를 고르는 능력은 다르다. 후자는 PoC에서 다루지 않았다.
  • 여러 장비 적용: 장비군마다 다른 화면과 레시피 절차를 담을 수 있느냐. 이것은 도메인 지식을 가진 현업 엔지니어 없이는 풀 수 없다.

앞의 세 가지는 플랫폼 팀이, 마지막은 셀이 푼다. 그래서 TF가 필요하다.

3. 무엇을 하는가 — 범위

구분 내용
최종 목표 신규 레시피 셋업의 전 과정 자동화: 생성 → 측정 위치·Align Key 등록 → 파라미터 → 검증 측정 → 저장
1차 범위 시행착오가 가장 많은 측정 위치·Align 셋업 구간
대상 장비 1차: CD-SEM/VeritySEM + ⟨확인: 장비군 1~2개⟩. 2차: 나머지 MI 장비군
1차에서 사람이 맡는 것 레시피 생성과 기본 정보 입력, 파라미터 설정, 검증 측정 판정, 저장. Agent는 그 사이의 측정 위치·Align 셋업 구간을 맡는다
자동화 수준 반자동(Supervised Autonomy): Agent가 조작하고, 위험 조작(측정 실행, 삭제, 모드 변경)과 레시피 저장·적용 직전에는 엔지니어가 승인한다. 완전 자동은 반복 검증과 안전 중단 기록까지 통과한 레시피 유형만 단계 승인을 거쳐 검토한다
제외 장비 유지보수, 하드웨어 제어, 장비 내부 소프트웨어 설치

4. 어떻게 하는가 — TF 구성

                  │  화면 인식·조작 엔진·안전 규칙  │
                  │  승인 화면·VLM 연동·교육       │
                  └──────────────┬───────────────┘
           ┌─────────────────────┼─────────────────────┐
   ┌───────┴───────┐     ┌───────┴───────┐     ┌───────┴───────┐
   │ 1차 셀 A       │     │ 1차 셀 B       │     │ 2차 셀들        │
   │ CD-SEM/Verity │     │ ⟨확인: 장비군⟩ │     │ 나머지 장비군   │
   │ MI 엔지니어   │     │ MI 엔지니어   │     │ 학습·데이터 준비│
   └───────────────┘     └───────────────┘     └───────────────┘
  • 공통 플랫폼은 모든 장비군이 같이 쓴다. 장비마다 엔진을 새로 만들지 않는다.
  • 장비군별 셀은 MI 현업 엔지니어 1~2명으로 구성한다. 그 장비의 레시피 절차 정의, 성공 판정 기준, 현장 검증을 맡는다.
  • 2차 셀도 1월에 함께 합류한다. 1차 기간에는 학습을 받고, 자기 장비 작업을 녹화해 절차서로 정리한다. 플랫폼이 준비되면 바로 들어온다.
  • 인프라(GPU·VLM 서빙)는 필요해지면 합류하고, 장비 벤더는 필요할 때 자문을 받는다.

역할 분담은 참여 팀과 역할에 있다.

5. 타임라인

시기 단계 하는 일 통과 기준
2026-11 기획 이 기획안 작성, 1차 장비군 후보 협의 기획안 완성
2026-12 승인 임원 보고, TF 구성 승인, 참여 엔지니어 지정 승인과 명단 확정
2027-01~02 온보딩 학습 과정, 셀별 현재 셋업 시간 측정, 대표 레시피 유형 선정, 성공 이미지 수집 시작. 플랫폼 팀은 PoC 남은 일 정리와 실행 엔진 작업 셀마다 기준선과 대상 유형 확정
2027-03~06 1차 구축 실행 엔진 제품화, 측정 위치·Align 셋업 기능 + 1차 셀 절차 정의, 오프라인·비생산 검증 1차 셀마다 대표 유형 1개를 비생산 환경에서 ⟨확인: N⟩회 연속 완주, 실패한 시도는 모두 안전하게 중단
2027-07~09 파일럿 1차 장비군 실장비 파일럿 (필요하면 셀 엔지니어 파견 요청) 성공률·셋업 시간 목표 ⟨확인⟩, 오조작으로 잘못 저장된 레시피 0건
2027-10~12 확장 2차 셀 합류, 1차 셀 유형 확대 2차 장비군 1개 이상 착수

단계 통과 결정: 단계가 끝날 때 리드가 통과 기준과 결과를 정리하고, 셀 엔지니어의 품질 확인을 받아 월간 임원 보고에서 통과를 승인받는다. 기준에 못 미치면 셋 중 하나를 정해 결정 기록에 남긴다: 보완(기간 연장), 축소(대상 유형·장비군 줄이기), 중단. 파일럿을 통과하지 못한 장비군은 2차 확장의 근거로 쓰지 않는다.

2027년 말 목표: 1차 장비군마다 대표 레시피 유형 1개 이상에서 측정 위치·Align 셋업 구간을 반자동으로 수행하고, 그 구간의 건당 셋업 시간을 ⟨확인⟩% 줄인다. 레시피 전 과정 자동 생성은 2028년 이후 목표다.

참여 팀과 역할

누가 TF에 들어오고, 무엇을 책임지는가. 공통 플랫폼 팀과 장비군별 셀로 나눈다.

왜 나누는가

장비군마다 자동화를 따로 만들면 화면 인식, 조작, 안전 장치를 장비 수만큼 다시 만든다. 반대로 플랫폼 팀이 모든 장비의 레시피 절차까지 알 수는 없다. 그래서 엔진은 한 곳(플랫폼)에서, 절차와 판정 기준은 장비를 아는 사람(셀)이 맡는다.

구성

공통 플랫폼 팀 본인 + ⟨확인: 개발 인원⟩ 화면 인식·조작 엔진, 안전 규칙, 승인 화면, VLM 연동, 교육 진행 주 업무

셀 엔지니어가 위험 조작과 레시피 저장의 최종 승인자다. Agent와 플랫폼 팀은 레시피를 혼자 확정하지 않는다.

파일럿 이후

  • 변경과 재검증: VLM 모델, 플랫폼, 장비 화면, 장비별 절차 중 하나라도 바뀌면 이전 검증 결과는 그대로 쓰지 않는다. 그 장비군의 대표 유형을 비생산 환경에서 다시 완주한 뒤에 운영에 반영한다.
  • 장애 연락: 플랫폼이나 모델 장애가 나면 플랫폼 팀이 셀에 알리고, 셀은 수동 셋업으로 돌아간다. 연락 경로는 ⟨확인⟩.
  • 운영 이관: 파일럿을 통과한 장비군을 TF 밖의 상시 운영으로 넘기는 조건과 받을 조직은 ⟨확인⟩. 2027-09 월간 보고에서 정한다.
  • TF 종료·연장: 2027-12 월간 보고에서 리드가 성과와 남은 범위를 정리해 올리고, 임원이 종료, 연장, 상시 조직 전환 중 하나를 정한다.

셀 엔지니어에게 기대하는 것

  • Python 코드를 읽고 간단히 고칠 수 있는 정도의 소양. 기초 문법은 TF에서 가르치지 않는다.
  • 자기 장비의 레시피 셋업 절차를 설명할 수 있다.
  • 겸직 시간 안에서 기준선 측정, 녹화, 검증을 한다.
  • AI·LLM 특성은 몰라도 된다. 온보딩에서 배운다 (온보딩 학습 과정).

운영 방식

회의, 보고, 의사결정, 작업 관리, 안전 원칙. 여러 팀이 겸직으로 모이는 TF라서 정해진 리듬이 없으면 흩어진다.

회의

회의 주기 참석 시간 다루는 것
실무 회의 초기 주 1회 → 집중 단계에서 주 2회 리드, 플랫폼 팀, 셀 엔지니어 ⟨확인: 60분⟩ 셀별 진행, 막힌 것, 다음 주 할 일, 결정 필요 사항
셀 작업 세션 셀마다 필요할 때 플랫폼 팀 1명 + 셀 — 절차 정의, 녹화 검토, 장비 검증
임원 보고 월 1회 리드 (필요하면 셀 대표) ⟨확인⟩ 진행, 지표, 위험, 요청 사항

주 2회로 바꾸는 시점: 1차 구축 단계(2027-03)에 들어가 셀들이 동시에 장비 검증을 하기 시작할 때. 바꿀 때는 결정 기록에 남긴다.

실무 회의 진행 순서

  1. 지난 회의 할 일 확인 (5분)
  2. 셀별 진행: 한 셀에 5분, 형식은 "한 것 / 막힌 것 / 다음 할 일"
  3. 결정 필요 사항: 그 자리에서 정하고 결정 기록에 남긴다. 못 정하면 담당과 기한을 정한다
  4. 위험 목록에서 바뀐 것 확인
  5. 다음 주 할 일과 담당 확정

회의록은 짧게, 결정과 할 일만 남긴다.

월간 임원 보고 형식

1페이지로 쓴다. 기능 설명보다 효과를 먼저 쓴다.

항목 내용
이번 달 결과 무엇이 되었나, 어떤 지표가 바뀌었나
지표 셋업 시간, 예정에 없던 개입 횟수, 셋업 뒤 첫 측정 성공률, 완주한 레시피 유형 수 (기준선 대비, 측정 규칙은 기획안)
다음 달 계획 단계와 통과 기준
위험 새로 생긴 것, 커진 것
요청 임원이 결정하거나 도와줘야 할 것
참여 시간 셀별 겸직 시간 실적 (계획 대비)

의사결정

  • 범위와 우선순위는 리드가 정한다. 장비 절차와 판정 기준은 셀 엔지니어가 정한다.
  • 결정은 결정 기록에 날짜, 결정, 이유와 함께 남긴다. 뒤집을 때도 남긴다.
  • 셀 사이에 의견이 갈리면 실무 회의에서 리드가 정한다. 예산이나 인력이 걸린 것은 월간 보고에서 임원에게 올린다.
  • 단계 통과는 리드가 정리하고 월간 보고에서 임원이 승인한다. 미달이면 보완, 축소, 중단 중 하나를 정한다 (기획안 5절).

작업 관리

  • 할 일은 ⟨확인: 이슈 트래커 / 사내 도구⟩에 셀 단위 라벨로 관리한다.
  • 코드는 공통 플랫폼 저장소 하나에 둔다. 장비별 절차는 같은 저장소 안의 장비군 폴더로 나눈다.
  • 장비 데이터, 화면 캡처, 사내 수치는 사내 환경에만 둔다. 이 문서 폴더에는 일반화된 계획만 남긴다.

안전 원칙 (모든 셀 공통)

PoC에서 정한 규칙을 그대로 가져온다.

  • 검증에 실패하면 기본은 중단이다. 무한 재시도는 없다. 마지막 대안은 사람에게 넘기는 것이다.
  • 되돌릴 수 없는 조작은 실행 전과 후 모두 검증한다. 실패하면 자동으로 다시 실행하지 않는다.
  • 모든 조작은 증거를 남긴다: 조작 전후 화면, VLM 응답, 좌표.
  • 낮은 CV 점수를 VLM 답변으로 덮어쓰지 않는다.
  • 엔지니어 작업 녹화는 화면만 본다. 입력을 가로채지 않는다.
  • 실장비 검증은 처음에는 엔지니어가 지켜보는 상태에서만 한다.

조작별 승인

조작 승인
화면 읽기, 창 전환, 값 확인 필요 없음
측정 위치·Align 후보 선택, 입력란 채우기 (저장 전) 필요 없음. 단계마다 검증하고 실패하면 중단
측정 실행 셀 엔지니어 승인
레시피 저장·적용 셀 엔지니어 승인
삭제, 덮어쓰기, 장비 모드 변경 셀 엔지니어 승인. 1차에서는 Agent에게 맡기지 않는 것을 기본으로 한다

장비군마다 다르게 분류할 조작은 셀이 절차 정의 때 이 표에 더한다.

중단, 인계, 복구

  • 즉시 중단: 엔지니어는 언제든 Agent를 멈출 수 있어야 한다. 중단 수단(버튼·단축키)은 ⟨확인⟩이며, 1차 구축 단계의 필수 기능이다.
  • 제어권 인계: Agent는 중단하거나 실패하면 마우스와 키보드에서 손을 떼고, 마지막 화면과 진행 단계를 엔지니어에게 넘긴다. 엔지니어가 수동으로 이어서 하거나 처음부터 다시 한다.
  • 원본 보존: 기존 레시피를 고치는 작업이면 시작 전에 원본을 백업한다. 신규 레시피는 승인 전까지 확정하지 않는다.
  • 오조작 복구: 잘못 저장된 레시피는 셀 엔지니어가 백업으로 되돌리고, 결정 기록에 원인과 함께 남긴다. 원인을 찾을 때까지 그 절차의 자동 실행을 멈춘다.

온보딩 학습 과정 (2027-01~02, 8주)

MI 현업 엔지니어가 AI Agent로 레시피를 자동화할 때 알아야 할 배경 지식을 쌓는 TF 전용 실무 과정.

왜 필요한가

셀 엔지니어는 장비와 레시피는 잘 알지만, LLM·VLM이 무엇을 잘하고 무엇을 못하는지는 모른다. 이걸 모르면 두 가지가 생긴다.

  • Agent에게 맡기면 안 되는 판단(정밀 좌표, 반복 가능한 판정)을 맡기는 절차를 쓴다.
  • Agent가 실패했을 때 원인이 모델인지, 화면 품질인지, 절차 정의인지 구분하지 못한다.

목표는 엔지니어가 자기 장비의 레시피 절차를 Agent가 실행할 수 있는 형태로 정의하고, 결과를 판정할 수 있게 되는 것이다. AI 개발자를 만드는 과정이 아니다.

전제

  • Python 기초는 다루지 않는다. 코드를 읽고 간단히 고칠 수 있는 정도의 소양은 갖고 온다.
  • 겸직 시간(주 ⟨확인: N⟩시간) 안에서 진행한다. 강의는 짧게 하고 실습을 길게 한다.
  • 강사는 리드와 공통 플랫폼 팀이 맡는다.
  • 1차·2차 셀 엔지니어가 모두 듣는다.

과정

주차 주제 배우는 것 실습
1 TF와 플랫폼 개요, Git ARC 목표, 셀의 역할, 저장소 구조, 브랜치와 리뷰 저장소 받기, 문서 수정 PR
2 LLM·VLM의 특성 잘하는 것(화면 의미 이해, 설명), 못하는 것(좌표가 흔들림, 기억 없음, 환각), 프롬프트가 결과를 바꾸는 방식 같은 화면을 여러 번 물어보고 답이 흔들리는 것 확인하기
3 왜 VLM과 CV를 나눠 쓰는가 "어디를 볼지"는 VLM, "정확히 어디인지"는 CV. 이미지 매칭 점수 읽는 법 PoC의 Align Key 탐색 결과를 보고 점수 해석하기
4 컴퓨터 사용 Agent의 동작 화면 캡처 → 판단 → 조작 → 검증 순환, 실패 유형(화면 품질, 모델, 절차) 플랫폼으로 비생산 화면에서 클릭·입력 시켜 보기
5 안전 규칙과 승인 검증 실패 시 중단, 되돌릴 수 없는 조작, 저장 전 승인, 증거 기록 실패 기록을 보고 원인 분류하기
6 작업 녹화 → 절차서 화면 녹화, 조작 타임라인, 한국어 절차서로 바꾸기 자기 장비 레시피 셋업 1건 녹화하고 절차서 만들기
7 절차를 플랫폼에 정의하기 단계, 각 단계의 성공 조건, 실패 시 행동, 조작별 승인 분류 6주차 절차서를 절차 정의로 옮기고, 녹화본에 대고 모의 실행하기
8 기준선 측정과 판정 기준 측정 양식으로 현재 셋업 시간 재기, 성공 판정 기준 정하기 셀별 기준선과 대표 레시피 유형을 발표

레시피 셋업 기능은 3~6월에 만든다. 그래서 온보딩 실습은 녹화본과 모의 실행으로 하고, 실제 장비 실행은 1차 구축 단계에서 한다.

기준선 측정 양식

8주차에 셀마다 이 양식으로 잰다. 파일럿에서도 같은 양식을 쓴다.

항목 적는 것
레시피 유형 셀의 대표 유형 1개
구간 자동화 대상 구간(측정 위치·Align 셋업)의 시작 화면과 끝 화면
소요 시간 구간 안의 실패·재작업·수동 인계를 포함한 시간. 승인 대기는 따로
예정에 없던 개입 반드시 거치는 승인은 빼고 센다
첫 측정 결과 셋업 뒤 첫 측정의 성공/실패
표본 수 ⟨확인: 유형당 최소 건수⟩

8주차 발표 결과가 TF 구성 기획안의 ⟨확인⟩ 칸(현재 셋업 시간, 목표 단축률)을 채운다.

수료 기준

  • 자기 장비 레시피 셋업 1건의 절차서가 있다.
  • 그 절차를 플랫폼 절차로 정의하고, 녹화본에 대고 모의 실행해 봤다.
  • Agent 실패 기록을 보고 원인(화면 품질 / 모델 / 절차 정의)을 구분할 수 있다.
  • 셀의 기준선과 성공 판정 기준이 정해져 있다.

선택 과정

더 깊이 알고 싶은 엔지니어는 AI/DT 교육 커리큘럼에서 준비 중인 오픈웨이트 LLM 심화 과정을 추가로 들을 수 있다. TF 수료와는 관계없다.

준비물

  • ⟨확인: 실습용 PC와 셀별 작업 녹화본 (6주차 전 녹화 승인 필요)⟩
  • ⟨확인: 실습 중 VLM 호출 한도⟩
  • 실습 자료: PoC의 공개 가능한 화면 예시와 실패 기록

0505-poc-assets.md

PoC 자산과 남은 과제

1차 PoC(Align Fail 대응 자동화)에서 레시피 자동 생성으로 가져오는 것과, 아직 풀지 않은 것.

왜 정리하는가

TF는 0에서 시작하지 않는다. PoC에서 이미 검증한 것을 공통 플랫폼의 출발점으로 쓴다. 반대로 PoC가 다루지 않은 것은 TF가 새로 풀어야 한다. 이 둘을 섞으면 일정을 낙관적으로 잡게 된다.

PoC가 무엇이었나

계측 Lot을 운영하다 보면 Align Fail(정렬 실패)이 자주 난다. 그러면 장비가 멈추고, 사람이 장비에 접속해 정렬을 다시 맞춰야 한다. PoC는 이 대응을 AI가 대신하게 만들었다. 알람 감지 → 장비 접속 → 정렬 보정 → 실패 시 담당자 알림 → 녹화로 이어지는 루프다. 실장비에서는 위치 재조정까지 자동으로 하고, 최종 확정은 엔지니어가 누르는 반자동으로 열었다.

Align Fail 대응은 레시피에 등록된 Align Key와 실제 Wafer 사이의 차이를 사람이 매번 맞추는 일이다. 레시피를 처음부터 제대로 만드는 것이 ARC의 본래 목표이고, Align Fail 대응은 그 일부를 먼저 떼어 검증한 것이다.

가져오는 것

자산 상태 공통 플랫폼에서의 쓰임
사내 화면 이해 모델(VLM·OCR) 서빙 운영 중 화면 이해의 기반. 모델 교체는 측정으로 결정
2단계 좌표 찾기 (대략 위치 → 정밀 좌표) + OCR 확인 검증 완료 장비 화면 클릭·입력
VLM/CV 역할 분리 원칙 확정 모든 셀의 설계 원칙
기존 Align Key 탐색 (성공 사례 기준 이미지, 저배율/고배율 재순위) 오프라인 검증 완료, 현장 검증 대기. 성공 이미지 공급 기능은 구현 대기 이미 등록된 Key를 다시 찾는 데 쓴다. 신규 등록 위치 선정은 아래 "새로 풀어야 하는 것"
상태 머신 기반 실행·판정 계층 판정 계층 구현, 실행 엔진은 데모 단계 레시피 셋업 절차 실행
안전 규칙 (검증 실패 시 중단, 비가역 조작 재실행 금지, 증거 기록) 확정 TF 공통 안전 원칙
엔지니어 작업 녹화 → 조작 타임라인 → 한국어 절차서 녹화 확보, 추출은 현장 미실행 셀의 절차 정의
실패 회복 기록 (알람 1건의 시도·판정을 한 줄로 기록) 구현 완료 셋업 시도 기록과 지표

레시피 생성을 위해 새로 풀어야 하는 것

과제 왜 PoC에 없었나 맡을 곳
레시피 생성의 전 과정 절차 (생성 → 위치 등록 → 파라미터 → 검증 → 저장) PoC는 기존 레시피의 정렬 보정만 다뤘다 셀 + 플랫폼
장비군마다 다른 화면과 절차 PoC는 한 장비군 화면만 다뤘다 셀
신규 Align·측정 위치 선정 (좋은 위치를 고르고 장비 자체 알고리즘으로 통하는지 확인) PoC는 이미 등록된 Key를 찾기만 했다. 위치 제안은 구현하지 않았다 플랫폼 + 셀 (실장비 검증)
성공 이미지 수집과 초기 확보 기준 이미지 방식은 레시피별 성공 이미지가 쌓여야 효과가 나는데, 공급 기능이 구현 대기다. 신규 레시피는 성공 이미지가 처음에 없다 플랫폼 (수집 기능) + 셀 (초기 이미지)
실행 엔진 제품화 PoC의 절차 실행 엔진은 데모 단계다 플랫폼
측정 결과 판정 (성공/실패, 위치 오프셋) Align 성공 여부만 판정했다 셀이 기준, 플랫폼이 구현
엔지니어와 대화하며 진행하는 승인 화면 PoC는 알림과 확정 버튼만 있었다 플랫폼
장비 PC 배포 (개발 도구 없는 PC에서 실행) 방식 결정 대기 플랫폼 + 인프라
등록 위치가 헷갈리기 쉬운 레시피의 재등록 알고리즘으로 안 풀리는 몫이 크다고 확인됨 셀

PoC의 남은 일 (TF 시작 전 정리)

TF 가동 전에 끝내거나, 끝내지 못하면 TF 1차 구축 단계로 넘긴다.

  • ⟨확인: 실알람 첫 완주⟩
  • ⟨확인: Align Key 탐색의 현장 실데이터 검증⟩
  • ⟨확인: 녹화 → 절차서 추출의 현장 실행⟩
  • ⟨확인: 장비 PC 배포 방식 결정⟩

PoC의 수치(대상 장비 수, 주간 발생 건수, 대응 시간, 정확도)는 사내용 문서에만 적는다.

위험 목록

TF 운영과 구현의 위험, 대응, 담당. 실무 회의에서 바뀐 것만 확인한다.

# 위험 가능성 영향 대응 담당 상태
R1 겸직이라 셀 엔지니어 시간이 확보되지 않는다 높음 높음 기획안에 주 N시간 명시, 월간 보고에 참여 시간 실적 보고, 파일럿 때 파견 요청 리드 열림
R2 엔지니어가 AI·LLM 특성을 몰라 Agent에 맞지 않는 절차를 쓴다 높음 중간 온보딩 8주, 2~3주차에서 VLM 한계를 직접 확인하는 실습 플랫폼 팀 열림
R3 Python 소양이 셀마다 다르다 중간 중간 합류 전 기대 수준 공지, 실습은 코드 작성보다 읽기·수정 중심 리드 열림
R4 장비군마다 화면과 절차가 크게 달라 공통 플랫폼에 담기지 않는다 중간 높음 1차를 2~3개 장비군으로 제한, 장비별 차이는 절차 정의로 흡수, 안 되면 결정 기록에 남기고 범위 조정 플랫폼 팀 열림
R5 Agent 오조작으로 잘못된 레시피가 저장된다 중간 높음 저장 전 셀 엔지니어 승인, 검증 실패 시 중단, 실장비는 초기에 입회 검증만 셀 + 플랫폼 열림
