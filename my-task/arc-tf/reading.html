ARC TF: 레시피 자동 생성 태스크포스

장비 레시피(Recipe) 셋업을 컴퓨터 사용(Computer-use) Agent로 자동화하려고, MI 현업 엔지니어와 공통 플랫폼 팀을 묶어 운영하는 TF의 작업공간. 본인이 리드한다.

한 문단 요약

2026년 현재 CD(Align Fail 자동 대응 Agent), Thickness(의뢰부터 Recipe 생성까지 ARC Pipeline), Inspection(ARC용 DB 구축, DRB 기반 ARC 생성)이 각자 ARC를 추진 중이고, 생성형 AI 모델에게 Recipe 작업 방식을 학습시키는 방법의 구체화와, Rule 기반 자동화, 이미지 처리(CV), ML/DL을 생성형 AI 모델과 함께 쓰는 구조가 공통 과제로 남았다. PoC(Align Fail 자동 대응)에서 Agent가 Recipe를 다루는 장비군 공통 방식 두 가지(VLM, PyAutoGUI, Win32를 조합한 Computer Use, 장비 밖에서 Recipe 파일을 편집하는 생성)를 확보했다. 동시에 현업 MI 엔지니어의 노하우를 AI가 쓰는 구조로 개발자가 구현하는 두 역할의 유기적인 협업이 필요하고, 조작, Reverse Engineering, 모델 최적화와 운영, 녹화 DB 추출, 기술 부채 해소는 장비군 공통 과제라는 것도 배웠다. LLM 모델만으로는 정밀 좌표, 장비 절차, 반복 가능한 판정, 화면 조작을 해결하지 못하므로 그 바깥을 채우는 공통 플랫폼이 필요하다. 그래서 공통 플랫폼 팀이 엔진을 만들고 장비군 담당(MI 엔지니어)이 절차와 판정 기준을 맡는 TF를 꾸린다. 2027 상반기에는 1차 장비군 CD-SEM, Thickness, Inspection 위주로 장비군별 목표와 공통 플랫폼 베타까지 가고, 같은 기간 다른 MI 장비군은 장비 특징, 작업 절차, 필요한 기능을 파악한다. 6월 베타 판정 뒤 하반기에 본격 참여한다. 엔지니어는 합류 시점마다 교육을 받으며 참여한다.

ARC TF 문제 정의 (Problem Statement)

MI 엔지니어는 레시피(Recipe) 셋업과 튜닝을 원격 화면에서 손으로 되풀이하느라, 더 많은 레시피를 다루고 문제를 빨리 찾고 실험할 시간을 잃고 있다.

왜 이 문서가 필요한가

TF 구성 기획안은 "TF를 만들자"는 해결책을 제안한다. 해결책을 말하기 전에 누가, 무엇을 하려다, 왜 막히는지를 한 장으로 맞춰 두려고 이 문서를 쓴다. 임원, 담당 엔지니어, 플랫폼 팀이 같은 문제를 보고 있어야 TF의 범위와 지표를 두고 다투지 않는다.

이 문서에는 해결책을 넣지 않는다. 해결 방향은 맨 끝에 한 절로만 적고, 상세는 기획안으로 넘긴다.

문제 서술 (Problem Framing Narrative)

나는: 계측(MI) 장비의 레시피를 셋업하고 튜닝하는 현업 엔지니어다. - CD-SEM, Thickness, VeritySEM 같은 장비를 원격 제어 화면(RCS, 웹 VDI → RCS/Radmin Viewer)으로 다룬다. - 신규 제품, 공정이 들어오거나 측정이 흔들릴 때마다 레시피를 만들거나 다시 맞춘다. 레시피 한 건에 30~60분이 든다 (셋업 전체 기준). - 어디를 측정 위치로, 어디를 Align Key로 잡아야 통하는지는 경험으로 안다. 그 경험은 문서가 아니라 내 머릿속에 있다.

하려는 것: - 레시피를 짧은 시간에 정확하게 만들고, 측정 문제가 생기면 원인을 빨리 찾아 고치고, 남는 시간에 더 많은 실험과 테스트를 하고 싶다.

그런데: - 측정 위치, Align 셋업 구간에서 "측정 → 실패 → 위치 재조정"을 되풀이한다. 시행착오가 가장 많은 구간이고, 그동안 화면 앞을 떠날 수 없다. - 레시피 한 건에 붙어 있는 동안 다른 레시피 요청은 쌓이고, 측정 문제의 원인 분석은 뒤로 밀린다. - 같은 레시피라도 누가 셋업하느냐에 따라 품질이 다르고, 담당자가 바뀌면 노하우가 함께 사라진다. - 반복 작업이 길어서 지친다. 새로운 조건을 시험해 볼 여력이 남지 않는다.

왜냐하면: - 레시피 셋업의 핵심 판단(이 위치가 좋은가, 이 측정이 성공인가)이 숙련자의 눈과 손에만 있다. 그 판단을 대신하거나 기록해 둘 수단이 없다. - 장비는 외부에서 조작할 API가 없다. 사람이 보는 원격 화면이 유일한 접점이라, 일반적인 스크립트 자동화가 통하지 않는다. - 장비별 절차를 아는 사람(현업 엔지니어)과 화면 자동화를 만들 수 있는 사람(개발)이 나뉘어 있다. 한쪽만으로는 자동화가 완성되지 않는다.

그래서 나는: - 중요한 일인데 대부분의 시간을 같은 클릭과 재조정에 쓰고 있어 답답하고 지친다. - 쌓여 가는 요청 앞에서 "실험은 나중에"를 반복하게 된다. - ⟨확인: 선발대(CD-SEM, Thickness, Inspection) 담당 엔지니어와 2차 장비군 담당 엔지니어도 같은 감정을 말하는지, 각 합류 교육 첫 주 인터뷰⟩

위 감정은 CD-SEM을 직접 맡는 리드의 경험에서 나왔다. 다른 장비군 엔지니어의 말로 확인되기 전에는 공통 문제로 일반화하지 않는다.

맥락과 제약 (Context & Constraints)

  • 조작 경로: 장비마다 다르다. CD-SEM은 엔지니어 PC → RCS로 바로 접속하고, VeritySEM, Thickness는 웹 VDI의 가상 Windows 안에서 RCS나 Radmin Viewer로 접속한다. 모니터는 대부분 FHD다.
  • 장비 PC 변경 불가: 장비 PC에는 아무것도 설치하지 않는다. 무엇을 하든 엔지니어 본인 PC에서 해야 한다.
  • 사내 모델만 사용: 외부 LLM API는 막혀 있다. 화면 이해는 사내 VLM, OCR로 해야 한다.
  • 생산 장비 안전: 잘못 저장된 레시피는 생산 측정에 바로 영향을 준다. 저장, 적용과 위험 조작(측정 실행, 삭제, 모드 변경)은 엔지니어가 최종 승인해야 한다.
  • 검증 시간: 실장비 검증은 장비 사용 인가를 받은 하루 1시간뿐이다.
  • 현업 시간: 담당 엔지니어는 겸직이다. 주 5시간(근무일마다 1시간)을 넘겨 기대할 수 없다.
  • 기밀: 장비 수치, 실명, 팀명은 사내용 문서에만 둔다.

최종 문제 정의 (Final Problem Statement)

Lesson Learned (공통)

  1. 생성형 AI 모델에게 Recipe 작업 방식을 어떻게 학습시킬 것인지 구체화 필요
  2. Rule 기반 자동화, 이미지 처리(CV), ML/DL을 생성형 AI 모델과 함께 쓰는 구조 필수
  3. LLM 모델만으로는 정밀 좌표, 장비 절차, 결과 확인, 화면 조작을 해결하지 못함. 그 바깥은 공통 플랫폼이 채워야 함 (상세는 별첨)

1. PoC에서 얻은 성과와 시사점

ARC는 처음부터 레시피 자동 생성을 목표로 했습니다. PoC로는 범위가 좁고 효과를 재기 쉬운 Align Fail 자동 대응을 골랐습니다. 이 PoC에서 특정 장비군에 묶이지 않고 레시피 자동 생성에 그대로 쓸 수 있는 공통 자산을 얻었고, MI 장비 전반으로 넓히려면 무엇이 필요한지에 대한 시사점도 얻었습니다.

얻은 자산 (장비군 공통)

확보한 것 내용 ARC에서의 쓰임
Agent가 Recipe를 다루는 방식: Computer Use API 없는 장비에서 Agent가 Recipe를 다루는 여러 접근 방식을 시험. VLM(화면을 보고 다음 조작 판단), PyAutoGUI(정해진 순서의 키보드, 마우스 입력), Win32(창과 컨트롤 단위 조작)를 조합해 Computer Use 구현 장비군과 무관한 화면 조작 엔진
장비 밖에서 Recipe 파일을 편집해 생성 장비 화면 조작이 아닌, 외부에서 Recipe 파일을 편집해 작성. 장비 화면을 거치지 않아 조작 단계 축소. Recipe 파일 구조 해석(Reverse Engineering) 필요 화면 조작 없이 Recipe 생성. 저장과 적용은 엔지니어 승인

Align Fail 대응의 세부 자산은 PoC 자산과 남은 과제에 있으며 수치는 사내용 문서에만 둡니다.

시사점 1: 개발자와 현업 엔지니어, 두 역할의 유기적인 협업 필요

역할 하는 일 한쪽만 있으면
개발자 화면 인식, 조작 엔진, 안전 규칙, 모델 서빙과 평가 장비 화면과 셋업 절차를 몰라 무엇을 자동화할지 정하지 못함
현업 엔지니어 Recipe 셋업 절차 정의, 성공 판정 기준, 실장비 검증, 결과 책임 화면 인식과 조작 엔진을 만들 수 없음
  • 현업 MI 엔지니어의 업무 노하우와 Recipe 셋업 방식을 AI가 활용할 수 있는 구조로 개발자가 구현해야 함
  • 다른 장비군에는 그 장비를 아는 개발자 부재. 장비군마다 같은 인력 확보 불가

시사점 2: ARC 공통 과제는 공통 플랫폼으로 대응

공통 과제 내용 공통 플랫폼에서
Agent의 마우스, 키보드 조작 장비군마다 화면은 달라도 캡처, 입력, 즉시 중단은 같은 문제 조작 엔진을 플랫폼 팀이 한 번 만들고 모든 장비군이 같이 씀
Reverse Engineering 외부 파일 편집 방식은 Recipe 파일 구조 해석이 전제 파일 구조 해석 방법과 도구를 공통으로 정리
AI 모델 최적화와 운영 유지 사내 VLM, OCR 서빙, 튜닝, 장애 대응, 버전 관리, 새 모델 벤치마크와 교체 모델 서빙과 평가를 플랫폼 팀이 한 번 만듦. 녹화본 평가 세트를 공통으로 두고 모델 교체는 측정으로 결정
녹화 DB 추출 녹화분 확보 경로가 정해져 있지 않음. 녹화분에서 Recipe 작업 내용을 추출하고 AI가 이해할 수 있게 라벨링하는 일은 장비를 아는 현업 엔지니어가 필요함 H/W 담당자와 접근 경로를 확정하고 녹화분 수집을 플랫폼 기능으로 만듦. 작업 내용 추출과 라벨링은 장비군 담당 엔지니어가 맡음
기술 부채 해소 Vibe Coding으로 원리 확인 없이 진행한 사항이 대부분임 플랫폼 팀이 PoC 코드의 원리를 확인하고 재사용, 고쳐 쓰기, 버림으로 정리 (2027-06 요소 목록)
  • 같은 일을 장비군마다 반복하면 확장 불가

시사점 3: 별도 운영 PC 대신 엔지니어 PC에 설치

처음에는 Agent 전용 PC를 따로 마련해 그 PC에서 운영하려고 했습니다. 그러나 사무 PC를 계속 늘리는 방식에는 제약이 많아 공통 플랫폼을 개발해 엔지니어 본인 PC에 설치하는 방향으로 바꿨습니다.

별도 PC 방식의 제약 엔지니어 PC 설치형에서
장비군, 엔지니어가 늘 때마다 PC 추가 확보 절차를 거쳐야 함 (자산 신청, 자리 확보 등) 이미 사용 중인 PC에 S/W를 설치하는 형태
PC마다 장비 접속 권한(RCS, SecureVDI)을 따로 받아야 함 엔지니어가 이미 가진 계정과 접속 경로를 그대로 씀. 보안 승인은 설치형 프로그램 하나로 받음
운영 PC 별도 관리로 인한 부담 사내 배포로 일괄 갱신
엔지니어가 결과를 보려면 그 PC 앞에 가거나 원격으로 따로 들어가야 함. 아무도 보지 않는 화면이 생김 Agent를 엔지니어가 보는 화면에서 운영, 엔지니어가 즉시 확인, 중단. 엔지니어가 원할 때 Agent를 실행하고 작업에 대한 책임을 짐 (Human on Command)
장비별로 따로 꾸리면 PC마다 자동화가 달라짐 모든 장비군이 같은 플랫폼을 씀
(변경 시 부작용) Agent가 엔지니어 화면을 일시적으로 제어. 화면 입력 몇 초 동안은 엔지니어가 PC를 쓸 수 없음. 관찰과 판단은 백그라운드로 가볍게 돌리고 입력은 제어권 인계(알림 → 인계 → 입력 → 반환)로 함

결론: MI 장비 전반의 ARC는 공통 플랫폼으로

  • ARC를 하기 위한 필수 요소들(화면 인식, 조작 엔진, Reverse Engineering, 안전 규칙, 모델 서빙과 평가, 녹화분 수집)은 공통 플랫폼으로 해결
  • 장비 노하우와 판정은 장비군 담당자(MI 엔지니어)의 역할
  • 개발자가 장비를 다 알 필요도, 엔지니어가 개발을 다 할 필요도 없게 만드는 것이 TF의 목적임

현업이 이미 만든 자동화 (Thickness)

  • Thickness 담당자들이 PyAutoGUI 기반으로 자동화해 둔 작업이 많음. 고정 좌표와 정해진 순서로 반복 입력을 처리하는 방식임
  • 검토 과제: 이 PyAutoGUI 자동화와 VLM 기반 방식을 어떻게 섞어 쓸지 정해야 함
  • 정해진 순서의 반복 입력: 검증된 PyAutoGUI 스크립트를 그대로 재사용
  • 화면 인식과 판단이 필요한 구간 (위치 확인, 예외 화면, 막힘): VLM이 맡음
  • PyAutoGUI 스크립트 앞뒤에 VLM 화면 확인을 붙여 화면이 예상과 다르면 멈추게 함
  • 2027-01 합류 교육 때 Thickness 기존 스크립트를 목록화하고 2027-06 요소 목록에 혼합 방식을 반영함

2. 레시피 셋업의 문제

문제

  • 레시피 셋업은 숙련 엔지니어가 원격 제어 화면에서 마우스와 키보드로 하는 반복 수작업임. 측정 위치를 잡을 때 측정, 실패, 재조정을 되풀이함
  • 노하우가 개인에게 있음. 담당자가 바뀌면 지식이 사라지고 사람마다 품질이 다름
  • 관리 장비가 늘어나거나 개발 제품이 증가하면 셋업 인력도 같은 비율로 늘어나야 하나, 이 구조로는 한계가 있음
  • 측정 중 Align Fail(정렬 실패) 알람이 나면 엔지니어가 원격으로 위치를 다시 잡을 때까지 장비가 멈춤

안 하면 생기는 일

  • ⟨확인: 신규 제품, 공정 도입 때 레시피 셋업 대기로 늦어지는 기간⟩
  • ⟨확인: 장비군별 레시피 셋업에 쓰는 엔지니어 시간 (월 기준)⟩
  • ⟨확인: Align Fail 알람으로 멈추는 장비 시간 (월 기준)⟩
  • 장비군마다 따로 자동화를 시도하면 공통 과제(조작, Reverse Engineering, 모델 운영, 녹화분 확보)와 안전 장치를 매번 새로 풀게 됨

3. 추진 방향: 선발대에서 영역 확장으로

핵심 개발 방향

가장 중요한 개발 방향은 공통 플랫폼을 통해 AI가 지식 자산화된 마우스, 키보드 조작과 레시피 셋업 방법을 수행할 수 있느냐입니다. 엔지니어 작업(화면 녹화, 마우스, 키보드 조작)을 지식 자산(절차, 노하우, 결정 지점)으로 만들고, 공통 플랫폼(화면 인식, 입력 실행, 안전 규칙)이 이를 수행해 2029년에는 Agent가 셋업을 진행하고 위험할 때만 엔지니어가 개입하는 것을 목표로 합니다.

핵심 요소 하는 일 근거
1. 지식 자산화 엔지니어 작업 녹화에서 절차, 노하우, 결정 지점을 추출. 현업 엔지니어가 라벨링하고 승인. Recipe 작업 방식을 AI가 학습할 수 있는 형태로 정리 Lesson Learned 1
2. 생성형 AI + 기존 자동화 결합 생성형 AI는 다음 할 일을 판단. Rule, CV, ML/DL은 정밀 좌표, 규칙 확인, 결과 검증을 맡음. 새 모델은 공통 평가 세트로 재고 교체 Lesson Learned 2, 3 (별첨)
3. 공통 실행 엔진 Computer Use(VLM, PyAutoGUI, Win32)와 외부 Recipe 파일 편집(Reverse Engineering). 엔지니어 승인, 즉시 중단, 제어권 인계 PoC 공통 자산
  • 플랫폼의 역할: 2028 보조(엔지니어 앞에서 반복 입력 대행) → 2029 자율(Agent가 셋업 진행)이 될 수 있도록 점진적 발전

단계별 추진

한 번에 모든 장비군으로 시작하지 않고 이미 기능이 갖춰진 장비군으로 먼저 플랫폼을 다진 뒤 넓힙니다.

단계 시기 대상 하는 일 넘어가는 조건
1차: 선발대 2027 상반기 CD-SEM, Thickness, Inspection 장비군별 목표 (CD-SEM Align Fail 자동 대응 및 Recipe Tuning(이미지 변경) 구현, Thickness Film 10 Layer 이하 의뢰 Recipe 90% 이상 생성 자동화, Inspection 전체 디바이스향 DRB 기반 ARC 확장(Optical Inspection 장비군)). 이 과정에서 공통 플랫폼 설계를 완성하고 베타 버전을 세 장비군 담당 엔지니어 PC에서 운영 2027-06 관문: 장비군별 목표와 플랫폼 베타를 따로 판정, 2차 합류는 베타 판정으로 결정
2차: 영역 확장 2027 하반기부터 다른 MI 장비군 2차 장비군 본격 합류. 교육, 작업 녹화, 화면 영역 지도, 절차 정의를 공통 플랫폼 위에서 진행. 1차 장비군은 절차화와 지식 자산으로 진행 2027-12 관문: 지식 자산, 2차 합류
  • 선발대가 CD-SEM, Thickness, Inspection인 이유: CD-SEM의 Align Fail PoC(화면 인식, Align Key 탐색, 반자동 운영), Thickness의 기존 PyAutoGUI 자동화와 ARC Pipeline, Inspection의 의뢰서 DB와 Recipe RAG를 재사용할 수 있음. 처음부터 만들지 않고 플랫폼 설계에 집중할 수 있음
  • 1차 장비군 위주로 개발을 시작하는 이유: 플랫폼보다 일이 먼저 넓어지면 장비군마다 따로 만들게 됨. 사람은 처음부터 정해 두되, 개발은 플랫폼이 준비된 만큼만 넓힘. 베타 판정으로 검증된 것만 넓혀 실패 비용도 줄임
  • 2차 장비군의 상반기 참여: 인터뷰, Recipe Workflow 조사로 준비 (주 1~2시간). 상반기 운영은 CD-SEM, Thickness, Inspection 중점이고, 나머지 장비군은 담당자 인터뷰와 Recipe Workflow 조사로 아래 내용을 파악함. 초기에 다른 장비군의 특징을 알아 두는 것이 중요함. 그래야 공통 플랫폼이 1차 장비군에만 맞춰지지 않음
  • 장비 특징: 화면 구성, 접속 경로, 원격 계층, 화면 품질
  • 작업 절차: 레시피 셋업과 Align 대응 순서, 막히는 지점 (작업 녹화로 남김. 녹화 DB 접근이 되면 DB에서, 안 되면 최소 녹화기로)
  • 필요한 기능: 공통 플랫폼에 있어야 할 기능과 장비군 고유 기능
  • 산출물: 장비군별 요구사항 정리. 2027-03 1차본을 플랫폼 설계 확정에 반영하고, 6월 베타 판정 전에 보완
  • 교육과 개발 지원은 하지 않음. 6월 베타 판정 뒤 주 5시간으로 늘리고 2기 교육 시작
  • 베타 기준 (2027-06 관문에서 판정): 선발대 담당 엔지니어 PC에서 설치형 에이전트가 엔지니어가 시작하는 관찰과 녹화, 장비군별 입력과 즉시 중단을 ⟨확인⟩주 동안 문제없이 운영 (상시 관찰 모드는 3분기에 완성). 엔지니어 PC 자원 한도 준수. 새 장비군은 장비별 코드 없이 화면 영역 지도와 절차 정의만으로 얹을 수 있는 구조
  • 베타 기준에 못 미치면 2차 합류를 늦추고 선발대에서 보완함

자동화 대상 구간의 실측값과 나머지 현재 값은 장비군마다 합류 교육 뒤 기준선 측정 기간(선발대 2027-02, 2차 2027-08)에 담당 엔지니어가 직접 측정해 확정하겠습니다. 측정하기 전에는 목표를 숫자로 정하지 않습니다.

자동화 측정 기준: ARC가 얼마나 넓게 쓰였는지는 Recipe 의뢰 수 기준으로, Recipe 하나에 Agent가 얼마나 개입했는지는 Recipe별 비율로 표기합니다.

  • ARC 적용 비율 = ARC를 적용한 Recipe 수 / 같은 기간 Recipe 의뢰 수 (%)
  • Agent 개입 범위 = Agent가 진행한 셋업 단계 수 / 그 Recipe의 전체 셋업 단계 수 (Recipe별 %)
  • 작업 경과 시간: 셋업 시작부터 끝까지 걸린 시간 (셋업 시간 단축 지표에 씀)

측정 규칙 (기준선과 이후 측정을 같은 조건으로 비교하기 위해 합류 교육 측정 양식에 고정)

  • 대상: 장비군마다 정한 대표 레시피 유형 1개. 전체 셋업이 아닌 자동화 대상 구간(측정 위치, Align 셋업) 의 시작과 끝을 정해 측정
  • 포함: 그 구간 안의 실패, 재작업, 수동 인계 시간. 승인 대기 시간은 별도 기록
  • 단계 구분: Recipe별 셋업 단계는 절차서의 의미 단계를 기준으로 셈. 반드시 거치는 엔지니어 승인(저장 전 등)은 Agent 진행에서 빼지 않음

ARC 적용 비율과 Agent 개입 범위가 오르면 회사에 무엇이 남는가

레시피 셋업 수요(건/월) × ARC 적용 비율 × 건당 셋업 시간 × Agent 개입 범위
  → 엔지니어 손을 거치지 않은 셋업 시간 (월 ⟨확인⟩시간)
  → 신규 제품, 공정 도입 때 셋업 대기 단축, 엔지니어가 분석, 개선 업무로 이동
  → 장비가 늘어도 셋업 인력을 같은 비율로 늘리지 않아도 됨
  • 가정: ⟨확인: 장비군별 월 셋업 수요와 증가 추세⟩. 셋업 수요가 장비, 제품 수와 함께 늘어야 "인력이 비례해야 한다"는 주장이 성립함

공통 플랫폼 구조

공통 플랫폼은 현업 엔지니어가 자기 작업을 AI가 이해하는 형태로 바꾸고, 시험해 보고, Agent로 실행하는 작업 공간입니다. ARC를 하기 위한 필수 요소들은 공통 플랫폼으로 해결하고, 장비 노하우와 판정은 장비군 담당자가 맡습니다.

엔지니어가 하는 일 내용
① 지식 자산화 자기 작업을 녹화해 AI가 이해할 수 있는 형태(절차, 노하우, 결정 지점)로 변환. 엔지니어가 검토하고 직접 승인. 결과는 Agent가 쓰는 Recipe DB로 축적
② 실험 녹화본으로 절차를 모의 실행해 보고 수정. 모델, 프롬프트, 절차를 바꿔 결과 비교. 실장비에 쓰기 전 미리 검증
③ 실행 Computer Use(VLM, PyAutoGUI, Win32로 화면 조작)와 외부 Recipe 파일 편집(Reverse Engineering). 엔지니어 승인, 즉시 중단, 제어권 인계
  • 공통 기반 (공통 플랫폼 팀): 모델 서빙과 평가(생성형 AI + Rule, CV, ML/DL), 녹화 DB 수집, 안전 규칙과 실행 로그, 설치형 에이전트와 사내 배포
  • 개선 순환: 엔지니어가 실전에서 사용 → 개발자에게 피드백 → 개발자가 플랫폼에 반영 → 다시 실전 사용, 반복. 플랫폼은 처음부터 완성해서 넘기는 것이 아니라 현업 사용과 피드백으로 함께 키움
  • AI가 정한 다음 조작은 서버의 규칙 확인이 허용 여부를 다시 판단하고, 정해진 조작 단위만 실행함. 결과가 불명확하거나 화면이 예상과 다르면 멈추고 엔지니어를 부름
  • 2027년에는 1차 장비군의 승인된 조작(장비군별 목표)만 자동 운영하고, 그 밖에는 화면 입력 없이 "다음에 할 일"을 제안만 해서 판단 정확도를 먼저 검증함. 일반 화면 입력은 2028 보조 단계부터

상세 설계는 공통 플랫폼 기술 설계에 있습니다.

자동화 수준과 안전 원칙

  • 반자동(Supervised Autonomy)이 원칙임: Agent가 조작하고, 위험 조작(측정 실행, 삭제, 모드 변경)과 레시피 저장, 적용 직전에는 엔지니어가 승인
  • Align Fail 자동 대응도 엔지니어가 자리에 있는 것이 전제임: Agent는 엔지니어 본인 PC에서 관찰과 판단을 백그라운드로 하고, 화면에 입력하는 몇 초 동안만 엔지니어에게서 제어권을 넘겨받음(알림 → 인계 → 입력 → 결과 확인 → 반환). 엔지니어가 마우스를 건드리면 즉시 멈춤. 결과의 책임은 담당 엔지니어에게 있음. 엔지니어가 없는 무인 운영은 목표가 아님
  • 1차 장비군 목표의 자동화는 승인된 예외임: 허용 조작은 장비군마다 승인받은 범위로 한정함. CD-SEM Align Fail은 위치 재조정, 재측정 재시도, Recipe 이미지 변경. Thickness는 Recipe 생성, Inspection은 DRB 튜닝 기반 Recipe 생성. 만들거나 고친 Recipe의 저장과 적용은 엔지니어 승인 뒤에만 함. 삭제, 모드 변경은 계속 금지. 인식이 불확실하거나 화면이 예상과 다르면 Agent가 스스로 멈추고 엔지니어를 부름
  • 자동 전환 승인: 반자동 운영 실적을 리드가 정리하고, 담당 엔지니어 확인을 거쳐 월간 보고에서 장비별로 승인받음
  • 레시피 셋업의 완전 자동은 반복 검증과 자체 중단 기록까지 통과한 레시피 유형만 단계 승인을 거쳐 검토함

6. 교육하며 운영

현업 엔지니어 대부분은 장비와 레시피는 잘 알지만 개발과 AI에는 익숙하지 않습니다. 교육을 먼저 끝내고 시작하지 않고 합류 시점마다 교육을 진행하면서 TF를 운영합니다.

  • 강사는 TF 리드와 공통 플랫폼 팀이 맡음. 교육 시간은 개발 인력 배분에 포함함

7. 일정

2027년은 상반기 선발대, 하반기 영역 확장으로 진행합니다. 상반기에 1차 장비군별 목표(CD-SEM Align Fail 자동 대응 및 Recipe Tuning(이미지 변경) 구현, Thickness Film 10 Layer 이하 의뢰 Recipe 90% 이상 생성 자동화, Inspection 전체 디바이스향 DRB 기반 ARC 확장(Optical Inspection 장비군))를 달성하면서 공통 플랫폼 설계를 완성하고 베타로 운영합니다. Align Fail은 일회성 시제품이 아니라 플랫폼 부품(화면 캡처, 화면 영역 지도, 입력 실행기, 자체 중단, 실행 로그)으로 만들고, 그 과정에서 필요했던 요소를 장기 계획에 반영합니다.

별첨: LLM 모델만으로는 ARC 자동화가 안 되는 이유

최신 LLM, VLM이 화면을 잘 읽어도, 모델 하나만으로는 레시피 셋업을 맡길 수 없습니다. 모델은 "화면을 보고 다음 할 일을 판단"하는 한 부분이고 나머지는 플랫폼이 채워야 합니다.

항목 모델만 쓸 때의 한계 그래서 플랫폼에 필요한 것
좌표 정밀도 같은 화면도 물을 때마다 위치가 달라짐. Align Key, 측정 위치는 정밀 좌표가 필요함 VLM은 "어디를 볼지", CV가 정밀 좌표, OCR로 결과 확인
장비 지식(노하우) 범용 모델은 사내 계측 화면, 셋업 절차, 성공 판정 기준을 모름 엔지니어 작업 녹화에서 뽑고 담당 엔지니어가 승인한 절차 (지식 자산)
성공/실패 여부 조작이 제대로 됐는지 스스로 확인하지 못하고 "성공"이라고 답할 수 있음. 실패를 놓치면 오측정, 레시피 오변경으로 이어짐 서버 규칙 확인, 조작 뒤 결과 검증, 불확실하면 멈추고 엔지니어 호출
진행 상태 셋업은 수십 번의 조작으로 이어지는데, 어디까지 했는지, 무엇이 바뀌었는지 놓침 절차 상태, 체크포인트, 실행 로그
화면 조작 모델은 답을 낼 뿐이고 장비에는 조작 API가 없음 화면 캡처, 입력 실행기, 제어권 인계, 즉시 중단
  • 모델이 좋아져도 이 표의 오른쪽 칸은 그대로 필요함. 최신 VLM은 공통 평가 세트로 재서 판단 부분만 바꿔 끼움

참여 팀과 역할

누가 TF에 들어오고, 무엇을 책임지는가. 공통 플랫폼 팀과 장비군 담당으로 나눈다.

왜 나누는가

장비군마다 자동화를 따로 만들면 화면 인식, 조작, 안전 장치를 장비 수만큼 다시 만든다. 반대로 플랫폼 팀이 모든 장비의 레시피 절차까지 알 수는 없다. 그래서 엔진은 한 곳(플랫폼)에서, 절차와 판정 기준은 장비를 아는 사람(장비군 담당)이 맡는다.

PoC는 리드 한 사람이 개발자와 CD-SEM 담당 두 역할을 함께 맡아 진행했다. 두 역할이 동시에 필요하다는 것, 그리고 모델 운영, 최신 VLM 테스트, 녹화분 확보까지 한 사람이 하기에는 시간이 부족하다는 것이 이 분업의 근거다 (PoC 성과와 시사점).

조직과 명단은 2026-12에 2차까지 한 번에 승인받는다. 초기 개발은 선발대(CD-SEM, Thickness, Inspection) 위주로 하고, 2차 장비군(다른 MI 장비군)은 상반기에 인터뷰, Recipe Workflow 조사로 준비하다가 공통 플랫폼이 베타 기준을 통과하면(2027-06) 본격 참여한다.

담당 엔지니어가 위험 조작과 레시피 저장의 최종 승인자다. Agent와 플랫폼 팀은 레시피를 혼자 확정하지 않는다.

파일럿 이후

  • 변경과 재검증: VLM 모델, 플랫폼, 장비 화면, 장비별 절차 중 하나라도 바뀌면 이전 검증 결과는 그대로 쓰지 않는다. 그 장비군의 대표 유형을 비생산 검증 시간에 다시 완주한 뒤에 운영에 반영한다.
  • 장애 연락: 플랫폼이나 모델 장애가 나면 플랫폼 팀이 장비군 담당에 알리고, 장비군 담당은 수동 셋업으로 돌아간다. 연락 경로는 ⟨확인⟩.
  • 운영 이관: 파일럿을 통과한 장비군을 TF 밖의 상시 운영으로 넘기는 조건과 받을 조직은 ⟨확인⟩. 2027-09 월간 보고에서 정한다.
  • TF 종료, 연장: 2027-12 월간 보고에서 리드가 성과와 남은 범위를 정리해 올리고, 임원이 종료, 연장, 상시 조직 전환 중 하나를 정한다.

담당 엔지니어에게 기대하는 것

  • 개발과 AI에 익숙하지 않아도 된다. 합류 시점마다 교육을 받으며 TF에 참여한다. Python은 읽고 간단히 고치는 정도까지 사전 자료와 1주차 실습으로 맞춘다.
  • 자기 장비의 레시피 셋업 절차를 설명할 수 있다.
  • 겸직 시간(근무일마다 1시간) 안에서 기준선 측정, 녹화, 검증을 한다.
  • AI, LLM 특성은 몰라도 된다. 합류 교육에서 배운다 (4주 합류 교육). 선발대는 2027-01, 2차 장비군은 2027-07에 4주 동안 듣는다.

운영 방식

회의, 보고, 의사결정, 작업 관리, 안전 원칙. 여러 팀이 겸직으로 모이는 TF라서 정해진 리듬이 없으면 흩어진다.

실무 회의 진행 순서

  1. 지난 회의 할 일 확인 (5분)
  2. 장비군별 진행: 한 장비군에 5분, 형식은 "한 것 / 막힌 것 / 다음 할 일"
  3. 결정 필요 사항: 그 자리에서 정하고 결정 기록에 남긴다. 못 정하면 담당과 기한을 정한다
  4. 위험 목록에서 바뀐 것 확인
  5. 다음 주 할 일과 담당 확정

회의록은 짧게, 결정과 할 일만 남긴다.

의사결정

  • 범위와 우선순위는 리드가 정한다. 장비 절차와 판정 기준은 담당 엔지니어가 정한다.
  • 결정은 결정 기록에 날짜, 결정, 이유와 함께 남긴다. 뒤집을 때도 남긴다.
  • 장비군 담당 사이에 의견이 갈리면 실무 회의에서 리드가 정한다. 예산이나 인력이 걸린 것은 월간 보고에서 임원에게 올린다.
  • 단계 통과는 리드가 정리하고 월간 보고에서 임원이 승인한다. 미달이면 보완, 축소, 중단 중 하나를 정한다 (기획안 5절).

작업 관리

  • 할 일은 ⟨확인: 이슈 트래커 / 사내 도구⟩에 장비군 단위 라벨로 관리한다.
  • 코드는 공통 플랫폼 저장소 하나에 둔다. 장비별 절차는 같은 저장소 안의 장비군 폴더로 나눈다.
  • 장비 데이터, 화면 캡처, 사내 수치는 사내 환경에만 둔다. 이 문서 폴더에는 일반화된 계획만 남긴다.

안전 원칙 (모든 장비군 공통)

PoC에서 정한 규칙을 그대로 가져온다.

  • 검증에 실패하면 기본은 중단이다. 무한 재시도는 없다. 마지막 대안은 사람에게 넘기는 것이다.
  • 되돌릴 수 없는 조작은 실행 전과 후 모두 검증한다. 실패하면 자동으로 다시 실행하지 않는다.
  • 모든 조작은 증거를 남긴다: 조작 전후 화면, VLM 응답, 좌표.
  • 낮은 CV 점수를 VLM 답변으로 덮어쓰지 않는다.
  • 엔지니어 작업 녹화는 화면만 본다. 입력을 가로채지 않는다.
  • 실장비 검증은 처음에는 엔지니어가 지켜보는 상태에서만 한다.
  • 실장비 검증은 장비 사용 인가를 받은 시간(하루 1시간)에만 한다. 이 시간을 이 문서들에서 "비생산 검증 시간"이라 부른다.
  • Agent는 엔지니어 본인 PC에 설치한 프로그램으로 돈다. 장비 PC에는 설치하지 않는다.

VDI 경유 장비군 화면 규칙 (Thickness, VDI를 거치는 2차 장비군)

Agent는 엔지니어 PC에서 웹 VDI 화면을 통해 RCS/Radmin을 조작한다. VDI 안에는 설치하지 않는다.

  • VDI 브라우저는 전체 화면(F11), 배율 100% 로 고정한다. FHD 모니터에서 화면 위치와 크기가 늘 같아야 좌표가 흔들리지 않는다.
  • 실행 중에는 VDI 브라우저 창이 맨 앞에 있어야 한다. VDI 화면이 아니면(다른 창, 잠김, 세션 끊김) 바로 중단하고 엔지니어에게 넘긴다.
  • 키 입력은 브라우저를 거친다. Alt+Tab, Win 키처럼 로컬 OS가 먼저 처리하는 키는 VDI까지 가지 않으므로, 절차는 클릭과 일반 문자 입력 위주로 정의한다.

중단, 인계, 복구

  • 즉시 중단: 엔지니어는 언제든 Agent를 멈출 수 있어야 한다. 중단 수단(버튼, 단축키)은 ⟨확인⟩이며, 1차 구축 단계의 필수 기능이다.
  • 제어권 인계: Agent는 중단하거나 실패하면 마우스와 키보드에서 손을 떼고, 마지막 화면과 진행 단계를 엔지니어에게 넘긴다. 엔지니어가 수동으로 이어서 하거나 처음부터 다시 한다.
  • 원본 보존: 기존 레시피를 고치는 작업이면 시작 전에 원본을 백업한다. 신규 레시피는 승인 전까지 확정하지 않는다.
  • 오조작 복구: 잘못 저장된 레시피는 담당 엔지니어가 백업으로 되돌리고, 결정 기록에 원인과 함께 남긴다. 원인을 찾을 때까지 그 절차의 자동 실행을 멈춘다.

4주 합류 교육 (합류 시점마다)

개발과 AI에 익숙하지 않은 MI 현업 엔지니어가 AI Agent로 레시피를 자동화할 때 알아야 할 배경 지식을 쌓는 TF 전용 실무 과정. 교육을 끝내고 시작하지 않고, 합류 시점마다 교육하며 TF를 운영한다.

왜 필요한가

담당 엔지니어는 장비와 레시피는 잘 알지만, LLM, VLM이 무엇을 잘하고 무엇을 못하는지는 모른다. 이걸 모르면 두 가지가 생긴다.

  • Agent에게 맡기면 안 되는 판단(정밀 좌표, 반복 가능한 판정)을 맡기는 절차를 쓴다.

목표는 엔지니어가 자기 장비의 레시피 절차를 Agent가 실행할 수 있는 형태로 정의하고, 결과를 판정할 수 있게 되는 것이다. AI 개발자를 만드는 과정이 아니다.

  • Python 기초 문법은 사전 자료로 제공한다. 과정 안에서는 코드를 읽고 간단히 고치는 정도까지만 1주차 실습으로 맞춘다.
  • 겸직 시간(주 5시간: 근무일마다 1시간, 4주 합계 20시간) 안에서 진행한다. 3주차에 다 끝내지 못한 절차 정의는 교육 뒤 TF 업무 시간(주 5시간)에 이어 간다. 강의는 짧게 하고 실습을 길게 한다.
  • 강사는 리드와 공통 플랫폼 팀이 맡는다.
  • 선발대와 2차 장비군 담당 엔지니어가 각자 합류 시점에 듣는다. 2기는 선발대 엔지니어가 실습 조교로 함께한다.

PoC 자산과 남은 과제

PoC(Align Fail 대응 자동화)에서 레시피 자동 생성으로 가져오는 공통 자산, 시사점, 아직 풀지 않은 것.

왜 정리하는가

PoC에서 이미 검증한 것을 공통 플랫폼의 출발점으로 쓴다. 반대로 PoC가 다루지 않은 것은 TF가 새로 풀어야 한다. 이 둘을 섞으면 일정을 낙관적으로 잡게 된다.

PoC가 무엇이었나

계측 Lot을 운영하다 보면 Align Fail(정렬 실패)이 자주 난다. 그러면 장비가 멈추고, 사람이 장비에 접속해 정렬을 다시 맞춰야 한다. PoC는 이 대응을 AI가 대신하게 만들었다. 알람 감지 → 장비 접속 → 정렬 보정 → 실패 시 담당자 알림 → 녹화로 이어지는 루프다. 실장비에서는 위치 재조정까지 자동으로 하고, 최종 확정은 엔지니어가 누르는 반자동으로 열었다.

Align Fail 대응은 레시피에 등록된 Align Key와 실제 Wafer 사이의 차이를 사람이 매번 맞추는 일이다. 레시피를 처음부터 제대로 만드는 것이 ARC의 본래 목표이고, Align Fail 대응은 그 일부를 먼저 떼어 검증한 것이다.

장비군 공통 자산

PoC에서 얻은 것 가운데 특정 장비군에 묶이지 않는 것은 두 가지다.

자산 내용
Agent가 Recipe를 다루는 방식: Computer Use API 없는 장비에서 여러 접근 방식을 시험했다. VLM(화면을 보고 다음 조작 판단), PyAutoGUI(정해진 순서의 키보드, 마우스 입력), Win32(창과 컨트롤 단위 조작)를 조합해 Computer Use를 구현했다
장비 밖에서 Recipe 파일을 편집해 생성 장비 화면 조작이 아닌, 외부에서 Recipe 파일을 편집해 작성한다. 장비 화면을 거치지 않아 조작 단계가 줄고, Recipe 파일 구조 해석(Reverse Engineering)이 전제다. 저장과 적용은 엔지니어가 승인한다

시사점

두 역할의 유기적인 협업이 필요하다. 개발자는 화면 인식, 조작 엔진, 안전 규칙, 모델 서빙을 만든다. 현업 엔지니어는 Recipe 셋업 절차와 성공 판정 기준을 정하고 실장비에서 검증하고 결과를 책임진다. 현업 MI 엔지니어의 업무 노하우와 Recipe 셋업 방식을 AI가 활용할 수 있는 구조로 개발자가 구현해야 한다.

ARC 공통 과제는 공통 플랫폼으로 대응한다.

공통 과제 공통 플랫폼에서
Agent의 마우스, 키보드 조작 조작 엔진을 플랫폼 팀이 한 번 만들고 모든 장비군이 같이 쓴다
Reverse Engineering Recipe 파일 구조 해석 방법과 도구를 공통으로 정리한다
AI 모델 최적화와 운영 유지 모델 서빙과 평가를 플랫폼 팀이 한 번 만든다. 녹화본 평가 세트를 공통으로 두고, 모델 교체는 측정으로 결정한다
녹화 DB 추출 H/W 담당자와 접근 경로를 확정하고, 녹화분 수집을 플랫폼 기능으로 만든다. 작업 내용 추출과 라벨링은 장비군 담당이 맡는다
기술 부채 해소 Vibe Coding으로 원리 확인 없이 진행한 사항이 대부분이다. 플랫폼 팀이 원리를 확인하고 재사용, 고쳐 쓰기, 버림으로 정리한다

같은 일을 장비군마다 반복하면 확장할 수 없다. 그래서 MI 장비 전반의 ARC는 공통 플랫폼을 만들어 개발(플랫폼 팀)과 장비 지식(장비군 담당)을 나눠 진행한다. CD-SEM은 Align Fail PoC를, Thickness는 현업이 만든 PyAutoGUI 자동화와 ARC Pipeline을, Inspection은 의뢰서 DB와 Recipe RAG를 재사용할 수 있어 선발대(1차)로 먼저 플랫폼을 다진다.

자산 상태 공통 플랫폼에서의 쓰임

2단계 좌표 찾기 (대략 위치 → 정밀 좌표) + OCR 확인 검증 완료 장비 화면 클릭, 입력

실패 회복 기록 (알람 1건의 시도, 판정을 한 줄로 기록) 구현 완료 셋업 시도 기록과 지표

레시피 생성을 위해 새로 풀어야 하는 것

과제 왜 PoC에 없었나 맡을 곳
레시피 생성의 전 과정 절차 (생성 → 위치 등록 → 파라미터 → 검증 → 저장) PoC는 기존 레시피의 정렬 보정만 다뤘다 장비군 담당 + 플랫폼
장비군마다 다른 화면과 절차 PoC는 한 장비군 화면만 다뤘다 장비군 담당
신규 Align, 측정 위치 선정 (좋은 위치를 고르고 장비 자체 알고리즘으로 통하는지 확인) PoC는 이미 등록된 Key를 찾기만 했다. 위치 제안은 구현하지 않았다 플랫폼 + 장비군 담당 (실장비 검증)
성공 이미지 수집과 초기 확보 기준 이미지 방식은 레시피별 성공 이미지가 쌓여야 효과가 나는데, 공급 기능이 구현 대기다. 신규 레시피는 성공 이미지가 처음에 없다 플랫폼 (수집 기능) + 장비군 담당 (초기 이미지)

1. 요약 (Executive Summary)

MI 엔지니어가 레시피 셋업의 측정 위치, Align 셋업 구간을 맡길 수 있는 반자동 Agent를 만든다. Agent는 엔지니어 본인 PC에서 돌고, 엔지니어가 보는 원격 화면(RCS, 웹 VDI → RCS/Radmin)을 읽고 같은 화면에 입력한다. 측정 실행과 저장은 엔지니어가 승인한다. 지금 이 구간은 숙련자가 "측정 → 실패 → 재조정"을 손으로 되풀이하는 곳이고, 레시피 셋업 전체에 평균 30~60분이 든다(현업 경험치). 일정은 기획안의 단계를 따른다. 2027년에는 화면 입력 없이 관찰, 절차화, Shadow 제안(S12)까지 만들고, 화면 입력(S1~S5, S8)은 2028 보조 단계에서 연다. 2028 보조 단계 파일럿에서 1차 장비군마다 대표 레시피 유형 1개의 이 구간 건당 소요 시간을 ⟨확인⟩% 줄이고, 오조작으로 잘못 저장된 레시피는 0건을 지킨다. Align Fail 자동 대응의 화면 입력은 기획안의 승인된 예외로 따로 다룬다.

플랫폼 구조(Offline 지식화, Online 실행, 판단과 규칙 확인과 실행의 분리, 안전 관문)는 공통 플랫폼 기술 설계에 있다.

2. 문제 (Problem Statement)

상세는 문제 정의에 있다. 여기서는 요구사항으로 이어지는 부분만 적는다.

누가

계측(MI) 장비의 레시피를 셋업하고 튜닝하는 현업 엔지니어. 선발대(1차)는 CD-SEM, Thickness, Inspection 담당자이고, 2027 하반기부터 다른 MI 장비군 담당자가 합류한다.

무엇이 문제인가

측정 위치와 Align Key를 잡는 동안 측정, 실패, 재조정을 되풀이하고, 그동안 화면 앞을 떠날 수 없다. 그 사이 다른 레시피 요청과 측정 문제의 원인 분석이 밀린다.

왜 아픈가

  • 엔지니어: 중요한 일인데 시간 대부분을 같은 클릭과 재조정에 쓴다. 지치고, 실험할 여력이 남지 않는다.
  • 회사: 노하우가 사람에게만 있어 품질이 사람마다 다르고, 장비가 늘면 셋업 인력도 같은 비율로 늘어야 한다.

7. 요구사항 (User Stories & Requirements)

가설 (Epic Hypothesis)

측정 위치, Align 셋업 구간을 반자동 Agent에 맡기면, 담당 엔지니어의 이 구간 건당 소요 시간이 ⟨확인⟩% 줄 것이다. 지금은 숙련자가 화면에서 시행착오를 손으로 되풀이하는 것 말고는 방법이 없기 때문이다. 파일럿에서 기준선과 같은 양식으로 재서 확인한다.

사용자 스토리

우선순위: 필수(해당 단계 통과에 필요), 권장(파일럿 전까지), 나중(2차 이후).

단계 구분 (2026-11-08 기획안과 맞춤): 2027 관찰과 지식화에서 만드는 것은 S6, S7, S9, S10, S11, S12. 화면에 입력하는 S1~S5, S8과 S13은 2028 보조 단계에서 연다. 2027년에 S1~S5의 설계와 녹화본 모의 실행은 해도 되지만 실장비 입력은 하지 않는다.

S1. 구간을 Agent에 맡기기, 필수 담당 엔지니어로서, 레시피 기본 정보를 입력한 뒤 측정 위치, Align 셋업을 Agent에게 넘기고 싶다. 그래야 시행착오 구간에서 손을 뗄 수 있다. - [ ] 엔지니어가 시작 화면에서 "시작"을 누르면 Agent가 그 화면을 절차의 시작 화면으로 인식한다. 시작 화면이 아니면 시작하지 않고 이유를 보여준다 - [ ] 실행 중에는 현재 단계와 다음 단계가 승인 화면에 보인다 - [ ] 끝나면 끝 화면, 등록된 위치, 소요 시간을 보여주고 제어권을 엔지니어에게 돌려준다

S2. Align Key 등록, 필수 담당 엔지니어로서, Agent가 Align Key를 장비 자체 알고리즘이 통하는 위치로 등록하기를 원한다. - [ ] 이미 성공 이미지가 있는 레시피 유형은 기준 이미지로 Key 후보를 찾는다 - [ ] 후보마다 CV 매칭 점수를 남기고, 점수가 기준 ⟨확인: 담당 엔지니어가 정함⟩ 미만이면 VLM 답으로 덮어쓰지 않고 중단한다 - [ ] 등록 뒤 장비의 Align이 성공했는지 화면으로 확인한다 - 🔵 열린 질문: 성공 이미지가 없는 신규 레시피에서 좋은 Key 위치를 어떻게 고르는가. PoC는 기존 Key 재탐색만 다뤘다. 1차 구축 초기에 장비군 담당과 기준을 정한다

S3. 측정 위치 등록, 필수 담당 엔지니어로서, Agent가 레시피 유형의 측정 위치를 절차대로 등록하기를 원한다. - [ ] 담당 엔지니어가 정한 절차의 단계마다 성공 조건을 검증한다 - [ ] 측정 실행이 필요한 단계는 S4의 승인을 거친다 - [ ] 측정 결과를 담당 엔지니어가 정한 판정 기준(성공/실패, 위치 오프셋)으로 판정하고, 판정 근거 화면을 남긴다

S4. 위험 조작 승인, 필수 담당 엔지니어로서, 측정 실행, 저장, 적용, 삭제, 덮어쓰기, 모드 변경 전에 승인하고 싶다. Agent가 생산 레시피를 혼자 확정하면 안 된다. - [ ] 운영 방식의 조작별 승인 표대로 승인이 필요한 조작은 승인 없이 실행되지 않는다 - [ ] 승인 화면에 무엇을 하려는지, 근거 화면, 되돌릴 수 있는지가 보인다 - [ ] 1차에서는 삭제, 덮어쓰기, 모드 변경을 Agent의 조작 목록에서 뺀다

S5. 즉시 중단과 인계, 필수 담당 엔지니어로서, 언제든 Agent를 멈추고 이어서 직접 하고 싶다. - [ ] 중단 수단(⟨확인: 버튼, 단축키⟩)을 누르면 진행 중인 조작이 끝난 직후 멈추고 마우스, 키보드에서 손을 뗀다 - [ ] 검증 실패, 예상 밖 화면, VDI 잠김, 세션 끊김이면 Agent가 스스로 중단한다 - [ ] 중단하면 마지막 화면, 진행 단계, 이유를 엔지니어에게 넘긴다 - [ ] 되돌릴 수 없는 조작이 실패하면 자동으로 다시 실행하지 않는다

S6. 시도 기록과 지표, 필수 TF 리드로서, 시도마다 무엇을 했고 어디서 실패했는지 남기고 싶다. 그래야 기준선과 비교하고 원인을 찾을 수 있다. - [ ] 시도 1건마다 조작 전후 화면, VLM 응답, 좌표, CV 점수, 판정, 구간 소요 시간, 개입 여부를 기록한다 - [ ] 소요 시간은 기준선 측정 양식과 같은 시작, 끝 화면 기준으로 잰다. 승인 대기 시간은 따로 적는다 - [ ] 기록은 장비 뷰어 창만 담는다. 데스크톱 전체와 키 입력은 기록하지 않는다 (데이터 취급)

S7. 장비군별 절차 정의, 필수 담당 엔지니어로서, 내 장비의 절차를 코드를 크게 고치지 않고 플랫폼에 정의하고 싶다. - [ ] 절차는 단계, 각 단계의 성공 조건, 실패 시 행동, 조작별 승인 분류로 정의한다 - [ ] 정의한 절차를 녹화본에 대고 모의 실행할 수 있다 (합류 교육 3주차 실습) - [ ] 장비군별 절차는 공통 저장소 안의 장비군 폴더로 나누고, 공통 엔진은 고치지 않는다 - 🔶 가정: 선발대 3개 장비군과 2차 장비군의 차이를 절차 정의만으로 담을 수 있다 (2027 하반기 2차 합류로 확인). 담기지 않으면 결정 기록에 남기고 범위를 조정한다 (위험 R4)

S8. VDI 경유 장비군 지원, 필수 (Thickness, VDI를 거치는 2차 장비군 담당) Thickness 같은 VDI 경유 장비군 담당 엔지니어로서, 웹 VDI를 거치는 화면에서도 같은 Agent를 쓰고 싶다. - [ ] VDI 브라우저가 전체 화면(F11), 배율 100%가 아니면 시작하지 않는다 - [ ] 조작마다 화면이 바뀔 때까지 기다린 뒤 검증한다 - [ ] 절차는 클릭과 일반 문자 입력 위주로 만들고, 로컬 OS가 가로채는 단축키는 쓰지 않는다 - [ ] CD-SEM에서 통과한 결과를 근거로 쓰지 않고 장비군마다 따로 검증한다 - 🔵 열린 질문: 엔지니어 PC의 입력 주입이 VDI 경로에서 막히지 않는가. 리드 본인 PC 테스트 대기 (위험 R16)

S9. 작업 녹화 → 절차서, 권장 담당 엔지니어로서, 내가 셋업하는 모습을 녹화해 한국어 절차서로 바꾸고 싶다. 그래야 노하우가 남고 S7의 재료가 된다. - [ ] 녹화는 본인 동의를 받고 녹화 중임을 화면에 표시한다 - [ ] 녹화본에서 조작 타임라인을 뽑고 한국어 절차서 초안을 만든다 - [ ] 계정, 비밀번호 입력 구간은 가린다

S10. 설치형 배포, 필수 담당 엔지니어로서, 개발 도구 없이 내 PC에 설치해 쓰고 싶다. - [ ] 엔지니어 PC에 설치 프로그램 하나로 설치된다. 장비 PC와 VDI 안에는 설치하지 않는다 - [ ] 사내 VLM 엔드포인트에만 연결한다 - 🔵 열린 질문: 보안 승인 범위와 절차 (위험 R6). 2027-03 전 확정

S11. 성공 이미지 수집, 권장 플랫폼 팀으로서, 셋업이 성공할 때마다 Align 성공 이미지를 모으고 싶다. 기준 이미지 방식은 이미지가 쌓여야 효과가 난다. - [ ] 엔지니어가 성공을 승인한 셋업의 Align 화면을 레시피 유형별로 저장한다 - [ ] 담당 엔지니어가 초기 이미지를 직접 넣을 수 있다

S12. 입력 없는 Shadow 제안, 필수 (2027 4분기) 담당 엔지니어로서, Agent가 내 화면을 보고 "다음에 무엇을 할지" 제안만 하는 것을 먼저 보고 싶다. 그래야 화면 입력을 맡기기 전에 판단을 믿을 수 있는지 확인할 수 있다. - [ ] Agent는 화면에 입력하지 않고, 현재 단계, 다음 조작 단위, 근거 시연, 근거 화면을 승인 화면에 보여준다 - [ ] 제안마다 담당 엔지니어가 맞음, 틀림, 모름을 표시하고 기록한다 - [ ] 상태, 분기 정확도와 미승인 행동 제안률을 기술 설계의 평가 방법대로 집계한다. 평가 시연은 지식 자산에서 뺀다

S13. 판단, 규칙 확인, 실행 분리, 필수 (2028 보조) TF 리드로서, LLM이 제안한 조작이 승인된 범위 밖이면 실행되지 않기를 원한다. - [ ] LLM은 분기, 조작 단위, 근거만 제안하고, 서버의 규칙 확인이 권한, 허용 분기, 인자, 값과 단위를 다시 확인한다 - [ ] 규칙 확인이 거부한 제안은 실행으로 넘어가지 않고 기록된다 - [ ] 승인 절차서와 허용 범위는 신뢰 저장소에서만 읽는다. 화면 OCR이나 검색 문서의 글로 바뀌지 않는다 - [ ] 조작 단위는 사전조건, 인자, 사후조건, 재시도 한도를 가진 계약으로 정의한다 (조작 단위 계약)

제약과 예외 상황

  • 장비 API 없음: 모든 조작은 화면으로만 한다.
  • 사내 모델만: 외부 LLM API는 쓰지 않는다. 화면 이해는 사내 VLM, OCR로 한다.
  • 화면 크기: FHD 모니터 기준. 🔵 열린 질문: FHD가 아닌 모니터를 쓰는 엔지니어가 있는가.
  • VDI 워터마크: 🔵 열린 질문: VDI 화면에 워터마크 오버레이가 있는가. 있으면 OCR, CV 매칭 기준을 다시 맞춘다.
  • 모델, 화면 변경: VLM 모델, 플랫폼, 장비 화면, 절차 중 하나라도 바뀌면 이전 검증 결과를 쓰지 않고 재검증한다.
  • 추론 서비스 장애: Agent가 멈추면 장비군 담당은 수동 셋업으로 돌아간다. 장애가 진행 중인 레시피에 흔적을 남기지 않아야 한다.

어떻게 만드는가? (How)

1. Offline: 녹화에서 승인된 절차까지

순서 단계 하는 일 사람의 역할
1 전처리 해상도, FPS, 시각 확인. 원본 프레임 번호 보존. 초당 1~2장으로 훑은 뒤 변화 구간만 원본으로 다시 검사 -
2 변화 감지, 이벤트 라이브 영역과 커서, 시계 변화는 빼고 조작 영역 변화만 이벤트로 묶음 (전후 화면, ROI, OCR) 화면 영역 지도 작성 (담당 엔지니어)
3 의미 행동 기록 VLM이 "관찰한 사실"과 "추정한 행동"을 나눠 적고 모든 판단을 원본 프레임에 연결. 모르는 것은 불확실 항목으로 남김 -
4 의미 단계 묶기 클릭 여러 개를 시작 조건, 완료 조건이 있는 단계 하나로 묶음 경계 검토
5 여러 시연 정렬 같은 작업의 녹화 여러 건을 정렬해 공통 경로와 분기 후보를 찾음 -
6 분기 승인 분기마다 "발견 → 원인 가설 → 승인" 상태를 따로 둠. 승인된 것만 실행에 씀 분기 조건 승인 (담당 엔지니어)
  • 영상 하나나 빈도만으로 분기 조건을 확정하지 않음. 분기 이유는 담당 엔지니어와 승인 절차서로 확인
  • 키 입력을 기록하지 않으므로 정확한 입력 순서, 화면 변화가 없는 실패 입력, 뷰어 창 밖 팝업은 복원할 수 없음. 그 구간은 "미관찰"로 표시하고 추정으로 메우지 않음
  • 자동 추출물은 실행 가능한 매크로가 아니라 검토할 절차 초안임. 이 원칙은 녹화 절차 추출 티켓의 결론(AI 초안 + 엔지니어 검토)과 같음
  • VLM이 내는 confidence 숫자는 보정된 확률이 아니므로 실행 승인 기준으로 쓰지 않음

3. Online: 한 단계씩 확인하며 실행

비슷한 시연 찾기

  1. 호환성 필터: 장비 모델, 화면 버전, 레시피 유형, 승인 범위가 맞지 않으면 제외 (유사도 점수로 보상하지 않음)
  2. 유사도 재순위: 현재 단계, 작업 목표, 화면 구성, 직전 작업 이력. 초기에는 상위 3건
  3. 맞는 시연이 없으면 "검토 요청"이 정상 결과임

판단, 규칙 확인, 실행의 분리

역할 하는 일 하지 않는 일
판단 (LLM) 다음 분기, 조작 단위, 근거를 제안 직접 화면 조작, 사전조건 충족 선언
규칙 확인 (서버) 권한, 허용 분기, 인자, 값과 단위, 절차 버전을 다시 확인. 거부하면 실행으로 넘기지 않음 판단
실행 (조작 단위) 지정된 조작 단위 하나만 실행하고 화면을 다시 관찰 임의 메뉴 탐색, 추가 수정

판단 입력 데이터 계약 (Decision Context)

LLM에 주는 입력을 JSON Schema로 고정합니다. 전체 스키마와 예시는 Codex 설계 슬라이드 12에 있습니다.

필드 내용 확인 책임
task, state 요청, 장비, 레시피 / 현재 단계, 완료 단계 요청과 절차 버전 확인
observation 화면 ID, 프레임 참조, 검증된 사실 VLM 주장만으로 채우지 않고 OCR, UI 상태 검사 결과를 연결
retrieved_demonstrations 호환되는 시연 최대 3건 메타데이터 필터 강제
approved_policy 승인 절차서, 허용 방식, 덮어쓰기 금지, 적용 금지 신뢰 저장소에서만 읽음. 화면 OCR이나 검색 문서의 글이 덮어쓸 수 없음
allowed_branches 승인 조건을 통과한 분기 목록 서버가 계산하고 다시 확인
  • 스키마 통과는 구조 검증일 뿐 승인 절차서 승인을 뜻하지 않음
  • 화면 안의 글자는 데이터로만 취급함 (지시로 해석하지 않음)

실행 루프

관찰 → 상태 인식 → 시연 검색, 판단 → 규칙 확인 → 조작 단위 1개 실행 → 사후조건 검증, 체크포인트 저장
  모름, 불일치, 시간 초과 → 중단하고 엔지니어 검토
  • 완료 저장은 사후조건을 확인한 뒤에만 함
  • 체크포인트는 소프트웨어 실행 위치만 복원함. 원격 화면이나 장비를 되돌리지 않음
  • 통신이 끊겨 실행 여부가 불명확하면 재시도하지 않고 실제 결과부터 조회함

4. 조작 단위 계약

항목 내용

설치형과 웹앱의 경계

순수 웹앱으로는 안 됩니다. 브라우저도 사용자가 고르고 동의하면 창을 캡처할 수 있지만(getDisplayMedia), 상시 관찰에 매번 동의를 받을 수 없고 OS 입력은 넣을 수 없습니다. 그래서 엔지니어 PC에는 캡처, 입력, 중단만 하는 얇은 에이전트를 두고, 나머지는 기존 서버의 웹앱에 둡니다.

백그라운드의 범위: 관찰과 판단만

SendInput은 실제 마우스와 키보드 입력 흐름을 엔지니어와 공유합니다. Agent가 입력하는 동안 엔지니어는 PC를 쓸 수 없습니다. 그래서 입력은 제어권 인계로 합니다.

알림 → 엔지니어가 넘겨줌 → 대상 창 활성화 확인 → 짧은 입력 → 결과 확인 → 제어권 반환
  엔지니어 마우스, 키보드 조작 / 포커스 이탈 / VDI 잠김 → 즉시 중단
  • 창 메시지(PostMessage) 입력은 RCS, Radmin, SecureVDI가 원격까지 전달하는지 확인되지 않았음. 기능으로 약속하지 않음
  • Windows는 자동 foreground 전환을 막을 수 있음. 엔지니어가 넘겨주는 동작을 기본으로 함
  • 가상 데스크톱, 별도 세션은 입력 장치가 분리되지 않아 해결책이 아님. 로컬 VM은 입력을 분리하지만 보안 승인, 자원 부담이 커서 제외. 같은 PC에서 동시 업무가 꼭 필요해지면 다시 검토

규칙 확인은 서버와 PC 두 곳에서

  • 서버: 권한, 승인 범위, 절차 버전 판정
  • PC: 입력 직전에 대상 창, 화면이 최신인지, 세션 잠김, 승인 유효기간, 중단 상태를 다시 검사. PC 검사는 거부만 더할 수 있고 서버 승인보다 넓어질 수 없음
  • 네트워크가 끊기면 새 입력을 멈추고 자동으로 재개하지 않음. 이미 보낸 클릭은 취소할 수 없으므로 결과가 불명확한 조작은 다시 보내지 않고 화면부터 다시 확인함

Align Fail 자동 대응 PoC의 공통 자산과 시사점을 바탕으로 공통 플랫폼을 만들어, 숙련 엔지니어의 레시피 셋업 노하우를 회사 자산으로 남기고 장비가 늘어도 셋업 인력을 같은 비율로 늘리지 않는 구조를 만들고자 합니다.

출발점: PoC의 성과와 시사점

  • PoC로 Agent가 Recipe를 다루는 장비군 공통 방식 확보: VLM, PyAutoGUI, Win32를 조합한 Computer Use, 장비 밖에서 Recipe 파일을 편집하는 생성
  • 개발자와 현업 엔지니어 두 역할의 유기적인 협업 필요: 현업 MI 엔지니어의 노하우와 Recipe 셋업 방식을 AI가 활용할 수 있는 구조로 개발자가 구현
  • Agent의 마우스, 키보드 조작, Reverse Engineering, AI 모델 최적화와 운영, 녹화 DB 추출, 기술 부채 해소는 장비군 공통 과제라 공통 플랫폼으로 대응
  • LLM 모델만으로는 안 됨: 정밀 좌표가 흔들리고, 장비 절차를 모르고, 성공/실패 여부를 스스로 확인하지 못하며, 진행 상태를 기억하지 못하고, 화면을 직접 조작하지 못함. 모델은 판단 한 부분이고 정밀 좌표(CV), 승인된 절차, 규칙 확인과 결과 검증, 입력 실행은 플랫폼이 채워야 함
  • 처음에는 Agent 전용 PC를 따로 두려 했으나, 사무 PC를 계속 늘리는 방식은 PC 추가 확보 절차, 장비 접속 권한, 별도 관리 부담, 아무도 보지 않는 화면 같은 제약이 많음. 그래서 공통 플랫폼을 개발해 엔지니어 본인 PC에 설치하는 방향으로 바꿈
  • 결론: MI 장비 전반으로 넓히려면 공통 플랫폼을 만들어 개발(플랫폼 팀)과 장비 지식(장비군 담당)을 나눠야 함

문제

  • MI 장비 레시피 셋업은 숙련 엔지니어가 원격 화면에서 손으로 반복하는 작업임. 레시피당 30~60분 소요
  • 판단 기준이 사람에게만 있어 담당자가 바뀌면 노하우가 사라짐
  • 장비, 제품이 늘면 셋업 인력도 같은 비율로 늘어야 함. Align Fail 알람이 나면 엔지니어가 하던 일을 멈추고 대응해야 장비가 다시 돎

해결 방향

  • 엔지니어 작업 녹화에서 절차와 판단 근거를 추출하고 담당 엔지니어가 승인해, 다른 엔지니어가 찾아 쓰는 지식 자산으로 축적함
  • AI는 현재 화면에 맞는 승인 절차를 찾아 한 단계씩 수행하고, 결과가 불명확하면 멈춤. 위험 조작과 저장, 적용은 엔지니어가 승인함
  • 초기 개발은 CD-SEM, Thickness, Inspection 위주(Align Fail PoC, 기존 PyAutoGUI 자동화와 ARC Pipeline, 의뢰서 DB와 Recipe RAG를 재사용)로 공통 플랫폼을 베타까지 만듦. 같은 기간 다른 MI 장비군은 인터뷰, Recipe Workflow 조사로 준비해 설계에 반영하고, 베타 뒤 본격 참여
  • 개발과 AI에 익숙하지 않은 엔지니어는 합류 시점마다 교육하며 TF를 운영함
