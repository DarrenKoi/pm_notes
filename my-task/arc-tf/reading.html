ARC TF: 레시피 자동 생성 태스크포스

장비 레시피(Recipe) 셋업을 컴퓨터 사용(Computer-use) Agent로 자동화하려고, MI 현업 엔지니어와 공통 플랫폼 팀을 묶어 운영하는 TF의 작업공간. 본인이 리드한다.

한 문단 요약

레시피 셋업은 숙련 엔지니어가 원격 제어 화면에서 손으로 하는 반복 작업이고, 장비가 늘면 사람도 그만큼 늘어야 한다. 1차 PoC(Align Fail 대응 자동화)에서 사내 VLM으로 API 없는 장비 화면을 보고 조작할 수 있다는 것, VLM과 CV를 나눠 쓰면 오프라인 평가에서 정밀 좌표도 잡힌다는 것을 확인했다. 남은 문제는 두 가지다. 하나는 현장 신뢰성과 실행 엔진 제품화이고, 다른 하나는 장비군마다 다른 레시피 절차다. 뒤의 것은 현업 지식 없이는 풀 수 없다. 그래서 공통 플랫폼 팀이 엔진을 만들고, 장비군 담당(MI 엔지니어)이 절차와 판정 기준을 맡는 TF를 꾸린다. 2026-11에 기획안을 쓰고, 12월에 임원 승인을 받고, 2027-01에 가동한다.

ARC TF 문제 정의 (Problem Statement)

MI 엔지니어는 레시피(Recipe) 셋업과 튜닝을 원격 화면에서 손으로 되풀이하느라, 더 많은 레시피를 다루고 문제를 빨리 찾고 실험할 시간을 잃고 있다.

왜 이 문서가 필요한가

TF 구성 기획안은 "TF를 만들자"는 해결책을 제안한다. 해결책을 말하기 전에 누가, 무엇을 하려다, 왜 막히는지를 한 장으로 맞춰 두려고 이 문서를 쓴다. 임원, 담당 엔지니어, 플랫폼 팀이 같은 문제를 보고 있어야 TF의 범위와 지표를 두고 다투지 않는다.

이 문서에는 해결책을 넣지 않는다. 해결 방향은 맨 끝에 한 절로만 적고, 상세는 기획안으로 넘긴다.

문제 서술 (Problem Framing Narrative)

나는: 계측(MI) 장비의 레시피를 셋업하고 튜닝하는 현업 엔지니어다. - CD-SEM, VeritySEM, Thickness 같은 장비를 원격 제어 화면(RCS, 웹 VDI → RCS/Radmin Viewer)으로 다룬다. - 신규 제품, 공정이 들어오거나 측정이 흔들릴 때마다 레시피를 만들거나 다시 맞춘다. 레시피 한 건에 평균 30~60분이 든다 (현업 경험치, 셋업 전체 기준). - 어디를 측정 위치로, 어디를 Align Key로 잡아야 통하는지는 경험으로 안다. 그 경험은 문서가 아니라 내 머릿속에 있다.

하려는 것: - 레시피를 짧은 시간에 정확하게 만들고, 측정 문제가 생기면 원인을 빨리 찾아 고치고, 남는 시간에 더 많은 실험과 테스트를 하고 싶다.

그런데: - 측정 위치, Align 셋업 구간에서 "측정 → 실패 → 위치 재조정"을 되풀이한다. 시행착오가 가장 많은 구간이고, 그동안 화면 앞을 떠날 수 없다. - 레시피 한 건에 붙어 있는 동안 다른 레시피 요청은 쌓이고, 측정 문제의 원인 분석은 뒤로 밀린다. - 같은 레시피라도 누가 셋업하느냐에 따라 품질이 다르고, 담당자가 바뀌면 노하우가 함께 사라진다. - 반복 작업이 길어서 지친다. 새로운 조건을 시험해 볼 여력이 남지 않는다.

왜냐하면: - 레시피 셋업의 핵심 판단(이 위치가 좋은가, 이 측정이 성공인가)이 숙련자의 눈과 손에만 있다. 그 판단을 대신하거나 기록해 둘 수단이 없다. - 장비는 외부에서 조작할 API가 없다. 사람이 보는 원격 화면이 유일한 접점이라, 일반적인 스크립트 자동화가 통하지 않는다. - 장비별 절차를 아는 사람(현업 엔지니어)과 화면 자동화를 만들 수 있는 사람(개발)이 나뉘어 있다. 한쪽만으로는 자동화가 완성되지 않는다.

그래서 나는: - 중요한 일인데 대부분의 시간을 같은 클릭과 재조정에 쓰고 있어 답답하고 지친다. - 쌓여 가는 요청 앞에서 "실험은 나중에"를 반복하게 된다. - ⟨확인: VeritySEM, Thickness 담당 엔지니어도 같은 감정을 말하는지, 온보딩 첫 주 인터뷰⟩

위 감정은 CD-SEM을 직접 맡는 리드의 경험에서 나왔다. 다른 장비군 엔지니어의 말로 확인되기 전에는 공통 문제로 일반화하지 않는다.

맥락과 제약 (Context & Constraints)

  • 조작 경로: 장비마다 다르다. CD-SEM은 엔지니어 PC → RCS로 바로 접속하고, VeritySEM, Thickness는 웹 VDI의 가상 Windows 안에서 RCS나 Radmin Viewer로 접속한다. 모니터는 대부분 FHD다.
  • 장비 PC 변경 불가: 장비 PC에는 아무것도 설치하지 않는다. 무엇을 하든 엔지니어 본인 PC에서 해야 한다.
  • 사내 모델만 사용: 외부 LLM API는 막혀 있다. 화면 이해는 사내 VLM, OCR로 해야 한다.
  • 생산 장비 안전: 잘못 저장된 레시피는 생산 측정에 바로 영향을 준다. 저장, 적용과 위험 조작(측정 실행, 삭제, 모드 변경)은 엔지니어가 최종 승인해야 한다.
  • 검증 시간: 실장비 검증은 장비 사용 인가를 받은 하루 1시간뿐이다.
  • 현업 시간: 담당 엔지니어는 겸직이다. 주 5시간(근무일마다 1시간)을 넘겨 기대할 수 없다.
  • 기밀: 장비 수치, 실명, 팀명은 사내용 문서에만 둔다.

최종 문제 정의 (Final Problem Statement)

MI 엔지니어는 신규, 변경 레시피의 측정 위치, Align 셋업을 시행착오 없이 짧은 시간에 끝낼 방법이 필요하다. 지금은 API 없는 장비 화면에서 숙련자가 눈과 손으로 측정, 실패, 재조정을 되풀이하는 수밖에 없어서 레시피당 30~60분이 들고, 그만큼 다른 레시피와 문제 원인 분석, 실험이 밀린다.

해결했는지는 이것으로 판단한다.

검증 방법

  • 담당 엔지니어에게 읽어 주기: 온보딩 첫 주에 VeritySEM, Thickness 담당 엔지니어에게 "최종 문제 정의"를 읽어 주고, "맞다"는 반응이 나오는지 본다. 다르면 "그런데"와 "왜냐하면"을 고친다.
  • 기준선 측정: 온보딩 8주차 실측 값으로 "30~60분"을 자동화 대상 구간 기준으로 바꾼다.
  • 임원 보고 전 점검: 이 문서의 한 문장만 들어도 "그건 풀 가치가 있다"고 고개를 끄덕일 수 있는지 본다. 끄덕이지 않으면 ⟨확인: 장비군별 월 셋업 수요⟩를 먼저 채운다.

해결 방향 (이 문서 범위 밖)

근본 원인의 세 번째 줄(절차를 아는 사람과 자동화를 만드는 사람이 나뉘어 있다)이 TF 구조의 이유다.

  • 현업 엔지니어(장비군 담당): 장비별 레시피 절차와 성공 판정 기준을 정의하고 현장에서 검증한다. 자동화의 "무엇을"을 맡는다.
  • 리드와 공통 플랫폼 팀: 화면 인식, 조작 엔진, 안전 규칙, 승인 화면을 만든다. 자동화가 가능하게 하는 "어떻게"를 맡는다.

요청 사항 (2026-12)

  • ARC TF 구성 승인: 공통 플랫폼 팀(개발 2명)과 장비군 담당 엔지니어로 2027-01부터 운영
  • 1차 지정군: CD-SEM, Thickness, VeritySEM 담당 엔지니어의 TF 조직도 협업 요청 (장비군마다 1~2명, 주 5시간)
  • 지정 사유: 이미 ARC 작업이 진척 중이며 엔지니어들도 기본적인 데이터 흐름과 작업 방식을 알고 있음
  • 공통 플랫폼의 기초 틀이 될 수 있도록 작업
  • 2차 지정군 (선택): Inspection 장비군
  • 1차 지정군 장비로 얻은 작업 노하우를 2차 장비군에 적용
  • 공통 플랫폼 개발을 실제로 적용하는 첫 대상
  • 개발 인력 2명: 1인당 업무 시간 50% 투입 (실질 1명)

확인 필요 사항 (R&D MI H/W 담당자)

  • 장비 화면 녹화분 DB에 직접 접근할 수 있는지 확인 필요
  • 가능하면: 녹화분을 바로 받아 써서 개발 속도가 빨라짐
  • 불가능하면: RCS에서 GUI 자동화로 녹화분을 내려받아야 함 (속도가 느리고, 다운로드 받는 자동화 작업 별도 필요)
  • 스크린샷과 녹화 영상을 매우 많이 쓰므로 스토리지 소모량이 매우 큼. 추후 스토리지 자산 확보가 필요함

1. 배경과 문제

문제

  • 레시피 셋업은 숙련 엔지니어가 원격 제어 화면에서 마우스와 키보드로 하는 반복 수작업임. 측정 위치를 잡을 때 측정, 실패, 재조정을 되풀이함
  • 노하우가 개인에게 있음. 담당자가 바뀌면 지식이 사라지고 사람마다 품질이 다름
  • 관리 장비가 늘어나거나 개발 제품이 증가하면 셋업 인력도 같은 비율로 늘어나야 하나, 이 구조로는 한계가 있음
  • 측정 중 Align Fail(정렬 실패) 알람이 나면 엔지니어가 원격으로 위치를 다시 잡을 때까지 장비가 멈춤

안 하면 생기는 일

  • ⟨확인: 신규 제품, 공정 도입 때 레시피 셋업 대기로 늦어지는 기간⟩
  • ⟨확인: 장비군별 레시피 셋업에 쓰는 엔지니어 시간 (월 기준)⟩
  • ⟨확인: Align Fail 알람으로 멈추는 장비 시간 (월 기준)⟩
  • 장비군마다 따로 자동화를 시도하면 화면 인식, 조작, 안전 장치를 매번 새로 만들게 됨

셋업 시간의 현재 값은 현업 경험치입니다. 자동화 대상 구간의 실측값과 나머지 현재 값은 TF 온보딩 기간(2027-01~02)에 담당 엔지니어가 직접 측정해 확정하겠습니다. 측정하기 전에는 목표를 숫자로 정하지 않습니다.

시간 구분: 효과를 계산할 때 세 가지 시간을 나눠 셉니다.

  • 작업 경과 시간: 셋업 시작부터 끝까지 걸린 시간
  • 엔지니어 직접 투입 시간: 엔지니어가 실제로 조작, 판단, 승인에 쓴 시간. 회사 효과 계산에는 이 값을 씀
  • 장비 정지 시간: Align Fail 등으로 장비가 멈췄다가 다시 측정하기까지의 시간. 회수한 장비 가동 시간은 이 정지 시간의 감소분으로 셈

측정 규칙 (기준선과 이후 측정을 같은 조건으로 비교하기 위해 온보딩 측정 양식에 고정)

  • 대상: 장비군마다 정한 대표 레시피 유형 1개. 전체 셋업이 아닌 자동화 대상 구간(측정 위치, Align 셋업) 의 시작과 끝을 정해 측정
  • 포함: 그 구간 안의 실패, 재작업, 수동 인계 시간. 승인 대기 시간은 별도 기록
  • 개입 횟수: 반드시 거치는 승인(저장 전 등)은 제외하고 예정에 없던 개입만 집계

엔지니어 시간이 줄면 회사에 무엇이 남는가

레시피 셋업 수요(건/월) × 건당 엔지니어 직접 투입 시간 감소분
  → 회수되는 엔지니어 시간 (월 ⟨확인⟩시간)
  → 신규 제품, 공정 도입 때 셋업 대기 단축, 엔지니어가 분석, 개선 업무로 이동
  → 장비가 늘어도 셋업 인력을 같은 비율로 늘리지 않아도 됨
  • 가정: ⟨확인: 장비군별 월 셋업 수요와 증가 추세⟩. 셋업 수요가 장비, 제품 수와 함께 늘어야 "인력이 비례해야 한다"는 주장이 성립함

3. 이미 확보한 것

1차 PoC (Align Fail 대응 자동화)

ARC는 처음부터 레시피 자동 생성을 목표로 했습니다. 1차 PoC로는 범위가 좁고 효과를 재기 쉬운 Align Fail 무인 대응을 선택했고 이 PoC에서 레시피 자동 생성에 그대로 쓸 기반을 검증했습니다.

확보한 것 레시피 자동 생성에서의 쓰임
사내 인프라에서 화면 이해 모델(VLM, OCR) 자체 운영 외부 API 없이 화면 이해
표준 컴포넌트가 아닌 계측 화면에서도 대략 위치 → 정밀 좌표 → OCR 확인 순서로 클릭 API 없는 장비 화면 조작
VLM은 "어디를 볼지", CV는 "정확히 어디인지"를 맡는 역할 분리 원칙 측정 위치, Align Key 등록의 정확도
최근 성공 사례를 모은 기준 이미지로 Align Key 탐색 정확도 개선 (오프라인 평가 기준) 레시피 Align 셋업
실장비 반자동 운영: 위치 재조정은 자동, 최종 확정은 엔지니어 TF의 안전 원칙
엔지니어 작업 녹화 → 조작 타임라인 → 한국어 절차서 장비별 레시피 절차 정의
SecureVDI 경유 화면에 키보드, 마우스 입력 가능 확인 (2026-11) VeritySEM, Thickness도 같은 방식으로 조작

상세 목록은 PoC 자산과 남은 과제에 있으며 수치는 사내용 문서에만 둡니다.

현업이 이미 만든 자동화 (Thickness)

  • Thickness 담당자들이 PyAutoGUI 기반으로 자동화해 둔 작업이 많음. 고정 좌표와 정해진 순서로 반복 입력을 처리하는 방식임
  • 검토 과제: 이 PyAutoGUI 자동화와 VLM 기반 방식을 어떻게 섞어 쓸지 정해야 함
  • 정해진 순서의 반복 입력: 검증된 PyAutoGUI 스크립트를 그대로 재사용
  • 화면 인식과 판단이 필요한 구간 (위치 확인, 예외 화면, 막힘): VLM이 맡음
  • PyAutoGUI 스크립트 앞뒤에 VLM 화면 확인을 붙여, 화면이 예상과 다르면 멈추게 함
  • 2027-01~02 온보딩 때 Thickness 기존 스크립트를 목록화하고, 2027-06 요소 목록에 혼합 방식을 반영함

PoC로 확인한 것: API 없는 장비 화면을 보고 조작 가능, 오프라인 평가에서 Align Key 탐색 가능, SecureVDI 경유 입력 가능

항목 확인 시점

PyAutoGUI 기존 자동화와 VLM 방식을 섞었을 때 안정적으로 동작하는가 2027 상반기 Thickness Align Fail 운영
Agent가 엔지니어가 한 작업의 의미를 파악하고 그대로 따라 진행할 수 있는가 2027 하반기 절차화, 2028 보조 단계
새로운 측정 파라미터를 추가할 때, 의뢰서를 근거로 위치를 찾고 몇 차례 조정을 거쳐 이미지를 제대로 등록할 수 있는가 2028 보조 단계, 2029 자율 단계

모두 장비 화면과 레시피 절차를 아는 현업 엔지니어들과 함께 검증해야 합니다. 그래서 TF가 필요합니다.

자동화 수준과 안전 원칙

  • 반자동(Supervised Autonomy)이 원칙임: Agent가 조작하고, 위험 조작(측정 실행, 삭제, 모드 변경)과 레시피 저장, 적용 직전에는 엔지니어가 승인
  • Align Fail 무인 대응은 승인된 예외임: 허용 조작은 레시피를 바꾸지 않는 위치 재조정과 해당 지점 재측정 재시도뿐임. 저장, 삭제, 모드 변경, 레시피 수정은 계속 금지. 인식이 불확실하거나 화면이 예상과 다르면 Agent가 스스로 멈추고 엔지니어를 부름
  • 무인 전환 승인: 반자동 운영 실적을 리드가 정리하고, 담당 엔지니어 확인을 거쳐 월간 보고에서 장비별로 승인받음
  • 레시피 셋업의 완전 자동은 반복 검증과 자체 중단 기록까지 통과한 레시피 유형만 단계 승인을 거쳐 검토함

참여 팀과 역할

누가 TF에 들어오고, 무엇을 책임지는가. 공통 플랫폼 팀과 장비군 담당으로 나눈다.

왜 나누는가

장비군마다 자동화를 따로 만들면 화면 인식, 조작, 안전 장치를 장비 수만큼 다시 만든다. 반대로 플랫폼 팀이 모든 장비의 레시피 절차까지 알 수는 없다. 그래서 엔진은 한 곳(플랫폼)에서, 절차와 판정 기준은 장비를 아는 사람(장비군 담당)이 맡는다.

실무 회의 진행 순서

  1. 지난 회의 할 일 확인 (5분)
  2. 장비군별 진행: 한 장비군에 5분, 형식은 "한 것 / 막힌 것 / 다음 할 일"
  3. 결정 필요 사항: 그 자리에서 정하고 결정 기록에 남긴다. 못 정하면 담당과 기한을 정한다
  4. 위험 목록에서 바뀐 것 확인
  5. 다음 주 할 일과 담당 확정

회의록은 짧게, 결정과 할 일만 남긴다.

의사결정

  • 범위와 우선순위는 리드가 정한다. 장비 절차와 판정 기준은 담당 엔지니어가 정한다.
  • 결정은 결정 기록에 날짜, 결정, 이유와 함께 남긴다. 뒤집을 때도 남긴다.
  • 장비군 담당 사이에 의견이 갈리면 실무 회의에서 리드가 정한다. 예산이나 인력이 걸린 것은 월간 보고에서 임원에게 올린다.
  • 단계 통과는 리드가 정리하고 월간 보고에서 임원이 승인한다. 미달이면 보완, 축소, 중단 중 하나를 정한다 (기획안 5절).

작업 관리

  • 할 일은 ⟨확인: 이슈 트래커 / 사내 도구⟩에 장비군 단위 라벨로 관리한다.
  • 코드는 공통 플랫폼 저장소 하나에 둔다. 장비별 절차는 같은 저장소 안의 장비군 폴더로 나눈다.
  • 장비 데이터, 화면 캡처, 사내 수치는 사내 환경에만 둔다. 이 문서 폴더에는 일반화된 계획만 남긴다.

안전 원칙 (모든 장비군 공통)

PoC에서 정한 규칙을 그대로 가져온다.

  • 검증에 실패하면 기본은 중단이다. 무한 재시도는 없다. 마지막 대안은 사람에게 넘기는 것이다.
  • 되돌릴 수 없는 조작은 실행 전과 후 모두 검증한다. 실패하면 자동으로 다시 실행하지 않는다.
  • 모든 조작은 증거를 남긴다: 조작 전후 화면, VLM 응답, 좌표.
  • 낮은 CV 점수를 VLM 답변으로 덮어쓰지 않는다.
  • 엔지니어 작업 녹화는 화면만 본다. 입력을 가로채지 않는다.
  • 실장비 검증은 처음에는 엔지니어가 지켜보는 상태에서만 한다.
  • 실장비 검증은 장비 사용 인가를 받은 시간(하루 1시간)에만 한다. 이 시간을 이 문서들에서 "비생산 검증 시간"이라 부른다.
  • Agent는 엔지니어 본인 PC에 설치한 프로그램으로 돈다. 장비 PC에는 설치하지 않는다.

VDI 경유 장비군 화면 규칙 (VeritySEM, Thickness)

Agent는 엔지니어 PC에서 웹 VDI 화면을 통해 RCS/Radmin을 조작한다. VDI 안에는 설치하지 않는다.

  • VDI 브라우저는 전체 화면(F11), 배율 100% 로 고정한다. FHD 모니터에서 화면 위치와 크기가 늘 같아야 좌표가 흔들리지 않는다.
  • 실행 중에는 VDI 브라우저 창이 맨 앞에 있어야 한다. VDI 화면이 아니면(다른 창, 잠김, 세션 끊김) 바로 중단하고 엔지니어에게 넘긴다.
  • 키 입력은 브라우저를 거친다. Alt+Tab, Win 키처럼 로컬 OS가 먼저 처리하는 키는 VDI까지 가지 않으므로, 절차는 클릭과 일반 문자 입력 위주로 정의한다.

중단, 인계, 복구

  • 즉시 중단: 엔지니어는 언제든 Agent를 멈출 수 있어야 한다. 중단 수단(버튼, 단축키)은 ⟨확인⟩이며, 1차 구축 단계의 필수 기능이다.
  • 제어권 인계: Agent는 중단하거나 실패하면 마우스와 키보드에서 손을 떼고, 마지막 화면과 진행 단계를 엔지니어에게 넘긴다. 엔지니어가 수동으로 이어서 하거나 처음부터 다시 한다.
  • 원본 보존: 기존 레시피를 고치는 작업이면 시작 전에 원본을 백업한다. 신규 레시피는 승인 전까지 확정하지 않는다.
  • 오조작 복구: 잘못 저장된 레시피는 담당 엔지니어가 백업으로 되돌리고, 결정 기록에 원인과 함께 남긴다. 원인을 찾을 때까지 그 절차의 자동 실행을 멈춘다.

MI 현업 엔지니어가 AI Agent로 레시피를 자동화할 때 알아야 할 배경 지식을 쌓는 TF 전용 실무 과정.

왜 필요한가

담당 엔지니어는 장비와 레시피는 잘 알지만, LLM, VLM이 무엇을 잘하고 무엇을 못하는지는 모른다. 이걸 모르면 두 가지가 생긴다.

  • Agent에게 맡기면 안 되는 판단(정밀 좌표, 반복 가능한 판정)을 맡기는 절차를 쓴다.
  • Agent가 실패했을 때 원인이 모델인지, 화면 품질인지, 절차 정의인지 구분하지 못한다.

목표는 엔지니어가 자기 장비의 레시피 절차를 Agent가 실행할 수 있는 형태로 정의하고, 결과를 판정할 수 있게 되는 것이다. AI 개발자를 만드는 과정이 아니다.

전제

  • Python 기초는 다루지 않는다. 코드를 읽고 간단히 고칠 수 있는 정도의 소양은 갖고 온다.
  • 겸직 시간(주 5시간: 근무일마다 1시간, 8주 합계 40시간) 안에서 진행한다. 강의는 짧게 하고 실습을 길게 한다.
  • 강사는 리드와 공통 플랫폼 팀이 맡는다.
  • 1차, 2차 담당 엔지니어가 모두 듣는다.

PoC 자산과 남은 과제

1차 PoC(Align Fail 대응 자동화)에서 레시피 자동 생성으로 가져오는 것과, 아직 풀지 않은 것.

왜 정리하는가

TF는 0에서 시작하지 않는다. PoC에서 이미 검증한 것을 공통 플랫폼의 출발점으로 쓴다. 반대로 PoC가 다루지 않은 것은 TF가 새로 풀어야 한다. 이 둘을 섞으면 일정을 낙관적으로 잡게 된다.

PoC가 무엇이었나

계측 Lot을 운영하다 보면 Align Fail(정렬 실패)이 자주 난다. 그러면 장비가 멈추고, 사람이 장비에 접속해 정렬을 다시 맞춰야 한다. PoC는 이 대응을 AI가 대신하게 만들었다. 알람 감지 → 장비 접속 → 정렬 보정 → 실패 시 담당자 알림 → 녹화로 이어지는 루프다. 실장비에서는 위치 재조정까지 자동으로 하고, 최종 확정은 엔지니어가 누르는 반자동으로 열었다.

Align Fail 대응은 레시피에 등록된 Align Key와 실제 Wafer 사이의 차이를 사람이 매번 맞추는 일이다. 레시피를 처음부터 제대로 만드는 것이 ARC의 본래 목표이고, Align Fail 대응은 그 일부를 먼저 떼어 검증한 것이다.

레시피 생성을 위해 새로 풀어야 하는 것

과제 왜 PoC에 없었나 맡을 곳
레시피 생성의 전 과정 절차 (생성 → 위치 등록 → 파라미터 → 검증 → 저장) PoC는 기존 레시피의 정렬 보정만 다뤘다 장비군 담당 + 플랫폼
장비군마다 다른 화면과 절차 PoC는 한 장비군 화면만 다뤘다 장비군 담당
신규 Align, 측정 위치 선정 (좋은 위치를 고르고 장비 자체 알고리즘으로 통하는지 확인) PoC는 이미 등록된 Key를 찾기만 했다. 위치 제안은 구현하지 않았다 플랫폼 + 장비군 담당 (실장비 검증)
성공 이미지 수집과 초기 확보 기준 이미지 방식은 레시피별 성공 이미지가 쌓여야 효과가 나는데, 공급 기능이 구현 대기다. 신규 레시피는 성공 이미지가 처음에 없다 플랫폼 (수집 기능) + 장비군 담당 (초기 이미지)
실행 엔진 제품화 PoC의 절차 실행 엔진은 데모 단계다 플랫폼
측정 결과 판정 (성공/실패, 위치 오프셋) Align 성공 여부만 판정했다 담당 엔지니어가 기준, 플랫폼이 구현
엔지니어와 대화하며 진행하는 승인 화면 PoC는 알림과 확정 버튼만 있었다 플랫폼
VDI 경유 조작 (웹 VDI → 가상 Windows → RCS/Radmin) PoC는 로컬 RCS 경로만 다뤘다. 두 번 원격을 거쳐 화질 저하, 지연, 브라우저의 단축키 가로채기, VDI 잠김, 세션 끊김이 생길 수 있다 플랫폼 + VeritySEM, Thickness 담당
배포 (개발 도구 없는 PC에서 실행) 설치형 프로그램으로 엔지니어 본인 PC에 배포하기로 결정 (2026-11-02). 패키징은 남음 플랫폼 + 인프라
등록 위치가 헷갈리기 쉬운 레시피의 재등록 알고리즘으로 안 풀리는 몫이 크다고 확인됨 장비군 담당

PoC의 남은 일 (TF 시작 전 정리)

TF 가동 전에 끝내거나, 끝내지 못하면 TF 1차 구축 단계로 넘긴다.

  • ⟨확인: 실알람 첫 완주⟩
  • ⟨확인: Align Key 탐색의 현장 실데이터 검증⟩
  • ⟨확인: 녹화 → 절차서 추출의 현장 실행⟩
  • 설치형 프로그램 패키징 (배포 방식은 엔지니어 본인 PC 설치로 결정)
  • 입력 주입 테스트: 리드 본인 PC에서 로컬 RCS 경로와 VDI 경로(본인 계정) 각각 "캡처 → 클릭, 입력 → 화면 변화 확인" 한 바퀴. 다른 사람 화면이 끼지 않게 본인 PC에서만 하고, 녹화, 로그는 저장하지 않으며, 승인이 필요 없는 조작(창 전환, 탭 클릭)만 쓴다. 측정 실행과 저장은 하지 않는다. 화면 캡처는 두 경로 모두 막히지 않음을 확인했다 (2026-11-02)
  • ⟨확인: VDI 화면의 워터마크 오버레이 여부 (OCR, CV 매칭에 영향)⟩

PoC의 수치(대상 장비 수, 주간 발생 건수, 대응 시간, 정확도)는 사내용 문서에만 적는다.

1. 요약 (Executive Summary)

MI 엔지니어가 레시피 셋업의 측정 위치, Align 셋업 구간을 맡길 수 있는 반자동 Agent를 만든다. Agent는 엔지니어 본인 PC에서 돌고, 엔지니어가 보는 원격 화면(RCS, 웹 VDI → RCS/Radmin)을 읽고 같은 화면에 입력한다. 측정 실행과 저장은 엔지니어가 승인한다. 지금 이 구간은 숙련자가 "측정 → 실패 → 재조정"을 손으로 되풀이하는 곳이고, 레시피 셋업 전체에 평균 30~60분이 든다(현업 경험치). 2027년 말까지 1차 장비군마다 대표 레시피 유형 1개에서 이 구간의 건당 소요 시간을 ⟨확인⟩% 줄이고, 오조작으로 잘못 저장된 레시피는 0건을 지킨다.

2. 문제 (Problem Statement)

상세는 문제 정의에 있다. 여기서는 요구사항으로 이어지는 부분만 적는다.

누가

계측(MI) 장비의 레시피를 셋업하고 튜닝하는 현업 엔지니어. 1차는 CD-SEM, VeritySEM, Thickness 담당자다.

무엇이 문제인가

측정 위치와 Align Key를 잡는 동안 측정, 실패, 재조정을 되풀이하고, 그동안 화면 앞을 떠날 수 없다. 그 사이 다른 레시피 요청과 측정 문제의 원인 분석이 밀린다.

왜 아픈가

  • 엔지니어: 중요한 일인데 시간 대부분을 같은 클릭과 재조정에 쓴다. 지치고, 실험할 여력이 남지 않는다.
  • 회사: 노하우가 사람에게만 있어 품질이 사람마다 다르고, 장비가 늘면 셋업 인력도 같은 비율로 늘어야 한다.

3. 사용자 (Target Users & Personas)

주 사용자: 1차 담당 엔지니어

  • 역할: 자기 장비군의 레시피 셋업 담당. TF에는 주 5시간(근무일마다 1시간) 겸직으로 참여한다.
  • 기술 수준: Python 코드를 읽고 간단히 고칠 수 있다. LLM, VLM의 특성은 온보딩에서 배운다.
  • 원하는 것: 시행착오 구간을 맡기고, 결과만 확인해 승인하는 것.
  • 걱정하는 것: Agent가 생산 레시피를 잘못 건드리는 것. 그래서 저장과 위험 조작의 최종 승인권을 엔지니어가 갖는다.
  • 장비군별 차이: CD-SEM은 엔지니어 PC → RCS로 바로 접속한다. VeritySEM, Thickness는 웹 VDI를 한 번 더 거친다. 화질, 지연, 단축키 처리가 다르다.

부 사용자

  • 2차 담당 엔지니어: 1차 기간에는 Agent를 쓰지 않는다. 자기 장비 작업을 녹화하고 절차서를 만든다. 플랫폼이 준비되면 같은 역할로 들어온다.
  • 공통 플랫폼 팀: 장비군별 절차를 받아 엔진에 담고, 실패 기록으로 원인을 찾는다.

해야 할 일 (Jobs-to-be-Done)

  • 새 레시피의 측정 위치와 Align Key를, 장비 자체 알고리즘이 통하는 위치로 빨리 잡는다.
  • 셋업이 어디서 왜 실패했는지 기록으로 확인한다.
  • 자기 장비의 절차를 사람이 바뀌어도 남는 형태로 정리한다.

7. 요구사항 (User Stories & Requirements)

가설 (Epic Hypothesis)

측정 위치, Align 셋업 구간을 반자동 Agent에 맡기면, 담당 엔지니어의 이 구간 건당 소요 시간이 ⟨확인⟩% 줄 것이다. 지금은 숙련자가 화면에서 시행착오를 손으로 되풀이하는 것 말고는 방법이 없기 때문이다. 파일럿에서 기준선과 같은 양식으로 재서 확인한다.

사용자 스토리

우선순위: 필수(1차 구축 통과에 필요), 권장(파일럿 전까지), 나중(2차 이후).

S1. 구간을 Agent에 맡기기, 필수 담당 엔지니어로서, 레시피 기본 정보를 입력한 뒤 측정 위치, Align 셋업을 Agent에게 넘기고 싶다. 그래야 시행착오 구간에서 손을 뗄 수 있다. - [ ] 엔지니어가 시작 화면에서 "시작"을 누르면 Agent가 그 화면을 절차의 시작 화면으로 인식한다. 시작 화면이 아니면 시작하지 않고 이유를 보여준다 - [ ] 실행 중에는 현재 단계와 다음 단계가 승인 화면에 보인다 - [ ] 끝나면 끝 화면, 등록된 위치, 소요 시간을 보여주고 제어권을 엔지니어에게 돌려준다

S2. Align Key 등록, 필수 담당 엔지니어로서, Agent가 Align Key를 장비 자체 알고리즘이 통하는 위치로 등록하기를 원한다. - [ ] 이미 성공 이미지가 있는 레시피 유형은 기준 이미지로 Key 후보를 찾는다 - [ ] 후보마다 CV 매칭 점수를 남기고, 점수가 기준 ⟨확인: 담당 엔지니어가 정함⟩ 미만이면 VLM 답으로 덮어쓰지 않고 중단한다 - [ ] 등록 뒤 장비의 Align이 성공했는지 화면으로 확인한다 - 🔵 열린 질문: 성공 이미지가 없는 신규 레시피에서 좋은 Key 위치를 어떻게 고르는가. PoC는 기존 Key 재탐색만 다뤘다. 1차 구축 초기에 장비군 담당과 기준을 정한다

S3. 측정 위치 등록, 필수 담당 엔지니어로서, Agent가 레시피 유형의 측정 위치를 절차대로 등록하기를 원한다. - [ ] 담당 엔지니어가 정한 절차의 단계마다 성공 조건을 검증한다 - [ ] 측정 실행이 필요한 단계는 S4의 승인을 거친다 - [ ] 측정 결과를 담당 엔지니어가 정한 판정 기준(성공/실패, 위치 오프셋)으로 판정하고, 판정 근거 화면을 남긴다

S4. 위험 조작 승인, 필수 담당 엔지니어로서, 측정 실행, 저장, 적용, 삭제, 덮어쓰기, 모드 변경 전에 승인하고 싶다. Agent가 생산 레시피를 혼자 확정하면 안 된다. - [ ] 운영 방식의 조작별 승인 표대로 승인이 필요한 조작은 승인 없이 실행되지 않는다 - [ ] 승인 화면에 무엇을 하려는지, 근거 화면, 되돌릴 수 있는지가 보인다 - [ ] 1차에서는 삭제, 덮어쓰기, 모드 변경을 Agent의 조작 목록에서 뺀다

S5. 즉시 중단과 인계, 필수 담당 엔지니어로서, 언제든 Agent를 멈추고 이어서 직접 하고 싶다. - [ ] 중단 수단(⟨확인: 버튼, 단축키⟩)을 누르면 진행 중인 조작이 끝난 직후 멈추고 마우스, 키보드에서 손을 뗀다 - [ ] 검증 실패, 예상 밖 화면, VDI 잠김, 세션 끊김이면 Agent가 스스로 중단한다 - [ ] 중단하면 마지막 화면, 진행 단계, 이유를 엔지니어에게 넘긴다 - [ ] 되돌릴 수 없는 조작이 실패하면 자동으로 다시 실행하지 않는다

S6. 시도 기록과 지표, 필수 TF 리드로서, 시도마다 무엇을 했고 어디서 실패했는지 남기고 싶다. 그래야 기준선과 비교하고 원인을 찾을 수 있다. - [ ] 시도 1건마다 조작 전후 화면, VLM 응답, 좌표, CV 점수, 판정, 구간 소요 시간, 개입 여부를 기록한다 - [ ] 소요 시간은 기준선 측정 양식과 같은 시작, 끝 화면 기준으로 잰다. 승인 대기 시간은 따로 적는다 - [ ] 기록은 장비 뷰어 창만 담는다. 데스크톱 전체와 키 입력은 기록하지 않는다 (데이터 취급)

S7. 장비군별 절차 정의, 필수 담당 엔지니어로서, 내 장비의 절차를 코드를 크게 고치지 않고 플랫폼에 정의하고 싶다. - [ ] 절차는 단계, 각 단계의 성공 조건, 실패 시 행동, 조작별 승인 분류로 정의한다 - [ ] 정의한 절차를 녹화본에 대고 모의 실행할 수 있다 (온보딩 7주차 실습) - [ ] 장비군별 절차는 공통 저장소 안의 장비군 폴더로 나누고, 공통 엔진은 고치지 않는다 - 🔶 가정: 세 장비군의 차이를 절차 정의만으로 담을 수 있다. 담기지 않으면 결정 기록에 남기고 범위를 조정한다 (위험 R4)

S8. VDI 경유 장비군 지원, 필수 (VeritySEM, Thickness 담당) VeritySEM, Thickness 담당 엔지니어로서, 웹 VDI를 거치는 화면에서도 같은 Agent를 쓰고 싶다. - [ ] VDI 브라우저가 전체 화면(F11), 배율 100%가 아니면 시작하지 않는다 - [ ] 조작마다 화면이 바뀔 때까지 기다린 뒤 검증한다 - [ ] 절차는 클릭과 일반 문자 입력 위주로 만들고, 로컬 OS가 가로채는 단축키는 쓰지 않는다 - [ ] CD-SEM에서 통과한 결과를 근거로 쓰지 않고 장비군마다 따로 검증한다 - 🔵 열린 질문: 엔지니어 PC의 입력 주입이 VDI 경로에서 막히지 않는가. 리드 본인 PC 테스트 대기 (위험 R16)

S9. 작업 녹화 → 절차서, 권장 담당 엔지니어로서, 내가 셋업하는 모습을 녹화해 한국어 절차서로 바꾸고 싶다. 그래야 노하우가 남고 S7의 재료가 된다. - [ ] 녹화는 본인 동의를 받고 녹화 중임을 화면에 표시한다 - [ ] 녹화본에서 조작 타임라인을 뽑고 한국어 절차서 초안을 만든다 - [ ] 계정, 비밀번호 입력 구간은 가린다

S10. 설치형 배포, 필수 담당 엔지니어로서, 개발 도구 없이 내 PC에 설치해 쓰고 싶다. - [ ] 엔지니어 PC에 설치 프로그램 하나로 설치된다. 장비 PC와 VDI 안에는 설치하지 않는다 - [ ] 사내 VLM 엔드포인트에만 연결한다 - 🔵 열린 질문: 보안 승인 범위와 절차 (위험 R6). 2027-03 전 확정

S11. 성공 이미지 수집, 권장 플랫폼 팀으로서, 셋업이 성공할 때마다 Align 성공 이미지를 모으고 싶다. 기준 이미지 방식은 이미지가 쌓여야 효과가 난다. - [ ] 엔지니어가 성공을 승인한 셋업의 Align 화면을 레시피 유형별로 저장한다 - [ ] 담당 엔지니어가 초기 이미지를 직접 넣을 수 있다

제약과 예외 상황

  • 장비 API 없음: 모든 조작은 화면으로만 한다.
  • 사내 모델만: 외부 LLM API는 쓰지 않는다. 화면 이해는 사내 VLM, OCR로 한다.

R1 겸직이라 담당 엔지니어 시간이 확보되지 않는다 높음 높음 기획안에 주 5시간(근무일마다 1시간) 명시, 월간 보고에 참여 시간 실적 보고, 파일럿 때 파견 요청 리드 열림
R2 엔지니어가 AI, LLM 특성을 몰라 Agent에 맞지 않는 절차를 쓴다 높음 중간 온보딩 8주, 2~3주차에서 VLM 한계를 직접 확인하는 실습 플랫폼 팀 SecureVDI 경로는 입력 가능 확인 (2026-11). 로컬 RCS 경로는 열림
R3 Python 소양이 장비군마다 다르다 중간 중간 합류 전 기대 수준 공지, 실습은 코드 작성보다 읽기, 수정 중심 리드 열림
R4 장비군마다 화면과 절차가 크게 달라 공통 플랫폼에 담기지 않는다 중간 높음 1차를 3개 장비군(CD-SEM, VeritySEM, Thickness)으로 제한, 장비별 차이는 절차 정의로 흡수, 안 되면 결정 기록에 남기고 범위 조정 플랫폼 팀 SecureVDI 경로는 입력 가능 확인 (2026-11). 로컬 RCS 경로는 열림
R5 Agent 오조작으로 잘못된 레시피가 저장된다 중간 높음 저장 전 담당 엔지니어 승인, 검증 실패 시 중단, 실장비는 초기에 입회 검증만 장비군 담당 + 플랫폼 열림
R6 장비 화면 녹화분 DB에 직접 접근할 수 없다 ⟨확인⟩ 중간 2026-12 R&D MI H/W 담당자에게 확인. 불가하면 RCS에서 GUI 자동화로 녹화분을 내려받음 (속도가 느리고 다운로드 자동화 작업이 별도로 필요해 관찰 일정에 여유를 둠, 야간 배치) 리드 열림
R7 비생산 검증 시간이 하루 1시간뿐이라 반복 완주 검증이 늦어진다 (장비 사용 인가가 매번 필요) 높음 높음 인가 요청을 기획안 요청 사항에 포함, 녹화본 기반 오프라인 검증으로 실장비 시간을 아끼고, 1시간 안에 끝나는 검증 단위로 나눈다 리드 열림
R8 추론 서비스 가용성 (장애나 용량 부족으로 Agent가 멈춤) 중간 중간 인프라 합류 시점 정하기, 장애 시 수동 셋업으로 돌아가는 절차, 호출이 많은 작업은 실시간 경로 밖에서 실행 플랫폼 팀 SecureVDI 경로는 입력 가능 확인 (2026-11). 로컬 RCS 경로는 열림
R9 PoC의 현장 검증이 끝나지 않은 채 TF가 시작된다 중간 중간 남은 항목을 1차 구축 단계 할 일로 명시 (PoC 자산) 리드 열림
R10 기준선(현재 셋업 시간)이 없어 효과를 증명하지 못한다 중간 높음 온보딩 8주차까지 장비군별 기준선 측정을 수료 기준으로 둔다 장비군 담당 열림
R11 공개 문서에 사내 정보가 섞인다 (수치뿐 아니라 시스템 운영 상태도) 낮음 높음 수치, 실명, 장비 상세, 시스템 운영 상태는 *_사내용.md(git 제외)에만 리드 열림
R12 신규 레시피에는 성공 이미지가 없어 PoC의 기준 이미지 방식이 바로 통하지 않는다 높음 중간 수집 기능 구현, 담당 엔지니어가 초기 이미지 확보, 신규 위치 선정은 별도 과제로 플랫폼 + 장비군 담당 열림
R13 위험 조작(측정 실행, 삭제, 모드 변경) 오조작 중간 높음 조작별 승인, 즉시 중단 수단, 원본 백업과 복구 절차 (운영 방식) 장비군 담당 + 플랫폼 열림
R14 녹화, 화면 데이터의 동의, 보존, 반출 문제 중간 높음 데이터 취급 규칙(장비 뷰어 창만 캡처, 키 입력 기록 안 함), 보안 담당 협의 리드 열림
R15 모델, 절차가 바뀐 뒤에도 예전 검증 결과를 계속 믿는다 중간 중간 변경 시 비생산 검증 시간에 재완주 후 반영 (참여 팀과 역할) 플랫폼 팀 SecureVDI 경로는 입력 가능 확인 (2026-11). 로컬 RCS 경로는 열림
R16 엔지니어 PC의 가상 입력(마우스, 키보드 주입)이 원격 제어 툴이나 보안 솔루션에 막힌다 ⟨확인⟩ 높음 2027-01 가동 전에 리드 본인 PC에서 로컬 RCS와 VDI 경로 각각 입력 주입 테스트 (저장 없음, 승인 불필요 조작만). 막히면 VDI 안에 설치하는 대안을 VDI 관리 조직과 협의 플랫폼 팀 SecureVDI 경로는 입력 가능 확인 (2026-11). 로컬 RCS 경로는 열림
R17 VDI 경유 장비군(VeritySEM, Thickness)에서 화질 저하, 지연, 단축키 가로채기, 세션 끊김으로 조작이 흔들린다 중간 중간 조작마다 화면이 바뀔 때까지 기다린 뒤 검증, 단축키보다 클릭 우선, VDI 화면이 아니면 중단하고 엔지니어에게 넘김, CV 점수 기준을 VDI 화면으로 다시 맞춤 플랫폼 + VeritySEM, Thickness 담당 열림
R18 스크린샷과 녹화 영상으로 스토리지 소모가 매우 커 할당 자원을 넘는다 높음 중간 보존 기한과 해상도 기준을 정하고 사용량을 매월 보고, 실측을 근거로 2027 하반기에 스토리지 자산 확보 요청 리드 열림
R19 Thickness 현업의 기존 PyAutoGUI 자동화와 VLM 방식이 충돌하거나 중복된다 중간 중간 온보딩 때 기존 스크립트 목록화, 정해진 반복 입력은 재사용, 인식과 판단은 VLM, 스크립트 앞뒤 화면 확인. 2027-06 요소 목록에 반영 플랫폼 팀 + Thickness 담당 열림
