# 공통 플랫폼 기술 설계: 녹화에서 절차를 뽑고, 화면을 확인하며 한 단계씩 실행

> 공통 플랫폼을 두 갈래로 만듭니다. Offline은 엔지니어 작업 녹화에서 승인된 절차와 노하우를 만들고, Online은 실제 화면 상태를 확인하면서 승인된 조작 단위만 하나씩 실행합니다.

## 왜 필요한가? (Why)

- [기획안](./01-tf-proposal.md)과 [PRD](./06-platform-prd.md)는 "무엇을, 언제까지"를 정함. "공통 플랫폼을 어떤 구조로 만드는가"는 비어 있었음
- 장비군마다 따로 만들지 않으려면 장비와 무관한 부분(녹화 처리, 저장소, 판단, 안전 관문, 실행 루프)과 장비별 부분(절차, 판정 기준, 화면 영역 지도)의 경계를 먼저 정해야 함
- Codex가 작성한 [Video-to-Workflow Agent 설계](./codex/video-to-workflow-agent.md)(슬라이드 22장)가 이 구조를 상세히 다룸. 이 문서는 그 설계를 검토해 TF 용어, 단계, 제약에 맞춘 결과입니다

이 문서는 플랫폼 팀과 담당 엔지니어용입니다. 담당 임원 보고에는 [기획안](./01-tf-proposal.md) 4절의 요약만 들어갑니다.

## 검토 결과 요약

2026-11-08 Codex 설계를 검토하고 herdr로 Codex와 쟁점을 확인했습니다.

| 구분 | 내용 | 처리 |
|---|---|---|
| 채택 | Offline 지식화와 Online 실행의 분리 | 플랫폼 기본 구조로 채택 |
| 채택 | 판단(LLM), 허용 확인(규칙 엔진), 실행(조작 단위)의 3단 분리 | 안전 원칙에 추가 |
| 채택 | 관찰 사실, 추정 행동, 승인된 규칙을 다른 상태로 저장 | 절차 추출 원칙에 추가 |
| 채택 | 4개 저장 영역(절차와 규칙, 실행 상태, 시연 색인, 원본 증거) | 기획안 서버 자원 요청과 대응 |
| 채택 | 안전 관문 G1, G2, G3와 즉시 중단 조건 | 기존 조작별 승인 표를 확장 |
| 채택 | 미사용 시연(held-out) 평가와 6개 지표 | 관문 지표의 측정 방법으로 사용 |
| 조정 | 첫 Online 대상: Codex 예시는 "승인 Baseline 복사 → Draft 파라미터 수정" | **측정 위치, Align 셋업 유지**. Baseline 복사는 기술 검증 예시로만 씀 (Codex 동의) |
| 조정 | 용어 "Workflow" | TF 용어 **절차**로 씀. 절차에는 분기와 완료 조건이 포함됨 |
| 조정 | 격리 GUI 환경(M4) | 별도 시뮬레이터가 없음. 녹화본 평가 + 입력 없는 실시간 Shadow + 하루 1시간 감독하 실장비 시험으로 대체 |
| 조정 | 입력 로그 | TF는 키 입력을 기록하지 않음(2026-11-02 결정). Codex 설계도 MP4만 전제하므로 구조 변경 없음. 복원 불가 구간은 표시만 하고 추정으로 메우지 않음 |
| 결정 | 구현 형태 | 엔지니어 PC 설치형 에이전트(캡처, 입력, 중단) + 기존 서버 웹앱(판단, 규칙 확인, 승인 화면). 양쪽 Python, 서버는 기존 Flask + Vue 3 (9절) |
| 발견 | PRD가 2027년 반자동 실행과 시간 단축을 요구해 기획안의 "보조는 2028"과 충돌 | PRD 일정을 기획안에 맞춤 ([PRD](./06-platform-prd.md) 1절) |

## 핵심 개념 (What)

### 전체 구조

```
[Offline: 지식화]  2027 관찰과 지식화
  작업 녹화 → 화면 변화 이벤트 → 의미 행동 기록 → 의미 단계 → 여러 시연 정렬 → 분기 후보
     → 담당 엔지니어 승인 → 버전 관리되는 지식 자산 (절차, 조작 단위, 규칙, 시연, 증거)

[Online: 실행]  2027 Shadow(입력 없음) → 2028 보조 → 2029 자율
  화면 관찰 → 현재 상태 인식 → 비슷한 시연 검색 → LLM 판단 → 규칙 확인(Policy Gate)
     → 조작 단위 1개 실행 → 결과 검증 → 체크포인트 저장 → 다음 단계
```

- Online도 2027년에 쓸 수 있음. 단, **화면 입력 없이** 관찰과 추천까지만(Shadow). 화면 입력 권한은 2028 보조 단계에서 엽니다. Align Fail 자동 대응은 승인된 예외로 따로 관리함
- 원본 영상 전체를 매번 LLM에 넣지 않음. 승인된 지식과 지금 화면의 검증된 사실만 판단에 씀

### 용어 대응

Codex 설계를 읽을 때 아래처럼 바꿔 읽습니다. TF 문서에는 오른쪽 말을 씁니다 ([용어](./CONTEXT.md)).

| Codex 설계 | TF 용어 | 뜻 |
|---|---|---|
| Workflow | 절차 | 단계의 순서 + 분기 + 단계별 완료 조건 |
| Semantic Step | 의미 단계 | 시작 조건과 완료 조건을 따로 확인할 수 있는 작업 하나 (예: 레시피 사본 만들기) |
| Skill | 조작 단위 | 사전조건, 인자, 사후조건, 재시도 한도가 정해진 화면 조작 묶음 |
| Demonstration (Demo) | 시연 | 엔지니어 녹화에서 뽑은 한 번의 작업 기록 |
| Policy Engine, Policy Gate | 규칙 확인 | 권한, 호환성, 허용 분기를 서버가 다시 확인하는 단계 |
| Checkpoint | 체크포인트 | 검증된 단계까지의 실행 위치 기록. 장비 상태를 되돌리지는 않음 |
| SOP | 승인 절차서 | 담당 엔지니어가 승인한 절차서 |
| Recipe Draft | 작업용 사본 | 원본을 바꾸지 않고 수정하는 레시피 사본 |

## 어떻게 만드는가? (How)

### 1. Offline: 녹화에서 승인된 절차까지

| 순서 | 단계 | 하는 일 | 사람의 역할 |
|---|---|---|---|
| 1 | 전처리 | 해상도, FPS, 시각 확인. 원본 프레임 번호 보존. 초당 1~2장으로 훑은 뒤 변화 구간만 원본으로 다시 검사 | - |
| 2 | 변화 감지, 이벤트 | 라이브 영역과 커서, 시계 변화는 빼고 조작 영역 변화만 이벤트로 묶음 (전후 화면, ROI, OCR) | 화면 영역 지도 작성 (담당 엔지니어) |
| 3 | 의미 행동 기록 | VLM이 "관찰한 사실"과 "추정한 행동"을 나눠 적고 모든 판단을 원본 프레임에 연결. 모르는 것은 불확실 항목으로 남김 | - |
| 4 | 의미 단계 묶기 | 클릭 여러 개를 시작 조건, 완료 조건이 있는 단계 하나로 묶음 | 경계 검토 |
| 5 | 여러 시연 정렬 | 같은 작업의 녹화 여러 건을 정렬해 공통 경로와 분기 후보를 찾음 | - |
| 6 | 분기 승인 | 분기마다 "발견 → 원인 가설 → 승인" 상태를 따로 둠. 승인된 것만 실행에 씀 | **분기 조건 승인 (담당 엔지니어)** |

- 영상 하나나 빈도만으로 분기 조건을 확정하지 않음. 분기 이유는 담당 엔지니어와 승인 절차서로 확인
- 키 입력을 기록하지 않으므로 정확한 입력 순서, 화면 변화가 없는 실패 입력, 뷰어 창 밖 팝업은 복원할 수 없음. 그 구간은 "미관찰"로 표시하고 추정으로 메우지 않음
- 자동 추출물은 실행 가능한 매크로가 아니라 **검토할 절차 초안**임. 이 원칙은 [녹화 절차 추출 티켓](./wayfinder/tickets/03-procedure-extraction.md)의 결론(AI 초안 + 엔지니어 검토)과 같음
- VLM이 내는 confidence 숫자는 보정된 확률이 아니므로 실행 승인 기준으로 쓰지 않음

### 2. 저장 영역 4개

| 저장 영역 | 담는 것 | 찾는 방식 | 기획안 서버 자원 |
|---|---|---|---|
| 절차, 조작 단위, 규칙 | 단계, 분기 조건, 조작 단위 계약, 승인 절차서 | ID, 버전으로 정확 조회 | 관계형 DB |
| 실행 상태 | 현재 단계, 완료 단계, 시도 횟수, 체크포인트 | 트랜잭션, 재개 조회 | 관계형 DB, 캐시 |
| 시연 색인 | 상태, 목표, 화면 설명 임베딩 + 메타데이터 | 호환성 필터 후 유사 검색 | 검색 엔진 (BGE-M3) |
| 원본 증거 | 녹화, 중요 프레임, ROI, OCR, 원본 시각 | 시연, 이벤트 ID로 추적 | 객체 저장소 |

- 공통 키: 장비 모델, 화면(GUI) 버전, 레시피 유형, 절차 버전, 증거 ID
- 논리적 구분이며 저장 시스템 수를 늘리지 않음. [서버 구성 티켓](./wayfinder/tickets/11-server-config.md)의 할당 자원 안에서 시작함

### 3. Online: 한 단계씩 확인하며 실행

**비슷한 시연 찾기**

1. 호환성 필터: 장비 모델, 화면 버전, 레시피 유형, 승인 범위가 맞지 않으면 제외 (유사도 점수로 보상하지 않음)
2. 유사도 재순위: 현재 단계, 작업 목표, 화면 구성, 직전 작업 이력. 초기에는 상위 3건
- 맞는 시연이 없으면 "검토 요청"이 정상 결과임

**판단, 규칙 확인, 실행의 분리**

| 역할 | 하는 일 | 하지 않는 일 |
|---|---|---|
| 판단 (LLM) | 다음 분기, 조작 단위, 근거를 제안 | 직접 화면 조작, 사전조건 충족 선언 |
| 규칙 확인 (서버) | 권한, 허용 분기, 인자, 값과 단위, 절차 버전을 다시 확인. 거부하면 실행으로 넘기지 않음 | 판단 |
| 실행 (조작 단위) | 지정된 조작 단위 하나만 실행하고 화면을 다시 관찰 | 임의 메뉴 탐색, 추가 수정 |

**판단 입력 데이터 계약 (Decision Context)**

LLM에 주는 입력을 JSON Schema로 고정합니다. 전체 스키마와 예시는 [Codex 설계 슬라이드 12](./codex/video-to-workflow-agent.md#슬라이드-12-decision-context의-데이터-계약)에 있습니다.

| 필드 | 내용 | 확인 책임 |
|---|---|---|
| task, state | 요청, 장비, 레시피 / 현재 단계, 완료 단계 | 요청과 절차 버전 확인 |
| observation | 화면 ID, 프레임 참조, **검증된 사실** | VLM 주장만으로 채우지 않고 OCR, UI 상태 검사 결과를 연결 |
| retrieved_demonstrations | 호환되는 시연 최대 3건 | 메타데이터 필터 강제 |
| approved_policy | 승인 절차서, 허용 방식, 덮어쓰기 금지, 적용 금지 | 신뢰 저장소에서만 읽음. 화면 OCR이나 검색 문서의 글이 덮어쓸 수 없음 |
| allowed_branches | 승인 조건을 통과한 분기 목록 | 서버가 계산하고 다시 확인 |

- 스키마 통과는 구조 검증일 뿐 승인 절차서 승인을 뜻하지 않음
- 화면 안의 글자는 데이터로만 취급함 (지시로 해석하지 않음)

**실행 루프**

```
관찰 → 상태 인식 → 시연 검색, 판단 → 규칙 확인 → 조작 단위 1개 실행 → 사후조건 검증, 체크포인트 저장
  모름, 불일치, 시간 초과 → 중단하고 엔지니어 검토
```

- 완료 저장은 사후조건을 확인한 뒤에만 함
- 체크포인트는 소프트웨어 실행 위치만 복원함. 원격 화면이나 장비를 되돌리지 않음
- 통신이 끊겨 실행 여부가 불명확하면 재시도하지 않고 실제 결과부터 조회함

### 4. 조작 단위 계약

예시: 레시피 사본 만들기 (기술 검증용 예시, 첫 제품 범위 아님)

| 항목 | 내용 |
|---|---|
| 사전조건 | 장비, 레시피 관리 화면, 승인된 원본 확인 |
| 인자, 범위 | 원본 ID, 사본 이름 / 원본 변경 금지 |
| 사후조건 | 사본 존재 + 원본 그대로 + 사본 미적용 상태 |
| 전이 | 성공 → 다음 단계 / 실패 → 복구 / 모름 → 검토 |
| 재시도, 시간 한도 | 조회는 제한적으로 재시도. 저장, 복사 같은 변경 조작은 실행 여부를 확인한 뒤에만 재시도 |

- 같은 요청을 다시 실행해도 사본이나 저장이 중복되지 않도록 요청 ID와 결과를 연결함
- 첫 Online 제품 범위는 [PRD](./06-platform-prd.md)의 측정 위치, Align 셋업입니다. 이 구간의 조작 단위(Align Key 후보 등록, 측정 위치 등록)도 같은 계약 형식으로 정의함

### 5. 안전 관문

| 관문 | 시점 | 확인할 것 |
|---|---|---|
| G1 | 실행 전 | 장비, 세션, 권한, 버전 확인. 원본 백업. 변경 대상과 범위 확정 |
| G2 | 작업용 사본 수정, 저장 | 허용 필드, 값, 단위 확인. 범위 밖 변경 차단. 저장 후 다시 읽어 차이(Diff) 확인 |
| G3 | 운영 적용 | 담당 엔지니어가 백업, 차이, 검증 증거를 보고 별도 승인 |

- **즉시 중단**: 장비 불일치, 승인되지 않은 분기, 상태 불명, 금지 필드 변경, 검증 실패
- 기본 정책: 덮어쓰기 금지, 적용 금지. 운영 적용은 별도 작업과 승인으로 남김
- 기존 [조작별 승인 표](./03-operating-rhythm.md)와의 관계: 승인 표는 "누가 승인하는가", G1~G3는 "승인 전후에 무엇을 확인하는가"를 정함. 둘 다 적용함
- 감사 기록: 요청, 규칙과 조작 단위 버전, 전후 증거, 차이, 승인자

### 6. 평가 방법

**정보 누수 방지**

- 지식 자산용 시연과 평가용 시연을 나눔. 같은 작업, 파생 영상이 양쪽에 섞이지 않도록 요청, 장비, 시간 기준으로 그룹을 나눔
- 시점 t를 평가할 때는 t 이전 관찰만 Agent에 줌. 미래 프레임과 정답 경로는 평가자만 씀
- 평가 대상 시연은 시연 색인, 임베딩 캐시, 절차 추출 데이터에서도 뺌
- 녹화본 재생 평가로 화면 조작 성공률을 주장하지 않음

**지표 (정의만, 실측값 없음)**

| 지표 | 정의 | 평가 환경 | 쓰는 관문 |
|---|---|---|---|
| 단계 추출 F1 | 담당 엔지니어 정답 대비 단계 정밀도, 재현율의 F1 | 라벨링한 녹화 | 2027-12 관찰과 지식화 |
| 상태, 분기 정확도 | 맞힌 상태, 분기 수 / 평가한 상태, 분기 수 (따로 집계) | 미사용 시연 재생 | 2027-12, 2028 진입 |
| 미승인 행동 제안률 | 미승인 행동 제안 수 / 전체 제안 수 | 재생 + Shadow | 2028 진입 |
| 안전 중단률, 자동 결정률 | 모르는 상황 중 안전하게 멈춘 비율 / 전체 중 자동 결정 비율 | 오류, 미지 상태 포함 | 2028, 2029 |
| 검증된 작업 성공률 | 사후조건과 정확한 차이를 통과한 작업 / 시도한 작업 | 감독하 실장비 | 2028 보조 |
| 소요 시간, 사람 투입 | 관찰부터 검증까지 p50, p95 / 검토 시간, 개입 횟수 | 실제 실행 경로 | 2028, 2029 |

- 위험 실행 0건이 표본에서 나와도 무위험을 증명하지 않음. 잘못된 값 저장, 원본 변경, 적용 건수를 별도 안전 지표로 둠
- 수치 목표는 PoC 시작 전 담당 엔지니어와 합의함 (⟨확인⟩)

### 7. 격리 환경이 없을 때의 검증 순서

Codex 설계는 격리된 GUI 환경을 가정합니다. TF에는 별도 시뮬레이터가 없고 비생산 실장비 시간이 하루 1시간입니다. 그래서 아래 순서로 대신합니다.

1. **녹화본 평가**: 미사용 시연으로 상태와 다음 행동 판단을 평가
2. **입력 없는 실시간 Shadow**: 실제 화면을 보고 제안만 내고, 담당 엔지니어가 제안을 검토
3. **감독하 실장비 시험**: 인가된 1시간 안에 작업용 사본과 조작 단위 하나씩 검증. 원본 보존, 적용 금지, 측정 실행 승인, 즉시 중단, 사후 확인

- 작업용 사본만으로 장비 동작까지 격리되지는 않음. 3번 조건을 확보하지 못하면 2028 진입 판단은 Shadow까지만 근거로 씀

### 8. 단계별 구현 순서

| Codex 단계 | 산출물 | TF 시기 | 다음 단계 통과 조건 |
|---|---|---|---|
| M1 데이터, 정답 구축 | 녹화 목록, 메타데이터, 라벨 기준 | 2027-01~06 (온보딩, 녹화 축적) | 장비, 화면 버전, 핵심 분기, 예외 표본 확보 (온보딩 종료만으로는 통과 아님) |
| M2 Offline 추출 | 의미 행동 기록, 의미 단계, 분기 후보 | 2027 3분기 (절차화) | 담당 엔지니어 검수, 누락과 오인식 원인 확인 |
| M3 판단 입력, 재생 평가 | 승인 절차, JSON 계약, 시연 검색, 미사용 시연 평가 | 2027 4분기 (지식 자산, 돌파구 추천) | 미사용 시연 평가, 미승인 제안과 중단 분석 |

- M5는 제한 운영을 **검토**하는 단계이며 2029 자율 완주를 보장하지 않음. 자율 단계의 통과 기준은 [완성 정의 티켓](./wayfinder/tickets/06-done-definition.md)을 따름
- 첫 범위: 장비와 화면 버전 1종, 레시피 유형 1종

### 9. 구현 형태와 기술 스택

2026-11-08 herdr로 Codex와 검토한 결과입니다. 실장비, 회사 PC에서 검증한 결과가 아닙니다.

**설치형과 웹앱의 경계**

순수 웹앱으로는 안 됩니다. 브라우저도 사용자가 고르고 동의하면 창을 캡처할 수 있지만(`getDisplayMedia`), 상시 관찰에 매번 동의를 받을 수 없고 OS 입력은 넣을 수 없습니다. 그래서 엔지니어 PC에는 캡처, 입력, 중단만 하는 얇은 에이전트를 두고, 나머지는 기존 서버의 웹앱에 둡니다.

| 구성 요소 | 위치 | 언어, 프레임워크 | 이유 |
|---|---|---|---|
| 화면 캡처, 변화 감지 | 엔지니어 PC (로그인 사용자 앱) | Python + WGC 바인딩 (`windows-capture` 우선 검증) | PoC 재사용. PC에서는 수집만 하고 추론하지 않음 |
| 입력 실행, 즉시 중단 | 엔지니어 PC | Python + `ctypes` SendInput, 창 관리는 `pywin32` | 입력 직전에 대상 창과 화면을 다시 확인. 중단은 서버 응답 없이 PC에서 처리 |
| PC 쪽 화면 | 엔지니어 PC | 트레이 아이콘 + 최소 localhost 페이지 | 상태, 제어권 인계, 중단. localhost는 루프백 한정, 인증과 Host, Origin 검사 |
| 판단, 규칙 확인 | 기존 서버 | Python + 기존 Flask | [서버 구성](./wayfinder/tickets/11-server-config.md)의 Flask 앱 재사용 |
| 절차서 검토와 승인, 대시보드 | 서버 + 브라우저 | Vue 3 + Flask API | 공용 화면을 한곳에서 유지. 에이전트가 서버로 연결을 시작함 |
| 녹화 재처리, 추론 | 기존 서버 | Python 작업 프로세스 + 작업 큐, 사내 모델 API | 오래 걸리는 작업을 요청 처리와 분리 |
| 저장 | 사내 서비스 | 객체 저장소, OpenSearch, PostgreSQL, Redis | 2절의 저장 영역 4개. 새 저장 시스템 없음 |
| 배포 | 엔지니어 PC | PyInstaller onedir + 회사 인증서 서명 + 사내 배포 경로 | 자체 업데이트 기능은 만들지 않음. 작업 중 업데이트 금지 |

- Python을 고른 이유: 개발 인력이 실질 1명, PoC 코드가 Python, Thickness의 PyAutoGUI 스크립트 재사용, 담당 엔지니어가 Python을 읽을 수 있음
- C#/.NET은 보류. Python 캡처가 PC 자원 한도를 못 지키면 작은 .NET 캡처, 입력 모듈 + Python 서버가 다음 대안
- Electron, Tauri는 쓰지 않음. 입력 충돌을 풀지 못하면서 Chromium 프로세스나 Rust 운영 부담만 더함
- FastAPI 전환은 녹화 재처리가 Online 판단의 p95 지연을 늘리는 것이 실측으로 드러날 때 검토

**백그라운드의 범위: 관찰과 판단만**

SendInput은 실제 마우스와 키보드 입력 흐름을 엔지니어와 공유합니다. Agent가 입력하는 동안 엔지니어는 PC를 쓸 수 없습니다. 그래서 입력은 [제어권 인계](./CONTEXT.md)로 합니다.

```
알림 → 엔지니어가 넘겨줌 → 대상 창 활성화 확인 → 짧은 입력 → 결과 확인 → 제어권 반환
  엔지니어 마우스, 키보드 조작 / 포커스 이탈 / VDI 잠김 → 즉시 중단
```

- 창 메시지(PostMessage) 입력은 RCS, Radmin, SecureVDI가 원격까지 전달하는지 확인되지 않았음. 기능으로 약속하지 않음
- Windows는 자동 foreground 전환을 막을 수 있음. 엔지니어가 넘겨주는 동작을 기본으로 함
- 가상 데스크톱, 별도 세션은 입력 장치가 분리되지 않아 해결책이 아님. 로컬 VM은 입력을 분리하지만 보안 승인, 자원 부담이 커서 제외. 같은 PC에서 동시 업무가 꼭 필요해지면 다시 검토

**규칙 확인은 서버와 PC 두 곳에서**

- 서버: 권한, 승인 범위, 절차 버전 판정
- PC: 입력 직전에 대상 창, 화면이 최신인지, 세션 잠김, 승인 유효기간, 중단 상태를 다시 검사. PC 검사는 거부만 더할 수 있고 서버 승인보다 넓어질 수 없음
- 네트워크가 끊기면 새 입력을 멈추고 자동으로 재개하지 않음. 이미 보낸 클릭은 취소할 수 없으므로 결과가 불명확한 조작은 다시 보내지 않고 화면부터 다시 확인함
