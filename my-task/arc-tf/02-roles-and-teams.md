# 참여 팀과 역할

> 누가 TF에 들어오고, 무엇을 책임지는가. 공통 플랫폼 팀과 장비군 담당으로 나눈다.

## 왜 나누는가

장비군마다 자동화를 따로 만들면 화면 인식, 조작, 안전 장치를 장비 수만큼 다시 만든다. 반대로 플랫폼 팀이 모든 장비의 레시피 절차까지 알 수는 없다. 그래서 **엔진은 한 곳(플랫폼)에서**, **절차와 판정 기준은 장비를 아는 사람(장비군 담당)이** 맡는다.

PoC는 리드 한 사람이 개발자와 CD-SEM 담당 두 역할을 함께 맡아 진행했다. 두 역할이 동시에 필요하다는 것, 그리고 모델 운영, 최신 VLM 테스트, 녹화분 확보까지 한 사람이 하기에는 시간이 부족하다는 것이 이 분업의 근거다 ([PoC 성과와 시사점](./05-poc-assets.md)).

조직과 명단은 2026-12에 2차까지 한 번에 승인받는다. 초기 개발은 선발대(CD-SEM, Thickness, Inspection) 위주로 하고, 2차 장비군(다른 MI 장비군)은 상반기에 인터뷰, Recipe Workflow 조사로 준비하다가 공통 플랫폼이 베타 기준을 통과하면(2027-06) 본격 참여한다.

## 구성

| 구분 | 구성 | 맡는 일 | 참여 형태 |
|---|---|---|---|
| TF 리드 | 본인 | TF 운영, 범위, 우선순위 결정, 임원 보고, 장비군 담당 간 조율 | 주 업무 |
| 공통 플랫폼 팀 | 개발 약 5명 규모: 임원, 팀장급 지정 4명 (백엔드 2, 프론트엔드 2) + 1차 MI팀 현업 엔지니어 개발 참여. TF 리드가 총괄 | 리드: 전체 설계, 모든 갈래 관여. 백엔드: 서버, 녹화 DB 추출, 데이터 파이프라인, 평가 세트, LLMOps. 프론트엔드: 설치형 에이전트, 승인 화면, 배포. 교육 진행 | 겸직 |
| 1차 장비군 담당 (선발대) | CD-SEM, Thickness, Inspection (장비군마다 MI 엔지니어 1~2명) | 레시피 절차 정의, 성공 판정 기준, 데이터 수집, 현장 검증, 공통 플랫폼 베타 사용과 피드백 | 겸직, 탄력 운영, 2027-01 합류 |
| 2차 장비군 담당 | 다른 MI 장비군마다 MI 엔지니어 1~2명 | 합류 뒤 교육, 작업 녹화, 화면 영역 지도, 절차 정의. 1차 담당과 같은 역할로 공통 플랫폼을 실제로 적용 | 2026-12 지정. 상반기 인터뷰, Recipe Workflow 조사, 2027-07부터 본격 참여 (6월 베타 배포 확인 뒤) |
| 인프라 | ⟨확인⟩ | GPU, VLM 서빙 운영 | 필요해지면 합류 |
| 장비 벤더 | ⟨확인⟩ | 화면, 레시피 구조 자문 | 필요할 때 |
| 정보보안 | ⟨확인⟩ | 설치형 프로그램 배포, 작업 녹화 승인 범위 | 승인 단계에서 협의 |

### 장비군 담당 명단

| 담당 | 장비군 | 단계 | 접속 경로 | 엔지니어 |
|---|---|---|---|---|
| A | CD-SEM | 1차 | 엔지니어 PC → RCS → 장비 | 리드(본인) |
| B | Thickness | 1차 | 엔지니어 PC → 웹 VDI(가상 Windows) → RCS/Radmin Viewer → 장비 | ⟨확인⟩ |
| C 이후 | 다른 MI 장비군 (⟨확인: 2차 장비군 목록⟩) | 2차 | 장비군마다 ⟨확인⟩ (VDI 경유면 B와 같음) | ⟨확인⟩ |

Thickness와 VDI를 거치는 2차 장비군은 원격 계층이 하나 더 있다. CD-SEM에서 통과한 결과를 이 장비군들의 근거로 쓰지 않고, 장비군마다 따로 검증한다.

실명과 팀명은 사내용 문서(`*_사내용.md`)에만 적는다.

## 책임 분담표 (RACI)

R=실행, A=최종 책임, C=협의, I=공유

| 일 | 리드 | 플랫폼 팀 | 담당 엔지니어 | 인프라 | 보안 |
|---|---|---|---|---|---|
| 범위, 우선순위 결정 | A | C | C | I | I |
| 공통 엔진, 안전 규칙 | A | R | C | C | C |
| 장비별 레시피 절차 정의 | I | C | R/A | - | - |
| 성공 판정 기준 | C | C | R/A | - | - |
| 현재 셋업 시간 측정 (기준선) | I | C | R/A | - | - |
| 작업 녹화, 절차서 정리 | I | C | R/A | - | - |
| 비생산, 파일럿 검증 | A | R | R | I | - |
| 레시피 저장 승인 (운영 중) | I | - | R/A | - | - |
| VLM 서빙 운영 | I | C | - | R/A | - |
| 설치형 프로그램 배포, 녹화 승인 범위 | R | C | I | - | A |
| 교육 진행 | A | R | - | - | - |
| 월간 임원 보고 | R/A | C | C | - | - |
| 단계 통과 정리 (승인은 임원) | R/A | C | C | - | - |
| 수집 데이터 관리 (녹화, 화면, 기록) | A | R | C | - | C |
| 위험 조작 승인, 즉시 중단 (운영 중) | I | - | R/A | - | - |
| 오조작 복구 (원본 레시피 되돌리기) | I | C | R/A | - | - |
| 장애 대응 (플랫폼, 모델 장애) | I | R/A | I | R | - |
| 모델, 절차 변경 승인과 재검증 | A | R | R | C | - |
| 운영 이관 | A | R | C | C | - |
| TF 종료, 연장 판단 (결정은 임원) | R | C | C | - | - |

**담당 엔지니어가 위험 조작과 레시피 저장의 최종 승인자다.** Agent와 플랫폼 팀은 레시피를 혼자 확정하지 않는다.

## 파일럿 이후

- **변경과 재검증**: VLM 모델, 플랫폼, 장비 화면, 장비별 절차 중 하나라도 바뀌면 이전 검증 결과는 그대로 쓰지 않는다. 그 장비군의 대표 유형을 비생산 검증 시간에 다시 완주한 뒤에 운영에 반영한다.
- **장애 연락**: 플랫폼이나 모델 장애가 나면 플랫폼 팀이 장비군 담당에 알리고, 장비군 담당은 수동 셋업으로 돌아간다. 연락 경로는 ⟨확인⟩.
- **운영 이관**: 파일럿을 통과한 장비군을 TF 밖의 상시 운영으로 넘기는 조건과 받을 조직은 ⟨확인⟩. 2027-09 월간 보고에서 정한다.
- **TF 종료, 연장**: 2027-12 월간 보고에서 리드가 성과와 남은 범위를 정리해 올리고, 임원이 종료, 연장, 상시 조직 전환 중 하나를 정한다.

## 담당 엔지니어에게 기대하는 것

- 개발과 AI에 익숙하지 않아도 된다. 합류 시점마다 교육을 받으며 TF에 참여한다. Python은 읽고 간단히 고치는 정도까지 사전 자료와 1주차 실습으로 맞춘다.
- 자기 장비의 레시피 셋업 절차를 설명할 수 있다.
- 겸직이며 참여 시간은 탄력적으로 운영한다. 그 안에서 기준선 측정, 녹화, 검증을 한다.
- AI, LLM 특성은 몰라도 된다. 주간 미팅에서 배운다 ([주간 미팅과 노하우 공유](./04-onboarding.md)). 2차 장비군은 합류 시점(2027-07)부터 참석한다.
