# 위험 목록

> TF 운영과 구현의 위험, 대응, 담당. 실무 회의에서 바뀐 것만 확인한다.

| # | 위험 | 가능성 | 영향 | 대응 | 담당 | 상태 |
|---|---|---|---|---|---|---|
| R1 | 겸직이라 셀 엔지니어 시간이 확보되지 않는다 | 높음 | 높음 | 기획안에 주 N시간 명시, 월간 보고에 참여 시간 실적 보고, 파일럿 때 파견 요청 | 리드 | 열림 |
| R2 | 엔지니어가 AI·LLM 특성을 몰라 Agent에 맞지 않는 절차를 쓴다 | 높음 | 중간 | 온보딩 8주, 2~3주차에서 VLM 한계를 직접 확인하는 실습 | 플랫폼 팀 | 열림 |
| R3 | Python 소양이 셀마다 다르다 | 중간 | 중간 | 합류 전 기대 수준 공지, 실습은 코드 작성보다 읽기·수정 중심 | 리드 | 열림 |
| R4 | 장비군마다 화면과 절차가 크게 달라 공통 플랫폼에 담기지 않는다 | 중간 | 높음 | 1차를 2~3개 장비군으로 제한, 장비별 차이는 절차 정의로 흡수, 안 되면 결정 기록에 남기고 범위 조정 | 플랫폼 팀 | 열림 |
| R5 | Agent 오조작으로 잘못된 레시피가 저장된다 | 중간 | 높음 | 저장 전 셀 엔지니어 승인, 검증 실패 시 중단, 실장비는 초기에 입회 검증만 | 셀 + 플랫폼 | 열림 |
| R6 | 장비 PC 화면 조작에 대한 보안 승인이 늦어진다 | 중간 | 높음 | 2027-03 전 승인 범위 확정을 기획안 요청 사항에 포함, 그 전에는 비생산 환경과 녹화본으로 진행 | 리드 | 열림 |
| R7 | 비생산 검증용 장비 시간을 못 얻는다 | 중간 | 높음 | 기획안 요청 사항에 포함, 녹화본 기반 오프라인 검증을 먼저 진행 | 리드 | 열림 |
| R8 | 추론 서비스 가용성 (장애나 용량 부족으로 Agent가 멈춤) | 중간 | 중간 | 인프라 합류 시점 정하기, 장애 시 수동 셋업으로 돌아가는 절차, 호출이 많은 작업은 실시간 경로 밖에서 실행 | 플랫폼 팀 | 열림 |
| R9 | PoC의 현장 검증이 끝나지 않은 채 TF가 시작된다 | 중간 | 중간 | 남은 항목을 1차 구축 단계 할 일로 명시 ([PoC 자산](./05-poc-assets.md)) | 리드 | 열림 |
| R10 | 기준선(현재 셋업 시간)이 없어 효과를 증명하지 못한다 | 중간 | 높음 | 온보딩 8주차까지 셀별 기준선 측정을 수료 기준으로 둔다 | 셀 | 열림 |
| R11 | 공개 문서에 사내 정보가 섞인다 (수치뿐 아니라 시스템 운영 상태도) | 낮음 | 높음 | 수치·실명·장비 상세·시스템 운영 상태는 `*_사내용.md`(git 제외)에만 | 리드 | 열림 |
| R12 | 신규 레시피에는 성공 이미지가 없어 PoC의 기준 이미지 방식이 바로 통하지 않는다 | 높음 | 중간 | 수집 기능 구현, 셀이 초기 이미지 확보, 신규 위치 선정은 별도 과제로 | 플랫폼 + 셀 | 열림 |
| R13 | 위험 조작(측정 실행·삭제·모드 변경) 오조작 | 중간 | 높음 | 조작별 승인, 즉시 중단 수단, 원본 백업과 복구 절차 ([운영 방식](./03-operating-rhythm.md)) | 셀 + 플랫폼 | 열림 |
| R14 | 녹화·화면 데이터의 동의·보존·반출 문제 | 중간 | 높음 | 데이터 취급 규칙, 보안 담당 협의 | 리드 | 열림 |
| R15 | 모델·절차가 바뀐 뒤에도 예전 검증 결과를 계속 믿는다 | 중간 | 중간 | 변경 시 비생산 재완주 후 반영 ([참여 팀과 역할](./02-roles-and-teams.md)) | 플랫폼 팀 | 열림 |
