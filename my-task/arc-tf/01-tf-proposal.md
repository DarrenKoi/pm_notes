# ARC TF 구성 기획안

> MI 장비 Recipe 셋업을 AI가 mouse와 keyboard를 직접 조작하는 컴퓨터 사용(Computer-use) 기반으로 자동화하려고 합니다. R&D MI 현업 엔지니어와 협업해 자동화 공통 플랫폼을 개발하고자 합니다.

**보고 대상**: AI TF 담당 임원, 기반기술센터장

## 1. 왜 해야 하는가

### 문제

- 레시피 셋업은 숙련 엔지니어가 원격 제어 화면에서 마우스와 키보드로 하는 반복 수작업임. 측정 위치를 잡을 때 측정, 실패, 재조정을 되풀이함
- 노하우가 개인에게 있음. 담당자가 바뀌면 지식이 사라지고, 사람마다 품질이 다름
- 관리 장비가 늘어나거나 개발 제품이 증가하면 셋업 인력도 같은 비율로 늘어나야 하나, 이 구조로는 한계가 있음

### 안 하면 생기는 일

- ⟨확인: 신규 제품·공정 도입 때 레시피 셋업 대기로 늦어지는 기간⟩
- ⟨확인: 장비군별 레시피 셋업에 쓰는 엔지니어 시간 (월 기준)⟩
- 장비군마다 따로 자동화를 시도하면 화면 인식, 조작, 안전 장치를 매번 새로 만들게 됨

### 효과

| 효과 | 측정 지표 | 현재 | 목표 |
|---|---|---|---|
| 셋업 시간 단축 | 레시피 1건 셋업 소요 시간 | 레시피당 평균 30~60분 (현업 경험치, 셋업 전체 기준). 자동화 대상 구간의 셀별 실측은 온보딩 8주차 | ⟨확인⟩% 단축 |
| 사람 개입 감소 | 1건당 엔지니어 개입 횟수 | ⟨확인⟩ | ⟨확인⟩ |
| 품질 균일화 | 셋업 뒤 첫 측정 성공률 | ⟨확인⟩ | ⟨확인⟩ |
| 지식 자산화 | 절차서로 정리된 레시피 유형 수 | 0 | 장비군마다 1개 이상 |
| 확장성 | 새 장비군 합류에 드는 기간 | — | ⟨확인⟩ |

셋업 시간의 현재 값은 현업 경험치입니다. 나머지 현재 값과 함께 TF 온보딩 기간(2027-01~02)에 셀 엔지니어가 직접 측정해 확정하겠습니다. 측정하기 전에는 목표를 숫자로 약속하지 않습니다.

**측정 규칙** (기준선과 파일럿을 같은 조건으로 비교하기 위해 온보딩 측정 양식에 고정)

- 대상: 셀마다 정한 대표 레시피 유형 1개. 전체 셋업이 아닌 **자동화 대상 구간(측정 위치·Align 셋업)** 의 시작과 끝을 정해 측정
- 포함: 그 구간 안의 실패·재작업·수동 인계 시간. 승인 대기 시간은 별도 기록
- 개입 횟수: 반드시 거치는 승인(저장 전 등)은 제외하고 **예정에 없던 개입**만 집계

### 셋업 시간이 줄면 회사에 무엇이 남는가

```
레시피 셋업 수요(건/월) × 건당 엔지니어 투입 시간 감소분
  → 회수되는 엔지니어 시간 (월 ⟨확인⟩시간)
  → 신규 제품·공정 도입 때 셋업 대기 단축, 엔지니어가 분석·개선 업무로 이동
  → 장비가 늘어도 셋업 인력을 같은 비율로 늘리지 않아도 됨
```

- 가정: ⟨확인: 장비군별 월 셋업 수요와 증가 추세⟩. 셋업 수요가 장비·제품 수와 함께 늘어야 "인력이 비례해야 한다"는 주장이 성립함

## 2. 이미 확보한 것 — 1차 PoC (Align Fail 대응 자동화)

ARC는 처음부터 레시피 자동 생성을 목표로 했습니다. 1차 PoC로는 범위가 좁고 효과를 재기 쉬운 **Align Fail(정렬 실패) 무인 대응**을 선택했고, 이 PoC에서 레시피 자동 생성에 그대로 쓸 기반을 검증했습니다.

| 확보한 것 | 레시피 자동 생성에서의 쓰임 |
|---|---|
| 사내 인프라에서 화면 이해 모델(VLM·OCR) 자체 운영 | 외부 API 없이 화면 이해 |
| 표준 컴포넌트가 아닌 계측 화면에서도 대략 위치 → 정밀 좌표 → OCR 확인 순서로 클릭 | API 없는 장비 화면 조작 |
| VLM은 "어디를 볼지", CV는 "정확히 어디인지"를 맡는 역할 분리 원칙 | 측정 위치·Align Key 등록의 정확도 |
| 최근 성공 사례를 모은 기준 이미지로 Align Key 탐색 정확도 개선 (오프라인 평가 기준) | 레시피 Align 셋업 |
| 실장비 반자동 운영: 위치 재조정은 자동, 최종 확정은 엔지니어 | TF의 안전 원칙 |
| 엔지니어 작업 녹화 → 조작 타임라인 → 한국어 절차서 | 장비별 레시피 절차 정의 |

상세 목록은 [PoC 자산과 남은 과제](./05-poc-assets.md)에 있으며, 수치는 사내용 문서에만 둡니다.

**PoC로 확인한 것**: API 없는 장비 화면을 보고 조작 가능, 오프라인 평가에서 Align Key 탐색 가능

**아직 확인하지 못한 것**:

- SecureVDI 경유 장비 화면도 VLM으로 문제없이 조작 가능한가
- 엔지니어가 한 작업을 Agent가 의미를 파악하고 그대로 따라 진행할 수 있는가
- 새로운 측정 파라미터를 추가할 때, 의뢰서를 근거로 위치를 찾고 몇 번의 조정을 거쳐 이미지를 제대로 등록할 수 있는가

세 가지 모두 장비 화면과 레시피 절차를 아는 현업 엔지니어와 함께 검증해야 합니다. 그래서 TF가 필요합니다.

## 3. 무엇을 하는가 — 범위

| 구분 | 내용 |
|---|---|
| 최종 목표 | 신규 레시피 셋업의 전 과정 자동화: 생성 → 측정 위치·Align Key 등록 → 파라미터 → 검증 측정 → 저장 |
| 1차 범위 | 시행착오가 가장 많은 **측정 위치·Align 셋업 구간** |
| 대상 장비 | 1차: CD-SEM, VeritySEM, Thickness. 2차: 나머지 MI 장비군 |
| 1차에서 사람이 맡는 것 | 레시피 생성과 기본 정보 입력, 파라미터 설정, 검증 측정 판정, 저장. Agent는 그 사이의 측정 위치·Align 셋업 구간을 담당 |
| 자동화 수준 | **반자동(Supervised Autonomy)**: Agent가 조작하고, 위험 조작(측정 실행, 삭제, 모드 변경)과 레시피 저장·적용 직전에는 엔지니어가 승인. 완전 자동은 반복 검증과 안전 중단 기록까지 통과한 레시피 유형만 단계 승인을 거쳐 검토 |
| 실행 방식 | 설치형 프로그램을 엔지니어에게 배포하고, 엔지니어가 **본인 PC에서** AI 자동화 프로그램과 함께 셋업. 장비 PC에는 설치하지 않음. 접속 경로는 장비군마다 다름: CD-SEM은 엔지니어 PC에서 RCS로 직접, VeritySEM·Thickness는 SecureVDI(웹 VDI)의 가상 Windows 안에서 RCS나 Radmin Viewer로 접속. Agent는 어느 경로든 엔지니어가 보는 화면(FHD 모니터 기준)을 캡처하고 같은 화면에 입력 |
| 제외 | 장비 유지보수, 하드웨어 제어, 장비 내부 소프트웨어 설치 |

## 4. 어떻게 하는가 — TF 구성

| 구분 | 구성 | 맡는 일 |
|---|---|---|
| TF 리드 + 공통 플랫폼 팀 | 리드(본인) 포함 개발 2명 | 화면 인식·조작 엔진, 안전 규칙, 승인 화면, VLM 연동, 교육 |
| 1차 셀 A | CD-SEM, 리드(본인) 담당 | 장비별 레시피 절차, 성공 판정 기준, 현장 검증 |
| 1차 셀 B | VeritySEM, MI 엔지니어 | 위와 같음 |
| 1차 셀 C | Thickness, MI 엔지니어 | 위와 같음 |
| 2차 셀 | 나머지 MI 장비군 | 1차 기간에는 학습과 작업 녹화·절차서 정리 |

- **공통 플랫폼**: 모든 장비군이 함께 사용. 장비마다 엔진을 새로 만들지 않음
- **장비군별 셀**: MI 현업 엔지니어 1~2명으로 구성. 그 장비의 레시피 절차 정의, 성공 판정 기준, 현장 검증 담당. CD-SEM 셀은 리드(본인)가 직접 담당
- **2차 셀**: 1월에 함께 합류. 1차 기간에는 학습을 받고 자기 장비 작업을 녹화해 절차서로 정리. 플랫폼 준비 후 바로 투입
- **인프라(GPU·VLM 서빙)**: 필요 시점에 합류. 장비 벤더는 필요할 때 자문

역할 분담은 [참여 팀과 역할](./02-roles-and-teams.md)에 있습니다.

## 5. 타임라인

| 시기 | 단계 | 하는 일 | 통과 기준 |
|---|---|---|---|
| 2026-11 | 기획 | 기획안 작성, 1차 장비군 후보 협의 | 기획안 완성 |
| 2026-12 | 승인 | 임원 보고, TF 구성 승인, 참여 엔지니어 지정 | 승인과 명단 확정 |
| 2027-01~02 | 온보딩 | 학습 과정, 셀별 현재 셋업 시간 측정, 대표 레시피 유형 선정, 성공 이미지 수집 시작. 플랫폼 팀은 PoC 남은 일 정리와 실행 엔진 작업 | 셀마다 기준선과 대상 유형 확정 |
| 2027-03~06 | 1차 구축 | 실행 엔진 제품화, 측정 위치·Align 셋업 기능 + 1차 셀 절차 정의, 오프라인·비생산 검증 | 1차 셀마다 대표 유형 1개를 비생산 검증 시간(인가받은 장비 시간, 하루 1시간)에 ⟨확인: N⟩회 연속 완주, 실패한 시도는 모두 안전하게 중단 |
| 2027-07~09 | 파일럿 | 1차 장비군 실장비 파일럿 (필요 시 셀 엔지니어 파견 요청) | 성공률·셋업 시간 목표 ⟨확인⟩, 오조작으로 잘못 저장된 레시피 0건 |
| 2027-10~12 | 확장 | 2차 셀 합류, 1차 셀 유형 확대 | 2차 장비군 1개 이상 착수 |

**단계 통과 결정**: 단계가 끝날 때 리드가 통과 기준과 결과를 정리하고, 셀 엔지니어의 품질 확인을 받아 월간 임원 보고에서 통과를 승인받겠습니다. 기준에 못 미치면 **보완**(기간 연장), **축소**(대상 유형·장비군 축소), **중단** 중 하나를 정해 [결정 기록](./decision-log.md)에 남깁니다. 파일럿을 통과하지 못한 장비군은 2차 확장의 근거로 쓰지 않습니다.

**2027년 말 목표**: 1차 장비군마다 대표 레시피 유형 1개 이상에서 **측정 위치·Align 셋업 구간을 반자동으로 수행**하고, 그 구간의 건당 셋업 시간을 ⟨확인⟩% 단축하는 것입니다. 레시피 전 과정 자동 생성은 2028년 이후 목표입니다.

| 3 | 공통 플랫폼 팀 개발 인력 배정 (본인 포함 2명, 교육도 이 2명이 담당) | 2026-12 |

| 6 | 엔지니어 PC용 설치형 프로그램 배포와 작업 녹화에 대한 보안 승인 범위 확정 | 2027-03 전 |

## 7. 위험과 대응 (요약)

| 위험 | 대응 |
|---|---|
| 현업 엔지니어가 AI·코드 특성에 익숙하지 않음 | 온보딩 8주 과정, 실습 중심 ([온보딩 학습 과정](./04-onboarding.md)) |
| 겸직이라 참여 시간 확보가 어려움 | 주 5시간(하루 1시간)을 기획안에 명시, 월간 보고에 참여 시간 기록 |
| 장비군마다 화면·절차가 크게 다름 | 공통 플랫폼과 장비별 절차를 분리, 1차는 3개 장비군으로 제한 |
| PoC에서 확인하지 못한 항목이 남음 (SecureVDI 조작, 작업 의미 파악·재현, 신규 파라미터 등록) | 1~2월에 플랫폼 팀이 사전 검증, 1차 구축 통과 기준에 반복 완주 포함 |
| Agent 오조작 | 위험 조작과 저장 전 엔지니어 승인, 즉시 중단 수단, 작업 전 원본 레시피 백업 |
