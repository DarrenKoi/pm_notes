# Auto Recipe Creation TF 구성 기획안

> Align Fail 자동 대응 PoC에서 얻은 공통 자산과 시사점을 바탕으로, MI 장비 레시피 셋업 자동화(ARC)를 공통 플랫폼 위에서 R&D MI 현업 엔지니어들과 함께 확장하고자 합니다.

## 요약

**2026 현황**: CD(Align Fail 자동 대응 Agent, Offline 테스트 중), Thickness(의뢰부터 Recipe 생성까지 ARC Pipeline), Inspection(의뢰서 DB화, Recipe RAG, NAND 1개 Tech에서 DRB 기반 ARC 생성)이 각자 추진 중. 공통 과제는 생성형 AI 모델에게 Recipe 작업 방식을 학습시키는 방법의 구체화와, Rule 기반 자동화, 이미지 처리(CV), ML/DL을 생성형 AI 모델과 함께 쓰는 구조

**출발점**: PoC(Align Fail 자동 대응)로 Agent가 Recipe를 다루는 두 가지 공통 방식 확보 (VLM, PyAutoGUI, Win32를 조합한 Computer Use, 장비 밖에서 Recipe 파일을 편집하는 생성). 현업 MI 엔지니어의 노하우를 AI가 쓰는 구조로 개발자가 구현하는 **두 역할의 유기적인 협업**이 필요하고, 조작, 모델 최적화와 운영, 녹화 DB 추출, 기술 부채 해소는 공통 플랫폼으로 풀 장비군 공통 과제. ARC를 위한 효율적인 작업 방법(자동화 방법, 사내 DB 테이블 등)은 주간 미팅에서 공유

**결론**: MI 장비 전반으로 ARC를 넓히려면 장비마다 한 사람이 처음부터 다 만드는 방식으로는 안 되고 **공통 플랫폼**을 만들어 개발(플랫폼 팀)과 장비 지식(장비군 담당)을 나눠 맡아야 함

**추진 방식**

| 단계 | 시기 | 대상 | 목표 |
|---|---|---|---|
| 1차: 선발대 | 2027 상반기 | CD-SEM, Thickness, Inspection 중점 운영 (2차 장비군은 인터뷰, Recipe Workflow 조사로 준비) | 장비군별 목표, 공통 플랫폼 설계 완성과 베타 테스트 |
| 2차: 영역 확장 | 2027 하반기부터 (6월 플랫폼 베타 배포 뒤) | 다른 MI 장비군 | 2차 장비군 본격 합류, 공통 플랫폼 위에서 녹화와 지식화 시작 |

- 선발대 지정 사유: CD-SEM의 Align Fail PoC(화면 인식, Align Key 탐색, 반자동 운영), Thickness의 기존 PyAutoGUI 자동화와 ARC Pipeline, Inspection의 의뢰서 DB와 Recipe RAG를 재사용할 수 있음
- 개발과 AI에 익숙하지 않은 엔지니어는 교육을 받으며 TF에 참여함. 교육 과정을 따로 두지 않고, 매주 미팅에서 개발 노하우를 공유하고 현재와 앞으로의 진행사항을 확인

**요청 사항 (2026-12)**

- ARC TF 구성 승인: 조직과 명단은 처음부터 전체로 승인, 초기 개발은 1차 장비군(CD-SEM, Thickness, Inspection) 위주로. 2027-01부터 운영
- 1차(선발대) CD-SEM, Thickness, Inspection 담당 엔지니어 장비군마다 1~2명 (참여 시간은 탄력적으로 운영)
- 2차 장비군(다른 MI 장비군) 담당 엔지니어 지정: 장비군마다 1~2명. 상반기는 인터뷰, Recipe Workflow 조사로 준비(작업 녹화 포함), 6월 베타 배포 확인 뒤 본격 참여
- 개발 인력 4명 지정: 백엔드 2, 프론트엔드 2 (1차 MI팀 현업 엔지니어의 개발 참여와 함께 공통 플랫폼 개발 약 5명 규모, 2027-01 합류)

**확인 필요 사항 (R&D MI H/W 담당자)**

- 장비 화면 녹화분 DB에 직접 접근할 수 있는지 확인 필요 (장비군 공통 과제 가운데 하나)
  - 가능하면: 녹화분을 바로 받아 써서 개발 속도가 빨라짐
  - 불가능하면: RCS에서 GUI 자동화로 녹화분을 내려받아야 함 (속도가 느리고 다운로드 자동화 작업 별도 필요)
- 스크린샷과 녹화 영상을 많이 쓰므로 스토리지 소모량이 매우 큼. 추후 스토리지 자산 확보가 필요함

**2027년 타겟**

| 시점 | 타겟 | 판정 |
|---|---|---|
| 2027 상반기 | 1차 장비군별 목표: CD-SEM **Align Fail 자동 대응 및 Recipe Tuning(이미지 변경) 구현**, Thickness **Film 10 Layer 이하 의뢰 Recipe 90% 이상 생성 자동화**, Inspection **전체 디바이스향 DRB 기반 ARC 확장(Optical Inspection 장비군)** (엔지니어 상주), **공통 플랫폼 설계 완성과 베타 테스트** | 2027-06 |
| 2027 연말 | 1차 장비군 셋업 절차, 노하우의 **지식 자산** 축적, 2차 장비군 여러 개가 공통 플랫폼 위에서 녹화 시작 | 2027-12 |

- 셋업 시간 단축은 2028 보조 단계부터, Agent가 레시피 셋업을 진행하는 자율 단계는 2029 타겟임
- 필요 자원: 공통 플랫폼 개발 약 5명 규모(지정 백엔드 2, 프론트엔드 2와 1차 MI팀 현업 엔지니어, TF 리드 별도), 담당 엔지니어(참여 시간은 탄력적으로 운영), 공통 프로젝트를 위한 HCP 환경 및 자원(현 H200 2장, 2027 하반기 4장 이상 확보), 영상 적재를 위한 별도 스토리지 DB

## 2026 ARC 추진 현황

MI 장비군 가운데 CD, Thickness, Inspection이 각자 ARC를 추진하고 있습니다. 진행 방식은 장비군마다 다르지만 남은 과제는 같습니다.

| 장비군 | 추진 현황 |
|---|---|
| CD | **Align Fail 자동 대응 Agent** 개발 진행 (Recipe Tuning 포함), 현재 Offline 테스트 중. 소형 VLM(Vision Language Model) 기반 장비 컨트롤(Computer-use) 기능 구현 |
| Thickness | 의뢰부터 Recipe 생성까지 **ARC Pipeline** 진행. DL 기반 Align Fail 대응 Offline 테스트 중. MI 장비군 중 가장 높은 자동화 구현 |
| Inspection | **DRB(Design Recipe Builder)**를 Tuning하는 방식으로 ARC 진행 중 (NAND Tech 1개 대상) |

### Lesson Learned

1. 생성형 AI 모델만으로 ARC 구현 어려움 (정밀 좌표 클릭, 셋업 절차, 결과 판단, 화면 조작 등의 문제)
2. Rule 기반 자동화, 컴퓨터 비전(CV), ML/DL을 생성형 AI 모델과 함께 쓰는 구조 필수
3. 생성형 AI 모델에게 Recipe 작업 방식을 어떻게 학습시킬지 구체화 필요

## 1. ARC 업무 전략 (PoC에서 확인한 것)

ARC는 처음부터 레시피 자동 생성을 목표로 했습니다. PoC로는 범위가 좁고 효과를 재기 쉬운 **Align Fail 자동 대응**을 골랐습니다. 이 PoC에서 특정 장비군에 묶이지 않고 레시피 자동 생성에 그대로 쓸 수 있는 공통 자산을 얻었고, MI 장비 전반으로 넓히려면 무엇이 필요한지에 대한 시사점도 얻었습니다.

### 얻은 자산 (장비군 공통)

| 확보한 것 | 내용 | ARC에서의 쓰임 |
|---|---|---|
| Agent가 Recipe를 다루는 방식: Computer Use | API 없는 장비에서 Agent가 Recipe를 다루는 여러 접근 방식을 시험. VLM(화면을 보고 다음 조작 판단), PyAutoGUI(정해진 순서의 키보드, 마우스 입력), Win32(창과 컨트롤 단위 조작)를 조합해 Computer Use 구현 | 장비군과 무관한 화면 조작 엔진 |
| 장비 밖에서 Recipe 파일을 편집해 생성 | 장비 화면 조작이 아닌, 외부에서 Recipe 파일을 편집해 작성. 장비 화면을 거치지 않아 조작 단계 축소. Recipe 파일 구조 해석 필요 | 화면 조작 없이 Recipe 생성. 장비별 파일 구조 해석이 필요해 장비군별 도구로 활용. 저장과 적용은 엔지니어 승인 |
| 최적화된 소형 모델 운영 | 기반기술센터에서 최적화된 소형 모델을 운영 | 자동화 작업에 함께 사용 |

Align Fail 대응의 세부 자산은 [PoC 자산과 남은 과제](./05-poc-assets.md)에 있으며 수치는 사내용 문서에만 둡니다.

### 시사점 1: 개발자와 현업 엔지니어, 두 역할의 유기적인 협업 필요

| 역할 | 하는 일 | 한쪽만 있으면 |
|---|---|---|
| 개발자 | 화면 인식, 조작 엔진, 안전 규칙, 모델 서빙과 평가 | 장비 화면과 셋업 절차를 몰라 무엇을 자동화할지 정하지 못함 |
| 현업 엔지니어 | Recipe 셋업 절차 정의, 성공 판정 기준, 실장비 검증, 결과 책임 | 화면 인식과 조작 엔진을 만들 수 없음 |

- 현업 MI 엔지니어의 업무 노하우와 Recipe 셋업 방식을 AI가 활용할 수 있는 구조로 개발자가 구현해야 함
- 다른 장비군에는 그 장비를 아는 개발자 부재. 장비군마다 같은 인력 확보 불가

### 시사점 2: ARC 공통 과제는 공통 플랫폼으로 대응

| 공통 과제 | 내용 | 공통 플랫폼에서 |
|---|---|---|
| Agent의 마우스, 키보드 조작 | 장비군마다 화면은 달라도 캡처, 입력, 즉시 중단은 같은 문제 | 조작 엔진을 플랫폼 팀이 한 번 만들고 모든 장비군이 같이 씀 |
| 효율적인 작업 방법 공유 | ARC에 쓸 수 있는 작업 방법(자동화 방법, 사내 DB 테이블 등)이 장비군마다 따로 있음 | 공통 플랫폼이 아닌 주간 미팅에서 공유 |
| AI 모델 최적화와 운영 유지 | 사내 VLM, OCR 서빙, 튜닝, 장애 대응, 버전 관리, 새 모델 벤치마크와 교체 | 모델 서빙과 평가를 플랫폼 팀이 한 번 만듦. 녹화본 평가 세트를 공통으로 두고 모델 교체는 측정으로 결정 |
| 녹화 DB 추출 | 녹화분 확보 경로가 정해져 있지 않음. 녹화분에서 Recipe 작업 내용을 추출하고 AI가 이해할 수 있게 라벨링하는 일은 장비를 아는 현업 엔지니어가 필요함 | H/W 담당자와 접근 경로를 확정하고 녹화분 수집을 플랫폼 기능으로 만듦. 작업 내용 추출과 라벨링은 장비군 담당 엔지니어가 맡음 |
| 기술 부채 해소 | Vibe Coding으로 원리 확인 없이 진행한 사항이 대부분임 | 플랫폼 팀이 PoC 코드의 원리를 확인하고 재사용, 고쳐 쓰기, 버림으로 정리 (2027-06 요소 목록) |

- 같은 일을 장비군마다 반복하면 확장 불가

### 시사점 3: 별도 운영 PC 대신 엔지니어 PC에 설치

처음에는 Agent 전용 PC를 따로 마련해 그 PC에서 운영하려고 했습니다. 그러나 사무 PC를 계속 늘리는 방식에는 제약이 많아 공통 플랫폼을 개발해 엔지니어 본인 PC에 설치하는 방향으로 바꿨습니다.

| 별도 PC 방식의 제약 | 엔지니어 PC 설치형에서 |
|---|---|
| 장비군, 엔지니어가 늘 때마다 PC 추가 확보 절차를 거쳐야 함 (자산 신청, 자리 확보 등) | 이미 사용 중인 PC에 S/W를 설치하는 형태 |
| PC마다 장비 접속 권한(RCS, SecureVDI)을 따로 받아야 함 | 엔지니어가 이미 가진 계정과 접속 경로를 그대로 씀. 보안 승인은 설치형 프로그램 하나로 받음 |
| 운영 PC 별도 관리로 인한 부담 | 사내 배포로 일괄 갱신 |
| 엔지니어가 결과를 보려면 그 PC 앞에 가거나 원격으로 따로 들어가야 함. 아무도 보지 않는 화면이 생김 | Agent를 엔지니어가 보는 화면에서 운영, 엔지니어가 즉시 확인, 중단. 엔지니어가 원할 때 Agent를 실행하고 작업에 대한 책임을 짐 (Human on Command) |
| 장비별로 따로 꾸리면 PC마다 자동화가 달라짐 | 모든 장비군이 같은 플랫폼을 씀 |
| (변경 시 부작용) | Agent가 엔지니어 화면을 일시적으로 제어. 화면 입력 몇 초 동안은 엔지니어가 PC를 쓸 수 없음. 관찰과 판단은 백그라운드로 가볍게 돌리고 입력은 제어권 인계(알림 → 인계 → 입력 → 반환)로 함 |

### 결론: MI 장비 전반의 ARC는 공통 플랫폼으로

- ARC를 하기 위한 필수 요소들(화면 인식, 조작 엔진, 안전 규칙, 모델 서빙과 평가, 녹화분 수집)은 **공통 플랫폼으로 해결**
- ARC를 위한 효율적인 작업 방법(자동화 방법, 사내 DB 테이블 등)은 **주간 미팅**에서 공유
- 장비 노하우와 판정은 **장비군 담당자**(MI 엔지니어)의 역할
- 개발자가 장비를 다 알 필요도, 엔지니어가 개발을 다 할 필요도 없게 만드는 것이 TF의 목적임

### 현업이 이미 만든 자동화 (Thickness)

- Thickness 담당자들이 PyAutoGUI 기반으로 자동화해 둔 작업이 많음. 고정 좌표와 정해진 순서로 반복 입력을 처리하는 방식임
- 검토 과제: 이 PyAutoGUI 자동화와 VLM 기반 방식을 어떻게 섞어 쓸지 정해야 함
  - 정해진 순서의 반복 입력: 검증된 PyAutoGUI 스크립트를 그대로 재사용
  - 화면 인식과 판단이 필요한 구간 (위치 확인, 예외 화면, 막힘): VLM이 맡음
  - PyAutoGUI 스크립트 앞뒤에 VLM 화면 확인을 붙여 화면이 예상과 다르면 멈추게 함
- 2027-01 합류 첫 달에 Thickness 기존 스크립트를 목록화하고 2027-06 요소 목록에 혼합 방식을 반영함

**아직 확인하지 못한 것**과 확인 시점:

## 2. 레시피 셋업의 문제

### 문제

- 레시피 셋업은 숙련 엔지니어가 원격 제어 화면에서 마우스와 키보드로 하는 반복 수작업임. 측정 위치를 잡을 때 측정, 실패, 재조정을 되풀이함
- 노하우가 개인에게 있음. 담당자가 바뀌면 지식이 사라지고 사람마다 품질이 다름
- 관리 장비가 늘어나거나 개발 제품이 증가하면 셋업 인력도 같은 비율로 늘어나야 하나, 이 구조로는 한계가 있음
- 측정 중 Align Fail(정렬 실패) 알람이 나면 엔지니어가 원격으로 위치를 다시 잡을 때까지 장비가 멈춤

### 안 하면 생기는 일

- ⟨확인: 신규 제품, 공정 도입 때 레시피 셋업 대기로 늦어지는 기간⟩
- ⟨확인: 장비군별 레시피 셋업에 쓰는 엔지니어 시간 (월 기준)⟩
- ⟨확인: Align Fail 알람으로 멈추는 장비 시간 (월 기준)⟩
- 장비군마다 따로 자동화를 시도하면 공통 과제(조작, 모델 운영, 녹화분 확보)와 안전 장치를 매번 새로 풀게 되고, 효율적인 작업 방법도 장비군 사이에 공유되지 않음

## 3. 추진 방향: 선발대에서 영역 확장으로

### 핵심 개발 방향

자동화 대상 구간의 실측값과 나머지 현재 값은 장비군마다 합류 뒤 기준선 측정 기간(선발대 2027-02, 2차 2027-08)에 담당 엔지니어가 직접 측정해 확정하겠습니다. 측정하기 전에는 목표를 숫자로 정하지 않습니다.

**자동화 측정 기준**: ARC가 얼마나 넓게 쓰였는지는 Recipe 의뢰 수 기준으로, Recipe 하나에 Agent가 얼마나 개입했는지는 Recipe별 비율로 표기합니다.

- ARC 적용 비율 = ARC를 적용한 Recipe 수 / 같은 기간 Recipe 의뢰 수 (%)
- Agent 개입 범위 = Agent가 진행한 셋업 단계 수 / 그 Recipe의 전체 셋업 단계 수 (Recipe별 %)
- 작업 경과 시간: 셋업 시작부터 끝까지 걸린 시간 (셋업 시간 단축 지표에 씀)

**측정 규칙** (기준선과 이후 측정을 같은 조건으로 비교하기 위해 기준선 측정 양식에 고정)

- 대상: 장비군마다 정한 대표 레시피 유형 1개. 전체 셋업이 아닌 **자동화 대상 구간(측정 위치, Align 셋업)** 의 시작과 끝을 정해 측정
- 포함: 그 구간 안의 실패, 재작업, 수동 인계 시간. 승인 대기 시간은 별도 기록
- 단계 구분: Recipe별 셋업 단계는 절차서의 의미 단계를 기준으로 셈. 반드시 거치는 엔지니어 승인(저장 전 등)은 Agent 진행에서 빼지 않음

### ARC 적용 비율과 Agent 개입 범위가 오르면 회사에 무엇이 남는가

```
레시피 셋업 수요(건/월) × ARC 적용 비율 × 건당 셋업 시간 × Agent 개입 범위
  → 엔지니어 손을 거치지 않은 셋업 시간 (월 ⟨확인⟩시간)
  → 신규 제품, 공정 도입 때 셋업 대기 단축, 엔지니어가 분석, 개선 업무로 이동
  → 장비가 늘어도 셋업 인력을 같은 비율로 늘리지 않아도 됨
```

- 가정: ⟨확인: 장비군별 월 셋업 수요와 증가 추세⟩. 셋업 수요가 장비, 제품 수와 함께 늘어야 "인력이 비례해야 한다"는 주장이 성립함

### 공통 플랫폼 구조

공통 플랫폼은 Computer Use 기반으로, RAG에 쌓은 엔지니어 지식에서 Recipe 셋업 Workflow를 만들고 Agent가 그 Workflow를 지키는지 확인합니다. 틀리면 엔지니어가 개입해 고치고, 고친 내용은 다시 RAG에 저장해 다음 Workflow를 보완합니다.

| 단계 | 하는 일 | 누가 |
|---|---|---|
| ① 녹화 추출, 라벨링 | 녹화 비디오에서 작업 내용을 추출하고, 현업 엔지니어가 라벨링 | 추출은 플랫폼, 라벨링은 현업 엔지니어 |
| ② RAG 저장 | 라벨링한 내용을 Recipe 셋업 지식 DB(절차, 노하우, 결정 지점)로 저장 | 플랫폼 |
| ③ Workflow 생성, 실행 | RAG에서 Recipe 셋업 Workflow를 만들고 Agent가 Computer Use(VLM, PyAutoGUI, Win32)로 실행 | 플랫폼, 엔지니어 검토와 승인 |
| ④ 준수 확인, 수정 | Agent가 Workflow를 지키는지 확인(생성형 AI + Rule, CV, ML/DL). 틀리면 엔지니어가 개입해 수정하고, 수정 내용은 ②로 돌아가 RAG를 보완 | 플랫폼, 현업 엔지니어 |

- **공통 플랫폼 팀이 만드는 것**: 녹화 내용 추출, RAG DB와 Workflow 생성, Computer Use 실행 엔진, 준수 확인과 즉시 중단
- **현업 엔지니어가 하는 것**: 추출 내용 라벨링, Workflow 검토와 승인, 실행 중 개입과 수정, 녹화본으로 미리 실험, 실전 사용 후 개발자에게 피드백 (개발자가 플랫폼에 반영). 진행사항과 피드백은 주간 미팅에서 개발자와 현업 엔지니어가 함께 공유
- **범위 밖**: 외부 Recipe 파일 편집은 장비마다 파일 구조가 달라 장비군별 도구로 진행하고 공통 플랫폼에는 넣지 않음. 장비별 작업 공간을 백엔드와 화면에 따로 두면 장비군 수만큼 플랫폼이 커지기 때문
- AI가 정한 다음 조작은 서버의 규칙 확인이 허용 여부를 다시 판단하고, 정해진 조작 단위만 실행함. 결과가 불명확하거나 화면이 예상과 다르면 멈추고 엔지니어를 부름
- 2027년에는 1차 장비군의 승인된 조작(장비군별 목표)만 자동 운영하고, 그 밖에는 화면 입력 없이 "다음에 할 일"을 제안만 해서 판단 정확도를 먼저 검증함. 일반 화면 입력은 2028 보조 단계부터

상세 설계는 [공통 플랫폼 기술 설계](./07-platform-architecture.md)에 있습니다.

### 자동화 수준과 안전 원칙

- **반자동(Supervised Autonomy)이 원칙임**: Agent가 조작하고, 위험 조작(측정 실행, 삭제, 모드 변경)과 레시피 저장, 적용 직전에는 엔지니어가 승인
- **Align Fail 자동 대응도 엔지니어가 자리에 있는 것이 전제임**: Agent는 엔지니어 본인 PC에서 관찰과 판단을 백그라운드로 하고, 화면에 입력하는 몇 초 동안만 엔지니어에게서 제어권을 넘겨받음(알림 → 인계 → 입력 → 결과 확인 → 반환). 엔지니어가 마우스를 건드리면 즉시 멈춤. 결과의 책임은 담당 엔지니어에게 있음. 엔지니어가 없는 무인 운영은 목표가 아님
- **1차 장비군 목표의 자동화는 승인된 예외임**: 허용 조작은 장비군마다 승인받은 범위로 한정함. CD-SEM Align Fail은 위치 재조정, 재측정 재시도, Recipe 이미지 변경. Thickness는 Recipe 생성, Inspection은 DRB 튜닝 기반 Recipe 생성. 만들거나 고친 Recipe의 저장과 적용은 엔지니어 승인 뒤에만 함. 삭제, 모드 변경은 계속 금지. 인식이 불확실하거나 화면이 예상과 다르면 Agent가 스스로 멈추고 엔지니어를 부름
- **자동 전환 승인**: 반자동 운영 실적을 리드가 정리하고, 담당 엔지니어 확인을 거쳐 월간 보고에서 장비별로 승인받음
- 레시피 셋업의 완전 자동은 반복 검증과 자체 중단 기록까지 통과한 레시피 유형만 단계 승인을 거쳐 검토함

### TF 구성

| 구분 | 구성 | 맡는 일 | 합류 |
|---|---|---|---|
| TF 리드 + 공통 플랫폼 팀 | TF 리드(ARC TF 총괄)와 공통 플랫폼 개발 약 5명 규모: 백엔드 2, 프론트엔드 2, 1차 MI팀 현업 엔지니어가 개발에 함께 투입 | 화면 인식, 조작 엔진, 안전 규칙, 승인 화면, LLMOps, 녹화 DB 추출, 교육 | 2027-01 |
| CD-SEM 담당 (선발대) | MI 엔지니어 1~2명 | 장비별 레시피 절차, 성공 판정 기준, 현장 검증. 목표: Align Fail 자동 대응 및 Recipe Tuning(이미지 변경) 구현 | 2027-01 |
| Thickness 담당 (선발대) | MI 엔지니어 1~2명 | 위와 같음. 기존 PyAutoGUI 자동화와 ARC Pipeline 공유. 목표: Film 10 Layer 이하 의뢰 Recipe 90% 이상 생성 자동화 | 2027-01 |
| Inspection 담당 (선발대) | MI 엔지니어 1~2명 | 위와 같음. 의뢰서 DB와 Recipe RAG 공유. 목표: 전체 디바이스향 DRB 기반 ARC 확장(Optical Inspection 장비군) | 2027-01 |
| 다른 MI 장비군 담당 (2차) | 장비군마다 MI 엔지니어 1~2명 | 위와 같음. 공통 플랫폼을 실제로 적용하는 첫 대상 | 2027-01 인터뷰, Recipe Workflow 조사, 2027-07 본격 참여 |

- **공통 플랫폼**: 모든 장비군이 함께 사용. 장비마다 엔진을 새로 만들지 않음
- **장비군 담당**: MI 현업 엔지니어 1~2명으로 구성. 그 장비의 레시피 절차 정의, 성공 판정 기준, 현장 검증을 맡음
- **2차 장비군 담당**: 2026-12에 선발대와 함께 지정. 상반기에는 인터뷰, Recipe Workflow 조사로 준비하고(요구사항 정리), 6월 베타 배포 확인 뒤 교육을 받으며 화면 영역 지도와 절차를 정의함
- **인프라(GPU, VLM 서빙)**: 필요 시점에 합류. 장비 벤더는 필요할 때 자문

**개발 인력 배분 (TF 리드 + 지정 4명 + 1차 MI팀 현업 엔지니어)**

개발 4명(백엔드 2, 프론트엔드 2)은 임원, 팀장급에서 지정을 요청합니다. 장비군 공통 과제(조작, 모델 운영, 녹화 DB 추출, 기술 부채 해소)를 나눠 맡을 개발 인력이 필요합니다.

| 사람 | 맡는 일 |
|---|---|
| TF 리드 | 전체 설계, 모든 갈래 관여, TF 운영, 교육 |
| 백엔드 (2명) | 서버(판단, 규칙 확인 API, 저장소), 녹화 DB 추출 알고리즘, 데이터 파이프라인, 평가 세트, LLMOps(HCP 장애 대응, 신규 오픈웨이트 모델 벤치마크, 교체 판단) |
| 프론트엔드 (2명, 클라이언트와 화면) | 엔지니어 PC 설치형 에이전트(캡처, 입력, 즉시 중단, 제어권 인계), Agent와 대화하며 작업하는 챗 UI, 승인 화면과 절차서 검토 화면, 배포 |

| 시기 | TF 리드 | 백엔드 (2명) | 프론트엔드 (2명) |
|---|---|---|---|
| 2027 상반기 (선발대) | 플랫폼 설계, 1차 장비군 목표 조율, 주간 미팅 진행 | 녹화 DB 추출, 서버 수집, 평가 세트, 새 모델 벤치마크 | 설치형 에이전트, 베타 배포 |
| 2027 하반기 (확장) | 선발대 절차화, 지식 자산, 주간 미팅 진행 | 지식 자산 DB, 돌파구 추천 검색, LLMOps | 상시 관찰 모드, 2차 장비군 화면 영역 지도 도구, 승인 화면 |

- LLMOps는 늘 손이 가는 일은 아니지만 주기적으로 챙겨야 함(HCP 다운, Hugging Face 신규 오픈웨이트 모델). 예고 없이 생기는 일이라 TF 리드가 맡으면 플랫폼 설계 일정이 끊김. 그래서 데이터와 묶어 백엔드가 맡음
- 지정 개발 인력은 개인 과제와 겸직함. 1차 MI팀 현업 엔지니어는 자기 장비 절차 정의와 함께 플랫폼 개발에도 투입됨
- 지정이 일부만 되면 프론트엔드를 먼저 채움. 6월 베타가 2차 본격 참여의 전제라 일정의 병목임. 백엔드 일은 TF 리드가 최소로 유지(PoC 서버 그대로, LLMOps는 장애 대응만, 2차 녹화는 DB로 받을 수 있는 범위로)
- 상반기에는 장비군별 목표와 플랫폼 베타를 우선함. 관찰과 지식화는 녹화 축적까지만 하고, 상시 관찰 모드는 3분기 초로 미룸
- 인력이 늘면 상시 관찰 모드와 채팅을 먼저 당김
- 인력이 모자라면 채팅 기능(6월, 12월 목표 밖)을 먼저 미루고, 다음으로 2차 장비군 합류 순서를 나눔

역할 분담은 [참여 팀과 역할](./02-roles-and-teams.md)에 있습니다.

## 6. 교육하며 운영

현업 엔지니어 대부분은 장비와 레시피는 잘 알지만 개발과 AI에는 익숙하지 않습니다. 교육 과정을 따로 두지 않고 **매주 미팅에서 개발 노하우를 공유하고 현재와 앞으로의 진행사항을 확인하면서 TF를 운영**합니다.

| 형태 | 주기 | 내용 | 얻는 것 |
|---|---|---|---|
| 주간 미팅 | 매주 | 개발자와 현업 엔지니어. 개발 노하우 공유(AI와 Agent 기초, 자동화 방법, 사내 DB 테이블 등), 장비군별 현재 진행사항과 앞으로 할 일 확인, 막힌 지점 질의 | 엔지니어가 자기 장비 절차를 Agent 실행 형태로 정의, 실전 피드백을 개발에 반영 |
| 기준선 측정 | 합류 첫 달 (선발대 2027-01~02, 2차 2027-07~08) | 현재 셋업 시간과 단계 측정, 대표 레시피 유형 선정, 작업 녹화 시작 | 효과 지표의 기준선 확보 |

- 목표는 AI 개발자를 만드는 것이 아니라, 엔지니어가 **자기 장비 절차를 Agent가 실행할 수 있는 형태로 정의하고 결과를 판정**할 수 있게 하는 것임
- 강사는 TF 리드와 공통 플랫폼 팀이 맡음. 교육 시간은 개발 인력 배분에 포함함

노하우 공유 주제와 기준선 측정 양식은 [주간 미팅과 노하우 공유](./04-onboarding.md)에 있습니다.

## 7. 일정

2027년은 상반기 선발대, 하반기 영역 확장으로 진행합니다. 상반기에 **1차 장비군별 목표(CD-SEM Align Fail 자동 대응 및 Recipe Tuning(이미지 변경) 구현, Thickness Film 10 Layer 이하 의뢰 Recipe 90% 이상 생성 자동화, Inspection 전체 디바이스향 DRB 기반 ARC 확장(Optical Inspection 장비군))를 달성하면서 공통 플랫폼 설계를 완성하고 베타로 운영**합니다. Align Fail은 일회성 시제품이 아니라 플랫폼 부품(화면 캡처, 화면 영역 지도, 입력 실행기, 자체 중단, 실행 로그)으로 만들고, 그 과정에서 필요했던 요소를 장기 계획에 반영합니다.

**장비군별 판정 지표 (6월 목표 달성 확인)**

| 장비군 | 지표 | 기준 |
|---|---|---|
| CD-SEM | 반자동 기간 제안 적중률 (엔지니어가 확정한 이미지 변경 가운데 Agent 제안과 같은 비율), 자동 기간 이미지 변경 뒤 재측정 성공률 | ⟨확인⟩% 이상, 장비별 최소 ⟨확인⟩건, 오측정 0건 |
| Thickness | 자동화 비율 (Film 10 Layer 이하 대상 의뢰 가운데 ARC Pipeline이 만든 Recipe를 엔지니어가 수정 없이 승인한 비율) | 90% 이상, 대상 의뢰 최소 ⟨확인⟩건 |
| Inspection | DRB 기반 ARC 적용 디바이스 비율 (전체 디바이스 가운데 DRB로 Recipe를 만든 디바이스 비율), 생성 Recipe를 엔지니어가 수정 없이 승인한 비율 | ⟨확인⟩% 이상 |

- 수치 기준(⟨확인⟩)은 2027-01 말까지 PoC와 장비군별 현황 실측을 근거로 확정
- 자동 전환은 반자동 운영 실적을 담당 엔지니어가 확인한 뒤 월간 보고에서 장비군별로 승인받음
- 보고 대표 숫자: 장비군별 목표 달성 비율
- 2027-06 산출물: **요소 목록**. 세 장비군의 상반기 작업에 쓰인 요소를 재사용, 고쳐 쓰기, 버림으로 나누고 플랫폼 기능에 대응시켜 하반기와 2028 계획의 입력으로 씀

- 엔지니어가 플랫폼에서 Agent와 대화하는 채팅 기능은 2028-01~03으로 넘김

### 목표 달성 확인과 2028 진입 조건

- 2차 본격 참여(2027-07)는 6월 베타 배포 확인을 거쳐야 함. 못 미치면 본격 참여를 늦추고 선발대에서 보완함. 2차 담당은 그동안 작업 녹화를 계속함
- 2028 보조 단계(반복 입력 대행)로 넘어가려면 두 가지가 필요함
  - 12월 목표 달성
  - 공통 기술, 안전 요건 충족: 입력 실행기가 실장비에서 의도한 조작만 하고, 불확실할 때 스스로 멈추는 것이 운영 기록으로 확인됨
- 장비군별 목표는 별도 성과 과제이므로, 미달이어도 위 두 조건을 채우면 2028 진입을 막지 않음. 미달분은 보완, 축소 결정 대상이 됨

**단계 통과 결정**: 목표 달성 확인 시점마다 리드가 기준과 결과를 정리하고 담당 엔지니어의 품질 확인을 받아 월간 보고에서 승인받겠습니다. 기준에 못 미치면 **보완**(기간 연장), **축소**(대상 유형, 장비군 축소), **중단** 중 하나를 정해 [결정 기록](./decision-log.md)에 남깁니다.
