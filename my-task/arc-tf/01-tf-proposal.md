# ARC TF 구성 기획안

> 장비 레시피(Recipe) 셋업을 컴퓨터 사용(Computer-use) Agent로 자동화하려고, MI 현업 엔지니어와 공통 플랫폼 팀을 묶은 TF를 2027년 1월부터 운영하겠다는 제안.

## 한 줄 요청

**2027년 1월부터 ARC TF를 구성하는 것을 승인해 주시고, 장비군별 MI 엔지니어가 겸직으로 참여하는 것(주 ⟨확인: N⟩시간)을 허락해 주십시오.**

## 1. 왜 해야 하는가

### 문제

- 레시피 셋업은 숙련 엔지니어가 원격 제어 화면에서 마우스와 키보드로 하는 반복 수작업이다. 측정 위치를 잡을 때는 측정, 실패, 재조정을 되풀이한다.
- 노하우가 개인에게 있다. 사람이 바뀌면 지식이 사라지고, 사람마다 품질이 다르다.
- 장비가 늘어나면 셋업 인력도 같은 비율로 늘어야 한다. 이 구조로는 규모를 키울 수 없다.

### 안 하면 생기는 일

- ⟨확인: 신규 제품·공정 도입 때 레시피 셋업 대기로 늦어지는 기간⟩
- ⟨확인: 장비군별 레시피 셋업에 쓰는 엔지니어 시간 (월 기준)⟩
- 장비군마다 따로 자동화를 시도하면 화면 인식, 조작, 안전 장치를 매번 새로 만들게 된다.

### 효과

| 효과 | 측정 지표 | 현재 | 목표 |
|---|---|---|---|
| 셋업 시간 단축 | 레시피 1건 셋업 소요 시간 | ⟨확인: 셀별 실측⟩ | ⟨확인⟩% 단축 |
| 사람 개입 감소 | 1건당 엔지니어 개입 횟수 | ⟨확인⟩ | ⟨확인⟩ |
| 품질 균일화 | 셋업 뒤 첫 측정 성공률 | ⟨확인⟩ | ⟨확인⟩ |
| 지식 자산화 | 절차서로 정리된 레시피 유형 수 | 0 | 장비군마다 1개 이상 |
| 확장성 | 새 장비군 합류에 드는 기간 | — | ⟨확인⟩ |

현재 값은 TF 온보딩 기간(2027-01~02)에 셀 엔지니어가 직접 측정해 채운다. 측정하기 전에는 목표를 숫자로 약속하지 않는다.

**측정 규칙** (기준선과 파일럿을 같은 조건으로 비교하려고 온보딩 측정 양식에 고정한다)

- 대상: 셀마다 정한 대표 레시피 유형 1개. 전체 셋업이 아니라 **자동화 대상 구간(측정 위치·Align 셋업)** 의 시작과 끝을 정해 잰다.
- 포함: 그 구간 안의 실패·재작업·수동 인계 시간. 승인 대기 시간은 따로 적는다.
- 개입 횟수: 반드시 거치는 승인(저장 전 등)은 세지 않고, **예정에 없던 개입**만 센다.

### 셋업 시간이 줄면 회사에 무엇이 남는가

```
레시피 셋업 수요(건/월) × 건당 엔지니어 투입 시간 감소분
  → 회수되는 엔지니어 시간 (월 ⟨확인⟩시간)
  → 신규 제품·공정 도입 때 셋업 대기 단축, 엔지니어가 분석·개선 업무로 이동
  → 장비가 늘어도 셋업 인력을 같은 비율로 늘리지 않아도 됨
```

- 가정: ⟨확인: 장비군별 월 셋업 수요와 증가 추세⟩. 셋업 수요가 장비·제품 수와 함께 늘어야 "인력이 비례해야 한다"는 주장이 성립한다.
- Align Fail PoC의 효과(장비 가동 시간 회수)는 운영 중 정렬 실패를 대응한 효과다. 신규 레시피 셋업의 효과로 옮겨 쓰지 않는다.

## 2. 이미 확보한 것 — 1차 PoC (Align Fail 대응 자동화)

ARC는 처음부터 레시피 자동 생성을 목표로 했다. 1차 PoC로는 범위가 좁고 효과를 재기 쉬운 **Align Fail(정렬 실패) 무인 대응**을 골랐다. 이 PoC에서 레시피 자동 생성에 그대로 쓸 기반을 검증했다.

| 확보한 것 | 레시피 자동 생성에서의 쓰임 |
|---|---|
| 사내 인프라에서 화면 이해 모델(VLM·OCR)을 자체 운영 | 외부 API 없이 화면 이해 |
| 표준 컴포넌트가 아닌 계측 화면에서도 대략 위치 → 정밀 좌표 → OCR 확인 순서로 클릭 | API 없는 장비 화면 조작 |
| VLM은 "어디를 볼지", CV는 "정확히 어디인지"를 맡는 역할 분리 원칙 | 측정 위치·Align Key 등록의 정확도 |
| 최근 성공 사례를 모은 기준 이미지로 Align Key 탐색 정확도 개선 (오프라인 평가 기준) | 레시피 Align 셋업 |
| 실장비 반자동 운영: 위치 재조정은 자동, 최종 확정은 엔지니어 | TF의 안전 원칙 |
| 엔지니어 작업 녹화 → 조작 타임라인 → 한국어 절차서 | 장비별 레시피 절차 정의 |

상세 목록은 [PoC 자산과 남은 과제](./05-poc-assets.md)에 있다. 수치는 사내용 문서에만 둔다.

**PoC로 확인한 것**: API 없는 장비 화면을 보고 조작할 수 있다는 것, 오프라인 평가에서 Align Key를 찾을 수 있다는 것.

**아직 확인하지 못한 것**:

- 현장 통합의 신뢰성: 실알람 첫 완주, Align Key 탐색의 실장비 검증이 남아 있다.
- 실행 엔진: 절차를 실행하는 엔진은 아직 데모 단계다. 레시피 셋업에 쓰려면 제품 수준으로 만들어야 한다.
- 신규 등록: 기존 Key를 찾는 능력과 새로 등록할 좋은 위치를 고르는 능력은 다르다. 후자는 PoC에서 다루지 않았다.
- 여러 장비 적용: 장비군마다 다른 화면과 레시피 절차를 담을 수 있느냐. 이것은 도메인 지식을 가진 현업 엔지니어 없이는 풀 수 없다.

앞의 세 가지는 플랫폼 팀이, 마지막은 셀이 푼다. 그래서 TF가 필요하다.

## 3. 무엇을 하는가 — 범위

| 구분 | 내용 |
|---|---|
| 최종 목표 | 신규 레시피 셋업의 전 과정 자동화: 생성 → 측정 위치·Align Key 등록 → 파라미터 → 검증 측정 → 저장 |
| 1차 범위 | 시행착오가 가장 많은 **측정 위치·Align 셋업 구간** |
| 대상 장비 | 1차: CD-SEM/VeritySEM + ⟨확인: 장비군 1~2개⟩. 2차: 나머지 MI 장비군 |
| 1차에서 사람이 맡는 것 | 레시피 생성과 기본 정보 입력, 파라미터 설정, 검증 측정 판정, 저장. Agent는 그 사이의 측정 위치·Align 셋업 구간을 맡는다 |
| 자동화 수준 | **반자동(Supervised Autonomy)**: Agent가 조작하고, 위험 조작(측정 실행, 삭제, 모드 변경)과 레시피 저장·적용 직전에는 엔지니어가 승인한다. 완전 자동은 반복 검증과 안전 중단 기록까지 통과한 레시피 유형만 단계 승인을 거쳐 검토한다 |
| 제외 | 장비 유지보수, 하드웨어 제어, 장비 내부 소프트웨어 설치 |

## 4. 어떻게 하는가 — TF 구성

```
                  ┌──────────────────────────────┐
                  │  TF 리드 (본인)               │
                  │  + 공통 플랫폼 팀              │
                  │  화면 인식·조작 엔진·안전 규칙  │
                  │  승인 화면·VLM 연동·교육       │
                  └──────────────┬───────────────┘
           ┌─────────────────────┼─────────────────────┐
   ┌───────┴───────┐     ┌───────┴───────┐     ┌───────┴───────┐
   │ 1차 셀 A       │     │ 1차 셀 B       │     │ 2차 셀들        │
   │ CD-SEM/Verity │     │ ⟨확인: 장비군⟩ │     │ 나머지 장비군   │
   │ MI 엔지니어   │     │ MI 엔지니어   │     │ 학습·데이터 준비│
   └───────────────┘     └───────────────┘     └───────────────┘
```

- **공통 플랫폼**은 모든 장비군이 같이 쓴다. 장비마다 엔진을 새로 만들지 않는다.
- **장비군별 셀**은 MI 현업 엔지니어 1~2명으로 구성한다. 그 장비의 레시피 절차 정의, 성공 판정 기준, 현장 검증을 맡는다.
- **2차 셀**도 1월에 함께 합류한다. 1차 기간에는 학습을 받고, 자기 장비 작업을 녹화해 절차서로 정리한다. 플랫폼이 준비되면 바로 들어온다.
- 인프라(GPU·VLM 서빙)는 필요해지면 합류하고, 장비 벤더는 필요할 때 자문을 받는다.

역할 분담은 [참여 팀과 역할](./02-roles-and-teams.md)에 있다.

## 5. 타임라인

| 시기 | 단계 | 하는 일 | 통과 기준 |
|---|---|---|---|
| 2026-11 | 기획 | 이 기획안 작성, 1차 장비군 후보 협의 | 기획안 완성 |
| 2026-12 | 승인 | 임원 보고, TF 구성 승인, 참여 엔지니어 지정 | 승인과 명단 확정 |
| 2027-01~02 | 온보딩 | 학습 과정, 셀별 현재 셋업 시간 측정, 대표 레시피 유형 선정, 성공 이미지 수집 시작. 플랫폼 팀은 PoC 남은 일 정리와 실행 엔진 작업 | 셀마다 기준선과 대상 유형 확정 |
| 2027-03~06 | 1차 구축 | 실행 엔진 제품화, 측정 위치·Align 셋업 기능 + 1차 셀 절차 정의, 오프라인·비생산 검증 | 1차 셀마다 대표 유형 1개를 비생산 환경에서 ⟨확인: N⟩회 연속 완주, 실패한 시도는 모두 안전하게 중단 |
| 2027-07~09 | 파일럿 | 1차 장비군 실장비 파일럿 (필요하면 셀 엔지니어 파견 요청) | 성공률·셋업 시간 목표 ⟨확인⟩, 오조작으로 잘못 저장된 레시피 0건 |
| 2027-10~12 | 확장 | 2차 셀 합류, 1차 셀 유형 확대 | 2차 장비군 1개 이상 착수 |

**단계 통과 결정**: 단계가 끝날 때 리드가 통과 기준과 결과를 정리하고, 셀 엔지니어의 품질 확인을 받아 월간 임원 보고에서 통과를 승인받는다. 기준에 못 미치면 셋 중 하나를 정해 [결정 기록](./decision-log.md)에 남긴다: **보완**(기간 연장), **축소**(대상 유형·장비군 줄이기), **중단**. 파일럿을 통과하지 못한 장비군은 2차 확장의 근거로 쓰지 않는다.

**2027년 말 목표**: 1차 장비군마다 대표 레시피 유형 1개 이상에서 **측정 위치·Align 셋업 구간을 반자동으로 수행**하고, 그 구간의 건당 셋업 시간을 ⟨확인⟩% 줄인다. 레시피 전 과정 자동 생성은 2028년 이후 목표다.

|---|---|---|

| 3 | 공통 플랫폼 팀의 개발·교육 인력 배정 (⟨확인: 인원⟩) | 2026-12 |
| 4 | 기존 사내 추론 인프라를 TF 실습·검증에 쓰는 것을 보장. 추가 비용이 생기면 승인할 주체 지정 | 2027-01 전 |
| 5 | 비생산 검증에 쓸 장비 시간이나 테스트 환경 ⟨확인⟩ | 2027-03 전 |
| 6 | 장비 PC 화면 조작과 작업 녹화에 대한 보안 승인 범위 확정 | 2027-03 전 |
| 7 | 파일럿 기간 셀 엔지니어 파견 (필요하면) | 2027-06 |

## 7. 위험과 대응 (요약)

| 위험 | 대응 |
|---|---|
| 현업 엔지니어가 AI·코드 특성에 익숙하지 않음 | 온보딩 8주 과정, 실습 중심 ([온보딩 학습 과정](./04-onboarding.md)) |
| 겸직이라 참여 시간이 확보되지 않음 | 주 N시간을 기획안에 명시, 월간 보고에 참여 시간 기록 |
| 장비군마다 화면·절차가 크게 다름 | 공통 플랫폼과 장비별 절차를 분리, 1차는 2~3개 장비군으로 제한 |
| PoC가 현장에서 아직 검증되지 않음 (실알람 완주, 실장비 탐색, 실행 엔진) | 1~2월에 플랫폼 팀이 정리, 1차 구축 통과 기준에 반복 완주를 넣음 |
| Agent 오조작 | 위험 조작과 저장 전 엔지니어 승인, 즉시 중단 수단, 작업 전 원본 레시피 백업 |
