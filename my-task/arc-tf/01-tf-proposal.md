# Auto Recipe Creation TF 구성 기획안

> Align Fail 자동 대응 PoC를 혼자 진행하며 얻은 성과와 시사점을 바탕으로, MI 장비 레시피 셋업 자동화(ARC)를 공통 플랫폼 위에서 R&D MI 현업 엔지니어들과 함께 확장하고자 합니다.

## 요약

**출발점**: PoC(Align Fail 자동 대응)로 API 없는 장비를 사내 AI로 읽고 조작하는 기반 확보. 동시에 이 일에는 **개발자와 현업 엔지니어 두 역할이 동시에 필요**하고, 모델 최적화와 운영, 최신 VLM 적용 테스트, 녹화 DB 추출까지 혼자 맡기에는 시간 부족

**결론**: MI 장비 전반으로 ARC를 넓히려면 장비마다 한 사람이 처음부터 다 만드는 방식으로는 안 되고 **공통 플랫폼**을 만들어 개발(플랫폼 팀)과 장비 지식(장비군 담당)을 나눠 맡아야 함

**추진 방식**

| 단계 | 시기 | 대상 | 목표 |
|---|---|---|---|
| 1차: 선발대 | 2027 상반기 | CD-SEM, Thickness 중점 운영 (2차 장비군은 인터뷰, Recipe Workflow 조사로 준비) | Align Fail 자동 대응 지능화, 공통 플랫폼 설계 완성과 베타 테스트 |
| 2차: 영역 확장 | 2027 하반기부터 (6월 베타 관문 통과 뒤) | 다른 MI 장비군 | 2차 장비군 본격 합류, 공통 플랫폼 위에서 녹화와 지식화 시작 |

- 선발대 지정 사유: CD-SEM의 Align Fail PoC(화면 인식, Align Key 탐색, 반자동 운영)와 Thickness의 기존 PyAutoGUI 자동화를 재사용할 수 있음
- 개발과 AI에 익숙하지 않은 엔지니어는 교육을 받으며 TF에 참여함. 교육은 합류 시점마다 진행 (1차 2027-01~02, 2차 2027-07~08)

**요청 사항 (2026-12)**

- ARC TF 구성 승인: 조직과 명단은 처음부터 전체로 승인, 초기 개발은 CD-SEM, Thickness 위주로. 2027-01부터 운영
- 1차(선발대) Thickness 담당 엔지니어 1~2명, 주 5시간 (CD-SEM은 TF 리드가 직접 담당)
- 2차 장비군(다른 MI 장비군) 담당 엔지니어 지정: 장비군마다 1~2명. 상반기는 인터뷰, Recipe Workflow 조사로 준비(작업 녹화 포함, 주 1~2시간), 6월 베타 판정 뒤 주 5시간
- 개발 인력 2명 지정 (TF 리드 포함 3명, 1인당 업무 시간 50%: 실질 1.5명, 2027-01 합류)

**확인 필요 사항 (R&D MI H/W 담당자)**

- 장비 화면 녹화분 DB에 직접 접근할 수 있는지 확인 필요 (PoC에서 겪은 허들 가운데 하나)
  - 가능하면: 녹화분을 바로 받아 써서 개발 속도가 빨라짐
  - 불가능하면: RCS에서 GUI 자동화로 녹화분을 내려받아야 함 (속도가 느리고 다운로드 자동화 작업 별도 필요)
- 스크린샷과 녹화 영상을 많이 쓰므로 스토리지 소모량이 매우 큼. 추후 스토리지 자산 확보가 필요함

**2027년 타겟**

| 시점 | 타겟 | 판정 |
|---|---|---|
| 2027 상반기 | CD-SEM, Thickness의 **Align Fail 자동 대응 지능화** (실알람 자동 대응, 엔지니어 상주), **공통 플랫폼 설계 완성과 베타 테스트** | 2027-06 |
| 2027 연말 | CD-SEM, Thickness 셋업 절차, 노하우의 **지식 자산** 축적, 2차 장비군 여러 개가 공통 플랫폼 위에서 녹화 시작 | 2027-12 |

- 셋업 시간 단축은 2028 보조 단계부터, Agent가 레시피 셋업을 진행하는 자율 단계는 2029 타겟임
- 필요 자원: 개발 3명(TF 리드 포함, 각 50%, 실질 1.5명), 담당 엔지니어 겸직, 기존 사내 VLM 서버와 사내 서버 자원, 녹화 스토리지. 새 서버 구매 없음

## 1. PoC에서 얻은 성과와 시사점

ARC는 처음부터 레시피 자동 생성을 목표로 했습니다. PoC로는 범위가 좁고 효과를 재기 쉬운 **Align Fail 자동 대응**을 골랐고 TF 리드가 CD-SEM 담당 엔지니어이자 개발자로 혼자 진행했습니다. 이 PoC에서 레시피 자동 생성에 그대로 쓸 기반을 얻었고 동시에 이 방식으로는 다른 장비군까지 넓힐 수 없다는 시사점도 얻었습니다.

### 얻은 자산

| 확보한 것 | 레시피 자동 생성에서의 쓰임 |
|---|---|
| 사내 인프라에서 화면 이해 모델(VLM, OCR) 자체 운영 | 외부 API 없이 화면 이해 |
| 표준 컴포넌트가 아닌 계측 화면에서도 대략 위치 → 정밀 좌표 → OCR 확인 순서로 클릭 | API 없는 장비 화면 조작 |
| VLM은 "어디를 볼지", CV는 "정확히 어디인지"를 맡는 역할 분리 원칙 | 측정 위치, Align Key 등록의 정확도 |
| 최근 성공 사례를 모은 기준 이미지로 Align Key 탐색 정확도 개선 (오프라인 평가 기준) | 레시피 Align 셋업 |
| 실장비 반자동 운영: 위치 재조정은 자동, 최종 확정은 엔지니어 | TF의 안전 원칙 |
| 엔지니어 작업 녹화 확보 (조작 타임라인, 한국어 절차서 추출은 현장 검증 전) | 장비별 레시피 절차 정의 |
| SecureVDI는 스크린샷 기반으로 키보드, 마우스 입력 가능 (큰 허들, headless 불가) | Thickness와 같은 VDI 경유 장비군도 같은 방식으로 조작. 다른 경로의 장비군은 접속 경로 확정 후 시험 |

상세 목록은 [PoC 자산과 남은 과제](./05-poc-assets.md)에 있으며 수치는 사내용 문서에만 둡니다.

### 시사점 1: 개발자와 현업 엔지니어, 두 역할이 동시에 필요함

| 역할 | PoC에서 한 일 | 한쪽만 있으면 |
|---|---|---|
| 개발자 | 화면 인식, 조작 엔진, 안전 규칙, 모델 서빙과 평가 | 장비 화면과 Align 절차를 몰라 무엇을 자동화할지 정하지 못함 |
| 현업 엔지니어 | Align 절차 정의, 성공 판정 기준, 실장비 검증, 결과 책임 | 화면 인식과 조작 엔진을 만들 수 없음 |

- PoC는 TF 리드가 두 역할을 혼자 맡아 진행
- 다른 장비군에는 그 장비를 아는 개발자 부재. 장비군마다 같은 인력 확보 불가

### 시사점 2: 혼자 진행하며 겪은 허들

| 허들 | 무엇이 어려웠나 | 공통 플랫폼에서 |
|---|---|---|
| AI 모델 최적화와 유지, 운영 | 사내 VLM, OCR 서빙을 직접 띄우고 튜닝, 장애 대응, 버전 관리까지 개발과 함께 맡음 | 모델 서빙과 평가를 플랫폼 팀이 한 번 만들고 모든 장비군이 같이 씀 |
| 최신 VLM 모델 적용 테스트 | 새 모델이 나올 때마다 장비 화면 기준으로 정확도를 다시 재야 함 | 녹화본 평가 세트를 공통으로 두고 모델 교체는 측정으로 결정 |
| 녹화 DB 추출 | 장비 화면 녹화분을 가져오는 경로가 정해져 있지 않아 녹화분 확보 자체에 시간 지연 | H/W 담당자와 접근 경로를 확정하고 녹화분 수집을 플랫폼 기능으로 만듦 |

- 이 허들을 개발, 현업 대응과 병행하기에는 시간 부족. 같은 일을 장비군마다 반복하면 확장 불가

### 시사점 3: 별도 운영 PC 대신 엔지니어 PC에 설치

처음에는 Agent 전용 PC를 따로 마련해 그 PC에서 운영하려고 했습니다. 그러나 사무 PC를 계속 늘리는 방식에는 제약이 많아 공통 플랫폼을 개발해 엔지니어 본인 PC에 설치하는 방향으로 바꿨습니다.

| 별도 PC 방식의 제약 | 엔지니어 PC 설치형에서 |
|---|---|
| 장비군, 엔지니어가 늘 때마다 PC를 추가로 확보해야 함 (자산 신청, 구매, 자리) | 이미 쓰는 PC에 설치하므로 PC가 늘지 않음 |
| PC마다 보안 프로그램, 계정, 장비 접속 권한(RCS, SecureVDI)을 따로 받아야 함 | 엔지니어가 이미 가진 계정과 접속 경로를 그대로 씀. 보안 승인은 설치형 프로그램 하나로 받음 |
| 운영 PC의 업데이트, 장애, 재부팅을 별도로 관리해야 함 | 공통 플랫폼 한 벌을 사내 배포로 일괄 갱신 |
| 엔지니어가 결과를 보려면 그 PC 앞에 가거나 원격으로 따로 들어가야 함. 아무도 보지 않는 화면이 생김 | Agent를 엔지니어가 보는 화면에서 운영, 엔지니어가 즉시 확인, 중단, 책임 |
| 장비별로 따로 꾸리면 PC마다 자동화가 달라짐 | 모든 장비군이 같은 플랫폼을 씀 |

- Agent가 엔지니어 화면을 일시적으로 제어: 엔지니어 PC 자원(CPU, 메모리)을 나눠 쓰고 화면 입력 몇 초 동안은 엔지니어가 PC를 쓸 수 없음. 그래서 관찰과 판단은 백그라운드로 가볍게 돌리고 입력은 제어권 인계(알림 → 인계 → 입력 → 반환)로 하며 PC 자원 한도를 베타 기준에 넣음

### LLM 모델만으로는 ARC 자동화가 안 되는 이유

최신 LLM, VLM이 화면을 잘 읽어도, 모델 하나만으로는 레시피 셋업을 맡길 수 없습니다. 모델은 "화면을 보고 다음 할 일을 판단"하는 한 부분이고 나머지는 플랫폼이 채워야 합니다.

| 항목 | 모델만 쓸 때의 한계 | 그래서 플랫폼에 필요한 것 |
|---|---|---|
| 좌표 정밀도 | 같은 화면도 물을 때마다 위치가 달라짐. Align Key, 측정 위치는 정밀 좌표가 필요함 | VLM은 "어디를 볼지", CV가 정밀 좌표, OCR로 결과 확인 |
| 장비 지식(노하우) | 범용 모델은 사내 계측 화면, 셋업 절차, 성공 판정 기준을 모름 | 엔지니어 작업 녹화에서 뽑고 담당 엔지니어가 승인한 절차 (지식 자산) |
| 성공/실패 여부 | 조작이 제대로 됐는지 스스로 확인하지 못하고 "성공"이라고 답할 수 있음. 실패를 놓치면 오측정, 레시피 오변경으로 이어짐 | 서버 규칙 확인, 조작 뒤 결과 검증, 불확실하면 멈추고 엔지니어 호출 |
| 진행 상태 | 셋업은 수십 번의 조작으로 이어지는데, 어디까지 했는지, 무엇이 바뀌었는지 놓침 | 절차 상태, 체크포인트, 실행 로그 |
| 화면 조작 | 모델은 답을 낼 뿐이고 장비에는 조작 API가 없음 | 화면 캡처, 입력 실행기, 제어권 인계, 즉시 중단 |

- 모델이 좋아져도 이 표의 오른쪽 칸은 그대로 필요함. 최신 VLM은 공통 평가 세트로 재서 판단 부분만 바꿔 끼움

### 결론: MI 장비 전반의 ARC는 공통 플랫폼으로

- 장비와 무관한 부분(화면 인식, 조작 엔진, 안전 규칙, 모델 서빙과 평가, 녹화분 수집)은 **플랫폼 팀이 한 번** 만듦
- 장비별 절차와 판정 기준만 **장비군 담당**(MI 엔지니어)이 채움
- 개발자가 장비를 다 알 필요도, 엔지니어가 개발을 다 할 필요도 없게 만드는 것이 TF의 목적임

### 현업이 이미 만든 자동화 (Thickness)

- Thickness 담당자들이 PyAutoGUI 기반으로 자동화해 둔 작업이 많음. 고정 좌표와 정해진 순서로 반복 입력을 처리하는 방식임
- 검토 과제: 이 PyAutoGUI 자동화와 VLM 기반 방식을 어떻게 섞어 쓸지 정해야 함
  - 정해진 순서의 반복 입력: 검증된 PyAutoGUI 스크립트를 그대로 재사용
  - 화면 인식과 판단이 필요한 구간 (위치 확인, 예외 화면, 막힘): VLM이 맡음
  - PyAutoGUI 스크립트 앞뒤에 VLM 화면 확인을 붙여 화면이 예상과 다르면 멈추게 함
- 2027-01~02 온보딩 때 Thickness 기존 스크립트를 목록화하고 2027-06 요소 목록에 혼합 방식을 반영함

**아직 확인하지 못한 것**과 확인 시점:

| 항목 | 확인 시점 |
|---|---|
| SecureVDI 경유 화면에서도 VLM 인식 정확도가 직접 접속과 같은가 | 2027 상반기 Thickness Align Fail 운영 |
| PyAutoGUI 기존 자동화와 VLM 방식을 섞었을 때 안정적으로 동작하는가 | 2027 상반기 Thickness Align Fail 운영 |
| 공통 플랫폼에 장비별 코드 없이 새 장비군을 얹을 수 있는가 | 2027 하반기 2차 장비군 합류 |
| Agent가 엔지니어가 한 작업의 의미를 파악하고 그대로 따라 진행할 수 있는가 | 2027 하반기 절차화, 2028 보조 단계 |
| 새로운 측정 파라미터를 추가할 때, 의뢰서를 근거로 위치를 찾고 몇 차례 조정을 거쳐 이미지를 제대로 등록할 수 있는가 | 2028 보조 단계, 2029 자율 단계 |

모두 장비 화면과 레시피 절차를 아는 현업 엔지니어들과 함께 검증해야 합니다. 그래서 TF가 필요합니다.

## 2. 레시피 셋업의 문제

### 문제

- 레시피 셋업은 숙련 엔지니어가 원격 제어 화면에서 마우스와 키보드로 하는 반복 수작업임. 측정 위치를 잡을 때 측정, 실패, 재조정을 되풀이함
- 노하우가 개인에게 있음. 담당자가 바뀌면 지식이 사라지고 사람마다 품질이 다름
- 관리 장비가 늘어나거나 개발 제품이 증가하면 셋업 인력도 같은 비율로 늘어나야 하나, 이 구조로는 한계가 있음
- 측정 중 Align Fail(정렬 실패) 알람이 나면 엔지니어가 원격으로 위치를 다시 잡을 때까지 장비가 멈춤

### 안 하면 생기는 일

- ⟨확인: 신규 제품, 공정 도입 때 레시피 셋업 대기로 늦어지는 기간⟩
- ⟨확인: 장비군별 레시피 셋업에 쓰는 엔지니어 시간 (월 기준)⟩
- ⟨확인: Align Fail 알람으로 멈추는 장비 시간 (월 기준)⟩
- 장비군마다 따로 자동화를 시도하면 PoC에서 겪은 허들(모델 운영, 최신 VLM 테스트, 녹화분 확보)과 화면 인식, 조작, 안전 장치를 매번 새로 풀게 됨

## 3. 추진 방향: 선발대에서 영역 확장으로

가장 중요한 개발 방향은 **공통 플랫폼을 통해 AI가 지식 자산화된 마우스, 키보드 조작과 레시피 셋업 방법을 수행할 수 있느냐**입니다. 이를 한 번에 모든 장비군으로 시작하지 않고 이미 기능이 갖춰진 장비군으로 먼저 플랫폼을 다진 뒤 넓힙니다.

| 단계 | 시기 | 대상 | 하는 일 | 넘어가는 조건 |
|---|---|---|---|---|
| 1차: 선발대 | 2027 상반기 | CD-SEM, Thickness | Align Fail 자동 대응 지능화. 이 과정에서 공통 플랫폼 설계를 완성하고 베타 버전을 두 장비군 담당 엔지니어 PC에서 운영 | 2027-06 관문: Align Fail 성과와 플랫폼 베타를 따로 판정, 2차 합류는 베타 판정으로 결정 |
| 2차: 영역 확장 | 2027 하반기부터 | 다른 MI 장비군 | 2차 장비군 본격 합류. 교육, 작업 녹화, 화면 영역 지도, 절차 정의를 공통 플랫폼 위에서 진행. 1차 장비군은 절차화와 지식 자산으로 진행 | 2027-12 관문: 지식 자산, 2차 합류 |

- **선발대가 CD-SEM, Thickness인 이유**: CD-SEM의 Align Fail PoC(화면 인식, Align Key 탐색, 반자동 운영)와 Thickness의 기존 PyAutoGUI 자동화를 재사용할 수 있음. 처음부터 만들지 않고 플랫폼 설계에 집중할 수 있음
- **CD-SEM, Thickness 위주로 개발을 시작하는 이유**: 플랫폼보다 일이 먼저 넓어지면 장비군마다 따로 만들게 됨. 사람은 처음부터 정해 두되, 개발은 플랫폼이 준비된 만큼만 넓힘. 베타 판정으로 검증된 것만 넓혀 실패 비용도 줄임
- **2차 장비군의 상반기 참여: 인터뷰, Recipe Workflow 조사로 준비** (주 1~2시간). 상반기 운영은 CD-SEM, Thickness 중점이고, 나머지 장비군은 담당자 인터뷰와 Recipe Workflow 조사로 아래 내용을 파악함. 초기에 다른 장비군의 특징을 알아 두는 것이 중요함. 그래야 공통 플랫폼이 CD-SEM, Thickness에만 맞춰지지 않음
  - 장비 특징: 화면 구성, 접속 경로, 원격 계층, 화면 품질
  - 작업 절차: 레시피 셋업과 Align 대응 순서, 막히는 지점 (작업 녹화로 남김. 녹화 DB 접근이 되면 DB에서, 안 되면 최소 녹화기로)
  - 필요한 기능: 공통 플랫폼에 있어야 할 기능과 장비군 고유 기능
  - 산출물: 장비군별 요구사항 정리. 2027-03 1차본을 플랫폼 설계 확정에 반영하고, 6월 베타 판정 전에 보완
  - 교육과 개발 지원은 하지 않음. 6월 베타 판정 뒤 주 5시간으로 늘리고 2기 교육 시작
- **베타 기준** (2027-06 관문에서 판정): 선발대 담당 엔지니어 PC에서 설치형 에이전트가 엔지니어가 시작하는 관찰과 녹화, Align Fail 입력과 즉시 중단을 ⟨확인⟩주 동안 문제없이 운영 (상시 관찰 모드는 3분기에 완성). 엔지니어 PC 자원 한도 준수. 새 장비군은 장비별 코드 없이 화면 영역 지도와 절차 정의만으로 얹을 수 있는 구조
- 베타 기준에 못 미치면 2차 합류를 늦추고 선발대에서 보완함

### 검토한 대안

| | A: 선발대만 + 개발 2명 | **B: 처음부터 전체 + 개발 3명 (권고)** | C: 전체 동시 개발 + 개발 3명 |
|---|---|---|---|

- B를 권고합니다. C의 장점 가운데 한 번의 승인, 장비군 차이의 설계 반영, 데이터 조기 축적은 가져오면서, 플랫폼이 준비되기 전 지원 부담은 거의 늘지 않습니다
- A는 PoC 시사점("혼자서는 무리")을 보고하면서 같은 구조를 다시 요청하는 셈이라 택하지 않습니다

자동화 대상 구간의 실측값과 나머지 현재 값은 장비군마다 온보딩 기간(선발대 2027-01~02, 2차 2027-07~08)에 담당 엔지니어가 직접 측정해 확정하겠습니다. 측정하기 전에는 목표를 숫자로 정하지 않습니다.

**시간 구분**: 효과를 계산할 때 두 가지 시간을 나눠 셉니다.

- 작업 경과 시간: 셋업 시작부터 끝까지 걸린 시간
- 엔지니어 직접 투입 시간: 엔지니어가 실제로 조작, 판단, 승인에 쓴 시간. 회사 효과 계산에는 이 값을 씀

**측정 규칙** (기준선과 이후 측정을 같은 조건으로 비교하기 위해 온보딩 측정 양식에 고정)

- 대상: 장비군마다 정한 대표 레시피 유형 1개. 전체 셋업이 아닌 **자동화 대상 구간(측정 위치, Align 셋업)** 의 시작과 끝을 정해 측정
- 포함: 그 구간 안의 실패, 재작업, 수동 인계 시간. 승인 대기 시간은 별도 기록
- 개입 횟수: 반드시 거치는 승인(저장 전 등)은 제외하고 **예정에 없던 개입**만 집계

### 엔지니어 시간이 줄면 회사에 무엇이 남는가

```
레시피 셋업 수요(건/월) × 건당 엔지니어 직접 투입 시간 감소분
  → 회수되는 엔지니어 시간 (월 ⟨확인⟩시간)
  → 신규 제품, 공정 도입 때 셋업 대기 단축, 엔지니어가 분석, 개선 업무로 이동
  → 장비가 늘어도 셋업 인력을 같은 비율로 늘리지 않아도 됨
```

- 가정: ⟨확인: 장비군별 월 셋업 수요와 증가 추세⟩. 셋업 수요가 장비, 제품 수와 함께 늘어야 "인력이 비례해야 한다"는 주장이 성립함

### 범위

| 구분 | 내용 |
|---|---|
| 최종 목표 | 신규 레시피 셋업의 전 과정 자동화: 생성 → 측정 위치, Align Key 등록 → 파라미터 → 검증 측정 → 저장 |
| 2027 상반기 선행 과제 | **Align Fail 자동 대응 지능화** (CD-SEM, Thickness). 플랫폼 부품으로 만들어 공통 플랫폼 설계를 완성하고 베타로 운영 |
| 레시피 셋업 자동화 대상 구간 | 시행착오가 가장 많은 **측정 위치, Align 셋업 구간**. 2027에는 관찰과 지식화, 2028부터 엔지니어 앞에서 Agent가 입력을 대행, 2029에 Agent가 진행 |
| 1차: 선발대 | CD-SEM, Thickness. 공통 플랫폼 설계와 베타 |
| 2차: 영역 확장 | 다른 MI 장비군. 2027 하반기 본격 합류, 공통 플랫폼을 실제로 적용 |
| 실행 방식 | 설치형 프로그램을 엔지니어에게 배포하고 엔지니어가 **자기 PC에서** AI 자동화 프로그램과 함께 작업. 장비 PC에는 설치하지 않음. 접속 경로는 장비군마다 다름: CD-SEM은 엔지니어 PC에서 RCS로 직접, Thickness와 VeritySEM은 SecureVDI(웹 VDI)의 가상 Windows 안에서 RCS나 Radmin Viewer로 접속 (2차 장비군 경로는 ⟨확인⟩). Agent는 어느 경로든 엔지니어가 보는 화면(FHD 모니터 기준)을 캡처하고 같은 화면에 입력 |
| 녹화분 확보 | 장비 화면 녹화분 DB 직접 접근(가능 여부를 R&D MI H/W 담당자에게 확인), 불가하면 RCS에서 GUI 자동화로 다운로드 (다운로드 자동화 작업 별도 필요) |
| 제외 | 장비 유지보수, 하드웨어 제어, 장비 내부 소프트웨어 설치 |

### 공통 플랫폼 구조

공통 플랫폼은 두 갈래로 만듭니다. 장비와 무관한 부분은 플랫폼 팀이 한 번 만들고, 장비별 절차와 판정 기준만 장비군 담당이 채웁니다. PoC의 허들이었던 모델 서빙과 평가, 녹화분 수집도 플랫폼 쪽에 둡니다.

| 갈래 | 하는 일 | 시기 |
|---|---|---|
| Offline: 지식화 | 엔지니어 작업 녹화 → 화면 변화 → 의미 단계 → 여러 녹화 비교로 분기 후보 → **담당 엔지니어 승인** → 지식 자산 | 2027 관찰과 지식화 |
| Online: 실행 | 현재 화면 확인 → 비슷한 사례 검색 → AI 판단 → **규칙 확인** → 승인된 조작 1개만 실행 → 결과 확인 후 다음 단계 | 2027 입력 없는 제안, 2028 보조, 2029 자율 |

- AI는 다음 조작을 **제안만** 함. 허용 여부는 서버의 규칙 확인이 다시 판단하고, 정해진 조작 단위만 실행함
- 결과가 불명확하거나 화면이 예상과 다르면 멈추고 엔지니어를 부름. 덮어쓰기와 운영 적용은 기본 금지
- 2027년에는 화면에 입력하지 않고 "다음에 할 일"을 제안만 해서 판단 정확도를 먼저 검증함. 화면 입력은 2028 보조 단계부터 (Align Fail 자동 대응은 승인된 예외)

상세 설계는 [공통 플랫폼 기술 설계](./07-platform-architecture.md)에 있습니다.

### 자동화 수준과 안전 원칙

- **반자동(Supervised Autonomy)이 원칙임**: Agent가 조작하고, 위험 조작(측정 실행, 삭제, 모드 변경)과 레시피 저장, 적용 직전에는 엔지니어가 승인
- **Align Fail 자동 대응도 엔지니어가 자리에 있는 것이 전제임**: Agent는 엔지니어 본인 PC에서 관찰과 판단을 백그라운드로 하고, 화면에 입력하는 몇 초 동안만 엔지니어에게서 제어권을 넘겨받음(알림 → 인계 → 입력 → 결과 확인 → 반환). 엔지니어가 마우스를 건드리면 즉시 멈춤. 결과의 책임은 담당 엔지니어에게 있음. 엔지니어가 없는 무인 운영은 목표가 아님
- **Align Fail 자동 대응은 승인된 예외임**: 허용 조작은 레시피를 바꾸지 않는 위치 재조정과 해당 지점 재측정 재시도뿐임. 저장, 삭제, 모드 변경, 레시피 수정은 계속 금지. 인식이 불확실하거나 화면이 예상과 다르면 Agent가 스스로 멈추고 엔지니어를 부름
- **자동 전환 승인**: 반자동 운영 실적을 리드가 정리하고, 담당 엔지니어 확인을 거쳐 월간 보고에서 장비별로 승인받음
- 레시피 셋업의 완전 자동은 반복 검증과 자체 중단 기록까지 통과한 레시피 유형만 단계 승인을 거쳐 검토함

### TF 구성

| 구분 | 구성 | 맡는 일 | 합류 |
|---|---|---|---|
| TF 리드 + 공통 플랫폼 팀 | TF 리드 + 지정 개발 2명 (백엔드, 프론트엔드) | 화면 인식, 조작 엔진, 안전 규칙, 승인 화면, LLMOps, 녹화 DB 추출, 교육 | 2027-01 |
| CD-SEM 담당 (선발대) | TF 리드 | 장비별 레시피 절차, 성공 판정 기준, 현장 검증 | 2027-01 |
| Thickness 담당 (선발대) | MI 엔지니어 1~2명 | 위와 같음. 기존 PyAutoGUI 자동화 공유 | 2027-01 |
| 다른 MI 장비군 담당 (2차) | 장비군마다 MI 엔지니어 1~2명 | 위와 같음. 공통 플랫폼을 실제로 적용하는 첫 대상 | 2027-01 인터뷰, Recipe Workflow 조사 (주 1~2시간), 2027-07 본격 (주 5시간) |

- **공통 플랫폼**: 모든 장비군이 함께 사용. 장비마다 엔진을 새로 만들지 않음
- **장비군 담당**: MI 현업 엔지니어 1~2명으로 구성. 그 장비의 레시피 절차 정의, 성공 판정 기준, 현장 검증을 맡음
- **2차 장비군 담당**: 2026-12에 선발대와 함께 지정. 상반기에는 인터뷰, Recipe Workflow 조사로 준비하고(요구사항 정리), 6월 베타 판정 뒤 교육을 받으며 화면 영역 지도와 절차를 정의함
- **인프라(GPU, VLM 서빙)**: 필요 시점에 합류. 장비 벤더는 필요할 때 자문

**개발 인력 배분 (TF 리드 + 지정 2명, 1인당 업무 시간 50% = 실질 1.5명)**

개발 2명은 임원, 팀장급에서 지정을 요청합니다. PoC처럼 TF 리드 혼자 개발하는 구조는 더 이상 유지할 수 없습니다.

| 사람 | 맡는 일 |
|---|---|
| TF 리드 | 전체 설계, 모든 갈래 관여, Align Fail 지능화, TF 운영, 교육, CD-SEM 담당 |
| 개발 A: 백엔드 | 서버(판단, 규칙 확인 API, 저장소), 녹화 DB 추출 알고리즘, 데이터 파이프라인, 평가 세트, LLMOps(HCP 장애 대응, 신규 오픈웨이트 모델 벤치마크, 교체 판단) |
| 개발 B: 프론트엔드 (클라이언트와 화면) | 엔지니어 PC 설치형 에이전트(캡처, 입력, 즉시 중단, 제어권 인계), 승인 화면과 절차서 검토 화면, 배포 |

| 시기 | TF 리드 | 개발 A: 백엔드 | 개발 B: 프론트엔드 |
|---|---|---|---|
| 2027 상반기 (선발대) | Align Fail 지능화 (CD-SEM 겸임), 플랫폼 설계, 1기 교육 | 녹화 DB 추출, 서버 수집, 평가 세트, 최신 VLM 벤치마크 | 설치형 에이전트, 베타 배포 |
| 2027 하반기 (확장) | 선발대 절차화, 지식 자산, 2기 교육 | 지식 자산 DB, 돌파구 추천 검색, LLMOps | 상시 관찰 모드, 2차 장비군 화면 영역 지도 도구, 승인 화면 |

- LLMOps는 늘 손이 가는 일은 아니지만 주기적으로 챙겨야 함(HCP 다운, Hugging Face 신규 오픈웨이트 모델). 예고 없이 생기는 일이라 TF 리드가 맡으면 Align Fail 일정이 끊김. 그래서 데이터와 묶어 백엔드가 맡음
- 세 사람 모두 개인 과제를 병행하므로 TF 전담은 불가함. 각자 업무 시간의 50%를 TF에 씀
- 지정이 1명만 되면 프론트엔드를 먼저 채움. 6월 베타가 2차 본격 참여의 관문이라 일정의 병목임. 백엔드 일은 TF 리드가 최소로 유지(PoC 서버 그대로, LLMOps는 장애 대응만, 2차 녹화는 DB로 받을 수 있는 범위로)
- 상반기에는 Align Fail과 플랫폼 베타를 우선함. 관찰과 지식화는 녹화 축적까지만 하고, 상시 관찰 모드는 3분기 초로 미룸
- 인력이 늘면 상시 관찰 모드와 채팅을 먼저 당김
- 인력이 모자라면 채팅 기능(관문 밖)을 먼저 미루고, 다음으로 2차 장비군 합류 순서를 나눔

역할 분담은 [참여 팀과 역할](./02-roles-and-teams.md)에 있습니다.

## 6. 교육하며 운영

현업 엔지니어 대부분은 장비와 레시피는 잘 알지만 개발과 AI에는 익숙하지 않습니다. 교육을 먼저 끝내고 시작하지 않고 **합류 시점마다 교육을 진행하면서 TF를 운영**합니다.

| 대상 | 시기 | 형태 | 끝나면 |
|---|---|---|---|
| 선발대 (Thickness 담당) | 2027-01~02, 8주 | 주 5시간 안에서 강의 짧게, 실습 길게. 실습은 PoC 녹화본과 모의 실행 | 기준선 측정, 대표 레시피 유형 선정, 작업 녹화 시작 |
| 2차 장비군 담당 | 2027-07~08, 8주 | 같은 과정. 실습은 선발대에서 만든 공통 플랫폼 베타로 | 기준선 측정, 대표 화면의 화면 영역 지도 초안, 작업 녹화 시작 (전체 화면은 4분기) |
| 전체 | 2027 내내 | 월간 회의에서 사례 공유, 막힌 지점 질의 | - |

- 목표는 AI 개발자를 만드는 것이 아니라, 엔지니어가 **자기 장비 절차를 Agent가 실행할 수 있는 형태로 정의하고 결과를 판정**할 수 있게 하는 것임
- 강사는 TF 리드와 공통 플랫폼 팀이 맡음. 교육 시간은 개발 인력 배분에 포함함

상세 과정은 [온보딩 학습 과정](./04-onboarding.md)에 있습니다.

## 7. 일정

2027년은 상반기 선발대, 하반기 영역 확장으로 진행합니다. 상반기에 **Align Fail 자동 대응 지능화를 빠른 첫 통과로 끝내면서 공통 플랫폼 설계를 완성하고 베타로 운영**합니다. Align Fail은 일회성 시제품이 아니라 플랫폼 부품(화면 캡처, 화면 영역 지도, 입력 실행기, 자체 중단, 실행 로그)으로 만들고, 그 과정에서 필요했던 요소를 장기 계획에 반영합니다.

### 관문과 2028 진입 조건

- 2차 본격 참여(2027-07)는 6월 베타 판정을 통과해야 함. 못 미치면 본격 참여를 늦추고 선발대에서 보완함. 2차 담당은 그동안 작업 녹화를 계속함
- 2028 보조 단계(반복 입력 대행)로 넘어가려면 두 가지가 필요함
  - 12월 관문 통과
  - 공통 기술, 안전 요건 충족: 입력 실행기가 실장비에서 의도한 조작만 하고, 불확실할 때 스스로 멈추는 것이 운영 기록으로 확인됨
- Align Fail의 성과 목표(자동 해결률)는 별도 성과 과제이므로, 미달이어도 위 두 조건을 채우면 2028 진입을 막지 않음. 미달분은 보완, 축소 결정 대상이 됨

**단계 통과 결정**: 관문마다 리드가 통과 기준과 결과를 정리하고 담당 엔지니어의 품질 확인을 받아 월간 보고에서 승인받겠습니다. 기준에 못 미치면 **보완**(기간 연장), **축소**(대상 유형, 장비군 축소), **중단** 중 하나를 정해 [결정 기록](./decision-log.md)에 남깁니다.

## 9. 위험과 대응 (요약)

| 구분 | 위험 | 대응 | 확인 시점 |

| 영역 확장 | 2차 장비군 여러 개가 한꺼번에 들어와 교육, 지원 부담이 큼 | 같은 8주 과정을 한 번에 진행, 장비군 합류 순서를 나눌 수 있게 둠 | 2027-07 |
