# 지도: ARC 플랫폼 단계별 개발 일정

## Destination

ARC 자동화 공통 플랫폼의 **단계별 개발 일정안(2027~2029, 1년에 1단계)** 과 **단계마다의 통과 기준**이 정해져서, [TF 구성 기획안](../01-tf-proposal.md) 5절 타임라인과 [플랫폼 PRD](../06-platform-prd.md)에 그대로 옮길 수 있는 상태.

## Notes

- **도메인**: [ARC TF 용어](../CONTEXT.md)를 따른다. 새 용어가 정해지면 그 파일에 바로 적는다.
- **스킬**: grilling 티켓은 `grilling` + `domain-modeling`. 조사는 `research`. 프로세스 스킬은 mattpocock 우선.
- **추적기**: 공개 저장소라 GitHub Issues 대신 이 폴더의 로컬 마크다운을 쓴다.
  - 티켓 하나 = `tickets/NN-이름.md`. 맨 위 frontmatter에 `type`(research, prototype, grilling, task), `status`(open, closed), `assignee`(빈 값 = 아무도 안 맡음), `blocked_by`(티켓 번호 목록).
  - 해결하면 파일 끝에 `## Resolution`을 쓰고 `status: closed`로 바꾼 뒤, 아래 "Decisions so far"에 한 줄을 더한다.
  - frontier = `status: open`이고 `assignee`가 비어 있고 `blocked_by`가 모두 closed인 티켓.
- **문체**: 기획안과 PRD로 옮길 문장은 한국 보고서 문체(개조식 ~임/~함/명사, 서술은 ~입니다/~습니다)로 쓴다.
- **사내 정보**: 공개 저장소다. 시스템 이름, 서버 사양, 실명, 수치는 `*_사내용.md`(git 제외)에만 둔다. 티켓에는 일반화해서 쓴다.
- **차트 작성 때 정한 전제** (2026-11-06 grilling):
  - 7개 기능은 플랫폼의 최종 모습이고, 2027~2029에 1년에 1단계씩 낸다. 회사 목표는 2030 ARC Agent 완성, 이 지도는 2029까지 **CD-SEM, Thickness 완성**을 노린다 (Thickness는 조건부)
  - 단계: 2027 **관찰과 지식화** (관찰, 녹화 → 절차, 노하우 → 지식 자산, 요청형 돌파구 추천, 채팅, 저자원 구조, 1차 3개 장비군 동시) → 2028 **보조** (보는 앞에서 반복 입력 대행, 막힘 자동 감지, 장비 데이터 읽기) → 2029 **자율** (Agent가 셋업 진행, 특이 사항, 위험 때만 개입)
  - 기간은 time-box로 정하고 범위를 조정한다. 단계 통과는 월간 보고에서 AI TF 담당 임원 1차 → 기반기술센터장 2차 승인 (항목별로 나누지 않음, 2026-11-06 확인). 기획안 본문에는 보고 대상을 적지 않음
  - 개발 인력은 2명(리드 포함). 둘 다 개인 과제를 병행해 각 50% 투입, **실질 1.0명** (2026-11-06 확인)
  - 관찰은 화면 위주. 1단계에서 읽는 시스템 데이터는 **레시피 의뢰서**(패턴 스키마, 좌표, 파라미터) 하나. 장비 데이터 읽기는 2단계
  - 엔지니어 PC는 캡처, 변화 감지, 전송만, 추론과 저장은 사내 서버. 서버 자원은 기획안 요청 사항에 추가한다
  - 셋업 시간 단축은 2028(보조)부터 타겟으로 둔다. 2027 지표는 1단계에 맞는 것으로 바꾼다
  - **2027년의 성과 과제는 Align Fail 자동 대응**이다. ARC 안의 작은 꼭지이고 PoC가 있어 1년 안에 현장 성과로 낼 수 있다. 관찰과 지식화는 플랫폼의 바탕으로 같이 간다 (2026-11-06 사용자 결정)
  - Align Fail은 **빠른 첫 통과**로 2027 상반기에 CD-SEM, Thickness 완성까지 간다 (AI 임원 요구). 그 과정에서 나온 요소 목록을 장기 계획에 반영한다 (2026-11-06)
  - 따라서 2027-01부터 화면 입력(위치 재조정 조작)이 있다. SecureVDI 경로 입력은 2026-11 확인했다. 기획안의 보안 승인 요청은 R&D MI H/W 담당자 확인 사항(녹화분 DB 직접 접근)으로 바꿨다

## Decisions so far

<!-- 닫힌 티켓마다 한 줄 -->

- [엔지니어 PC에서 상시 관찰할 때 자원을 얼마나 쓰는가](tickets/02-client-footprint.md): WGC 창 단위 캡처 + 타일 비교 변화 감지. 추정 예산 평균 CPU 2%, RAM 150MB, 업로드 300kbps 이하. 캡처 보호가 켜지면 불가 (현재 두 경로는 캡처됨). 실측은 별도 티켓
- [서버 스택(MinIO, OpenSearch, Redis)으로 1단계를 운영할 수 있는가](tickets/01-server-stack.md): 대부분 가능. PostgreSQL(권한, 감사) 추가, 화면 검색은 VLM 설명 텍스트 + BGE-M3로 우회, OpenSearch 2.19 이상. MinIO, Redis는 라이선스 검토 필요
- [녹화에서 절차와 노하우를 자동으로 뽑아낼 수 있는 수준은 어디까지인가](tickets/03-procedure-extraction.md): 절차는 AI 초안 + 엔지니어 검토. 키 입력, 수치, 단계 묶기는 사람 몫. 노하우는 결정 지점 질문에 대한 엔지니어 답변에서 나옴. 녹화 1건에 VLM 약 100~250회 호출(추정)
- [2027 단계의 통과 기준 (Align Fail 자동 대응 + 관찰과 지식화)](tickets/05-phase1-gate.md): Align Fail은 CD-SEM, 상반기 반자동 → 하반기 무인 전환, 통과 지표 자동 해결률, 대표 숫자 회수 가동 시간. 관찰과 지식화는 절차서 수, 추천 채택률, PC 자원 한도 3개. 두 관문 따로 판정, 2028 진입은 관찰과 지식화 통과가 조건. 2027-06 반기 점검
- [2029년 "한 장비군 완성"의 정의와 그 장비군](tickets/06-done-definition.md): CD-SEM과 Thickness(입력 주입 통과 조건부). 셋업 수요 상위 유형의 의뢰서 기반 셋업을 자율 완주, 저장 승인 1회는 유지. 레시피 유형 × 단계 신뢰도가 높으면 지켜보기 생략. 2029 VeritySEM은 보조, 2차 장비군은 관찰과 지식화 통과
- [서버 구성과 라이선스 확정](tickets/11-server-config.md): 새 서버 없이 사내 서비스 할당 (MinIO 10TB 요청, OpenSearch 3.7 기존 100GB, PostgreSQL, Redis 2GB, MongoDB 예비, 앱은 기존 VLM 서버). 수집은 상시 관찰(변화 시 1장)과 녹화(초당 10장 → 서버 재처리로 중요 프레임만 보관) 두 모드. 라이브 영역은 담당 엔지니어가 화면 영역 지도로 정함
- [2027 관찰과 지식화 단계의 분기별 계획](tickets/07-phase1-plan.md): Align Fail은 빠른 첫 통과로 상반기에 CD-SEM(2월 반자동), Thickness(4월 반자동, SecureVDI 입력 시험 조건부) 무인 대응까지, 2027-06 관문과 요소 목록. 관찰과 지식화는 상반기 녹화 축적 → 3분기 절차 추출 → 4분기 지식 자산, 추천, 채팅은 2028-01~03으로 이월. 보안 승인은 관찰, 입력 두 건으로 분리

## Not yet specified

- **2028 보조 단계의 대행 대상**: 어떤 반복 입력부터 대신할지. 1단계 관찰 데이터에서 반복 빈도를 보고 정해야 한다.
- **막힘 자동 감지 기준**: 같은 화면 반복, 오래 멈춤 등 무엇을 막힘으로 볼지. 1단계에 요청형 막힘 기록이 쌓여야 정할 수 있다.
- **2029 자율 단계의 위험 판정**: Agent가 스스로 멈추고 엔지니어를 부를 조건.
- **인력 증원 효과**: 개발 인력이 늘면 어느 단계가 당겨지는지. 1단계 계획이 나왔으므로 첫 후보는 3분기로 미룬 상시 관찰 모드와 이월된 채팅이다.
- **기획안 메시지 변경**: 2027 약속이 셋업 시간 단축에서 지식 자산, 추천으로 바뀌면, 임원 보고의 핵심 메시지와 pptx를 어떻게 바꿀지.

## Out of scope

- 2030 ARC Agent 완성까지의 전체 계획: 이 지도는 2029까지다.
- 각 단계의 구현 스펙: 일정이 정해진 뒤 PRD에서 다룬다.
- 기획안, PRD 문서 고치기: 지도가 끝난 뒤 하는 일이다 (지도는 결정까지만).
