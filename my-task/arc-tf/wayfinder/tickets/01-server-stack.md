# 서버 스택(MinIO, OpenSearch, Redis)으로 1단계를 운영할 수 있는가

## Question

1단계(관찰과 지식화)의 서버 쪽 일을 **MinIO + OpenSearch + Redis** 세 가지로 감당할 수 있는가? 모자라면 무엇이 더 필요한가?

서버가 맡을 일:
- 엔지니어 작업 녹화 영상, 화면 캡처 저장 (객체 저장)
- 절차, 노하우, 의뢰서 내용을 모은 지식 자산의 저장과 검색 (키워드 + 벡터 의미 검색, 임베딩은 사내 BGE-M3)
- 막힘에서 비슷한 상황 찾기 (화면 이미지 + 텍스트로 검색)
- 엔지니어 PC에서 올라오는 관찰 이벤트 수신, 작업 대기열, 채팅 세션 상태
- 사내 VLM(OpenAI 호환 API) 호출을 줄 세우기

알고 싶은 것:
1. 각 일을 셋 중 무엇이 맡는가, 셋 다로 안 되는 일이 있는가 (예: 작업 큐, 관계형 데이터)
2. OpenSearch의 벡터 검색(k-NN)으로 텍스트와 이미지 임베딩 검색이 되는가, 버전 조건
3. 엔지니어 10~20명, 3개 장비군 규모에서 규모를 어림잡는 방법 (저장량, 메모리). 숫자가 아니라 산정식과 근거
4. 세 가지 모두 사내 설치형(온프레미스)으로 라이선스 문제 없이 쓸 수 있는가

공식 문서 위주로 확인한다. 회사 서버 사양은 적지 않는다.

## Resolution

조사 결과: 브랜치 `research/01-server-stack`의 `my-task/arc-tf/wayfinder/research/01-server-stack.md` (2026-11-06, 병합하지 않음)

- 세 가지로 대부분 가능함
  - MinIO: 녹화 영상, 화면 캡처 저장
  - OpenSearch: 키워드 + 벡터 하이브리드 검색. 하이브리드는 2.10부터, RRF는 2.19부터라 **2.19 이상** 필요
  - Redis: 관찰 이벤트 큐(Streams), 채팅 세션 상태, VLM 호출 제한(INCR/EXPIRE)
- 빠진 것
  - 사용자, 권한, 감사 기록 같은 관계형 데이터를 둘 곳이 없음 → **PostgreSQL 추가** 권장
  - BGE-M3는 텍스트 전용이라 화면 이미지 임베딩 모델이 없음 → 1단계는 VLM으로 화면을 설명 텍스트로 바꾼 뒤 BGE-M3로 임베딩
  - Redis Streams 큐는 최소 1회 전달이고 장애 때 최대 약 1초 분량을 잃을 수 있음 → 작업을 두 번 받아도 문제없게 처리
- 규모 산정식: 1024차원 HNSW(M=16) 기준 벡터당 약 4.6KB, 100만 벡터에 약 4.6GB. 레플리카 수만큼 늘어남. 녹화 용량식과 Redis 실측 방법은 조사 문서에 있음
- 라이선스 검토 필요
  - MinIO: 조사 문서에 따르면 커뮤니티 저장소가 2026-04-25 보관 처리되어 유지보수가 끝났고(AGPLv3, 소스 배포만), 후속인 AIStor Free는 단일 노드만 허용함. 수정 없이 사내에서만 쓰면 AGPL 공개 의무는 없다고 해석함
  - Redis 8: RSALv2, SSPLv1, AGPLv3 중 하나를 골라야 함. 대안은 Valkey(BSD-3)
  - OpenSearch(Apache 2.0): 검토 거의 불필요
- 남는 결정 → 새 티켓 "서버 구성과 라이선스 확정"
