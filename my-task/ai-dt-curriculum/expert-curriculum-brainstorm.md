# Expert 분과 — 커리큘럼·인증 체계 브레인스토밍

> AI Agent를 전문적으로 개발하고 S/W 지식도 해박한 인력을 길러내는 Expert 과정의 커리큘럼과 인증 체계를 잡기 위한 출발점 정리.

**읽는 법**: 1장은 확정된 전제와 결정이다. 2~5장은 논의를 시작할 때의 **초안 가설**로 기록용이다. 논의는 끝났으며(6장), 확정 내용은 [커리큘럼 정리본](./expert-curriculum.md)과 [인증 체계 정리본](./expert-certification.md)이 기준이다.

---

## 1. 확정된 전제

### 과제 전체

- **목적**: 제조 회사에서 1인 1Agent 개발(운영) 실행 방안 도출
- **수단**: 교육 과정 신설 + 인증 체계 정리 방향 논의
- **방식**: 분과별로 커리큘럼을 정리하고 발표 자료를 만든다
- **분과**: DT / 분석형 AI · AI Literacy · 생성형 AI · 전임직(생산직) 특화 · Expert · Fast Track

### 내 담당 — Expert 분과

- **산출물**: Expert 교육 커리큘럼 + 인증 체계 + 발표 자료
- **Expert의 정의**: AI Agent에 대한 전문 지식을 갖추고 직접 개발하며, S/W에 대한 지식도 해박한 사람

### 논의로 확정된 결정 (2026-10-07)

| 항목 | 결정 |
|------|------|
| Expert의 범위 | Agent를 가장 잘 만드는 개인(Builder)과, 전문 지식으로 다른 사람이 Agent를 만들도록 가이드하는 사람(Guide) 둘 다 포함 |
| Builder와 Guide의 관계 | **단계형** — 먼저 Builder로 인증받고, 그 위에 Guide 단계가 있다 |
| 인증 체계 | 분과마다 독립된 인증 (6개 분과 공통 사다리가 아님) |
| Fast Track의 정의 | 개발 전 과정(end to end)을 빠르게 교육하고 완성까지 가이드하는 커리큘럼 |
| 실습 환경 | 사내 일반 cloud 개발 환경 사용 |

### 논의로 확정된 결정 (2026-10-09)

| 항목 | 결정 |
|------|------|
| 핵심 주장 | 질 낮은 Agent가 무분별하게 쏟아지는 것을 사전에 막고, 1인 1Agent 이후 각자의 Agent가 유지·보수·고도화되도록 가이드할 Expert가 필요하다 |
| Expert의 역할 | 각 팀의 챔피언으로 활동한다. Agent·tool 마켓에 올리려면 팀 Expert의 승인을 받아야 한다 (1차 관문) |
| 승인 권한 | Guide만 승인한다. 첫 Guide 배출 전에는 초기 심사단이 대행한다. Guide가 없는 팀과 Guide 본인의 Agent는 다른 팀 Guide가 승인한다 |
| 승인 기준 | 제안서 8.5의 필수 통과 기준 + 운영 담당자·인수인계 문서 유무 |
| 대상 | 코드를 짤 수 있고, 네트워크·클라우드와 사내 제공 서비스를 이해하는 사람. 규모는 분과가 제안한다 |
| 입과 확인 | 2시간 진단 과제 + 인터뷰. 기존 실적이 있으면 면제. 32시간 준비 과정은 Expert 과정에서 뺀다 |
| 실습 환경 범위 | 사내 LLM API 호출과 배포 공간 모두 가능 → 운영 중인 Agent로 심사한다 |
| 제안서의 지위 | [실행 제안](./expert-curriculum-proposal.md)의 뼈대를 기준안으로 채택. 숫자는 파일럿 후 조정 |
| 교육 형태 | 본안은 업무 병행 12주·96시간(시나리오 A). 기존 개발자 직접 응시(D)와 Guide 승급(G) 포함. B·F는 부록, C·E는 제외 |
| 단계 수 | Builder·Guide 두 단계만 |
| Guide 승급 | 교육 이수 + 본인 Agent 1건 + 타인과 함께한 Agent 2건. 공동 개발 이력과 다른 팀 가이드 이력을 동등하게 인정한다. 공동 개발 건은 본인 기여를, 가이드 건은 가이드받은 사람의 독립 수행을 확인한다 |
| 승인 역량의 확보 | 공동 개발 이력만으로 Guide가 된 사람의 리뷰·판정 경험 공백은 Guide 교육의 리뷰·심사 실습으로 메운다. 실적 요건에 가이드 건을 따로 강제하지 않는다 |
| Fast Track 연결 | 입과 자격으로 연결하지 않는다. Fast Track 교육생 가이드는 Guide 실적으로 인정하되 의무가 아니다 |
| 첫 기수 심사자 | 사내 개발·운영 및 Agent 개발 경험자로 초기 심사단. 자동 Guide 인정 없이 우선 응시 기회 |
| 목표 규모 | 장기 목표는 팀당 Guide 1명 이상. 첫 기수는 12명 파일럿, Agent 개발 수요가 큰 팀부터 |
| 효력·갱신 | 유효 2년, 매년 활동 확인. 1년간 승인·가이드 활동이 없으면 Guide 인증은 유지하고 승인 권한만 비활성으로 둔다. 필수 기준 위반을 통과시킨 것이 확인되면 조사 후 승인 권한 정지. 인사 연계는 활동 시간의 업무 인정만 요구 |
| 임팩트 지표 | 1차 승인의 반려·보완 비율과 사유, 마켓 등록 3개월 뒤 운영 중이며 한 번 이상 개선된 Agent 비율 |
| 발표 | 양식 없음. 5단 구성(왜 필요한가 → 인재상 → 커리큘럼 → 인증 → 운영·자원). 1차는 분과별 커리큘럼 담당 구성원, 이후 임원 보고 |

### 벤치마크 후 확정된 결정 (2026-10-09)

근거는 [벤치마크 종합](./public-curriculum-benchmark-summary.md)이다. 확정 내용은 [커리큘럼 정리본](./expert-curriculum.md)과 [인증 체계 정리본](./expert-certification.md)에 담았다.

| 항목 | 결정 |
|------|------|
| Builder 시간 조정 | 총 96시간 유지. B2 12→8시간, B3 8→10시간(메모리·컨텍스트), B7 8→10시간(보안) |
| 필수로 넣는 주제 | 세션·장기 메모리와 컨텍스트 압축(B3), 관측과 자동 평가(B6·B8), MCP 서버 직접 제작(B5). 계획·성찰 패턴은 B4에서 짧게 |
| 선택으로 두는 주제 | Agent 간 프로토콜(A2A), 코딩 Agent 확장, 다중 Agent (B9) |
| 교재 | 공개 자료(Hugging Face, Microsoft)를 각색해 개념 교재로 쓰고, 실습은 사내 모델 기준 한 경로만 자체 제작. B4는 프레임워크 없이 실행 루프를 직접 구현 |
| Guide 판정 실습 | G1·G3 실습을 실제 판정으로 한다. 고의 결함이 섞인 제출물을 승인·보완·반려로 판정하고 통과 기준을 둔다. 승급 후 첫 승인 3건은 초기 심사단이 함께 확인 |
| Guide 교육 시간 | 24시간, 모듈당 6시간 유지. G2는 Carpentries 자료, G1은 Google 코드 리뷰 가이드를 각색 |
| 마켓 관문 보강 | 제출 양식에 도구별 읽기·쓰기 선언, 운영·제거 책임자, 알려진 한계. 권한이나 도구가 늘어나면 재승인. Guide 인증과 승인 권한의 활성 상태를 분리 |
| 인증 유예 대비 | 첫 기수의 인증율은 목표 지표가 아니다. 수료율과 인증율을 따로 보고하고, 통과 기준은 파일럿 뒤 근거가 있을 때만 조정 |

사무실에서 확인할 것: ⟨확인: 사내 모델의 tool calling·구조화 출력 지원⟩, ⟨확인: 마켓 운영 조직·2차 관문⟩, ⟨확인: 대상 팀 수⟩, ⟨확인: 현재 사내 Agent 수와 운영 중 비율⟩

## 2. 왜 Expert 과정이 필요한가 (초안 가설)

1인 1Agent가 실제로 돌아가려면 "각자 Agent를 만드는 다수"만으로는 부족하고, 그 다수를 받쳐 주는 소수가 필요하다는 가설에서 출발한다.

- **공통 기반을 만드는 사람**: 여러 사람이 가져다 쓰는 도구·연결부·템플릿을 누군가는 만들어야 한다.
- **품질을 판정하는 사람**: 만들어진 Agent가 현업에 써도 되는 수준인지 검토할 기준과 사람이 필요하다.
- **운영을 책임지는 사람**: 과제명이 "개발(운영)"이다. 만든 뒤 고장·오답·비용을 감당할 역량이 있어야 한다.
- **다른 분과의 강사·멘토 풀**: Expert 수료자가 다른 과정의 교육자로 순환되는 구조가 될 수 있다.

> 결정됨: 둘 다 Expert이며 Builder → Guide 단계형이다 (1장).

## 3. 인재상과 타 분과와의 경계 (초안 가설)

### 수료 후 할 수 있어야 하는 것

1. 현업 문제를 Agent로 풀 수 있는지 판단하고, 풀 수 없으면 근거를 들어 거절한다.
2. Agent를 설계·구현·평가·배포·운영까지 혼자 끝낸다.
3. 남이 만든 Agent의 코드와 설계를 리뷰한다.
4. 여러 사람이 재사용하는 공통 부품(도구, 연결부, 평가 세트)을 만든다.

### 경계가 모호한 분과

| 상대 분과 | 정리해야 할 경계 |
|-----------|------------------|
| 생성형 AI | 어디까지가 생성형 AI 과정이고 어디부터 Expert인가 (예: 노코드/프롬프트 수준 vs 코드로 직접 구현) |
| Fast Track | 정의는 확정(1장). 남은 것은 Expert와의 연결 — 수료를 Expert 입과 자격으로 볼지, Expert Guide가 Fast Track 가이드를 맡을지 (6장 Q7) |
| DT / 분석형 AI | 데이터·분석 역량을 Expert의 선수 조건으로 둘지, 무관한 별도 축으로 둘지 |

## 4. 커리큘럼 모듈 후보 (초안 가설)

Expert의 정의가 "Agent 전문성 + S/W 지식" 두 축이므로 모듈도 두 축으로 나눈다.

### 축 A — S/W 엔지니어링 기본기

| 모듈 | 다룰 내용 |
|------|-----------|
| 개발 기본 | 버전 관리, 코드 리뷰, 테스트 작성, 의존성·환경 관리 |
| 서비스 구성 | API 설계, 데이터 저장소, 인증·권한 |
| 배포·운영 | 배포 절차, 로그·모니터링, 장애 대응 |
| 보안·기밀 | 사내 데이터 취급, 권한 분리, 외부 반출 통제 |

### 축 B — AI Agent 전문성

| 모듈 | 다룰 내용 |
|------|-----------|
| LLM 동작 이해 | 토큰·컨텍스트, 모델 한계, 모델 선택 기준 |
| Agent 구조 | Agent 루프, 도구 호출, 상태 관리와 복구 |
| 컨텍스트·지식 연결 | 프롬프트 설계, 검색 증강(RAG), 사내 시스템 연결(MCP 등) |
| 평가·검증 | 평가 세트 구축, 자동 채점, 회귀 확인 |
| 안전장치 | 가드레일, 사람 승인 지점, 실패 시 동작 |
| 운영 | 관측성(Observability), 비용·지연 관리, 버전 교체 |
| 멀티 에이전트 | 역할 분담, 오케스트레이션, 언제 쓰지 말아야 하는가 |

### 축 C — 현업 적용 (캡스톤)

- 자기 부서의 실제 문제로 Agent를 만들어 운영까지 올리는 과제
- 제조 현장 특성 반영: 사내 모델·사내망 환경에서만 동작해야 한다는 제약, 문서 보안, 설비·공정 도메인 지식

> 검증할 질문: 축 A를 Expert 과정 안에서 가르칠 것인가, 입과 조건(선수 역량)으로 걸러낼 것인가? 가르치면 과정이 길어지고, 걸러내면 대상자가 줄어든다.

## 5. 인증 체계 후보 (초안 가설)

### 무엇으로 인증하는가

| 방식 | 장점 | 한계 |
|------|------|------|
| 필기·지식 시험 | 대량 평가 가능, 기준이 명확 | 실제 개발 역량을 못 가려낸다 |
| 실기 과제 (제한 시간 구현) | 구현 능력 확인 | 운영 역량은 안 보인다 |
| 산출물 심사 (운영 중인 Agent) | "개발(운영)" 목적과 직결 | 심사자 역량·공수 필요, 기준 표준화 어려움 |
| 동료 기여 (리뷰·멘토링·공통 부품) | Expert의 조직적 역할 반영 | 정량화 어려움 |

**초안 입장**: Expert는 지식 시험이 아니라 **운영 중인 Agent + 심사**로 인증한다. 필기는 입과 자격 확인 정도로만 쓴다.

### 정해야 할 설계 요소

- **등급**: Builder → Guide 단계형으로 확정. 단계 수와 Guide 승급 조건은 미정 (6장 Q9·Q10)
- **분과 간 정합**: 분과별 독립 인증으로 확정. 따라서 Expert 입과 조건을 타 분과 인증에 걸 수 없고 자체 기준이 필요하다
- **유효 기간·갱신**: 기술 변화가 빠르므로 갱신 조건이 필요한지
- **인증 이후의 역할**: 강사·멘토·리뷰어 의무를 인증 유지 조건으로 걸지
- **심사 주체**: 누가 Expert를 심사하는가 (첫 기수는 심사할 Expert가 없다)

## 6. 논의 진행 상태 (grilling)

`grilling` 방식으로 7라운드까지 진행해 2026-10-09에 논의를 마쳤다. 남은 가지는 없다. 확정된 결정은 1장에, 확정 내용을 풀어 쓴 문서는 [커리큘럼 정리본](./expert-curriculum.md)과 [인증 체계 정리본](./expert-certification.md)에 있다.

2~5장은 논의를 시작할 때의 초안 가설로, 기록으로 남긴다. 정리본과 다르면 정리본이 기준이다.

### 남은 일

- 사무실 확인 항목(1장 끝)을 채운다
- 분과 발표 자료를 만든다. 1차는 분과별 커리큘럼 담당 구성원 대상, 이후 임원 보고
