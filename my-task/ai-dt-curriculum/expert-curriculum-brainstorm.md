# Expert 분과 — 커리큘럼·인증 체계 브레인스토밍

> AI Agent를 전문적으로 개발하고 S/W 지식도 해박한 인력을 길러내는 Expert 과정의 커리큘럼과 인증 체계를 잡기 위한 출발점 정리.

**읽는 법**: 1장은 확정된 전제와 결정이다. 2~5장은 논의를 시작하기 위한 **초안 가설**이며 합의된 내용이 아니다. 6장은 논의 진행 상태로, **이어갈 때는 6장부터 읽는다.**

---

## 1. 확정된 전제

### 과제 전체

- **목적**: 제조 회사에서 1인 1Agent 개발(운영) 실행 방안 도출
- **수단**: 교육 과정 신설 + 인증 체계 정리 방향 논의
- **방식**: 분과별로 커리큘럼을 정리하고 발표 자료를 만든다
- **분과**: DT / 분석형 AI · AI Literacy · 생성형 AI · 전임직(생산직) 특화 · Expert · Fast Track

### 내 담당 — Expert 분과

- **산출물**: Expert 교육 커리큘럼 + 인증 체계 + 발표 자료
- **Expert의 정의**: AI Agent에 대한 전문 지식을 갖추고 직접 개발하며, S/W에 대한 지식도 해박한 사람

### 논의로 확정된 결정 (2026-10-07)

| 항목 | 결정 |
|------|------|
| Expert의 범위 | Agent를 가장 잘 만드는 개인(Builder)과, 전문 지식으로 다른 사람이 Agent를 만들도록 가이드하는 사람(Guide) 둘 다 포함 |
| Builder와 Guide의 관계 | **단계형** — 먼저 Builder로 인증받고, 그 위에 Guide 단계가 있다 |
| 인증 체계 | 분과마다 독립된 인증 (6개 분과 공통 사다리가 아님) |
| Fast Track의 정의 | 개발 전 과정(end to end)을 빠르게 교육하고 완성까지 가이드하는 커리큘럼 |
| 실습 환경 | 사내 일반 cloud 개발 환경 사용 |

## 2. 왜 Expert 과정이 필요한가 (초안 가설)

1인 1Agent가 실제로 돌아가려면 "각자 Agent를 만드는 다수"만으로는 부족하고, 그 다수를 받쳐 주는 소수가 필요하다는 가설에서 출발한다.

- **공통 기반을 만드는 사람**: 여러 사람이 가져다 쓰는 도구·연결부·템플릿을 누군가는 만들어야 한다.
- **품질을 판정하는 사람**: 만들어진 Agent가 현업에 써도 되는 수준인지 검토할 기준과 사람이 필요하다.
- **운영을 책임지는 사람**: 과제명이 "개발(운영)"이다. 만든 뒤 고장·오답·비용을 감당할 역량이 있어야 한다.
- **다른 분과의 강사·멘토 풀**: Expert 수료자가 다른 과정의 교육자로 순환되는 구조가 될 수 있다.

> 결정됨: 둘 다 Expert이며 Builder → Guide 단계형이다 (1장).

---

## 3. 인재상과 타 분과와의 경계 (초안 가설)

### 수료 후 할 수 있어야 하는 것

1. 현업 문제를 Agent로 풀 수 있는지 판단하고, 풀 수 없으면 근거를 들어 거절한다.
2. Agent를 설계·구현·평가·배포·운영까지 혼자 끝낸다.
3. 남이 만든 Agent의 코드와 설계를 리뷰한다.
4. 여러 사람이 재사용하는 공통 부품(도구, 연결부, 평가 세트)을 만든다.

### 경계가 모호한 분과

| 상대 분과 | 정리해야 할 경계 |
|-----------|------------------|
| 생성형 AI | 어디까지가 생성형 AI 과정이고 어디부터 Expert인가 (예: 노코드/프롬프트 수준 vs 코드로 직접 구현) |
| Fast Track | 정의는 확정(1장). 남은 것은 Expert와의 연결 — 수료를 Expert 입과 자격으로 볼지, Expert Guide가 Fast Track 가이드를 맡을지 (6장 Q7) |
| DT / 분석형 AI | 데이터·분석 역량을 Expert의 선수 조건으로 둘지, 무관한 별도 축으로 둘지 |

## 4. 커리큘럼 모듈 후보 (초안 가설)

Expert의 정의가 "Agent 전문성 + S/W 지식" 두 축이므로 모듈도 두 축으로 나눈다.

### 축 A — S/W 엔지니어링 기본기

| 모듈 | 다룰 내용 |
|------|-----------|
| 개발 기본 | 버전 관리, 코드 리뷰, 테스트 작성, 의존성·환경 관리 |
| 서비스 구성 | API 설계, 데이터 저장소, 인증·권한 |
| 배포·운영 | 배포 절차, 로그·모니터링, 장애 대응 |
| 보안·기밀 | 사내 데이터 취급, 권한 분리, 외부 반출 통제 |

### 축 B — AI Agent 전문성

| 모듈 | 다룰 내용 |
|------|-----------|
| LLM 동작 이해 | 토큰·컨텍스트, 모델 한계, 모델 선택 기준 |
| Agent 구조 | Agent 루프, 도구 호출, 상태 관리와 복구 |
| 컨텍스트·지식 연결 | 프롬프트 설계, 검색 증강(RAG), 사내 시스템 연결(MCP 등) |
| 평가·검증 | 평가 세트 구축, 자동 채점, 회귀 확인 |
| 안전장치 | 가드레일, 사람 승인 지점, 실패 시 동작 |
| 운영 | 관측성(Observability), 비용·지연 관리, 버전 교체 |
| 멀티 에이전트 | 역할 분담, 오케스트레이션, 언제 쓰지 말아야 하는가 |

### 축 C — 현업 적용 (캡스톤)

- 자기 부서의 실제 문제로 Agent를 만들어 운영까지 올리는 과제
- 제조 현장 특성 반영: 사내 모델·사내망 환경에서만 동작해야 한다는 제약, 문서 보안, 설비·공정 도메인 지식

> 검증할 질문: 축 A를 Expert 과정 안에서 가르칠 것인가, 입과 조건(선수 역량)으로 걸러낼 것인가? 가르치면 과정이 길어지고, 걸러내면 대상자가 줄어든다.

---

## 5. 인증 체계 후보 (초안 가설)

### 무엇으로 인증하는가

| 방식 | 장점 | 한계 |
|------|------|------|
| 필기·지식 시험 | 대량 평가 가능, 기준이 명확 | 실제 개발 역량을 못 가려낸다 |
| 실기 과제 (제한 시간 구현) | 구현 능력 확인 | 운영 역량은 안 보인다 |
| 산출물 심사 (운영 중인 Agent) | "개발(운영)" 목적과 직결 | 심사자 역량·공수 필요, 기준 표준화 어려움 |
| 동료 기여 (리뷰·멘토링·공통 부품) | Expert의 조직적 역할 반영 | 정량화 어려움 |

**초안 입장**: Expert는 지식 시험이 아니라 **운영 중인 Agent + 심사**로 인증한다. 필기는 입과 자격 확인 정도로만 쓴다.

### 정해야 할 설계 요소

- **등급**: Builder → Guide 단계형으로 확정. 단계 수와 Guide 승급 조건은 미정 (6장 Q9·Q10)
- **분과 간 정합**: 분과별 독립 인증으로 확정. 따라서 Expert 입과 조건을 타 분과 인증에 걸 수 없고 자체 기준이 필요하다
- **유효 기간·갱신**: 기술 변화가 빠르므로 갱신 조건이 필요한지
- **인증 이후의 역할**: 강사·멘토·리뷰어 의무를 인증 유지 조건으로 걸지
- **심사 주체**: 누가 Expert를 심사하는가 (첫 기수는 심사할 Expert가 없다)

## 6. 논의 진행 상태 (grilling)

`grilling` 방식으로 질문을 라운드 단위로 확정해 가는 중이다. 2026-10-07에 3라운드 질문까지 나간 상태에서 멈췄다. 확정된 결정은 1장에 있다. 화살표(➡️)는 Claude의 권고이며 결정이 아니다.

### 답을 기다리는 질문

| 번호 | 질문 | ➡️ 권고 |
|------|------|---------|
| Q2 | **대상과 규모** — Expert 대상자가 누구이고 몇 명인지 위에서 주어졌는가, 분과가 제안하는가 | 주어진 게 없으면 "이미 코드를 짜는 사람 중 소수, 지원 후 선발" |
| Q3 | **위에서 내려온 조건** — 분과 공통 작성 양식, 발표 일정, 청중, 분량 중 정해진 것 | 사실 확인. 양식이 없으면 "인재상 → 커리큘럼 → 인증 → 운영 방안" 4단 구성 |
| Q7 | **Fast Track 연결** — Fast Track 수료(완성한 Agent 1개)를 Expert 입과 자격으로 인정할지, Expert Guide가 Fast Track 가이드를 맡을지 | 둘 다 연결. 독립 인증이라 입과 근거가 필요하고, Guide 역량을 실제 활동으로 심사할 수 있다. Fast Track 분과와 합의 필요 |
| Q8 | **cloud 환경 범위** — 교육생이 사내 LLM을 API로 호출할 수 있는가, 만든 Agent를 띄워 둘 배포 공간이 있는가 | 사실 확인. 배포 공간이 없으면 심사 기준을 "배포 가능한 상태의 Agent + 시연"으로 낮춘다 |
| Q9 | **단계 수** — Builder·Guide 두 단계로 끝인가, 아래 준비 단계나 위 상위 단계를 더 두는가 | 두 단계만. 아래 수준은 타 분과가 맡고, 상위 단계는 Guide 배출 후 필요해지면 추가 |
| Q10 | **Guide 승급 조건** — (a) 추가 교육 이수, (b) 리뷰·멘토링·공통 부품 기여 실적, (c) 둘 다 | (c), 무게는 실적. 교육은 리뷰 기준과 심사 방법을 맞추는 짧은 과정 |
| Q11 | **첫 기수 Builder 심사자** — Guide가 아직 없는 첫 기수는 누가 심사하는가 | 분과 위원 + 사내 기존 개발 조직 전문가로 초기 심사단, 첫 Guide 배출 후 이관. 초기 심사단을 첫 Guide로 인정할지도 함께 결정 |

### 위 답이 나온 뒤에 물을 질문

| 질문 | 먼저 필요한 답 |
|------|----------------|
| Builder 인증 방식 — 운영 중인 Agent 심사인가, 시연인가 | Q8 |
| 입과 조건 — 독립 인증 아래에서 Expert 입과 자격을 무엇으로 확인하는가 | Q2, Q7 |
| 교육 형태 — 업무 병행인가 집중 과정인가, 총 기간 | Q2 |
| S/W 기본기(4장 축 A)를 과정 안에서 가르칠지, 입과 조건으로 걸러낼지 | Q2, 입과 조건 |
| Guide 단계의 커리큘럼 내용 | Q10 |
| 인증의 효력 — 인사·평가·역할 반영, 유효 기간과 갱신 | Q9, Q10 |

### 논의가 끝나면 할 일

- 2~5장의 가설을 확정 내용으로 고쳐 쓴다
- 커리큘럼 정리본, 인증 체계 정리본, 발표 자료를 만든다
