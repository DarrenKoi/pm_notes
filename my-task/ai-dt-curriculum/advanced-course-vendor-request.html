AI Agent 고급 과정 교육 요청

계속 늘어나는 팀별 AI Agent를 각 팀 안에서 이끌 챔피언을 기르는 과정을 요청합니다. 혼자 Agent를 만들 수 있는 개발자가, 그 Agent를 팀이 함께 개발·배포·운영·개선하는 체계로 올리도록 가르치는 것이 목표입니다.

왜 이 과정이 필요한가

사내 AI Agent는 팀마다 만들어 운영하고 있고 그 수가 계속 늘고 있습니다. 중앙 조직이 모든 Agent를 직접 챙길 수 없는 규모라서, 각 팀 안에 품질을 지킬 사람이 있어야 합니다.

수강 대상은 이미 혼자 Agent를 만들 수 있습니다. 부족한 것은 그다음 단계입니다.

  • 팀 개발 — 여러 사람이 각자 코딩 Agent를 쓰며 같은 저장소를 고칩니다. 컨텍스트와 결정 이력이 개인의 대화창에만 남아 팀원끼리, 그리고 팀원들의 Agent끼리 이어지지 않습니다.
  • 배포 품질 — 프롬프트나 모델을 바꿨을 때 품질이 떨어졌는지 자동으로 걸러내는 파이프라인이 없습니다.
  • 운영 — Agent가 늘수록 호출량·지연·비용이 커지는데, 어디서 문제가 생기는지 보이지 않습니다.
  • 모델 — 범용 모델로 안 풀리는 도메인 작업을 소형 모델 파인튜닝으로 풀 인력이 없습니다.

대상과 편성

  • 대상: 혼자 Agent를 설계·배포·운영해 본 개발자.
  • 선수 역량: Python, LLM API 호출, RAG·MCP·평가 기초. 이 내용은 다시 가르치지 않습니다.
  • Git은 예외: 혼자 커밋·푸시만 해 본 사람이 많습니다. 브랜치·MR·worktree 같은 팀 개발용 Git은 과정 안에서 처음부터 가르쳐 주십시오(A0). 개강 전에 2~3시간 분량의 자율 학습 자료도 부탁드립니다.
  • 편성: 수료생 수가 많지 않으므로 모든 실습을 2인 1조 5개 조로 편성합니다.

팀 개발에서 반드시 지킬 규칙 (A0 필수 내용)

브랜치 전략과 worktree 사용법은 업체에서 구성해 주십시오. 다만 아래 규칙은 교육에 반드시 넣어 주십시오.

구분규칙이유
브랜치main에 직접 push하지 않는다. main을 보호 브랜치로 설정한다리뷰·CI 없이 들어간 변경이 모두를 깨뜨린다
브랜치작업 하나 = 이슈 하나 = 브랜치 하나. 브랜치 이름에 이슈 번호를 넣는다무엇을 왜 바꿨는지 추적된다
브랜치브랜치는 짧게 유지하고 자주 main을 반영한다. 머지 후 삭제한다오래된 브랜치일수록 충돌이 커진다
MRMR은 작게 나눈다. 리뷰어 1명 이상 승인과 CI 통과 없이는 머지하지 않는다큰 MR은 리뷰가 형식이 된다
커밋커밋 메시지 규칙을 팀이 정한다(예: feat:, fix: + 무엇을 왜)이력이 곧 팀의 기억이다
커밋공유 브랜치에 force push하지 않는다다른 사람의 커밋이 사라진다
보안키·비밀번호·사내 데이터를 커밋하지 않는다. .gitignore와 커밋 전 검사로 막는다한 번 들어간 비밀은 이력에서 지우기 어렵다
보안대용량 파일·모델 가중치·데이터셋은 저장소에 넣지 않는다저장소가 무거워지고 반출 통제가 어려워진다
Agent코딩 Agent에게 main push 권한을 주지 않는다. Agent 작업은 자기 브랜치·worktree에서 한다Agent의 실수가 바로 공용 코드가 되는 것을 막는다
AgentAgent가 만든 변경도 사람이 읽고 MR을 올린다. 작성자 책임은 사람에게 있다리뷰 없이 쌓인 Agent 코드는 아무도 이해하지 못한다
Agent공유 컨텍스트 파일과 팀 rule 변경은 MR로 팀 합의를 거친다모든 팀원의 Agent 행동이 함께 바뀐다

  1. Git이 익숙하지 않은 수강생을 하루 안에 브랜치·MR·worktree까지 끌어올린 경험이 있습니까? 진도가 처지는 수강생은 어떻게 돕습니까?
  2. A1을 어떤 도구와 방식으로 가르칩니까? 팀이 각자의 LLM으로 같은 저장소를 개발하는 사례를 보여주실 수 있습니까?
  3. GitLab CI에 LLM 평가 게이트를 넣은 실습 예시가 있습니까? 폐쇄망 GitLab 환경에 적용해 본 경험이 있습니까?
  4. 가상 프로젝트와 평가 세트를 제조 업무와 비슷하게 만들 수 있습니까?
  5. Phoenix 셀프호스팅을 실습 환경에 포함할 수 있습니까?
  6. 파인튜닝 실습에서 5개 조가 동시에 학습하려면 어느 정도 GPU가 필요하고, 야간 학습이 실패하면 어떻게 대응합니까?
  7. 교육 후 사내 강사가 재운영할 수 있도록 교재·코드·평가 세트를 넘겨받을 수 있습니까?

후속 과정 후보: 챔피언 심화 3일

2주 과정에 넣으면 깊이가 무너지는 주제입니다. 아래 두 과정은 챔피언 역할에 바로 필요해서 선택 견적을 함께 받으려 합니다. 진행 여부는 기본 과정 결과를 보고 정합니다. 기본 과정 A2에는 품질 게이트 운용에 필요한 최소한의 평가 설명이 들어가야 합니다.

평가 설계 심화 (12시간)

평가를 "돌리는" 수준에서 평가를 "믿을 수 있게 만드는" 수준으로 올립니다.

  • 최종 답변만 볼지, 도구 선택·단계별 경로까지 볼지
  • 운영 추적의 실패 사례를 평가 세트로 편입, 버전관리, 낡은 문항 정리
  • 규칙 비교 · LLM-as-judge · 사람 판정 중 무엇을 언제 쓸지
  • LLM-as-judge와 사람 판정의 일치도 보정, judge의 편향
  • LLM 출력의 흔들림을 감안해 점수 차이가 진짜인지 판단
  • 품질 게이트의 임계값과 허용 하락폭 설정

Agent 보안 레드팀 (12시간)

기본 과정 A6은 준비된 공격 시나리오로 방어 정책을 검증하는 데까지 다룹니다. 레드팀은 공격을 직접 설계·자동 생성하고 결과를 분석합니다. 공격자 입장에서 직접 뚫어 보고 뚫린 사례를 평가 세트에 넣어 다시 뚫리지 않게 만듭니다.

  • 직접·간접 프롬프트 주입, 탈옥, 도구를 이용한 권한 상승
  • 시스템 프롬프트·타 사용자 데이터 유출, 악성 MCP 서버
  • 무한 루프·비용 폭주
  • OWASP Top 10 for LLM Applications를 점검 목록으로 활용
  • 오픈소스 레드팀 도구(예: garak, PyRIT, promptfoo)로 공격 자동화
  • 뚫린 사례를 회귀 평가 세트에 넣고 CI 게이트에 연결

본 자료의 시간 배분은 예시이며 교육 업체가 조정합니다.
