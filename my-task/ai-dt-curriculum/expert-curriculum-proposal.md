# Expert 양성 방향·교육 과정·인증 시스템 제안

> 제조 회사의 1인 1Agent 개발·운영을 지원할 Expert를 Builder → Guide로 양성하는 실행안. 대상과 환경에 따라 선택할 수 있도록 7개 시나리오를 비교한다.

## 읽기 안내

- 먼저 1장의 추천 목록과 4장의 시나리오 비교표를 읽는다.
- 실제 교육 편성은 5~7장, 인증 제도는 8~10장을 읽는다.
- 첫 기수 준비와 의사결정은 11~13장을 읽는다.
- 기존에 확정한 전제와 이번 제안은 구분했다. 교육 시간, 인원, 점수, 갱신 주기는 모두 검토용 제안값이다.
- 사내 모델 API 제공 여부, 배포 공간, 교육 대상 규모, 업무시간 확보, 인사 연계는 확인되지 않았다. 조건별 대안을 함께 제시한다.
- 조직 전체의 교육 제도와 시스템을 실제로 도입한 문서가 아니라, Expert 분과에서 검토할 설계안이다.

## 1. 먼저 검토할 추천 목록

| 구분 | 도입하면 좋은 항목 | 추천 이유 |
|---|---|---|
| 방향 | 개인 개발 역량을 검증하는 Builder와 타인을 지도하는 Guide | 기존 Builder → Guide 결정을 교육·평가에 연결한다 |
| 방향 | 문제 정의·S/W·Agent·평가·운영을 끝까지 다루는 교육 | 실행 시연 이후 유지보수까지 책임질 수 있어야 한다 |
| 방향 | 특정 도구보다 원리와 변경 대응을 가르치는 과정 | 사내 모델·프레임워크가 바뀌어도 역량을 유지한다 |
| 방향 | Agent와 일반 자동화 중 적합한 방법을 고르는 훈련 | Agent가 필요 없는 업무를 구분할 수 있어야 한다 |
| 교육 | 입과 진단 후 필요한 사람에게만 32시간 준비 과정 | 선수 역량 차이를 본 과정에서 반복해서 메우지 않는다 |
| 교육 | 업무 병행 12주·96시간 Builder 표준 과정 | 강의, 실습, 실제 과제를 한 일정으로 운영한다 |
| 교육 | 공통 필수 과정과 직무 선택 실습 | 동일한 인증 기준으로 서로 다른 업무를 다룬다 |
| 교육 | 정상 동작과 장애·권한·중복 실행을 함께 다루는 캡스톤 | 성공한 시연 하나로 역량을 판단하지 않는다 |
| 교육 | Builder 인증 후 Guide 교육 24시간과 현장 활동 | 리뷰·멘토링은 별도 역량으로 검증한다 |
| 인증 | 개인 실기 + 산출물 + 운영 증거 + 구술 심사 | 팀 성과와 개인 역량을 구분한다 |
| 인증 | 총점 외 필수 통과 기준 | 높은 기능 점수로 보안·운영 결함을 상쇄하지 못하게 한다 |
| 인증 | 수료증과 역량 인증 구분 | 교육을 들었다는 사실과 독립 수행 역량을 구분한다 |
| 인증 | 기존 개발자에게 동일 심사의 직접 응시 경로 | 이미 가진 역량에 대해 교육 시간을 강제하지 않는다 |
| 운영 | 초기 심사단과 공개된 평가표 | 첫 기수부터 판단 기준을 맞춘다 |
| 운영 | 인증 대장·증거 저장소·기존 학습 시스템 활용 | 첫 기수에 별도 인증 플랫폼을 만들 필요가 없다 |

추천 시작점은 시나리오 A의 소규모 표준 과정이다. 인원 확보보다 교육 시간을 보장하고, 심사 가능한 과제와 환경을 준비하는 일을 먼저 한다. 첫 Builder 기수 이후 Guide 실증을 거쳐 부서 확산 여부를 판단한다.

## 2. 왜 필요한가? (Why)

### 2.1 조직에서 해결할 문제

1인 1Agent를 추진하면 개발 이후에도 질문이 남는다.

- 이 업무에 Agent가 필요한가?
- 사내 시스템과 연결할 때 어느 권한까지 허용할 것인가?
- 잘못된 답변과 실패를 어떤 기준으로 판정할 것인가?
- 모델이나 문서가 바뀌어도 기존 기능이 유지되는가?
- 담당자가 이동해도 다른 사람이 운영할 수 있는가?
- 다른 구성원이 비슷한 문제를 풀 때 누가 검토하고 지도할 것인가?

Expert 과정은 이 질문에 설계·코드·시험 결과·운영 기록으로 답할 사람을 기른다. 1인 1Agent는 개인이 업무에 맞는 Agent를 개발·관리할 수 있다는 목표로 해석한다. 모든 사람이 별도 서버를 운영하거나 같은 기능을 중복 개발해야 한다는 뜻으로 운영하지 않는다.

### 2.2 교육의 성공 정의

| 단계 | 교육 후 수행할 수 있어야 하는 일 | 확인할 증거 |
|---|---|---|
| Builder | 자신의 업무 과제를 설계·구현·평가하고 정해진 범위에서 운영한다 | 개인 변경 실기, 실행 가능한 코드, 평가 결과, 복구·인수인계 기록 |
| Guide | 다른 사람의 설계와 코드를 검토하고, 문제를 진단하며 스스로 개선하도록 지도한다 | 리뷰 전후 차이, 멘티의 독립 수행, 재사용·지도 실적, 심사 기준 적용 |

Agent 제작 개수와 강의 출석만으로 성공을 판단하지 않는다. 인증 직후 독립 수행 여부와 이후 활용·유지 현황을 확인한다.

## 3. 핵심 개념 (What)

### 3.1 유지할 기존 결정과 새 제안

| 항목 | 기존 문서에서 확정한 내용 | 이번 문서의 제안 |
|---|---|---|
| 목적 | 제조 회사의 1인 1Agent 개발·운영 | 독립 개발·운영 역량과 조직 내 지도 역량을 함께 확보 |
| Expert 범위 | Builder와 Guide 모두 포함 | 역할별 학습 목표·심사 기준 명시 |
| 단계 | Builder → Guide | 인증 등급은 두 단계로 시작 |
| 분과 관계 | 분과별 독립 인증 | 타 분과 수료·인증은 참고 증거로 활용하고 필수 자격으로 강제하지 않음 |
| Fast Track | 개발 전 과정을 빠르게 교육하고 완성까지 지도 | 수료자가 입과 진단 또는 Builder 심사에 응시하도록 연결 |
| 실습 환경 | 사내 일반 cloud 개발 환경 | API·배포·데이터 접근 확인 후 운영 시나리오 선택 |

근거는 [기존 Expert 브레인스토밍의 확정 전제](./expert-curriculum-brainstorm.md)다. 기존 문서의 열린 질문을 확정된 조직 정책처럼 쓰지 않았다. 타 분과 독립 인증 자체가 상호 입과 요건을 금지하는 것은 아니지만, 이 제안에서는 독립적인 역량 진단을 우선한다.

### 3.2 양성 방향 후보

| 방향 | 교육 중심 | 장점 | 주의할 점 | 채택 제안 |
|---|---|---|---|---|
| 기술 심화형 | Agent 구조, 도구, 검색, 디버깅 | 기술 문제를 직접 해결할 사람 확보 | 프레임워크 사용법만 가르치면 운영 역량이 빠짐 | 공통 과정의 필수 기반 |
| 업무 적용형 | 현업 문제, 데이터, 효과 검증 | 실제 업무 활용과 연결 | 쉬운 시연 과제로만 평가하면 기술 깊이를 확인하기 어려움 | 모든 Builder의 캡스톤에 적용 |
| 운영 신뢰성형 | 권한, 평가, 배포, 관측, 복구 | 유지 가능한 서비스 개발 | 현장 접근권한을 얻지 못한 교육생의 평가가 어려움 | 공통 필수, 환경별 증거 구분 |
| 조직 확산형 | 리뷰, 멘토링, 표준, 재사용 | 다른 분과와 부서의 수행 능력 확대 | 개발 역량 없이 강의만 잘하는 사람을 Expert로 인정할 위험 | Builder 인증 이후 Guide에 적용 |
| 모델 연구형 | 학습, 미세조정, 고급 수학 | 별도 모델 개발 직무에 유용 | 일반 Agent 개발·운영 목표보다 범위가 큼 | 과제에 필요할 때 선택 심화 |

권고는 기술 심화·업무 적용·운영 신뢰성을 Builder에 묶고, 조직 확산을 Guide에서 검증하는 방식이다.

Anthropic은 사전에 정한 경로를 따르는 workflow와 모델이 실행 경로를 결정하는 agent를 구분하고, 필요한 복잡도부터 선택하도록 권고한다. 이 원칙을 교육에 적용해 규칙 기반 처리, 단일 LLM 호출, workflow, agent를 비교하는 실습을 둔다. 이 교육 구성은 본 문서의 제안이다. [공식 근거](https://www.anthropic.com/engineering/building-effective-agents)

## 4. 어떻게 운영할 것인가? (How): 7개 시나리오

### 4.1 비교 목록

시간은 교육생 1인 기준이다. 별도 표시가 없으면 강의·지도 실습·자기 과제 수행을 모두 포함한다. 인증 심사와 운영 관찰에 필요한 기간은 구분했다.

| 시나리오 | 적용 조건 | 교육 구성·기간 제안 | 인증 경로 | 주요 한계 |
|---|---|---|---|---|
| A. 업무 병행 표준형 | 코드 작성 경험과 주 8시간 확보 | Builder 12주·96시간 | 동일 Builder 심사, 업무 사용 관찰 후 확정 | 업무시간 보호가 없으면 과제만 야간으로 밀림 |
| B. 집중형 | 단기 전담 배정 가능 | 3주·90시간 + 후속 2주·6시간 | 교육 총 96시간, 이후 관찰·심사 | 집중 교육 종료 시점에는 운영 증거 부족 |
| C. 비개발자 전환형 | 현업 전문성은 있으나 개발 경험 부족 | 준비 4주·32시간 + A의 12주·96시간 | 준비 진단 통과 후 동일 Builder 심사 | 128시간으로 모든 비개발자가 Expert가 된다고 보장할 수 없음 |
| D. 기존 개발자 인증형 | 이미 Agent 또는 서비스를 개발·운영 | 진단 후 필요한 모듈만, 학습 시간 개별 편성 | 동일 심사에 직접 응시 | 기존 프로젝트도 본인 기여와 증거 최신성을 확인해야 함 |
| E. 환경 제약형 | 사내 API·데이터·배포 일부 미제공 | A의 96시간을 합성 데이터·격리 환경으로 수행 | 수료와 모듈 성취 기록, 최종 Builder 인증은 증거 보완 후 | 모의 실습을 실제 운영 증거로 대체할 수 없음 |
| F. 현장 특화형 | 교대근무·설비 접근 제약이 큼 | 16주·96시간, 주 6시간 분산 | 현장 승인 범위 내 Builder 심사 | 실제 설비 변경은 교육 실습만으로 허가되지 않음 |
| G. 부서 확산형 | 인증 Builder와 지도 수요 확보 | Guide 4주·24시간 + 8주 활동·32시간 | Guide 실적 심사 | 강의 횟수만 늘어나면 멘티 자립을 확인할 수 없음 |

Guide의 활동 시간 32시간은 멘토링·리뷰·정리의 예산 가정이다. 멘티의 개발 시간은 포함하지 않는다. A~F의 Builder 학습 경로와 G의 Guide 승급 경로는 이어서 사용할 수 있다.

### 4.2 A. 업무 병행 표준형: 첫 기수 추천

- 대상은 기초 코드를 읽고 API를 호출할 수 있는 현업 개발자·자동화 담당자다.
- 예시 규모는 12명, 4명당 멘토 1명이다. 실제 모집 규모가 아니다.
- 주 8시간은 지도 학습 3시간과 실습·개인 과제 5시간으로 나눈다.
- 매주 과제 산출물을 제출하고 4·8·12주에 중간 점검을 한다.
- 캡스톤은 2인 협업을 허용하되 개인별 코드 기여와 실기를 심사한다.
- 운영 관찰은 승인된 사용자·데이터 범위에서 4주를 제안한다. 마지막 4주 실습과 겹칠 수 있으나 미완료자는 후속 관찰 후 인증한다.

과제 책임자와 부서장이 업무시간을 확보해 주지 못하면 B 또는 다음 기수로 배정한다. 일정표에 교육시간만 넣고 현업 업무량을 그대로 두는 방식은 피한다.

### 4.3 B. 집중형: 빠른 구축과 후속 운영을 분리

- 1주차는 S/W·LLM·도구, 2주차는 검색·평가·권한, 3주차는 캡스톤과 복구 실습에 집중한다.
- 3주 동안 주 30시간, 후속 2주에 주 3시간을 편성해 총 96시간을 맞춘다.
- 집중 교육 종료 때는 수료 여부를 판단하고, Builder 인증은 후속 운영 증거와 개인 심사를 받은 뒤 발급한다.
- 전담 시간이 실제로 확보되고 개발 환경이 사전 준비된 경우에 선택한다.

후속 지도 6시간은 전체 운영 노동을 뜻하지 않는다. 배포 유지·사용자 대응은 승인된 업무 배정으로 별도 확보한다.

### 4.4 C. 비개발자 전환형: 준비 과정을 따로 둔다

- Python 또는 조직 표준 언어, Git, API, 예외 처리, 테스트를 32시간에 집중한다.
- 준비 과정 종료 때 개인 진단 과제를 다시 수행한다.
- 기초 미달자는 추가 학습 후 재진단한다. Expert 본 과정에서 기초 교육을 무제한 연장하지 않는다.
- 업무 지식을 과제와 평가 사례에 활용하되 개발·운영 통과 기준을 낮추지 않는다.
- 코딩 경험이 거의 없는 경우 Fast Track 등을 준비 경로로 활용할 수 있다. 타 분과와 실제 연결은 별도 합의가 필요하다.

### 4.5 D. 기존 개발자 인증형: 교육 면제와 인증 면제를 구분

- 최근 프로젝트의 코드·평가·운영 증거를 제출하고 동일한 개인 실기에 응시한다.
- 진단 결과에 따라 Agent 평가, 권한, 복구 등 부족한 모듈만 수강한다.
- 기존 S/W 경력이나 외부 자격증만으로 Builder 인증을 자동 발급하지 않는다.
- 실적 인정은 승인된 증거 범위로 제한하며, 소스·운영 기록을 외부로 제출하지 않는다.

### 4.6 E. 환경 제약형: 검증된 범위를 기록

| 제공되지 않는 것 | 교육 대안 | 증거의 한계·후속 조치 |
|---|---|---|
| 사내 LLM API | 계약된 응답을 반환하는 모의 도구로 흐름·오류 처리를 실습 | 모델 동작·성능은 미검증. 승인된 실제 모델 평가 필요 |
| 실제 업무 데이터 | 합성·비식별 데이터로 데이터·권한 테스트 | 현업 데이터 적합성과 업무 효과는 미검증 |
| 배포 공간 | 격리 실습 환경에서 배포·중단·복구 시연 | 실제 서비스 운영은 미검증 |
| 업무 사용자 접근 | 평가자가 역할을 맡아 업무 시나리오 수행 | 실제 사용자 활용·운영 관찰은 미검증 |

이 경로에서는 수료증과 확인된 모듈 성취만 기록한다. 정식 Builder 인증은 승인된 실제 모델, 대표 업무 데이터, 사용자 사용·운영 관찰 증거를 보완한 뒤 발급한다. 조직이 실습 수준의 별도 인증을 원한다면 명칭과 효력을 별도 합의해야 하며, 이 초안에서는 새 등급을 만들지 않는다.

### 4.7 F. 현장 특화형: 현장 지식과 실행 권한을 함께 다룬다

- 공통 96시간의 목표는 유지하고 짧은 실습으로 분산한다.
- 선택 과제는 현장 문서 검색, 이력 조회, 보고서 초안, 점검 안내 등으로 구성한다.
- 읽기·추천·쓰기 동작을 분리하고, 승인받은 실습 시스템에서만 쓰기·복구 시험을 한다.
- 설비 제어가 필요한 과제는 시뮬레이터나 별도 테스트 환경을 먼저 사용한다.
- 실제 설비 적용은 현장의 기존 변경·안전·운영 승인 절차를 따른다.
- 교대근무로 출석이 어려운 학습자에게 녹화 학습과 같은 기준의 개인 실기를 제공한다.

### 4.8 G. 부서 확산형: Guide를 검증한 뒤 확대

- Builder 인증자를 대상으로 리뷰·지도·평가자 훈련을 실시한다.
- Guide 후보 1명당 멘티 2명을 예시로 배정한다.
- 8주 동안 설계·구현·평가·운영 점검을 지도하고 전후 증거를 수집한다.
- 멘티가 후보자 대신 자신의 Agent를 수정·설명·복구할 수 있는지 확인한다.
- Guide 후보에게 모든 멘티의 코드를 대신 작성하게 하지 않는다.
- 해당 Guide 후보의 지도 실적을 심사하는 사람은 후보의 단독 직속 멘토와 분리한다.

### 6.3 선택 심화 후보 목록

| 선택 주제 | 적합한 직무·과제 | 실습 방향 |
|---|---|---|
| 문서·RAG 심화 | 절차서·지식 검색 | 출처·문서 갱신·권한별 검색 결과 비교 |
| 업무 API·MCP 도구 | 이력 조회·업무 처리 | 입력·출력 계약과 접근 범위 검증 |
| 데이터·분석 도구 | 표·로그 분석 | 계산은 코드·분석 도구로 수행하고 LLM은 선택·설명을 담당 |
| 이미지·문서 이해 | 이미지·도면·스캔 문서 | 읽기 실패·단위·좌표·낮은 신뢰도 처리 |

6시간 선택 실습은 전문 분야 전체 숙련을 뜻하지 않는다. 실제 필요가 확인되면 별도 심화 과정으로 확장한다. 모든 교육생에게 다중 Agent나 미세조정을 의무화하지 않는다.

### 6.4 캡스톤 과제 후보

| 과제 | 핵심 역량 | 심사에서 확인할 실패 |
|---|---|---|
| 절차서·지식 탐색 Agent | 검색, 출처, 최신성, 권한 | 출처 없는 답변·오래된 지침·접근 불가 자료 |
| 업무 이력 분석 보조 Agent | 도구 호출, 계산 검증 | 잘못된 필터·빈 결과·단위 혼동 |
| 보고서 작성 Agent | 근거 정리, 구조화, 사람 검토 | 허구 수치·누락·출처 불일치 |
| 업무 요청 처리 Agent | 상태, 승인, 중복 방지 | 승인 누락·중복 등록·타인 권한 사용 |
| GUI 작업 보조 Agent | 화면 상태, 중단·복구 | 화면 변경·인식 실패·잘못된 대상 선택 |
| 기존 Agent 개선 | 코드 이해, 회귀, 운영 | 개선과 함께 기존 기능이 깨지는 문제 |

과제마다 사용자 1명 이상, 과제 책임자, 허용 데이터, 기준선, 수행 범위를 교육 초기에 정한다. 기준선은 기존 수작업 또는 기존 자동화 결과다. 교육용 증거는 회사가 승인한 저장소에 둔다.

### 7.2 현장 활동 8주·32시간 예시

- 멘티 2명에게 각각 설계·구현·평가·운영 점검을 제공한다.
- 서로 다른 산출물에 대한 실질 리뷰 3건 이상을 남긴다.
- 자신의 공통 도구·평가 세트·가이드 중 하나를 다른 사람이 실제 사용하고 피드백하도록 한다.
- 재사용할 개발 항목이 없으면 새로운 공통 부품을 억지로 만들지 않는다. 기존 부품의 개선·적용 가이드도 인정한다.
- 30분 설명과 30분 실습 지도에서 학습자가 수행하는지 관찰한다.
- 마지막에 멘티가 독립 변경 과제를 수행하도록 하고, 후보자의 직접 코딩 도움 없이 평가한다.

건수는 심사 증거를 모으기 위한 제안 최소치다. 리뷰 3건을 제출했다는 사실만으로 통과시키지 않는다. 발견한 문제, 개선 결과, 멘티의 독립 수행이 있어야 한다.

| 필기 시험 | 개념 이해 | 실제 구현·운영 미확인 | 진단·학습 점검 |
| 개인 실기 | 직접 변경·디버깅 | 장기 운영 미확인 | Builder 필수 |
| 프로젝트 산출물 심사 | 설계·구현·평가 일관성 | 팀 성과가 개인 역량을 가릴 수 있음 | 개인 기여 검증과 함께 필수 |
| 운영 증거 심사 | 사용·장애·개선·복구 | 환경과 과제에 따라 기회 차이 | 범위·조건을 기록해 필수 |
| 구조화 구술 | 선택 이유와 문제 대응 | 평가자 편차 | 동일 핵심 질문·평가표로 필수 |
| 리뷰·멘토링 실적 | 조직 내 지도 역량 | 활동 건수만으로는 질을 판단하기 어려움 | Guide 필수 |
| 외부 자격증·배지 | 외부 과정에서의 성취 | 사내 업무·권한·운영을 직접 증명하지 않음 | 참고 자료, 내부 인증 자동 대체 없음 |

OPM의 구조화 인터뷰는 공통 질문과 평가 기준을 사용하는 방식이다. 이를 참고해 개인 심사의 핵심 질문과 채점 근거를 맞추는 방안을 제안한다. [공식 근거](https://www.opm.gov/policy-data-oversight/assessment-and-selection/structured-interviews/)

### 8.2 수료와 인증 구분

| 기록 | 발급 조건 제안 | 뜻 |
|---|---|---|
| Builder 과정 수료 | 필수 모듈·과제 완료와 참여 확인 | 정해진 과정을 완료함 |
| Expert Builder | 개인 실기·산출물·운영·구술의 통과 | 기록된 업무 범위에서 독립 개발·운영 역량 확인 |
| Guide 과정 수료 | Guide 교육·연습 완료 | 지도·심사 방법을 학습함 |
| Expert Guide | 유효한 Builder 인증 + 지도 활동·심사 통과 | 개발 역량을 바탕으로 타인의 수행을 지도할 수 있음 |

Builder 인증은 다른 Agent의 출시 승인이나 설비 제어 권한을 자동 부여하지 않는다. Guide 인증도 조직의 정식 출시·보안 심사 권한을 자동 부여하지 않는다. 직무 배정과 권한은 별도 조직 절차로 정한다.

### 8.3 Builder 심사 절차

1. 제출물과 개인 기여를 확인한다.
2. 평가자가 정한 입력으로 같은 버전의 Agent를 다시 실행한다.
3. 90분 개인 실기에서 요구사항 변경과 장애 진단을 수행한다.
4. 운영 관찰·복구·인수인계 증거를 검토한다.
5. 30분 구술에서 대안, 실패 원인, 권한, 운영 판단을 확인한다.
6. 점수와 필수 통과 기준을 함께 판정한다.
7. 통과·보완·미통과와 근거를 기록한다. 보완자는 부족 항목을 다시 평가한다.

실기에는 승인된 AI 코딩 도구와 문서를 허용한다. 사용 내역을 기록하고, 생성 코드를 설명·수정·검증할 수 있어야 한다. 타인의 대리 수행은 허용하지 않는다. 같은 난이도의 변형 과제를 제공하고 도구·네트워크 조건을 맞춘다.

### 8.4 Builder 평가표: 100점

| 영역 | 배점 | 통과 증거 |
|---|---:|---|
| 업무 정의·해법 선택 | 10 | 기준선, 성공·실패 기준, Agent 선택 근거 |
| S/W·개인 구현 | 20 | 재현, 코드 이해, 변경 실기, 오류 처리 |
| Agent·도구·지식 연결 | 20 | 도구 계약, 상태·종료, 검색·연결 동작 |
| 평가·회귀 | 20 | 평가 세트, 기준선 비교, 미공개 입력 확인 |
| 보안·권한·통제 | 15 | 접근 제한, 비밀정보 관리, 승인·주입 시험 |
| 배포·운영·인수인계 | 15 | 사용 관찰, 자원·지연 기록, 장애 대응·복구 |
| 합계 | 100 | 모든 영역을 평가 |

채점은 영역별 0~4단계를 배점에 환산한다. 영역 점수 = 배점 × 단계 ÷ 4이며 소수점은 총점 계산 후 첫째 자리까지 표시한다.

| 단계 | 공통 판정 기준 |
|---|---|
| 0 | 증거가 없거나 실행 불가 |
| 1 | 설명은 있으나 핵심 요구사항이 동작하지 않음 |
| 2 | 정상 경로는 동작하지만 주요 예외·검증이 부족 |
| 3 | 요구사항과 주요 예외를 독립 수행하고 재현 가능한 증거 제공 |
| 4 | 3단계에 더해 변경·미공개 입력에서 효과와 한계를 검증 |

권고 통과선은 총점 80점 이상, 모든 영역 3단계 이상, 아래 필수 기준 모두 통과다. 3단계만 받은 경우 총점 75점이므로 일부 영역에서 추가 검증이 필요하다. 이 기준은 기수 시작 전에 공개하고, 파일럿 후 다음 기수 기준을 조정한다.

### 8.5 총점으로 상쇄하지 않는 필수 기준

- 다른 사용자·조직의 허용되지 않은 정보에 접근하지 않는다.
- 비밀정보를 코드·응답·로그에 노출하지 않는다.
- 승인이 필요한 쓰기 동작은 승인 전 실행되지 않는다.
- 재시도·중복 요청이 업무를 중복 처리하지 않는다.
- 도구 실패·컨텍스트 초과·예산 소진에서 종료 또는 정해진 대체 동작을 수행한다.
- 모르는 질문이나 근거가 없는 판단을 성공 처리하지 않는다.
- 평가·운영 결과를 조작하지 않고 개인 기여를 설명한다.
- 개인 실기에서 요구사항 변경과 장애 원인 설명·복구를 수행한다.

해당 기능이 없는 과제는 관련 시험을 무조건 면제하지 않는다. 예를 들어 읽기 전용 Agent는 쓰기가 불가능함을 증명하고, 개인 실기에서 공통 쓰기·승인·중복 처리 시험을 수행한다.

NIST AI RMF와 생성형 AI 프로파일은 개발·사용·평가 과정의 신뢰성과 위험 관리를 다룬다. 여기서는 교육생이 위험을 시험 가능한 요구사항으로 바꾸게 하는 참고 틀로 사용한다. 위 통과선과 인증 등급은 NIST의 요구사항이 아닌 내부 제안이다. [공식 근거](https://www.nist.gov/itl/ai-risk-management-framework)

### 8.6 운영 증거 기준

관찰 기간은 승인된 사용 범위에서 4주를 제안한다. 기간만 채우지 말고 실행 수, 입력 유형, 실패·중단, 사람 개입, 자원·지연을 함께 기록한다.

- 실제 사용자 사용 기록과 미리 합의한 업무 결과 판정을 제출한다.
- 최소 한 번의 복구·중단·재개 시험을 안전한 환경에서 수행한다.
- 실제 장애가 없으면 장애를 주입한 시험 결과로 복구 역량을 검증한다.
- 기준선과 같은 대표 입력으로 비교하고 실패 사례를 숨기지 않는다.
- 사용 빈도가 낮으면 관찰 기간을 연장하고, 부족한 유형은 별도 시험으로 보완한다.
- 실제 사용과 추가 시험을 결과표에서 분리한다.
- 운영 증거가 미완료라면 교육은 수료 처리하되 Builder 인증을 유예한다.

성과 지표는 과제별로 정한다. 검색 과제의 정답·근거 일치와 업무 처리 과제의 완료·중복 방지는 같은 지표로 뭉치지 않는다. 작은 평가 세트로 현업 전체의 안전이나 품질을 보증하지 않는다.

## 9. Guide 인증과 심사 운영

### 9.1 Guide 평가표: 100점

| 영역 | 배점 | 확인 증거 |
|---|---:|---|
| 설계·코드 리뷰 | 30 | 결함 근거, 우선순위, 수정 전후 확인 |
| 멘토링·학습자 자립 | 30 | 진단, 지도 기록, 멘티 독립 수행 |
| 재사용·운영 전파 | 20 | 타인의 실제 적용과 피드백 반영 |
| 평가·설명·심사 일치 | 20 | 공통 샘플 채점, 근거 설명, 지도 시연 |
| 합계 | 100 | Builder 인증이 유효해야 응시 가능 |

Builder와 같은 0~4단계 환산, 총점 80점 이상, 모든 영역 3단계 이상을 제안한다. 멘티가 완성한 Agent 수는 참고 지표다. 환경 제약으로 배포하지 못해도 후보자의 지도 품질을 평가할 수 있으나, 멘티가 직접 변경·시험하는 증거는 필요하다.

### 9.2 첫 기수 심사자 확보

- 사내 S/W 개발·운영 경험자와 Agent 개발·평가 경험자로 초기 심사 풀을 구성한다.
- 후보 1명당 기술 심사자 2명이 독립 채점한다. 과제 책임자는 업무 적합성 확인에 참여한다.
- 보안·권한 쟁점이 있으면 해당 담당자가 필수 기준 판정에 참여한다.
- 직속 멘토나 공동 개발자는 자신이 지도·개발한 부분의 단독 심사자가 되지 않는다.
- 기존 직급이나 심사 참여만으로 초기 심사자에게 Guide 인증을 자동 부여하지 않는다.
- 초기 심사 풀 후보에게 샘플 과제 리뷰와 장애 진단을 수행시켜 심사 역량을 확인한다.
- 충분한 심사자를 확보하지 못하면 기수 규모를 줄이고 확정 인증을 유예한다.

### 9.3 심사 편차·재응시·이의제기

- 첫 심사 전 통과·보완·미통과 샘플을 함께 채점해 해석을 맞춘다.
- 심사자 총점 차이가 10점을 넘거나 필수 기준 판정이 다르면 제3자가 재검토한다.
- 초기 채점과 조정 근거를 모두 남긴다.
- 미통과자는 결함, 필요한 증거, 재응시 범위를 받는다.
- 보완 기한은 결과 통지 후 4주, 이의제기는 통지 후 10영업일을 제안한다.
- 이의제기는 원심사의 단독 심사자가 결정하지 않는다.
- 학습자는 증거와 평가표를 열람하되 미공개 문항과 다른 사람의 기밀 자료는 공유하지 않는다.

## 10. 인증 기록·갱신·활용

### 10.1 인증 시스템 도입 옵션

| 옵션 | 구성 | 도입 시점 제안 |
|---|---|---|
| 최소 운영 | 기존 LMS 또는 승인된 문서함, 인증 대장, 평가표, 증거 링크 | 첫 기수 |
| 조직 확산 | 기존 학습·인사 시스템에 상태·이력·유효기간 연동 | 반복 기수에서 조회·관리 수요가 확인될 때 |
| 디지털 배지 | 검증 가능한 발급자·기준·증거 메타데이터 | 외부 이동성이나 플랫폼 간 교환이 필요할 때 |

먼저 최소 운영을 도입한다. 승인된 저장소가 기존 시스템으로 충분하면 별도 웹서비스를 개발하지 않는다.

1EdTech Open Badges는 성취, 발급자, 수여자, 기준과 증거를 표현하는 방식을 제공한다. 배지 표준은 평가의 질을 대신 보증하지 않으므로 심사 기준부터 정한다. 외부 배지를 도입하더라도 내부 코드·데이터·운영 로그를 공개하지 않는다. [공식 근거](https://www.1edtech.org/standards/open-badges)

### 10.2 인증 대장에 남길 항목

| 항목 | 기록 예 |
|---|---|
| 인증 식별자·수여자 | 내부 인증 ID, 조직이 허용한 개인 식별정보 |
| 인증 단계·상태 | Builder 또는 Guide, 유효·갱신대기·만료·효력정지 |
| 기준 버전 | 심사에 사용한 교육·평가표 버전 |
| 발급·만료일 | 유효기간 산정과 갱신 알림 |
| 검증 범위 | 과제 유형, 사용 환경, 역할·권한 범위 |
| 평가 증거 | 코드 버전, 평가 결과, 운영 관찰, 개인 실기 기록 |
| 심사 근거 | 영역별 점수, 필수 기준, 심사자, 보완·이의 이력 |
| AI 도구 사용 | 사용한 도구와 개인 수행 확인 기록 |
| Guide 활동 | 리뷰·지도·재사용 증거와 기여 범위 |
| 열람·보존 | 접근권한과 조직이 승인한 보존·삭제 기준 |

인증 대장에는 증거 링크와 요약을 둔다. 원본 기밀 자료를 복제하지 않는다. 심사·이의제기에 필요한 증거는 승인된 보존기간 동안 접근 가능하도록 관리한다.

### 10.3 갱신안

- 인증 유효기간은 2년을 제안한다.
- 매년 최근 활동·검증 환경·주요 변경사항을 확인한다.
- Builder는 최근 12개월 내 평가 갱신·운영 개선·장애 대응·동등한 실기 중 하나로 현재 역량을 보인다.
- Guide는 Builder 역량 유지와 최근 지도·리뷰·재사용 실적을 제출한다.
- 보안·권한·복구 등 필수 기준이 바뀌면 해당 항목에 대한 추가 확인을 한다.
- 직무 이동이나 휴직으로 실적이 없으면 갱신대기로 두고, 복귀 후 실기로 갱신할 수 있게 한다.
- Guide 활동만 중단한 사람은 현재 Builder 역량을 확인해 Builder로 유지할 수 있다.
- 증거 조작이나 중대한 미해결 필수 기준 결함은 조사·소명 후 효력정지·취소를 판단한다.

기술 변화가 생겼다는 이유만으로 모든 사람에게 전체 교육을 재수강시키지 않는다. 변경된 기준과 부족한 역량을 확인한다.

### 10.4 인증 후 역할·지원 후보

- Builder에게 승인된 업무 Agent 개발·유지 역할을 배정한다.
- Guide에게 리뷰, 과제 상담, 다른 분과 멘토링을 배정한다.
- 활동을 수행할 업무시간과 개발 환경을 함께 제공한다.
- 인사·평가 연계는 별도 합의한다. 자격 취득만으로 자동 승진·보상을 약속하지 않는다.
- Guide 의무를 과도하게 늘려 본인 개발·운영을 못 하게 하지 않는다.

## 11. 첫 기수 도입 순서와 필요한 자원

### 11.1 실행 순서

| 단계 | 할 일 | 다음 단계로 넘어갈 조건 |
|---|---|---|
| 시작 전 4~3주 | 과제·대상·시간·환경 확인 | API·데이터·권한·배포 가능 여부와 시나리오 결정 |
| 시작 전 2주 | 진단·과제 선정·준비 과정 배정 | 교육시간, 과제 책임자, 대표 입력 확보 |
| 시작 전 1주 | 실습 리허설·심사자 채점 연습 | 정상·장애 실습 실행과 평가표 공개 |
| 1~4주 | 업무 정의·S/W·최소 Agent | 개인 실행과 과제 적합성 확인 |
| 5~8주 | 연결·평가·보안 | 평가 세트와 주요 예외·필수 기준 점검 |
| 9~12주 | 배포·운영·캡스톤 | 인수인계와 심사 증거 준비 |
| 이후 필요한 기간 | 운영 관찰 보완·개인 심사 | 미완료 항목 해소 후 인증 |
| Builder 배출 이후 | Guide 교육·8주 활동 | 지도·리뷰·자립 증거 확보 후 Guide 심사 |
| 반복 기수 결정 전 | 교육·심사·활용 결과 검토 | 실패 원인과 자원 한계를 반영해 규모 결정 |

표의 준비 일정은 32시간 준비 과정을 포함하지 않는다. 시나리오 C 대상자는 준비 4주를 별도로 확보한다.

### 11.2 12명 파일럿 자원 계산 예시

| 자원 | 계획 가정 | 계산 |
|---|---|---|
| 교육생 시간 | 1인 96시간 | 12 × 96 = 1,152 인시 |
| 멘토 시간 | 3명, 주 2시간, 12주 | 3 × 2 × 12 = 72 인시 |
| Builder 심사 | 1인당 심사자 2명, 각 3시간 | 12 × 2 × 3 = 72 인시 |
| 강사·준비·운영 | 기존 콘텐츠·환경에 따라 달라짐 | 별도 산정 |
| 관찰·현업 대응 | 교육시간 밖의 필요 업무가 있음 | 과제 책임자와 별도 산정 |

심사자 3시간은 사전 증거 검토 1시간, 개인 실기 90분, 구술 30분이다. 재심과 심사자 기준 정렬 시간은 포함하지 않았다. 위 계산은 예산 가정이며 실제 투입 실적이 아니다.

### 11.3 파일럿에서 확인할 지표

| 지표 | 계산·확인 방법 | 해석할 때 주의 |
|---|---|---|
| 수료율 | 수료자 ÷ 입과자 | 수료와 인증을 구분 |
| 최초 인증 통과율 | 첫 심사 통과자 ÷ 첫 심사 응시자 | 미응시·유예 인원 별도 표시 |
| 독립 수행 | 개인 실기에서 도움 없이 변경·복구 | 팀 산출물만으로 계산하지 않음 |
| 인증 이후 유지 | 인증 3개월 후 계속 사용하는 과제 ÷ 인증 과제 | 정책·직무·환경으로 중단한 이유 구분 |
| 업무 효과 | 같은 입력·기준선 대비 시간·오류·사람 개입 | 과제별 조건과 실패 결과 표시 |
| Guide 지도 효과 | 멘티의 진단 대비 독립 수행 변화 | 멘티 역량·환경 차이 함께 기록 |
| 심사 부담 | 후보 1인당 검토·재심 시간 | 기수 확대 전 병목 확인 |
| 운영 신뢰성 | 권한·중복·복구 시험과 실제 결함 기록 | 사고 0건만으로 안전을 주장하지 않음 |

파일럿에서는 숫자 목표를 임의로 고정하기보다 측정 방법을 먼저 정한다. 통과율을 높이기 위해 기준을 낮추지 않는다.

## 12. 예상되는 운영 실패와 대응 목록
