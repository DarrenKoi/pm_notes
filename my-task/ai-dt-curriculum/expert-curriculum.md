# Expert 커리큘럼 정리본

> 팀마다 Agent의 품질을 지키고 유지·보수를 가이드할 Expert를 Builder(96시간) → Guide(24시간)로 양성하는 교육 과정. 2026-10-09까지의 논의와 공개 커리큘럼 벤치마크를 반영한 확정본이다.

**읽는 법**: 시간과 인원은 파일럿 후 조정하는 값이다. 사무실에서 확인할 수치는 `⟨확인⟩`으로 남겼다. 인증 기준은 [인증 체계 정리본](./expert-certification.md)에 있다.

## 1. 왜 필요한가? (Why)

### 문제

1인 1Agent가 시작되면 Agent가 한꺼번에 만들어진다. 지금은 그 품질을 판정할 사람도, 만든 뒤 유지·보수를 도울 사람도 정해져 있지 않다.

### 안 하면 생기는 일

- 질 낮은 Agent가 검증 없이 쏟아져 Agent·tool 마켓에 올라간다. 권한을 넘는 접근, 근거 없는 답변, 중복 처리가 현업에서 발견된다.
- 만든 사람이 자리를 옮기면 Agent가 방치된다. 고치거나 고도화할 사람이 없다.

### 효과

- 팀마다 Expert가 챔피언으로 활동하며 팀원의 Agent를 가이드한다.
- 마켓에 올리려면 팀 Expert(Guide)의 승인을 먼저 받는다. 질 낮은 Agent를 등록 전에 걸러낸다.
- 각자의 Agent가 장기적으로 유지·보수·고도화되도록 팀 안에 물어볼 사람이 생긴다.

### 측정 지표

| 지표 | 계산 | 기준값 |
|------|------|--------|
| 난립 방지 | 1차 승인에서 반려·보완된 비율과 주요 사유 | 제도 시행 후 측정 |
| 유지·고도화 | 마켓 등록 3개월 뒤에도 운영 중이며 한 번 이상 개선된 Agent 비율 | ⟨확인: 현재 사내 Agent 수와 운영 중 비율⟩ |
| 양성 규모 | Guide가 1명 이상 있는 팀의 비율 | ⟨확인: 대상 팀 수⟩ |

첫 기수의 인증율은 목표 지표가 아니다. 수료율과 인증율은 따로 보고한다.

## 2. 핵심 개념 (What)

### 인재상

| 단계 | 할 수 있는 일 | 조직에서의 역할 |
|------|---------------|-----------------|
| Builder | 업무 문제를 Agent로 풀지 판단하고, 설계·구현·평가·배포·운영까지 혼자 끝낸다 | 팀의 Agent 개발·유지 담당 |
| Guide | 다른 사람의 Agent를 리뷰하고, 스스로 고치도록 지도하며, 마켓 등록을 1차 승인한다 | 팀 챔피언. 마켓의 1차 관문 |

단계는 두 개뿐이다. Builder 인증을 받은 뒤에 Guide로 승급한다.

### 대상과 입과

- 대상은 코드를 짤 수 있고, 네트워크·클라우드와 사내 제공 서비스를 이해하는 사람이다.
- 2시간 진단 과제와 인터뷰로 확인한다. 진단 과제는 사내 cloud에서 사내 서비스 API를 호출하는 작은 과제 하나다. 기존 실적(만든 코드·서비스)이 있으면 진단을 면제한다.
- 개발 기초를 가르치는 준비 과정은 두지 않는다. 진단 미달자는 타 분과 과정을 수강한 뒤 다시 응시한다.
- Fast Track 수료는 입과 자격과 연결하지 않는다. 수료하지 않고도 Agent를 개발하는 사람이 있기 때문이다.
- 이미 Agent를 개발·운영하는 사람은 교육 없이 같은 Builder 심사에 직접 응시할 수 있다.

### 규모

- 장기 목표는 팀당 Guide 1명 이상이다.
- 첫 기수는 12명 파일럿으로, Agent 개발 수요가 큰 팀부터 선발한다.

### 실습 환경

사내 일반 cloud 개발 환경을 쓴다. 사내 LLM API 호출과 배포 공간이 모두 가능하므로 실습 결과물을 실제로 띄워 운영한다. 외부 LLM API는 쓰지 않는다.

## 3. 어떻게 가르치는가? (How)

### 3.1 Builder 과정: 12주·96시간

업무 병행으로 주 8시간이다. 지도 학습 3시간과 실습·개인 과제 5시간으로 나눈다. 모듈 실습은 캡스톤에 누적된다.

| 모듈 | 시간 | 가르치는 것 | 수행 결과 |
|------|-----:|-------------|-----------|
| B1. 업무 문제·해법 선택 | 6 | 사용자, 업무 흐름, 기준선, Agent가 필요한지 판단 | 일반 자동화와 Agent를 비교한 과제 정의서 |
| B2. Agent 서비스 엔지니어링 | 8 | 테스트, 재현 가능한 환경, 오류 처리, API 계약 | 재현 가능한 작은 서비스. 1주차에 사내 모델의 호환 범위 점검 |
| B3. LLM·컨텍스트·메모리 | 10 | 토큰·컨텍스트 한계, 구조화 출력, 세션 메모리와 장기 메모리, 컨텍스트 선택·압축 | 긴 대화에서 요약 손실과 다른 세션 정보 혼입을 시험한 결과 |
| B4. 도구·Agent 실행 | 12 | 도구 계약, 실행 루프, 상태, 종료 조건, 재시도, 사람 승인 지점, 계획·성찰 패턴 | 프레임워크 없이 구현한 실행 루프. 도구 실패·중복 요청·중단 후 재개 시험 |
| B5. 지식·시스템 연결 | 8 | 검색 증강(RAG), 출처, 문서 갱신, 접근권한, MCP | 직접 만든 MCP 서버 1개. 검색 실패·권한 차이·오래된 문서 처리 |
| B6. 평가·개선 | 10 | 기준선, 평가 세트, 자동 평가, 회귀, 도구 선택과 상태 전이의 판정 | 변경 전후 비교. 자동 판정과 사람 판정의 불일치 확인 |
| B7. 보안·통제 | 10 | 최소 권한, 프롬프트 주입, 비밀정보, 승인, 도구별 위험 등급 | 권한 우회·기밀 노출·승인 누락 시험. 도구별 읽기·쓰기 선언 |
| B8. 배포·운영 | 10 | 배포, 로그, 추적(tracing), 버전, 자원, 복구, 인수인계 | 배포·중단·복구 시연과 운영 인수인계 문서 |
| B9. 선택 심화 | 6 | 직무에 필요한 주제 하나 | 선택 과제의 효과와 한계 설명 |
| B10. 통합 캡스톤 | 16 | 구현 통합, 사용자 검증, 심사 준비 | 운영 중인 Agent와 개인 기여 증거 |
| 합계 | 96 | | |

초안에서 달라진 점은 네 가지다.

- **B2를 12시간에서 8시간으로 줄였다.** 입과자가 이미 개발할 줄 알고, 공개 과정은 모두 이 내용을 선수 조건으로 둔다.
- **B3을 8시간에서 10시간으로 늘려 메모리를 넣었다.** 공개 과정은 세션·장기 메모리와 컨텍스트 압축을 독립 단원으로 가르친다.
- **B7을 8시간에서 10시간으로 늘렸다.** Guide의 승인 기준이 대부분 권한·승인·중복 처리이고, 공개 인증 시험도 보안 비중이 더 높다.
- **B5에 MCP 서버 제작을, B6·B8에 자동 평가와 추적을 필수로 명시했다.** 마켓에는 tool도 올라가므로 Builder가 tool을 만들 줄 알아야 한다.

B9 선택 주제는 Agent 간 프로토콜(A2A), 코딩 Agent 확장, 다중 Agent, 문서·RAG 심화, 이미지·문서 이해, GUI 자동화다. 다중 Agent는 필수로 올리지 않는다.

### 3.2 12주 편성

| 주차 | 편성 | 주차 결과 |
|------|------|-----------|
| 1 | B1 6시간 + B2 2시간 | 과제 정의서, 사내 모델 호환 범위 확인 |
| 2 | B2 6시간 + B3 2시간 | 테스트·환경·오류 처리 |
| 3 | B3 8시간 | 컨텍스트·메모리 실습 |
| 4 | B4 8시간 | 직접 구현한 실행 루프 |
| 5 | B4 4시간 + B5 4시간 | 실패 복구, 검색 연결 |
| 6 | B5 4시간 + B6 4시간 | MCP 서버, 초기 평가 세트 |
| 7 | B6 6시간 + B7 2시간 | 자동 평가·회귀 |
| 8 | B7 8시간 | 권한·주입·승인 시험 |
| 9 | B8 8시간 | 배포·추적·복구 |
| 10 | B8 2시간 + B9 6시간 | 운영 보완, 선택 심화 |
| 11 | B10 8시간 | 통합 검증, 사용자 확인 |
| 12 | B10 8시간 | 인수인계, 증거 정리 |

4·8·12주에 중간 점검을 한다. 승인된 사용 관찰은 준비된 과제부터 9주차 이후에 시작한다.

### 3.3 Guide 과정: 24시간 + 실적

Builder 인증자만 수강한다. 교육 이수만으로 Guide가 되지 않는다.

| 모듈 | 시간 | 가르치는 것 | 실습 |
|------|-----:|-------------|------|
| G1. 설계·코드 리뷰 | 6 | 요구사항, 오류 경로, 권한, 변경 영향. Agent 고유 항목(도구 계약, 종료 조건, 평가 세트) | 고의 결함이 섞인 제출물을 승인·보완·반려로 판정 |
| G2. 멘토링·교육 설계 | 6 | 선수 역량 진단, 질문, 과제 분할, 피드백 | 학습자가 직접 실행·설명·변경하게 하는 지도 시연 |
| G3. 평가·심사 일치 | 6 | 평가표 적용, 판정 사례, 이해충돌 | 같은 제출물을 여럿이 채점해 근거를 비교. 잘못된 승인과 과한 반려 사례 포함 |
| G4. 재사용·운영 전파 | 6 | 문서, 공통 도구, 인수인계, 장애 회고 | 등록 후 변경 시 재승인, Guide 부재 시 대행 절차 연습 |
| 합계 | 24 | | |

G1·G3 실습은 연습용 예제가 아니라 실제 판정이다. 통과 기준이 있으며 Guide 승급의 필수 요건이다. 공동 개발 이력만으로 승급하는 사람의 리뷰·판정 경험 공백을 이 실습으로 메운다.

승급에 필요한 실적은 [인증 체계 정리본](./expert-certification.md) 4장에 있다.

### 3.4 교재

개념 교재는 공개 자료를 각색하고, 실습은 사내 모델 기준으로 한 경로만 자체 제작한다. 프레임워크 여러 개를 비교해 가르치지 않는다.

| 용도 | 쓸 자료 | 조건 |
|------|---------|------|
| Builder 개념 교재 | Hugging Face Agents Course (Apache-2.0), Microsoft AI Agents for Beginners (MIT) | 라이선스·저작권 고지 유지, 변경 사실 표시 |
| 상태·메모리 실습 | LangChain Academy 실습 저장소 (MIT) | 외부 API와 외부 추적 연결을 사내 구성으로 교체 |
| G1 리뷰 기준 | Google 코드 리뷰 가이드 (CC BY 3.0) | 출처 표기. Agent 고유 항목은 추가 작성 |
| G2 교수법 | The Carpentries 강사 양성 교재 (CC BY 4.0) | 출처 표기 |
| 출제 범위 점검 | AWS·Microsoft·Google 인증의 공개 시험 범위 | 참조만. 문항과 배지는 쓰지 않는다 |

자체 제작할 것은 다음과 같다. 공개 과정이 다루지 않는 부분이자 이 과정의 차별점이다.

- B1의 과제 정의서 양식과 사례
- 사내 모델·사내 검색·사내 배포로 수행하는 실습 전체
- 중복 요청, 중단 후 재개, 권한별 검색 차이, 오래된 문서 시험
- 운영 인수인계와 4주 사용 관찰
- Guide 과정의 결함 제출물과 판정 기준

공개 실습을 옮길 때 두 가지를 확인한다. 사내 모델이 tool calling과 구조화 출력을 지원하는지(⟨확인: 사내 모델의 tool calling·구조화 출력 지원⟩), 그리고 프레임워크가 추적 기록을 외부 서버로 보내지 않게 설정했는지다.

근거는 [공개 커리큘럼 벤치마크 종합](./public-curriculum-benchmark-summary.md)에 있다.

### 3.5 조건이 다를 때

| 조건 | 대안 |
|------|------|
| 단기 전담 배정이 가능하다 | 3주 집중 90시간 + 후속 2주 6시간. 인증은 운영 증거를 받은 뒤 발급 |
| 교대근무로 주 8시간이 어렵다 | 16주에 주 6시간으로 분산 |
| 업무시간을 확보하지 못했다 | 다음 기수로 배정한다. 현업 업무량을 그대로 두고 교육시간만 얹지 않는다 |

### 3.6 첫 기수 준비

| 시점 | 할 일 |
|------|-------|
| 시작 4~3주 전 | 대상 팀·과제·교육시간 확보, 사내 모델 호환 범위 확인 |
| 시작 2주 전 | 입과 진단, 과제 선정, 과제 책임자 지정 |
| 시작 1주 전 | 실습 리허설, 초기 심사단의 채점 연습, 평가표 공개 |
| 1~12주 | Builder 과정 |
| 이후 | 운영 관찰 보완과 Builder 심사 |
| Builder 배출 후 | Guide 교육과 승급 심사 |
