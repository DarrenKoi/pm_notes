# 리버스 엔지니어링 작업 절차

> 범위 확인 → 질문 정하기 → 대상 식별 → 정찰 → 정적 분석 → 동적 확인 → 기록. 분석 하나마다 이 7단계를 따른다.

## 왜 필요한가? (Why)

리버스 엔지니어링은 끝이 없는 작업이다. 바이너리 하나에 함수가 수천 개 있고, 다 읽을 수는 없다. 절차 없이 시작하면 흥미로운 함수를 따라가다 하루가 가고, 처음 질문에는 답하지 못한다.

절차가 지키는 것은 세 가지다.

- **범위**: 허가받은 대상만, 허가받은 방법으로 분석한다.
- **초점**: 질문에 답하는 데 필요한 코드만 읽는다.
- **재현성**: 나중에 같은 결론을 다시 끌어낼 수 있도록 근거를 남긴다.

## 핵심 개념 (What)

전체 흐름은 다음과 같다. 5단계와 6단계는 가설이 확인될 때까지 반복한다.

```text
1. 범위와 허가 확인
2. 질문 정하기 ─────────────┐
3. 대상 식별                │
4. 정찰(Triage)             │ 답이 안 나오면
5. 정적 분석 ◀──┐           │ 질문을 다시 쪼갠다
6. 동적 확인 ───┘ 반복      │
7. 기록과 보고 ─────────────┘
```

에이전트와 REA를 쓰면 3~6단계의 손작업이 크게 줄어든다. 1, 2, 7단계는 줄지 않는다. 그 세 단계가 사람이 하는 일이다.

## 어떻게 사용하는가? (How)

분석을 시작할 때 [분석 기록 양식](./templates/investigation-log.md)을 복사해서 단계마다 채운다.

### 1. 범위와 허가를 확인한다

동료가 만든 도구라도 바로 분석하지 않는다. 아래 네 가지를 먼저 확인하고 기록 양식에 적는다.

- **소유자**: 이 프로그램을 만든 사람 또는 소유 부서. 연락이 되면 먼저 물어본다. 리버스 엔지니어링보다 질문 한 번이 빠른 경우가 많다.
- **목적**: 유지보수, 연동, 재구현, 버전 확인 중 무엇인가.
- **허가**: 소유자나 관리자의 동의를 받았는가. 외부 상용 소프트웨어는 라이선스가 리버스 엔지니어링을 금지할 수 있으므로, 사내 제작 도구와 구분한다.
- **실행 환경**: 실행해도 되는 환경이 있는가. 장비, 운영 DB, 공유 파일에 쓰는 도구는 운영 환경에서 실행하지 않는다.

> [!warning] 운영 환경에서 실행하지 않는다
> 장비 제어, DB 쓰기, 파일 삭제를 하는 도구는 동적 분석 중에 그 동작을 실제로 한다. 정적 분석으로 무엇을 건드리는지 먼저 확인하고, 테스트 환경이나 격리된 VM에서만 실행한다.
>
> VM 안에서 실행해도 네트워크가 열려 있으면 운영 DB와 장비에 접속할 수 있다. REA는 네트워크 격리나 샌드박스를 제공하지 않는다. 실행 전에 아래 세 가지를 확인한다.
> - 운영망 접근이 막혀 있다.
> - 운영 계정의 자격 증명(설정 파일, 환경 변수, 저장된 토큰)이 없다.
> - 공유 폴더가 연결되어 있지 않다.

### 2. 질문을 정한다

"이 프로그램을 분석해줘"는 질문이 아니다. 답할 수 있는 크기로 쪼갠다.

| 나쁜 질문 | 좋은 질문 |
|---|---|
| 이 도구 분석해줘 | "Export 버튼을 누르면 어떤 파일이 어떤 형식으로 만들어지는가?" |
| 이 웹 앱 API 알려줘 | "목록 화면이 로드될 때 어떤 엔드포인트를 어떤 파라미터로 부르는가?" |
| 이 계산 로직 뭐야 | "결과 화면의 보정값은 어떤 입력으로 어떻게 계산되는가? 같은 값을 내는 Python 함수로 옮길 수 있는가?" |

좋은 질문에는 세 가지가 있다. 관찰할 수 있는 시작점(버튼, 화면, 파일), 알고 싶은 결과(형식, 엔드포인트, 계산식), 그리고 끝났다고 판단할 기준이다.

질문마다 "어떤 증거가 있으면 답이 되는가"를 같이 적는다. 예를 들어 "Export 파일 형식" 질문이라면 파일을 쓰는 함수의 디컴파일 결과와 실제로 만들어진 파일 한 개가 증거다.

### 3. 대상을 식별한다

분석할 파일이 정확히 무엇인지 고정한다.

1. 원본을 건드리지 않도록 분석용 폴더에 복사한다.
2. 해시를 기록한다. 나중에 "그 파일이 이 파일인가"를 확인하는 유일한 방법이다.

	```bash
	shasum -a 256 /absolute/path/to/target.exe
	```

3. 파일 형식을 확인한다. 확장자를 믿지 않는다.

	```bash
	file /absolute/path/to/target.exe
	```

4. 버전 정보, 빌드 날짜, 함께 배포된 파일(설정 파일, DLL, `.asar`, `.map`)을 목록으로 남긴다.

설치 폴더째 받았고 무엇으로 만들었는지 모르면 REA의 `inspect_desktop_application`에 폴더를 넘긴다. 런타임 후보와 다음에 쓸 도구를 알려준다.

### 4. 정찰한다 (Triage)

코드를 읽기 전에 겉에서 보이는 것을 모은다. 이 단계에서 진입점 후보를 3~5개 찾는 것이 목표다.

- **문자열**: 에러 메시지, 로그 문구, URL, SQL, 파일 경로, 화면 문구. 질문과 관련된 문자열이 가장 좋은 진입점이다.
- **임포트**: 파일, 네트워크, 레지스트리, DB 드라이버 중 무엇을 쓰는가.
- **리소스와 설정 파일**: 화면 정의, 설정 파일, 내장된 템플릿.
- **의존성**: Go 모듈, Rust 크레이트, npm 패키지, Python 버전. 직접 짠 코드와 라이브러리 코드를 나누는 기준이 된다.
- **웹 앱이면**: 소스 맵 유무, 라우트 목록, API 엔드포인트 후보.

라이브러리 코드는 읽지 않는다. 직접 짠 코드만 읽어도 시간이 모자란다.

### 5. 정적 분석으로 경로를 따라간다

진입점 하나를 골라 질문의 결과까지 따라간다.

1. 진입점(문자열, 라우트, 버튼 핸들러)을 참조하는 함수를 상호 참조로 찾는다.
2. 그 함수의 디컴파일 결과를 읽고, 질문과 관련된 호출만 따라간다.
3. 따라가면서 함수에 이름을 붙인다. `FUN_00401a20` 대신 `save_recipe_candidate` 같은 이름을 붙여 두면 다음 함수를 읽기 쉬워진다.
4. 가설을 한 문장으로 적는다. "이 함수가 CSV를 쓰고, 세 번째 열이 보정값이다."

한 경로에서 막히면 다른 진입점으로 간다. 간접 호출이나 암호화된 데이터 앞에서 계속 파고드는 것보다 빠르다.

### 6. 동적 관찰로 확인한다

5단계의 가설은 추론이다. 실행해서 관찰로 바꾼다.

- **웹 앱**: 브라우저를 원격 디버깅 포트와 함께 띄우고 화면을 조작하면서 네트워크 요청과 스크립트를 기록한다. 또는 DevTools에서 HAR 파일을 저장해서 오프라인으로 읽는다.
- **데스크톱 도구**: 테스트 환경에서 실행하고 만들어진 파일, 출력, 로그를 확인한다.
- **계산 로직**: 같은 입력을 원본 도구와 재구현 코드에 넣고 결과를 비교한다. 경계값(0, 음수, 빈 입력, 아주 큰 값)을 꼭 넣는다.

관찰 결과가 가설과 다르면 5단계로 돌아간다. 다른 결과가 나왔다는 것은 실패가 아니라 정보다.

### 7. 기록하고 보고한다

질문 목록으로 돌아가서 각 질문을 셋 중 하나로 표시한다.

- **답함**: 관찰 근거가 있다.
- **일부 답함**: 추론까지는 했지만 관찰로 확인하지 못했다.
- **미해결**: 근거가 없다. 어디까지 찾아봤는지 적는다.

보고에는 결론마다 근거를 붙인다. REA를 썼다면 Evidence ID를 함께 적는다. "찾아봤는데 없었다"는 결론은 어디까지 찾아봤는지와 함께 적는다. 범위가 없는 부재 주장은 쓰지 않는다.

재구현했다면 비교 테스트를 함께 남긴다. 테스트가 없는 재구현은 "아마 같을 것"이라는 추론일 뿐이다.
