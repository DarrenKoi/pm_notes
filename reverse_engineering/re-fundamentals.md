# 리버스 엔지니어링 기초 개념

> 완성된 결과물(바이너리, 번들, 네트워크 트래픽)에서 거꾸로 설계와 동작을 읽어내는 일. 무엇을 볼 수 있고 무엇은 볼 수 없는지를 아는 것이 기술의 절반이다.

## 왜 필요한가? (Why)

사내에서 리버스 엔지니어링이 필요한 상황은 대개 넷 중 하나다.

- **소스가 없다.** 만든 사람이 퇴사했거나, 저장소 없이 실행 파일만 공유 폴더에 남았다.
- **소스와 배포본이 다르다.** 저장소의 코드와 실제로 돌고 있는 `.exe`가 같은 버전인지 아무도 모른다.
- **연동해야 한다.** 웹 앱이 어떤 API를 어떤 형식으로 부르는지 문서가 없다.
- **같은 기능을 새로 만들어야 한다.** 기존 도구의 계산식이나 판정 로직을 그대로 옮겨야 한다.

넷 다 질문이 같다. "이 프로그램은 실제로 무엇을 하는가?" 리버스 엔지니어링은 그 질문에 근거를 붙여 답하는 방법이다.

## 핵심 개념 (What)

### 컴파일은 정보를 버린다

소스 코드가 실행 파일이 될 때 많은 정보가 사라진다. 리버스 엔지니어링의 난이도는 어떤 정보가 얼마나 사라졌는지로 정해진다.

| 사라지는 것 | 결과 | 남는 단서 |
|---|---|---|
| 변수 이름, 주석 | 디컴파일 결과에 `local_18`, `param_1` 같은 이름이 붙는다 | 문자열, 로그 메시지, 에러 문구 |
| 함수 이름(스트립된 바이너리) | 함수가 `FUN_00401a20` 같은 주소로만 보인다 | 외부 라이브러리 호출(import), 내보낸 함수(export) |
| 타입과 구조체 | 포인터 연산이 `*(int *)(param_1 + 0x10)`처럼 보인다 | 오프셋 패턴, 디버그 정보(DWARF, PDB)가 남은 경우 |
| 제어 구조 | 최적화로 반복문과 분기가 원래 모양과 달라진다 | 어셈블리, 제어 흐름 그래프(CFG) |

반대로 언어마다 남는 정보가 많은 경우도 있다. 아래 "대상별 난이도"에서 다룬다.

### 정적 분석과 동적 분석

- **정적 분석(Static Analysis)**: 실행하지 않고 파일을 읽는다. 디스어셈블, 디컴파일, 문자열 검색, 상호 참조 추적이 여기에 속한다. 안전하고 반복할 수 있지만, 실제로 어느 경로가 실행되는지는 모른다.
- **동적 분석(Dynamic Analysis)**: 실행하면서 관찰한다. 브라우저 DevTools, 네트워크 캡처, 디버거, 프로세스 출력 기록이 여기에 속한다. 실제 값을 볼 수 있지만, 실행한 경로만 보인다.

정적 분석으로 후보를 좁히고, 동적 분석으로 확인하는 순서가 기본이다. 정적 분석만으로 "이 함수가 호출된다"고 말하면 추론이다. 실행 중에 호출을 관찰해야 관찰이 된다.

### 꼭 알아야 할 용어

- **디스어셈블(Disassemble)**: 기계어 바이트를 어셈블리 명령어로 바꾼다. 정확하지만 읽기 어렵다.
- **디컴파일(Decompile)**: 어셈블리를 C 비슷한 의사 코드(Pseudocode)로 바꾼다. 읽기 쉽지만 원본 소스가 아니다. 디컴파일러가 타입을 잘못 추정하면 결과도 틀린다.
- **심볼(Symbol)**: 함수와 변수의 이름 정보. 디버그 빌드에는 많고, 릴리스 빌드에서는 스트립(Strip)되어 없을 수 있다.
- **임포트·익스포트(Import, Export)**: 프로그램이 외부 라이브러리에서 가져다 쓰는 함수와 밖으로 내보내는 함수. 스트립된 바이너리에서도 대부분 남아 있어서 첫 단서가 된다. 예를 들어 `CreateFileW`를 임포트하면 파일이나 장치를 열 수 있다는 후보 단서다. 임포트는 실제 호출을 증명하지 않으므로, 호출 경로와 인수를 따로 확인한다.
- **상호 참조(Cross-reference, Xref)**: "이 함수를 누가 부르는가", "이 문자열을 누가 읽는가"의 목록. 문자열 하나에서 출발해 그 문자열을 쓰는 함수로 거슬러 올라가는 것이 가장 흔한 탐색 방법이다.
- **호출 그래프(Call Graph)**: 함수 사이의 호출 관계. 호출자(Caller)와 피호출자(Callee)로 나뉜다.
- **소스 맵(Source Map)**: 압축된 JavaScript 번들을 원본 파일과 줄 번호로 되돌리는 매핑 파일(`.map`). 사내 웹 앱은 소스 맵을 지우지 않고 배포하는 경우가 많다. 소스 맵의 `sourcesContent` 필드에 원본 내용이 들어 있으면 원본 소스를 거의 그대로 얻는다. 이 필드는 선택 사항이므로, 비어 있으면 원본 파일 경로와 줄 번호만 얻는다.
- **진입점(Entry Point)**: 분석을 시작할 지점. `main` 함수일 수도 있고, 버튼 클릭 핸들러, HTTP 라우트, 에러 문자열일 수도 있다. 좋은 진입점을 고르는 것이 분석 시간을 가장 많이 줄인다.

### 기계어 바이트, 어셈블리, 의사 코드

셋은 같은 함수를 다른 높이에서 본 모습이다. CPU가 실행하는 것은 기계어 바이트뿐이고, 어셈블리와 의사 코드는 사람이 읽으려고 만든 번역이다.

| 층 | 정체 | 누가 만드나 | 원본과의 관계 |
|---|---|---|---|
| 기계어 바이트(Machine Code) | `.exe`, `.dll` 안에 실제로 들어 있는 숫자 | 컴파일러 | 이것이 원본이다 |
| 어셈블리(Assembly) | 바이트 하나하나에 명령어 이름을 붙인 글자 표기 | 디스어셈블러 | 거의 1:1 대응. 정확하다 |
| 의사 코드(Pseudocode) | 여러 명령어를 묶어 `if`, 변수, `return`으로 다시 쓴 C 비슷한 코드 | 디컴파일러 | 추정으로 복원한 것. 원본 소스가 아니다 |

아래 C 함수 하나를 세 층으로 따라가 본다.

```c
// 원본 소스 (분석할 때는 이것이 없다)
int check_limit(int value) {
    if (value > 100) {
        return -1;
    }
    return value * 2;
}
```

**1. 기계어 바이트.** Windows x64용으로 최적화 컴파일(`clang -target x86_64-pc-windows-msvc -O1`)하면 함수 전체가 15바이트가 된다. 16진수 편집기로 파일을 열면 보이는 것이 이것이다.

```text
8d 14 09 83 f9 65 b8 ff ff ff ff 0f 4c c2 c3
```

어디서 명령어가 끝나는지도 바이트만 봐서는 알 수 없다. x86 명령어는 길이가 1바이트에서 15바이트까지 제각각이다.

**2. 어셈블리.** 디스어셈블러는 바이트를 명령어 단위로 끊고 이름을 붙인다. 위 바이트를 `objdump -d --x86-asm-syntax=intel`로 디스어셈블한 실제 결과다.

```text
주소  바이트           어셈블리                  뜻
0:   8d 14 09         lea   edx, [rcx + rcx]   edx = value * 2
3:   83 f9 65         cmp   ecx, 0x65          value 와 101 비교
6:   b8 ff ff ff ff   mov   eax, 0xffffffff    eax = -1
b:   0f 4c c2         cmovl eax, edx           value < 101 이면 eax = edx
e:   c3               ret                      eax 값을 반환
```

바이트와 명령어가 한 줄씩 짝을 이룬다. `c3`은 언제나 `ret`이고, `83 f9 65`의 마지막 `65`는 비교할 숫자 101(0x65)이다. 그래서 어셈블리는 정확하다. 대신 읽는 사람이 규칙을 알아야 한다.

- `ecx`에 첫 번째 인수 `value`가 들어 있다. Windows x64 호출 규약(Calling Convention)이 그렇게 정해 두었다. 반환값은 `eax`에 넣는다.
- 원본의 `value > 100`은 `value < 101`로 뒤집혀 있다.
- 원본에는 `if`가 있었는데 어셈블리에는 분기(점프)가 없다. 컴파일러가 두 결과를 미리 다 계산해 두고 `cmovl`(조건부 이동)로 하나를 고르게 바꿨다. "컴파일은 정보를 버린다" 표의 "제어 구조" 항목이 이런 경우다.

**3. 의사 코드.** 디컴파일러는 명령어들의 데이터 흐름을 따라가서 레지스터를 변수로, 비교와 조건부 이동을 `if`로 다시 묶는다. Ghidra는 대략 아래 모양으로 보여준다(형태를 보여주려는 예시이며, 실제 출력은 버전과 설정에 따라 다르다).

```c
int check_limit(int param_1)
{
  int iVar1;

  iVar1 = -1;
  if (param_1 < 0x65) {
    iVar1 = param_1 * 2;
  }
  return iVar1;
}
```

의미는 원본과 같지만 모양은 다르다. 이것이 의사 코드의 성격이다.

- 이름이 사라졌다. `value`는 `param_1`, 임시값은 `iVar1`이 된다. 함수 이름 `check_limit`도 심볼이 없으면 `FUN_140001000`처럼 주소로 붙는다.
- 상수가 바뀐 채로 남는다. `100`이 아니라 `0x65`(101)와 `<`로 나온다.
- 구조가 다시 만들어진다. 원본의 "일찍 반환"이 "기본값을 넣고 덮어쓰기"로 바뀌었다.
- 타입은 추정이다. 여기서는 `int`가 맞았지만, 포인터나 구조체는 자주 틀린다. 틀린 타입 위에서 읽은 의사 코드는 그럴듯하게 틀린다.

정리하면, 의사 코드로 빨리 뜻을 파악하고 중요한 판단(경계값, 분기 조건, 인수 순서)은 어셈블리로 확인한다. 기계어 바이트를 직접 볼 일은 드물다. 패치 위치를 찾거나 디스어셈블러가 코드와 데이터를 헷갈렸을 때 정도다.

### 대상별 난이도

같은 "프로그램"이라도 무엇으로 만들었는지에 따라 얻을 수 있는 정보가 크게 다르다. 사내 도구에서 자주 보는 대상을 쉬운 순서로 적었다.

| 대상 | 무엇이 남는가 | 난이도 | 비고 |
|---|---|---|---|
| 웹 앱 프런트엔드(Vue, React 번들) | JS 코드 전체, 소스 맵이 있으면 원본 | 쉬움 | 브라우저에 이미 다 내려와 있다 |
| Electron 앱 | `app.asar` 안에 JS 코드 전체 | 쉬움 | 압축을 풀면 웹 앱과 같다 |
| .NET 어셈블리(C# `.exe`, `.dll`) | 클래스, 메서드 이름, IL 명령어 | 쉬움 | 메타데이터가 풍부하다. NativeAOT 빌드는 예외 |
| PyInstaller로 묶은 Python `.exe` | 내부 `.pyc` 바이트코드, Python 버전 | 보통 | 압축을 풀 수는 있지만 `.pyc`를 `.py`로 되돌리는 것은 별도 도구가 필요하다 |
| Go, Rust 바이너리 | 모듈과 의존성 정보 | 보통 | 바이너리가 크고 런타임 코드가 많다 |
| C, C++ 네이티브 바이너리 | 기계어, 임포트, 문자열 | 어려움 | Ghidra 같은 디컴파일러가 필요하다 |
| 웹 앱 백엔드(Flask, FastAPI 서버) | 밖에서는 HTTP 요청과 응답만 | 서버 접근에 달림 | 서버 접근 권한이 없으면 API 동작만 관찰할 수 있다 |

사내 웹 앱 하나를 분석한다면 실제 작업은 대개 "프런트엔드 번들 읽기 + 네트워크 요청 관찰"이다. 백엔드 로직은 프런트엔드가 보내는 요청과 받는 응답으로 추론한다. 백엔드를 직접 보려면 서버 접근 권한을 받는 편이 리버스 엔지니어링보다 빠르다.

### 증거의 등급

분석 결과를 쓸 때는 각 주장이 어느 등급인지 함께 적는다. REA도 결과를 이 세 가지로 나눠서 돌려준다.

| 등급 | 뜻 | 예 |
|---|---|---|
| 관찰(Observation) | 도구가 직접 본 사실 | "함수 `0x401a20`이 문자열 `"Recipe saved"`를 참조한다" |
| 추론(Inference) | 관찰을 묶어서 내린 해석 | "`0x401a20`이 레시피 저장 함수일 것이다" |
| 미확인(Unknown) | 도구가 볼 수 없었던 것 | "간접 호출 대상이라 누가 이 함수를 부르는지 정적으로 알 수 없다" |

리버스 엔지니어링 보고서가 틀리는 가장 흔한 이유는 추론을 관찰처럼 쓰는 것이다. 디컴파일 결과를 읽고 "이 함수는 A를 한다"고 쓰면 추론이다. 실행해서 A가 일어나는 것을 봐야 관찰이 된다.

### 디컴파일러가 틀리는 지점

Ghidra의 의사 코드는 강력하지만 아래 경우에는 그대로 믿지 않는다.

- **간접 호출(Indirect Call)**: 함수 포인터, 가상 함수, 콜백은 호출 대상을 정적으로 모를 수 있다. 호출 그래프에서 빠진다.
- **반환하지 않는 함수(No-return)**: `exit`나 예외를 던지는 함수 뒤의 코드를 디컴파일러가 잘라낼 수 있다.
- **타입 추정 실패**: 구조체를 몰라서 오프셋 연산으로 보이거나, 부호 있는 정수와 없는 정수를 혼동한다.
- **최적화된 코드**: 인라인된 함수, 펼쳐진 반복문은 원래 소스 모양과 다르다.

이런 지점은 어셈블리를 직접 보거나 실행해서 확인한다.

## 어떻게 사용하는가? (How)

개념을 실제 분석에 적용하는 순서는 [리버스 엔지니어링 작업 절차](./re-process.md)에 있다. 도구 사용법은 [REA + Ghidra로 분석하는 방법](./rea-usage-guide.md)에 있다.

처음이라면 쉬운 대상부터 시작한다. 사내 웹 앱 하나를 골라서 브라우저 DevTools의 **Sources** 탭에 소스 맵이 있는지 보고, **Network** 탭에서 버튼 하나를 눌렀을 때 나가는 요청을 확인한다. 이 두 가지만으로도 리버스 엔지니어링의 기본 흐름인 "진입점 찾기 → 코드 따라가기 → 실행으로 확인"을 한 번 경험할 수 있다.
