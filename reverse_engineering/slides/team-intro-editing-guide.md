# RE, REA 입문 deck 편집 지침

> `re-rea-team-intro.pptx`에 회사에서 얻은 REA 실행 결과를 끼워 넣거나 내용을 고치는 LLM과 사람을 위한 지침. 사내 결과는 `extra_사내용.json` 한 파일에만 적는다.

## 왜 필요한가? (Why)

이 deck은 개념과 절차를 설명하는 29장이다. 발표에서는 회사 PC에서 REA를 실제로 돌린 결과를 사이사이에 보여 줄 예정이다. 그 작업은 사내 LLM에 연결된 에이전트(pi)가 이 저장소를 읽고 한다. 이때 세 가지가 깨지기 쉽다.

- **기밀**: 이 저장소는 공개다. 사내 도구의 이름, 경로, 디컴파일 코드가 커밋되면 밖으로 나간다.
- **구조**: pptx와 md는 스크립트가 만든 결과물이다. 결과물을 직접 고치면 다음 생성 때 사라진다.
- **모양**: 글이 상자를 넘치면 발표 화면에서 잘린다. 스크립트는 글 길이를 재지 않는다.

## 핵심 개념 (What)

### 파일 구성

| 파일 | 역할 | git |
|---|---|---|
| `build_team_intro.py` | 생성 스크립트. 공개 내용은 `SLIDES` 목록에 있다 | 올린다 |
| `re-rea-team-intro.pptx`, `.md` | 공개 deck과 발표 원고. 스크립트가 만든다 | 올린다 |
| `extra_example.json` | 추가 슬라이드의 형식 예시 | 올린다 |
| `extra_사내용.json` | 회사에서 얻은 결과로 만든 추가 슬라이드 | **제외** |
| `re-rea-team-intro_사내용.pptx`, `.md` | 추가 슬라이드가 들어간 발표용 결과물 | **제외** |
| `img_사내용/` | 사내 화면 캡처를 두는 폴더(필요할 때 만든다) | **제외** |

`reverse_engineering/.gitignore`가 이름에 `_사내용`이 들어간 파일과 폴더를 모두 제외한다. 사내 내용을 담는 파일은 반드시 이 글자를 이름에 넣는다.

### 무엇을 어디에 고치는가

| 하려는 일 | 고칠 곳 |
|---|---|
| 회사에서 얻은 REA 결과를 끼워 넣기 | `extra_사내용.json`만 |
| 개념 설명, 용어, 공개 가능한 내용 고치기 | `build_team_intro.py`의 `SLIDES` |
| 로고, 슬로건, 부서 이름 넣기 | `build_team_intro.py` 위쪽의 `LOGO`, `SLOGAN`, `DEPT`. 값을 바꾼 채로 커밋하지 않는다 |

`.pptx`와 `.md`는 직접 고치지 않는다. 도식을 그리는 함수(`draw_*`)도 고치지 않는다.

### 끼워 넣기 좋은 자리

`after`는 공개 deck의 슬라이드 번호다. 추가 슬라이드는 그 번호 바로 뒤에 들어간다. 다른 추가 슬라이드가 있어도 번호의 뜻은 바뀌지 않는다.

| after | 앞 슬라이드 | 넣으면 좋은 결과 | 알맞은 kind |
|---|---|---|---|
| 9 | 단서를 따라가는 길 | 실제 도구에서 문구, 문자열, 함수로 따라간 기록 | `draw_chain` |
| 12 | 대상에 따라 난이도가 다르다 | 설치 폴더를 판별한 결과(무엇으로 만든 프로그램인가) | `table` |
| 22 | 프롬프트에 넣을 네 가지 | 실제로 보낸 프롬프트 | `code` |
| 24 | 네이티브 .exe 분석 흐름 | 정찰에서 찾은 후보, 깊게 읽은 함수 요약 | `table`, `code` |
| 25 | 결과를 읽는 법 | REA가 돌려준 관찰, 추론, 미확인, 한계 | `draw_result` |
| 26 | 이런 일에 쓰면 좋다 | 질문별 답과 등급 요약, Ghidra 화면 캡처 | `table`, `image` |

발표는 60분이다. 추가 슬라이드 한 장에 약 2분이 들므로 3~5장으로 제한하고, 넘으면 공개 슬라이드에서 훑고 지나갈 장을 발표자와 정한다.

## 어떻게 사용하는가? (How)

### 1. 예시를 복사해서 시작한다

```powershell
cd reverse_engineering\slides
Copy-Item extra_example.json extra_사내용.json
```

`extra_사내용.json`은 슬라이드 목록이다. 파일은 UTF-8(BOM 없음)으로 저장한다. 엄격한 JSON이라 주석과 끝 쉼표는 오류다. Windows 경로의 백슬래시는 `\\`로 쓴다.

### 2. 슬라이드를 적는다

모든 슬라이드에 공통인 항목은 아래와 같다.

| 항목 | 필수 | 내용 |
|---|---|---|
| `after` | 예 | 1~29. 이 번호의 공개 슬라이드 뒤에 넣는다 |
| `kind` | 예 | 아래 일곱 가지 중 하나 |
| `title` | 예 | 제목. 한글 22자 이내 |
| `msg` | 예 | 파란 상자의 핵심 메시지 한 문장. "입니다" 체, 한글 45자 이내 |
| `notes` | 아니요 | 발표자 노트 |
| `foot` | 아니요 | 하단 참고 문장. 넣으면 본문 높이가 줄어든다. 두 줄 이내 |
| `part` | 아니요 | 오른쪽 위 표시. 기본값은 "REA 실행 결과" |

kind별 항목은 아래와 같다. 완전한 예는 `extra_example.json`에 있다.

| kind | 항목 | 글 분량의 한도 |
|---|---|---|
| `table` | `head`(열 제목), `rows`(행 목록), `widths`(열 너비 비율), `tint`(선택. 글자가 들어 있으면 그 칸을 칠할 색) | 7행 이내. 한 칸은 두 줄 이내 |
| `code` | `code`(왼쪽 고정폭 글), `side`(오른쪽 설명 목록) | 코드 17줄, 한 줄 영문 70자 또는 한글 38자 이내. 설명 6개 이내 |
| `draw_result` | `rows`(`[등급, 문장, 색]` 4개), `items`(`[제목, 설명]` 3개), `head`(선택. 왼쪽 머리글) | 문장은 한글 45자 이내 |
| `draw_chain` | `nodes`(`[머리, 설명, 고정폭 예시]` 3~5개), `gap`, `sample_size`, `labels`(선택) | 5개일 때 설명은 한글 27자, 예시는 영문 18자 이내 |
| `cards` | `items`(`[머리, 설명]` 3~4개) | 설명은 5줄 이내 |
| `two` | `groups`(`[머리, [문장, ...]]` 2개). 왼쪽은 기존, 오른쪽은 개선 | 한쪽에 4문장 이내 |
| `image` | `image`(이 폴더 기준 경로. 예: `img_사내용/ghidra.png`) | 가로로 긴 그림. 본문 높이에 맞춰 줄인다 |

글 안에서 `**글자**`는 굵게, `\n`은 줄바꿈이다. 색은 `#` 없는 16진수 여섯 자리로 쓴다. 이 deck이 쓰는 색은 연한 파랑 `E8F0FA`, 연노랑 `FFF2CC`, 밝은 회색 `D9D9D9`, 연한 분홍 `FCE4E4`, 짙은 파랑 `1F5AA6`이다. 새 색을 추가하지 않는다.

### 3. 다시 만든다

```powershell
python build_team_intro.py
```

`extra_사내용.json`이 있으면 공개 파일 두 개에 더해 `_사내용` 파일 두 개가 생긴다. 발표에는 `re-rea-team-intro_사내용.pptx`를 쓴다. `python-pptx` 패키지가 필요하다. 회사 PC에 새로 설치할 때는 사내 설치 금지 목록과 라이선스를 먼저 확인한다.

### 4. 확인한다

- PowerPoint로 열어 추가한 슬라이드마다 글이 상자 밖으로 나가거나 잘리지 않는지 본다. 넘치면 글을 줄이거나 슬라이드를 둘로 나눈다. 글자 크기를 줄여서 해결하지 않는다.
- `git status`에 `_사내용` 파일이 보이지 않는지 확인한다. 보이면 커밋하지 않고 `.gitignore`부터 확인한다.

### 5. 내용 규칙을 지킨다

- **REA가 실제로 돌려준 것만 적는다.** 결과를 짐작해서 채우지 않는다. 수치(걸린 시간, 함수 수)는 측정한 값만 적고, 없으면 그 항목을 뺀다.
- **등급을 지우지 않는다.** 관찰, 추론, 미확인의 구분과 한계, 커버리지를 그대로 옮긴다. 추론을 관찰처럼 고쳐 쓰지 않는다. 이 deck 11장과 25장이 가르치는 내용이다.
- **가릴 것을 가린다.** 장비 이름, 내부 시스템 주소, 사람 이름, 인증 정보는 사내용 파일에도 적지 않는다. 디컴파일 코드는 설명에 필요한 몇 줄만 쓴다.
- **청중은 비전공자다.** 새 용어가 나오면 `foot`에 한 줄로 풀어 쓴다. 공개 deck에서 이미 설명한 용어(8장, 18장의 표)는 다시 설명하지 않는다.
- **문장 부호**: em dash와 가운데 점을 쓰지 않는다. 나열은 쉼표, 부연은 괄호로 쓴다.
- **분석 대상의 허가**: 결과를 발표에 써도 되는지 소유 부서에 확인한다. 절차는 [작업 절차 1단계](../re-process.md#1-범위와-허가를-확인한다)에 있다.

### 공개 내용을 고칠 때

`SLIDES`의 사실은 이 폴더의 `.md` 문서에 근거가 있어야 한다. 폴더 밖 문서를 근거로 쓰지 않는다. 줄이면서 지우면 안 되는 단서가 있다.

- Windows의 Ghidra 연동은 "실험 단계, 읽기 전용"이다.
- "닫으면 기록이 사라진다"는 현재 배포본(6.8.0) 기준이다.
- Ghidra가 필요한 대상은 "네이티브 프로그램"이다. .NET이라도 NativeAOT 빌드는 여기에 든다.
- 임포트는 호출 가능성이지 호출의 증명이 아니다.
- 디컴파일 결과는 추정이고 원본 소스가 아니다.

공개 슬라이드는 20~30장을 유지한다. 스크립트가 이 범위와 문장 부호 규칙을 실행할 때 검사한다.
