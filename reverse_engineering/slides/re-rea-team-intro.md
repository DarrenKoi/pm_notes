# 리버스 엔지니어링 입문과 REA 활용법: 팀 공유 발표 원고

> 전공이 다양한 팀원에게 리버스 엔지니어링(RE)과 REA 활용법을 소개하는 29장짜리 발표 자료. 새 용어는 나올 때마다 풀어서 설명한다.

## 왜 필요한가? (Why)

팀원 대부분은 전기 공학이나 컴퓨터 공학 전공이 아니다. 기존 문서는 용어를 안다고 가정하고 쓰였으므로, 발표에서는 용어 설명과 비유를 먼저 두고 회사 환경(Windows PC, Ghidra 설치 가능)에서 REA를 쓰는 방법으로 이어 간다.

## 핵심 개념 (What)

| 파일 | 역할 |
|---|---|
| `re-rea-team-intro.pptx` | 발표용 슬라이드. 슬라이드마다 발표자 노트가 있다 |
| `re-rea-team-intro.bento.html` | 같은 내용의 HTML deck(Bento 형식). 브라우저로 열어 Slideshow로 발표한다 |
| `re-rea-team-intro.md` | 이 문서. 슬라이드 내용과 발표자 노트를 글로 옮긴 원고 |
| `build_team_intro.py` | 세 파일을 만드는 스크립트. 내용은 이 스크립트의 `SLIDES`에 있다 |

구성은 4부이고 발표 시간은 질문을 포함해 60분이다. 1부 리버스 엔지니어링이란(3~12장), 2부 작업 절차(13~15장), 3부 Ghidra와 REA(16~19장), 4부 회사 PC에서 써 보기(20~27장), 마무리(28~29장). 슬라이드의 도식은 이 원고에서 목록과 표로 옮겨 적었다.

## 어떻게 사용하는가? (How)

pptx, HTML deck, 이 문서는 직접 고치지 않는다. `build_team_intro.py`의 `SLIDES`를 고친 뒤 저장소 루트에서 다시 만든다.

```bash
python reverse_engineering/slides/build_team_intro.py
```

footer의 로고, 슬로건, 부서 이름은 자리 표시다. 회사 PC에서 스크립트 위쪽의 `LOGO`, `SLOGAN`, `DEPT` 값을 바꾼 뒤 다시 만든다. 슬라이드의 사실은 이 폴더의 문서에 근거가 있어야 한다. 문서를 고치면 해당 슬라이드도 함께 고친다.

아래부터 슬라이드 원고다.

팀 공유 세미나  |  2026-11


**발표자 노트**: 오늘은 리버스 엔지니어링이 무엇인지, 그리고 회사 PC에서 Ghidra와 REA로 어떻게 해 볼 수 있는지 소개합니다. 프로그래밍 전공이 아니어도 이해할 수 있게 준비했습니다.

### 2. 오늘 다룰 내용

> 전공과 상관없이 따라올 수 있도록, 새 용어는 나올 때마다 풀어서 설명합니다

시간 배분(모두 60분): 시작 3분, 1부 17분, 2부 6분, 3부 8분, 4부 16분, 정리와 질문 10분.

- **1부  RE란 무엇인가**: 무엇이고 왜 필요한가. 꼭 알아야 할 용어. 정적 분석과 동적 분석
- **2부  작업 절차**: 허가 확인부터 보고까지 7단계. 시작 전의 안전 수칙. 좋은 질문을 만드는 법
- **3부  Ghidra와 REA**: 실행 파일을 읽는 도구 Ghidra. 그 도구를 AI에게 맡기는 REA. AI 쪽 용어 정리
- **4부  회사 PC에서 쓰기**: Windows에서 되는 것과 안 되는 것. 설치와 연결. 질문하는 법과 결과 읽는 법

**발표자 노트**: 네 부분으로 진행합니다. 끝나고 나면 세 가지를 얻어 가시면 됩니다. 리버스 엔지니어링이 어떤 일인지 설명할 수 있고, 분석을 시작하기 전에 무엇을 확인해야 하는지 알고, REA에게 좋은 질문을 쓸 수 있게 됩니다. 한 장에 2분 안쪽으로 진행합니다.

### 3. 리버스 엔지니어링이란 무엇인가

> 완성된 결과물에서 거꾸로 설계와 동작을 읽어내는 일입니다

보통의 개발(Forward)은 설계에서 제품으로 간다. 리버스 엔지니어링(Reverse)은 같은 길을 제품에서 설계 쪽으로 거슬러 올라간다.

1. **설계와 의도**: 무엇을 어떻게 만들지 정한 것. 비유: 요리 구상
1. **소스 코드**: 사람이 읽고 쓰는 프로그램 원문. 비유: 레시피
1. **실행 파일**: 우리 손에 있는 완성품 (.exe). 비유: 완성된 요리

참고: 줄여서 RE라고 부른다. 완성품의 단서로 동작을 **추정**하는 일이다. 원래 설계와 작성 방식까지 똑같이 복원되지는 않는다. 목적은 프로그램을 뚫는 것이 아니라 이해하는 것이다.

**발표자 노트**: 리버스는 '거꾸로'라는 뜻입니다. 보통은 설계에서 제품으로 가는데, 리버스 엔지니어링은 제품에서 설계 쪽으로 거슬러 올라갑니다. 완성된 요리를 맛보고 재료와 조리 순서를 되짚는 것과 같습니다. 다만 원래 레시피를 그대로 되찾는 것은 아니고, 단서로 추정하는 것입니다. 해킹과 같은 말도 아닙니다. 사내 도구가 실제로 무엇을 하는지 이해하려는 일입니다.

### 4. 왜 우리에게 필요한가

> 상황은 달라도 답해야 할 질문은 하나입니다

네 상황의 공통 질문: "이 프로그램은 실제로 무엇을 하는가?" 리버스 엔지니어링은 이 질문에 근거를 붙여 답하는 방법이다.

- **소스가 없다**: 만든 사람이 떠났거나, 저장소 없이 실행 파일만 공유 폴더에 남았다
- **소스와 배포본이 다르다**: 저장소의 코드와 실제로 돌고 있는 프로그램이 같은 버전인지 아무도 모른다
- **연동해야 한다**: 웹 앱이 어떤 주소로 어떤 형식의 데이터를 주고받는지 문서가 없다
- **새로 만들어야 한다**: 기존 도구의 계산식과 판정 기준을 그대로 옮겨야 한다

참고: 소스 코드(Source Code): 사람이 작성한 프로그램 원문.  배포본: 사용자 PC에 실제로 설치되어 돌고 있는 프로그램.  저장소: 소스 코드를 보관하는 곳.

**발표자 노트**: 사내 도구는 만든 사람이 자리를 옮기면 실행 파일만 남는 경우가 많습니다. 고치거나, 다른 시스템과 잇거나, 새로 만들려면 그 프로그램이 실제로 무엇을 하는지부터 알아야 합니다. 리버스 엔지니어링은 그 질문에 근거를 붙여 답하는 방법입니다.

### 5. 용어 1: 프로그램은 어떻게 만들어지는가

> 사람이 읽는 글(소스 코드)을 컴퓨터가 읽는 숫자(실행 파일)로 바꾼 것이 프로그램입니다

1. **소스 코드 (Source Code)**: 사람이 읽고 쓰는 글. 이름, 설명(주석), 구조가 모두 들어 있다. 비유: 레시피

	```text
	if (value > 100)
	    return -1;
	return value * 2;
	```

1. **컴파일 (Compile)**: 소스 코드를 기계어로 번역하는 과정. 번역하는 프로그램이 컴파일러다. 비유: 조리

	```text
	소스 코드  →  기계어
	```

1. **실행 파일 (Binary)**: 컴퓨터가 실행하는 숫자 묶음. Windows에서는 .exe, .dll 파일. 비유: 완성된 요리

	```text
	8d 14 09 83 f9 65
	b8 ff ff ff ff
	0f 4c c2 c3
	```


핵심: 리버스 엔지니어링은 이 화살표를 거꾸로 거슬러 올라간다

참고: 이 그림은 C, C++처럼 기계어로 바로 만드는(네이티브) 프로그램의 예다. 웹, .NET, Python 프로그램은 남는 정보와 분석 방법이 다르다(12장).

**발표자 노트**: 용어부터 정리하겠습니다. 개발자가 쓰는 글이 소스 코드이고, 그것을 컴퓨터가 알아듣는 숫자로 번역하는 과정이 컴파일입니다. 결과물이 우리가 더블클릭하는 exe 파일입니다. 우리 손에는 보통 오른쪽 끝의 실행 파일만 있습니다. 왼쪽의 세 줄짜리 코드는 뒤에서 계속 예시로 씁니다. 값이 100보다 크면 -1, 아니면 2배를 돌려주는 코드입니다.

### 6. 컴파일은 정보를 버린다

> 사라진 정보가 많을수록 분석이 어렵습니다. 그래서 남은 단서에서 출발합니다

| 소스 코드에 있던 것 | 실행 파일에서는 | 분석할 때 보이는 모습과 쓰임 |
|---|---|---|
| 변수 이름, 설명(주석) | 사라짐 | local_18, param_1 같은 기계적인 이름으로 보인다 |
| 함수 이름 | 자주 사라짐 | FUN_00401a20처럼 위치(주소)로만 보인다 |
| 값의 종류(타입) | 자주 사라짐 | 숫자 계산과 위치 계산으로만 보인다 |
| 코드의 원래 모양 | 바뀜 | 더 빨리 돌도록 고쳐져서(최적화) 조건문과 반복문이 달라진다 |
| 화면 문구, 에러 메시지(문자열) | 남음 | 분석의 가장 좋은 출발점이 된다 |
| 외부 기능 호출 목록(임포트) | 남음 | 파일, 네트워크 등 무엇을 쓰는지 짐작하는 단서 |
| 실제 동작(기계어) | 남음 | 도구로 다시 글로 바꿔서 읽는다 |

참고: 비유: 이름표가 떨어진 서류함. 내용은 남아 있지만 각 칸의 역할은 찾아봐야 안다.  배포 설정에 따라 이름과 타입 정보가 남기도 한다. 남아 있으면 더 많이 알 수 있다.  함수(Function): 한 가지 일을 하는 코드 묶음.

**발표자 노트**: 컴퓨터는 변수 이름이나 주석이 필요 없기 때문에 번역할 때 버립니다. 그래서 실행 파일을 다시 글로 바꿔도 이름이 사라져 있습니다. 대신 화면에 보이는 문구나 에러 메시지 같은 글자는 그대로 남아서, 분석의 출발점이 됩니다. 빨간 칸이 잃는 것, 파란 칸이 남는 것입니다.

### 7. 같은 함수의 세 가지 모습

> 의사 코드로 빨리 뜻을 파악하고, 중요한 판단은 어셈블리로 확인합니다

1. **기계어 (Machine Code)**: 파일 안에 실제로 들어 있는 숫자. 이것이 원본이다.

	```text
	8d 14 09 83 f9 65
	b8 ff ff ff ff
	0f 4c c2 c3
	```

1. **어셈블리 (Assembly)**: 숫자에 명령어 이름을 붙인 표기. 정확하지만 읽기 어렵다.

	```text
	lea   edx, [rcx + rcx]
	cmp   ecx, 0x65
	mov   eax, 0xffffffff
	cmovl eax, edx
	ret
	```

1. **의사 코드 (Pseudocode)**: 읽기 좋게 다시 쓴 추정본. 원본이 아니다. param_1: 첫 입력값, 0x65: 101

	```text
	iVar1 = -1;
	if (param_1 < 0x65) {
	  iVar1 = param_1 * 2;
	}
	return iVar1;
	```


핵심: 왼쪽일수록 정확하다 (원본 그대로). 오른쪽일수록 읽기 쉽지만 추정이 섞인다

참고: 앞 장의 소스 "value가 100보다 크면 -1, 아니면 2배"와 같은 동작이다. 입력 100 → 200, 입력 101 → -1. 이름 value는 param_1이 되었고, "100보다 크다"는 "101보다 작다"의 반대 모양으로 바뀌었다.

**발표자 노트**: 같은 함수 하나를 세 가지 높이에서 본 모습입니다. 왼쪽이 파일에 실제로 든 숫자이고, 가운데가 그 숫자에 이름을 붙인 어셈블리, 오른쪽이 도구가 사람이 읽기 좋게 다시 써 준 의사 코드입니다. 오른쪽으로 갈수록 읽기 쉽지만 도구의 추정이 섞입니다. 어셈블리를 읽을 줄 몰라도 됩니다. 의사 코드가 원본이 아니라는 점만 기억하시면 됩니다.

### 8. 용어 2: 분석할 때 쓰는 말

> 용어는 많아 보여도, 모두 "단서를 찾고 따라가는" 동작에 붙인 이름입니다

| 용어 | 쉬운 뜻 | 비유 |
|---|---|---|
| 디스어셈블 (Disassemble) | 기계어 숫자를 어셈블리 명령어로 바꾼다 | 모스 부호를 글자로 옮겨 적기 |
| 디컴파일 (Decompile) | 남은 단서를 읽기 쉬운 코드로 다시 쓴다. 원문과 같다는 보장은 없다 | 요리를 맛보고 레시피 다시 쓰기 |
| 심볼 (Symbol) | 함수와 변수의 이름 정보. 배포할 때 지워지는 경우가 많다 | 서류함 칸에 붙은 이름표 |
| 임포트 (Import) | 프로그램이 Windows 같은 외부에서 빌려 쓰는 기능의 목록 | 요리에 쓴 시판 소스 목록 |
| 문자열 (String) | 프로그램 안에 든 글자. 화면 문구, 에러 메시지, 파일 경로 | 제품에 인쇄된 문구 |
| 상호 참조 (Xref) | "이 문자열과 함수를 누가 쓰는가"의 목록 | 책 뒤의 찾아보기(색인) |
| 진입점 (Entry Point) | 분석을 시작하는 지점. 버튼, 에러 문구, 화면 이름 | 미로의 입구 |

**발표자 노트**: 일곱 개를 다 외울 필요는 없습니다. 다음 장에서 이 용어들이 실제로 어떤 순서로 쓰이는지 그림으로 보겠습니다. 임포트는 프로그램이 파일을 여는지, 네트워크를 쓰는지 짐작하게 해 주는 단서입니다. 다만 임포트에 있다고 해서 실제로 호출했다는 증명은 아닙니다.

### 9. 단서를 따라가는 길: 화면 문구에서 코드까지

> 눈에 보이는 문구 하나가 가장 좋은 출발점입니다

1. **1  화면**: 눈에 보이는 버튼이나 문구에서 시작한다

	```text
	[ Export ]
	```

1. **2  문자열**: 그 문구를 파일 안에서 찾는다

	```text
	"Export completed"
	```

1. **3  상호 참조**: 그 문자열을 쓰는 함수를 찾는다

	```text
	누가 쓰는가?
	```

1. **4  함수 (진입점)**: 이름이 없어 주소로 불린다. 여기서부터 읽는다

	```text
	FUN_140012340
	```

1. **5  의사 코드**: 디컴파일해서 읽고, 여기서 부르는 함수를 따라간다

	```text
	if (...) { ... }
	```


핵심: REA도 속으로는 이 순서로 움직인다. 사람은 출발점(문구)을 알려 주면 된다

참고: 주소와 문구는 설명용 예시다.  임포트도 출발점이 된다. 예: 파일을 여는 Windows 기능을 빌려 쓰는 곳을 찾는다.

**발표자 노트**: 가장 흔한 탐색 방법입니다. 화면에 보이는 문구를 문자열에서 찾고, 상호 참조로 그 문구를 쓰는 함수를 찾고, 그 함수를 디컴파일해서 읽습니다. 앞 장의 용어가 이 순서로 쓰입니다. 뒤에서 볼 REA도 속으로는 이 순서로 움직입니다.

### 10. 정적 분석과 동적 분석

> 정적 분석으로 후보를 좁히고, 동적 분석으로 확인하는 순서가 기본입니다

두 분석은 번갈아 쓴다. 정적 분석에서 가설을 세워 동적 분석으로 확인하고, 결과가 다르면 다시 읽는다.

**정적 분석 (Static): 실행하지 않고 읽는다**

- 비유: 설계 도면을 펴 놓고 읽기
- 하는 일: 디컴파일, 문자열 검색, 호출 관계 추적
- 장점: 안전하고 몇 번이든 반복할 수 있다
- 한계: 실제로 어느 경로가 실행되는지는 모른다

**동적 분석 (Dynamic): 실행하면서 본다**

- 비유: 장비를 돌려 보면서 계측하기
- 하는 일: 화면 조작, 통신 기록, 출력 파일 확인
- 장점: 실제 값을 볼 수 있다
- 한계: 실행해 본 경로만 보인다. 운영 환경에서는 하지 않는다


핵심: 읽어서 가설을 세우고, 실행해서 확인한다. 결과가 가설과 다르면 실패가 아니라 정보다

**발표자 노트**: 도면만 봐서는 실제로 그 경로가 쓰이는지 알 수 없고, 돌려 보기만 해서는 돌려 본 경우만 알 수 있습니다. 그래서 둘을 같이 씁니다. 읽어서 가설을 세우고, 실행해서 확인합니다. 결과가 가설과 다르면 실패가 아니라 정보입니다.

### 11. 증거의 등급: 관찰, 추론, 미확인

> 보고서가 틀리는 가장 흔한 이유는 추론을 관찰처럼 쓰는 것입니다

미확인(Unknown): 도구가 볼 수 없었던 것. 예: 간접 호출이라 누가 이 함수를 부르는지 실행 전에는 찾지 못했다.

1. **관찰 (Observation)**: 도구가 직접 본 사실. 예: 이 함수가 문자열 'Recipe saved'를 참조한다
1. **추론 (Inference)**: 관찰을 묶어서 내린 해석. 예: 이 함수가 레시피 저장 함수일 것이다
1. **실행해서 확인**: 테스트 환경에서 저장을 실행해 본다
1. **관찰 (Observation)**: 확인된 사실. 예: 저장할 때 이 함수가 호출되었다

참고: 디컴파일 결과를 읽고 "이 함수는 A를 한다"고 쓰면 추론이다. 실행해서 A가 일어나는 것을 봐야 관찰이 된다. REA는 결과를 이 세 가지로 나눠서 돌려준다.  간접 호출: 부를 대상이 실행 중에 정해지는 호출.

**발표자 노트**: 실험 보고서에서 측정값과 해석을 구분하는 것과 같습니다. 그림은 한 가지 사례입니다. 문자열 참조를 본 것은 관찰, 그래서 저장 함수일 것이라는 것은 추론, 실행해서 확인하면 다시 관찰이 됩니다. REA도 결과를 이 세 가지로 나눠서 주기 때문에, 기록할 때 이 구분을 지우면 안 됩니다.

### 12. 대상에 따라 난이도가 다르다

> 무엇으로 만들었는지에 따라 남는 정보가 다릅니다. 쉬운 대상부터 시작합니다

**쉬움**

- **웹 앱의 화면 쪽**: 화면 쪽 코드가 이미 브라우저에 내려와 있다
- **웹 기술로 만든 설치형 앱 (Electron)**: 압축을 풀면 웹 앱과 같다
- **일반 .NET 프로그램 (C#)**: 클래스와 메서드 이름이 남는다

**보통**

- **Python 프로그램을 exe로 묶은 것 (PyInstaller)**: 내부 파일 목록이 남는다. 소스 복원은 별도 도구
- **Go, Rust 프로그램**: 모듈과 의존성 정보가 남는다

**어려움**

- **C, C++ 프로그램 (네이티브)**: 기계어, 임포트, 문자열만 남는다. Ghidra가 필요하다
- **웹 앱의 서버 쪽**: 밖에서는 요청과 응답만 보인다. 접근 권한을 받는 편이 빠르다


참고: 소스 맵(Source Map): 압축된 웹 코드를 원본 파일과 줄 번호로 되돌리는 지도 파일. 원본 내용이 들어 있으면 원본에 가깝게 읽을 수 있다.  네이티브(Native): CPU가 바로 실행하는 기계어로 만든 프로그램.

**발표자 노트**: 같은 프로그램이라도 만든 언어에 따라 난이도가 크게 다릅니다. 웹 앱은 코드가 이미 브라우저에 내려와 있어서 쉽습니다. C나 C++로 만든 프로그램이 가장 어렵고, 이때 Ghidra가 필요합니다. 서버 쪽은 접근 권한을 받는 것이 리버스 엔지니어링보다 빠릅니다.

### 13. 작업 절차 7단계

> 코드를 읽기 전에 허가, 질문, 대상부터 고정합니다

1~3단계는 준비, 4~6단계는 분석, 7단계는 정리다. 6단계 결과가 가설과 다르면 5단계로 돌아간다.

1. **범위와 허가**: 소유자, 목적, 동의, 실행 환경 확인
1. **질문 정하기**: 답할 수 있는 크기로 쪼갠다
1. **대상 식별**: 복사하고 해시를 기록한다
1. **정찰**: 문자열, 임포트에서 진입점 후보 찾기
1. **정적 분석**: 진입점에서 답까지 경로를 따라간다
1. **동적 확인**: 테스트 환경에서 실행해 확인한다
1. **기록과 보고**: 관찰, 추론, 미확인을 구분해 남긴다

참고: 해시(Hash): 파일의 지문. 내용이 한 글자만 달라도 값이 바뀐다. "그 파일이 이 파일인가"를 확인하는 데 쓴다.

**발표자 노트**: 새 분석을 시작할 때마다 이 순서를 따릅니다. 앞의 세 단계는 코드를 한 줄도 읽지 않는 단계인데, 여기를 건너뛰면 엉뚱한 파일을 분석하거나 끝이 없는 분석을 하게 됩니다. 폴더에 분석 기록 양식이 있으니 복사해서 단계마다 채우면 됩니다.

### 14. 시작 전에: 허가와 안전

> 동료가 만든 도구라도 바로 분석하지 않습니다

- **허가 범위 안에서만**: 소유 부서와 목적을 먼저 확인한다. 만든 사람에게 연락이 되면 묻는 편이 더 빠르다. 외부 상용 소프트웨어는 라이선스가 분석을 금지할 수 있다.
- **운영 환경에서 실행하지 않는다**: 장비 제어, DB 쓰기, 파일 삭제를 하는 도구는 분석 중에도 그 동작을 실제로 한다. REA는 실행 환경을 격리해 주지 않는다. 운영망, 운영 계정 정보, 공유 폴더가 연결되지 않은 테스트 환경에서만 실행한다.
- **회사 밖으로 내보내지 않는다**: 분석은 내 PC에서 하지만 결과는 AI 모델로 전달된다. 사내 LLM에 연결된 에이전트에서만 쓴다. 외부 AI 서비스에 붙여 넣지 않는다.

핵심: 확인한 내용(소유자, 목적, 허가, 실행 환경)은 분석 기록 양식에 먼저 적고 시작한다

**발표자 노트**: 세 가지를 먼저 확인합니다. 첫째는 허가입니다. 둘째는 실행 환경입니다. 분석하려고 실행한 도구가 실제 장비나 운영 DB를 건드릴 수 있습니다. 셋째는 반출입니다. 디컴파일한 코드나 경로 같은 결과가 AI 모델로 넘어가기 때문에 사내 LLM에 연결된 에이전트만 씁니다.

### 15. 좋은 질문이 분석의 절반이다

> "분석해줘"는 질문이 아닙니다. 시작점, 알고 싶은 결과, 끝낼 기준을 넣습니다

**나쁜 질문**

- "이 도구 분석해줘"
- "이 웹 앱 API 알려줘"
- "이 계산 로직 뭐야"

**좋은 질문**

- "Export 버튼을 누르면 어떤 파일이 어떤 형식으로 만들어지는가?"
- "목록 화면이 열릴 때 어떤 주소를 어떤 조건으로 호출하는가?"
- "결과 화면의 보정값은 어떤 입력으로 어떻게 계산되는가?"


참고: 질문마다 "어떤 증거가 있으면 답이 되는가"를 같이 적는다. 예: 파일을 쓰는 함수의 디컴파일 결과와 실제로 만들어진 파일 한 개.  API: 프로그램끼리 데이터를 주고받는 창구.

**발표자 노트**: 좋은 질문에는 세 가지가 들어 있습니다. 버튼이나 화면처럼 눈으로 볼 수 있는 시작점, 파일 형식이나 계산식처럼 알고 싶은 결과, 그리고 여기까지 알면 끝이라는 기준입니다. 사람에게 일을 맡길 때와 똑같습니다.

### 16. Ghidra: 실행 파일을 읽는 도구

> Ghidra(기드라)는 미국 NSA가 공개한 무료 분석 도구입니다. 회사 PC에 설치할 수 있습니다

**Ghidra가 해 주는 일**

- 실행 파일을 열어 함수 목록을 만든다
- 기계어를 어셈블리로 바꾼다 (디스어셈블)
- 어셈블리를 의사 코드로 바꾼다 (디컴파일)
- 문자열, 임포트, 상호 참조를 찾아 준다

**직접 쓰면 어려운 점**

- 화면과 메뉴가 많아 익히는 데 시간이 든다
- 프로젝트 생성, 파일 가져오기, 자동 분석 대기를 거쳐야 한다
- 함수 수십 개를 클릭으로 따라가면 반나절이 걸린다
- 결과를 읽으려면 C 언어와 어셈블리 지식이 필요하다


핵심: REA는 오른쪽의 손작업을 AI 에이전트에게 넘긴다 (다음 장)

**발표자 노트**: Ghidra는 앞에서 본 디스어셈블과 디컴파일을 해 주는 프로그램입니다. 무료이고 공개 소프트웨어입니다. 다만 전문가용 도구라서 화면이 복잡하고, 손으로 따라가는 작업이 많습니다. 이 손작업을 덜어 주는 것이 다음 장의 REA입니다.

### 17. REA: Ghidra를 AI에게 맡긴다

> 사람은 질문하고, AI 에이전트가 REA를 통해 Ghidra를 대신 조작합니다

1. **사람**: 질문을 고르고 결과의 등급을 따진다.
2. **AI 에이전트 (pi)**: 질문을 받아 어떤 도구를 쓸지 정한다. 사내 LLM(AI 모델)과 연결되어 있고, 도구 결과가 모델로 전달된다.
3. **REA**: 스킬(작업 지침서)과 MCP 서버(분석 도구 묶음). 에이전트가 MCP로 도구를 부르면 근거와 한계가 붙은 결과를 돌려준다.
4. **분석 엔진**: Ghidra(C, C++ 프로그램), JavaScript와 Electron 분석기, .NET과 Python 분석기, Chrome(웹 페이지 관찰).

REA와 분석 엔진은 내 PC에서 실행된다.


참고: REA(Reverse Engineer Anything): 공개 도구(github.com/morluto/rea). 분석은 내 PC에서 실행되고, 결과는 에이전트가 쓰는 AI 모델로 전달된다. 그래서 사내 LLM에 연결된 에이전트만 쓴다.

**발표자 노트**: REA는 AI 에이전트에 붙여 쓰는 분석 도구 묶음입니다. 우리가 글로 질문하면 에이전트가 REA의 도구를 부르고, REA가 Ghidra를 화면 없이 돌려서 결과를 돌려줍니다. 중요한 점은 REA가 결과마다 근거와 한계를 붙인다는 것입니다. AI가 근거 없이 지어내는 것을 막는 장치입니다. REA는 Ghidra 전용이 아니어서 웹 앱이나 .NET, Python 프로그램은 Ghidra 없이 분석합니다.

### 18. 용어 3: AI와 REA 쪽 말

> REA 스킬은 '지침서', MCP는 '연결선', Ghidra는 '엔진'으로 기억하면 됩니다

| 용어 | 쉬운 뜻 | 비유 |
|---|---|---|
| AI 에이전트 (Agent) | 지시를 받으면 도구를 스스로 골라 여러 단계의 일을 하는 AI 프로그램. 회사에서는 pi | 일을 맡길 수 있는 조수 |
| MCP | 에이전트가 외부 도구를 쓰기 위한 연결 규격 (Model Context Protocol) | 장비와 PC를 잇는 표준 커넥터 |
| REA 스킬 (Skill) | 에이전트에게 주는 작업 지침서. 어떤 순서로 어떤 도구를 쓸지 적혀 있다 | 작업 표준서 |
| 프로바이더 (Provider) | 네이티브 실행 파일을 분석하는 엔진. Ghidra, Hopper, IDA 중 우리는 Ghidra | 계측 장비 본체 |
| 세션 (Session) | 대상을 열고 닫을 때까지의 작업 한 묶음. 닫기 전에 근거를 파일로 저장한다 | 장비 한 번 가동 |
| Evidence | 도구 결과 한 건의 기록. 번호(Evidence ID)로 가리킨다 | 측정 기록지 |

**발표자 노트**: REA를 설치하면 두 가지가 함께 들어옵니다. 하나는 실제 분석 도구 묶음인 MCP 서버이고, 다른 하나는 에이전트가 그 도구를 어떻게 쓸지 적어 둔 지침서인 스킬입니다. 스킬 이름은 reverse-engineer-anything입니다. 우리는 스킬을 직접 읽을 필요는 없고, 에이전트가 읽고 따릅니다.

### 19. 직접 할 때와 REA로 할 때

> 손작업은 에이전트에게 넘기고, 사람은 질문과 판단에 집중합니다

**Ghidra를 직접 쓸 때**

- 프로젝트를 만들고 파일을 가져온다
- 자동 분석이 끝나기를 기다린다
- 함수 목록과 디컴파일 창을 오가며 클릭한다
- 읽은 내용을 손으로 정리한다

**REA를 쓸 때**

- 대상 경로와 질문을 글로 적는다
- 에이전트가 필요한 함수만 찾아서 읽는다
- 결론마다 근거 번호와 등급이 붙어서 온다
- 사람은 결과를 검토하고 다음 질문을 정한다


참고: 질문에 답할 소스가 온전히 있으면 소스부터 읽는다. REA는 배포된 결과물에서만 확인할 수 있는 사실이 필요할 때 쓴다. 예: 저장소의 코드와 배포된 .exe가 같은지 확인할 때.

**발표자 노트**: REA를 쓴다고 사람이 할 일이 없어지는 것은 아닙니다. 클릭하는 일이 없어지고, 질문을 고르는 일과 결과를 따지는 일이 남습니다. 그리고 소스가 온전히 있으면 소스부터 읽습니다. 실제 배포본이 소스와 같은지 확인하고 싶을 때가 REA를 쓸 때입니다.

### 20. 회사 PC(Windows)에서 되는 것과 안 되는 것

> Windows의 Ghidra 연동은 실험 단계이고 읽기 전용입니다. 사내 도구 분석에는 충분합니다

| 하려는 일 | Windows | 알아둘 점과 대처 |
|---|---|---|
| .exe, .dll 분석 (Ghidra) | 됨 | 읽기 전용. 대상 파일은 로컬 디스크(C:\re-work 등)에 복사해 둔다 |
| 일반 .NET 프로그램 분석 | 됨 | Ghidra 없이 별도 분석기로 본다 |
| Python을 exe로 묶은 프로그램 | 됨 | 내부 목록과 구조를 본다. 원래 Python 소스로 되돌려 주지는 않는다 |
| Electron 앱, 웹 페이지 관찰, HAR 분석 | 됨 | Chrome을 분석 전용 프로필로 띄운다 |
| REA로 함수에 이름, 주석 붙이기 | 안 됨 | 에이전트에게 주소와 제안 이름을 표로 정리하게 해서 기록에 남긴다 |
| 설치형 프로그램의 실행 관찰 | 안 됨 | 사람이 테스트 환경에서 직접 실행한다. 웹 페이지 관찰은 된다 |
| 공유 폴더, USB의 파일을 Ghidra로 분석 | 안 됨 | 고정 로컬 디스크(NTFS)로 복사한 뒤 분석한다 |

참고: HAR: 브라우저의 통신 기록 파일. 로그인 상태를 유지하는 인증 정보가 들어 있을 수 있으므로 분석이 끝나면 지운다.

**발표자 노트**: REA 문서는 맥과 리눅스 기준으로 쓰인 부분이 많아서, Windows에서 안 되는 기능이 몇 가지 있습니다. 실제로 아쉬운 것은 함수에 이름을 붙이는 기능 하나입니다. 에이전트에게 따라간 함수의 주소와 제안 이름을 표로 정리하라고 하면 됩니다. 그리고 분석할 파일은 반드시 로컬 디스크에 복사해 둡니다.

### 21. 설치와 연결 순서

> 새로 설치할 때는 사내 설치 금지 목록과 라이선스를 먼저 확인합니다

```text
# 1. 준비물 확인 (REA가 대신 설치해 주지 않는다)
#    Node.js 22.23.4 이상(22.x) 또는 24.22.1 이상(24.x)
#    Ghidra 12.1 이상의 12.x
#    JDK 21 이상 (Ghidra 12.2는 JDK 25 이상)

# 2. REA 설치 (npm: Node.js에 딸린 설치 도구)
npm install --global rea-agents

# 3. Ghidra와 Java의 위치를 알려 준다
$env:GHIDRA_INSTALL_DIR = "C:\tools\ghidra_12.1.4_PUBLIC"
$env:JAVA_HOME = "C:\Program Files\Java\jdk-21"
$env:REA_ANALYSIS_PROVIDER = "ghidra"

# 4. 진단
rea doctor --provider ghidra --json

# 5. 에이전트(pi)에 등록하고 확인
rea setup --client pi --dry-run --json
rea setup --client pi --yes --json
rea doctor --client pi --json
```

- **PowerShell**: Windows의 명령 입력 창. 여기에 왼쪽 명령을 입력한다
- **JDK**: Ghidra를 실행하는 데 필요한 Java 도구
- **환경 변수**: 프로그램에게 알려 주는 설정값. 여기서는 Ghidra와 Java가 설치된 위치
- **--dry-run**: 바뀔 내용만 미리 보여 주고 아무것도 바꾸지 않는다
- 등록한 뒤 pi에서 **/reload**를 실행한다
- 경로는 실제 설치 위치로 바꾼다. 자세한 내용은 rea-windows-pi-setup.md

**발표자 노트**: 한 번만 하면 되는 작업이고, 오늘 외울 내용은 아닙니다. 이런 순서라는 것만 보시면 됩니다. 준비물 세 가지는 REA가 대신 설치해 주지 않으니 먼저 있어야 합니다. rea doctor는 건강 검진 같은 명령입니다. 문제가 있으면 어디가 문제인지 알려 줍니다. 막히면 설정 문서를 보거나 저에게 물어보시면 됩니다.

### 22. 프롬프트에 넣을 네 가지

> 프롬프트(AI에게 보내는 지시문)의 질이 결과의 질을 정합니다. 이 틀을 복사해서 씁니다

나쁜 예는 "이 exe 분석해줘"다. 에이전트가 함수 목록부터 훑기 시작하고 결과는 넓고 얕다. CSV: 쉼표로 열을 나눈 표 파일.

1. **대상**: 파일의 전체 경로. "내 앱"처럼 모호하게 쓰지 않는다

	```text
	대상: C:\re-work\recipe-tool\RecipeTool.exe
	```

1. **질문**: 눈에 보이는 시작점과 알고 싶은 결과. 진입점 후보를 주면 빨라진다

	```text
	질문: "Export" 버튼을 누르면 만들어지는 CSV의
	      열 구성과 각 열의 계산 방법을 알고 싶다.
	진입점 후보: 문자열 "Export completed", "csv".
	```

1. **실행 범위**: 읽기만 할지, 실행해도 되는지. 적지 않으면 에이전트가 프로그램을 실행할 수 있다

	```text
	방법: 정적 분석만 한다. 프로그램을 실행하지 않는다.
	      프로바이더는 ghidra.
	```

1. **근거 요구**: 결론마다 근거 번호와 등급. 못 찾은 부분도 보고하게 한다

	```text
	결과 형식: 결론마다 Evidence ID와
	          관찰/추론/미확인 구분을 붙여라.
	          확인하지 못한 부분은 어디까지 찾아봤는지 적어라.
	```


**발표자 노트**: 에이전트에게 보내는 글에 이 네 가지를 넣습니다. 왼쪽이 실제 예시이고 오른쪽이 각 부분의 역할입니다. 특히 세 번째가 중요합니다. 정적 분석만 하라고 적지 않으면 에이전트가 프로그램을 실행하는 도구를 고를 수 있습니다. 나쁜 예는 '이 exe 분석해줘'입니다. 결과가 넓고 얕게 나옵니다. 질문이 여러 개면 나눠서 묻습니다.

### 23. 대상별로 REA가 가는 길

> Ghidra가 필요한 것은 기계어로 바로 만든(네이티브) 프로그램입니다

1. **네이티브 프로그램 (C, C++ 등)**: **Ghidra 필요**

	```text
	open_binary
	→ analyze_function
	```

1. **일반 .NET 프로그램 (C#)**: Ghidra 불필요

	```text
	inspect_managed_artifact
	```

1. **Python을 exe로 묶은 것 (PyInstaller)**: Ghidra 불필요

	```text
	open_binary
	→ inspect_artifact
	```

1. **웹 기술로 만든 설치형 앱 (Electron)**: Ghidra 불필요

	```text
	analyze_javascript_
	application
	```


참고: 도구 이름은 외울 필요가 없다. 에이전트가 고른다.  브라우저에 열린 웹 앱은 Chrome 관찰 도구(inspect_web_page)로 본다.  .NET이라도 기계어로 빌드한 것(NativeAOT)은 네이티브 경로로 간다.

**발표자 노트**: 에이전트는 대상의 형식을 보고 첫 도구를 고릅니다. 우리가 알아 둘 것은 하나입니다. 설치 폴더를 받았는데 무엇으로 만든 프로그램인지 모르면 폴더째 넘기면 REA가 판별해 줍니다. exe 하나가 아니라 폴더째 넘기는 이유는 DLL, 설정, 리소스가 함께 있어야 실제 동작을 설명할 수 있기 때문입니다. Ghidra까지 가는 것은 맨 왼쪽 길뿐입니다.

### 24. 네이티브 .exe 분석 흐름

> 넓게 훑은 뒤 한 곳만 깊게 봅니다. 닫기 전에 근거를 저장합니다

1. **정찰**: 문자열과 임포트로 관련 함수 후보를 찾는다. 아직 디컴파일하지 않는다
1. **진입점 선택**: 질문과 가장 가까운 함수 하나를 고른다
1. **깊게 읽기**: 그 함수만 분석한다. 요약부터 받고 필요한 부분만 펼친다
1. **어셈블리 확인**: 결과가 이상하면 디컴파일러를 거치지 않고 확인하게 한다
1. **근거 저장**: export_evidence_bundle로 근거를 파일에 저장한다
1. **세션 닫기**: close_binary. 현재 배포본(6.8.0)은 닫을 때 세션 기록을 지운다

참고: 큰 파일은 Ghidra가 처음 여는 데 몇 분이 걸린다. REA가 Ghidra 시작을 기다리는 기본 시간은 330초다.

**발표자 노트**: C나 C++ 프로그램을 분석할 때의 순서입니다. 왼쪽 깔때기처럼 처음에는 전체에서 후보를 좁히고, 함수 하나를 고른 뒤에야 깊게 읽습니다. 그리고 세션을 닫으면 근거 기록이 지워질 수 있으니 닫기 전에 꼭 파일로 저장하게 합니다.

### 25. 결과를 읽는 법

> 에이전트의 설명을 그대로 믿지 않습니다. 세 가지를 확인합니다

REA 결과에는 관찰, 추론, 미확인, 한계가 나뉘어 적힌다(슬라이드의 예시는 설명용으로 단순화한 것이다).

- **1  무엇을 못 봤는가**: 한계와 미확인부터 읽는다. 간접 호출, 잘린 결과가 여기에 적힌다
- **2  전체인가, 일부인가**: 커버리지(Coverage)를 본다. 일부만 보고 "없다"고 결론 내리지 않는다
- **3  어느 문장이 추론인가**: 추론은 실행해서 확인할 대상이다
- **관찰**: 함수 FUN_140012340이 문자열 "Export completed"를 참조한다  [Evidence ID]
- **추론**: 이 함수가 CSV 파일을 저장하는 함수일 것이다
- **미확인**: 간접 호출이라 누가 이 함수를 부르는지 찾지 못했다
- **한계**: 함수 목록의 일부 페이지만 읽었다  (커버리지: 일부)

참고: 남은 질문이 있으면 그 질문 하나만 좁혀서 다시 묻는다. 같은 분석을 그대로 다시 돌리지 않는다.

**발표자 노트**: AI가 쓴 설명은 그럴듯하게 읽힙니다. 그래서 결과를 받으면 먼저 무엇을 못 봤는지부터 확인합니다. REA는 한계와 커버리지를 결과에 같이 적어 주니 그 부분을 건너뛰지 않습니다. 왼쪽은 형식을 단순하게 보인 예시입니다.

### 26. 이런 일에 쓰면 좋다

> 배포된 결과물에서만 확인할 수 있는 사실이 필요할 때 씁니다

계산 로직을 옮길 때의 검증: 같은 입력(정상값, 경계값인 0과 음수와 아주 큰 값, 빈 입력)을 원본 도구와 새로 만든 코드에 넣고 출력을 비교한다. 시험한 입력에서 같으면 통과이고(프로그램 전체가 같다는 뜻은 아니다), 다르면 다시 분석한다.

- **버전 비교**: 지난달 배포본과 이번 배포본은 무엇이 다른가
- **계산 로직 옮기기**: 기존 도구의 계산식을 새 코드로 옮긴다
- **연동 정보 파악**: 웹 앱이 어떤 주소와 형식으로 데이터를 주고받는가
- **인수인계 없는 도구 파악**: 이 도구가 어떤 파일과 설정을 읽고 쓰는가

**발표자 노트**: 우리 팀에서 쓸 만한 경우 네 가지입니다. 특히 계산 로직을 옮길 때는 아래 그림처럼 옮긴 코드와 원본 도구에 같은 입력을 넣어 비교하는 것까지 해야 합니다. 0, 음수, 빈 값 같은 경계값도 꼭 넣습니다.

### 27. 자주 만나는 문제

> 막히면 먼저 rea doctor로 진단하고, 그다음 rea update로 최신 버전을 받습니다

| 증상 | 원인 | 해결 |
|---|---|---|
| pi에 REA 도구가 안 보인다 | 등록이 안 됐거나 다시 불러오지 않았다 | rea doctor --client pi 확인 후 /reload |
| Ghidra를 못 찾는다 | Ghidra 위치 설정이 등록 정보에 없다 | 등록 환경에 GHIDRA_INSTALL_DIR을 넣고 재시작 |
| 큰 파일이 시간 초과된다 | Ghidra 시작이 330초를 넘었거나, 에이전트의 대기 시간이 먼저 끝났다 | 어느 쪽인지 구분한 뒤 해당 제한 시간을 늘린다 |
| 결과에 의사 코드가 없다 | 기본 응답이 요약이다 | 필요한 부분만 펼쳐 달라고 한다 (inspect_analysis_view) |
| 닫았더니 근거가 사라졌다 | 현재 배포본은 세션을 닫을 때 기록을 지운다 | 닫기 전에 export_evidence_bundle로 저장 |

**발표자 노트**: 처음 쓸 때 자주 만나는 문제 다섯 가지입니다. 대부분 연결 설정 문제이고 rea doctor가 원인을 알려 줍니다. REA는 업데이트가 잦아서, 이상하면 최신 버전으로 올려 보는 것도 방법입니다.

### 28. 정리: 세 가지 원칙과 첫 실습

> 도구보다 원칙이 먼저입니다. 실습은 쉬운 대상부터 시작합니다

**꼭 지킬 세 가지**

- **허가 범위 안에서만** 분석한다
- **관찰, 추론, 미확인**을 구분해서 적는다
- 분석 결과를 **회사 밖으로 내보내지 않는다**. 사내 LLM에 연결된 에이전트만 쓴다

**처음 해 볼 실습**

- 사내 웹 앱 하나를 고르고 소유 부서의 동의를 받는다
- 개발자 도구(F12)의 Sources 탭에서 소스 맵이 있는지 본다
- Network 탭에서 버튼을 눌렀을 때 나가는 요청을 본다. 테스트 화면에서, 데이터를 바꾸지 않는 버튼으로 한다
- 익숙해지면 REA로 설치형 프로그램 하나에 질문 하나를 해 본다


핵심: 허가받은 대상에, 좁은 질문을 던지고, 근거의 등급을 따진다

**발표자 노트**: 오늘 내용에서 세 가지만 기억하신다면 왼쪽입니다. 실습은 웹 앱부터 권합니다. 브라우저만 있으면 되고, 진입점 찾기, 코드 따라가기, 실행으로 확인하기라는 기본 흐름을 한 번 경험할 수 있습니다.
