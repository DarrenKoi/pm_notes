# 02. 벡터, 임베딩, RAG와 온톨로지

## 이 글에서 답할 질문

- 문장이나 이미지가 어떻게 숫자로 바뀌나요?
- 벡터 검색은 키워드 검색과 무엇이 다른가요?
- RAG는 사내 자료를 어떻게 답변에 연결하나요?
- RAG가 원하는 문서를 못 찾을 때 무엇을 먼저 살펴야 하나요?
- 온톨로지는 지식 자산과 Agent 성능을 어떻게 연결하나요?

## 먼저 한 문장으로 정리해 보겠습니다

> 임베딩은 의미를 벡터로 표현하고, 벡터 검색은 가까운 의미를 찾으며, RAG는 찾은 자료를 LLM의 답변 근거로 제공합니다.

## Vector: 방향과 크기를 가진 숫자 묶음

Vector(벡터)는 여러 숫자를 순서대로 모은 값입니다.

```text
"설비 이상 진동" → [0.12, -0.44, 0.81, ...]
```

각 숫자 하나의 뜻을 사람이 직접 읽기는 어렵습니다. 의미가 비슷한 데이터끼리 벡터 공간에서 가까운 위치에 놓이도록 만드는 것이 중요합니다.

## Embedding: 의미를 벡터로 바꾸는 과정과 결과

Embedding(임베딩)은 문장·이미지·소리 같은 데이터를 의미를 반영한 벡터로 바꾸는 과정 또는 그 결과입니다.

도서관에 비유하면 임베딩은 책마다 “주제 좌표”를 붙이는 작업입니다. 제목에 같은 단어가 없어도 주제가 비슷하면 가까운 서가에 놓을 수 있습니다.

| 문장 | 키워드 일치 | 의미 관계 |
|---|---:|---|
| “장비 진동이 평소보다 큽니다.” | - | 기준 문장 |
| “설비 떨림 수치가 상승했습니다.” | 낮음 | 매우 비슷함 |
| “진동 교육 일정을 알려 주세요.” | 일부 있음 | 다른 의미 |

키워드 검색은 같은 단어를 찾는 데 강합니다. 벡터 검색은 표현이 달라도 의미가 가까운 내용을 잘 찾아냅니다. 실제 서비스에서는 두 방식을 합친 Hybrid Search(하이브리드 검색)를 자주 사용합니다.

## Vector Database: 벡터를 저장하고 가까운 값을 찾는 저장소

Vector Database(벡터 데이터베이스)는 많은 임베딩을 저장하고 질문 벡터와 가까운 항목을 빠르게 찾도록 설계된 저장소입니다.

일반적인 처리 과정은 다음과 같습니다.

```text
[자료를 준비할 때]
문서 → 작은 단위로 분할 → 임베딩 생성 → 벡터와 원문 저장

[질문을 받을 때]
질문 → 임베딩 생성 → 가까운 벡터 검색 → 관련 원문 반환
```

벡터 DB가 원문 자체를 이해하거나 답변을 작성하는 것은 아닙니다. “가까운 자료를 찾는 역할”을 담당합니다.

## RAG: 찾은 자료를 읽고 답하도록 만드는 구조

RAG(Retrieval-Augmented Generation, 검색 증강 생성)는 질문과 관련된 자료를 먼저 검색한 뒤, 그 자료를 LLM에 함께 제공해 답변을 생성하는 방식입니다.

```text
사용자 질문
    ↓
질문 임베딩
    ↓
관련 문서 검색 ── 벡터 DB·키워드 검색
    ↓
질문 + 검색된 문서
    ↓
LLM이 근거를 바탕으로 답변
    ↓
답변 + 출처
```

### 일반 업무 예시

“출장비 한도는 얼마인가요?”라는 질문을 받으면 RAG는 최신 출장 규정의 관련 문단을 찾아 LLM에 전달합니다. LLM은 그 문단을 읽고 금액과 적용 조건을 설명합니다.

### 제조 현장 예시

“이 알람 코드가 발생했을 때 먼저 무엇을 확인해야 하나요?”라는 질문을 받으면 매뉴얼, 장애 이력, 조치 절차에서 관련 내용을 찾아 순서대로 정리할 수 있습니다.

## RAG가 필요한 이유

- 모델이 학습하지 않은 내부 문서를 답변에 활용합니다.
- 문서를 다시 학습시키지 않고도 자료를 갱신할 수 있습니다.
- 답변과 함께 근거 문서를 제시합니다.
- 접근 권한과 검색 범위를 시스템에서 통제할 수 있습니다.

## RAG 품질을 좌우하는 두 단계: 청킹과 리랭킹

RAG가 기대만큼 동작하지 않을 때 원인은 대개 모델이 아니라 검색 쪽에 있습니다. 그중에서도 다음 두 단계가 결과를 크게 좌우합니다.

### Chunking: 문서를 검색 단위로 자르기

Chunking(청킹)은 긴 문서를 검색과 임베딩에 쓸 작은 덩어리로 나누는 작업입니다. 임베딩은 덩어리 하나를 벡터 하나로 압축하므로 어떻게 자르느냐가 곧 무엇을 찾을 수 있느냐를 결정합니다.

| 자르는 방식 | 생기는 문제 |
|---|---|
| 너무 크게 | 한 덩어리에 여러 주제가 섞여 의미가 흐려집니다 |
| 너무 작게 | 문장은 찾았는데 앞뒤 맥락이 빠져 답을 못 만듭니다 |
| 글자 수로만 | 표가 중간에서 잘리고 절차의 3번과 4번이 갈라집니다 |

그래서 실무에서는 제목·절 단위처럼 문서의 구조를 따라 자르고 덩어리마다 상위 제목을 함께 붙여 두는 방식을 많이 씁니다. 앞뒤를 조금씩 겹쳐 자르면 경계에서 잘리는 문제를 줄일 수 있습니다.

절차서, 규정, 표가 많은 사내 문서는 특히 구조를 살려 잘라야 합니다. "3단계에서 무엇을 확인하나요"라는 질문에 답하려면 그 절차 전체가 한 덩어리에 들어 있어야 합니다.

### Reranker: 찾아온 결과를 다시 줄 세우기

벡터 검색은 수백만 건에서 후보를 빠르게 추리는 데 강하지만 그 안의 순서까지 정확하지는 않습니다. Reranker(리랭커)는 1차로 찾은 후보 수십 건을 질문과 하나씩 대조해 다시 정렬하는 모델입니다.

```text
질문 → 벡터·키워드 검색으로 후보 50건 (빠르지만 순서가 거침)
                  ↓
       리랭커가 질문과 하나씩 비교
                  ↓
        상위 5건만 LLM에 전달 (느리지만 정확)
```

1차 검색으로 넓게 훑고 2차 정렬로 정밀하게 고르도록 단계를 나누는 이유는 비용 때문입니다. 정확한 방식은 느리므로 전체에 적용할 수 없고 빠른 방식은 순서가 거칠기 때문입니다.

리랭킹을 넣으면 LLM에 넘기는 문서 수를 줄이면서도 정확도를 유지할 수 있습니다. 넘기는 문서가 줄면 토큰 비용과 응답 시간도 함께 줄어듭니다.

## 사내 AI에서 RAG가 사실상 필수인 이유

번역이나 일반적인 문장 다듬기에는 별도의 지식 연결이 없어도 됩니다. 그러나 **사내 고유 지식, 최신 규정, 업무 이력, 권한이 있는 자료를 바탕으로 답하거나 행동하는 AI Agent를 만들려면 RAG를 포함한 검색·지식 연결 기반은 사실상 필수**입니다.

LLM 자체는 우리 회사의 최신 업무 기준과 암묵지, 시스템 상태를 자동으로 알지 못합니다. 모델을 크게 만드는 것만으로 이 간격을 메울 수도 없습니다. 비정형 문서에는 RAG가 대표적인 방법이고 정확한 운영 값에는 데이터베이스 조회나 API 도구가 더 적합할 수 있습니다. 중요한 것은 Agent가 필요한 근거를 신뢰할 수 있는 경로로 가져와 판단에 사용하게 만드는 것입니다.

```text
사내 문서·데이터·업무 경험
            ↓
정리·분류·권한·버전 관리
            ↓
검색 가능한 지식 자산
            ↓
RAG가 필요한 근거를 검색
            ↓
Agent가 근거를 바탕으로 판단·도구 사용
            ↓
결과와 피드백을 다시 지식으로 축적
```

따라서 Agent 성능은 모델 성능만으로 결정되지 않습니다.

```text
Agent 성능
  = 모델의 기본 능력
  + 검색된 지식의 품질
  + 도구와 업무 절차
  + 권한과 검증 체계
```

아무리 좋은 모델을 사용해도 오래된 절차서, 서로 충돌하는 문서, 출처를 알 수 없는 자료가 검색되면 Agent는 잘못된 근거로 자신 있게 행동할 수 있습니다. 반대로 지식이 체계적으로 관리되면 더 작은 모델도 정해진 업무에서 안정적인 결과를 낼 수 있습니다.

## 문서 보관을 넘어 지식 자산화로

파일을 한곳에 모아 두는 것만으로는 지식 자산화가 이루어지지 않습니다. AI와 사람이 반복해서 활용할 수 있도록 다음 정보를 함께 관리해야 합니다.

| 관리 항목 | 확인할 질문 | Agent 성능과의 연결 |
|---|---|---|
| 소유자 | 누가 내용을 책임지고 갱신하나요? | 오래된 지식의 방치 방지 |
| 유효기간·버전 | 현재 적용되는 기준은 무엇인가요? | 충돌하는 답변 감소 |
| 출처·근거 | 원본과 승인 이력을 찾을 수 있나요? | 답변 검증과 감사 가능 |
| 메타데이터 | 공정, 설비, 제품, 업무 단계가 표시되어 있나요? | 검색 범위와 정확도 개선 |
| 접근 권한 | 사용자와 Agent가 볼 수 있는 자료인가요? | 정보 노출 방지 |
| 문서 구조 | 제목, 단락, 표, 용어가 일관적인가요? | Chunk 분할과 검색 품질 개선 |
| 평가·피드백 | 잘못 찾은 자료와 누락을 기록하나요? | 검색과 지식의 지속 개선 |

좋은 RAG 구축은 일회성 데이터 적재가 아니라 **지식을 수집하고, 정리하고, 검증하고, 사용 결과를 다시 반영하는 운영 체계**를 만드는 일입니다.

## Ontology: 사내 지식의 공통 지도

Ontology(온톨로지)는 업무에서 사용하는 대상과 개념, 속성, 관계를 일관된 구조로 정의한 **지식의 지도**입니다.

예를 들어 제조 업무에서는 다음 관계를 표현할 수 있습니다.

```text
설비
 ├─ 설치 위치 → 공정
 ├─ 처리 대상 → 제품
 ├─ 발생 이벤트 → 알람
 └─ 알람의 대응 → 점검 절차

제품
 └─ 적용 조건 → Recipe
```

단순 용어집이 “이 단어는 이런 뜻입니다”라고 설명한다면, 온톨로지는 “이 대상이 다른 대상과 어떻게 연결됩니다”까지 표현합니다.

| 구성 요소 | 예시 |
|---|---|
| 개념·대상 | 설비, 공정, 제품, Recipe, 알람 |
| 속성 | 설비 코드, 위치, 버전, 발생 시각 |
| 관계 | 설비가 공정에 속함, 알람이 점검 절차와 연결됨 |
| 동의어·표준어 | 장비·설비, Recipe·레시피의 표현 통합 |
| 규칙 | 특정 알람은 지정된 설비 유형에만 적용 |

### 온톨로지가 RAG와 Agent를 돕는 방법

- 서로 다른 부서의 표현을 표준 용어로 연결합니다.
- 질문에 나온 설비·제품·공정을 구분해 검색 범위를 좁힙니다.
- 단순히 비슷한 문장뿐 아니라 관계가 있는 자료까지 찾게 합니다.
- Agent가 어떤 도구와 절차를 사용해야 하는지 판단하는 단서를 제공합니다.
- 서로 모순되는 관계나 잘못 연결된 데이터를 발견하는 데 도움을 줍니다.

온톨로지가 있다고 RAG가 자동으로 좋아지는 것은 아닙니다. 처음부터 모든 지식을 거대한 구조로 만들기보다 검색이 자주 실패하고 부서별로 표현 차이가 큰 핵심 업무부터 개념과 관계를 정의하는 편이 현실적입니다.

## 자주 생기는 오해

### “RAG를 쓰면 환각이 없어지나요?”

아닙니다. 검색 결과가 부정확하거나 LLM이 자료를 잘못 해석하면 틀린 답이 나올 수 있습니다. 출처 표시와 평가가 여전히 필요합니다.

### “문서를 벡터 DB에 넣으면 모델이 학습하나요?”

아닙니다. 모델의 파라미터는 바뀌지 않습니다. 질문할 때 필요한 문서를 찾아 임시로 컨텍스트에 넣는 방식입니다.

### “벡터 검색은 항상 키워드 검색보다 좋은가요?”

아닙니다. 제품 코드, 오류 번호, 사람 이름처럼 정확한 문자열이 중요한 검색은 키워드 방식이 더 적합할 수 있습니다.

### “검색된 문서는 모두 믿어도 되나요?”

아닙니다. 오래된 문서, 중복 자료, 권한이 잘못 설정된 자료가 섞일 수 있습니다. 문서의 소유자·유효기간·보안 등급을 함께 관리해야 합니다.

## 좋은 RAG를 만드는 일곱 가지 질문

1. 믿을 수 있는 원본 문서만 들어가 있나요?
2. 문서를 찾기 좋은 크기로 나누었나요?
3. 정확한 문자열 검색과 의미 검색을 적절히 조합했나요?
4. 사용자가 볼 수 있는 문서만 검색하나요?
5. 답변에 출처와 “모르겠습니다”라는 선택지가 있나요?
6. 핵심 용어와 대상의 관계가 일관되게 정의되어 있나요?
7. 검색 실패와 현업 피드백이 지식 갱신으로 이어지나요?

## 핵심 요약

- 벡터는 숫자 묶음이고 임베딩은 데이터의 의미를 벡터로 표현합니다.
- 벡터 검색은 표현이 달라도 의미가 가까운 자료를 찾는 데 유용합니다.
- RAG는 검색 결과를 LLM에 제공해 내부·최신 지식에 근거한 답변을 돕습니다.
- RAG가 잘 안 되는 원인은 대개 모델이 아니라 청킹과 검색 순위에 있습니다.
- 사내 고유 지식을 사용하는 Agent에는 RAG를 포함한 검색·지식 연결과 체계적인 지식 자산화가 사실상 필수입니다.
- 온톨로지는 사내 개념과 관계를 정의해 검색과 Agent 판단의 정확도를 높이는 데 도움을 줄 수 있습니다.
- RAG는 재학습이 아니며, 정확성을 자동으로 보장하지도 않습니다.
