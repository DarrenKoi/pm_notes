# 09. 프롬프트, RAG, 파인튜닝 중 무엇을 선택할까

## 이 글에서 답할 질문

- 우리 업무에 파인튜닝이 필요한가요?
- RAG와 파인튜닝은 무엇을 각각 해결하나요?
- 잘 동작하는지 어떻게 확인하나요?

## 먼저 한 문장으로 정리해 보겠습니다

> 지식이 부족하면 RAG로 가져오고 형식과 말투가 흔들리면 프롬프트와 예시로 잡고 그래도 반복해서 부족한 패턴이 남을 때에야 파인튜닝을 검토합니다.

## 네 가지 방법을 한 표로 비교하기

| 방법 | 무엇을 바꾸나요 | 잘 해결하는 문제 | 준비 비용 | 갱신 방법 |
|---|---|---|---|---|
| 프롬프트 개선 | 요청 문장만 | 목적·형식·제약 전달 | 매우 낮음 | 문장 수정 |
| Few-shot 예시 | 요청 안의 예시 | 고유 분류 기준, 출력 형식 | 낮음 | 예시 교체 |
| RAG | 참고 자료 | 사내 지식, 최신 정보, 근거 제시 | 중간 | 문서 갱신 |
| 파인튜닝 | 모델 파라미터 | 고정된 스타일·형식·도메인 표현 | 높음 | 재학습 |

위에서부터 순서대로 시도하는 것이 대체로 효율적입니다. 아래로 갈수록 효과가 큰 것이 아니라 **비용과 되돌리기 어려움이 커집니다.**

## 의사결정 순서

```text
결과가 만족스럽지 않다
        ↓
모델이 몰라서 틀리나? ──── 예 ──→ RAG 또는 도구 연결
        │ 아니오
        ↓
형식·기준이 흔들리나? ─── 예 ──→ 프롬프트 정교화 + Few-shot
        │ 아니오
        ↓
같은 패턴을 매번 길게 설명해야 하나? ─ 예 ─→ 파인튜닝 검토
        │ 아니오
        ↓
모델 자체의 능력 한계 ──→ 더 큰 모델 또는 추론 모델
```

핵심 질문은 **"모델이 몰라서 틀리는가, 알면서 다르게 하는가"**입니다. 모르는 문제에 파인튜닝을 하면 비용만 쓰고 환각이 늘어납니다.

## 파인튜닝에 대한 흔한 오해

### "사내 문서를 파인튜닝하면 AI가 우리 회사를 알게 되나요?"

기대만큼 되지 않습니다. 파인튜닝은 지식을 정확히 주입하는 수단으로는 약합니다. 문서를 학습시켜도 모델은 내용을 정확히 외우기보다 그 문체와 형식을 흉내 내는 쪽에 가깝습니다. 결과적으로 **우리 회사 문서처럼 보이지만 틀린 답**이 나오기 쉽습니다.

게다가 규정이 바뀔 때마다 다시 학습해야 합니다. 특정 문서만 삭제하기도 어렵고 사용자별 권한 구분도 불가능합니다. 사내 지식은 대부분 RAG와 도구 연결이 맞습니다.

### "파인튜닝은 언제 유리한가요?"

- 출력 형식이 매우 엄격하고 반복적일 때
- 사내 고유 용어와 표기 규칙을 일관되게 지켜야 할 때
- 프롬프트가 지나치게 길어져 매 호출의 비용이 부담될 때
- 작은 모델로 특정 작업만 저렴하게 처리하고 싶을 때

즉 파인튜닝은 지식보다 **행동 방식**을 고정하는 데 적합합니다.

### LoRA: 전체를 다시 학습하지 않는 방법

LoRA(Low-Rank Adaptation)는 모델 전체를 다시 학습하는 대신 작은 보조 가중치만 학습하는 방식입니다. 필요한 GPU와 시간이 크게 줄고 용도별 어댑터를 만들어 바꿔 끼울 수 있습니다. 사내에서 파인튜닝을 검토한다면 대개 이런 경량 방식이 현실적인 출발점입니다.

## 사내 환경에서 추가로 고려할 점

외부 서비스를 자유롭게 쓰기 어려운 환경이라면 선택 기준이 달라집니다.

| 고려 사항 | 확인할 질문 |
|---|---|
| 데이터 반출 | 이 자료를 이 시스템에 넣어도 되나요? |
| 사용 가능한 모델 | 사내에서 제공되는 모델과 임베딩은 무엇인가요? |
| 연산 자원 | 파인튜닝에 쓸 GPU와 담당 인력이 있나요? |
| 운영 주체 | 학습한 모델을 이후 누가 관리하나요? |

특히 마지막 항목이 자주 빠집니다. 파인튜닝 모델은 만든 뒤에도 버전 관리, 성능 추적, 재학습 계획이 계속 필요합니다. 담당자가 정해지지 않은 파인튜닝은 6개월 뒤 아무도 손대지 못하는 자산이 됩니다.

## 그래서 잘 되는지 어떻게 확인하나요?

어떤 방법을 선택하든 "돌려 보니 괜찮네요"는 근거가 되지 못합니다. AI 출력은 매번 조금씩 달라지므로 표본으로 확인해야 합니다.

### Golden Set: 정답이 있는 시험지 만들기

Golden Set(골든셋)은 실제 업무에서 뽑은 입력과 사람이 합의한 기대 출력의 모음입니다. 규모는 크지 않아도 됩니다. 대표 사례와 경계 사례를 합해 30~100건이면 시작할 수 있습니다.

```text
현업 사례 수집 → 기대 출력 합의 → 골든셋 확정
        ↓
프롬프트·RAG·모델 변경
        ↓
골든셋으로 재실행하고 점수 비교
        ↓
떨어진 항목 확인 후 반영
```

이 절차의 진짜 가치는 점수 자체가 아니라 **바꾼 것이 이전 것을 망가뜨리지 않았음을 확인**하는 데 있습니다.

### 무엇을 측정하나요?

| 측정 항목 | 확인 방법 |
|---|---|
| 정확성 | 정답과 일치하는 비율 |
| 근거 충실성 | 답변이 검색된 문서에 실제로 근거하는지 |
| 검색 품질 | 필요한 문서가 상위에 검색되는지 |
| 형식 준수 | 정해진 항목과 구조를 지키는지 |
| 거절 적절성 | 모르는 것을 모른다고 답하는지 |
| 비용·지연 | 토큰 사용량과 응답 시간 |

### LLM-as-a-Judge: AI가 AI를 채점하기

정답이 하나로 정해지지 않는 요약이나 설명은 사람이 매번 채점하기 어렵습니다. 이때 별도의 모델에게 채점 기준을 주고 평가를 맡기는 방법을 씁니다.

빠르고 저렴하지만 한계가 분명합니다. 채점 모델에도 편향이 있고 길고 자신감 있는 답에 높은 점수를 주는 경향이 알려져 있습니다. 그래서 사람 검토를 대체하는 것이 아니라 **1차 선별로 쓰고 표본은 사람이 다시 확인**하는 구성이 안전합니다.

## 시작할 때의 현실적인 순서

1. 실제 업무 사례 30건을 모읍니다.
2. 기본 프롬프트로 실행하고 틀린 것을 분류합니다.
3. 원인이 지식 부족인지, 지시 부족인지 나눕니다.
4. 지식 부족이면 자료 연결을, 지시 부족이면 프롬프트와 예시를 개선합니다.
5. 골든셋으로 다시 측정합니다.
6. 여기까지에서 해결되지 않은 것만 파인튜닝 후보로 남깁니다.

대부분의 사내 과제는 4단계에서 충분한 수준에 도달합니다.

## 핵심 요약

- 프롬프트 → 예시 → RAG → 파인튜닝 순으로 검토하면 비용 대비 효과가 좋습니다.
- 파인튜닝은 지식 주입이 아니라 행동 방식을 고정하는 데 적합합니다.
- 사내 지식은 대부분 RAG와 도구 연결이 정답이며 권한과 갱신 측면에서도 유리합니다.
- 골든셋 없이 바꾸면 무엇이 좋아지고 나빠졌는지 알 수 없습니다.
- LLM 채점은 1차 선별이고, 최종 판단의 책임은 사람에게 남습니다.
