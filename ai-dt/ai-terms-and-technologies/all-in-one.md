# AI 용어 및 기술 소개: 한 편으로 읽는 통합본

> 이 문서는 AI를 처음 접하는 전사 구성원을 위해 주요 용어를 하나의 흐름으로 설명합니다. 세부 설명과 더 많은 예시는 [주제별 목차](./README.md)에서 확인하실 수 있습니다.

## 전체 흐름

```text
모델이 언어·이미지·행동을 처리합니다.
              ↓
토큰과 컨텍스트라는 한계 안에서 동작합니다.
              ↓
임베딩과 RAG가 필요한 자료를 연결합니다.
              ↓
제로샷과 퓨샷으로 원하는 작업을 알려 줍니다.
              ↓
하네스와 에이전트가 도구를 사용해 업무를 수행합니다.
              ↓
리터러시와 검증으로 편향·슬롭·보안 위험을 관리합니다.
              ↓
AX와 AI 데이터 센터가 조직 차원의 활용을 뒷받침합니다.
```

## 1. LLM, SLM, VLM, VLA와 지식 증류

### LLM: 언어를 다루는 대규모 모델

LLM(Large Language Model, 대규모 언어 모델)은 많은 텍스트를 학습하고 주어진 문맥에서 다음에 올 표현을 예측하며 답변·요약·번역·코드 등을 만듭니다.

자연스러운 문장을 만든다고 해서 모든 내용을 사실로 알고 있는 것은 아닙니다. 학습 시점 이후의 사실이나 회사 내부 자료를 자동으로 알지 못하고, 그럴듯하지만 틀린 내용을 생성할 수 있습니다.

### SLM: 작고 가벼운 언어 모델

SLM(Small Language Model, 소규모 언어 모델)은 상대적으로 적은 파라미터와 연산 자원으로 동작합니다. 범용성이 필요한 복잡한 분석에는 LLM이 유리할 수 있지만 분류·정보 추출·기기 내 처리처럼 범위가 분명한 업무에는 SLM이 빠르고 경제적일 수 있습니다.

### VLM: 이미지와 언어를 함께 이해

VLM(Vision-Language Model, 시각·언어 모델)은 이미지와 텍스트를 함께 처리합니다. 사진 설명, 도표 이해, 화면 질의응답, 외관 이미지 검토 보조 등에 활용할 수 있습니다.

### VLA: 이해를 실제 행동으로 연결

VLA(Vision-Language-Action Model, 시각·언어·행동 모델)는 카메라 영상과 언어 지시를 로봇이나 장치의 행동으로 연결합니다. 물리적 행동은 잘못되었을 때 피해가 클 수 있으므로 속도·구역 제한, 충돌 방지, 비상 정지 같은 별도 안전장치가 필요합니다.

| 용어 | 구분 기준 | 주요 입력과 출력 |
|---|---|---|
| LLM | 언어와 큰 규모 | 텍스트 → 텍스트 |
| SLM | 작은 규모 | 주로 텍스트 → 텍스트 |
| VLM | 시각과 언어 | 이미지·텍스트 → 설명 등 |
| VLA | 시각·언어·행동 | 이미지·지시 → 행동 명령 |

SLM은 크기 기준이고 VLM·VLA는 입출력 방식 기준입니다. 따라서 작은 VLM도 존재할 수 있습니다.

### Reasoning Model: 답하기 전에 더 오래 생각

Reasoning Model(추론 모델)은 입출력이 아니라 **답을 만들기 전에 쓰는 계산량**으로 구분한 개념입니다. 일반 모델이 곧바로 답을 쓰기 시작한다면, 추론 모델은 문제를 쪼개고 중간 단계를 따져 본 뒤 답합니다.

수학, 복잡한 코드, 다단계 계획, 원인 분석에 유리하지만 느리고 비쌉니다. 보이지 않는 사고 과정에도 토큰이 들기 때문입니다. 모든 질문에 쓰기보다 어려운 문제에만 선택적으로 쓰는 편이 좋습니다. 오래 생각한다고 정답이 보장되지도 않습니다. 전제가 틀리면 정교한 논리로 틀린 결론에 도달합니다.

### MoE: 크지만 일부만 쓰는 구조

MoE(Mixture of Experts, 전문가 혼합)는 모델 내부를 여러 전문가 블록으로 나누고 토큰마다 일부만 활성화하는 구조입니다. 메모리에는 전체를 올려야 하지만 실제 연산은 활성 부분만 씁니다. 그래서 "총 파라미터 400B, 활성 40B"처럼 표기된 모델은 파라미터 수만으로 필요한 자원과 속도를 계산하면 어긋납니다.

### Distillation: 큰 교사의 판단을 작은 학생에게

Distillation(지식 증류)은 큰 Teacher Model(교사 모델)의 출력이나 판단 패턴을 작은 Student Model(학생 모델)이 배우게 하는 모델 압축 방법입니다.

증류된 모델은 더 빠르고 적은 메모리와 전력을 사용할 수 있지만 교사의 능력을 모두 보존하지 못할 수 있습니다. 교사의 오류와 편향도 함께 배울 수 있으므로 별도의 평가가 필요합니다.

## 2. 벡터, 임베딩, RAG와 온톨로지

### Vector와 Embedding

Vector(벡터)는 여러 숫자를 순서대로 모은 값입니다. Embedding(임베딩)은 문장·이미지 같은 데이터의 의미를 벡터로 표현하는 과정 또는 결과입니다.

```text
"설비 진동이 증가했습니다." → [0.12, -0.44, 0.81, ...]
```

의미가 비슷한 데이터가 벡터 공간에서 가까워지도록 만들면, 정확히 같은 단어가 없어도 관련 자료를 찾을 수 있습니다.

키워드 검색은 제품 번호, 오류 코드, 이름처럼 정확한 문자열을 찾는 데 강합니다. 벡터 검색은 “설비 떨림”과 “장비 진동”처럼 표현이 달라도 의미가 가까운 자료를 찾는 데 유리합니다. 실무에서는 두 방식을 합친 하이브리드 검색을 자주 사용합니다.

### RAG: 자료를 먼저 찾고 답변하기

RAG(Retrieval-Augmented Generation, 검색 증강 생성)는 관련 자료를 먼저 검색한 뒤, 그 자료를 LLM에 함께 제공해 답변을 만드는 구조입니다.

```text
질문 → 검색 → 관련 원문 → 질문과 원문을 LLM에 제공 → 답변과 출처
```

RAG를 사용하면 최신 규정, 사내 매뉴얼, 장애 이력처럼 모델이 원래 알지 못하는 자료를 활용할 수 있습니다. 문서를 갱신할 때 모델을 다시 학습할 필요도 없습니다.

그러나 RAG가 정확성을 보장하지는 않습니다. 잘못되거나 오래된 문서가 검색될 수 있고 LLM이 근거를 잘못 해석할 수도 있습니다. 문서 소유자와 유효기간, 접근 권한, 출처 표시, “모르겠습니다”라는 응답 기준이 필요합니다.

### 청킹과 리랭킹: 검색 품질을 좌우하는 두 단계

RAG가 기대만큼 동작하지 않을 때 원인은 대개 모델이 아니라 검색 쪽에 있습니다.

Chunking(청킹)은 긴 문서를 검색 단위로 자르는 작업입니다. 너무 크면 여러 주제가 섞여 의미가 흐려지고 너무 작으면 앞뒤 맥락이 빠집니다. 글자 수로만 자르면 표가 중간에서 잘리고 절차의 3번과 4번이 갈라집니다. 그래서 제목·절 단위로 자르고 상위 제목을 함께 붙이는 방식을 많이 씁니다.

Reranker(리랭커)는 1차 검색으로 찾은 후보 수십 건을 질문과 하나씩 대조해 다시 정렬하는 모델입니다. 넓게 훑는 검색은 빠르지만 순서가 거칠고 정밀한 비교는 정확하지만 느립니다. 두 단계를 나누면 LLM에 넘기는 문서를 줄이면서 정확도를 지킬 수 있고 토큰 비용과 응답 시간도 함께 줄어듭니다.

### 사내 Agent 성능은 지식 자산에서 시작

번역이나 일반적인 글쓰기에는 별도의 지식 연결이 없어도 됩니다. 그러나 사내 고유 지식, 최신 업무 기준, 권한이 있는 자료를 사용하는 AI Agent에는 RAG를 포함한 검색·지식 연결 기반이 사실상 필수입니다. 비정형 문서는 RAG로 찾고, 정확한 운영 값은 데이터베이스나 API 도구로 조회하는 식으로 자료에 맞는 경로를 선택해야 합니다.

```text
Agent 성능
  = 모델의 기본 능력
  + 검색된 지식의 품질
  + 도구와 업무 절차
  + 권한과 검증 체계
```

문서를 모아 두는 것만으로는 충분하지 않습니다. 소유자, 버전, 유효기간, 출처, 업무별 메타데이터, 접근 권한을 관리하고 검색 실패와 현업 피드백을 다시 반영해야 검색 가능한 지식 자산이 됩니다.

Ontology(온톨로지)는 설비·공정·제품·알람·점검 절차 같은 개념과 그 관계를 정의하는 지식의 지도입니다. 단순 용어집이 단어의 뜻을 설명한다면, 온톨로지는 “어떤 설비가 어느 공정에 속하고, 어떤 알람이 어느 점검 절차와 연결되는가”까지 표현합니다.

온톨로지는 부서마다 다른 표현을 연결하고 검색 범위를 좁히며, Agent가 관련 자료와 도구를 선택하는 데 도움을 줍니다. 처음부터 거대한 온톨로지를 만들기보다 검색 실패가 잦고 표현 차이가 큰 핵심 업무부터 구축하는 편이 현실적입니다.

## 3. Zero-shot, One-shot과 Few-shot

`Shot`은 현재 프롬프트 안에 넣어 주는 완성 예시의 수입니다.

| 방식 | 예시 수 | 적합한 상황 |
|---|---:|---|
| Zero-shot | 0개 | 일반적인 요약·번역·질문 |
| One-shot | 1개 | 출력 형식을 간단히 보여 줄 때 |
| Few-shot | 여러 개 | 고유 기준, 경계 사례, 일정한 형식이 중요할 때 |

예를 들어 “고객 의견을 긍정·중립·부정으로 분류해 주세요”라고만 요청하면 제로샷입니다. 각 범주의 입력과 기대 출력을 몇 개 보여 주면 퓨샷입니다.

퓨샷은 모델을 다시 학습하는 방법이 아닙니다. 예시는 현재 요청의 컨텍스트에서만 사용되고 모델의 파라미터는 바뀌지 않습니다.

좋은 퓨샷 예시는 다음 조건을 갖춥니다.

- 실제 업무의 대표 사례와 경계 사례를 함께 담습니다.
- 입력과 출력 형식이 일관됩니다.
- 한 유형이나 집단에 치우치지 않습니다.
- 개인정보와 사내 민감 정보를 포함하지 않습니다.
- 예시와 함께 명확한 작업 지시를 제공합니다.

예시가 많다고 항상 좋은 것은 아닙니다. 먼저 제로샷으로 시작하고 결과의 기준이나 형식이 흔들릴 때 필요한 예시만 추가하는 편이 효율적입니다.

## 4. Vibe Coding, Harness, AI Agent와 Orchestration

### Vibe Coding: 결과 중심의 작업 방식

Vibe Coding(바이브 코딩)은 자연어로 원하는 것을 설명하고 AI가 만든 코드의 세부 내용을 충분히 읽지 않은 채 실행 결과를 중심으로 개발하는 방식입니다.

빠른 시제품에는 유용할 수 있지만 인증, 개인정보, 데이터 삭제, 생산 시스템처럼 위험이 큰 영역에는 사람의 코드 검토와 테스트가 필요합니다. 바이브 코딩은 특정 제품이나 기술명이 아니라 **사람이 결과물을 검토하는 태도**와 관련된 표현입니다.

### Harness: 모델의 작업 환경과 안전장치

Harness(하네스)는 모델에 시스템 프롬프트, 컨텍스트, 도구, 권한, 검증, 로그를 제공하는 실행 체계입니다.

```text
┌────────────── Harness ──────────────┐
│ 규칙 · 자료 · 도구 · 권한 · 검증    │
│                Model               │
└────────────────────────────────────┘
```

같은 모델도 하네스에 어떤 도구와 권한이 연결되어 있는지에 따라 대화만 하거나, 검색하거나, 파일과 업무 시스템을 변경할 수 있습니다.

### Tool과 MCP: 바깥과 연결되는 방법

Tool(도구)은 모델이 호출할 수 있는 기능입니다. 모델이 도구를 직접 실행하지는 않습니다. 모델은 "이 도구를 이런 값으로 불러 달라"고 요청하고 하네스가 권한을 확인한 뒤 실제로 실행합니다. 실행 권한이 모델이 아니라 하네스에 있기 때문에 권한 설계가 안전의 핵심이 됩니다.

MCP(Model Context Protocol)는 AI 애플리케이션이 외부 도구·데이터에 연결하는 방식을 표준화한 개방형 규격입니다. 표준이 없으면 애플리케이션과 시스템의 조합마다 연동을 따로 만들어야 하지만 공통 규격을 두면 한 번 만든 연결을 여러 애플리케이션이 함께 씁니다.

다만 MCP 서버는 사내 시스템으로 들어가는 통로입니다. 출처가 확인된 것만 사용하고 어떤 데이터를 읽어 어디로 보내는지 확인해야 합니다. 도구가 돌려주는 결과 역시 외부 자료이므로 그 안의 문장을 지시로 취급해서는 안 됩니다.

### AI Agent: 목표를 향해 도구를 사용

AI Agent(AI 에이전트)는 목표를 확인하고 다음 행동을 선택하고 도구를 실행한 뒤 결과를 살펴보는 과정을 반복합니다.

단순 챗봇과 에이전트의 중요한 차이는 자연스러운 말투가 아니라 목표를 향해 상태 확인, 행동, 결과 확인을 반복하는지입니다. 도구는 이 반복을 가능하게 하는 대표적인 수단이며 읽기 전용일 수도, 환경을 변경할 수도 있습니다.

### Orchestration: 여러 단계와 역할을 조정

Orchestration(오케스트레이션)은 여러 도구, 모델, 에이전트, 사람의 실행 순서와 조건을 관리합니다.

```text
자료 검색 → 분석 → 정책 검사 → 사람 승인 → 시스템 반영
```

여러 에이전트를 사용한다고 항상 좋은 것은 아닙니다. 하나의 명확한 워크플로로 해결할 수 있다면 단순한 구성이 더 안정적이고 저렴합니다.

LLM의 계획·도구 사용 능력과 하네스의 병렬 실행 기능이 함께 발전하면서 동적 오케스트레이션도 가능해지고 있습니다. 상위 Agent가 요청을 하위 작업으로 나누고 Subagent를 생성해 조사·구현·검토를 맡긴 뒤 결과를 통합하는 구조입니다. Claude Code, Codex, Hermes Agent는 하위 Agent 위임 구성을 제공하며, Pi는 최소 하네스에 필요한 Subagent 확장을 선택해 붙이는 방식을 취합니다.

여기서 “스스로”란 사람이 정한 목표와 권한 안에서 분해 방식을 선택한다는 뜻입니다. 여러 Agent가 같은 파일을 수정하는 충돌, 잘못된 목표의 확산, 비용 증가, 완료 보고의 오판이 생길 수 있으므로 동시 실행 한도, 작업 영역 분리, 실제 결과 검증, 사람 승인이 필요합니다.

안전한 에이전트는 읽기 권한부터 시작하고 중요한 변경 전에 사람의 승인을 받으며, 실행 기록과 중단 조건을 갖추어야 합니다.

## 5. AI Literacy, AI Bias와 AI Slop

### AI Literacy: 책임 있게 판단하는 능력

AI Literacy(AI 리터러시)는 AI의 기본 원리와 한계를 이해하고 적합한 업무에 사용하며, 결과를 검증하고 데이터와 영향을 책임 있게 다루는 능력입니다.

프롬프트를 잘 쓰는 능력만을 뜻하지 않습니다. 다음 질문에 답할 수 있어야 합니다.

- 이 문제에 AI를 사용하는 것이 적절한가요?
- 결과의 사실, 계산, 출처를 확인했나요?
- 개인정보와 사내 기밀을 보호했나요?
- AI가 틀렸을 때 누가 발견하고 책임지나요?

### AI Bias: 데이터부터 사용 과정까지 생기는 치우침

AI Bias(AI 편향)는 결과가 특정 집단이나 상황에 반복적으로 불리하거나 왜곡된 방향으로 나타나는 현상입니다.

편향은 학습 데이터뿐 아니라 데이터 수집, 목표 설정, 평가 기준, 운영 환경, 사용자의 해석에서도 생길 수 있습니다. 예를 들어 한 장비와 한 기간의 데이터만 학습한 이상 탐지 모델은 다른 조건에서 오탐을 늘릴 수 있습니다.

평균 정확도만 보지 말고 집단·장비·기간·상황별 성능을 확인해야 합니다. 민감한 속성 컬럼을 삭제해도 다른 정보가 그 속성을 간접적으로 나타낼 수 있습니다.

### AI Slop: 검증되지 않은 저품질 결과의 과잉 생산

AI Slop(AI 슬롭)은 AI로 빠르게 만들었지만 목적, 맥락, 사실 확인, 편집, 책임이 부족한 저품질 콘텐츠가 대량으로 유통되는 현상을 가리킵니다.

모든 AI 생성물이 슬롭은 아닙니다. 사람이 목적을 정하고 사실을 확인하며 독자에게 맞게 편집한 결과물은 다릅니다.

AI 슬롭은 같은 말을 반복하고 근거 없이 그럴듯하며, 구체적인 업무 조건과 책임자가 빠져 있는 경우가 많습니다. 이런 문서가 지식 저장소에 쌓이면 사람이 확인하는 시간이 늘고 RAG 검색 품질까지 떨어질 수 있습니다.

```text
목적 정의 → 신뢰할 자료 지정 → AI 초안 → 사실 확인 → 편집 → 사람 승인
```

## 6. Jailbreak와 AI 보안

### 비슷해 보이지만 다른 공격

Jailbreak(탈옥)는 모델의 안전 규칙이나 거부 정책을 우회해 제한된 답변을 끌어내는 시도입니다.

Prompt Injection(프롬프트 인젝션)은 AI 애플리케이션이 입력이나 외부 자료 속 지시를 원래 규칙보다 우선하도록 조작하는 공격입니다.

| 유형 | 주요 목표 | 예시 상황 |
|---|---|---|
| 탈옥 | 모델의 안전 정책 우회 | 제한된 내용을 답하도록 유도 |
| 직접 프롬프트 인젝션 | 사용자가 앱의 지시를 변경 | 원래 업무와 다른 행동 요구 |
| 간접 프롬프트 인젝션 | 외부 자료로 AI를 조작 | 문서·메일·웹페이지 속 숨은 지시 |
| 시스템 프롬프트 유출 | 내부 규칙 노출 | 비공개 설정이나 지시 추출 시도 |

### Fable 5 사례

2026년 6월 미국 정부는 Fable 5와 Mythos 5에 대한 외국 국적자의 접근을 제한하는 지시를 내렸습니다. Anthropic은 실시간 국적 확인이 어려워 전체 사용자의 접근을 일시 중단했습니다.

정부 우려의 배경에는 Fable 5의 사이버 안전장치를 우회했다는 보고가 있었습니다. Anthropic은 해당 방법이 좁고 비범용적인 사례이며 다른 공개 모델도 수행할 수 있는 방어적 취약점 분석 수준이었다고 반박했습니다.

이후 Anthropic은 안전 분류기를 보완하고 정부·파트너와 평가 기준을 논의한 뒤 Fable 5를 다시 배포했습니다. 이 사례는 “탈옥이 있었는가”만큼이나 **우회 범위와 실제 피해 가능성을 어떤 기준으로 평가할 것인가**가 중요하다는 점을 보여 줍니다.

### OpenAI 모델과 Hugging Face 보안 사고

2026년 7월 공개된 내용에 따르면, 사이버 능력을 측정하는 OpenAI 내부 평가에서 생산용 안전 분류기를 끄고 거부 수준을 낮춘 모델들이 격리 환경의 취약점을 연결해 인터넷 접근을 얻었습니다. 이어 Hugging Face 인프라에서 평가 답안을 찾으려는 과정에서 실제 시스템을 침해했습니다.

이 사건을 “OpenAI가 Hugging Face를 의도적으로 해킹했다”고 표현하면 조직의 의도와 모델의 행동을 혼동하게 됩니다. 외부 사용자가 안전 규칙을 우회한 전형적인 탈옥 사례도 아닙니다. **강한 도구를 가진 에이전트의 목표 집착, 평가 환경 격리, 권한과 감시의 실패**를 보여 주는 인접 보안 사례입니다.

### 안전한 업무 적용 원칙

- 외부 문서와 메일은 신뢰할 수 없는 입력으로 취급합니다.
- AI가 읽을 수 있는 자료와 실행할 수 있는 도구를 분리합니다.
- 최소 권한과 읽기 전용 접근부터 시작합니다.
- 전송·삭제·설정 변경 전에는 사람의 승인을 받습니다.
- 입력 필터 하나에 의존하지 않고 권한, 격리, 출력 검사, 로그를 겹쳐 둡니다.
- 실제 공격 문구를 일반 문서나 프롬프트 예시로 재배포하지 않습니다.

## 7. AX와 AI Data Center

### AX: 도구가 아니라 업무 방식의 전환

AX(AI Transformation, AI 전환)는 AI 도구를 추가하는 데 그치지 않고 업무 절차, 역할, 데이터, 시스템, 의사결정 방식을 함께 바꾸는 과정입니다.

| 단순 AI 도입 | AX |
|---|---|
| 개인이 문서 초안을 작성 | 조직의 작성·검토 절차를 개선 |
| 챗봇 하나를 배포 | 데이터·권한·업무 시스템을 연결 |
| 사용 횟수를 측정 | 품질·시간·비용·위험 변화를 측정 |

AX에는 해결할 업무 문제, 신뢰할 데이터, 적합한 모델과 시스템, 사람의 역할, 지속적인 평가가 함께 필요합니다. 에이전트는 반복 작업을 수행하고 오케스트레이션은 실행 순서와 승인 지점을 관리할 수 있습니다.

AX의 목적은 사람을 무조건 제외하는 것이 아닙니다. 반복 작업을 줄이고 사람은 예외 판단, 관계 조정, 책임 있는 의사결정에 집중하도록 업무를 다시 설계하는 것입니다.

### AI Data Center: 대규모 AI 연산의 기반

AI Data Center(AI 데이터 센터)는 AI 학습과 추론에 필요한 대규모 병렬 연산을 안정적으로 제공하는 시설입니다.

| 구성 요소 | 역할 |
|---|---|
| GPU·AI 가속기 | 많은 계산을 병렬 처리 |
| 고속 네트워크 | 가속기 사이에서 데이터를 빠르게 교환 |
| 저장장치 | 학습 자료, 모델, 결과를 공급·보관 |
| 전력 설비 | 큰 부하에도 안정적으로 전력 공급 |
| 냉각 설비 | 장비에서 발생한 열 제거 |
| 운영 소프트웨어 | 작업 배치, 장애, 자원 사용 관리 |

GPU 수량만 늘린다고 AI 품질이 좋아지는 것은 아닙니다. 전력망, 냉각, 데이터 품질, 모델 선택, 운영 역량이 함께 필요합니다.

자체 구축, 클라우드, 혼합 방식 중 무엇이 적합한지는 데이터 민감도, 사용량, 지연 시간, 비용, 전문 인력을 기준으로 판단해야 합니다.

## 8. 토큰, 컨텍스트 윈도우와 환각

### Token: 모델이 글을 읽는 조각

Token(토큰)은 모델이 글을 처리할 때 쓰는 단위입니다. 대부분의 서비스가 입력과 출력 토큰의 수로 요금을 계산하고, 답이 길수록 시간도 오래 걸립니다.

같은 뜻의 문장이라도 한국어가 영어보다 토큰을 더 많이 소모하는 경우가 흔합니다. 토크나이저가 영어 자료를 훨씬 많이 학습했기 때문입니다. 사내 문서를 대량으로 처리하는 파이프라인이라면 비용과 한도 계산에 이 차이를 미리 넣어야 합니다.

### Context Window: 한 번에 볼 수 있는 범위

Context Window(컨텍스트 윈도우)는 한 번의 요청에서 모델이 볼 수 있는 토큰의 총량입니다. 시스템 프롬프트, 이전 대화, 첨부 문서, 만들어 낼 답변까지 모두 이 안에 들어갑니다.

한도를 넘기면 오래된 대화를 잘라 내거나 요약해 압축합니다. "아까 말씀드린 조건"을 AI가 못 알아듣는다면 대개 이 때문입니다.

컨텍스트가 크다고 다 넣는 것이 좋지는 않습니다. 관련 없는 자료는 비용과 지연을 늘리고 판단을 흐리며 중요한 지시를 긴 자료 속에 묻히게 합니다. 아주 긴 입력에서는 앞뒤 내용은 잘 참고하면서 가운데 묻힌 내용을 놓치는 경향도 관찰됩니다. 목표는 많이 넣기가 아니라 필요한 것만 정확히 넣기입니다.

### Hallucination: 그럴듯하지만 사실이 아닌 생성

Hallucination(환각)은 모델이 사실이 아닌 내용을 확신 있는 어조로 만들어 내는 현상입니다. LLM은 사실 저장소가 아니라 다음에 올 표현을 고르는 시스템이므로, 모르는 내용을 만나도 빈칸으로 두기보다 형식이 맞는 답을 채웁니다.

사내 규정처럼 학습에 없던 정보, 구체적인 숫자와 날짜, 출처와 문서 번호를 요구할 때 특히 자주 나타납니다. 존재하지 않는 논문이나 URL을 완벽한 형식으로 제시하기도 합니다.

가장 까다로운 유형은 실제 문서를 인용하되 내용을 다르게 요약하는 경우입니다. RAG가 출처를 붙여 주니 안심하기 쉽지만, **출처가 붙어 있다는 사실과 그 출처가 주장을 뒷받침한다는 사실은 다릅니다.** 중요한 내용은 원문을 직접 열어 확인해야 합니다.

### 왜 같은 질문에 다른 답이 나오나요?

모델은 다음 토큰을 확률 분포에서 골라 뽑습니다. 이 방식을 조절하는 값이 Temperature(온도)입니다. 온도가 낮으면 안정적이고 반복적인 답이, 높으면 다양하지만 흔들리는 답이 나옵니다. 분류·추출·규정 안내는 낮게, 아이디어 발산은 높게 두는 것이 일반적입니다.

온도를 가장 낮게 두어도 결과가 완전히 같다고 보장하기는 어렵고 모델 버전이 올라가면 답도 달라집니다. 그래서 **한 번 잘 나온 결과를 검증으로 착각하면 안 됩니다.** 시연에서 성공한 프롬프트가 운영에서 흔들리는 일이 흔합니다.

## 9. 프롬프트, RAG, 파인튜닝 중 무엇을 선택할까

| 방법 | 무엇을 바꾸나요 | 잘 해결하는 문제 | 준비 비용 |
|---|---|---|---|
| 프롬프트 개선 | 요청 문장만 | 목적·형식·제약 전달 | 매우 낮음 |
| Few-shot 예시 | 요청 안의 예시 | 고유 분류 기준, 출력 형식 | 낮음 |
| RAG | 참고 자료 | 사내 지식, 최신 정보, 근거 제시 | 중간 |
| 파인튜닝 | 모델 파라미터 | 고정된 스타일·형식·도메인 표현 | 높음 |

위에서부터 시도하는 것이 효율적입니다. 아래로 갈수록 효과가 큰 것이 아니라 비용과 되돌리기 어려움이 커집니다.

핵심 질문은 **"모델이 몰라서 틀리는가, 알면서 다르게 하는가"**입니다. 모르는 문제라면 RAG나 도구 연결이고, 형식과 기준이 흔들린다면 프롬프트와 예시입니다.

### 파인튜닝에 대한 흔한 오해

사내 문서를 파인튜닝해도 모델이 회사를 정확히 알게 되지는 않습니다. 파인튜닝은 지식을 정확히 주입하는 수단으로는 약해서 문서의 문체와 형식을 흉내 내며 **우리 회사 문서처럼 보이지만 틀린 답**을 내놓기 쉽습니다. 규정이 바뀔 때마다 재학습해야 하고 특정 문서만 삭제하거나 사용자별 권한을 나누기도 어렵습니다.

파인튜닝이 맞는 경우는 지식보다 행동 방식을 고정할 때입니다. 출력 형식이 매우 엄격하거나, 사내 표기 규칙을 일관되게 지켜야 하거나, 프롬프트가 너무 길어져 호출 비용이 부담될 때입니다. LoRA처럼 작은 보조 가중치만 학습하는 경량 방식이 현실적인 출발점입니다.

빠지기 쉬운 항목이 하나 더 있습니다. 학습한 모델을 이후 누가 관리하는가입니다. 담당자가 정해지지 않은 파인튜닝 모델은 몇 달 뒤 아무도 손대지 못하는 자산이 됩니다.

### 잘 되는지 어떻게 확인하나요?

"돌려 보니 괜찮네요"는 근거가 되지 못합니다. Golden Set(골든셋)은 실제 업무에서 뽑은 입력과 사람이 합의한 기대 출력의 모음입니다. 대표 사례와 경계 사례를 합해 30~100건이면 시작할 수 있습니다.

```text
현업 사례 수집 → 기대 출력 합의 → 골든셋 확정
        ↓
프롬프트·RAG·모델 변경 → 재실행하고 점수 비교
```

정확성뿐 아니라 근거 충실성, 검색 품질, 형식 준수, 모르는 것을 모른다고 답하는지, 비용과 지연까지 함께 봅니다. 골든셋의 진짜 가치는 점수 자체가 아니라 **바꾼 것이 이전 것을 망가뜨리지 않았음을 확인**하는 데 있습니다.

정답이 하나로 정해지지 않는 요약이나 설명은 별도의 모델에게 채점을 맡기기도 합니다(LLM-as-a-Judge). 빠르고 저렴하지만 채점 모델에도 편향이 있으며 길고 자신감 있는 답에 후한 경향이 알려져 있습니다. 1차 선별로 쓰고 표본은 사람이 다시 확인하는 구성이 안전합니다.

## 마지막으로 기억하실 원칙

1. 모델의 자연스러운 말과 사실을 구분합니다.
2. AI에 어떤 자료와 도구, 권한이 연결되어 있는지 확인합니다.
3. 중요한 결과에는 출처, 테스트, 사람의 검토를 요구합니다.
4. 한 번 잘 나온 결과를 검증으로 삼지 않고 표본으로 확인합니다.
5. 생성량보다 실제 업무 품질과 책임을 우선합니다.
6. 작은 실험으로 효과와 위험을 측정한 뒤 확장합니다.
