# 04. 바이브 코딩에서 하네스, 에이전트와 오케스트레이션까지

## 이 글에서 답할 질문

- 바이브 코딩은 단순히 AI로 코딩한다는 뜻인가요?
- 모델과 하네스, AI 에이전트는 무엇이 다른가요?
- MCP는 왜 여기저기서 언급되나요?
- 오케스트레이션은 왜 필요한가요?

## 먼저 한 문장으로 정리해 보겠습니다

> 모델이 두뇌라면 하네스는 작업 장비와 안전장치이고, 에이전트는 그 환경에서 목표를 수행하는 작업자이며, 오케스트레이션은 여러 작업의 순서와 협업을 조정하는 역할입니다.

## Vibe Coding: 결과를 보며 감각적으로 만드는 작업 방식

Vibe Coding(바이브 코딩)은 자연어로 원하는 것을 설명하고 AI가 만든 코드를 세부적으로 검토하지 않은 채 실행 결과를 중심으로 개발하는 작업 방식입니다.

빠른 시제품이나 개인 실험에는 유용할 수 있습니다. 그러나 인증, 개인정보, 생산 시스템, 데이터 삭제처럼 실패 비용이 큰 영역에서 코드를 읽고 검증하지 않으면 위험합니다.

바이브 코딩은 다음과 구분해야 합니다.

- 특정 모델이나 제품 이름이 아닙니다.
- 결과가 반드시 나쁘다는 뜻도 아닙니다.
- “AI를 사용한 모든 코딩”을 뜻하지도 않습니다.
- 핵심 기준은 사람이 변경 내용을 얼마나 이해하고 검토했는가입니다.

## Model: 답을 생성하는 두뇌

Model(모델)은 주어진 컨텍스트를 바탕으로 다음 출력을 생성합니다. 모델만으로는 파일을 읽거나 데이터베이스를 조회하거나 실제 프로그램을 실행할 수 없습니다.

## Harness: 모델이 일할 수 있게 둘러싼 실행 체계

Harness(하네스)는 모델을 실제 제품이나 업무에 사용할 수 있도록 감싸는 소프트웨어 체계입니다.

하네스에는 보통 다음 요소가 들어갑니다.

- 역할과 규칙을 알려 주는 System Prompt
- 대화와 자료를 관리하는 Context
- 검색, 파일, API 등을 사용하는 Tools
- 허용 범위를 정하는 Permission과 Sandbox
- 결과를 점검하는 Test, Evaluation, Guardrail
- 작업 기록과 오류를 남기는 Log

```text
┌──────────────────── Harness ────────────────────┐
│ 규칙 · 컨텍스트 · 도구 · 권한 · 검증 · 기록     │
│                                                │
│                    Model                       │
└────────────────────────────────────────────────┘
```

같은 모델을 사용해도 하네스가 다르면 결과와 행동이 달라질 수 있습니다. 한 서비스에서는 대화만 하고 다른 서비스에서는 파일을 수정하는 이유도 하네스에 연결된 도구와 권한이 다르기 때문입니다.

## Tool과 MCP: 모델이 바깥과 연결되는 방법

Tool(도구)은 모델이 호출할 수 있는 기능입니다. 문서 검색, 데이터베이스 조회, 파일 읽기, 메일 발송처럼 모델 혼자서는 할 수 없는 일을 대신합니다. 모델은 도구를 직접 실행하지 않습니다. "이 도구를 이런 값으로 불러 주세요"라고 요청하면 하네스가 실제로 실행하고 결과를 돌려줍니다.

```text
모델: "search_manual 도구를 '진동 알람'으로 호출해 주세요"
                    ↓
하네스가 권한을 확인하고 실제 실행
                    ↓
모델: 돌아온 결과를 읽고 다음 판단
```

이 구조에서 실행 권한은 모델이 아니라 하네스에 있습니다. 권한 설계가 안전의 핵심인 이유입니다.

### MCP: 도구를 붙이는 공통 규격

MCP(Model Context Protocol)는 AI 애플리케이션이 외부 도구와 데이터에 연결하는 방식을 표준화한 개방형 규격입니다.

표준이 없던 시절에는 도구 하나를 붙일 때마다 제품별로 따로 개발해야 했습니다. 사내 시스템 5개를 AI 도구 3개에 연결하려면 15벌의 연동을 만들어야 하는 셈입니다. MCP는 그 사이에 공통 규격을 두어 한 번 만든 연결을 여러 애플리케이션이 함께 쓰도록 합니다.

```text
[표준 없이]                    [MCP로]

앱A ─ 시스템1                  앱A ┐
앱A ─ 시스템2                  앱B ┼─ MCP ─┬─ 시스템1
앱B ─ 시스템1                  앱C ┘       ├─ 시스템2
앱B ─ 시스템2                              └─ 시스템3
... 조합마다 개별 개발
```

주변 기기를 규격이 다른 단자마다 따로 만들지 않고 공통 단자 하나로 연결하는 것과 비슷합니다.

### 보안 관점에서 기억할 점

편리한 만큼 위험도 같이 옮겨 옵니다.

- MCP 서버는 사내 시스템에 접근하는 통로이므로 출처가 확인된 것만 사용해야 합니다.
- 연결한 서버가 어떤 데이터를 읽고 어디로 보내는지 확인해야 합니다.
- 도구가 돌려주는 결과도 외부 자료입니다. 그 안에 담긴 문장을 지시로 취급하면 안 됩니다.
- 도구를 많이 연결할수록 모델이 잘못된 도구를 고를 가능성도 함께 늘어납니다.

## AI Agent: 목표를 향해 반복해서 행동하는 시스템

AI Agent(AI 에이전트)는 목표를 받고 현재 상태를 확인하고 필요한 도구를 선택해 실행한 뒤, 결과를 보고 다음 행동을 이어 가는 시스템입니다.

```text
목표 확인
   ↓
계획 또는 다음 행동 선택
   ↓
도구 실행
   ↓
결과 확인
   ↓
완료 여부 판단 ── 미완료라면 반복
```

예를 들어 “이번 주 고객 문의를 유형별로 정리해 주세요”라는 목표를 받은 에이전트는 승인된 문의 시스템을 조회하고 내용을 분류하고 보고서를 저장할 수 있습니다.

단순 챗봇과 에이전트의 중요한 차이는 말투가 아니라 **목표를 향해 상태를 확인하고 행동하고, 결과를 보고 다음 행동을 선택하는 과정을 반복하는가**에 있습니다. 도구는 이 반복을 가능하게 하는 대표적인 수단입니다. 검색처럼 읽기 전용일 수도 있고 시스템 변경처럼 환경에 영향을 줄 수도 있습니다. 영향력이 커질수록 최소 권한, 승인 절차, 실행 기록이 중요해집니다.

## Orchestration: 여러 작업과 에이전트를 조정하기

Orchestration(오케스트레이션)은 여러 단계, 도구, 모델, 에이전트의 실행 순서와 조건을 조정하는 일입니다.

오케스트라 지휘자가 모든 악기를 직접 연주하지는 않지만 시작 시점과 순서, 균형을 맞추는 것과 비슷합니다.

```text
요청 접수
   ↓
자료 검색 Agent
   ↓
분석 Agent
   ↓
보안·품질 검토
   ↓
사람 승인
   ↓
결과 저장 또는 시스템 반영
```

모든 업무에 여러 에이전트가 필요한 것은 아닙니다. 하나의 명확한 워크플로로 해결할 수 있다면 단순한 구성이 더 안정적이고 저렴합니다.

## Agent가 스스로 오케스트레이션하는 모습

LLM은 긴 작업을 계획하고 도구 결과를 해석하는 능력이 점점 좋아지고 있습니다. 동시에 하네스도 컨텍스트 관리, 장기 작업, 병렬 실행, Agent 간 메시지 전달을 지원하도록 고도화되고 있습니다. 두 변화가 만나면서 사람이 모든 작업 순서를 미리 작성하지 않아도 상위 Agent가 목표를 보고 필요한 하위 작업을 나누는 모습을 볼 수 있습니다.

```text
사용자: "이 프로젝트의 보안 문제를 찾아 수정해 주세요."
                         ↓
                   상위 Agent
       ┌─────────────────┼─────────────────┐
       ↓                 ↓                 ↓
 인증 코드 조사     의존성 위험 조사      테스트 확인
  Subagent A          Subagent B          Subagent C
       └─────────────────┼─────────────────┘
                         ↓
             결과 비교·통합·재검증
                         ↓
                  사용자에게 보고
```

상위 Agent는 보통 다음 과정을 수행합니다.

1. 요청의 범위와 완료 조건을 파악합니다.
2. 직접 처리할 일과 위임할 일을 구분합니다.
3. Subagent(하위 에이전트)에 역할, 자료, 도구, 완료 조건을 전달합니다.
4. 서로 독립적인 작업은 동시에 실행합니다.
5. 돌아온 결과를 비교하고 충돌이나 누락을 확인합니다.
6. 필요한 경우 추가 조사를 지시하고 최종 결과를 통합합니다.

이 방식을 Dynamic Orchestration(동적 오케스트레이션)이라고 볼 수 있습니다. 사람이 고정된 순서도를 모두 작성하는 대신, Agent가 현재 상황에 따라 작업 분해와 위임 방식을 선택하기 때문입니다.

### 현재 하네스에서 볼 수 있는 예

| 하네스 | Subagent와 오케스트레이션의 모습 |
|---|---|
| [Claude Code](https://code.claude.com/docs/en/sub-agents) | 특정 역할·도구·컨텍스트를 가진 Subagent를 정의하고 작업을 위임할 수 있습니다. |
| [Codex](https://learn.chatgpt.com/docs/agent-configuration/subagents) | 상위 Agent가 하위 Agent에 독립 작업을 맡기고 결과를 받아 통합하는 구성을 지원합니다. |
| [Hermes Agent](https://hermes-agent.nousresearch.com/docs/guides/delegation-patterns/) | 격리된 하위 Agent를 만들고 독립적인 조사나 리뷰를 병렬 실행한 뒤 상위 Agent가 결과를 종합할 수 있습니다. |
| [Pi](https://pi.dev/) | 핵심은 최소한의 하네스로 유지하며 Subagent를 기본 내장하지 않습니다. 필요하면 [확장 패키지](https://pi.dev/packages/pi-sub-agent)를 설치하거나 직접 워크플로를 구성할 수 있습니다. |

제품 기능과 기본 설정은 계속 바뀔 수 있습니다. 중요한 공통 원리는 **상위 Agent가 목표를 분해하고 제한된 컨텍스트와 권한을 가진 하위 Agent에 위임하고, 결과를 다시 검증한다**는 것입니다.

### “스스로”의 의미와 한계

여기서 “스스로 오케스트레이션한다”는 말은 Agent가 의식이나 조직의 권한을 얻었다는 뜻이 아닙니다. 사람이 정한 목표, 하네스가 허용한 도구와 권한, 비용·시간·동시 실행 한도 안에서 작업 분해 방식을 선택한다는 뜻입니다.

Subagent를 많이 만들면 다음 위험도 커집니다.

- 같은 파일이나 시스템을 동시에 변경해 충돌할 수 있습니다.
- 잘못 이해한 목표가 여러 Agent에 빠르게 퍼지기 쉽습니다.
- 중간 결과와 출처가 요약 과정에서 빠질 수 있습니다.
- 토큰, GPU, API 호출 비용이 예상보다 커질 수 있습니다.
- 상위 Agent가 하위 Agent의 “완료했다”는 보고를 검증 없이 그대로 믿어 버립니다.

따라서 쓰기 대상 분리, 동시 실행 한도, 최소 권한, 실제 변경 내역 확인, 테스트와 사람의 승인 같은 통제가 필요합니다. 모델이 똑똑해질수록 통제를 없애는 것이 아니라 더 큰 능력을 안전하게 사용할 수 있도록 하네스도 함께 좋아져야 합니다.

## 개인 사용에서 관리 가능한 시스템으로

| 단계 | 중심 질문 | 필요한 통제 |
|---|---|---|
| 대화형 도움 | 좋은 답을 받았나요? | 사실 확인 |
| 바이브 코딩·시제품 | 원하는 결과가 동작하나요? | 변경 내용과 테스트 확인 |
| 하네스 기반 도구 사용 | 무엇을 읽고 실행할 수 있나요? | 권한, 샌드박스, 로그 |
| 에이전트 자동화 | 목표를 잘못 이해하면 어떻게 되나요? | 중단 조건, 승인, 재시도 제한 |
| 오케스트레이션 | 여러 단계의 책임은 누구에게 있나요? | 상태 관리, 단계별 검증, 감사 기록 |

이 표는 반드시 거쳐야 하는 성숙도 순서가 아닙니다. 업무 위험이 낮다면 단순한 대화형 도구가 가장 적합할 수 있습니다.

## 안전한 업무 적용 원칙

1. 읽기 권한부터 시작하고 쓰기·삭제 권한은 나중에 추가합니다.
2. 중요한 변경 전에는 사람의 승인을 받습니다.
3. 에이전트의 설명이 아니라 실제 결과와 변경 내역을 확인합니다.
4. 테스트, 타입 검사, 정책 검사처럼 판정 기준이 분명한 검증을 둡니다.
5. 실패 횟수와 비용, 실행 시간을 제한합니다.
6. 누가 무엇을 요청하고 어떤 도구가 실행되었는지 기록합니다.

## 핵심 요약

- 바이브 코딩은 AI 코드를 검토하는 태도에 달린 작업 방식입니다.
- 하네스는 모델에 컨텍스트, 도구, 권한, 검증을 제공하는 실행 체계입니다.
- 도구를 실제로 실행하는 주체는 모델이 아니라 하네스이며, MCP는 그 연결을 표준화한 규격입니다.
- 에이전트는 목표를 향해 도구 사용과 판단을 반복합니다.
- 오케스트레이션은 여러 단계와 에이전트를 조정합니다.
- 고도화된 Agent는 목표를 나누고 Subagent를 생성해 병렬로 위임한 뒤 결과를 통합할 수 있습니다.
- 자동화 수준이 높아질수록 사람의 승인과 기술적 안전장치가 더 중요합니다.
