# 소형 모델 프롬프팅 플레이북

소형/중형 모델은 "지능으로 때우는" 게 안 된다. 구조가 곧 품질이다.

## 1. 지시는 명확하고, 하나의 목표로

- 대형 모델은 모호한 지시를 보정해 주지만, 소형 모델은 모호함을 그대로 반영한다.
- 한 요청에 하나의 명확한 목표. 여러 작업은 분리해서 호출.
- 출력 형식을 프롬프트에서 명시적으로 강제한다:

  - 수학: "단계별로 추론하고 최종 답을 `\boxed{}` 안에 넣어라." (Qwen 공권)
  - 객관식: `"answer"` 필드에 선택지만, 예: `"answer": "C"` (Qwen 공식)
  - 일반: "JSON으로만 응답하라. 다른 텍스트 금지" + 스키마 예시 제공

## 2. Few-shot은 소형 모델에서 특히 강력

- 2~5개의 입출력 예시가 지시문 수백 토큰보다 효과적인 경우가 많다.
- 예시는 **실제 운영 데이터 분포**에서 뽑는다 (도메인 용어, 형식, 엣지 케이스 포함).
- 예시에 어려운 케이스(빈 입력, 예외 형식)를 하나 섞으면 견고함이 올라간다.

## 3. 시스템 프롬프트 설계

- 역할, 출력 규칙, 금지사항을 앞쪽에 배치 (소형 모델은 초반 컨텍스트에 편중 — position bias).
- 규칙은 불릿 리스트로 짧게. 긴 서술형 지시는 이탈률이 높다.
- 시스템 프롬프트는 고정하고 prefix caching이 작동하게 → 비용 절감.

## 4. 구조화 출력 (JSON 모드)

- vLLM/SGLang의 guided decoding(structured outputs)을 쓰면 JSON 스키마 준수를 디코딩 레벨에서 강제할 수 있다 — 프롬프트로 설득하는 것보다 훨씬 신뢰도 높음.
- OpenAI strict-schema 스타일로 스키마 작성: `additionalProperties: false`, 모든 필드 required, 선택 필드는 `{"type": ["string", "null"]}`.

## 5. 복잡한 과제는 분해 (체인/파이프라인)

- 소형 모델에게 "A 분석해서 B 계획 세우고 C 코드 작성해"를 한 번에 주면 중간 단계가 무너진다.
- 호출을 나누고, 각 단계의 출력을 다음 단계의 입력으로 명시적으로 전달.
- 장기 에이전트 과제는 모델이 중간에 방향을 잃는다 → 계획→실행→검증의 명시적 사이클로 운영.

## 6. 언어 일관성

- 한국어 운영이라면 시스템 프롬프트에 "항상 한국어로 답변"을 명시. 다국어 모델 특성상 thinking이 영어로 새어 나오거나 언어가 혼용될 수 있고, presence_penalty를 높게 주면 혼용이 심해진다.

## 7. 검증 프롬프트 (self-verification)

- 답 생성 후 "아래 답이 조건을 만족하는지 검토하고 문제가 있으면 고쳐라"를 별도 호출로 수행. 소형 모델은 한 번의 생성에서 자기검증이 잘 안 되지만, 별도 턴으로 주면 잡아내는 비율이 올라간다.

## 8. 벤치마크/평가 시 표준화

- 평가 프롬프트는 형식을 표준화해야 비교 가능. Qwen 공식 권장 형식(위 1번)을 그대로 쓸 것.
