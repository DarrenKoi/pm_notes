# 사내 AI Agent·Skill 플랫폼 운영·거버넌스

> 사업부별 독립 1차 플랫폼과 별도 2차 전사 플랫폼을 실제로 운영할 때 누가 무엇을 언제 판단하고 실행하는지 정의한다.

## 문서 범위

이 문서는 게시 심사, 등급, 승격, 타 사업부 접근, 폐기, 인시던트, 조직 개편과 정기 운영 등 **사람과 프로세스**만 다룬다. 시스템 구조, 기술 스택, API와 데이터 모델은 다루지 않는다.

운영 절차는 다음 전제를 따른다.

- 1차 플랫폼은 사업부(Biz)마다 별도 인스턴스로 운영하며 멀티테넌시(Multi-tenancy)를 사용하지 않는다.
- 2차 전사 플랫폼은 별도로 존재하고, 1차에서 검증된 Agent를 심사 후 승격한다.
- Agent는 Skill, 로컬·원격 MCP server, 팀 서버가 운영하는 hosted agent를 포괄하며 여러 오픈소스 런타임이 공존한다.
- Skill과 MCP server는 실행 가능한 코드와 프롬프트를 포함할 수 있으므로 게시를 사내 실행물 배포로 취급한다. Hosted agent는 설치물이 아니라 서비스 접근 권한을 배포하는 것으로 취급한다.
- 사원 ID·이름·현재 소속은 public `sub`를 사용하는 전사 사원 마스터를 단일 진실 원천(SSOT)으로 삼는다.
- 작성자는 자신의 게시물을 심사할 수 없다. 리뷰어 독립성(Separation of duties)을 모든 사람 심사에 적용한다.
- 기본 제공 사용량 분석에 의존하지 않는다. 직접 계측한 구간만 실측치로 인정하고 누락 구간을 함께 표시한다.
- 발행된 버전의 내용은 바꾸지 않는다. 폐기는 삭제가 아니라 상태 전이(Status transition)로 처리한다.
- 사업부 간 신뢰는 명시적이고 비전이(Non-transitive)다. A가 B를 신뢰하고 B가 C를 신뢰해도 A가 C를 신뢰한 것으로 보지 않는다.

관련 기준은 [요구사항 정의서](./01-requirements.md)와 [Agent·Skill 레지스트리 조사](./research/agent-skill-registry-research.md)를 따른다.

## 운영 조직(RACI)

RACI는 실행 책임(Responsible), 최종 책임(Accountable), 협의(Consulted), 통보(Informed)를 뜻한다. 한 활동의 최종 책임자는 한 역할만 둔다.

### 역할과 예상 투입

| 역할 | 핵심 책임 | 예상 투입 |
|---|---|---|
| 플랫폼 운영자 | 인스턴스 상태, 게시 흐름, 권한 만료, 업그레이드, 장애 격리와 운영 기록 관리 | 초기 구축·안정화는 전담, 안정화 후 인스턴스 규모와 업무량에 따라 전담 또는 겸직 |
| 보안·거버넌스 담당 | 보안 정책, 고위험 게시물, 타 사업부 실행 권한, 긴급 회수와 중대 인시던트 최종 판단 | 겸직 가능하나 P0/P1 대응 당번과 대체 담당자 지정 필수 |
| 리뷰어 풀 | 제작자와 독립된 기능·안전성·문서 심사, 이해충돌 신고 | 각 사업부 3명 이상을 권장하며 겸직 가능. 본인·직속 제작 건 심사 금지 |
| 사업부 관리자 | 사업부 자산, 공개 범위, 신뢰 관계, 소유권 승계와 운영 예외 승인 | 사업부별 주·대체 관리자 각 1명 이상, 겸직 |
| Agent 제작자·제공 팀 | 제출 자료, 평가 증적, 런타임 호환성, 유지보수와 사용자 통보를 책임진다. Hosted agent 제공 팀은 엔드포인트 가용성·응답시간·장애 대응과 종료 시점까지의 서비스를 책임진다. | 자산별 주·대체 책임자 지정. Hosted agent는 운영 당번이 있는 팀 책임으로 배정 |

## 게시(Publish) 심사 프로세스

### 표준 경로

모든 기간은 영업일 기준 제안값이며, 세부 값은 [제안 운영 수치](#제안-운영-수치)에서 조정한다.

| 단계 | 담당 | 수행 내용 | 판정 기준 | SLA |
|---|---|---|---|---|
| 1. 제출 | Agent 제작자·제공 팀 | 자산 유형, 소유자·대체 소유자, 목적, 버전, 호환 런타임, 변경 내용, 권한, 의존성, 평가 결과와 공개 희망 등급을 제출한다. Hosted agent는 서비스 SLO와 장애·종료 계획을 추가한다. | 필수 자료 완비, 제출자에게 해당 자산 제출 권한 존재 | 제출 즉시 접수, P-01 |
| 2. 자동 검사 | 플랫폼 운영자(A), 자동 검사(R) | 설치형 자산은 비밀정보, 외부 호출, 실행 파일, 광범위 권한과 취약 패턴을 검사한다. Hosted agent는 필수 서비스·보안 증적의 누락을 검사하며 코드 스캔을 통과한 것으로 간주하지 않는다. | 유형별 차단 항목 0건, 경고 항목은 사유와 완화책 기재 | P-02: 1영업일 이내 |
| 3. 사람 심사 | 독립 리뷰어 | 실제 동작과 선언된 목적의 일치, 권한 최소화, 프롬프트 안전성, 평가 결과와 문서를 확인한다. | 체크리스트 통과, 이해충돌 없음, 보완 항목 해소 | P-03: 3영업일 이내 |
| 4. 보안 심사 | 보안·거버넌스 | 외부 통신, 셸 실행, 민감정보 접근 등 고위험 항목이 있는 제출만 추가 심사한다. | 정책 위반 0건 또는 승인된 예외 존재 | P-04: 3영업일 이내 |
| 5. 결정 | 지정 리뷰어 | 승인, 보완 요청 또는 반려를 사유와 함께 기록한다. 운영자는 승인된 등급과 공개 범위만 적용한다. | 작성자와 결정자가 다름, 모든 필수 판정 기록 완료 | P-05: 심사 완료 후 1영업일 이내 |

보완 요청은 항목별 완료 조건을 적는다. 제작자가 P-06 안에 보완하지 않으면 신청을 종료하고 같은 버전을 다시 제출할 때 새 심사 건으로 처리한다.

### 작성자와 심사자 분리 강제

1. 제출자는 자신을 리뷰어 또는 최종 결정자로 지정할 수 없다.
2. 리뷰어는 배정 수락 전에 공동 작성, 직속 보고 관계, 이해관계를 신고한다.
3. 이해충돌이 있으면 플랫폼 운영자가 리뷰어 풀에서 다시 배정한다.
4. 리뷰어가 제출물에 수정자로 참여하면 다른 리뷰어가 처음부터 재심사한다.
5. 게시 기록에는 제출자, 리뷰어, 최종 결정자를 남기고 월 1회 동일인 여부를 감사한다.

### 리뷰어 부족 시 대체 경로

리뷰어 부족은 독립 심사를 생략하는 일반 예외가 아니다. 다음 조건을 모두 만족하는 경우에만 **실험(Experimental)** 등급으로 임시 게시할 수 있다.

- 자동 검사에서 차단 항목이 없고 제작자가 위험과 동작 범위를 서면 확인한다.
- 노출 범위는 제작 팀 내부로 제한하고, 타 사업부 접근·2차 승격·공식 업무 사용을 금지한다.
- 외부 네트워크 호출, 민감정보 접근, 광범위 파일시스템 쓰기 또는 셸 실행이 있으면 대체 경로를 사용할 수 없다.
- 코드 대신 서비스 통제를 심사해야 하는 hosted agent와 원격 MCP server에는 대체 경로를 적용하지 않는다.
- 모든 화면과 설치 안내에 "독립 심사 전" 경고를 표시한다.
- P-07 안에 사후 감사를 완료한다. 기한 내 완료하지 못하면 신규 설치를 중단하고 폐기 예정으로 전환한다.

## 심사 체크리스트

### 모든 자산 공통

| 항목 | 검사 방식 | 리뷰어 확인 내용 | 반려 기준 |
|---|---|---|---|
| 사내 기밀·개인정보 | 자동 + 수동 | 번들·프롬프트·입출력·로그에 민감정보가 없는지와 처리 목적·범위가 승인됐는지 확인 | 실제 비밀정보 포함, 승인 없는 민감정보 처리, 마스킹 불가 |
| 자격증명 | 자동 + 수동 | 키·토큰·비밀번호가 코드·문서·예제·응답에 포함되지 않고 사용 권한이 최소화됐는지 확인 | 실제 자격증명 포함, 평문 저장·공유 요구, 과도한 권한 |
| 프롬프트 인젝션(Prompt injection) | 수동 | 외부 입력과 도구 결과를 지시로 오인하지 않는지, 권한 상승·안전 규칙 무시를 유도할 수 있는지 시험 | 사용자 승인 없이 고위험 도구 실행, 안전 규칙 우회, 행동 은폐 지시 |
| 목적과 실제 동작 일치 | 수동 | 설명한 기능, 입력·출력, 부작용과 실제 실행 범위를 비교 | 숨겨진 동작, 선언하지 않은 데이터 수집·전송·파일 변경 |
| 의존성·출처 | 자동 + 수동 | 모든 의존성과 출처, 버전, 라이선스·사용 조건, 유지 주체를 확인 | 출처 불명, 허용되지 않은 의존성, 검증 불가능한 버전 |
| 자산 유형·사용 방식 | 수동 | Skill, 로컬·원격 MCP server, hosted agent 구분과 설치·호출 방식이 실제와 일치하는지 확인 | 유형 오표기, 설치물 또는 원격 호출 은폐 |
| 평가(Evaluation) | 자동 + 수동 | 대표 업무 시나리오, 실패 사례, 기대 결과와 재현 가능성을 확인 | 핵심 시나리오 실패, 결과 조작, 평가 증적 부재 |
| 문서화 수준 | 자동 + 수동 | 목적, 대상 사용자, 설치 또는 호출 방법, 입력·출력, 권한, 제한, 오류 대응, 소유자와 지원 기간 확인 | 필수 항목 누락으로 사용자가 위험 또는 한계를 판단할 수 없음 |
| 유지보수 책임 | 수동 | 주·대체 책임자와 문의·장애 대응 경로가 유효한지 확인 | 책임자 부재, 지원 종료 계획 없음, 연락 불가 |

### Skill

| 항목 | 검사 방식 | 리뷰어 확인 내용 | 반려 기준 |
|---|---|---|---|
| 파일 내용·무결성 | 자동 + 수동 | 제출 파일 전체, 스크립트, 심사 대상과 게시 대상의 동일성을 확인 | 숨겨진 실행물, 심사 후 변경, 버전 재사용, 무결성 불일치 |
| 외부 네트워크 호출 | 자동 + 수동 | URL, 통신 명령, 라이브러리 사용과 호출 대상을 선언 내용과 대조 | 외부 인터넷·외부 LLM API 호출, 미신고 목적지, 우회 통신 |
| 파일시스템 접근 | 자동 + 수동 | 읽기·쓰기 경로가 업무 목적에 필요한 최소 범위인지 확인 | 상위 경로 탐색, 무제한 재귀 접근, 불필요한 사용자·공유 경로 변경 |
| 셸(Shell) 실행 | 자동 + 수동 | 실행 명령, 인자, 입력값 검증, 권한과 실패 시 영향을 확인 | 임의 명령 삽입 가능, 관리자 권한 요구, 파괴적 명령의 안전장치 부재 |
| 런타임 호환성 | 자동 + 수동 | 지원 런타임·버전별 설치와 대표 평가 결과를 확인 | 지원한다고 표시한 런타임에서 설치·핵심 시나리오 실패 |

### MCP server

| 항목 | 검사 방식 | 리뷰어 확인 내용 | 반려 기준 |
|---|---|---|---|
| 설치·접근 형태 | 자동 + 수동 | 로컬 설치형과 원격형을 구분하고 실제 실행·접근 경로를 확인 | 형태 오표기, 미신고 실행 파일 또는 엔드포인트 |

| 로컬 실행 범위 | 자동 + 수동 | 로컬 설치형의 파일시스템, 셸, 네트워크 접근과 무결성을 Skill 기준으로 확인 | Skill 차단 기준과 동일 |
| 원격 엔드포인트 보안 | 수동 | 원격형의 인증, 사용자별 인가, 접근 회수, 데이터 흐름과 장애 연락 경로를 확인 | 미인증 접근, 사용자 간 권한 혼동, 회수 불가, 미승인 데이터 전송 |
| 호환성 | 자동 + 수동 | 지원 클라이언트·런타임·버전과 대표 도구 호출 결과를 확인 | 지원 표시 조합에서 연결·핵심 호출 실패 |

### Hosted agent

Hosted agent는 코드 스캔 결과만으로 승인하지 않는다. 제공 팀이 운영하는 서비스 통제와 실제 호출 증적을 중심으로 심사하며, 소스 또는 배포 아티팩트가 제공되면 코드 검사는 보조 증적으로 사용한다.

| 항목 | 검사 방식 | 리뷰어 확인 내용 | 반려 기준 |
|---|---|---|---|
| 엔드포인트 보안 | 수동 | 인증, 사용자·조직별 인가, 세션 격리, 접근 만료·회수와 비정상 호출 대응을 확인 | 미인증 접근, 권한 혼동, 접근 회수 불가 |
| 데이터 취급 | 수동 | 입력·출력·로그의 데이터 등급, 보관, 마스킹, 삭제, 하위 서비스 전달 범위를 확인 | 미승인 보관·전달, 보존 기간 부재, 기밀 노출 가능성 |
| 외부 통신 | 수동 | 호출 대상과 하위 의존 서비스가 사내 정책 범위인지 확인 | 외부 인터넷·외부 LLM API 또는 미신고 목적지 사용 |
| 가용성·응답시간 | 수동 | 월 가용성, p95 응답시간, 측정 기간, 계획 점검과 최근 장애 실적을 선언 SLO와 대조 | SLO 미정의, 측정 불가, 반복 미달에 대한 개선 계획 부재 |
| 운영·인시던트 책임 | 수동 | 제공 팀의 주·대체 책임자, 운영 당번, 장애 통보·복구·긴급 중단 절차를 확인 | 상시 연락 경로 부재, 격리·사용자 통보 불가 |
| 변경·종료 관리 | 수동 | 호환성을 깨는 변경의 재심사, 종료 유예, 대체재와 사용자 이전 계획을 확인 | 무통보 변경·종료 가능, 대체 또는 이전 안내 계획 부재 |

## 등급(Tier) 정의

| 등급 | 진입 심사 | 노출·사용 범위 | 표시와 제한 |
|---|---|---|---|
| 실험(Experimental) | 자동 검사 통과. 독립 리뷰 완료 전에도 제한적으로 가능 | 기본은 제작 팀 내부. 사업부 관리자의 별도 승인 없이 사업부 전체·타 사업부 노출 금지 | "검증 전" 경고 상시 표시, 공식 업무 의존 금지, 승격 신청 불가 |
| 검증(Verified) | 자동 검사 + 독립 리뷰어 1명. 고위험이면 보안 심사 추가 | 해당 1차 인스턴스의 승인된 사업부 사용자. 타 사업부는 별도 접근 승인 필요 | 심사일·검증 버전 표시, 변경 버전은 재심사 |
| 공식(Official) | Verified 충족 + 2차 승격 심사와 보안·거버넌스 승인 | 2차 전사 플랫폼의 승인된 사용자 범위 | 전사 유지보수 기준과 지원 책임 표시, 후속 버전 자동 승격 금지 |

낮은 등급도 조건부 게시할 수 있지만 사용자는 설치 전에 등급, 마지막 심사일, 알려진 제한과 지원 수준을 확인해야 한다. 등급은 인기나 사용량만으로 자동 상승하지 않는다.

### Hosted agent 헬스체크와 `degraded`

헬스체크 실패는 등급을 자동으로 바꾸지 않는다. 플랫폼은 H-01 간격으로 확인해 H-02만큼 연속 실패하면 되돌릴 수 있는 조치만 자동 수행한다.

1. 상태를 `degraded`로 전환하고 신규 접근 권한 부여와 신규 연결을 차단한다.
2. 소유 팀과 플랫폼 운영자에게 통보하고 카탈로그 검색 순위를 낮추며 경고 배지를 표시한다.
3. 헬스체크가 회복되면 `degraded`를 자동 해제하고 신규 접근·연결을 복구한다.
4. 등급 강등, Deprecated 전환 또는 Recalled 전환은 장애 영향과 반복성을 검토한 사람이 결정한다. 보안 위험이나 광범위 오작동은 [긴급 회수](#긴급-회수kill-switch) 절차를 우선 적용한다.

### 단계와 심사 주체

| 단계 | 주체 | 내용 | SLA |

| 2. 1차 확인 | 1차 플랫폼 운영자 | 자격, 증적 기간, 원본 버전, 소유권과 미해결 이슈를 확인한다. | PR-07: 2영업일 이내 |

| 5. 결정·이관 준비 | 2차 플랫폼 운영자(A), 관련 담당자(R) | 승인·조건부 승인·보완·반려를 기록한다. 설치형은 메타데이터와 집계 사용 증적을 등록하고 승인된 아티팩트의 복사 권한·원본 경로를 준비한다. 실제 바이트는 2차 플랫폼의 최초 설치 요청 때 복사한다. hosted agent·원격 MCP server는 승인된 접근 정보와 서비스 SLO를 등록한다. | PR-10: 결정 후 3영업일 이내 준비 완료 |

1차 게시 심사와 달리 승격 심사는 **전사 범위의 재사용성, 중복, 사업부 경계 데이터 처리, 전사 장애 영향, 장기 지원 역량**을 추가로 본다.

승격 후에도 원본 사업부는 출처와 기능 유지보수 책임을 진다. Hosted agent 제공 팀은 전사 승격 후에도 엔드포인트 가용성·응답시간, 계획 점검, 장애 대응과 서비스 종료일까지의 사용자 보호를 책임진다. 2차 플랫폼 운영자는 전사 게시·배포 상태와 사용자 공지를 책임진다. 책임을 전사 조직으로 이전하려면 인수자, 범위, 효력일과 미해결 이슈를 양측이 승인해야 하며, 인수 완료 전에는 원본 사업부 책임이 유지된다.

반려된 신청은 반려 사유를 해소하고 새 버전 또는 변경 증적을 제출하면 재신청할 수 있다. 같은 증적을 그대로 재제출할 수 없으며 PR-12 이내 재신청은 이전 심사 기록을 연결해 변경 항목만 우선 확인한다. 그 이후에는 전체 심사를 다시 수행한다.

## 타 사업부 접근 승인 프로세스

타 사업부 접근은 기본 차단한다. 읽기 전용 게스트 열람도 인스턴스 경계를 넘는 접근이며, 내려받기·설치·실행 권한을 자동으로 포함하지 않는다.

| 단계 | 담당 | 처리 내용 | 완료 조건 |
|---|---|---|---|
| 1. 요청 | 요청 사업부 관리자 | 대상 사업부·인스턴스, 자산, 사용자 범위, 행위, 업무 목적과 기간을 제출한다. | 최소 권한과 종료일 명시 |
| 2. 소유 측 검토 | 자산 소유 사업부 관리자 | 건별 승인 또는 사업부 관계별 승인 중 범위를 정하고 소유자 의견을 확인한다. | 대상 자산과 허용 행위 명시 |
| 3. 위험 검토 | 보안·거버넌스 | 내려받기·설치·실행, 민감정보 또는 광범위 권한이 포함된 요청을 심사한다. | 정책 위반 없음 또는 승인된 예외 |
| 4. 승인·등록 | 자산 소유 사업부 관리자(A), 플랫폼 운영자(R) | 승인 범위를 `(resource, relation, subject, expiresAt)` 관계 튜플로 등록하고 양측 책임자와 회수 조건을 기록한다. `subject`에는 불변 사원 ID 또는 `team:<team_id>#member` 같은 레지스트리 발급 ID 집합만 사용하며 표시명·이메일을 넣지 않는다. | X-01 이내 결정, 최대 X-02 기간 |
| 5. 재승인·종료 | 양측 사업부 관리자 | X-03 전에 필요성과 사용자를 재검토한다. 미승인 또는 만료 시 접근을 종료한다. | 연장 근거 또는 종료 기록 |

관계별 승인은 승인서에 적힌 자산 범위와 행위에만 적용한다. A→B 승인은 B→A를 허용하지 않으며 A→B와 B→C가 있어도 A→C를 허용하지 않는다. 새로운 방향·사업부·인스턴스·자산 범위마다 별도 승인이 필요하다.

## 폐기(Deprecate)·회수 프로세스

### 폐기 사유와 처리

| 사유 | 예시 | 기본 처리 |
|---|---|---|
| 유지보수 중단 | 책임자 퇴직, 지원 종료 | 대체 책임자 지정 시도 후 폐기 예정 전환 |
| 보안 결함 | 자격증명 노출, 권한 상승, 악성 동작 가능 | 위험에 따라 즉시 회수 또는 유예 없는 설치·실행 중단 |
| 정책 위반 | 외부 API 호출, 미승인 데이터 처리 | 접근 중단 후 조사, 재승인 전 복구 금지 |
| 대체됨 | 후속 Agent·Skill 또는 통합 자산 제공 | 대체 자산과 이전 방법을 안내하고 유예 후 종료 |

### 상태 전이

```text
Draft → In Review → Active(tier: Experimental | Verified | Official)
                         ⇄ Degraded(tier 유지)
                         ├─→ Deprecated → Withdrawn
                         └─→ Recalled ──→ Withdrawn

Deprecated → Active  : 폐기 사유 해소 + 독립 재심사 승인 시에만 가능
Recalled   → Active  : 사고 원인 제거 + 보안·거버넌스 재승인 시에만 가능
```

Active와 Degraded 사이의 전이는 헬스체크 결과에 따라 자동 처리한다. Degraded에서는 신규 접근 권한 부여와 신규 연결만 차단하며 등급은 유지한다. Deprecated·Recalled 전환은 자동화하지 않는다.

발행된 버전의 아티팩트와 메타데이터는 수정·삭제하지 않고 상태와 상태 변경 사유만 갱신한다. Withdrawn 이후에도 감사와 영향 분석에 필요한 기록은 보존한다.

### 일반 폐기

1. 제작자가 사유, 대체 자산, 신규 설치 또는 접근 승인 종료일과 지원 종료일을 제출한다.
2. 사업부 관리자가 영향 사용자와 유예기간 D-01을 승인한다.
3. 플랫폼 운영자가 기존 사용자에게 D-02 일정으로 반복 통보한다.
4. 신규 설치·접근 승인 종료일에 해당 행위를 차단하고, 지원 종료일에 Withdrawn으로 전환한다.
5. 잔여 사용자가 있으면 사업부 관리자가 예외 종료일과 책임자를 승인한다.

### Hosted agent 전용 폐기

1. 제공 팀은 서비스 종료일, 영향받는 호출 사용자, 종료 사유, 대체 Agent 또는 업무 우회책과 이전 방법을 제출한다.
2. 사업부 관리자는 일반 폐기 유예기간 D-01 이상을 확보하고, 플랫폼 운영자는 신규 접근 승인을 먼저 중단한다.
3. 제공 팀과 플랫폼 운영자는 기존 호출 사용자에게 D-02 일정으로 종료일·영향·대체재·이전 검증 방법을 통보한다.
4. 제공 팀은 보안 긴급 회수가 아닌 한 종료일까지 선언한 가용성·응답시간 SLO와 장애 대응을 유지한다.
5. 플랫폼 운영자는 기존 사용자의 이전 또는 예외 승인 상태를 확인하고, 사업부 관리자가 종료를 승인한 뒤 접근 권한을 회수한다.
6. 제공 팀은 최종 호출 종료 후 서비스를 내리고, 플랫폼 운영자는 상태를 Withdrawn으로 전환한다. 카탈로그 기록과 감사 이력은 삭제하지 않는다.

### 긴급 회수(Kill switch)

기밀 유출, 악성 코드, 정책 위반 또는 광범위 오작동의 즉각적 위험이 있으면 보안·거버넌스 담당자가 긴급 회수를 승인하고 플랫폼 운영자가 I-01 안에 신규 설치·실행·다운로드와 타 사업부 접근을 차단한다. Hosted agent는 제공 팀이 동시에 호출 접수를 중단하고 진행 중 요청의 안전한 종료 여부를 보고한다. P0에서 승인 대기 자체가 피해를 키우면 당번 운영자가 먼저 격리하고 I-02 안에 보안·거버넌스의 사후 승인을 받는다. 제작자·제공 팀은 사용자에게 우회책을 제공하되 재공개 전 독립 재심사를 받아야 한다.

### 대응 흐름

1. **탐지:** 신고 또는 모니터링을 접수하고 인시던트 지휘자, 심각도, 영향 자산·버전·인스턴스를 지정한다.
2. **격리:** 다운로드·설치·실행·타 사업부 접근을 필요한 최소 범위에서 중단하고 증적을 보존한다. 불확실하면 더 높은 심각도로 시작한다.
3. **통보:** 보안·거버넌스, 사업부 관리자, 제작자와 영향 사용자에게 확인된 사실, 현재 영향, 임시 조치와 다음 갱신 시각을 알린다.
4. **복구:** 수정 버전은 새 게시물로 제출하고 자동 검사와 독립 심사를 다시 거친다. 기존 버전을 덮어쓰지 않는다.
5. **사후분석(Post-incident review):** I-11 안에 원인, 탐지·대응 타임라인, 영향, 재발 방지 조치, 책임자와 기한을 기록한다. P0/P1 조치는 월간 거버넌스 회의에서 완료까지 추적한다.

## 조직 개편 대응 운영 절차

팀 표시명 변경은 자산 재게시 사유가 아니다. 레지스트리는 사원 마스터 조회 API가 제공하고 Redis에 저장하는 `empno`별 이름·현재 소속팀명·팀 코드명을 하루 1회 야간 배치로 동기화하고 마지막 성공 스냅샷을 유지한다. 팀 멤버십은 자동 동기화하며 수동 멤버십 관리 UI는 운영하지 않는다. 발행·승격 직전에는 마스터를 실시간 조회해 현재 소속과 쓰기 권한을 다시 확인한다.

rename과 팀 코드 변경은 정보 손실이 없는 관측값 갱신이므로 자동 처리한다. 분할·병합·해체는 소유권과 권한의 귀속을 바꾸므로 아래 승인 절차를 적용한다. 자산과 조직의 불변 ID, 과거 표시명, 당시 소속과 감사 이력은 두 경로 모두 유지한다.

| 시점 | 담당 | 수행 내용 |
|---|---|---|
| 개편 D-30 | 사업부 관리자 | 분할·병합·해체 대상 팀, 후속 조직, 자산·권한·신뢰 관계와 주·대체 책임자 목록을 작성한다. |
| 개편 D-20 | Agent 제작자·사업부 관리자 | 소유 자산, 지원 상태와 미해결 이슈를 확인한다. 사원 마스터의 불변 사원 ID로 원작성자와 현재 소속 팀을 찾아 승계 후보로 기록하고, 응답이 없으면 orphan 후보로 표시한다. |
| 개편 D-10 | 사업부 관리자, 보안·거버넌스 | 분할·병합·해체의 소유권 승계, 권한 축소·종료, 타 사업부 신뢰 관계 재승인 대상을 결정한다. |
| 개편 D-day | 플랫폼 운영자 | 승인된 분할·병합·해체 결정을 반영한다. rename·팀 코드 변경은 동기화 결과로 자동 반영됐는지 확인하고 이전·현재 관측값, 원작성자 사원 ID와 승인 기록을 보존한다. |
| 개편 D+5 | 사업부 관리자 | 자산 소유권, 접근 권한, 알림 대상과 통계 연속성을 표본 검증한다. |
| 개편 D+30 | 플랫폼 운영자 | 미완료 승계, orphan 자산, 만료되지 않은 구 조직 권한을 감사하고 종료 보고한다. |

팀이 해체되면 사업부 관리자가 후속 조직과 새 주·대체 책임자를 지정하고 양측 확인을 받아 승계한다. 병합 시에도 원조직별 이력을 유지하며 새 조직의 권한은 자동 확장하지 않고 재승인한다. 원작성자의 사원 ID는 소유권 변경과 무관하게 제작 이력에 계속 남긴다.

야간 동기화가 실패하면 마지막 성공 스냅샷으로 읽기와 기존 권한 판정을 계속하고 실패를 운영 기록에 남긴다. 연속 3일 실패하면 플랫폼 운영자와 사원 마스터 운영자에게 경보하며 발행·승격은 직전 실시간 조회가 성공할 때까지 허용하지 않는다.

**Orphan 자산 규칙:** 팀 소유권이나 주·대체 책임자가 끊기면 신규 게시와 승격을 즉시 중단한다. 사업부 관리자는 먼저 자산에 기록된 불변 사원 ID로 원작성자를 사원 마스터에서 찾고 재직 중이면 원작성자와 그 사원의 현재 소속 팀에 승계 의사를 요청한다. 원작성자가 퇴직했거나 현재 팀이 인수를 거부하면 사업부 관리자가 다른 책임 조직을 지정한다. O-01 안에 책임 조직과 주·대체 책임자가 모두 확정되지 않으면 Deprecated로 전환하고 기존 사용자에게 알린다. Hosted agent는 운영 책임팀이 없는 즉시 신규 호출을 차단하며 보안 위험이 있거나 서비스를 안전하게 유지할 조직이 없으면 유예 없이 Recalled로 전환한다.
