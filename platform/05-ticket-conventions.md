# 코딩 에이전트용 티켓 규약

> 티켓 하나만 받은 구현 에이전트가 범위를 넘지 않고 한 세션 안에 구현·검증·보고까지 끝내기 위한 작성 규칙이다.

이 문서는 실제 티켓 목록이 아니라 **양식과 규율**만 정의한다. 계층과 설계 결정의 단일 출처는 [아키텍처 설계서](./02-architecture.md)다. 티켓은 그 문서의 L1~L10 및 L6b와 **결정 요약의 D#**를 복사하지 않고 ID와 절 번호로 참조한다.

## 1. 티켓 크기 기준

티켓은 아래 조건을 **모두** 만족할 때 한 세션 크기로 본다. 숫자는 기본 상한이며, 더 작은 변경으로 목적을 달성할 수 있으면 작게 쓴다.

| 판정 축 | 기본 상한 | 통과 조건 |
|---|---:|---|
| 제품 코드 변경 | 3개 파일 | 한 계층(L#) 안에서 하나의 동작만 바꾼다. 테스트·문서 파일은 별도 계산한다. |
| 공개 인터페이스 | 신규 또는 변경 1개 | 스키마, API, 이벤트, 어댑터 계약 중 하나만 다룬다. 계약과 구현을 동시에 처음 정의하지 않는다. |
| 테스트 변경 | 1~3개 파일 | 각 수용 기준을 실행 가능한 검사에 대응시키며 중복 테스트를 만들지 않는다. |
| 수용 기준 | 3~7개 | 각 항목이 명령의 성공 또는 구체적 출력으로 판정된다. |
| 의존 계층 | 주 계층 1개 | 다른 계층 변경이 필요하면 계약 티켓과 소비자 티켓으로 나눈다. |
| 실행 시간 | 한 작업 세션 | 필요한 문맥 읽기부터 red→green, 관련 회귀 검사, 완료 보고까지 이어서 끝낼 수 있다. |

상한 안이어도 서로 독립적인 두 동작을 묶으면 큰 티켓이다. 상한을 넘더라도 동일 파일의 기계적 변경처럼 분리 비용이 더 큰 경우에는 이유와 예상 범위를 티켓에 적고 사람이 승인해야 `ready`가 된다.

### 너무 큰 티켓의 냄새(Smell)

- 제목에 서로 독립적인 동사가 둘 이상 있다: "스키마 추가 및 API 구현 및 UI 연결".
- L2 Catalog와 L4 API처럼 둘 이상의 계층을 동시에 완성하려 한다.
- 아키텍처 결정 요약의 D# 중 둘 이상을 새로 해석하거나 변경해야 한다.
- 수용 기준 일부가 다른 팀, 미정 정책 또는 아직 없는 계약에 의존한다.
- 구현 전에 "관련 파일을 찾아본다"가 필요하지만 티켓에 시작 경로가 없다.
- 테스트 명령이나 기대 결과를 티켓 작성자가 적을 수 없다.
- 기존 공개 계약을 바꾸면서 모든 소비자도 같은 티켓에서 수정한다.
- 실패 시 어느 변경을 되돌려야 하는지 한 문장으로 말할 수 없다.

### 쪼개는 순서

1. **계약 먼저:** 스키마·API·이벤트·공개 타입을 확정하고 계약 검사만 통과시키는 티켓을 만든다.
2. **생산자 다음:** 계약을 생성하거나 저장하는 한 계층의 구현을 분리한다.
3. **소비자별 분리:** API, 검색, 배포 어댑터 등 소비 계층마다 별도 티켓을 만든다.
4. **운영 경로 분리:** 관측, 마이그레이션, 롤아웃 검증은 기능 구현과 별도 티켓으로 둔다.
5. 각 티켓이 독립적으로 red→green이 되도록 임시 테스트 더블 또는 고정 계약을 사용하되, 나중 기능을 미리 구현하지 않는다.

## 2. 티켓 템플릿

### 항목별 목적

| 항목 | 필요한 이유 |
|---|---|
| 티켓 ID·제목 | 변경의 고유한 추적 단위와 단일 결과를 고정한다. |
| 소속 계층(L#) | 작업 경계와 책임 위치를 아키텍처에 연결한다. L6b도 독립 계층 ID로 쓴다. |
| 선행 티켓 | 시작 가능 여부와 병렬 실행 가능성을 판정한다. |
| 맥락(Context) | 저장소 전체를 탐색하지 않고도 필요한 설계와 현재 흐름을 찾게 한다. |
| 범위(In scope) | 이번 세션에서 만들어야 할 결과를 한정한다. |
| 범위 밖(Out of scope) | 주변 개선을 발견해도 변경하지 않을 경계를 고정한다. 항상 작성한다. |
| 수용 기준 | 에이전트가 완료를 자칭하지 못하도록 관찰 가능한 종료 조건을 준다. |
| 검증 방법 | 실행 명령, 테스트 경로와 기대 결과를 한 쌍으로 묶는다. |
| 건드리면 안 되는 것 | 동시 작업과 안정 계약을 경로·인터페이스 수준에서 보호한다. |
| 참고 규약 | 새 패턴을 발명하지 않고 이미 검증된 구현을 재사용하게 한다. |

### 복사해서 쓰는 양식

```markdown
# <PLAT-L#-NNN> <하나의 결과를 나타내는 동사형 제목>

## 식별

- 티켓 ID: `PLAT-<L1|L2|L3|L4|L5|L6|L6B|L7|L8|L9|L10>-<NNN>`
- 소속 계층: `<L# 또는 L6b>` — `platform/02-architecture.md §3`
- 관련 결정: `<D#>` — `platform/02-architecture.md §결정 요약`
- 선행 티켓: `<없음 | [티켓 ID, ...]>`

## 맥락(Context)

- 문제: <현재 관찰 가능한 실패 또는 아직 없는 동작>
- 필요한 이유: <사용자 또는 다음 계층에 주는 영향>
- 설계 근거:
  - `platform/02-architecture.md §<절 번호와 제목>`
  - `platform/01-requirements.md <FR/NFR ID>`
  - `platform/03-operations.md §<절 제목>`
- 시작 파일:
  - `<현재 흐름의 진입점 경로>`
  - `<재사용할 타입·도우미·테스트 경로>`

## 범위(In scope)

- [ ] <하나의 구현 결과>
- [ ] <그 결과를 검증하는 최소 테스트>
- 변경 허용 경로: `<파일 또는 좁은 디렉터리 목록>`

## 범위 밖(Out of scope)

- <인접 계층 또는 후속 티켓의 작업>
- <이번 티켓에서 바꾸지 않을 계약·운영 정책>

## 수용 기준(Acceptance Criteria)

- [ ] AC-1: <입력/상태>에서 <명령 또는 호출> 시 <정확한 출력·상태·오류>가 확인된다.
- [ ] AC-2: `<테스트 경로>::<테스트 이름>`이 <보호할 회귀 동작>을 검증한다.
- [ ] AC-3: <금지 입력 또는 실패 조건>은 <정확한 오류/상태>로 거부된다.

## 검증 방법

| 수용 기준 | 실행 명령 | 기대 결과 |
|---|---|---|
| AC-1 | `<정확한 명령>` | 종료 코드 0, `<기대 출력 또는 통과 개수>` |
| AC-2 | `<정확한 테스트 파일 명령>` | 지정 테스트 통과 |
| AC-3 | `<정확한 명령>` | 지정 오류·상태 검증 후 테스트 종료 코드 0 |

## 건드리면 안 되는 것

- 수정 금지 파일: `<경로>`
- 변경 금지 인터페이스: `<스키마/API/이벤트/공개 타입 이름과 버전>`
- 동시 작업 소유 경로: `<다른 티켓 ID>: <경로>`

## 참고 규약

- `<따라야 할 기존 구현 경로>` — <재사용할 패턴>
- `<따라야 할 기존 테스트 경로>` — <검증 스타일>

## 완료 보고

- 변경: <파일별 한 줄>
- 검증: `<실행한 명령>` → <실제 결과>
- 남은 일: <없음 | 후속 티켓 ID와 이유>
- 범위 밖 발견: <없음 | 변경하지 않고 기록한 사항>
```

빈 항목은 삭제하지 않고 `없음`이라고 쓴다. 경로, 절 번호, 명령을 `<관련 파일>`, `<테스트 실행>`처럼 추상적으로 남긴 티켓은 `ready`가 아니다.

## 3. 수용 기준 작성법

수용 기준은 **입력·행위·관찰 결과**를 포함한다. 구현 방식이 아니라 외부에서 판정할 동작을 적고, 각 항목을 검증 명령에 연결한다.

| 소재 | 나쁜 기준 | 좋은 기준 |
|---|---|---|
| L2 카탈로그 스키마 | 카탈로그 스키마가 잘 검증된다. | 필수 `name`이 없는 문서를 저장하면 `tests/catalog/test_schema.py::test_rejects_missing_name`이 검증 오류를 확인하고 통과한다. |
| L2/L5 소유권 튜플 | 소유자만 수정할 수 있다. | `maintainer` 관계만 가진 사용자의 상태 변경 요청은 403이고, `owner` 관계 사용자의 동일 요청은 성공함을 지정 테스트가 확인한다. |
| L6 Presigned URL | 다운로드 URL이 안전하게 만료된다. | 만료 시간을 지난 URL은 다운로드가 거부되고, 만료 전 URL은 동일 SHA-256 바이트를 반환함을 시간 고정 테스트가 확인한다. |
| L6b 헬스체크 저하 | 장애 Agent를 자동으로 격리한다. | 5분 간격 헬스체크가 연속 6회 실패하면 `degraded`가 되고 신규 접근 권한 부여·신규 연결이 차단되며 tier는 유지된다. 다음 성공 시 `active`로 자동 복구됨을 `tests/endpoints/test_health.py`가 확인한다. |
| L9 증분 폴링 | 변경분만 잘 동기화한다. | 체크포인트 이후 생성·상태 변경된 항목만 반영되고 이전 항목은 중복 생성되지 않음을 두 번의 폴링 테스트가 확인한다. |
| L6 런타임 어댑터 | 여러 런타임을 지원한다. | `runtimes`에 대상 런타임이 포함된 자산만 어댑터 출력에 나타나고 미선언 자산은 제외됨을 고정 입력 테스트가 확인한다. |
| L1 아티팩트 무결성 | 업로드가 안전하다. | 선언한 SHA-256과 업로드 바이트가 다르면 커밋 전 거부되고 L2 카탈로그에 레코드가 생성되지 않음을 통합 테스트가 확인한다. |
| L5 비전이 신뢰 | 타 사업부 권한이 올바르다. | A→B와 B→C allowlist만 있을 때 A 사용자의 C 접근은 403이며, A→C가 명시된 뒤에만 허용됨을 인가 테스트가 확인한다. |

피해야 할 표현은 "정상적으로", "적절히", "사용하기 쉽게", "문제없이", "필요한 경우"다. 숫자, 상태, 오류 코드, 정렬 결과, 생성 레코드 수처럼 검사 가능한 값으로 바꾼다.

## 4. 티켓 의존성 관리

### 표기 방식

- 티켓 ID는 `PLAT-L#-NNN`을 사용하며 L6b는 ID에서 `L6B`로 표기한다.
- `선행 티켓: 없음`이면 독립 시작 후보이고, 있으면 `선행 티켓: [PLAT-L2-001, PLAT-L4-003]`처럼 ID 목록을 쓴다.
- 의존성은 "코드를 재사용할 것"이 아니라 **선행 티켓의 어떤 계약 또는 산출물이 필요한지** 맥락에 적는다.
- 순환 의존성이 생기면 두 티켓을 합치지 않는다. 공통 계약을 확정하는 더 작은 선행 티켓을 만든다.

### 병렬 실행 판정

다음 네 질문이 모두 `예`일 때만 병렬 실행한다.

| 질문 | 예의 의미 |
|---|---|
| 선행 관계가 없는가? | 어느 티켓도 다른 티켓의 미완료 산출물을 읽지 않는다. |
| 변경 허용 경로가 겹치지 않는가? | 제품 코드뿐 아니라 테스트, 설정, 마이그레이션 경로도 겹치지 않는다. |
| 공유 계약을 바꾸지 않는가? | 같은 스키마, API, 이벤트, 공개 타입 또는 고정 샘플을 수정하지 않는다. |
| 검증이 서로의 상태를 요구하지 않는가? | 각 티켓의 명령이 상대 변경 없이 독립 실행된다. |

하나라도 `아니오`이면 순차 실행하거나 계약 티켓을 먼저 완료한다.

### 파일 충돌 회피

1. `ready` 전 티켓마다 변경 허용 경로를 파일 또는 가장 좁은 디렉터리 단위로 배정한다.
2. 동시에 진행 중인 두 티켓에 같은 경로를 배정하지 않는다.
3. 공통 파일이 필요하면 그 파일만 다루는 선행 티켓을 만들고 병합한 뒤 소비자 티켓을 시작한다.
4. 공유 테스트 파일도 제품 코드와 같은 충돌 대상으로 본다. 각 계층의 새 테스트 파일로 분리할 수 있으면 분리한다.
5. 작업 중 범위 밖 파일 변경이 필요해지면 수정하지 않고 티켓을 `blocked`로 전환해 필요한 계약과 경로를 기록한다.

### 공유 인터페이스 변경

스키마, OpenAPI 계약, 이벤트 형식, 공개 타입, 어댑터 인터페이스는 **계약 확정 티켓**에서 먼저 변경한다. 이 티켓은 다음만 포함한다.

- 계약 문서 또는 스키마 변경
- 하위 호환성 또는 명시적 실패를 검증하는 계약 테스트
- 소비자별 후속 티켓이 사용할 고정 예제

생산자와 각 소비자 구현 티켓은 계약 티켓을 선행 의존성으로 선언한다. 여러 소비자는 경로가 겹치지 않을 때만 병렬 실행한다.

## 5. 에이전트 구현 필수 규율

1. **범위를 먼저 고정한다.** 시작 전에 변경 허용 경로, 금지 파일, 선행 티켓 완료를 확인한다.
2. **red를 확인한다.** 비사소한 동작은 수용 기준을 잡는 최소 테스트가 변경 전 실패하는지 확인한다. 기존 테스트로 이미 red가 재현되면 재사용한다.
3. **최소 변경으로 green을 만든다.** 티켓 범위의 동작만 구현하고 인접 리팩터링은 남은 일로 보고한다.
4. **계약 변경을 분리한다.** 스키마·API·이벤트·공개 타입 변경이 티켓에 명시되지 않았다면 변경하지 않는다. 필요하면 별도 계약 티켓으로 돌린다.
5. **검증 없이 완료하지 않는다.** 모든 티켓은 최소 1개의 실행 가능한 검증을 저장소에 남기고, 티켓에 적힌 명령과 관련 회귀 검사를 실행한다.
6. **실제 결과를 보고한다.** 실행하지 않은 명령을 예정 또는 통과로 쓰지 않는다.

### 완료 보고 형식

```markdown
## 완료 보고 — <티켓 ID>

- 변경
  - `<경로>`: <바뀐 동작>
- 검증
  - `<명령>` → 종료 코드 <n>, <통과/실패 개수 또는 핵심 출력>
- 남은 일
  - <없음 | 후속 티켓 ID와 남은 이유>
- 범위 준수
  - 허용 경로 밖 변경: <없음 | 경로와 사유>
  - 변경하지 않은 발견 사항: <없음 | 한 줄>
```

검증 실패, 실행 불가, 범위 밖 변경 필요가 남아 있으면 `done`이 아니라 `blocked` 또는 `review`로 보고한다.

## 6. 티켓 상태와 흐름

```text
draft → ready → in-progress → review → done
                   │            │
                   └→ blocked ←─┘
                        │
                        └→ ready  (차단 원인 해소 후 재판정)
```

| 상태 | 의미 | 진입 조건 | 이탈 조건 |
|---|---|---|---|
| `draft` | 요구와 경계가 작성 중 | 티켓 생성 | ready 체크리스트 전부 충족 |
| `ready` | 에이전트가 단독 착수 가능 | 승인된 범위·계약·검증 명령 존재 | 에이전트가 경로 소유권을 확보하고 착수 |
| `in-progress` | 한 에이전트가 구현 중 | 선행 티켓 완료, 변경 경로 충돌 없음 | 수용 기준·검증 완료 또는 외부 차단 확인 |
| `review` | 구현과 자동 검증이 끝나 사람 판단 대기 | 완료 보고와 실제 검증 결과 제출 | 사람 리뷰 승인 또는 보완 요구 |
| `done` | 범위와 수용 기준이 모두 충족 | 자동 검사 통과 + 사람 리뷰 승인 | 재개하지 않음. 새 요구는 새 티켓 |
| `blocked` | 현재 권한·계약·외부 결정 없이는 진행 불가 | 차단 증거, 필요한 결정·소유자 기록 | 원인 해소 후 `ready` 체크리스트 재검토 |

### `ready` 판정 체크리스트

아래 항목 하나라도 비어 있으면 에이전트에게 배정하지 않는다.

- [ ] 티켓 ID, 단일 결과 제목, 주 계층 L# 또는 L6b가 있다.
- [ ] 관련 아키텍처 절 번호와 D#가 현재 문서와 일치한다.
- [ ] 모든 선행 티켓이 `done`이며 필요한 계약 산출물이 존재한다.
- [ ] 시작 파일과 재사용할 기존 패턴의 실제 경로가 있다.
- [ ] In scope와 Out of scope가 모두 작성됐다.
- [ ] 변경 허용 경로와 수정 금지 경로가 구체적이며 진행 중 티켓과 겹치지 않는다.
- [ ] 모든 수용 기준이 자동 검증 가능하고 검증 명령에 연결됐다.
- [ ] 테스트 파일 경로, 실행 명령과 기대 결과가 현재 환경에서 유효하다.
- [ ] 공개 계약 변경은 별도 계약 티켓으로 분리됐거나 이 티켓 자체가 승인된 계약 티켓이다.
- [ ] 한 세션 크기 기준을 충족하거나 예외 사유가 사람에게 승인됐다.

## 7. 리뷰 기준

### 자동 검사로 판정할 것

| 대상 | 통과 조건 |
|---|---|
| 수용 기준 | 티켓에 연결된 모든 테스트 명령 종료 코드 0 |
| 회귀 | 영향 계층의 기존 테스트 명령 종료 코드 0 |
| 정적 품질 | 저장소에 이미 있는 포맷·린트·타입 검사 통과 |
| 계약 | 스키마·API·이벤트·공개 타입의 계약 검사 통과 |
| 변경 범위 | 수정 파일이 티켓의 변경 허용 경로 안에만 존재 |
| 금지 내용 | 비밀정보, 외부 엔드포인트, 임시 우회와 비활성화된 테스트가 새로 포함되지 않음 |

### 사람이 판단할 것

| 대상 | 확인 질문 |
|---|---|
| 설계 정합성 | 지정한 L# 책임과 D# 결정을 그대로 따르는가? |
| 문제 해결 | 테스트에 맞춘 우회가 아니라 티켓의 실제 원인을 해결했는가? |
| 최소 범위 | 같은 결과를 더 적은 파일·상태·새 인터페이스로 만들 수 있었는가? |
| 보안 경계 | L1, L5, L6b, L9, L10 관련 변경이 신뢰·데이터·실행 경계를 약화하지 않는가? |
| 실패 의미 | 오류가 숨겨지지 않고 호출자와 운영자가 판단할 수 있는 형태로 남는가? |
| 유지보수성 | 기존 패턴을 재사용했고 다음 에이전트가 공개 계약을 다시 추론할 필요가 없는가? |
| 티켓 준수 | 범위 밖 발견을 임의 수정하지 않고 별도 후속 작업으로 남겼는가? |

리뷰 결과는 `APPROVE` 또는 `REQUEST-CHANGES`로 끝낸다. 변경 요청은 실패한 수용 기준, 파일과 필요한 결과를 지정하며 새 범위를 끼워 넣지 않는다. 새 요구는 별도 `draft` 티켓으로 만든다.
