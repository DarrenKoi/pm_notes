01

배포 토폴로지

사업부(Biz)마다 별도 인스턴스로 배포한다. 하나를 여러 사업부가 나눠 쓰는 멀티테넌시가 아니다. 그래서 인스턴스 경계가 곧 보안 경계이고 크로스-Biz 접근은 앱 내부 권한이 아니라 토큰 레이어 문제가 된다.

hosted agent 가 설계를 바꾼 지점

아티팩트가 없으므로 불변성·서명 모델이 적용되지 않는다. 심사 대상이 "무엇이 배포되는가"에서 "누가 무엇을 계속 책임지는가"로 바뀐다. 제공 팀이 서버를 내리면 사용자가 즉시 깨지므로 유예기간과 사전 통보가 절차가 아니라 요구사항이다.

제약이 만들어낸 관측 가능성

Anthropic 은 Skills API 로 사용량 분석을 제공하지 않는다고 명시한다. 그런데 hosted agent 는 호출이 Endpoint Broker 를 지나므로 확실하게 계량된다. 그래서 승격 지표를 종류별로 다르게 잡는다 — 경유형은 실제 호출량, 설치형은 설치 수와 게이트웨이 호출 수.

platform.claude.com · agent-skills/enterprise
03

소프트웨어 계층

L1–L10 과 L6b 를 하나의 FastAPI 앱 + 워커로 구현한다. 인스턴스가 이미 N개로 늘어나는 구조라 서비스 수까지 곱하면 운영 부하가 N×M 이 된다.

L1Artifact Store번들 저장. 발행 버전은 불변MinIO · Object Lock
L2Catalog정규화 문서 · 소유권 · 심사 상태MongoDB
L3Search전문 검색 · 패싯 · 랭킹OpenSearch
L4API발행 · 조회 · 상태전이 · 승격FastAPI
L5AuthSSO · M2M · 소유권 판정OIDC · RFC 9068
L6Distribution런타임별 배포 표면 (어댑터)marketplace.json · generic
L6bEndpoint Brokerhosted agent 중개 · 헬스체크 · 계량자체 구현
L7Cache / Queue캐시 · 레이트리밋 · 잡Redis
L8Observability사용량 · 지연 · 에러OTel → Data Prepper
L9Federation전사 인스턴스와 동기화push + pull + lazy copy
L10Governance심사 게이트 · 서명 · 등급cosign · in-toto/SLSA
04

매년 바뀌는 팀 이름

우리 조직의 특성이 그대로 설계 제약이 됐다. 팀 이름은 매년 바뀌고 사원 마스터에 불변 조직 코드가 있는지는 확인할 수 없다. 확실한 것은 empno 가 불변이라는 것뿐이다.

반례 — npm 의 실패 방식

npm 은 스코프가 곧 조직명이라 조직 이름을 바꿀 수 없다. 새 조직을 만들고, 멤버와 팀을 옮기고, 모든 package.json 의 스코프를 고치고, 전 패키지를 재발행한 뒤 지원팀에 옛 조직 삭제를 요청해야 한다.

docs.npmjs.com/renaming-an-organization

선례 — MCP 의 분리

MCP server.json 은 name(불변, reverse-DNS, 패턴 강제)과 title("optional human-readable display name")을 스키마 수준에서 분리해 뒀다. 우리도 같은 분리를 팀에 적용한다.

github.com/modelcontextprotocol/registry

우리의 답 — 이름이 아니라 관계로

# 네임스페이스에 팀명이 아니라 team_id 를 넣는다
kr.co.skhynix.dram.T-004821/defect-summarizer

# 소유권은 관계 튜플. subject 자리에 집합을 넣을 수 있다
agent:…/defect-summarizer#maintainer @ team:T-004821#member
team:T-004821#member @ user:E123456
team:T-004821#member @ user:E789012
사건바뀌는 것튜플 변경문서 재발행
팀 이름 변경displayName 1건0건0건
사원의 팀 이동members 배열1건0건
팀 병합successorTeamId멤버십만0건
조직 코드가 나중에 발견됨참조 필드 추가0건0건

절대 규칙: 튜플의 subject 에 표시명·이메일을 넣지 않는다. Google 은 Directory API 문서에서 "그룹 이메일을 영속 데이터의 키로 쓰지 말라"고 하면서 정작 Cloud IAM 은 principal 을 group:EMAIL 로 바인딩한다 — 자사 제품 안의 모순이다. 우리는 그 함정을 처음부터 만들지 않는다.

05

규모 판정 — 엔진을 도입하지 않는 이유

관계 튜플 모델은 Google 의 Zanzibar 에서 왔다. 그런데 모델은 가져오되 규모 대응책은 가져오지 않는다.

논문이 말하는 실제 숫자
15,000 네임스페이스당 튜플 중앙값

흔히 인용되는 2조 튜플은 1,500개 이상 네임스페이스의 합계다. 우리 레지스트리 전체가 대략 그 한 개 네임스페이스 크기다.

Zanzibar, USENIX ATC '19
결론과 재검토 조건

SpiceDB · OpenFGA · Ory Keto 는 모두 폐쇄망 자체 호스팅이 되지만 셋 다 우리에게 없는 관계형 DB를 요구한다. MongoDB 튜플 컬렉션으로 충분하다.

재검토 트리거값
튜플 수1,000,000
관계 그래프 깊이3
인가 판정 QPS1,000

이전 비용은 스키마 변환 스크립트 1개다. 지금 미루는 데 드는 비용이 없다.

06

조직 동기화

사원 마스터가 empno → 이름 · 현재 소속팀명 · 팀 코드명을 조회 API 로 제공한다. 멤버십은 1일 1회 야간 배치로 자동 동기화하고 관리 UI 를 만들지 않는다. 팀마다 멤버 집합이 있으므로 집합을 비교하면 조직 개편의 종류를 추론할 수 있다.

관측해석처리근거
코드 동일, 이름만 변경단순 rename자동정보 손실 없음
코드 변경, 멤버 대부분 일치같은 팀의 코드 변경자동teamId 유지
한 팀 멤버가 여러 팀으로 분산분할 (split)사람 판단자산의 행선지 결정 필요
여러 팀 멤버가 한 팀으로 수렴병합 (merge)승인successorTeamId 제안
팀 소멸, 멤버 흩어짐해체승계 시도원작성자 empno 경로

동기화 실패가 권한 상실이 되면 안 된다

조회 API 가 죽거나 부분 응답을 주면 마지막 성공 스냅샷을 유지하고 멤버를 지우지 않는다. 연속 3일 실패 시 경보. 읽기는 하루 지연을 허용하되, 발행·승격 같은 쓰기 동작 직전에만 실시간 조회한다.

07

GitLab 을 배포 백엔드로 쓸 수 있는가

절반은 된다. 저장·인증·심사 파이프라인은 GitLab 이 가져가고 카탈로그·검색·텔레메트리·승격·hosted agent 는 여전히 우리 몫이다.

계층대체GitLab 기능남는 문제
L5 Auth전부OIDC provider (Free)토폴로지 결정 필요
L10 Governance부분(큼)MR 승인 · CI · secret detection강제 승인은 Premium 부터
L1 Artifact부분generic package · container registry불변성이 약함. Maintainer 가 삭제 가능
L4 API · L6 배포부분REST API · 다운로드어댑터·스키마 계약은 우리 몫
L2 Catalog불가—질의 가능한 자산 문서 저장소가 없음
L3 Search불가advanced search패키지·레지스트리를 색인하지 않음
L6b Broker불가—hosted agent 대응 기능 자체가 없음
L8 관측거의 불가감사 이벤트 (Premium)다운로드 수·pull 이벤트 웹훅 없음
L9 연합방향 불일치Geo · 미러링 · export승격 의미론에 맞지 않음

불변성이 약하다

generic package 는 기본이 동일 버전 재발행 허용이고 중복을 막아도 Maintainer 가 삭제할 수 있다. Object Lock 등가물은 컨테이너 불변 태그(Ultimate)뿐이다.

사용량을 못 준다

패키지 API 는 last_downloaded_at 하나뿐. 다운로드 카운트도 발행·pull 웹훅 이벤트도 없다. GitLab 이 다운로드를 서빙하면 아무도 세지 않는다.

rename 을 안전하게 만들지 않는다

리다이렉트는 옛 경로를 누가 점유하면 죽고 컨테이너 태그가 있으면 네임스페이스 rename 자체가 차단된다. 경로에 팀명을 넣지 않는 규칙이 오히려 더 중요해진다.

08

주요 결정

D5
인스턴스 관계는 N-to-1 기본
신뢰가 비전이라 N-to-N 은 관계 수가 N² 로 늘어난다
D6
승격은 push(결정) + pull(메타데이터) + lazy copy(아티팩트)
push 연합을 표준화한 1차 자료가 없고 사전 전량 미러링은 어느 자료도 지지하지 않는다
D8
Object Lock 은 COMPLIANCE 가 아니라 GOVERNANCE 모드
COMPLIANCE 는 root 도 삭제 불가 — 보안 사고 시 회수가 불가능해진다
D10
자산을 3종으로 나누고 배포·심사·폐기 경로를 분리
셋의 배포 행위가 근본적으로 다르다
D13
팀은 조직이 아니라 empno 집합을 갖는 그룹. team_id 는 자체 발급
조직 코드의 불변성을 확인할 수 없으므로 그것에 의존하지 않는다
D15
전용 권한 엔진 미도입 — MongoDB 튜플 컬렉션
우리 전체가 Zanzibar 한 개 네임스페이스 크기. 엔진 셋 다 없는 DB 를 요구한다
D17
조직 동기화는 1일 1회 야간 배치
하루 지연 허용이 확정되어 실시간 동기화·이벤트 구독·캐시 무효화가 전부 불필요해졌다
09

이 회의에서 정해야 할 것

아직 답이 없고 답에 따라 구현 대상이 갈리는 항목들이다.

GQ1 · GQ3 · GQ4

사내 GitLab 실측

라이선스 티어, 컨테이너 레지스트리 활성 여부, 임의 OCI 아티팩트 지원. UI 15분 + oras push 30분이면 판정된다. L1·L5·L10 의 구현 대상이 여기서 정해진다.

사원 마스터

조회 API 계약

응답 스키마, 인증, 호출 한도, Redis 직접 읽기 허용 여부. Org Sync 는 가짜 구현으로 먼저 진행하지만 실제 연동에 필요하다.

Q2d

복수 팀 소속

한 사원이 겸직·매트릭스로 여러 팀에 속할 수 있는가. members 가 단순 집합이면 되는지 주·부 소속 구분이 필요한지가 갈린다.

Q13

지원 런타임 우선순위

오픈소스 런타임 중 무엇을 먼저 지원하는가. 어댑터 개수가 곧 개발량이다. 현재 계획은 P1 에 2개까지.

Q9

런타임 계측 가능 여부

사내 배포 런타임에 OTLP exporter 를 기본 탑재할 수 있는가. 설치형 자산의 실행을 볼 수 있는 유일한 경로다.

인력

6.5 FTE 확보

못 하면 인원을 늘리는 대신 범위를 줄인다. 버릴 수 있는 순서는 확산 자동화 → 승격·연합 → 서명 → 어댑터 2호. Endpoint Broker 와 정적 스캔은 버리지 않는다.
