# 사내 AI Agent·Skill 공유 관리 플랫폼 요구사항 정의서

> 사업부 구성원이 AI Agent와 Skill을 안전하게 게시·검색·설치·실행하고, 활용성이 검증된 자산을 전사 플랫폼으로 승격할 수 있게 한다.

## 왜 필요한가? (Why)

사업부에서 만든 Agent와 Skill이 개인이나 특정 팀에 흩어지면 중복 개발이 늘고, 누가 관리하는지와 안전하게 사용할 수 있는지를 판단하기 어렵다. 팀 이름이 매년 바뀌는 환경에서는 이름을 기준으로 소유권과 실적을 관리할 경우 검색, 통계, 감사 이력이 끊길 수 있다. 따라서 조직 개편에도 자산의 정체성과 책임 관계를 유지하면서 사업부 내 재사용을 촉진하고, 검증된 자산만 전사 범위로 승격하는 관리 체계가 필요하다.

본 플랫폼은 **사업부(Biz)마다 별도 인스턴스로 배포·운영되는 1차 플랫폼**이다. 하나의 인스턴스를 여러 사업부가 나누어 쓰는 멀티테넌트(Multi-tenant) 서비스가 아니며, 2차 전사 플랫폼은 각 1차 인스턴스의 상위에 별도 플랫폼으로 존재한다. 사내망에서만 동작하며 외부 LLM API를 사용하지 않고, 승인된 사내 오픈소스 LLM의 OpenAI 호환 API만 사용한다.

### 관리 대상 자산

"Agent"는 여러 오픈소스 런타임에서 동작하는 다음 자산을 포괄한다.

| 자산 유형 | 배포·사용 방식 | 운영 특성 |
|---|---|---|
| Skill | `SKILL.md`와 스크립트로 구성된 파일 묶음을 내려받아(Download) 호환 런타임에 설치(Install) | 설치 후 사용자 환경에서 실행 |
| MCP server | 로컬 설치형은 내려받아 실행하고, 원격형은 승인된 엔드포인트에 접근 | 설치형·원격형에 따라 심사와 운영 책임이 달라짐 |
| Hosted agent | 제공 팀이 운영하는 서버의 엔드포인트를 사용자가 호출 | 설치물이 아니라 접근 권한을 배포하며, 제공 팀의 서비스 가용성에 의존 |

## 이해관계자와 페르소나

| 페르소나 | 주요 목표 | 현재 불편(Pain) |
|---|---|---|
| Agent 제작자·제공 팀 | Skill·MCP server를 게시하거나 hosted agent 접근을 제공하고, 호환성·서비스 상태·활용도를 관리한다. | 자산 유형별 배포 방식이 다르고, hosted agent의 가용성·응답시간·장애 공지 책임이 분명하지 않다. |
| 일반 사용자 | 업무에 맞는 검증된 자산을 찾아 설치하거나 접근 권한을 받아 사용한다. | 어떤 런타임에서 동작하는지, 설치형인지 호출형인지, 서비스가 현재 사용 가능한지 알기 어렵다. |
| 팀·사업부 관리자 | 자산 소유권, 공개 범위, 운영 책임자와 사업부 내 활용 현황을 관리한다. | 조직명 변경 때 소유권과 통계가 단절되고, 방치된 자산을 식별하기 어렵다. |
| 플랫폼 운영자 | 사업부별 인스턴스를 일관되게 배포·모니터링하고 장애와 업그레이드에 대응한다. | 인스턴스별 버전·설정이 달라질 수 있고, 전체 운영 상태와 승격 이관 결과를 한 번에 파악하기 어렵다. |
| 보안·거버넌스 담당 | 접근, 변경, 실행, 승격이 정책에 맞는지 검증하고 감사 증적을 확보한다. | 타 조직 사용과 민감 권한에 대한 통제가 일관되지 않고, 필요한 감사 이력을 추적하기 어렵다. |

## 핵심 유스케이스(User Stories)

| ID | 단계 | 유저스토리 |
|---|---|---|
| US-01 | 제작 | Agent 제작자로서 게시 전에 자산 유형, 설명, 소유 조직, 원작성자, 책임자, 버전, 호환 런타임, 입력·출력, 권한 및 사용 조건을 등록하고 싶다. 그래야 다른 사용자가 용도와 실행 조건을 판단할 수 있다. |
| US-02 | 게시 | Agent 제작자로서 검증을 통과한 버전을 공개 범위와 함께 게시하고 싶다. 그래야 승인된 대상만 재사용할 수 있다. |
| US-03 | 검색·외부 열람 | 일반 사용자로서 소속 사업부 인스턴스에서 자산을 검색하고, 신뢰 관계가 승인된 타 사업부 인스턴스의 읽기 전용 공개 자산은 게스트로 확인하고 싶다. 그래야 인스턴스 경계를 지키면서 재사용 후보를 찾을 수 있다. |
| US-04 | 설치 | 일반 사용자로서 Skill 또는 로컬 MCP server의 호환 런타임과 의존 조건을 확인한 뒤 선택한 버전을 내려받아 설치하고 싶다. 그래야 재현 가능한 상태로 사용할 수 있다. |
| US-05 | 접근·실행 | 일반 사용자로서 원격 MCP server 또는 hosted agent의 접근 권한을 요청하고 서비스 상태·사용 조건을 확인한 뒤 호출하고 싶다. 그래야 별도 설치 없이 제공 팀의 서비스를 안전하게 사용할 수 있다. |
| US-06 | 사용량 확인 | 제작자와 관리자로서 설치 수, 활성 사용자 수, 실행 수, 성공률, 사용자 조직과 평가 추이를 보고 싶다. 그래야 유지보수와 확산 여부를 판단할 수 있다. |
| US-07 | 피드백·개선 | 일반 사용자로서 평점과 피드백을 남기고, 제작자로서 버전별 피드백을 확인하고 싶다. 그래야 품질을 지속해서 개선할 수 있다. |
| US-08 | 승격 신청 | 제작자 또는 사업부 관리자로서 활용성과 품질 증적을 첨부해 2차 플랫폼 승격을 신청하고 싶다. 그래야 사업부 밖에서도 재사용할 수 있다. |
| US-09 | 승격 심사 | 보안·거버넌스 담당자와 심사자로서 기준별 증적을 검토하고 승인, 보완 요청 또는 반려 결정을 기록하고 싶다. 그래야 전사 공개 위험을 통제할 수 있다. |
| US-10 | 승격 이관 | 플랫폼 운영자로서 승인된 버전의 아티팩트, 필수 메타데이터, 검증 결과와 집계된 사용 증적을 1차 인스턴스에서 별도 2차 플랫폼으로 이관하고 결과를 추적하고 싶다. 그래야 플랫폼 간 출처와 상태가 불명확해지지 않는다. |
| US-11 | 폐기 | 제작자 또는 관리자로서 자산을 폐기 예정(Deprecated)으로 표시하고, hosted agent는 서비스 종료 전에 대체재·종료일·이전 방법을 안내하고 싶다. 그래야 호출 사용자가 갑작스러운 중단 전에 이전할 수 있다. |
| US-12 | 조직 개편 | 팀·사업부 관리자로서 조직 표시명이 바뀌어도 자산 소유권과 과거 사용 통계를 이어 보고 싶다. 그래야 책임과 성과 이력이 단절되지 않는다. |

## 기능 요구사항(Functional Requirements)

MoSCoW 우선순위는 Must, Should, Could, Won't(이번 범위 제외)를 사용한다.

| ID | 요구사항 | 우선순위 | 근거 페르소나 |
|---|---|---|---|
| FR-01 | 각 인스턴스는 Agent와 Skill에 전역적으로 중복되지 않는 불변 ID를 부여해야 하며, ID 네임스페이스(Namespace)에 불변 사업부 식별자를 포함해 다른 1차 인스턴스 및 2차 플랫폼의 자산과 충돌하지 않게 해야 한다. | Must | 제작자, 관리자, 운영자 |
| FR-02 | 제작자는 자산명, 설명, 자산 유형, 배포·사용 방식, 버전, 소유 조직·원작성자·책임자, 호환 런타임과 버전, 입력·출력, 의존성, 요구 권한, 사용 조건을 등록·수정할 수 있어야 한다. Hosted agent와 원격 MCP server는 제공 팀, 접근 대상과 서비스 수준 목표(SLO)를 추가로 등록해야 한다. | Must | 제작자, 사용자 |
| FR-03 | 시스템은 자산 버전별 변경 내용, 게시자, 게시 시각과 검증 상태를 보존하고 사용자가 조회할 수 있게 해야 한다. | Must | 제작자, 사용자, 거버넌스 |
| FR-04 | 게시 전 필수 메타데이터, 허용되지 않은 비밀정보 포함 여부, 정책상 필수 검증 결과를 확인하고 실패 시 게시를 차단해야 한다. | Must | 제작자, 거버넌스 |
| FR-05 | 제작자 또는 관리자는 자산 공개 범위를 개인, 팀, 사업부 내부 또는 승인된 타 사업부의 읽기 전용 게스트 대상으로 지정할 수 있어야 한다. 타 사업부 공개는 설치·실행 권한을 자동 부여하지 않아야 한다. | Must | 제작자, 관리자, 거버넌스 |
| FR-06 | 사용자는 사내 인증(Authentication)을 거쳐야 하며, 모든 인스턴스는 public subject identifier인 동일한 `sub`로 같은 사원을 식별하고 사용자·조직·역할·자산 공개 범위에 따라 인가(Authorization)해야 한다. | Must | 사용자, 관리자, 거버넌스 |
| FR-07 | 타 사업부 사용자의 접근은 인스턴스 경계를 넘는 크로스 인스턴스(Cross-instance) 접근으로 처리하고 기본 차단해야 한다. 양 사업부 간 유효한 신뢰 관계, 대상 자산의 외부 공개 범위와 게스트 권한이 모두 확인된 경우에만 허용하며 결정 이력을 남겨야 한다. | Must | 사용자, 관리자, 거버넌스 |
| FR-08 | 사용자는 키워드와 업무 목적을 검색하고 자산 유형, 태그, 소유 조직, 상태, 평점, 최종 갱신일로 필터링할 수 있어야 한다. | Must | 사용자 |
| FR-09 | 검색 결과와 상세 화면은 최신 게시 버전, 검증 상태, 소유자, 접근 가능 여부, 폐기 여부를 명확히 표시해야 한다. | Must | 사용자 |
| FR-10 | 사용자는 Skill과 로컬 설치형 MCP server에 대해 권한, 호환 런타임과 의존 조건을 확인한 후 특정 버전을 내려받기(Download) 또는 설치(Install)할 수 있어야 한다. | Must | 사용자 |
| FR-11 | 시스템은 설치된 자산의 ID와 버전을 기록하고 새 버전 또는 폐기 예정을 사용자에게 알려야 한다. | Should | 사용자, 제작자 |
| FR-12 | 시스템은 외부 LLM API 호출을 허용하지 않고 승인된 사내 OpenAI 호환 LLM API를 사용하는 실행만 허용해야 한다. | Must | 운영자, 거버넌스 |
| FR-13 | 사용자는 설치형 자산의 실행 또는 원격 MCP server·hosted agent 호출의 접수, 진행, 성공·실패 상태와 사용 가능한 오류 정보를 확인할 수 있어야 한다. | Must | 사용자, 운영자 |
| FR-14 | 각 인스턴스는 자산·버전·사용자 조직별 설치 수, 활성 사용자 수, 실행 수, 성공률과 사용자 평가를 집계하고, 통계에 출처 인스턴스와 불변 사업부 식별자를 포함해야 한다. | Must | 제작자, 관리자, 운영자 |
| FR-15 | 사용자는 사용한 버전에 평점과 피드백을 남길 수 있고, 제작자는 이를 버전별로 조회할 수 있어야 한다. | Should | 사용자, 제작자 |
| FR-16 | 제작자 또는 사업부 관리자는 정해진 증적과 목표 이관 버전을 첨부해 2차 플랫폼 승격을 신청할 수 있어야 한다. | Must | 제작자, 관리자 |
| FR-17 | 승격 심사자는 기준별 결과와 의견을 기록하고 승인, 보완 요청 또는 반려할 수 있어야 한다. | Must | 운영자, 거버넌스 |
| FR-18 | 승인된 승격 건은 원본 1차 인스턴스와 별도 2차 플랫폼 사이의 이관으로 처리하고, 이관 대상·제외 대상·무결성 확인 결과를 기록하며 원본 인스턴스에서 후속 상태를 확인할 수 있어야 한다. | Must | 운영자, 제작자 |
| FR-19 | 제작자 또는 관리자는 자산을 폐기 예정으로 전환하며 사유, 대체 자산, 신규 설치 또는 신규 접근 승인 종료일, 최종 실행·호출일과 지원 종료일을 지정할 수 있어야 한다. | Must | 제작자, 사용자, 운영자 |
| FR-20 | 시스템은 폐기 예정 자산의 기존 설치 사용자와 hosted agent·원격 MCP server 접근 사용자에게 알리고, 종료일 이후 신규 설치·접근과 기존 호출을 정해진 순서대로 차단하며 감사 이력은 삭제하지 않아야 한다. | Must | 사용자, 운영자, 거버넌스 |
| FR-21 | 관리자는 불변 조직 ID에 연결된 표시명, 상위 조직, 책임자와 유효 기간을 변경·승계할 수 있어야 한다. | Must | 관리자, 거버넌스 |
| FR-22 | 운영자와 보안 담당자는 인증, 권한 결정, 게시, 설치, 실행, 설정 변경, 승격 및 폐기 이벤트를 조건별로 조회할 수 있어야 한다. | Must | 운영자, 거버넌스 |
| FR-23 | 운영자는 서비스 상태, 실행 실패율, 처리 지연과 비정상 접근 징후를 확인하고 임계치 초과 알림을 받을 수 있어야 한다. | Must | 운영자, 거버넌스 |
| FR-24 | 관리자는 장기간 책임자 부재, 사용 없음 또는 지원 종료일 경과 자산을 식별할 수 있어야 한다. | Could | 관리자, 운영자 |
| FR-25 | 게스트 사용자는 자신의 소속 사업부와 인증된 사용자임을 확인받아야 하며, 허용된 자산의 검색·상세 조회만 수행할 수 있어야 한다. 내려받기, 설치, 실행, 수정은 별도 명시적 승인이 없으면 차단해야 한다. | Must | 사용자, 관리자, 거버넌스 |
| FR-26 | 사업부 관리자는 사업부 간 신뢰 관계의 상대 사업부, 허용 행위, 대상 자산 범위, 승인자, 시작일과 만료일을 관리할 수 있어야 하며, 만료·철회 시 신규 크로스 인스턴스 접근을 즉시 차단해야 한다. | Must | 관리자, 거버넌스 |
| FR-27 | 각 인스턴스는 자신의 애플리케이션 버전, 적용 설정 기준 버전, 최종 업그레이드 시각과 지원 상태를 운영자가 확인할 수 있게 해야 한다. | Must | 운영자 |
| FR-28 | 운영자는 인스턴스별 업그레이드 대상·순서·유지보수 시간·결과·되돌림 여부를 기록하고, 실패한 인스턴스의 추가 롤아웃을 중단할 수 있어야 한다. | Must | 운영자 |
| FR-29 | 원격 MCP server와 hosted agent의 사용자는 다운로드 대신 별도의 접근 권한을 부여받아야 하며, 제공 팀은 승인·만료·회수 조건과 현재 서비스 상태를 공개해야 한다. | Must | 사용자, 제작자, 관리자 |
| FR-30 | 시스템은 자산별 지원 런타임과 호환 버전, 검증일과 검증 결과를 표시하고, 호환성이 확인되지 않은 조합에는 경고해야 한다. | Must | 제작자, 사용자 |
| FR-31 | 사용자 ID와 이름은 전사 사원 마스터를 단일 진실 원천(SSOT)으로 조회해야 하며, 레지스트리는 별도의 사용자 원장을 소유하거나 상충하는 사용자 정보를 생성하지 않아야 한다. | Must | 사용자, 관리자, 거버넌스 |
| FR-32 | 시스템은 자산의 원작성자를 불변 사원 ID로 기록하고, 조직 변경 이후에도 사원 마스터의 현재 소속과 연결해 소유권 승계 후보를 식별할 수 있어야 한다. | Must | 제작자, 관리자, 거버넌스 |
| FR-33 | Hosted agent 제공 팀은 계획 점검, 장애, 복구 예상 시각과 서비스 종료를 사용자와 플랫폼 운영자에게 공지할 수 있어야 한다. | Must | 사용자, 제작자, 운영자 |
| FR-34 | 레지스트리는 팀을 만들 때 불변 `team_id`를 자체 발급해야 하며, 사원 마스터의 팀명과 팀 코드명은 변경 가능한 관측값으로만 연결해야 한다. | Must | 관리자, 운영자, 거버넌스 |
| FR-35 | 인가는 `(resource, relation, subject, expiresAt)` 관계 튜플로 판정하고 `subject`에는 불변 사원 ID 또는 레지스트리 발급 ID와 `team:<team_id>#member` 형태의 집합 참조만 허용해야 한다. 표시명과 이메일은 권한 주체로 저장하지 않아야 한다. | Must | 사용자, 관리자, 거버넌스 |
| FR-36 | 시스템은 사원 마스터 조회 API가 제공하고 Redis에 저장하는 `empno`별 이름·현재 소속팀명·팀 코드명을 하루 1회 야간 동기화하고 팀 멤버십을 자동 갱신해야 한다. 별도 멤버십 관리 UI를 제공하지 않으며, 발행·승격 직전에는 마스터를 실시간 조회해 쓰기 권한과 현재 소속을 다시 확인해야 한다. | Must | 제작자, 관리자, 운영자 |
| FR-37 | Hosted agent가 헬스체크 연속 실패 임계치를 넘으면 시스템은 상태를 `degraded`로 자동 전환하고 신규 접근 권한 부여와 신규 연결을 차단하며, 소유 팀 통보·검색 순위 하락·경고 표시를 수행해야 한다. 헬스체크가 회복되면 `degraded` 상태를 자동 해제하되 등급 변경과 폐기 전환은 사람의 승인으로만 수행해야 한다. | Must | 사용자, 제작자, 운영자 |

## 비기능 요구사항(Non-Functional Requirements)

아래 수치는 초기 운영 목표이며, 실제 사용자·자산 규모가 확정되면 부하 시험과 보안 정책 검토를 거쳐 기준선으로 확정한다.

| ID | 영역 | 측정 가능한 목표 |
|---|---|---|
| NFR-01 | 성능 | 정상 부하에서 검색 요청의 95백분위수(p95)는 2초 이하, 자산 상세 조회 p95는 1.5초 이하여야 한다. |
| NFR-02 | 성능 | 각 인스턴스는 500명의 동시 사용자 조건에서 게시·검색·설치 메타데이터 요청의 월간 성공률 99.5% 이상을 유지해야 한다. 대용량 파일 전송 시간은 별도 측정한다. |
| NFR-03 | 가용성 | 계획된 점검을 제외한 월간 서비스 가용성 99.9% 이상을 인스턴스별로 충족하고 보고해야 한다. 한 인스턴스의 장애가 다른 사업부 인스턴스의 가용성에 영향을 주어서는 안 된다. |
| NFR-04 | 가용성 | 각 인스턴스의 장애 발생 시 복구 시간 목표(RTO)는 4시간 이내, 복구 시점 목표(RPO)는 1시간 이내여야 하며 모든 인스턴스는 반기마다 복구 시험을 수행해야 한다. |
| NFR-05 | 보안 | 인증이 필요한 기능에 대한 미인증 요청과 권한 밖 자산 요청은 100% 거부해야 하며, 권한 정책 회귀 시험을 배포마다 통과해야 한다. |
| NFR-06 | 보안 | 전송 중·저장 중 보호가 필요한 데이터는 사내 보안 기준을 100% 충족해야 하며, 비밀정보 원문은 자산 패키지와 로그에 저장하지 않아야 한다. |
| NFR-07 | 보안 | Critical 취약점은 확인 후 24시간 이내 완화 또는 서비스 차단, High 취약점은 7일 이내 조치해야 한다. |
| NFR-08 | 감사 | 인증, 인가 결정, 게시, 설치, 실행, 관리자 변경, 승격, 폐기 이벤트의 100%에 행위자, 대상 불변 ID, 시각, 결과를 기록해야 한다. |
| NFR-09 | 감사 | 감사 로그는 최소 2년간 검색 가능하게 보존하고, 월 1회 무결성 점검에서 누락·변조 0건을 목표로 해야 한다. 최종 보존 기간은 사내 정책으로 확정한다. |
| NFR-10 | 확장성 | 각 인스턴스는 사용자 10,000명, Agent·Skill 100,000개, 자산 버전 1,000,000개, 일 실행 이벤트 1,000,000건까지 NFR-01~03 목표를 유지할 수 있어야 한다. 전체 운영 규모는 이 기준에 인스턴스 수 N을 곱해 산정해야 한다. |
| NFR-11 | 확장성 | 기준 규모의 2배 부하 시험에서 오류율은 1% 미만이어야 하며, 용량 증설 판단에 필요한 포화 지표를 분기마다 검토해야 한다. |
| NFR-12 | 모니터링 | 가용성, p95 응답 시간, 실행 실패율, 인증·인가 거부율을 1분 이하 간격으로 측정하고 Critical 상태는 5분 이내 운영자에게 통보해야 한다. |
| NFR-13 | 운영부하 | 운영자는 운영 중인 인스턴스 100%의 버전, 설정 기준 준수 여부, 가용성 및 업그레이드 상태를 10분 이내에 파악할 수 있어야 한다. |
| NFR-14 | 운영부하 | 정기 업그레이드는 승인된 배포 기간부터 30일 이내에 대상 인스턴스 100%에 적용하거나 예외 승인 상태로 전환해야 하며, 실패 인스턴스는 30분 이내에 추가 롤아웃에서 제외해야 한다. |
| NFR-15 | Hosted agent | 제공 팀은 계획 점검을 제외한 월 가용성 99.5% 이상과 자산 특성에 맞는 p95 응답시간 목표를 선언·측정해야 한다. 시스템은 월 가용성을 99.5% 미만으로 선언한 Hosted agent의 등록을 차단해야 한다. 대화형 Agent의 초기 p95 목표는 10초 이하이며, 이를 충족하지 못한 월에는 원인과 개선 계획을 공개해야 한다. |
| NFR-16 | Hosted agent | 제공 팀은 계획 점검을 최소 7일 전에 공지하고, 예기치 않은 중단은 탐지 후 30분 이내에 상태와 다음 갱신 시각을 공지해야 한다. |
| NFR-17 | 신원 | 사원 마스터의 이름·현재 소속팀명·팀 코드명은 하루 1회 야간 배치로 동기화해 1일 이내 반영해야 한다. 발행·승격 같은 쓰기 동작은 배치 시점과 무관하게 직전 실시간 조회가 성공한 경우에만 허용해야 한다. |
| NFR-18 | 신원 | 사원 마스터 동기화 실패 시 마지막 성공 스냅샷을 읽기와 기존 권한 판정에 사용하고 기존 사용자를 임의의 새 사용자로 생성하지 않아야 한다. 연속 3일 실패하면 운영자에게 경보해야 한다. |

## 조직명 변경과 소유권 연속성 요구사항

| 항목 | 요구사항 |
|---|---|
| 불변 ID와 표시명 | 팀은 레지스트리가 자체 발급한 불변 `team_id`를 사용하고, 사업부도 생성 후 바뀌지 않는 식별자를 가져야 한다. 화면과 검색에는 사원 마스터에서 동기화한 팀명·팀 코드명 등 변경 가능한 관측값을 사용하되 모든 자산, 권한, 통계, 감사 기록은 불변 ID를 기준으로 연결해야 한다. |
| 명칭 이력 | 조직 표시명의 이전 값, 새 값, 변경 사유, 변경일, 변경자를 보존하고 해당 기간을 조회할 수 있어야 한다. 과거 기록은 당시 표시명과 현재 표시명을 모두 확인할 수 있어야 한다. |
| 소유권 승계 | 조직 통합·분리·폐지 시 관리자는 후속 조직과 책임자를 지정해야 한다. 승계 전후의 조직 ID 관계, 대상 자산, 승인자와 효력 발생일을 기록해야 한다. |
| 원작성자 추적 | 자산의 원작성자는 사원 마스터의 불변 사원 ID로 기록해야 한다. 팀이 해체되어도 당시 작성자와 그 사원의 현재 소속을 조회할 수 있어야 하며, 사용자 이름의 별도 사본을 소유권 근거로 사용하지 않아야 한다. |
| 권한 검증 | 소유권 승계 시 기존 권한을 무조건 복사하지 않고, 새 조직 범위에 맞게 재검토해야 한다. 완료 전에는 자산의 기존 공개 범위를 확대하지 않아야 한다. |
| 검색 연속성 | 현재 팀명과 과거 팀명 중 어느 것으로 검색해도 동일한 조직과 소유 자산을 찾을 수 있어야 하며, 결과에는 현재 표시명을 우선 노출해야 한다. |
| 통계 연속성 | 조직명 변경 전후 통계를 같은 불변 ID로 연속 집계해야 한다. 조직 통합·분리 시에는 원조직 기준과 현조직 기준 집계를 구분해 재현할 수 있어야 한다. |
| 감사 보존 | 이름 변경이나 승계 후에도 기존 게시, 실행, 승인, 폐기 감사 기록의 행위자와 당시 소속을 변경하거나 삭제하지 않아야 한다. |

## 사업부별 독립 인스턴스 운영 요구사항

| 항목 | 요구사항 |
|---|---|
| 배포 단위 | 각 사업부는 하나 이상의 독립 1차 인스턴스를 배포 단위로 가지며, 다른 사업부와 사용자·자산·설정·운영 상태를 공동 테넌트로 공유하지 않아야 한다. |
| 버전 기준 | 운영 조직은 지원 중인 표준 버전과 지원 종료일을 정하고, 모든 인스턴스의 현재 버전과 표준 대비 차이를 식별할 수 있어야 한다. |
| 설정 표준화 | 공통 필수 설정 항목과 허용 편차를 정의하고 인스턴스별 준수 여부를 확인해야 한다. 사업부별 예외는 사유, 승인자와 만료일을 기록해야 한다. |
| 업그레이드 롤아웃 | 업그레이드는 대상 인스턴스, 적용 순서, 검증 조건, 중단 조건과 되돌림 조건을 사전에 정하고 단계적으로 수행해야 한다. 선행 인스턴스가 검증 조건을 통과하지 못하면 후속 적용을 중단해야 한다. |
| 운영 책임 | 각 인스턴스는 주 운영자와 대체 운영자, 장애 연락 경로, 유지보수 시간과 지원 상태를 가져야 한다. |
| 상태 가시성 | 운영자는 인스턴스 수 N이 증가해도 각 인스턴스의 가용성, 버전, 설정 편차, 장애와 업그레이드 결과를 동일 기준으로 비교할 수 있어야 한다. |

## 1차 플랫폼에서 2차 플랫폼으로의 승격

### 승격 자격 차원과 필수 증적

승격 수치, 담당자, SLA와 실행 순서는 [운영·거버넌스 프로세스](./03-operations.md#1차에서-2차로의-승격-프로세스)가 소유한다. 요구사항은 자산 유형에 맞게 다음 자격 차원과 증적을 빠짐없이 평가할 것을 요구한다.

| 자격 차원 | 필수 증적 | 보장 조건 |
|---|---|---|
| 사용량·조직 간 재사용 | 출처 인스턴스, 측정 기간, 활성 사용자·실행·재사용 팀 집계와 계측 누락 구간 | 일회성 수요가 아니며 제작 팀 밖에서도 재사용됐음을 판정할 수 있어야 한다. |
| 사용자 평가·실행 품질 | 버전별 평가 수·평점, 실행 수, 성공·실패 정의와 성공률 | 사용자 가치와 운영 안정성을 같은 버전 기준으로 재현할 수 있어야 한다. |
| Hosted agent 서비스 품질 | 가용성·응답시간 SLO, 실제 측정값, 계획·비계획 중단과 공지 기록 | 전사 사용자가 제공 팀 서비스에 의존할 수 있는지 판정할 수 있어야 한다. |
| 유지보수성·문서 완결성 | 주·대체 책임자, 지원·폐기 계획, 목적·입출력·권한·의존성·설치 또는 접근 방법·제한·변경 이력 | 다른 조직이 독립적으로 도입하고 지원받을 수 있어야 한다. |
| 보안·거버넌스 | 심사 결과, 미해결 위험, 예외 승인과 계측 완전성 | 사업부 경계를 넘는 권한·데이터·운영 위험이 명시적으로 승인돼야 한다. |
| 전사 중복성 | 2차 플랫폼의 기존 자산과 비교한 기능·운영 중복 검토 | 중복 등록과 사용자 혼선을 방지해야 한다. |

### 인스턴스 간 이관 대상

| 구분 | 이관 요구사항 |
|---|---|
| 아티팩트(Artifact) | Skill과 로컬 설치형 MCP server는 심사·승인된 정확한 버전의 무결성 정보, 복사 권한과 원본 경로를 먼저 등록해야 한다. 실제 바이트는 2차 플랫폼의 최초 설치 요청 때 복사하고 이후 2차 플랫폼에서 로컬 서빙해야 한다. Hosted agent와 원격 MCP server는 설치 아티팩트 대신 승인된 접근 정보와 서비스 계약을 이관하며, 승인되지 않은 버전과 운영 중 생성된 임시 데이터는 제외해야 한다. |
| 메타데이터 | 자산 불변 ID, 자산 유형, 배포·사용 방식, 원본 인스턴스와 사업부 식별자, 이름, 설명, 버전, 호환 런타임, 입력·출력, 의존성, 요구 권한, 원작성자, 소유·지원 정보, 변경 이력, 사용 조건, 서비스 SLO, 검증·심사 결과를 이관해야 한다. |
| 사용 이력 | 승격 판단에 사용된 기간별 설치 수, 활성 사용자 수, 실행 수, 성공률, 재사용 팀 수와 평점의 집계값 및 산정 기간을 이관해야 한다. 사용자별 실행 입력·출력과 원본 감사 로그는 기본 이관 대상에서 제외하고, 별도 정책과 승인을 받은 경우에만 포함해야 한다. |
| 식별자 연결 | 2차 플랫폼은 원본 자산의 불변 ID와 출처 인스턴스를 보존하고, 2차 플랫폼 식별자를 새로 부여한다면 양 식별자의 대응 관계를 조회할 수 있게 해야 한다. |
| 이관 검증 | 송신·수신 양측은 이관 항목 목록, 버전, 누락 여부와 무결성 확인 결과를 기록해야 하며 검증 실패 시 공개를 차단해야 한다. |

### 승격 워크플로

구체적인 단계, 담당자와 SLA는 [운영·거버넌스 프로세스](./03-operations.md#단계와-심사-주체)를 따른다. 시스템은 신청 증적, 단계별 판정·승인자·시각·근거, 이관 검증 결과와 공개 상태를 연결해 기록하고 1차 인스턴스에서 후속 상태를 조회할 수 있게 해야 한다.

승격은 자산의 ID, 출처, 제작 조직, 버전 및 심사 이력을 잃지 않아야 한다. 승인되지 않은 후속 버전이 자동으로 전사 공개되어서는 안 되며, 각 버전은 필요한 심사를 별도로 거쳐야 한다.

## 자산 유형별 폐기 요구사항

| 자산 유형 | 폐기 시 필수 조치 |
|---|---|
| Skill | 신규 다운로드·설치 종료일, 최종 지원일, 대체 버전 또는 제거 방법을 공지한다. 이미 설치된 복사본을 자동으로 제거할 수 없음을 사용자에게 알린다. |
| 로컬 MCP server | 신규 설치 종료일, 실행 중단 권고일, 로컬 자격증명·데이터 정리 방법과 대체재를 안내한다. |
| 원격 MCP server | 신규 접근 승인을 먼저 중단하고 기존 사용자의 호출 종료일, 데이터 회수 방법과 대체 엔드포인트를 안내한다. |
| Hosted agent | 제공 팀은 서비스 종료 예정일 전에 신규 접근 승인을 중단하고, 기존 호출 사용자에게 종료일·영향·대체재·이전 방법을 사전 통보해야 한다. 보안 긴급 회수를 제외하면 공지된 유예기간 동안 선언 SLO와 지원 책임을 유지해야 한다. |

Hosted agent는 제공 팀 서버가 중단되면 사용자가 즉시 영향을 받으므로, 단순 카탈로그 상태 변경만으로 폐기를 완료한 것으로 보지 않는다. 마지막 호출 종료, 접근 권한 회수, 사용자 통보와 대체재 안내가 모두 확인되어야 한다.

## 범위 밖(Out of Scope)

- 2차 전사 플랫폼 자체의 구축과 운영 정책 수립
- Agent·Skill 제작용 IDE, 소스코드 편집기 또는 범용 개발 환경 제공
- 기반 LLM의 학습, 파인튜닝(Fine-tuning), 평가 모델 개발과 서빙 기술 설계
- 외부 인터넷, 외부 SaaS 또는 외부 LLM API 연동
- 업무별 Agent의 프롬프트·도메인 로직을 대신 개발하는 일
- 구체적인 아키텍처, 제품, 데이터 저장소, 배포 방식과 기술 스택 선정
- 사용자 단말과 실행 환경에 대한 전사 표준 설치 도구 개발
- 사업부 간 비용 정산과 과금 체계
