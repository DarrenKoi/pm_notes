# 구축 계획 — 인력·기간 산정

> 사업부 1차 플랫폼을 실제로 구축하는 데 필요한 인원 구성, 단계별 범위, 기간 추정.

수치는 **제안값**이다. 아래 [산정 전제](#산정-전제)가 깨지면 그대로 어긋나므로 전제를 먼저 확정한 뒤 조정할 것.

---

## 왜 필요한가? (Why)

이 프로젝트는 규모를 착각하기 쉽다. "업로드·다운로드 사이트"로 보면 2~3인 두 달짜리로 보이지만 실제로 시간을 먹는 것은 **레지스트리 본체가 아니라 그 주변**이다.

| 착각 | 실제 |
|---|---|
| 파일 올리고 받는 CRUD | 발행 파이프라인(검증·스캔·서명·불변 커밋)이 본체보다 크다 |
| 자산은 한 종류 | **세 종류(Skill / MCP server / hosted agent)** 이고 배포·심사·폐기 경로가 각각 다르다 |
| 런타임 하나에 붙이면 됨 | 오픈소스 런타임 포함 다수 공존 → **어댑터가 개발량이 된다** |
| 로그인 붙이면 끝 | 인스턴스가 N개라 인증이 **토큰 레이어 설계**가 된다 (Q7b 하나에 구조가 갈린다) |
| 나중에 모니터링 추가 | 승격 판단 근거가 사용량이므로, 텔레메트리가 없으면 **플랫폼의 존재 이유가 작동하지 않는다** |
| 인스턴스 1개 만들면 됨 | 배포 단위가 N개다. 자동화가 안 되면 운영 부하가 N배로 곱해진다 |

## 산정 전제

| # | 전제 | 깨지면 |
|---|---|---|
| A1 | 사내에 공통 OIDC IdP 가 이미 있고 신규 RP 등록이 가능하다 | Auth 단계 +4주, SAML 브릿지 필요 시 +6주 |
| A1b | **subject identifier 는 public, 사원 마스터 단일 테이블 존재** (확정됨) | — 이 전제가 확정되어 크로스-인스턴스 신원 리스크가 제거됨 |
| A2 | MongoDB / Redis / OpenSearch / MinIO 는 사내 관리형으로 제공받는다 (직접 운영 아님) | Infra 1.0 FTE 상시 추가 |
| A3 | 지원 런타임을 **P1 에서는 2개까지**로 제한한다 (Q13) | 3개째부터 어댑터당 +2주 |
| A3b | hosted agent 를 **P1 범위에 포함**한다 | 제외하면 P1 -4주, 대신 팀 서버 운영형 자산을 초기에 못 받는다 |
| A4 | 초기 대상 인스턴스는 **1개 사업부**. 이후 복제 | 동시 다중 사업부면 Phase 0 에 배포 자동화 선투자 필요 |
| A5 | 보안 심사 인력은 기존 조직에서 겸직으로 확보 | 전담 채용 리드타임 별도 |
| A6 | 2차 전사 플랫폼의 인터페이스는 우리가 제안하고 상대가 수용한다 | 협의 기간이 크리티컬 패스가 됨 |

### 코어 밖 (겸직·간헐)

| 롤 | 투입 | 시점 |
|---|---|---|
| 심사 리뷰어 풀 | 사업부당 2~3명, 주 2~4시간 | Phase 2 이후 상시 |
| 사내 IdP 담당 | 협의 5~10인일 | Phase 1 초 |

**6.5 FTE 를 확보 못 하면** 범위를 줄이는 것이 맞다 — 인원을 늘리는 대신 Phase 3(승격·연합)을 통째로 뒤로 미룬다. 승격은 1차 인스턴스에 쓸 만한 에이전트가 쌓인 뒤에야 실제로 필요해진다.

## 어떻게 진행하는가? (How) — 단계별 계획

### 전체 일정 (6.5 FTE 기준)

| Phase | 기간 | 누적 | 끝나면 가능해지는 것 |
|---|---|---|---|
| **P0. 결정과 골격** | 3주 | 3주 | 구조가 갈리는 질문이 닫히고 배포 골격이 선다 |
| **P1. 레지스트리 MVP** | 10주 | 13주 | 세 종류 자산을 올리고 찾고 설치·연결할 수 있다 |
| **P2. 거버넌스·관측** | 7주 | 20주 | 심사를 거쳐 안전하게 배포하고, 무엇이 쓰이는지 보인다 |
| **P3. 승격·연합** | 6주 | 26주 | 2차 전사 플랫폼으로 승격이 돌아간다 |
| **P4. 확산** | 4주 | 30주 | 다른 사업부 인스턴스를 복제 배포할 수 있다 |

**약 6.5개월 (P0~P3), 확산까지 7.5개월.** 자산 3종과 다중 런타임이 확정되면서 P1 이 8주 → 10주로 늘었다.

### P0. 결정과 골격 — 3주

| 산출물 | 담당 |
|---|---|
| 열린 질문 **Q13 · Q2c/Q2d** 종결 (Q1·Q2·Q2b·Q2e·Q4·Q7b·Q14·Q15 는 종결됨) | PM, 보안 |
| **사원 마스터 조회 API 계약 확인** — 응답 스키마, 인증, 호출 한도, Redis 직접 읽기 허용 여부 | 백엔드, PM |
| [GitLab 실측 체크리스트](./06-gitlab-check.md) 수행 — GQ1~GQ4 | DevOps |
| 지원 런타임 우선순위 확정, 어댑터 인터페이스 규격 | 아키텍트 |
| 스키마 v0 확정 + `$schema` 날짜 스탬프 규약 | 백엔드, 아키텍트 |
| 인스턴스 1식 배포 (Mongo/Redis/OpenSearch/MinIO 연결 확인) | DevOps |
| CI 파이프라인, 리포지토리 구조 | DevOps |

> **P0 를 건너뛰지 말 것.** 남은 구조적 질문은 **Q13(런타임 우선순위)** — P1 개발량을 직접 정한다 — 와 **GitLab 실측 4건**이다. 후자는 L1(아티팩트 저장)·L5(인증)·L10(거버넌스)의 구현 대상을 정한다. 다만 [§ArtifactStore seam](./06-gitlab-check.md) 덕분에 답을 기다리며 멈출 필요는 없다.

### P1. 레지스트리 MVP — 10주

| 주 | 범위 |
|---|---|
| 1–2 | 카탈로그 CRUD, MongoDB `$jsonSchema` validator, 감사 로그 |
| 2–3 | **Org Sync** — 사원 마스터 조회 API 연동, 1일 1회 배치, `teams.members` 갱신, 멤버 집합 비교로 개편 감지, 실패 시 스냅샷 유지 |
| 2–4 | MinIO 업로드·presigned 다운로드, Object Lock(GOVERNANCE), `fileSha256` 검증 |
| 3–5 | OIDC 로그인, RFC 9068 토큰 검증, `aud` 검사, **관계 튜플 인가 판정**(집합 subject, 만료 조건) |
| 4–6 | OpenSearch 색인·검색, Redis 큐/레이트리밋 |
| 5–7 | 배포 표면 어댑터 1호(`marketplace.json` 동적 생성) + generic API, 설치 경로 E2E |
| 6–9 | **Endpoint Broker(L6b)** — hosted agent 등록, 헬스체크, 접근 토큰 발급·만료, 호출 계량 |
| 7–9 | 어댑터 2호 (오픈소스 런타임) |
| 6–10 | 프론트엔드: 카탈로그·상세·발행 콘솔 (자산 3종 분기 포함) |

**P1 완료 판정:** 사원이 Skill·MCP server 를 올려 다른 사원이 설치·실행할 수 있고 팀이 hosted agent 를 등록해 다른 사원이 접근 권한을 받아 호출할 수 있다. 심사는 아직 없다.

### P2. 거버넌스·관측 — 7주

| 주 | 범위 |
|---|---|
| 1–3 | 발행 파이프라인 게이트: 매니페스트 검증, 정적 스캔 룰셋 (설치형) + 엔드포인트 심사 게이트 (hosted) |
| 2–4 | cosign 자체 키 서명, in-toto/SLSA 증명 저장·검증 |
| 3–5 | 심사 워크플로 + 관리자·리뷰어 화면, 등급(tier) 노출 |
| 4–6 | OTel Collector → Data Prepper → OpenSearch, `gen_ai.*` + 사내 커스텀 속성 |
| 5–7 | 사용량 대시보드(자산 종류별 지표 분리), 폐기 상태 전이 + hosted agent 유예 경로 |

> **계측 난이도가 자산 종류마다 다르다.** hosted agent 는 Endpoint Broker 를 지나므로 P1 시점에 이미 호출량이 잡힌다. 설치형은 설치 수까지만 보이며 실행 계측은 **사내 배포 런타임에 OTLP exporter 를 기본 탑재**할 수 있는지에 달렸다(Q9). 불가능하면 설치 수 + 게이트웨이 호출 수로 승격 기준을 다시 잡는다.

### P3. 승격·연합 — 6주

| 주 | 범위 |
|---|---|
| 1–2 | 2차 플랫폼 인터페이스 협의 및 계약 확정 (선행 필수) |
| 2–4 | 승격 신청 API(`/v0.1/x/…/promote`), 심사 워크플로 |
| 3–5 | 증분 폴링(`updated_since`) 제공, 아티팩트 lazy copy 경로 |
| 4–6 | 크로스-Biz 게스트 읽기, allowlist(비전이) 및 만료·재승인 |

> 1주차 협의가 안 끝나면 이 Phase 전체가 밀린다. **P1 중에 미리 착수**하는 것이 안전하다.

### P4. 확산 — 4주

| 범위 |
|---|
| 인스턴스 배포 자동화(설정 템플릿화, 시크릿 분리) |
| 두 번째 사업부 인스턴스 실제 배포 및 회귀 확인 |
| 운영 런북, 업그레이드 롤아웃 절차 |

## 규모를 줄이는 선택지

인원이나 기간이 부족할 때 **무엇을 먼저 버릴 수 있는가**. 위에서부터 안전한 순서다.

| 버리는 것 | 절감 | 대가 |
|---|---|---|
| P4 확산 자동화 | 4주 | 두 번째 인스턴스를 수동 배포. 3개째부터 아프다 |
| P3 승격·연합 | 6주 | 2차 승격이 수동 이관이 된다. 초기엔 승격 대상 자체가 적어 감내 가능 |
| 서명·증명(cosign/SLSA) | 2주 | 무결성이 `fileSha256` 만 남는다. 폐쇄망이면 위험도 낮음 |
| 런타임 어댑터 2호 | 2주 | 런타임 1개만 지원. 오픈소스 런타임 사용자가 배제된다 |
| Org Sync 개편 자동 감지 | 1주 | 멤버십 동기화만 하고 분할·병합 추론은 수동. 연 1회 작업이라 감내 가능 |
| 설치형 런타임 텔레메트리 | 3주 | hosted agent 지표는 그대로 남는다. 설치형만 설치 수로 판정 |
| **Endpoint Broker(L6b)** | 4주 | **hosted agent 를 아예 못 받는다.** 팀 서버 운영형이 주력이면 버리지 말 것 |
| **정적 스캔 게이트** | 3주 | **버리지 말 것.** 실행물을 사내에 배포하는 구조라 이 게이트가 없으면 사고가 곧 사내 전파다 |
| **감사 로그** | 1주 | **버리지 말 것.** 사후에 소급 생성할 수 없다 |

| GitLab 실측 결과가 늦게 나옴 | L1 구현 대상 미정 | `ArtifactStore` seam 으로 MinIO 구현부터 진행. 결정 시 구현체 교체 |
| hosted agent 제공 팀의 서버가 자주 죽음 | 사용자 신뢰 붕괴 | 헬스체크 연속 실패 시 자동 강등(§8). 제재 규칙은 Q14 |
