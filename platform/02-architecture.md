# 아키텍처 설계서 — 사내 AI Agent·Skill 공유 플랫폼 (1차/사업부)

> 사업부마다 독립 배포되는 레지스트리 1차 인스턴스의 소프트웨어 계층, 데이터 모델, 인증·승격·관측 경로를 정의한다.

이 문서는 **무엇을 만드는가**를 다룬다. 요구사항은 [01-requirements.md](./01-requirements.md), 운영 프로세스는 [03-operations.md](./03-operations.md), 근거 조사는 [research/agent-skill-registry-research.md](./research/agent-skill-registry-research.md) 에 있다. 기술 선택의 1차 출처는 조사 문서에 있으므로 여기서는 **결정과 그 이유**만 적는다.

---

## 왜 필요한가? (Why)

에이전트·스킬을 공유한다는 것은 **사내에 실행 가능한 코드와 프롬프트를 배포한다**는 뜻이다. 파일 공유 폴더나 위키로 하면 세 가지가 반드시 깨진다.

| 깨지는 것 | 증상 |
|---|---|
| 출처와 무결성 | 누가 만들었고 그 사이 바뀌었는지 알 수 없다 |
| 소유권의 연속성 | 조직이 매년 개편되면 자산이 무주공산이 된다 |
| 사용 실태 | 어떤 에이전트가 실제로 쓰이는지 몰라 승격 판단 근거가 없다 |

이 세 가지를 각각 **불변 아티팩트 저장**, **불변 ID 기반 소유권 모델**, **표준 텔레메트리**로 푸는 것이 이 아키텍처의 뼈대다.

## 확정 전제 (Given)

| # | 전제 | 아키텍처에 주는 영향 |
|---|---|---|
| G1 | 1차 플랫폼은 **사업부(Biz)마다 별도 인스턴스**로 배포. 멀티테넌시 아님 | 인스턴스 경계가 곧 보안 경계. 크로스-Biz 접근은 앱 내부 권한이 아니라 **토큰 레이어** 문제 |

| G3 | 외부 LLM API 사용 불가, 폐쇄망 | 서명·검증은 자체 키(cosign), 인터넷 의존 서비스 금지 |
| G4 | 가용 스택: Python 3.11 / FastAPI / Flask / Node.js, MongoDB / Redis / OpenSearch / MinIO | OCI 레지스트리가 없다 → digest 기반 불변성을 **MinIO Object Lock + 자체 매니페스트**로 직접 구현 |
| G5 | 팀명이 매년 바뀐다 | 식별자에 팀명을 넣지 않는다 (§5) |
| G6 | **오픈소스 런타임 포함, 여러 런타임이 공존**한다 | 카탈로그는 런타임 중립이어야 한다. 배포 표면(L6)은 **런타임별 어댑터**로 분리 |
| G7 | **"Agent"는 포괄적 용어** — Skill / MCP server / 팀 서버가 운영하는 hosted agent | 자산 종류마다 배포·심사·폐기 경로가 다르다 (§2) |
| G8 | 사내 IdP subject identifier 는 **public**. 전 사원 ID·이름 **단일 마스터 테이블** 존재 | 크로스-인스턴스 신원 판정이 성립한다. 레지스트리는 사용자 정보를 소유하지 않는다 |
| G9 | **`empno`(사번)가 불변인 유일한 식별자.** 조직 코드의 불변성은 **확인 불가** | 조직 코드에 **의존하지 않는** 설계여야 한다 (§5.3) |
| G10 | `empno` → **이름 / 현재 소속팀 이름 / 팀 코드명** 조회 API 존재. **Redis 에 저장**됨 | 팀 멤버십을 **자동 동기화**할 수 있다. 멤버십 관리 UI 불필요 (§5.4) |

## 핵심 개념 (What)

### 1. 배포 토폴로지

```
[사원 PC / 에이전트 런타임]
        │  ① OIDC 로그인 (공통 사내 IdP)
        │  ② 카탈로그 조회 · 설치
        ▼
┌───────────────────────────┐   ┌───────────────────────────┐
│  Biz-A 1차 인스턴스        │   │  Biz-B 1차 인스턴스        │
│  API / Mongo / Redis /    │   │  (동일 구성, 독립 배포)     │
│  OpenSearch / MinIO       │   │                           │
└──────────┬────────────────┘   └──────────┬────────────────┘
           │ ③ 승격 발행 (push)             │
           │    + 증분 폴링 (pull)          │
           ▼                                ▼
        ┌──────────────────────────────────────┐
        │  2차 전사 플랫폼 (별도 운영 주체)      │
        └──────────────────────────────────────┘
```

**인스턴스 간 관계는 N-to-1 을 기본으로 한다.** Biz끼리 직접 신뢰 관계를 맺으면 관계 수가 N²로 늘어나고, Claude Code 의 신뢰 모델이 **비전이(trust does not chain through intermediate marketplaces)** 이므로 그 부담을 줄일 방법이 없다. 타 Biz 에이전트가 필요하면 원칙적으로 **전사(2차)를 경유**한다. 예외적 직접 접근은 §7.3 의 게스트 경로로 한정한다.

### 2. 자산 종류 — 무엇을 등록하는가

"Agent"는 포괄적 용어다. 레지스트리가 다루는 것은 최소 세 종류이고, **셋의 배포 행위가 서로 다르다.**

| 종류 | 실체 | 배포 행위 | 아티팩트 | 의존하는 것 |
|---|---|---|---|---|
| **Skill** | 파일 묶음 (`SKILL.md` + 스크립트) | **내려받아 설치** | MinIO 번들 | 사용자 로컬 런타임 |
| **MCP server** | 실행형 프로세스 또는 원격 엔드포인트 | 설치 또는 **연결** | 번들 또는 없음 | 로컬 실행 환경 또는 제공 서버 |
| **Hosted agent** | **팀 서버가 띄워둔 서비스** | **접근 권한 부여** | 없음 (엔드포인트만) | **제공 팀의 서버 가동 상태** |

세 번째가 아키텍처에 주는 충격이 가장 크다.

| Skill/설치형과 다른 점 | 결과 |
|---|---|
| 설치 시점에 사용자 손으로 넘어가지 않는다 | 레지스트리가 **런타임 상태를 알아야 한다** — 살아있는가, 응답하는가 |
| 아티팩트가 없다 | 불변성·서명 모델이 적용되지 않는다. 대신 **엔드포인트 계약과 가용성 약속**이 심사 대상 |
| 제공 팀이 서버를 내리면 즉시 깨진다 | 폐기가 **파괴적 행위**다. 유예기간·사전 통보가 절차가 아니라 요구사항 |
| 호출이 제공 팀 서버를 통과한다 | **호출을 실제로 계량할 수 있다.** 자산 종류별 계측 범위는 §10 이 단독으로 정의한다 |

카탈로그 스키마는 셋을 하나로 담는다 — MCP `server.json` 이 이미 `packages[]`(설치형)와 `remotes[]`(원격형)를 나란히 두고 있어 구조를 그대로 쓴다.

### 2-1. 런타임 중립성

런타임이 여러 개이므로 **카탈로그는 런타임 중립**으로 두고, 런타임별 차이는 배포 표면(L6)의 어댑터로 흡수한다.

```
        [ 카탈로그 — 런타임 중립 정규화 문서 ]
                        │
     ┌──────────────────┼──────────────────┐
     ▼                  ▼                  ▼
 marketplace.json   generic API        (추가 런타임)
 어댑터             `/v0.1/servers`     어댑터
     │                  │
 Claude Code        OSS 런타임 / 자체 클라이언트
```

- 문서는 `runtimes[]` 로 **호환 런타임을 선언**한다. 선언하지 않은 런타임에서는 검색 결과에 노출하지 않는다.
- 어댑터는 **읽기 전용 투영(projection)** 이다. 카탈로그가 진실이고 어댑터는 표현이다. 새 런타임 지원 = 어댑터 1개 추가이지 스키마 변경이 아니다.

### 3. 소프트웨어 계층

| # | 계층 | 책임 | 구현 |
|---|---|---|---|
| L1 | **Artifact Store** | 번들 `tar.gz`, 서명, SBOM. 발행 버전은 불변 | MinIO — 버킷 생성 시 versioning + Object Lock 활성화. 발행 시 **GOVERNANCE 모드** 리텐션 부여(우회에 별도 권한 필요), 보안 사고 대응 여지를 남긴다 |
| L2 | **Catalog** | 매니페스트 정규화 문서, 버전 이력, 소유권 튜플, 심사·승격 상태 | MongoDB — 컬렉션별 `$jsonSchema` validator, `validationAction: error` |
| L3 | **Search Index** | 전문 검색, 패싯, 랭킹 | OpenSearch — 카탈로그 변경을 Redis 큐 경유로 비동기 색인 |
| L4 | **API** | 레지스트리 REST. 발행·조회·상태전이·승격 | FastAPI — 계약이 곧 OpenAPI 이고 MCP 레지스트리도 `openapi.yaml` 을 규격으로 배포한다. Flask 는 이 계약을 손으로 유지해야 해서 탈락 |
| L5 | **Auth** | 사내 SSO, M2M 토큰, 네임스페이스 소유권 판정 | 공통 사내 IdP(OIDC) + 인스턴스별 Resource Server. RFC 9068 `at+jwt` |
| L6 | **Distribution** | 런타임별 배포 표면 | 어댑터 구조(§2-1). Claude Code 는 `marketplace.json` 동적 생성, 그 외는 generic API. 아티팩트는 MinIO presigned URL |
| L6b | **Endpoint Broker** | hosted agent 접근 중개 | 엔드포인트 카탈로그, 헬스체크, 접근 토큰 발급·만료, 호출 계량 |
| L7 | **Cache / Queue** | 카탈로그 캐시, 레이트리밋, 스캔·색인 잡 | Redis — 레이트리밋은 `INCR` + `EXPIRE` 를 Lua 로 원자화 |
| L8 | **Observability** | 사용량·지연·에러·비용 | OTel SDK → Collector → Data Prepper → OpenSearch |
| L9 | **Federation** | 전사 인스턴스와의 동기화 | 승격 결정은 push, 데이터 정합은 pull |
| L10 | **Governance** | 심사 게이트, 서명·검증, 등급 | 발행 파이프라인의 차단 게이트. cosign 자체 키 + in-toto/SLSA |

L1~L10 은 **하나의 FastAPI 애플리케이션 + 하나의 워커**로 구현한다. 초기부터 마이크로서비스로 쪼개지 않는다 — 인스턴스가 이미 N개로 늘어나는 구조라 서비스 수까지 곱하면 운영 부하가 N×M 이 된다.

### 4. 프로세스 구성 (인스턴스 1개당)

| 프로세스 | 역할 | 비고 |
|---|---|---|
| `registry-api` | FastAPI (uvicorn), 무상태 | 수평 확장 대상 |
| `registry-worker` | 색인, 보안 스캔, 서명 검증, 승격 동기화 | Redis 큐 소비 |
| `registry-scheduler` | 주기 작업(폴링, 리텐션, 통계 롤업) | 단일 인스턴스 |
| MongoDB / Redis / OpenSearch / MinIO | 사내 공용 또는 인스턴스 전용 | §11 참조 |

## 어떻게 사용하는가? (How)

### 5. 데이터 모델

카탈로그 문서 스키마는 **MCP `server.json` 을 확장**한다. 새로 발명하지 않는 이유: 클라이언트가 표준 인터페이스로 소비할 수 있고, 확장 지점(`_meta`, `/x/` 경로)이 이미 규격에 있다.

#### 5.1 `agents` 컬렉션 (버전별 1문서)

```jsonc
{
  "$schema": "https://registry.<사내도메인>/schemas/2026-09-03/agent.schema.json",
  "name": "kr.co.skhynix.<biz>.<team_id>/<agent-name>",   // 불변. 팀명 아님
  "title": "웨이퍼 결함 요약 에이전트",                      // 가변 표시명
  "description": "...",
  "version": "1.4.2",                                     // 범위 표기 금지
  "kind": "skill | mcp-server | hosted-agent",
  "runtimes": ["claude-code", "oss-runtime-x"],           // 호환 런타임 선언
  "packages": [{                                          // 설치형만
    "registryType": "internal-minio",
    "identifier": "s3://agents/<biz>/<name>/1.4.2/bundle.tar.gz",
    "fileSha256": "…"                                     // 필수로 승격
  }],
  "remotes": [{                                           // hosted agent / 원격 MCP
    "type": "streamable-http",
    "url": "https://agent-x.<team>.<사내>/mcp",
    "operatedBy": "T-004821",                             // 운영 책임 팀 (불변 ID)
    "sla": { "availability": "0.995", "p95LatencyMs": 3000 },  // NFR 최소치 미만은 등록 차단
    "healthUrl": "https://agent-x.<team>.<사내>/health"
  }],
  "_meta": {
    "kr.co.skhynix.registry/official": {
      "status": "active | deprecated | deleted",
      "statusChangedAt": "…", "publishedAt": "…", "isLatest": true,
      "ownerTeamId": "T-004821",                          // 불변 조직 ID
      "bizId": "BIZ-DRAM",
      "tier": "experimental | verified | official",
      "reviewStatus": "pending | approved | rejected",
      "promotion": { "state": "none | requested | promoted", "upstreamName": null }
    },
    "kr.co.skhynix.registry/publisher-provided": { }      // 발행자 자유 필드, 4KB 상한
  }
}
```

**불변 규칙:** 발행된 문서에서 변할 수 있는 것은 `status` 계열과 `_meta` 의 심사·승격 필드뿐이다. `name`/`version`/`fileSha256` 이 바뀌면 그것은 새 버전이다. 이 규칙이 있어야 상위 인스턴스의 증분 폴링이 성립한다.

#### 5.2 소유권 — 이름이 아니라 관계로

**ReBAC(관계 기반) 을 뼈대로, 만료만 조건(ABAC)으로 얹는다.** Google 이 Zanzibar 로 관계를, IAM Conditions 로 조건을 처리하는 것과 같은 층위 구성이다.

```jsonc
// ownership 컬렉션 — 튜플 하나의 형태
{ "resource": "agent:kr.co.skhynix.dram.T-004821/defect-summarizer",
  "relation": "owner",              // owner | maintainer | reviewer | member | admin | guest
  "subject":  "user:E123456",       // user:<empno> | team:<team_id>#member
  "grantedAt": "…", "grantedBy": "user:E999999",
  "expiresAt": null }               // null=무기한. 값이 있으면 판정 시 비교 (조건 층)
```

| namespace | object id | 관계 |
|---|---|---|
| `agent:` | `kr.co.skhynix.<biz>.<team_id>/<name>` | `owner`, `maintainer`, `reviewer` |
| `team:` | `T-004821` (레지스트리 발급) | `member`, `admin` |
| `user:` | `E123456` (**empno**) | (subject 전용) |
| `biz:` | `BIZ-DRAM` | `guest` |

**파생 규칙** — Zanzibar 의 userset rewrite 에 해당하지만, 우리는 **코드 상수 몇 줄**로 충분하다. 설정 언어를 만들 이유가 없다.

```
owner      ⊂ maintainer ⊂ reviewer          # 상위가 하위를 포함
maintainer ⊃ team:<소유팀>#member            # 소유 팀 멤버는 자동 maintainer
```

핵심은 **subject 자리에 집합을 넣을 수 있다**는 것이다. `@team:T-004821#member` 튜플 1건이 팀원 전원을 커버하므로, 사람이 들고나도 에이전트 쪽 튜플은 움직이지 않는다.

> **절대 규칙: 튜플의 subject 에 표시명·이메일을 넣지 않는다.** Google 은 Directory API 문서에서 "그룹 이메일을 영속 데이터의 키로 쓰지 말라"고 하면서, 정작 Cloud IAM 은 principal 을 `group:EMAIL` 로 바인딩한다 — 자사 제품 안의 모순이다. 우리는 그 함정을 처음부터 만들지 않는다.

**엔진을 도입하지 않는다 (확정).** 가져오는 것은 *데이터 모양* 하나뿐이고, 운영 컴포넌트는 늘리지 않는다. SpiceDB·OpenFGA·Ory Keto 는 모두 Apache-2.0 에 폐쇄망 자체 호스팅이 되지만, 셋 다 **우리에게 없는 관계형 DB** 를 요구한다. 그리고 규모가 맞지 않는다 — Zanzibar 논문의 **네임스페이스당 튜플 중앙값은 약 15,000건**이고, 우리 레지스트리 전체가 대략 그 한 개 네임스페이스 크기다. 2조 튜플은 1,500개 네임스페이스의 합계다.

| 재검토 트리거 | 값 |
|---|---|
| 튜플 수 | 100만 건 |
| 관계 그래프 깊이 | 3 이상 |
| 인가 판정 QPS | 1,000 |

셋 중 하나라도 넘으면 전용 엔진을 다시 검토한다. 그때 이전 비용은 **스키마 변환 스크립트 1개**이므로 지금 미루는 데 드는 비용이 없다.

#### 5.3 조직 — 불변 ID와 가변 표시명의 분리

**팀을 "조직"이 아니라 "그룹 리소스"로 모델링한다.** 팀은 *사번의 집합*이고, 그 집합에 레지스트리가 발급한 자체 식별자가 붙는다. 이렇게 두면 불변 조직 코드가 없어도 — 있는지 몰라도 — 모델이 성립한다.

```jsonc
// teams 컬렉션 — 조직이 아니라 그룹
{ "teamId": "T-004821",                    // 레지스트리 자체 발급. 불변
  "displayName": "AI솔루션2팀",             // 매년 바뀜
  "bizId": "BIZ-DRAM",
  "members": ["E123456", "E234567"],       // empno 집합. 사원 마스터에서 자동 동기화 (§5.4)
  "observedOrgCode": "ORG-77Q",            // 마스터가 준 팀 코드명. 관측값이지 식별자가 아니다
  "observedOrgName": "AI솔루션2팀",
  "history": [ { "displayName": "AI기술팀", "from": "2025-01-01", "to": "2025-12-31" } ],
  "status": "active | merged | dissolved",
  "successorTeamId": null }                // 병합·해체 시 승계 대상
```

| 케이스 | 무엇이 바뀌는가 |
|---|---|
| 팀명 변경 | `displayName` 1건. 소유권·자산 문서는 손대지 않음 |
| 사원의 팀 이동 | `members` 배열에서 이동. **정책은 그대로** |
| 팀 병합 | `members` 합치고 `successorTeamId` 설정 |
| 조직 코드가 바뀜 | `observedOrgCode` 갱신. `teamId` 는 불변 |

**`observedOrgCode` 는 식별자가 아니라 관측값이다.** 마스터가 팀 코드명을 주긴 하지만 그것이 매년 불변인지는 확인할 수 없다(G9). 확인 못 한 것을 식별자로 쓰면, 그게 바뀌는 해에 소유권이 통째로 끊긴다. 그래서 레지스트리는 자기 `teamId` 를 쥐고 외부 코드는 **관측 기록**으로만 둔다.

### 5.4 조직 동기화 (Org Sync)

`empno` → 이름·소속팀·팀 코드명 조회 API 가 있고 Redis 에 저장돼 있으므로(G10), 팀 멤버십은 **손으로 관리하지 않는다.**

**동기화 주기는 1일 1회.** 조직 개편 반영이 하루 늦어도 무방하다는 것이 확정 전제다. 이 값이 설계를 크게 단순화한다 — 실시간 동기화도, 변경 이벤트 구독도, 캐시 무효화 전략도 필요 없다. 야간 배치 1개면 된다.

```
사원 마스터 조회 API ──(1일 1회 배치)──▶ Redis ──▶ Org Sync 워커
                                                    │
                                          ┌─────────┴─────────┐
                                          ▼                   ▼
                                   teams.members 갱신    변화 감지 → 리포트
```

**조직 개편을 자동으로 감지하는 방법.** 우리에게는 팀마다 **멤버 집합**이 있으므로, 동기화 시점 간 집합을 비교하면 무슨 일이 일어났는지 추론할 수 있다.

| 관측 | 해석 | 처리 |
|---|---|---|
| 코드 동일, 이름만 변경 | 단순 rename | `displayName` 갱신. 자동 |
| 코드 변경, 멤버 집합 **대부분 일치** | 같은 팀의 코드 변경 | 기존 `teamId` 유지, `observedOrgCode` 갱신. 자동 |
| 한 팀의 멤버가 **여러 팀으로 분산** | 분할(split) | **사람 판단 필요.** 자산 소유권을 어디로 보낼지 결정 |
| 여러 팀의 멤버가 **한 팀으로 수렴** | 병합(merge) | `successorTeamId` 설정 제안 후 승인 |
| 팀 소멸, 멤버가 흩어짐 | 해체 | 자산이 무주공산 → §7.2 원작성자 경로로 승계 시도 |

자동으로 처리할 것과 사람이 봐야 할 것을 이 표가 가른다. **rename 과 코드 변경은 자동, 분할·병합·해체는 승인 절차**로 보낸다 — 전자는 정보 손실이 없고 후자는 결정이 필요하기 때문이다.

동기화 실패 시에는 **마지막으로 성공한 스냅샷을 유지**한다. 조회 API 장애가 곧 권한 상실이 되면 안 된다. 하루 주기이므로 **연속 실패 3일**을 경보 임계로 둔다.

> **하루의 권한 공백을 감수한다는 뜻이다.** 팀을 옮긴 사원은 최대 하루 동안 이전 팀 권한을 유지한다. 이걸 좁히려면 발행·승격 같은 **쓰기 동작 직전에만** 마스터를 직접 조회하는 예외를 두면 된다 — 읽기는 하루 지연을 허용하고 쓰기만 실시간으로 확인하는 비대칭이 비용 대비 효과가 가장 좋다.

| 컬렉션 | 주요 인덱스 |
|---|---|
| `agents` | `{name:1, version:1}` unique, `{_meta…ownerTeamId:1}`, `{_meta…updatedAt:1}` (증분 폴링용) |
| `ownership` | `{resource:1, subject:1, relation:1}` unique |
| `teams` | `{teamId:1}` unique, `{displayName:1}` (검색용, unique 아님) |
| `audit` | `{at:1}` TTL 없음(감사 보존), `{actor:1}` |

### 6. 식별자 체계 — 매년 바뀌는 팀명 대응

| 원칙 | 구현 | 반례에서 배운 것 |
|---|---|---|
| 네임스페이스에 **`team_id`** 를 넣고 팀명은 절대 넣지 않는다 | `kr.co.skhynix.<biz>.<team_id>/<agent>` | npm 은 스코프=조직명이라 rename 시 **전 패키지 재발행**을 요구한다 |
| 식별자와 표시명을 스키마에서 분리 | `name`(불변) vs `title`·`displayName`(가변) | MCP `server.json` 이 같은 분리를 한다 |
| 소유권은 롤/관계 배정 | §5.2 튜플 | PyPI 의 조직 롤/프로젝트 롤 분리 |
| 이름 변경 경로가 필요하면 **rename map** 을 카탈로그가 제공 | `GET /v0.1/x/kr.co.skhynix/renames` | Claude Code marketplace 의 `renames` 필드 |

**`team_id` 는 레지스트리가 자체 발급한다.** 사내 조직 코드의 존재 여부에 **의존하지 않는다** (G9). 확인이 안 되는 것에 설계를 걸지 않는다는 뜻이다 — 나중에 조직 코드가 있다고 밝혀지면 `teams.externalOrgCode` 라는 **선택적 참조 필드**로 붙기만 하고, 식별자 체계와 소유권 모델은 그대로다.

### 7. 인증·인가

#### 7.1 원칙

인스턴스가 서로를 신뢰하는 구조(레지스트리↔레지스트리 신뢰)는 **표준이 없다.** 대신 표준 경로는 **공통 IdP 하나를 두고 각 인스턴스를 별개의 Resource Server 로 만드는 것**이다.

```
사용자 ──OIDC 로그인──▶ 사내 IdP
                          │  resource=https://registry-b.<사내>  (RFC 8707)
                          ▼
                     access token (aud = registry-b)
                          │
사용자 ──────────────────▶ Biz-B 인스턴스  ── aud 가 자기 자신인지 검증
```

- 토큰의 `aud` 가 **자기 자신이 아니면 거부**한다. 토큰 패스스루는 금지(MCP 스펙상 MUST NOT).
- 인스턴스가 다른 인스턴스를 사용자 대신 호출할 때는 **RFC 8693 token exchange** 로 `act` 클레임이 남는 위임(delegation)을 쓴다. 사칭(impersonation)이 아니라 위임이어야 감사와 사용량 귀속이 성립한다.

#### 7.2 신원 — 사원 마스터가 단일 진실 원천

사내 IdP 의 subject identifier 는 **public** 이다. Biz-A 인스턴스와 Biz-B 인스턴스가 **같은 사원을 같은 `sub` 로 본다** — 인스턴스가 N개로 쪼개져도 신원 판정이 성립한다. 여기에 전 사원 ID·이름이 담긴 **단일 마스터 테이블**이 있으므로:

| 규칙 | 이유 |
|---|---|
| 레지스트리는 **사용자 정보를 소유하지 않는다** | 표시명·소속은 조회 시 마스터에서 가져온다. 복제하면 그 순간부터 낡는다 |
| 저장하는 것은 **사원 ID 뿐** | 감사 로그·소유권 튜플·텔레메트리 모두 ID 만 남긴다 |
| 사원 ID 는 **불변** | 팀이 해체돼도 "누가 만들었는가"는 끊기지 않는다 → 무주공산 자산의 승계 단서 (§5.3) |

**조직 개편에서 실제로 쓰이는 방식:** 팀 소유권이 끊긴 자산은 `teams.successorTeamId` 를 먼저 따라가고, 그것도 없으면 **원작성자 사원 ID → 마스터에서 조회한 현 소속 팀**으로 승계를 시도한다. 사원 ID 가 불변이라서 이 경로가 성립한다.

#### 7.3 크로스-Biz 접근 3경로

| 경로 | 방식 | 비고 |
|---|---|---|
| A. 전사 경유(기본) | 승격된 에이전트를 2차에서 설치 | 신뢰 관계 N개로 유지 |
| B. 게스트 읽기 | 타 Biz 사용자가 카탈로그만 조회. 아티팩트 다운로드 불가 | 노출 범위를 문서가 `visibility: biz \| cross-biz` 로 선언 |
| C. 명시적 allowlist | Biz-A 인스턴스가 Biz-B 를 명시적으로 허용 | **비전이.** A가 B를 믿어도 B가 믿는 C로 전이되지 않는다. 만료·재승인 필요 |

클라이언트 측에도 같은 모델이 이미 있다 — Claude Code 는 `allowCrossMarketplaceDependenciesOn` allowlist 없이는 마켓플레이스 간 설치를 거부하고, 그 신뢰는 체이닝되지 않는다.

### 8. 발행 파이프라인

```
업로드 → ①매니페스트 검증 → ②정적 스캔 → ③서명 → ④MinIO 커밋(Object Lock)
        → ⑤카탈로그 등록(status=pending) → ⑥사람 심사 → ⑦active + 색인
```

| 단계 | 차단 조건 |
|---|---|
| ① 매니페스트 | `SKILL.md` frontmatter 필수 필드(`name` ≤64 `[a-z0-9-]`, `description` ≤1024) 위반, 예약어(`anthropic`/`claude`), 버전 범위 표기 |
| ② 정적 스캔 | 자격증명 하드코딩, 외부 네트워크 호출, 셸·파일시스템 접근 범위 |
| ③ 서명 | cosign 자체 키. in-toto Statement + SLSA Provenance predicate 를 함께 저장 |
| ⑥ 심사 | 등급별 강도. 판정 기준과 SLA 는 [03-operations.md](./03-operations.md) |

⑤ 이후 문서는 불변이다. 심사 결과는 `_meta` 의 상태 전이로만 반영한다.

**Hosted agent 는 이 파이프라인을 타지 않는다.** 아티팩트가 없으므로 ②③④가 성립하지 않는다. 대신 별도 게이트를 거친다.

| 단계 | 검사 |
|---|---|
| ① 엔드포인트 계약 | `remotes[]` 필수 필드, `healthUrl` 응답 확인 |
| ② 엔드포인트 보안 | TLS, 인증 요구 여부, 사내망 범위, 데이터 취급 범위 |
| ③ 가용성 약속 | `sla` 선언값과 운영 책임 팀(`operatedBy`) 확인 |
| ④ 등록 | 헬스체크 스케줄 등록(5분 간격). **연속 6회 실패 시 자동 `degraded`** — 아래 참조 |

설치형이 "무엇이 배포되는가"를 심사한다면, hosted agent 는 **"누가 무엇을 계속 책임지는가"** 를 심사한다.

**헬스체크 실패 시 — 되돌릴 수 있는 것만 자동화한다.**

| | 동작 |
|---|---|
| **자동** | `status` → `degraded`. **신규 접근 부여·신규 연결 차단**, 소유 팀 통보, 검색 순위 하락 + 경고 배지. 기존 사용자는 유지 |
| **자동 복구** | 헬스체크 회복 시 `degraded` 자동 해제 |
| **사람 결정** | 등급(tier) 강등, 폐기 전환. **자동 강등은 하지 않는다** |

등급은 심사의 결과물이지 가동률의 함수가 아니다. 가동률로 등급을 자동으로 내리면 일시적 장애가 심사 이력을 지운다.

### 9. 승격 (1차 → 2차)

**결정은 push, 데이터는 pull.** 어느 1차 자료도 downstream→upstream push 연합을 표준화하지 않았다(전부 pull). 그래서 두 방향을 나눈다.

```
Biz 인스턴스 ──POST /v0.1/x/kr.co.skhynix/promote──▶ 전사   (승격 신청 = 이벤트)
전사 ──GET /v0.1/servers?updated_since=<RFC3339>──▶ Biz     (메타데이터 = 증분 폴링)
전사 ──GET presigned URL, 최초 요청 시에만───────▶ Biz MinIO (아티팩트 = lazy copy)
```

- **아티팩트 사전 전량 미러링은 하지 않는다.** Artifactory 가 remote repository 에 대해 명시적으로 그렇게 한다("not pre-fetched… only fetched and stored on demand"). 첫 설치 요청 시 전사 MinIO 로 복사하고 이후는 로컬에서 서빙한다 — Biz 인스턴스 장애에도 이미 쓰이는 에이전트는 살아남는다.
- `updated_since` 를 쓰면 삭제분(`include_deleted`)이 자동으로 따라오므로 폐기 전파가 공짜로 된다.
- 폴링 주기는 **시간 단위**로 충분하다. 승격은 실시간성이 필요 없는 이벤트다.

**아티팩트는 lazy copy 로 확정한다** (D6, Q4 종결). 승격 승인 시점에 일어나는 것은 **메타데이터 등록과 복사 권한·경로 준비**이고, 실제 바이트 복사는 2차 플랫폼이 **최초 설치 요청을 받을 때** 일어난다. 운영 문서의 "승인 후 N영업일" SLA 는 전자를 가리킨다.

**남은 미결은 상태 전파다** — 원본이 deprecated 되면 승격본은 어떻게 되는가 → [Q5](#열린-질문).

### 10. 텔레메트리

```
에이전트 런타임 ──OTLP──▶ OTel Collector ──▶ Data Prepper ──▶ OpenSearch
                                              (otel_trace_source)   (otel-v1-apm-span)
```

- 속성은 OTel **GenAI semantic conventions** 의 `gen_ai.*` 를 쓴다. `gen_ai.agent.id` 가 "unique and stable identifier" 로 정의돼 있어 §6 의 불변 ID 가 그대로 들어간다.
- **팀/소유자 속성은 표준에 없다.** `skhynix.team_id`, `skhynix.biz_id`, `skhynix.agent_version` 을 커스텀 속성으로 추가한다.
- 보존은 OpenSearch ISM 정책으로. 원시 스팬은 단기, 승격 판정용 집계는 장기로 롤업한다.

**계측 가능성이 자산 종류마다 다르다.** 이것이 §2 분류가 실제로 중요한 이유다.

| 종류 | 볼 수 있는 것 | 방법 |
|---|---|---|
| **Hosted agent** | **호출 수·지연·에러·사용자** 전부 | 제공 팀 서버가 OTLP 를 내보낸다. 안 내보내면 Endpoint Broker(L6b)가 중개하며 계량한다 |
| **MCP server (원격)** | 연결·호출 수·사용자 | 동일하게 Broker 를 경유한다 |
| MCP server (설치형) | 설치 시점까지만 | 아래 Skill 과 같다 |
| Skill / 설치형 | **설치 시점까지만** | Anthropic 은 "Usage analytics are not currently available through the Skills API" 라고 명시한다. 런타임이 OTLP 를 내보내지 않으면 실행은 보이지 않는다 |

**즉 Broker 를 경유하는 것(hosted agent, 원격 MCP server)은 계량되고, 사용자 손으로 넘어가는 것(Skill, 설치형 MCP server)은 설치까지만 보인다.** 따라서 승격 지표를 종류별로 다르게 잡는다 — 경유형은 실제 호출량으로, 설치형은 **설치 수 + 사내 LLM 게이트웨이 호출 수**로 판정한다. 오픈소스 런타임은 계측 훅을 넣을 수 있으므로, 사내 배포 런타임에 OTLP exporter 를 기본 탑재하는 것이 설치형 계측의 유일한 현실적 경로다 → [Q9](#열린-질문).

### 11. 버전 파편화 대응 (인스턴스가 N개이므로)

인스턴스마다 배포 시점이 다르다는 전제에서 **처음부터** 넣어야 하는 것들이다. 나중에 넣으면 이미 갈라진 뒤다.

| 규율 | 방법 |
|---|---|
| 문서 스키마 버전 | 문서마다 **날짜 스탬프 `$schema` URL** 을 박는다 |
| API 버전 | 안정 `/v0.1` 과 개발 `/v0` 분리, 안정 경로는 **additive-only** |
| 확장 | reverse-DNS 격리(`/v0.1/x/kr.co.skhynix/...`), 소비자는 **확장 부재를 정상 처리해야 한다** |
| 데이터 | 발행 메타데이터 불변, 버전 범위 표기 금지 |

## 결정 요약

| ID | 결정 | 근거 |
|---|---|---|
| D1 | 카탈로그 스키마는 MCP `server.json` 확장 | 표준 클라이언트 소비 가능, 확장 지점이 규격에 있음 |
| D2 | 아티팩트는 **직접 호스팅**(MCP 와 의도적 분기) | MinIO 가 있고 폐쇄망이므로 외부 패키지 레지스트리 참조가 불가 |
| D3 | API 는 FastAPI | 계약=OpenAPI, 스펙 파일 수기 유지 불필요 |
| D4 | 단일 앱 + 워커 (마이크로서비스 아님) | 인스턴스가 이미 N개. 서비스 수까지 곱하지 않는다 |
| D5 | 인스턴스 관계는 N-to-1 기본 | 신뢰가 비전이라 N-to-N 은 N² 운영 부담 |
| D6 | 승격은 push(결정) + pull(데이터) + lazy copy(아티팩트) | push 연합 표준 부재, 사전 미러링은 어느 자료도 지지하지 않음 |
| D7 | 소유권은 관계 튜플 | 조직 개편이 튜플 갱신 1건으로 끝남 |
| D8 | Object Lock 은 GOVERNANCE 모드 | COMPLIANCE 는 root 도 삭제 불가 — 보안 사고 시 회수 불가능해짐 |
| D9 | 카탈로그는 **런타임 중립**, 런타임 차이는 어댑터로 | 오픈소스 런타임 포함 다수 공존. 새 런타임 = 어댑터 1개 |
| D10 | 자산을 **3종(Skill / MCP server / hosted agent)** 으로 나누고 배포·심사·폐기 경로를 분리 | 셋의 배포 행위가 근본적으로 다름. `server.json` 의 `packages[]`/`remotes[]` 구조를 그대로 사용 |
| D11 | hosted agent 는 **Endpoint Broker(L6b)** 를 경유 | 계량·접근제어·헬스체크가 한 지점에 모임. 승격 판정의 유일한 확실한 데이터 원천 |
| D12 | 사용자 정보는 **사원 마스터에서 조회**, 레지스트리는 ID 만 저장 | 복제하면 낡는다. 사원 ID 불변성이 조직 개편 승계의 단서 |
| D13 | 팀은 **조직이 아니라 `empno` 집합을 멤버로 갖는 그룹 리소스**. `team_id` 는 레지스트리 자체 발급 | 조직 코드의 불변성을 **확인할 수 없으므로** 의존하지 않는다. 외부 코드는 관측값으로만 보관 |
| D14 | 팀 멤버십은 사원 마스터에서 **자동 동기화**. 멤버십 관리 UI 를 만들지 않는다 | 조회 API 가 있으므로 손으로 관리할 이유가 없다. 개편 감지는 **멤버 집합 비교**로 추론하고, rename·코드변경은 자동, 분할·병합·해체만 승인으로 보낸다 |
| D15 | 인가는 **ReBAC 튜플 + 만료 조건**. 전용 엔진(SpiceDB/OpenFGA) 대신 **MongoDB 튜플 컬렉션** | Zanzibar 네임스페이스당 튜플 중앙값 약 1.5만 건 — 우리 전체가 그 한 개 크기. 엔진 셋 다 우리에게 없는 관계형 DB 를 요구한다. 재검토 트리거를 미리 정해둔다 |
| D17 | 조직 동기화는 **1일 1회 야간 배치** | 하루 지연 허용이 확정. 실시간 동기화·이벤트 구독·캐시 무효화가 전부 불필요해진다. 쓰기 동작 직전에만 실시간 조회 |
| D16 | 팀 병합 시 에이전트 튜플을 **건드리지 않고** `successorTeamId` 를 **1홉만** 따라간다 | Google 이 "그룹의 롤을 회수하고 최소 7일 기다린 뒤 삭제하라"고 경고하는 것과 같은 이유 — 즉시 없애면 회복이 불가능하다. 2홉 이상은 정리 대상으로 경보 |
